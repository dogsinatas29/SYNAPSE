## 1. Executive Summary & Purpose

Phase 2.5 소스 감사에서 확인된 핵심 결함은 특정 분석기 하나의 버그가 아니라, **수집(Ingestion)부터 최종 보고서(Report) 생성에 이르기까지 파이프라인의 5대 경계에서 데이터 계약이 파편화되어 발생한 구조적 문제**이다.

본 마스터 플랜의 궁극적 목표는 **단일 분석 데이터 계약(Single Analysis Data Contract)**을 확립하여 다음 5대 조건을 수학적·구조적으로 보장하는 것이다:
1. **수집 경계:** 애플리케이션 분석 대상($V_{\text{app}}$)과 빌드·인프라 노드($V_{\text{build}}$)가 물리적으로 완전 분리된다.
2. **간선 무결성:** 분석 대상 그래프의 모든 간선 양 끝점이 분석 대상 노드 집합에 온전히 존재한다 ($\forall e \in E_{\text{target}}, \text{endpoints} \in V_{\text{target}}$).
3. **클러스터 무결성:** 노드 투영 이후 클러스터 멤버십과 노드의 소속이 100% 일치한다.
4. **분석 경로 통일:** 모든 외부 진입점(UI, CLI, 이벤트 핸들러)이 우회 없이 동일한 단일 투영 관문 계약을 준수한다.
5. **보고서 계보 일관성:** 분석 결과와 최종 보고서가 동일한 입력 상태 및 검증된 증거 계보(`findingId` $\rightarrow$ `evidenceId` $\rightarrow$ `reportSection`)를 공유한다.

## 3. Five-Stage Dependency Precedence Chain (선행조건 적용 순서)

Track A의 5개 계층은 엄격한 단방향 인과관계를 가지며, **앞선 계층의 계약과 증거가 확보되기 전에는 하위 계층을 착수하거나 고정할 수 없다.**
하위 계층의 임시방편(보고서 텍스트 억제, 분석기 내부 필터 등)으로 상위 계층의 결함을 은폐하는 것은 전면 금지된다.

## 4. Phase 3 Gates & Exit Criteria (게이트별 필수 증거)

각 단계(P3-1 ~ P3-5)는 독립적인 Gate를 통과해야만 다음 단계의 공식 구현으로 승격될 수 있다.

| Gate | 판정 대상 | 필수 통과 조건 (Invariants) | 필요 증거 수준 (Required Evidence) |
| :--- | :--- | :--- | :--- |
| **Gate 3.1** | **Ingestion Boundary** | $V_{\text{build}} \cap V_{\text{app}} = \varnothing$, 분류 불명 노드의 `RUNTIME` 편입 차단 | 소스 레벨 분류기 인터셉터 코드 + 노드 카탈로그 전수 검사 |
| **Gate 3.2** | **Edge Integrity** | Dangling Edge = 0, 유효 간선 손실 = 0 ($E_{\text{valid}}^{B} \subseteq E_{\text{valid}}^{A}$) | 런타임 RustDesk 기준선 1:1 차분 튜플 매칭 증거 패키지 |
| **Gate 3.3** | **Cluster Integrity** | $\forall n \in C.\text{nodes}, n \in V_{\text{target}}$, 빈 클러스터 정리 완료 | 클러스터 멤버십 전수 대조 로그 + 고아 클러스터 0건 증거 |
| **Gate 3.4** | **Path Unification** | 모든 외부 진입점(제품 6개, CLI 2개)의 단일 투영 관문 경유 | 진입점별 콜스택 트레이스 + 우회 경로 0건 감사 보고서 |
| **Gate 3.5** | **Report Lineage** | 보고서 입력 출처 단일화, 원본 직접 파싱 0건, 증거 튜플 일치 | 산출물 해시 대조 + `simulation_evidence` 입력 계보 증거 |

### 4.1 Gate 판정의 4대 필수 증거 요건
단순히 "코드가 작성되었다"는 사실은 증거로 인정하지 않는다. 모든 Gate는 다음 4종의 증거가 동시에 제출되어야 승인된다:
1. **Specification:** 무엇을 보장하는가 (수학적 불변식 및 인터페이스 타입 계약).
2. **Implementation Evidence:** 실제 소스 코드가 계약을 엄격히 구현하였는가 (정밀 Diff).
3. **Test Evidence:** 어떤 기준선과 경계 조건으로 검증하였는가 (재현 가능한 차분 결과).
4. **Independent Audit:** 제3자 관점에서 회귀 및 잠재적 부작용이 배제되었는가 (거버넌스 검토).
