# v0.3.10 Spec --- Architectural Decoupling & Multi-Rule Engines

## 1. Goal

Decouple canvas-engine into independent rule engines (Visual / Spatial /
Logic) to enforce deterministic behavior, reduce cognitive load, and
eliminate inconsistency.

------------------------------------------------------------------------

## 2. Core Architecture

### Intent Pipeline (MANDATORY FLOW)

EventHandler → Intent → RuleEngine → StateManager → RenderEngine

All state changes MUST pass through this pipeline.

------------------------------------------------------------------------

## 3. Core Concepts

### 3.1 Intent (Single Source of Truth)

``` ts
type Intent =
  | { type: 'ADD_NODE'; payload: any }
  | { type: 'CONNECT_EDGE'; payload: any }
  | { type: 'MOVE_NODE'; payload: any };
```

------------------------------------------------------------------------

### 3.2 Rule Engines (Three Domains)

#### VisualRuleEngine

-   Enforces UI consistency
-   No rendering logic, only validation

#### SpatialRuleEngine

-   Enforces layout constraints
-   Deterministic rules only (no physics engines initially)

#### LogicRuleEngine (ValidationHarness)

-   Validates system integrity
-   Rejects invalid operations

------------------------------------------------------------------------

### 3.3 Rule Verdict

``` ts
type RuleVerdict = {
  allowed: boolean;
  reasons?: string[];
  severity?: 'info' | 'warn' | 'critical';
};
```

------------------------------------------------------------------------

### 3.4 RuleEngine (Compositor, NOT God Object)

``` ts
function judge(intent): FinalVerdict {
  return mergeVerdicts([
    visual.evaluate(intent),
    spatial.evaluate(intent),
    logic.evaluate(intent),
  ]);
}
```

Responsibilities: - Aggregate results ONLY - No rule logic inside

------------------------------------------------------------------------

## 4. State Management

### StateManager (PURE)

``` ts
apply(state, intent) => newState
```

Constraints: - No side effects - No rule validation - Fully
deterministic

------------------------------------------------------------------------

## 5. Render System

### RenderProtocol (STRICT SOURCE)

``` ts
export const RenderProtocol = Object.freeze({
  NODE: {
    BORDER_WIDTH: 2,
    FONT_SIZE: 12,
  },
});
```

Rules: - No hardcoded literals allowed - All visual values MUST come
from protocol

------------------------------------------------------------------------

## 6. Spatial Constraints (Minimal Deterministic Model)

``` ts
type SpatialConstraints = {
  minNodeDistance: number;
  edgeCurvature: (distance: number) => number;
  snapToGrid: (pos: Vec2) => Vec2;
};
```

------------------------------------------------------------------------

## 7. Guardrails

### 7.1 Hardcoded Literal Ban

-   Enforced via ESLint + CI

### 7.2 Validation Interceptor

EventHandler MUST NOT bypass RuleEngine.

### 7.3 Strict Immutability

-   Object.freeze on all rule definitions
-   Optional deepFreeze in dev mode

## 9. Execution Strategy

### Phase 1

-   Intent system
-   Basic ValidationHarness

### Phase 2

-   RuleEngine integration
-   Event → Intent conversion

### Phase 3

-   StateManager (pure)

### Phase 4

-   RenderProtocol enforcement

### Phase 5

-   Spatial rules (final step)

------------------------------------------------------------------------

## 10. Success Criteria

-   No state mutation outside StateManager
-   No rendering outside RenderEngine
-   No rule bypass possible
-   Full determinism (same input → same output)

------------------------------------------------------------------------

## 11. Non-Goals (v0.3.10)

-   No risk scoring system
-   No physics-based layout
-   No dynamic rule mutation

------------------------------------------------------------------------

## 12. Key Principle

System correctness is enforced by execution path, not developer
discipline.

All behavior must be: - Intent-driven - Rule-validated -
Protocol-constrained
