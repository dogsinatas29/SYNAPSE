## 🧠 상세 설계 및 로직 (시니어 엔지니어 보강안)
지금 설계된 "위에서 아래로 흐르는 중력(Layer Index)"은 훌륭하지만, 실제 복잡한 시스템을 통제하려면 예외와 유연함이 필요합니다. '망상'이 아닌 '작동하는 규격'을 위한 4대 보완점입니다.

### 1. 'Sidecar' 및 'Cross-cutting' 레이어 정의 (Layer 0 / Layer 99)
모든 노드가 순차적 수직 계층에만 속할 순 없습니다. Logger, Utility, Constants, Global Exception Handler 같은 공통 모듈은 모든 레이어(1~4)에서 호출될 수 있어야 합니다.
- **보강 제안**: 특정 레이어 인덱스를 `Shared(0)` 혹은 `Global(99)`로 지정하는 예외 규칙을 도입합니다.
- **효과**: `Layer 0` 혹은 명시된 유틸리티 레이어는 중력 법칙(Layer Gravity)의 검사를 통과하여 전역적인 접근을 허용합니다.

### 2. 'Escape Hatch' (예외 처리 규정)
현실 세계의 코딩에서는 때로 성능 병목이나 레거시 라이브러리의 한계 때문에 레이어 규칙을 깨야 할 순간이 옵니다. 이때 무조건 💀 VIOLATION만 띄우면 개발자는 툴 자체를 꺼버리게 됩니다.
- **보강 제안**: 코드 주석이나 설정을 통해 특정 엣지에 대해 **'Temporary Bypass'**를 허용하는 메커니즘을 명시해야 합니다. (예: `// @synapse-ignore: circular-dependency-checked`)
- **효과**: 아키텍처의 유연함을 제공하되, 무분별한 우회를 방지하기 위해 해당 엣지는 캔버스상에 노란색 경고 마커(Warning)로 렌더링되어 지속적인 감사를 받게 됩니다.

### 3. 'State'와 'Event'의 방향성 명시 (Command vs Event)
데이터베이스(Layer 4)에서 프론트엔드(Layer 1)로의 직접적인 Call은 금지되지만, **'Event'**나 'Pub/Sub' 형태의 간접 데이터 전달은 발생할 수 있습니다.
- **보강 제안**: 엣지의 타입을 `Command(Direct Call)`와 `Event(Indirect)`로 명확히 분리합니다.
- **효과**: 하위 레이어에서 상위 레이어로의 전파(역류)는 오직 `Event` 타입으로만 가능하며, 이 경우 `Event Bus` 노드를 필수적으로 경유하도록 흐름을 시각화하고 룰 엔진에 강제합니다.

### 4. CI/CD 파이프라인 연동 (Headless Mode)
VS Code 확장 프로그램으로서의 시각적 통제만 강조되어 있으나, 진정한 'Iron Guard'라면 빌드 단계에서부터 실패를 띄울 수 있어야 합니다.
- **보강 제안**: CLI 환경에서도 이 규칙을 차갑게 검사할 수 있는 `synapse-check` 같은 Headless 모드 로드맵을 확립합니다.
- **효과**: 캔버스를 열지 않아도 터미널(CI/CD)에서 아키텍처 위반을 잡아내어, 실질적인 '코드의 목줄' 역할을 수행합니다.

## 🏛️ LogicAnalyzer.ts: Layer Violation Detection Logic
실제 구동되는 '폭포수 규칙' 검증 알고리즘 명세입니다.

### 1. 전제 조건 (Input Data)
분석기는 다음 세 가지 데이터를 실시간으로 수신하여 검증을 시작합니다.
- **Node Metadata**: `{ id, layerIndex, type (Shared|Normal|Bridge) }`
- **Edge Data**: `{ sourceNodeId, targetNodeId, type (Call|Event) }`
- **Global Rules**: `Layer_Index_Policy` (예: `target.layer > source.layer`)

### 2. 단계별 검증 알고리즘 (The Iron Guard Pipeline)
모든 엣지는 생성/수정 시 다음 '4단계 검문소'를 통과해야 합니다.

- **Step 1: Shared Layer 통과 (The Ghost Pass)**
  - **로직**: `source.layer === 0` (Shared) 이거나 `target.layer === 0` 이면 무조건 PASS.
  - **이유**: 유틸리티나 공통 라이브러리는 중력의 법칙을 무시하고 어디든 흐를 수 있어야 합니다.
- **Step 2: 동일 레이어 허용 여부 (Intra-Layer Check)**
  - **로직**: `source.layer === target.layer` 인 경우.
  - **판단**: `Allow_Same_Layer_Call` 옵션에 따라 결정. (기본은 PASS지만, 클러스터 간 인터페이스 강제 모드에서는 VIOLATION 처리 가능)
- **Step 3: 중력 법칙 검증 (The Gravity Law)**
  - **로직**: `target.layer < source.layer` 인가? (하류에서 상류로 역행하는가?)
  - **결과**: `true`라면 즉시 CRITICAL VIOLATION (💀) 발생.
- **Step 4: 인터페이스(Bridge) 강제 검증 (The Gatekeeper)**
  - **로직**: 서로 다른 클러스터 간의 연결인데, `target.type`이 Bridge/Facade가 아닌가?
  - **결과**: `true`라면 아키텍처 오염으로 간주하고 WARNING.

### 3. 시각화 및 피드백 루프 (Output)
검증 결과에 따라 SYNAPSE 캔버스와 Antigravity 에디터에 다음과 같이 시각적 타격을 가합니다.

| 등급 | 상태 | 시각적 표현 | 비고 |
| :--- | :--- | :--- | :--- |
| **Normal** | ✅ Clear | Gruvbox Green (Solid) | 정상적인 의존성 흐름 |
| **Warning** | ⚠️ Warning | Gruvbox Yellow (Dash) | 인터페이스 미준수 (캡슐화 파괴) |
| **Critical** | 💀 Violation | Gruvbox Red (Bold Dot + 💀) | 레이어 역행 (스파게티 확정) |

### 4. 성능 최적화 (Debouncing)
타이핑 한 번마다 전체 그래프를 스캔하는 렌더링 렉을 방지하기 위한 구조입니다.
- **Surgical Scan**: 파일이 저장될 때, 해당 파일과 연결된 Edge들만 부분적으로 재검증합니다.
- **Async Worker**: 검증 로직은 메인 UI 스레드가 아닌 웹 워커(Web Worker)에서 비동기로 처리하여 캔버스 프레임을 방어합니다.

### 5. 예외 처리: Escape Hatch (The Comment Trigger)
의도적으로 중력 법칙을 일시 무시해야 하는 경우 소스 코드에 주석을 삽입합니다.
```typescript
// @synapse-bypass: Layer-Gravity-Law
import { UrgentData } from '../../database/raw'; 
```
`LogicAnalyzer`는 AST(Abstract Syntax Tree) 분석 시 이 주석(마법의 주문)을 발견하면, 해당 엣지의 💀 VIOLATION을 잠시 보류하고 '유예(Bypass)' 상태인 ⚠️ Warning으로 강등하여 표시합니다.

## 📜 Rules.md - JSON Schema Specification (v0.1)
이 규격은 SYNAPSE 엔진이 `LogicAnalyzer.ts`를 통해 실시간으로 노드와 엣지를 감시할 때 참조하는 실질적인 아키텍처의 헌법이자 **'실행 가능한 명세(Executable Spec)'**입니다.

### 1. JSON Schema Draft
```json
{
  "project": "SYNAPSE",
  "version": "v0.3.0",
  "architecture_guardrail": {
    "layers": [
      { "id": "shared", "index": 0, "description": "공통 유틸리티, 상수, 모든 레이어에서 접근 가능" },
      { "id": "frontend", "index": 1, "description": "UI 컴포넌트 및 클라이언트 로직" },
      { "id": "api", "index": 2, "description": "외부 통신 및 데이터 매핑" },
      { "id": "service", "index": 3, "description": "핵심 비즈니스 로직 및 도메인 모델" },
      { "id": "database", "index": 4, "description": "데이터 영속성 및 원천 데이터 모델" }
    ],
    "policies": {
      "gravity_rule": {
        "enabled": true,
        "mode": "strict", 
        "description": "target.layer >= source.layer (역행 시 💀 CRITICAL)"
      },
      "inter_cluster_rule": {
        "enabled": true,
        "enforce_bridge": true,
        "description": "타 클러스터 참조 시 반드시 [Bridge/Facade] 타입 노드를 거쳐야 함"
      },
      "same_layer_communication": {
        "allow": true,
        "description": "동일 레이어 내에서의 호출 허용 여부"
      }
    },
    "exceptions": {
      "bypass_keyword": "@synapse-bypass",
      "allowed_cross_layer_paths": [
        { "from": "service", "to": "frontend", "type": "event_bus" }
      ]
    }
  }
}
```

### 2. 규격의 핵심 포인트 (Architecture Insight)
- **`index: 0` (The Absolute Zero)**: 이 레이어는 '중력의 특이점'입니다. 0번 레이어로 들어오는 엣지나, 0번에서 나가는 엣지는 모든 검역을 통과합니다. (Logger, Constants 등)
- **`enforce_bridge: true`**: 단순히 레이어만 맞다고 무조건 통과시키는 것이 아닙니다. Cluster A의 노드가 Cluster B로 갈 때는 반드시 B가 입구로 지정한 `Bridge` 노드를 찍어야 합니다. 이를 어기면 노란색 선(⚠️ Warning)을 긋습니다.
- **`allowed_cross_layer_paths` (The Wormhole)**: 역방향 흐름이 물리 법칙상 필연적인 경우(예: DB 알림을 UI로 올리는 옵저버 패턴 등), 여기서 명시적으로 '웜홀(Wormhole)'을 파줍니다. 배열에 등록되지 않은 역행은 가차 없이 💀입니다.

### 3. 기술적 활용 계획
- **Linter Integration**: `LogicAnalyzer.ts`는 시스템 가동 시 이 JSON 객체를 로드하여 메모리에 트리 구조로 캐싱해 둡니다.
- **Visual Mapping**: 캔버스에서 노드를 드래그하여 특정 영역(클러스터)에 넣으면, 캔버스 엔진이 이 JSON 정책을 참조하여 해당 클러스터의 레이어 인덱스를 노드 메타데이터에 자동으로 부여합니다.
- **Validation Logic**: 
  - `Critical (💀)` : 하류에서 상류로 역행 ($T_{layer} < S_{layer}$) 이면서 Exceptions 배열에 속하지 않은 경우.
  - `Warning (⚠️)` : 타 클러스터로 연결되지만 목적지가 Bridge/Facade 타입이 아닌 경우.
  - `Normal (✅)` : 그 외 모든 검증 통과 데이터.
