인덱스(chat.ChatSessionStore.index)가 비어 있었다면, 실제 데이터는 인덱스 없이 통째로 'LOB(Large Object)' 형태로 박혀 있을 확률이 높네. 아래 키워드로 SELECT를 날려보게나.

데이터 크기 순 정렬 (Size-based Prioritization):
복잡하게 이름 찾지 말고, ItemTable에서 value 컬럼의 **길이(length)**가 가장 긴 녀석들 상위 5개만 뽑아보게나. 2.1MB의 데이터라면 분명 압도적인 크기를 자랑하는 레코드가 하나 있을 걸세. 그놈이 바로 자네가 찾는 **'진실의 뭉치'**지.

값(Value)의 시작 패턴 확인:
찾아낸 키의 value가 [(배열)이나 {(객체)로 시작하면 럭키! 하지만 \x01\x02 같은 바이너리로 시작한다면... 아까 말한 대로 Protobuf의 늪으로 들어가는 입구일세.

용량 기반 스캐닝 (The Big Fish):

글로벌 vs 워크스페이스 (Storage Isolation):

Global state.vscdb: 사용자 계정 설정, 테마, 그리고 **'모든 워크스페이스에 걸친 통합 채팅 기록'**이 여기 있을 수 있네.

Workspace state.vscdb: 특정 프로젝트 폴더 안에서 나눈 **'컨텍스트가 제한된 대화'**는 보통 여기에 박히지.

📉 ItemTable의 2.1MB와 'Trajectory'의 심층 분석
SQLite의 '고스트 데이터' (Bloat & Fragmentation):
자네의 의심대로, 2.1MB라는 크기는 실제 데이터보다 **'프리-알로케이션(Pre-allocation)'**이나 '삭제된 레코드의 잔재' 때문일 확률이 높네. SQLite는 데이터를 지워도 파일 크기를 바로 줄이지 않고 VACUUM 명령 전까지는 빈 페이지로 남겨두거든. 만약 그 빈 공간 속에 자네가 그토록 찾던 **'삭제된 대화의 파편'**이 남아있다면, 그건 그야말로 **'디지털 포렌식'**의 승리일세.

antigravityUnifiedStateSync.trajectorySummaries:
이 키 이름이 모든 걸 말해주고 있네. **'Unified State Sync'**는 구글의 여러 서버와 클라이언트 간의 상태를 동기화하는 엔진이고, **'Trajectory Summaries'**는 자네와 AI가 나눈 대화의 핵심 요약본이자 진행 경로(Trajectory)네.

전략: 이 필드가 Base64나 JSON 덩어리라면, 자네는 굳이 전체 로그를 복구할 필요 없이 이 **'요약본'**만으로도 자네 설계의 맥락을 완벽히 복원할 수 있을 걸세.

출력되는 데이터는 UTF-8 형태로 표시할 것

## 🧠 상세 설계 및 로직 (ToT Analysis 기반)

### 🌳 Branch 1: 세션 초기화 안정화 (Session Guard)
- **Problem:** Record 토글 시 중복 세션 파일 생성.
- **Solution:** `PromptLogger` 싱글톤에 `activeSessionPath` 락(Lock) 구현.
- **Logic:** `initializeSession()` 호출 시 이미 활성화된 세션이 있다면 해당 경로를 재사용.

### 🌳 Branch 2: 비표준 프롬프트 캡처 (API Sniffing)
- **Problem:** 안티그래비티의 커스텀 Prompt API로 인해 대화 로그 누락.
- **Solution:** `extension.ts`에서 명령 가로채기 및 `ChatExtractor.ts` 확장.
- **Logic:** `antigravity.chat.sendMessage` 등의 내부 커맨드 파라미터를 추출하여 감사 로그에 주입.

### 🌳 Branch 3: SQLite 상태 기반 맥락 복원 (Trajectory Forensic)
- **Problem:** IDE 재시작 시 맥락 소실.
- **Solution:** `state.vscdb`의 `trajectorySummaries` 추출기 구현.
- **Logic:** `sqlite3`로 `ItemTable`을 스캔하여 '진실의 뭉치' (Trajectory)를 추출, UTF-8 휴리스틱 필터링 적용.
