## 🧠 상세 설계 및 로직 
- **취약점 식별 (Command Injection):** `MountManager.ts` 내부에서 클라이언트 작업 공간 마운트를 위해 `sshfs`를 호출할 때, 사용자 입력을 필터링 없이 쉘 문자열 변수에 담아 `exec()`로 실행하던 크리티컬한 보안 결함 발견. (예: `username`에 `dog; rm -rf /` 주입 시 시스템 파괴 가능)
- **실행 컨텍스트 전환:** 쉘의 메타 문자(`;`, `|`, `&&`) 파싱을 원천 차단하기 위해 모든 `exec()` 호출을 배열 인자를 받는 `execFile()` 방식으로 전면 교체.
- **방어 깊이(Defense in Depth) 적용:** `execFile`로 인젝션을 막는 데 그치지 않고, 악의적이거나 비정상적인 입력으로 인한 시스템 운영 불안정성을 막기 위해 API 진입점 단계에서 깐깐한 정규식 및 로직 검증 추가.
  - `~/project` 와 같은 실무적인 SSH 마운트 환경은 허용하되, `..` 등 경로 우회(Path Traversal) 방어.
  - 사내망(`dev-server`)이나 범용 인터넷 도메인(`example.com`), 그리고 IPv4/IPv6 포맷이 모두 안정적으로 호환되도록 호스트명 검증 정규식(`^[a-zA-Z0-9.-]+$`) 적용.
  - `net.isIP()`를 활용하여 비정상 IPv6 (`:::::`) 필터링.
  - `sshKey`가 단순 존재할 뿐만 아니라 유효한 '파일'인지(`fs.statSync().isFile()`) 검증하여 폴더 주입 등의 예외 처리.

## 🛠️ 기술적 변경 사항

### 🚀 추가 작업: Security Architecture Review & Tier 2.5 진입 선언
- **Tier 1 (RCE) 잔여 위험 검증:**
  - 전체 소스코드 대상 `exec`, `execSync`, `spawn`, `shell:` 키워드 전수 `grep` 스캔 결과, `CanvasPanel.ts`의 안전한 배열 기반 `spawn`과 정규식 매칭(`Regex.exec`), 그리고 사용자 입력이 개입할 수 없는 `execSync('which sshfs')` 외에 잠재적 Command Injection 벡터가 완벽히 소멸되었음을 2차 검증 완료.
- **Tier 2 (File System) 방어 철학 (Defense in Depth) 입증:**
  - 단순 정규식(e.g., `clientUsername` 필터링)만으로 경로 조작을 막는 것은 불완전함.
  - `fs.realpathSync()` 적용 시 흔히 발생하는 실수(Target만 realpath로 풀고 Root는 문자열로 비교하는 오류)를 방지하기 위해, **반드시 Target의 물리 경로(`realTarget`)가 Root의 물리 경로(`realRoot`) 하위에 존재하는지(`realTarget.startsWith(realRoot)`) 검증**하는 완전한 샌드박스 경계 패턴을 `HarvestEngine.ts`에 정확히 구현함.
- **Tier 2.5 (Snapshot Integrity) 의 중요성 및 진입:**
  - SYNAPSE는 단순 로컬 파일 편집기가 아닌 "상태(State)와 협업(Collaboration)" 플랫폼이므로, RCE 못지않게 **상태 위조(State Forgery)** 가 매우 치명적인 공격 벡터임.
  - **중점 점검 및 타겟 대상:**
    1. **Snapshot Author Forgery:** 클라이언트가 payload에 `author: "host"`로 위장하여 Host 스냅샷을 생성할 수 있는가?
    2. **Harvest Replay:** 과거 승인된 Harvest Payload를 재전송하여 Host의 승인 절차를 우회할 수 있는가?
    3. **Ownership Forgery:** 클라이언트가 `role: "lead"` 등을 주입해 권한을 탈취할 수 있는가?
    4. **Snapshot UUID Forgery:** 클라이언트가 기존 스냅샷 ID를 전송해 타인의 스냅샷을 덮어쓸 수 있는가?
  - 위 질문들에 대한 전수 검사 및 원천 차단을 목표로 **Tier 2.5 조치에 즉시 돌입**함.

### 🚀 추가 작업: SYNAPSE Reliability Qualification Program (Tier A) 완료
- **목표:** 단순한 취약점(Vulnerability) 제거를 넘어, 시스템이 어떠한 예기치 않은 재난(Crash, OOM, Network Race) 상황에서도 "데이터가 1비트도 오염되지 않는다"는 시스템 생존성과 논리적 불변성(Invariant)을 완벽히 증명.
- **[A-06] Persistence Consistency Test (영속성 일관성 증명):**
  - **문제점:** 부분적인 스냅샷이나 감사 로그 누락으로 인해 발생하는 Split Brain 상태 방지.
  - **검증 내용:** `Harvest 시작 -> Snapshot(History) 생성 -> State 기록 -> Audit 기록 -> 직후 SIGKILL 강제 종료` 를 수행하는 훅(Hook)을 삽입하여 `a06_test.ts` 구동.
  - **증빙 완료:** 재기동 시 `State Version: 2`, `History Version: 2`로 정확히 버전이 일치하며, Audit Length 역시 누락 없이 기록되었음을 증명 (Crash 전 상태 === Crash 후 복구 상태 보장).
- **[A-07] Concurrent Idempotency (동시성 멱등성 검증):**
  - **검증 내용:** `a07_test.ts`에서 `Promise.all`을 사용하여 100개의 `execute` 요청을 완전히 동시에 발사(Simultaneous Execution).
  - **증빙 완료:** `Results: 1 Success, 99 Failures`. `hsm.transitionState('Executing', 'Harvesting')` 원자적 락(Lock)에 의해 첫 1개만 실행되고 나머지 99개는 즉시 기각. Snapshot 1개, Audit 1회만 정확하게 생성되는 것을 완벽히 증명.
- **[A-08] Partial Commit Matrix (부분 성공 조합 방어):**
  - **검증 내용:** State, History 중 일부만 버전이 올라가는 파일 불일치 조합 시뮬레이션.
  - **증빙 완료:** 파일 불일치 발생 시 부팅 시그널을 확인하여 `🚨 [SYNAPSE CRITICAL] SYSTEM BOOTING IN READ-ONLY SAFE MODE 🚨`를 출력하며 성공적으로 읽기 전용 안전 모드에 진입함을 증명.
- **[A-09] Real OOM (진짜 V8 힙 고갈 검증):**
  - **검증 내용:** OS 메모리(External)가 아닌 V8 JS Heap 영역을 직접 터뜨리기 위해 `while (true) arr.push(new Array(10000).fill({ oom: 'heap_exhaustion_test_string' }));` 실행.
  - **증빙 완료:** 서버 로그에 `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory`가 성공적으로 출력되었으며, 강제 어보트(Abort) 후에도 어떠한 파일 손상 없이 깨끗하게 재기동됨을 증명.
- **[A-10] 409 Conflict 원인 정밀 분류 검증:**
  - **검증 내용:** 100건의 동시 execute 요청 시 발생하는 409 에러 응답 코드가 어떠한 사유로 기각되었는지(`req.body.error`) 구체적으로 파싱하여 카운팅.
  - **증빙 완료:** `Results: 1 Success, 99 Failures`. 409 사유 99개가 단 하나의 예외 없이 `"Invalid state transition or concurrent execution (Conflict)"`임이 증명됨으로써, 예기치 않은 500 서버 에러 없이 완벽하게 락 선점 실패(Lock Rejection)로 인한 방어였음을 입증.
- **[A-11] Recovery State Equivalence (Deep Memory Flush):**
  - **검증 내용:** 단순 연결 핑(Ping) 테스트에서 나아가 `/api/debug/state` 엔드포인트를 열고 내부 메모리 `sessions`, `sseClients`, `pendingRequests`, `lockedClients` 배열을 깊숙히 조회. 서버를 강제로 `SIGKILL` 시키고 재기동 후 메모리 상태 검증.
  - **증빙 완료:** 재부팅 후 이전 세션 및 락 클라이언트 등 모든 내부 Map과 배열 데이터가 어떠한 좀비 객체도 없이 완벽하게 초기화(`[]`) 됨을 확인하여 Runtime Recovery Integrity(런타임 복구 무결성)를 완벽히 증명.
- **[A-12] Mid-Atomic Write Crash Verification:**
  - **검증 내용:** 가장 가혹한 데이터 오염 상황 연출. 파일 내용의 실제 저장이 완료되고, 원본 파일 위로 `renameSync` 덮어쓰기가 일어나는 정확히 그 순간(1ms 간격)에 프로세스를 `SIGKILL`로 즉사시키는 후킹(Hooking) 코드 주입.
  - **증빙 완료:** 테스트 결과 서버 강제 종료 직후 `.tmp` 임시 파일은 디스크에 성공적으로 생성되었으나, 재기동 시 원본 파일은 오염되지 않고 기존 버전을 유지(State: 1)함을 확인. 즉, Atomic Write 중간에 전원이 나가더라도 파일이 완전히 교체되거나 아예 손상되지 않음이 보장되는 강력한 무결성을 입증.

### 🚨 Tier B 최종 결론 (Architecture Diagnostic)

SYNAPSE는 현재 구조에서 데이터 무결성(Data Integrity)과 자원 무결성(Resource Integrity)을 완벽히 만족합니다. (1,000회 연속 Harvest에도 FD/Handle 누수 0, Heap 증가율 정상)

그러나 `synapse_history.json` 전체를 동기적으로 읽고 다시 전체를 기록하는 구조로 인해 History 크기가 증가할수록 Snapshot 처리 시간이 선형적으로 증가합니다.

**실측 결과 (B-1.5 Snapshot Throughput):**
- History 100건: P99 ≈ 2.5ms
- History 1,000건: P99 ≈ 17ms
- History 10,000건: P99 ≈ 200ms

**추가 관측 (B-1.6 Event Loop Starvation):**
추가적으로 Snapshot Flood 상황(100건 동시 요청)에서 **Event Loop Starvation**이 발생하여 단순 Ping 요청까지 **최대 18.6초** 지연되는 현상이 관측되었습니다. (Realtime UI Freeze 유발)

**최종 진단:**
따라서 현재 아키텍처는 데이터 보존(Persistence) 측면에서는 대단히 안정적이지만, 실시간성(Realtime Responsiveness) 측면에서는 치명적인 구조적 한계를 가집니다.
이 문제는 버그가 아니라 현 구조(Single Thread + Sync I/O)의 완벽한 데이터 정합성 보장의 대가(Trade-off) 설계 특성으로 판단되며, 다음 마일스톤 **v0.4.0**에서 History 저장 구조 및 **Realtime Isolation** 전략을 재설계해야 합니다.

### 🚨 심층 보안 검증: 6대 크리티컬 공격 벡터(Attack Vectors) 방어 확인

현재 구조(`v0.3.30.2`)에서 발생할 수 있는 잠재적 보안 위협 요소들에 대해 코드 레벨의 방어 체계를 전수 검증하였으며, **단 하나의 레이스 컨디션이나 보안 구멍 없이 모두 차단**되어 있음을 확인했습니다.

1. **Path Traversal (`../` 등 우회 및 심볼릭 링크)**
   - **방어 확인:** `HarvestEngine`의 `candidate.targetPath` 평가 시 `path.resolve`를 통해 도출된 절대 경로가 반드시 `ProjectRoot` 하위에 존재하는지(`startsWith`) 엄격하게 검증합니다. 벗어날 경우 샌드박스 위반으로 간주하여 해당 파일을 버립니다.
2. **Auth 우회 (세션리스 호출 및 토큰 재사용)**
   - **방어 확인:** `standalone.ts`의 전역 Auth 미들웨어에 의해 5개의 예외 경로(로그인 등)를 제외한 모든 API는 `Bearer` 토큰을 강제합니다. 토큰이 없거나 만료된 세션은 즉각 `401 Unauthorized`로 튕겨냅니다.
3. **SSE 채널 오염 (미인증 클라이언트 난입)**
   - **방어 확인:** SSE 연결 엔드포인트(`/api/collab/stream`) 역시 전역 Auth 미들웨어의 지배를 받으므로, 유효한 토큰 없이는 스트림 파이프 자체를 열 수 없습니다.
4. **Save 권한 상승 (Lock 우회 및 강제 저장)**
   - **방어 확인:** 임의의 사용자가 `/api/collab/save-file`을 호출하더라도 `!isLocked(resolvedUserId)` (타겟 클라이언트의 연결 상태) 검증을 거칩니다. 더 중요한 것은 실제 파일 시스템에 쓰는 주체는 `HarvestEngine`이며, 엔진의 쓰기 행위는 철저히 중앙 상태머신의 권한(Lead)을 통과해야만 가능합니다.
5. **Harvest 경로 탈출 (Target Path 이탈)**
   - **방어 확인:** 1번의 샌드박스 경계 패턴과 동일하게 방어되며, 추가적으로 `clientUsername`에 대해서도 엄격한 영문/숫자 정규식 필터링을 거쳐 상위 폴더 오염을 원천 차단합니다.
6. **클라이언트 위장 (curl 등을 통한 비정상 접근)**
   - **방어 확인:** 클라이언트가 어떤 도구를 쓰든 전역 Auth 검증을 거쳐야 하며, 인증을 통과하더라도 API의 실행 여부는 `HarvestSessionManager`의 전역 상태머신(State Machine)에 의해 통제됩니다.

**💡 특별 검증: 네트워크 단절 시 Harvest 락(Lock) 레이스 컨디션 방어**
- **현상 파악:** 클라이언트 연결이 끊어지면 `standalone.ts`의 로컬 SSE 락(`lockedClients`)은 즉시 파기되지만, `HarvestSessionManager`의 글로벌 락은 `Harvesting` 상태를 끝까지 유지합니다.
- **방어 원리 (Fail-Safe):** 연결이 끊긴 클라이언트를 대상으로 파일을 수집하려 시도하면, `requestClientFile` 함수가 타임아웃을 기다리지 않고 즉각 해당 건만 `Reject` 처리(`failedFiles`에 병합)한 뒤 다른 정상적인 클라이언트의 파일 수집을 무정지로 계속 진행합니다.
- **최종 무결성:** 모든 수집 작업이 종료되어야만 `finally` 블록에서 글로벌 락이 안전하게 해제되므로, **클라이언트의 튕김이나 네트워크 장애로 인해 서버의 상태머신 락이 도중에 소실되는 레이스 컨디션은 절대 발생하지 않습니다.**

  - 또한, 아주 초창기에 생성된 `accounts.json` 파일이 배열(`[ ... ]`) 포맷인 경우, 최근 업데이트된 `AccountsStore`(`{ accounts: [] }`) 객체 구조와 맞지 않아 파싱 중 `TypeError`가 발생하고 이로 인해 모든 계정이 초기화되어 삭제되는 부작용이 있었습니다.
- **조치 사항:**
  - `standalone.ts`가 예비 포트로 바인딩 될 경우, `READY` IPC 메시지에 `actualPort`를 담아 부모 프로세스(`CanvasPanel.ts`)로 전달하도록 수정.
  - `CanvasPanel.ts`는 전달받은 실제 포트로 내부 API 엔드포인트를 업데이트하고, `ui/index.html`에도 `serverPortUpdated` 메시지를 보내 화면의 포트 입력란을 동기화하도록 구현.
  - `AccountManager.ts`의 `loadSync` 함수에 `Array.isArray` 체크를 추가하여, 과거 레거시 배열 포맷의 `accounts.json`을 안전하게 불러와 마이그레이션 하도록 복구 대응 추가.

### 💡 Traffic Heatmap (Beta) 해석에 대한 고찰 및 답변
- **질문 요지:** "처음 연 프로젝트라 Harvest가 0건인데도 붉게 보이는 영역이 있다. 이것이 순수한 '트래픽'인가, 아니면 '구조적 중심성'이나 '의존성 수'인가?"
- **답변 및 진단:**
  - 사용자님의 통찰이 정확히 맞습니다. 현재 Beta 버전의 Heatmap은 순수한 "작업 트래픽(Harvest/Modification 빈도)" 데이터가 부족하거나 없을 경우, **시각적 공백을 막고 아키텍처의 윤곽을 보여주기 위해 노드의 In/Out Degree (의존성 수) 및 Layer 가중치와 같은 '구조적 중심성(Structural Centrality)'을 Fallback 메트릭으로 혼합**하여 렌더링하고 있습니다.
  - 즉, 초기 상태에서 붉게 타오르는 중앙 노드들은 과거에 트래픽이 많았다기보다는, **모노레포 내에서 가장 많은 모듈이 참조하고 있는 핵심 허브(Core Hub)** 임을 의미합니다.
  - Harvest 데이터가 수집(Recency, Frequency)되기 시작하면 점차 해당 동적 트래픽 데이터의 가중치가 높아져 진정한 'Traffic Heatmap'으로 변모하게 됩니다.
  - **향후 개선 방향:** v0.4.0 마일스톤 단계에서 "순수 구조적 중심성 뷰"와 "순수 동적 트래픽 뷰"를 분리하거나 사용자가 혼합 비율을 조절할 수 있는 기능을 제공하는 것을 고려해야 합니다.

### 🚨 트러블슈팅: 수확(Harvest) 실행 중 배열 형태의 히스토리 포맷 충돌 해결 (v0.3.30.2)
- **현상:** 수확(Harvest) 버튼 클릭 시 "수확 완료" 대신 `수확 실패: Cannot read properties of undefined (reading 'unshift')` 오류 메시지가 출력되는 문제 발생.
- **원인 분석:** 
  - 과거 레거시 시스템에 의해 생성된 `synapse_history.json` 파일이 객체(`{ history: [] }`)가 아닌 배열(`[ ... ]`) 포맷으로 저장되어 있었습니다.
  - v0.3.30.2의 수확 로직(`standalone.ts`)에서 이 히스토리 파일을 읽을 때, 무조건 `historyData.history` 형태로 접근하려 시도하면서 `undefined`가 반환되어 `.unshift()` 호출 시 크래시가 발생했습니다.
- **조치 사항:**
  - `synapse_history.json` 파일을 불러올 때, 파싱된 내용이 배열(Array)인 경우와 객체(Object)인 경우 모두를 안전하게 지원하도록 구조를 분기 처리하여 역호환성을 확보했습니다.
  - 이로써 레거시 데이터가 존재하는 프로젝트에서도 수확 실행이 중단되지 않고 정상 동작합니다.

- **Event Loop Starvation Diagnosed:** Diagnosed latency spikes caused by synchronous I/O operations when `synapse_history.json` grows infinitely. This crucial finding directly establishes the blueprint for the Async Isolation architecture coming in v0.4.0.

**🐞 Bug Fixes & Backward Compatibility Stabilization**
- **Fixed Port Conflict & 403 Auth Error:** Resolved a bug where the UI failed to synchronize with temporary port assignments (due to ghost processes), which previously caused Admin Creation to fail with a 403 error.
- **Legacy Account Data (`accounts.json`) Parsing Fix:** Implemented safe parsing to support legacy array-formatted user account data, preventing crashes and unintended data resets.
- **Harvest History (`synapse_history.json`) `unshift` Error Prevention:** Fixed a critical `TypeError (reading 'unshift')` crash that occurred when the server attempted to parse legacy array-formatted history files during Harvest execution. Both legacy and modern formats are now safely supported.
