## 📋 Phase 1 Technical Details

### ProjectMetadata Path Validation Logic
```
Input: targetPath (e.g., "../etc/passwd" or "src/main.ts")
  1. resolved = path.resolve(projectRoot, targetPath)
  2. root = path.resolve(projectRoot)
  3. Check: resolved.startsWith(root + path.sep) || resolved === root
  4. Fail → throw Error / return false
  5. Pass → allow operation
```

### SymbolIndex Data Model
```
SymbolIndex
  ├─ projectName: string
  ├─ projectRoot: string
  ├─ folderTree: FolderTree (recursive)
  │    ├─ path: string
  │    ├─ name: string
  │    ├─ children: FolderTree[]
  │    └─ fileCount: number
  ├─ fileRegistry: Map<relPath, FileEntry>
  │    ├─ filePath, fileName, extension, size
  │    ├─ isSource, isDocumentation
  │    └─ functionCount, classCount
  └─ functionCatalog: FunctionEntry[]
       ├─ functionId (base64-encoded unique)
       ├─ functionName
       ├─ filePath
       ├─ className (nullable)
       └─ lineNumber
```

### SnapshotSystem Versioning
```
Save Flow:
  graphModel.createSnapshot()
    → snapshot.snapshotVersion = increment
    → snapshot.metadata = { projectUUID, projectName, snapshotCount }
    → snapshot.checksum = sha256(JSON.stringify(data)).slice(0,16)
    → history.push({ id, timestamp, version, checksum, data })
    → persist to data/synapse_history.json (max 20)

Restore Flow:
  → find snapshot (by ID or latest)
  → if checksum exists: recompute and compare (warn on mismatch)
  → graphModel.restoreSnapshot(target)
```

## 📋 Phase 3 Technical Details

### Submission Flow
```
[Member]
  Workspace Complete
       │
       ▼
  createSubmission(projectUUID, sessionId, clientId, files)
       │
       ├── Validate: member role + active session + file boundaries
       ├── Create SubmissionSnapshot (immutable = true)
       ├── Create ReviewState (state = 'pending')
       └── Freeze Member (isMemberFrozen = true)
       
[Lead]
       │
       ▼
  startReview(submissionId, leadId)
       │
       ├── Validate: lead has Verify permission
       └── ReviewState.state = 'review'
       
       │
       ▼
  applyRemoteEdit(submissionId, leadId, filePath, newContent)
       │
       ├── Validate: lead has RemoteEdit permission
       ├── Backup originalContent to RemoteEditAction log
       └── Update file content in snapshot.files[]
       
       │
       ▼
  approveSubmission(submissionId, leadId)
       │
       └── ReviewState.state = 'approved' → Ready for Phase 7 Harvest
       
  rejectSubmission(submissionId, leadId, reason)
       │
       └── ReviewState.state = 'rejected' → Return to client
```

## 🐛 Hotfix: Collaboration Server Start/Stop (2026-06-09)

### 문제
WebView의 "서버 관리" 패널에서 "서버 시작" 버튼을 눌러도 상태가 계속 "중지됨"으로 표시됨.

### 원인
`src/webview/CanvasPanel.ts`의 `handleStartServer()`에 두 가지 버그 존재:

1. **`serverStarted` 메시지 누락 (치명적)**
   - `cp.spawn()`으로 서버 프로세스를 실행한 후 WebView에 `serverStarted` 커맨드를 전송하는 코드가 없음
   - WebView는 "시작 중..." 상태에서 영원히 대기하다가, 프로세스가 종료되면 `serverStopped`를 받아 "중지됨"으로 전환
   - 서버가 정상 실행되어도 UI는 계속 중지 상태로 표시됨

2. **포트 충돌 오류 무음 처리**
   - 이미 실행 중인 서버가 포트 3000을 점유하고 있을 때, 새 프로세스는 `EADDRINUSE`로 즉시 종료
   - stderr의 에러 메시지는 단순 `Logger.warn`으로만 기록되고 사용자에게 표시되지 않음
   - 사용자는 서버가 왜 시작되지 않는지 알 수 없음

### 수정 내용
| 변경 | 파일 | 설명 |
|------|------|------|
| `serverStarted` 전송 추가 | `CanvasPanel.ts:819` | `cp.spawn()` 직후 WebView에 서버 시작 상태 전송 |
| 포트 충돌 감지 | `CanvasPanel.ts:798-800` | stderr에서 `EADDRINUSE`/`already in use`/`listen` 패턴 감지 시 사용자에게 오류 메시지 표시 |
| 비정상 종료 처리 | `CanvasPanel.ts:812-816` | exit code가 0이 아닌 경우 `serverError` 메시지로 사용자 알림 |

- **파일:** `src/webview/CanvasPanel.ts` (handleStartServer 메서드 내부, 5라인 수정)

## 🔧 Hotfix v0.3.30d — `saveConnState is not defined` Scoping Bug

### 문제
`ui/index.html`에서 `saveConnState()`가 `loginResult` 핸들러(`index.html:1604`)에서 호출되었으나, 함수 정의는 `DOMContentLoaded` 콜백 내부(`index.html:1856`)에 있어 스코프 불일치로 `ReferenceError` 발생. 변수 `connHost`, `connPort`, `connDot`, `connStatus`도 동일한 스코프 문제로 `loginResult` 핸들러에서 접근 불가.

### 수정 사항
1. **함수 및 DOM 참조 최상위 스코프로 이동** (`index.html:1357-1388`)
   - `connPanel`, `connHost`, `connPort`, `connUser`, `connPass`, `connError`, `connStatus`, `connDot` → `let` 선언을 `DOMContentLoaded` 밖으로 이동
   - `connectedUser` → 최상위 `let connectedUser = null`
   - `updateConnStatus()`, `loadConnState()`, `saveConnState()`, `clearConnState()` → 최상위 함수로 이동
   - 내부 DOM 할당문 (`document.getElementById(...)` 등)은 `DOMContentLoaded` 내에 유지 (값 할당 시점 보장)
2. **중복 `let connectedUser = null` 제거** — `DOMContentLoaded` 내부 선언이 최상위 변수를 가리던 문제 해결
3. **`getConnHostPort()` 기본값 제거** — `host`가 빈 문자열일 때 `localhost`로 fallback하지 않음. WebView message handler가 `message.host` falsy 체크로 빈 값을 skip하도록 이미 설계됨 (CanvasPanel.ts:482)
4. **재패키지**: `synapse-visual-architecture-0.3.30.vsix` (559 files, 28.84MB)

### 영향 범위
- `loginResult` 핸들러가 `saveConnState()` 및 DOM 참조를 정상적으로 접근 가능
- 로그인 후 "접속중" 상태에서 진행되지 않는 hang 해결

## 🔧 Layer Visibility — 접속 중인 클라이언트만 레이어로 표시 (2026-06-15)

### 문제
서버(admin)가 `/api/state`를 통해 `clientLayer: usr_1781244031137...`를 설정하여, 아무 클라이언트도 접속하지 않았는데도 `👤 usr_1781244031137...` 레이어가 표시됨.

- `CanvasPanel.ts`의 `_onServerReady()`가 admin auto-login 후 `_connUserId`를 `clientLayer`로 설정한 상태로 `sendProjectState()` 호출 → 서버 노드에 admin의 userId가 clientLayer로 태깅됨

- `canvas-engine.js`의 `refreshClientLayersFromAccounts()`가 `accounts.json`의 모든 계정을 레이어로 등록 → 접속 상태와 무관하게 레이어 생성

### 수정 (옵션 B: connected-clients만 레이어로)

#### canvas-engine.js
| 변경 | 설명 |

| `_updateClientLayerUI()` 수정 | 레이어 토글 UI를 `clientLayers` 레지스트리를 기준으로 렌더링 (접속 dot 표시) |

#### CanvasPanel.ts
| 변경 | 설명 |
|------|------|
| admin 노드 clientLayer 제거 | admin(`_isServerOwner`)이 보내는 state의 `update`/`updates.data`에서 `clientLayer`와 `clientUsername` 할당 생략. base state로 유지 |

## 🚀 서버 접속 + SSH 마운트 통합 (2026-06-15)

### 필요성
로그인(Synapse 인증)과 SSH 마운트(파일 시스템 접근)가 분리되어 로그인 후에도 SSH 정보가 없으면 클라이언트 노드가 생성되지 않음. SSH 설정은 CLI로만 가능하여 UI 부재.

### 결정
"서버 접속" 패널 하나로 로그인 + SSH 마운트를 한 번에 처리. SSH 정보가 있으면 로그인 성공 시 자동 마운트 → 노드 생성.

### UI 변경
| 항목 | 설명 |
|------|------|
| `#conn-ssh-host` | SSH Host 입력 (optional) |
| `#conn-ssh-user` | SSH User 입력 (optional, 기본값: Synapse username) |
| `#conn-ssh-mount` | SSH Mount Path 입력 (optional) |
| 구분선 "원격 마운트 (선택)" | 패스워드 아래에 SSH 섹션 구분 |

### 로직 변경

#### `AccountManager.ts` — `updateSSHInfo()` 메서드 신규
```typescript
updateSSHInfo(username, { sshHost, sshPort, sshUser, sshMountPath, sshKey }): boolean
```
- 기존 계정의 SSH 필드만 업데이트
- `sshMountPath`가 있으면 `validateMountPath()` 검증
- 변경 사항을 `data/accounts.json`에 저장

#### `standalone.ts` — `POST /api/auth/login`
- `req.body`에서 `sshHost, sshPort, sshUser, sshMountPath, sshKey` 수용
- `AccountManager.updateSSHInfo()`로 계정에 SSH 정보 저장
- 저장 후 `AccountManager.login()`으로 갱신된 `user` 객체 재조회
- 기존 mount 블록 (`user.sshHost && user.sshMountPath`) 재사용

#### `CanvasPanel.ts` — `handleLogin()` 시그니처 확장
```typescript
handleLogin(host, port, username, password, sshHost?, sshUser?, sshMountPath?)
```
- body에 SSH 필드가 있으면 `/api/auth/login` 요청에 포함

#### `ui/index.html` — Browser/VSCode login 전송
| 모드 | 변경 |
|------|------|
| Browser fetch | `body`에 `sshHost`, `sshUser`, `sshMountPath` 포함 (undefined면 생략) |
| VSCode postMessage | `vscode.postMessage({..., sshHost, sshUser, sshMountPath})` |

### 수정 파일

| 문제 | 원인 | 수정 |
|------|------|------|
| 캔버스 빈 화면 + SSH 버튼 미동작 | `const body: any = { ... }` — TypeScript `: any`가 plain JS에서 SyntaxError 발생 → `<script>` 블록 전체 중단 | `const body: any` → `const body` |

- **서버에서 sshfs 미설치** — mount 실패해도 로그인은 성공 (기존과 동일)

## 🔧 세션 모델 복구 + HTTP Push 아키텍처 전환 (2026-06-16)

### 발견된 문제

#### 문제 1: 레이어 가시성 — "Server Admin" 레이어 표시

**증상:** 레이어 가시성 패널에 "Server Admin" 레이어가 표시됨

**원인:** `accountListResult` 핸들러에서 `acc.username === 'server'` 체크가 `'Server Admin'`과 불일치하여 필터링 실패

**수정:** `if (acc.username === 'server') continue;` → `if (acc.userId === '_server_admin_') continue;`

#### 문제 2: sshfs 마운트 실패 — NAT 네트워크 환경

**증상:** VM 클라이언트 접속 시 노드가 표시되지 않음

**근본 원인 분석:**
```
1. 서버 로그에 [Auth] Mounted / [Auth] Mount failed 메시지 없음
2. SSH 인증 실패: ssh test1@192.168.0.240 → Permission denied
3. VM 실제 IP: 10.0.2.15 (NAT), 서버에서 접속 시도한 IP: 192.168.0.240 (불일치)
4. GNOME Boxes SLIRP 네트워크: 호스트 → VM 직접 접속 불가
5. socat 포트 포워딩 시도: ssh -p 2222 test1@localhost → 연결 끊김
6. Bridged Adapter: GNOME Boxes에서 지원 안 
7. virsh 사용 불가: 네트워크 설정 변경 불가
```

**결론:** sshfs 기반 마운트는 NAT 환경에서 동작 불가

### 해결책: HTTP Push 아키텍처

#### 기존 구조 (sshfs - 불가)
```
서버 → 클라이언트 VM에 SSH 접속 → 마운트 → 스캔
```

#### 변경 구조 (HTTP Push - 가능)
```
클라이언트 → 서버에 파일 데이터 전송 → 서버가 nodes/clusters 생성
```

## 🚀 Phase 1A — Client Push 데이터 영속화 + 자동 재푸시 (2026-06-18)

### 배경
SSH 마운트는 서버→클라이언트 역방향 접속이 필요하여 NAT/VM/Docker 환경에서 구조적 한계 존재. 반면 Client Push는 클라이언트→서버 방향이므로 네트워크 환경과 무관하게 동작.

### 아키텍처 전환
```
[이전] 서버가 클라이언트에 접속하여 파일 읽기 (SSHFS)
[변경] 클라이언트가 서버에 분석 결과를 밀어넣기 (HTTP Push)
```

### 변경 파일

#### `src/server/standalone.ts`
- **clientPushData 영속화:** `data/client_push/<userId>.json` 저장
- **24h TTL 복원:** 서버 시작 시 stale 파일 삭제 + 로그
- **push 키를 userId 기반으로 변경:** username 변경/재사용과 무관
- **clientLayer 태깅:** userId 기반 (username은 data.clientUsername으로 보관)
- **`/api/state` Map 기반 병합:** node/edge/cluster 전부 ID 기준 덮어쓰기 (중복 제거)
- **로그아웃 시 삭제 없음:** TTL 기반 자동 정리

#### `src/webview/CanvasPanel.ts`
- **ID 정규화:** `client::<userId>::<path>` (불변 식별자 기반)
- **`_pushInFlight` 가드:** VSCode 저장 시 이벤트 다중 발생으로 인한 중복 push 방지
- **FileSystemWatcher:** `vscode.workspace.createFileSystemWatcher` — 3초 디바운스 자동 재푸시
- **무한 루프 방지:** `data/`, `.synapse/` 디렉토리 제외
- **SynapseIgnore 적용:** 스캔 + watcher 모두 `.synapseignore` 패턴 필터링
- **watcher 정리:** 로그아웃/서버 중지 시 `_stopPushWatcher()`

### 데이터 흐름 (변경 후)
```
클라이언트 로그인
    ↓
_pushClientState() → 서버에 파일 트리 전송
    ↓
서버: clientPushData 저장 + data/client_push/<userId>.json 기록
    ↓
FileSystemWatcher 시작 (3초 디바운스)
    ↓
파일 변경 감지 → _pushClientState() 자동 호출
    ↓
관리자: GET /api/state → Map 기반 병합 → 그래프 표시

서버 재시작
    ↓
data/client_push/*.json → 24h TTL 검증 → clientPushData 복원
    ↓
기존 클라이언트 데이터 유지
```

### Phase 1A 범위
| 포함 | 미포용 (Phase 1B+) |
|------|-------------------|
| 영속화 + 24h TTL | FileScanner 클라이언트 이전 |
| 자동 재푸시 (전체 스캔) | LogicAnalyzer 클라이언트 이전 |
| ID 정규화 (userId 기반) | Incremental Push |
| Map 기반 병합 (node/edge/cluster) | SSH 격하 |
| .synapseignore 적용 | |

### 검증 케이스
| 테스트 | 기대 |
|--------|------|
| 서버 시작 | `[ClientPush] Restored N client push cache(s)` |
| 로그인 → 파일 추가 → 3초 | 새 노드 그래프 표시 |

## 📝 Post-Work Log: WebGL 클라이언트 노드 좌표 동기화 2차 수정 (2026-06-20)

### 문제 상황

Accel: OFF → ON 전환 시 클라이언트 노드에서만 아래 두 가지 증상 발생:

1. **클러스터 밖 클라이언트 노드**: 이전 스냅샷 위치에 렌더링 (현재 위치와 불일치)
2. **클러스터 안 클라이언트 노드**: WebGL 전환 후 아예 사라짐

호스트의 자체 노드는 정상. 접속한 클라이언트의 노드만 해당.

### 근본 원인 분석

두 렌더 경로가 서로 다른 노드 소스를 사용하고 있었음:

| 경로 | 노드 소스 | clientLayerOffset |
|---|---|---|
| **2D (Accel: OFF)** | `_visibleNodesCache` | `renderNode()` → `_getNodeRenderY()` 내부에서 적용 ✅ |
| **WebGL (Accel: ON)** | `_visibleNodesCache` 동일 | `updateNodeData()` → `n.position.y` 원본 그대로 ❌ |

- `getClientLayerOffset(clientId)`는 `this.clientLayers[clientId].order` 기반 O(1) 해시 조회. 클러스터(cluster) 기반이 아닌 **클라이언트 유저 ID 기반** 고정 Y 오프셋 계산 `(order + 1) * 300 + 50`.
- 클러스터 안 노드 사라짐: raw `position.y`가 offset 없이 전달되면 viewport 위쪽(음수 Y)에 그려져 화면 밖 소멸.
- `cluster.collapsed` 필터는 `_visibleNodesCache` 빌드 단계에서 이미 처리되어 있으므로 **`_webglVisibleNodesCache`는 해당 필터링을 자동 상속**.

### 해결 내용

**파일:** `ui/canvas-engine.js`

`isGraphDataDirty` 시점에만 `_webglVisibleNodesCache`를 별도 빌드하는 로직 추가:

```javascript
// [v0.3.30-webgl-fix] Build WebGL-ready cache: bake clientLayerOffset into position.y
this._webglVisibleNodesCache = this._visibleNodesCache.map(n => {
    const cl = n.clientLayer || (n.data && n.data.clientLayer);
    if (!cl) return n; // Host node — no offset needed (pass by reference, no allocation)
    const offsetY = this.getClientLayerOffset(cl);
    if (!offsetY) return n;
    return { ...n, position: { x: n.position?.x || 0, y: (n.position?.y || 0) + offsetY } };
});
```

- 호스트 노드: 원본 참조 그대로 전달 (allocation 없음)
- 클라이언트 노드: Y 좌표에 offset bake-in된 shallow clone 생성
- `dirty` 시에만 실행되므로 매 프레임 allocation 없음 (성능 규칙 준수)

이후 `webglRenderer.render()`와 `getProjectedNodePositions()` 양쪽에 `_webglVisibleNodesCache` 전달.

     - **Rule 1 (Strip):** 대상 경로가 클라이언트의 `remotePath`로 시작하면, Segment 경계를 확인(`path.sep` 기준)하여 안전하게 잘라내어 순수 상대 경로로 변환.

     - **Rule 3 (Boundary Validation):** 최종적으로 조합된 절대 경로가 `.synapse/mnt/[username]` 디렉터리 하위에 완전히 귀속되는지 `startsWith(mountRoot + path.sep)`를 통해 재검증하여, 시스템 이탈 공격 원천 차단.

### 🏗️ 아키텍처 결정: 실시간 파일 릴레이 (SSE 기반 On-demand Pull)
- **상태:** ✅ Completed (구현 완료)
- **배경:** SSHFS(`MountManager`)를 폐기하고 HTTP Push 방식으로 전환했으나, `ClientPush` 페이로드에는 그래프 메타데이터(노드, 엣지)만 포함되고 파일 본문 텍스트는 전송되지 않음. 결과적으로 다른 클라이언트의 파일을 "즉석에서 바로 열고 보는" 기능이 마비됨 (메모리 직통 파이프라인이 빈 깡통 상태).
- **설계 방향 (Two-Track 통신):**
  1. **Graph Meta Sync:** 기존 10초 주기의 `VersionPoll` 및 `ClientPush` 구조 유지.
  2. **File On-demand Fetch:** **SSE (Server-Sent Events)**를 이용한 실시간 파일 릴레이 채널 신설.
- **SSE 채널 생명주기 (Lock 결합):**
  - `Client Connect → Lock 시작 → SSE 스트림 open`
  - `Client Disconnect/Unlock → SSE 스트림 close`
  - SSE 연결이 되어 있다는 것 자체가 해당 클라이언트가 실시간 응답 가능한 Lock 상태임을 보증함.
- **실행 흐름:**
  1. Architect(Client A)가 캔버스에서 Client B의 노드 더블클릭.
  2. Server가 SSE 채널을 통해 Client B에게 `send_file_content: [filePath]` 이벤트 푸시.
  3. Client B가 이벤트를 수신하여 로컬 파일을 즉시 읽고 `POST /api/collab/response`로 텍스트 반환.
  4. Server가 반환된 텍스트를 메모리에 임시 캐싱하고 Architect(Client A)에게 `openFile` 응답 완료.

### 🛡️ SSE 구현 세부 사항 및 엣지 케이스 방어
- **15초 Timeout 에러 핸들링:** 
  - `request-file` API는 대상 클라이언트의 응답이 15초를 초과하면 즉시 `HTTP 504 Gateway Timeout`을 반환합니다.
  - Architect 캔버스에서는 조용히 실패(Silent Failure)하지 않고 명확한 에러 팝업(`타 클라이언트 파일 요청 실패: File request timed out`)을 발생시켜 디버깅과 상태 인지를 돕습니다.
- **캐시 생명주기 및 덮어쓰기 최적화:**
  - 가져온 파일은 `.synapse/cache/{clientUsername}/` 경로에 임시 저장되어 VS Code 에디터 탭으로 열립니다.
  - `path.basename`을 사용 시 발생하는 이름 충돌(`src/utils/index.ts`와 `src/core/index.ts`가 겹치는 현상)을 막기 위해 경로의 슬래시를 언더스코어(`_`)로 치환하여 고유 파일명(`src_utils_index.ts`)으로 평면(Flat) 캐싱합니다.
  - 새로운 파일 요청 시 동일한 경로의 파일이면 **기존 캐시 파일을 그대로 덮어쓰기(Overwrite)** 하여 불필요한 I/O 비용과 무한한 디스크 점유율 증가를 원천 방지합니다.

### 🔒 아키텍처 결정: Connection Lock 및 Remote File Save (Lock-First Architecture)
- **상태:** ✅ Completed (구현 완료)
- **배경:** Architect가 타 클라이언트의 파일을 원격으로 편집(저장)할 때 로컬 편집과의 충돌을 막기 위해, 쓰기(Write) 파이프라인을 구축하기에 앞서 접속 시점부터 편집 영역을 독점(Lock)하는 보안 우선 정책(Lock-first)을 채택.
- **Phase 1: Connection Lock (서버 & 클라이언트)**
  - **서버(`standalone.ts`)**: 클라이언트가 SSE 채널로 접속하면 즉시 `lockedClients` 맵에 `{ lockedAt, lockedBy: 'server' }`를 기록하여 독점 점유 시작. SSE가 끊기면 Lock 해제.
  - **클라이언트(`CanvasPanel.ts`)**: SSE 채널 오픈/종료 시 내부 `_isLocked` 플래그를 동기화하고 웹뷰 UI 쪽에 `{ command: 'lockStateChanged' }` 이벤트를 전송하여 잠금 상태를 즉각 반영할 수 있게 조치.
- **Phase 2: Remote File Save (양방향 동기화)**
  - **Save Route Guard**: 서버의 `/api/collab/save-file` 엔드포인트는 가장 먼저 `isLocked(userId)`를 검증. Lock이 풀려있을 경우 조용히 실패(Silent failure)하지 않고 명확한 `403 Forbidden` (`Client not locked — write rejected`) 에러를 즉각 반환.
  - **Architect 트리거 (Ctrl+S 연동)**: Architect가 캔버스에서 연 캐시 파일(`.synapse/cache/...`)의 원본 경로를 `_cachePathMap` 메모리에 기억. VS Code의 `onDidSaveTextDocument` 이벤트를 구독해 저장이 감지되면 즉시 해당 텍스트를 서버로 전송.
  - **클라이언트 Write (Client-side Enforcement)**: 대상 클라이언트(test1)는 SSE로 `save_file_content` 이벤트를 수신하면, 서버와 클라이언트 간의 일시적 비동기화(Race Condition) 방지를 위해 다시 한 번 자신의 `_isLocked` 상태를 자체 검증. 안전한 경우에만 `vscode.workspace.fs.writeFile`을 호출해 원본 로컬 디스크 파일에 데이터를 덮어씌움. Architect 쪽에 저장 성공/실패 여부를 팝업 알림으로 직관적 피드백.

  - 향후 확장성(Snapshot, Session 로깅 등)을 고려하여 각 클라이언트별 User Root(`clients/{username}/`)를 자동 생성하도록 설계 개편.
  - 생성 구조: `.synapse/clients/{username}/harvest/`, `/snapshots/`, `/cache/`, `/metadata.json`
- **2. Harvest ≠ Sync 철학 확립**
  - **Harvest(데이터 수집):** Client → Snapshot → Server → Archive 단방향 수집 프로세스로 정의. (v0.3.30 완료)
  - **Sync(데이터 통합):** 수확된 코드를 실제 워크스페이스에 덮어쓰고 병합하는 과정. 덮어쓰기 정책, 충돌 해결, 롤백, Git Dirty 상태 관리 등 막대한 복잡성을 유발하므로 v0.3.30에서는 제외하고 **v0.4+ 백로그(연구 항목)**로 공식 이관.
- **3. Virtual Debugger 의존성 및 책임 분리 (Host Only)**
  - 현재 Virtual Debugger는 `File System → VS Code Diagnostics → Graph` 구조를 따르므로, 그 책임은 오직 **Host(Architect) Workspace**에만 국한됨.
  - 수확본(Harvest Copy)을 분석할 경우, 클라이언트의 실제 작업본(Working Copy)과 싱크가 맞지 않아 "오래된 복사본의 에러"를 띄우는 신뢰성 붕괴(False Positive) 문제가 발생.
  - 따라서, 클라이언트 디버깅은 v0.4+에서 **클라이언트가 직접 자신의 Diagnostics를 푸시(Diagnostics Push)**하는 `Remote Diagnostics Layer` 구조로 설계 이관함.
- **4. v0.3.30 종료 조건 달성**
  - 다중 클라이언트 수확 검증 완료, Path Traversal 보안 유지.
  - 아키텍처 문서 최신화 및 책임 분리 명시.
  - Git Tag `v0.3.30` 고정을 위한 최종 안정화 달성.
