# SYNAPSE v0.3.30 Harvest Goal

# Purpose

Harvest는 Merge가 아니다.

Harvest는 승인된 결과물을 Master Layer로 복사하는 작업이다.

Harvest는 다음 작업을 수행하지 않는다.

* Merge
* Auto Merge
* Conflict Resolution
* Delete
* Rename
* Refactor
* Rewrite
* Code Generation

Harvest는 Copy Operation Only 이다.

---

# Core Principle

## Source Of Truth

Architect(Server)는 유일한 Source Of Truth이다.

Master Layer는 Architect의 실제 프로젝트 디렉토리이다.

모든 Compare는 Master Layer를 기준으로 수행한다.

모든 Harvest는 Master Layer에 반영된다.

Client는 Source Of Truth가 아니다.

Submission은 Source Of Truth가 아니다.

---

## Master Layer

예시:

project/

├── src/

├── docs/

├── Cargo.toml

└── README.md

Master Layer는 실제 파일 시스템이다.

Harvest의 최종 목적지는 항상 Master Layer이다.

---

# Layer Model

## Layer Identity Rule

파일의 고유 식별자는 다음과 같다.

(Layer, File Path)

예:

(Master, src/main.ts)

(ClientA, src/main.ts)

(ClientB, src/main.ts)

동일 경로 파일은 Layer가 다르면 서로 다른 객체이다.

---

## Layer Coexistence

동일 파일이 여러 Layer에 존재하는 것은 정상 상태이다.

예:

Master

src/main.ts

Client A

src/main.ts

Client B

src/main.ts

이는 충돌이 아니다.

---

# Submission Model

## Submission Definition

Client는 프로젝트 전체를 제출하지 않는다.

Client는 자신이 수정한 파일만 제출한다.

예:

submission_xxx/

├── src/main.ts

└── src/auth.ts

Submission은 변경 파일 묶음이다.

---

## Submission Snapshot

Submission 생성 시 Snapshot이 생성된다.

Submission Snapshot은 생성 이후 절대 변경되지 않는다.

Client Workspace가 이후 변경되어도 Submission Snapshot은 영향을 받지 않는다.

Harvest는 항상 Submission Snapshot 기준으로 수행된다.

---

## Submission Structure

submission_xxx/

├── files/

└── metadata.json

---

## metadata.json

예시:

```json
{
  "submissionId": "submission_20260612_151530_4821",
  "clientId": "usr_alpha",
  "status": "PENDING",
  "createdAt": "2026-06-12T15:15:30Z",
  "fileCount": 2
}
```

---

## Submission State

* PENDING
* HARVESTED
* REJECTED

Submission은 삭제하지 않는다.

모든 Submission은 Audit Record이다.

---

## Submission ID Rule

Submission ID는 서버가 생성한다.

Client는 Submission ID를 생성하지 않는다.

Submission ID는 전역 유일해야 한다.

예:

submission_20260612_151530_4821

---

# Compare

## Definition

Compare는 Master Layer와 Submission Snapshot의 차이를 계산한다.

Compare는 파일을 수정하지 않는다.

Compare는 결과만 생성한다.

---

## Compare Trigger

Harvest 버튼을 누를 때 수행한다.

Workflow:

Harvest

↓

Compare

↓

Diff View

↓

Approval

↓

Harvest Execute

자동 Compare는 수행하지 않는다.

---

## Compare Scope

비교 대상:

Master Layer

VS

Submission Snapshot

Master는 항상 Source Of Truth이다.

---

## Compare Result

허용 상태:

* UNCHANGED
* MODIFIED
* ADDED

REMOVED 상태는 사용하지 않는다.

삭제는 Harvest의 범위가 아니다.

---

## Compare Algorithm

SHA256 기반 비교

예:

Master SHA256 = ABC

Submission SHA256 = ABC

결과:

UNCHANGED

---

Master SHA256 = ABC

Submission SHA256 = XYZ

결과:

MODIFIED

---

Submission만 존재

결과:

ADDED

---

## Compare Lifetime

Compare 결과는 휘발성 데이터이다.

서버 메모리에만 존재한다.

Harvest 화면을 닫으면 제거된다.

서버 재시작 시 유지되지 않는다.

Compare 결과는 Source Of Truth가 아니다.

---

# Diff Visualization

## Visual Rule

색상에 의존하지 않는다.

배지로 표시한다.

예:

main.ts [MODIFIED]

auth.ts [ADDED]

README.md [UNCHANGED]

---

## Compare Graph Rule

레이어 그래프에서 동일 경로의 파일이 존재하고 내용이 다를 경우 상태를 표시한다.

예:

src/main.ts [MODIFIED]

상태는 그래프와 파일 목록 양쪽에서 확인 가능해야 한다.

---

## VSCode Diff Integration

SYNAPSE는 Diff Viewer가 아니다.

SYNAPSE는 Diff Detector이다.

상세 변경 내용은 VSCode Diff 기능을 사용한다.

비교 대상:

Master Layer File

VS

Submission Snapshot File

Architect가 MODIFIED 파일을 선택하면 VSCode Diff View를 열 수 있어야 한다.

---

# Approval

## Approval Rule

승인 전에는 어떤 파일도 복사되지 않는다.

Compare

↓

Approval

↓

Harvest

---

## Approval Scope

파일 단위 승인

예:

[✓] src/main.ts

[✓] src/auth.ts

[ ] src/experimental.ts

Harvest는 승인된 파일만 복사한다.

---

# Harvest

## Definition

Harvest는 Copy Operation이다.

Submission Snapshot

↓

Master Layer

↓

파일 복사

---

## Harvest Target

복사 대상:

* MODIFIED
* ADDED

복사 제외:

* UNCHANGED

---

## Harvest Rule

Harvest는 승인된 파일만 복사한다.

Harvest는 판단하지 않는다.

Harvest는 복사만 수행한다.

---

## Harvest Does Not

Harvest는 다음 작업을 수행하지 않는다.

* Merge
* Auto Merge
* Conflict Resolution
* Delete
* Rename
* Refactor
* Rewrite
* Code Generation

---

# Harvest Failure Policy

Harvest는 SSH/SCP 파일 복사와 동일한 원칙을 따른다.

Harvest는 트랜잭션 시스템이 아니다.

Harvest는 Rollback을 수행하지 않는다.

예:

src/main.ts SUCCESS

src/auth.ts SUCCESS

src/config.ts FAILED

이미 성공한 복사는 유지한다.

실패 사실만 기록한다.

---

# Harvest Report

## Purpose

Harvest 결과를 Audit Record로 남긴다.

---

## Storage

.synapse/reports/

---

## Report Generation Rule

Compare만 수행한 경우 Report를 생성하지 않는다.

Harvest가 실제 수행된 경우에만 생성한다.

---

## Report Files

harvest_<timestamp>.md

harvest_<timestamp>.json

---

## Report Contents

* Harvest ID
* Submission ID
* Client ID
* Timestamp
* Harvested Files
* SUCCESS Files
* FAILED Files

---

# Synchronization Rule

Harvest는 Master Layer 갱신만 책임진다.

Harvest:

Submission Snapshot

↓

Master Layer

Harvest 성공이 Client Workspace 동기화를 의미하지 않는다.

---

## Optional Synchronization

동기화 기능이 구현되는 경우:

Master Layer

↓

Server

↓

Client Workspace

Harvest와 Synchronization은 별개의 기능이다.

---

## Server Driven Refresh

Server가 Harvest 이후 Client Workspace를 수정하는 것은 허용된다.

Server는 Client 파일을 저장할 수 있다.

Server는 Client 파일을 갱신할 수 있다.

그러나 이는 Harvest의 책임이 아니다.

별도 Synchronization 기능의 책임이다.

---

# Security Constraints

## Project Boundary Rule

Harvest는 PROJECT_ROOT를 절대 벗어날 수 없다.

허용:

src/main.ts

docs/spec.md

.synapse/reports/report.md

거부:

../../../etc/passwd

../../../home/user/file.txt

/etc/cron.d/job

---

## Submission Boundary Rule

Harvest는 Submission Snapshot만 사용한다.

Client Workspace를 다시 읽지 않는다.

---

# Final Definition

Architect(Server)는 유일한 Source Of Truth이다.

Master Layer는 Architect 프로젝트 자체이다.

Client는 변경 파일을 Submission Snapshot으로 제출한다.

Submission Snapshot은 Immutable 하다.

Compare는 Harvest 검토 시점에 수행된다.

Compare 결과는 휘발성 데이터이다.

Approval은 Architect가 수행한다.

Harvest는 승인된 파일만 복사한다.

Harvest는 삭제하지 않는다.

Harvest는 Merge하지 않는다.

Harvest는 Copy Operation Only 이다.

Harvest 이후에는 Audit 목적의 Harvest Report를 생성한다.
