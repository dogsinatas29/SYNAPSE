# SYNAPSE v0.3.30

# Phase3 — SSH Transport / Submission Boundary

## Purpose

Phase3 defines the collaboration boundary between Client and Server.

Connect is not collaboration start.

Connect is submission.

```text
Client Workspace
        ↓
Submission Snapshot
        ↓
Server Storage
        ↓
Review Pending
        ↓
Review Controlled
```

Phase3 defines how a completed workspace becomes a review artifact.

Phase3 does not perform analysis.

Phase3 does not perform verification.

Phase3 does not perform harvest.

# Submission Snapshot

The Submission Snapshot is a collaboration artifact.

```text
Submission Snapshot
≠ GraphSnapshot
```

```text
Submission Snapshot
≠ ViewSnapshot
```

```text
Submission Snapshot
≠ CanvasState
```

```text
Submission Snapshot
≠ ProjectState
```

Runtime snapshots are internal Synapse structures.

Submission Snapshot represents the exact state submitted by the client.

---

# Snapshot Principle

Submission Snapshot is not a visualization artifact.

Submission Snapshot is not a runtime artifact.

Submission Snapshot is not a working copy.

Submission Snapshot is the review baseline.

```text
Submission Snapshot
        ↓
Review
        ↓
Verify
        ↓
Harvest
```

The original snapshot remains immutable throughout the review lifecycle.

The snapshot serves as the authoritative record of what the client originally submitted.

---

# Review Controlled Principle

After submission:

```text
Member
=
Read Only
```

```text
Lead
=
Review Allowed
Remote Edit Allowed
```

The submission enters a review-controlled state.

The original snapshot remains immutable.

Review activities operate on the submitted workspace, not on the snapshot itself.

---

# Submission Authority

Client owns:

* Local Workspace

Server owns:

* Submission Snapshot
* Review State

Lead may temporarily modify the submitted workspace during review.

Lead does not modify the immutable snapshot.

---

# Remote Edit Principle

Lead possesses Remote Edit authority.

Remote Edit operates on the client's physical source files.

Examples:

* Fix incorrect import
* Fix file name mismatch
* Fix reference mismatch
* Fix path mismatch
* Apply small integration corrections

Remote Edit is intended for review-time corrections.

It is not intended to replace normal development workflow.

Remote Edit produces a modified workspace.

The original snapshot remains preserved as submitted evidence.

---

# Review Model

```text
Original Submission Snapshot
        ↓
Immutable Baseline
        ↓
Lead Review
        ↓
Lead Remote Edit
        ↓
Corrected Workspace
```

The corrected workspace may differ from the original snapshot.

The original snapshot remains available for comparison and audit purposes.

# Server Authority

Server owns:

* Submission Snapshot
* Review State
* Verification State
* Harvest State

Server does not own:

* Client Identity

Server may temporarily obtain review-time edit authority over submitted work through Lead permissions.

---

# Storage Model

Submitted work is stored by the server.

Purpose:

* Review
* Verification
* Harvest Preparation

Storage does not imply Harvest.

Storage does not imply Acceptance.

Storage only preserves the submitted state.

The original submission snapshot must remain available throughout the review lifecycle.
