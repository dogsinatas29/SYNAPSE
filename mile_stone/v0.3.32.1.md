# v0.3.32.1 설계 (최종)

## Goal

Flow View를 DAG Layout에서 Semantic Flow Layout으로 전환한다.

## Principle

1. **START를 포함하는 Connected Component = Main Flow**
2. **START에 도달할 수 없는 Component = Detached Flow**
3. **Detached Flow는 종류에 따라 Zone으로 분리: Client Zone / Orphan Zone**
4. **각 Zone 내부에서 기존 BFS Layering 유지**

## Pipeline

```
buildFlow (기존 유지)
    ↓
buildConnectedComponents (신규)
    ↓
classifyZones (신규)
    ↓
layoutFlow (Zone별 Y 오프셋 적용)
    ↓
renderFlow (Zone 구분선 렌더링)
```

## Zone Rules

```
Main Flow
START → ... → END

Client Zone
test_network.ts → TEST_network.ts

Orphan Zone
isolated_file.ts
```

# Phase 8: Connected Component 검증 (2026-06-26)

## 테스트 결과

### 서버 단독 실행
```
Component #0 size=265 hasStart=true hasClient=false
```

### 클라이언트 접속 후
```
Component #0 size=269 hasStart=true hasClient=false
```

## 해석

1. **Component가 1개뿐** — client 노드 4개가 메인 그래프와 같은 Connected Component에 편입됨
2. **size 265 → 269** — client 노드 4개가 Flow 데이터셋에 정상 진입
3. **hasClient=false** — step ID가 `client::...`가 아니라 `step_N` 형식이라 검출 실패 (진단 버그)

## 결론: Connected Component 분리 가설 — 아직 확정 불가

1개의 Component로 나왔지만, 이는 client 노드가 메인 그래프와 약한 edge로 연결되어 있을 가능성을 배제하지 않음.

다만 client 노드가 완전히 분리된 서브그래프라는 가설은 기각.

# Phase 9: START의 의미 재분석 (2026-06-26)

## 핵심 발견: START는 장식에 가까움

### 현재 Root 선택 로직 (line 93)
```javascript
const roots = nodes.filter(n => !inDegrees[n.id] && n.type !== 'external');
```

→ **순수 topology 기반.** in-degree=0인 노드 전부가 root.

### Root 정렬 (line 96-108)
```javascript
const isPriority = (name) => name.includes('main.') || name.includes('app.') || name.includes('index.');
```

→ `main/app/index`를 **앞으로** 정렬. 하지만 **선택**이 아니라 **정렬**. 모든 in-degree=0 노드가 여전히 root.

### START 연결 (line 234-243)
```javascript
steps.push({
    id: 'step_start',
    allNexts: rootStepIds  // 모든 root 노드에 연결
});
```

→ START → **모든 root** (mod, rules, spec, campaign, constraint_meta... 전부)

## 현재 START 메커니즘 분석

| 주장 | 사실 |
|------|------|
| "START는 진짜 시작점이다" | ❌ 장식에 가까움 |
| "START에서 의미적 흐름이 시작된다" | ❌ in-degree=0 노드 전부에 연결 |
| "Entry Point를 알고 있다" | ❌ topology만 보고 semantics 모름 |
| "main/app/index를 우선한다" | ⚠️ 정렬만, 선택 아님 |

## 현재 Flow View의 한계

> "연결된 노드들의 DAG"는 만들 수 있지만
> "프로그램의 시작점에서 흘러가는 실행 흐름"은 만들 수 없다.

현재 시스템은 **"어디서 시작되는지 모른다"**가 더 정확한 표현.

## v0.3.32.1 설계 수정 필요

### 기존 설계
```
Connected Component Classification → Zone Based Placement
```

### 수정된 설계
```
Entry Point Resolver (최우선)
    ↓
Connected Component Classification
    ↓
Zone Based Placement
```

**첫 번째 구현 항목은 Client Zone도 아니고 Layer도 아닌, Entry Point Resolver.**

```text
1. extension.ts
2. main.ts
3. index.ts
4. user-selected entry
```

중 하나를 강제로 선택하고, 그 노드에서 `ENTRY → reachable → END`를 만들어야 합니다.

그 없이는 지금처럼 `mod, rules, spec, campaign, constraint_meta`가 전부 같은 급의 root로 취급됩니다.

# Phase 11: Entry Point Resolver 구현 (2026-06-26)

## 구현 내용

### Step 1 — Entry Point Resolver (`ui/canvas-engine.js`)

`buildFlow()` 내 Root 선택 로직 수정:

**수정 전:**
```javascript
const roots = nodes.filter(n => !inDegrees[n.id] && n.type !== 'external');
// + 정렬 로직
```

**수정 후:**
```javascript
const entryPoint = nodes.find(n => n.data?.file?.match(/extension\.[tj]s$/))
    || nodes.find(n => n.data?.file?.match(/main\.[tj]s$/))
    || nodes.find(n => n.data?.file?.match(/index\.[tj]s$/))
    || null;

let roots;
if (entryPoint) {
    roots = [entryPoint];  // Entry Point 단일 root
} else {
    // 기존 in-degree=0 + 정렬 fallback
}
```

### Step 2 — START 연결 (기존 유지)

START의 `allNexts: rootStepIds`가 이미 `roots`를 기반으로 하므로, roots가 `[entryPoint]`만 포함하면 자동으로 START → Entry Point 단일 연결.

### Step 3 — Checkpoint A 로그

```javascript
// [Checkpoint A] START → Entry Point 흐름 검증
const startStep = steps.find(s => s.id === 'step_start');
const startNextLabels = (startStep?.allNexts || []).map(id => {
    const s = steps.find(x => x.id === id);
    return s ? s.label : id;
});
console.log("[FLOW_DEBUG] CHECKPOINT_A START.next", startNextLabels);

// START에서 5단계까지 추적
let traceId = startStep?.next;
const trace = ['START'];
for (let i = 0; i < 5 && traceId; i++) {
    const s = steps.find(x => x.id === traceId);
    if (!s) break;
    trace.push(s.label);
    traceId = s.next;
}
console.log("[FLOW_DEBUG] CHECKPOINT_A trace", trace.join(' → '));
```

### 추가된 진단 로그

```javascript
console.log("[FLOW_DEBUG] entryPoint", entryPoint?.data?.file || "null");
console.log("[FLOW_DEBUG] roots count", roots.length);
console.log("[FLOW_DEBUG] roots files", roots.slice(0, 10).map(r => r.data?.file || r.id));
```

## Phase 19: Simplified Layout 구현 (2026-06-27)

### 문제

기존 X축 balancing 알고리즘 (`parentsMap`, `parentOffsetSum`, `spiral search`)이 DAG 구조를 왜곡시킴.
END가 sink 노드임에도 불구하고 리프 노드들의 평균 위치로 끌려가며 레이아웃 붕괴.

### 해결

복잡한 X축 balancing 로직 전체 제거.
순수 레벨 기반 그리드 배치로 단순화:

```js
// [v0.3.32.1] Simplified Layout: Pure level-based grid
const nodesByLevel = {};
flow.steps.forEach(step => {
    const lvl = levels[step.id] || 0;
    if (!nodesByLevel[lvl]) nodesByLevel[lvl] = [];
    nodesByLevel[lvl].push(step.id);
});

// Simple grid assignment: x = index * stepWidth, y = level * stepHeight
Object.keys(nodesByLevel).sort((a, b) => a - b).forEach(lvl => {
    const levelNum = parseInt(lvl);
    const nodesInLevel = nodesByLevel[lvl];
    nodesInLevel.forEach((nodeId, idx) => {
        const x = startX + (idx * stepWidth);
        const y = startY + (levelNum * stepHeight);
        positions[nodeId] = { x, y };
    });
});
```

### 제거된 요소

- `parentsMap` (역방향 인접 맵)
- `offsets` (오프셋 계산)
- `occupied` (충돌 회피)
- `spiral search` (빈 슬롯 탐색)
- `root centering` (루트 노드 중앙 정렬)

### 목표

예측 가능한 계층형 레이아웃으로 DAG 구조 검증.
추후 crossing minimization 등 최적화는 구조 검증 후 단계적 도입.

### 2. Kahn's 알고리즘 순환(Cycle) 방어 로직 구현
- **문제 진단:** `processedCount 3 / 60` 상태로 정렬이 멈추는 현상 발생. 원인은 입력 그래프가 완전한 DAG가 아니라 루프(LOOP)와 분기 역방향 엣지가 섞여 있었기 때문.
- **조치 사항:** 
  - 위상 정렬 계산 직전에 가벼운 **DFS(깊이 우선 탐색)**를 수행하여 역방향 엣지(Back-edges)를 식별(`backEdges` 집합에 저장).
  - `inDegree` 및 `adj`(인접 리스트)를 구성할 때 이 식별된 역방향 간선들을 무시(필터링)하도록 로직 수정.
  - 실제 렌더링에 필요한 `next`, `alternateNext` 데이터는 원본 그대로 보존하여 시각적 손실(연결선 누락) 없이 오직 **"계산용 그래프"에서만 사이클을 끊어냄**.
- **효과:** 
  - Kahn 알고리즘이 교착(Deadlock)에 빠지지 않고 모든 노드(60/60)를 성공적으로 순회.
  - Flow View의 레벨(계층) 연산 정상화.

### 3. 사이클(Back-edge) 노드 시각화 (Phase A)
- **조치 사항:** `layoutFlow`에서 추출된 `backEdges` (루프 및 역참조 간선들)를 렌더링 단계로 전달.
- **효과:** `renderConnection` 시 역방향 사이클 간선을 감지하여 붉은색(`Gruvbox Red`, `#fb4934`) 점선(`[8, 4]`)으로 강렬하게 시각화.
- 사용자는 화면 상에서 어떤 연결이 아키텍처 상향/루프 구조를 띠고 있는지 한눈에 확인할 수 있게 됨.

### 4. Barycenter Ordering (Phase 1) 도입
- **문제 진단:** `v0.3.32.1`에서 위상 정렬 마비 사태를 해결하여 모든 노드를 렌더링하는 데 성공했으나, 기존 `idx % MAX_COLS` 방식의 임의적 가로(X축) 배치로 인해 엣지(연결선) 교차가 극심하여 가독성이 떨어짐.
- **조치 사항:** Sugiyama 레이아웃 알고리즘의 2단계인 **Barycenter Ordering (무게 중심 기반 정렬)**을 Single-pass (위에서 아래로 1회) 방식으로 구현.
  - 기존의 `MAX_COLS` 강제 줄바꿈(Wrapping) 구조를 폐기하고 순수한 Layer(계층) 구조 유지.
  - 각 노드의 X축 배치 순서를 결정할 때, 이전 계층(Level - 1)에 존재하는 **부모 노드들의 평균 X 인덱스(Barycenter)**를 계산하여 정렬.
  - 루트 부근의 노드들(`parents.length === 0`)은 기존 순서를 그대로 보존하여 상단 배치가 흔들리지 않도록 보장.
  - 각 레이어의 너비를 계산하여 한가운데(`startXCentered`)를 기준으로 노드를 전개(Row Centering).
- **효과:** 부모-자식 간의 물리적 X좌표가 최대한 가깝게 정렬되어 **일반 엣지 교차(Edge Crossings)가 눈에 띄게 감소**하고 다이어그램 가독성이 획기적으로 상승함. Multi-pass 최적화는 v0.3.33으로 연기됨.
