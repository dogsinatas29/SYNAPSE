## 🧠 상세 설계 및 로직 (Architectural Plan)

### 🚨 배경 및 문제 의식 (The Monolith Trap)
현재 `FileScanner.ts`와 `ReferenceVerifier.ts` 내부에 Python, Java, Kotlin, Rust, C++, TS 등의 파싱 규칙과 Ghost Rule(예: `EXTERNAL_PACKAGES` 하드코딩)이 한데 얽혀 있습니다. 
최근 Android(Java/Kotlin) 대응을 진행하며 플랫폼 특화 로직이 코어(Node/Edge 생성 및 렌더링)에 영향을 미치기 시작했습니다. 이는 전형적인 **Resolver Monolith**의 한계이며, 규모가 큰 프로젝트(Django Monorepo, Unreal Engine 등)에서 발생할 "그래프 렌더링 및 클러스터링 이슈"를 "언어별 파서 문제"와 혼동하게 만드는 끔찍한 디버깅 지옥을 초래할 수 있습니다.

### 🏗️ 1단계: 인터페이스 정의 및 구조 분리 (Core Definition)
모든 언어별 파서 로직을 걷어내어 독립된 `Provider (Frontend)`로 분리하고, 코어 엔진은 오직 공용 규격인 `DependencyFact` IR만 소비하도록 구조를 개편합니다.

```typescript
// 1. 공통 IR (Intermediate Representation) 규격
export interface DependencyFact {
    source: string;
    target: string;
    type: string;          // 'dependency' | 'api_call' | 'db_query' 등
    ghost: boolean;        // 해당 언어 Provider가 판단한 Ghost 여부
    strength: number;      // 결합도 강도 (Optional)
}

// 2. Language Frontend Interface
export interface LanguageFrontend {
    // 1. 타겟 언어의 파일들을 수집
    discoverFiles(workspacePath: string): string[];

    // 2. 파일에서 클래스/함수 추출
    extractSymbols(content: string, filePath: string): SymbolInfo[];

    // 3. 의존성 및 외부 패키지 식별
    extractDependencies(content: string, filePath: string): DependencyFact[];

    // 4. 언어별 특수 Ghost Rule 정의 (예: android.*, java.*)
    getGhostRules(): string[];
}
```

                    ├───────────────┤

### 🛠️ 3단계: 점진적 적용 및 검증 순서 (Execution Phasing)
가장 안전한 디버깅을 위해 언어를 한 번에 추가하지 않고 다음 순서로 쪼개어 작업합니다.

- **P0. 인터페이스 추출 및 코어 분리 (Refactoring Core):** `LanguageFrontend` 인터페이스와 `DependencyFact` 정의, `FileScanner`/`ReferenceVerifier` 내부를 플러그인(Provider) 방식으로 리팩토링.
- **P1. 기존 Android(Java/Kotlin) Provider 이관 및 정상 동작 복구:** 가장 복잡했던 안드로이드 룰(`android.*`, `androidx.*`)을 `AndroidFrontend`로 격리하고 코어 파이프라인(클러스터링, 렌더링)이 문제없이 도는지 검증.
- **P2. Workspace Persistence 보장 검증:** 언어 분리 후에도 상태 스냅샷 저장 및 복구가 무결한지 확인.
- **P3. Python Provider 추가:** `PythonFrontend` 분리.
- **P4. Rust Provider 추가:** `RustFrontend` 분리.
- **P5. C/C++ Provider 추가:** `CppFrontend` 분리.

## ⚠️ 예외 처리 및 주의 사항
- **Ghost Rule 이관:** 기존 `ReferenceVerifier.ts`에 존재하던 하드코딩된 `EXTERNAL_PACKAGES`는 코어에서 삭제하고, 각 언어 `Provider`의 `getGhostRules()` 리턴값 또는 `extractDependencies` 단계의 `ghost: true` 플래그로 완전히 책임을 위임해야 합니다.
- **코어의 무지(Ignorance):** SYNAPSE 코어는 더 이상 "이 파일이 파이썬인지 텍스트인지" 알 필요가 없습니다. 오로지 주입받은 Provider가 던져주는 `DependencyFact`만을 신뢰하며 공간을 분할(Continent)하고 렌더링에만 집중합니다.

### 🛑 [Review Note] 이전 접근의 한계 및 교정 방향
- **빈 파일(AST) 검증의 한계:** 앞서 "파서가 죽지 않는다"는 점은 증명했으나, 정작 중요한 것은 `tokio`, `fastapi`, `app.services` 같은 식별자가 **내부 의존성인지, 외부 프레임워크인지, Ghost인지 판별하는 리졸버(Resolver)의 정확성**에 있었습니다.
- **화이트리스트(EXTERNAL_PACKAGES)의 한계:** 언어별로 수십 개 패키지를 하드코딩해봤자, 실제 대형 사내 모노레포에 들어가면 대응이 불가합니다. 이 부분은 향후 **언어별 패키지 매니저 (`package.json`, `requirements.txt`, `Cargo.toml` 등)**를 기반으로 동적 판별하는 방향으로 리팩토링 되어야 합니다.
- **Dynamic Extension Inference의 위험성:** 70%가 `.ts`인 프로젝트에서 사용자가 `.py` 파일을 원할 때 자동 할당해버리는 것은 위험한 추론이었습니다. 이 코드는 방금 즉시 폐기하고, 확장자 없는 노드 생성 시 **VS Code의 QuickPick (드롭다운)** 창을 띄워 유저에게 직접 확장자를 묻도록 안전하게 롤백 및 재구현했습니다.

### 💎 [Architectural Refinement] 생태계(Ecosystem) 기반 의존성 분류 및 Workspace 분리
과거 AXON의 실패(리졸버 분리 실패)를 거울삼아, 단순한 `ghost=true/false` 로직을 폐기하고 다음과 같이 아키텍처를 고도화합니다.

1. **DependencyKind 분류 도입:** 
의존성을 단순히 고스트냐 아니냐로 판별하지 않고 생태계 계층에 맞게 분류합니다.
```typescript
enum DependencyKind {
    LOCAL,         // 프로젝트 내부 (예: import { User } from '@/domain')
    STDLIB,        // 언어 표준 라이브러리 (예: #include <vector>, from typing import Optional)
    THIRD_PARTY,   // 외부 라이브러리 (예: use tokio::sync::Mutex)
    FRAMEWORK,     // 거대 프레임워크 (예: import React from 'react')
    GENERATED,     // 빌드 시 생성 파일 (예: Android R.java, protobuf)
    GHOST          // 분석 무가치 대상 (예: android.content.Context)
}
```

2. **WorkspaceResolver 계층 독립:**
단일 `package.json` 파싱은 모노레포(pnpm workspace, Turborepo, Nx, Cargo members, Gradle subprojects) 환경에서 완벽히 깨집니다. 
따라서 `LanguageFrontend` 내부에 패키지 파서를 두는 대신, 별도의 **`WorkspaceResolver` 계층**을 신설하여 모노레포 구조를 전역적으로 파악한 후 분류(`DependencyClassification`)를 수행합니다.

```text
  [ Language Frontend ]
           ↓ (DependencyFact)
  [ Workspace Resolver ] (Monorepo & Package Manager 분석)
           ↓ (DependencyClassification)
  [ Graph Builder & SYNAPSE CORE ] (Subcluster, Traffic, Semantic)
```

3. **작업 및 이관 순서 (안정성 최우선):**
리팩토링 도중 0.3.32.2의 핵심 기능(노드 생성/삭제, 스냅샷, 서브클러스터)이 오염되는 것을 막기 위해 안드로이드 이관을 맨 마지막으로 미룹니다.
- **1순위:** Resolver Core 추출 (`src/core/resolver/` 디렉토리 신설)
- **2순위:** TS Resolver 이관 (기존 동작 그대로 유지, 기능 변화 없음)
- **3순위:** 0.3.32.2 기능 회귀 테스트 (노드/엣지 생성/삭제, 스냅샷 등 코어 파이프라인 무결성 확인)
- **4순위:** Python Resolver 추가
- **5순위:** Rust Resolver 추가
- **6순위:** Android(Java/Kotlin) Resolver 이관 (가장 복잡한 룰셋을 아키텍처가 증명된 마지막에 탑재)
