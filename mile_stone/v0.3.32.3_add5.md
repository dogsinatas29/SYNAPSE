# Milestone v0.3.32.3_add5 - Cluster Collapse Protocol & Validation

---

## 1. 개요 (Overview)
**목표**: `Cache Build` 병목(약 5초)을 해결하기 위해 고안된 **Cluster Collapse** 가설을 실제 런타임 구현(v0.3.32.4) 전에 사전 검증한다.
**핵심 질문**: "실제로 클러스터 내부 노드와 엣지를 제거(Collapse)해서 웹뷰로 넘겼을 때, 우리가 기대하는 수치(Cache Build Time 80% 이상 감소)가 정확히 나오는가?"
**결론**: 이 실험 결과에 따라 v0.3.32.4의 개발 방향(Cluster Runtime vs Edge Virtualization vs Spatial Index Worker)이 확정된다.

---

## 2. 진단 및 검증 절차 (Add5 Protocol)

### Step -1: Current State Baseline Capture
Collapse 적용 전, 원본 상태의 계측 결과를 먼저 수집하여 기준점(Baseline)으로 삼는다.
선형성 검증을 위해 10K, 15K, 20K 노드에 대해 각각 벤치마크를 실행한다.
- `benchmark/baseline_10k.json`
- `benchmark/baseline_15k.json`
- `benchmark/baseline_20k.json`

(단, 노드 수 외에 **Edge Density = Edges / Nodes** 수치를 반드시 함께 기록하여 밀도 차이로 인한 변수를 통제한다)

### Step 0: Cache Build Breakdown (계측 세분화)
현재 통합된 `Webview Load` 시간 중 `Cache Build`에 소요되는 시간을 프론트엔드(`loadProjectState`) 단에서 다음의 핵심 단계로 분해하여 측정한다.
- **Node Cache**: 노드 객체 순회 및 초기화
- **Edge Cache**: 엣지 객체 순회 및 Lookup Map 생성
- **Cluster Cache**: 클러스터 연산
- **Spatial Index**: QuadTree 등 공간 검색 캐시 생성
- **Label Cache**: 라벨 렌더링을 위한 텍스트 메트릭 측정 및 캐싱

**Total 검증 룰:**
`Node + Edge + Cluster + Spatial + Label + Other = Total Cache Build`를 보장하여 누락된 시간을 `Other`로 추적한다.

### Step 0-A: Cache Memory Attribution
각 Cache Build 단계 전후의 Heap Used 변화량을 측정한다.
*주의: JS GC 개입으로 인해 음수가 발생할 수 있으므로, Memory 지표는 '참고 지표(보조 증거)'로만 사용하고 최종 의사결정은 Time Attribution(CPU 시간)을 최우선 기준으로 삼는다.*

### Step 0-B: Complexity Estimation (Growth Ratio)
Baseline 결과(10K, 15K, 20K)를 통해 각 컴포넌트의 시간 복잡도(O)를 사전에 추정한다.

| 시간 복잡도 | 10K -> 15K 예상 증가율 | 15K -> 20K 예상 증가율 | 조치 |
| --- | --- | --- | --- |
| **Linear (O(N))** | 1.50x | 1.33x | 정상 (무시 가능) |
| **N log N** | 1.6~1.8x | 1.4~1.6x | 주의 |
| **Quadratic (O(N²))** | 2.25x | 1.78x | **최우선 제거 타겟** |

### Step 1: Collapsed Cluster 구현 (Backend Mocking - 3-way Split)
페이로드 변형에 따른 성능 변화를 독립적으로 추적하기 위해 실험을 3가지로 분리한다.
- **Experiment A (Node Collapse Only)**: 클러스터 내부 Node만 제거
- **Experiment B (Edge Collapse Only)**: 클러스터 내부 Edge만 제거
- **Experiment C (Node + Edge Collapse)**: Node 및 Edge 모두 제거

### Step 2: Payload 및 Deserialize 비교
직렬화된 JSON 문자열의 전체 크기(MB)와 `JSON.parse` 시간을 벤치마크한다.

### Step 2-A: Payload Attribution (객체 크기 상세 분석)
전체 페이로드 중 각 구성요소가 차지하는 용량 비율(%)과 평균 객체 크기(Bytes/Object)를 파악한다.
```text
Payload Breakdown (Example)
Nodes:   4.1MB (15.8%) | Count: 20000 | Avg: 215 bytes/node
Edges:  18.7MB (71.9%) | Count: 80000 | Avg: 245 bytes/edge
Clusters: 0.9MB (3.4%) | Count: 500
```

### Step 3: Cache Build 감소 효과 검증 (비율 % 포함)
새롭게 주입된 세분화 계측기를 통해, 감소된 엣지 및 노드 처리가 실제 Cache Build 시간을 얼마나 단축시켰는지 컴포넌트별 절대값(ms)과 비중(%)을 모두 산출한다.
```text
Cache Build Total = 5126ms

Edge Cache      2510ms (48.9%)
Spatial Index   1420ms (27.7%)
Node Cache       610ms (11.9%)
Label Cache      310ms (6.0%)
Cluster Cache    140ms (2.7%)
Other            136ms (2.6%)
```

### Step 4: Scaling Correlation Check (비례성 검증)
노드/엣지 제거율(Collapse Ratio)과 Cache Build 감소율의 상관관계를 각 Experiment (A, B, C) 별로 계산한다.

### Step 5: Root Cause Classification
상관관계 결과를 바탕으로 측정된 Cache Build 시간 중 **가장 비중이 높은 컴포넌트(Top Contributor)**를 식별하여 최종 병목의 성격을 확정한다.

### Step 6: Architecture Decision Rules (Exit Criteria)
도출된 증거를 바탕으로 다음의 Hard Rule에 따라 `v0.3.32.4_decision.md`를 작성하고 다음 개발 마일스톤을 확정한다.

**Decision Rules**:
- **IF** (Top1 - Top2 < 10%) **OR** (Top1 40~50% AND Top2 > 30%)
  ➜ **Mixed Architecture (복합 최적화)** 채택 (단일 원인 확정 금지)
- **IF** (Edge Cache > 50% of Cache Build) **OR** (Edge Payload > 50% of Payload) **OR** (Experiment B Improvement > 70%)
  ➜ **Edge Runtime 우선 최적화**
- **IF** (Spatial Index > 50% of Cache Build)
  ➜ **Spatial Runtime 분리 우선**
- **IF** (Node/Cluster Cache > 50% of Cache Build) **OR** (Experiment A Improvement > 70%)
  ➜ **Cluster Runtime 도입 (현 기조 유지)**
