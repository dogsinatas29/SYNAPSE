## 🎯 최종 DataPipeline 오케스트레이터 스냅샷 (v0.3.32.3 완료)

410줄의 비대했던 `DataPipeline`이 순수 오케스트레이터로 성공적으로 탈바꿈했습니다 (현재 245줄). 이제 파이프라인은 8단계의 거시적 데이터 흐름 제어에만 집중합니다.

### 🧬 DataPipeline 8단계 파이프라인
1. **Scan**: `GraphAnalyzer`를 통한 노드/클러스터 기본 구축 및 참조 목록 추출.
2. **Policy**: `GhostPolicy`를 호출하여 불필요한 참조를 1차 필터링 (Pure).
3. **Resolve**: `ReferenceResolver`로 최종 Target ID와 출처 확정 (Pure).
4. **Expand**: `GhostExpander`를 통해 미해결 참조를 능동적 Ghost 엔티티로 확장 (Pure).
5. **Build**: `EdgeBuilder`로 엣지 객체들을 조립 (Pure) 및 DataPipeline 상태에 순수 결과들 주입(Inject).
6. **Analyze**: `analyzeGraph()`로 그래프 차수, 밀도, 방향성 트래픽 계산.
7. **Layout**: `LayoutEngine`을 호출하여 물리적/논리적 좌표(Layout) 및 클러스터 BoundingBox 도출.
8. **Community**: `CommunityDetector`로 그룹 매핑 산출, 이후 DataPipeline이 최종 노드에 상태 주입(Inject).
9. **Diagnostics & Output**: 파생 정보들을 수집하여 Reporter를 호출하고 진단 로그 파일 작성.

### 📝 향후 방향성 (Next Milestone)
현재 `DataPipeline`은 충분히 "좋은 구조" 영역에 진입하였으며, DI (Context) 도입이나 Reporter 병합 등의 2j 단계 리팩토링은 한계 효용(ROI)이 낮아 당분간 유보합니다. 다음 마일스톤은 실제 프로덕트 가치를 창출할 수 있는 기능 개발(Harvest, Interaction, Graph UX, Performance, Security 등)로 복귀할 것을 권장합니다.

## [2026-07-03] Viewport Culling & LOD Optimization (버전 0.3.32.3 대응)

### 1. 병목 원인 분석
- 15K 노드와 60K 엣지를 렌더링하는 과정에서 화면 밖에 있는 노드와 엣지까지 모두 Canvas API(`ctx.stroke()`, `ctx.fillText()` 등)로 렌더링을 시도하여, `RenderCall` 시간이 2470ms까지 치솟는 문제(O(N) 순회 오버헤드) 확인.

### 2. 최적화 로직 적용 (Viewport Culling & LOD)
- **Edge Culling (`renderEdges2D`)**: 카메라 Viewport Bounding Box를 계산하여 엣지의 양 끝점 Box와 교차하지 않으면 즉시 스킵.
- **Node Culling (`renderNodes2D`)**: 노드 좌표가 화면 영역 밖에 있으면 렌더링 생략.
- **Cluster & Ghost Node Culling**: 동일한 Viewport 검사를 통해 불필요한 Canvas 연산 원천 차단.
- **WebGL Hybrid Badge Culling**: 배지(Badge) 렌더링 시 투영된 스크린 좌표가 화면 밖이면 렌더링 생략.
- **Fallback LOD (Level of Detail)**: Zoom 레벨이 0.35 이하일 때 번들 엣지가 없고 개별 엣지가 2000개를 초과하면 프레임 방어를 위해 렌더링 스킵 적용.

### 3. 성능 검증 결과 (2026-07-03, 138초 DevTools 프로파일링)

| 항목 | 값 |
|---|---|
| 총 녹화 시간 | **138초** |
| Main Thread Active Time | **4.37초 (3.2%)** |
| Scripting | 818ms |

**핵심 결론:** 138초 동안 CPU를 3.2%밖에 사용하지 않았다. Viewport Culling이 정상 작동 중이며, 현재 병목은 SYNAPSE 렌더링 알고리즘이 아니라 벤치마크의 대용량 반복 IPC 전송(GC 압박)이다.

#### FPS 구간별 관측 결과
