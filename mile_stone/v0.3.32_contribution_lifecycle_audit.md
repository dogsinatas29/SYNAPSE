# 2. Contribution Identity

## Canonical Identity (Compare~Harvest 구간)

```
(filePath, userId)
```

## Evidence

CompareEngine은 `visibleClientIds`를 순회하며 각 클라이언트의 파일을 개별 CompareResult로 생성한다.

```typescript
// CompareEngine.ts:35-61
for (const clientId of visibleClientIds) {
    for (const cFile of clientHashes) {
        results.push({
            filePath: relPath,
            state: 'ADDED' | 'MODIFIED',
            clientUsername: username,
            userId: clientId
        });
    }
}
```

동일 `src/foo.ts`라도 alice와 bob이 각각 제출하면 별도 CompareResult 2개가 생성된다.

```
alice/src/foo.ts → CompareResult { filePath: "src/foo.ts", userId: "alice" }
bob/src/foo.ts   → CompareResult { filePath: "src/foo.ts", userId: "bob" }
```

## Identity Preservation Matrix

| Field | filePath | userId | clientUsername |
|-------|----------|--------|----------------|
| `CompareResult` | ✅ | ✅ | ✅ |
| `HarvestCandidate` | ✅ | ✅ | ✅ |
| `HarvestResult.harvestedFiles` | ✅ | ❌ | ❌ |
| `HarvestResult.harvestedClients` | ❌ | ❌ | ✅ |
| `HarvestResult.failedFiles` | ✅ | ✅ | ✅ |
| `History Snapshot` | ✅ | ❌ | ❌ |

## Caveat

Compare~Harvest 구간에서는 `(filePath, userId)`가 유지되나,
Archive 단계에서는 `filePath`만 보존된다.

```
Compare Domain:  Identity = (filePath, userId)
Archive Domain:  Identity = filePath
```

이 차이는 v0.3.32 설계에서 중요하다.
FlowRenderer가 `Compared → Harvested → Archived`를 하나의 Entity로 연결하려면
현재 저장 구조만으로는 완전한 추적이 불가능할 수 있다.

# 4. Runtime Transformations

## CompareResult → HarvestCandidate

```
CompareResult[]
    ↓
    Architect Selection (UI Action)
    ↓
HarvestCandidate[]
```

이 변환에는 런타임 상태 머신이 존재하지 않는다.
Architect가 UI에서 CompareResult를 선택하여 HarvestCandidate로 변환하는 행위만 존재한다.

## HarvestCandidate → HarvestResult

```
HarvestCandidate[]
    ↓
    HarvestEngine.harvest()
    ↓
HarvestResult
```

## HarvestResult → History Snapshot

```
HarvestResult
    ↓
    synapse_history.json 저장
    ↓
History Snapshot { id, timestamp, label, data: HarvestResult }
```

# 7. Actual Pipeline (코드 역추적)

```
POST /api/client/push
    ↓ (clientPushData Map 저장 + 영속화)
    ↓ (Canvas 렌더링용, Harvest 파이프라인 미참여)

POST /api/harvest/start
    ↓ hsm.startSession()
    ↓ state → Locked
    ↓ SSE broadcast: session_locked

POST /api/harvest/compare
    ↓ hsm.transitionState(Locked, Comparing)
    ↓ SSE: request_hashes → 클라이언트 해시 요청
    ↓ CompareEngine.compare() → CompareResult[] 생성
    ↓ hsm.transitionState(Comparing, Approving)

POST /api/harvest/execute
    ↓ hsm.transitionState(Approving, Executing)
    ↓ hsm.transitionState(Executing, Harvesting)
    ↓ SSE: send_file_content → 클라이언트 파일 요청
    ↓ HarvestEngine.harvest(candidates, requestClientFile)
    ↓ synapse_history.json → snapshot 저장
    ↓ SSE broadcast: session_unlocked
    ↓ hsm.unlockSession()
```

# 9. Open Design Questions

## Q1: Archive 단계에서 Contribution Identity를 보존할 것인가?

현재 `HarvestResult.harvestedFiles`는 `string[]`이다.
`filePath`만 보존하고 `userId`는 손실된다.

만약 v0.3.32에서 Archive까지 완전한 추적을 원하면
`HarvestResult` 구조를 변경해야 한다.

## Q2: Flow View는 Compare Domain을 시각화하는가?

Compare~Harvest 구간에서는 `(filePath, userId)`가 유지된다.
Flow View가 이 구간만 시각화하면 Identity Loss 문제는 발생하지 않는다.

## Q3: Archive → Flow View 연결 시 Identity Loss를 허용하는가?

Archived 상태에서는 `filePath`만 보존된다.
Flow View가 `Compared → Harvested → Archived`를 하나의 Entity로 연결하면
Archive 단계에서 userId 정보가 사라진다.

이 Loss를 허용할 것인지, 아니면 HarvestResult 구조를 변경할 것인지 결정해야 한다.

# Conclusion

v0.3.32의 Flow Subject는 **Contribution Lifecycle**이다.
런타임에서 확인된 상태는 **Compared, Harvested, Archived** 3개이다.
Canonical Identity는 **(filePath, userId)**이며, Archive에서 **filePath**로 축소된다.

이 감사 결과를 바탕으로 v0.3.32_goal.md를 수정할 수 있다.
