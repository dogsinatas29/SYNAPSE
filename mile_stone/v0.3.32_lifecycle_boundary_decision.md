# SYNAPSE v0.3.32

## Lifecycle Boundary Decision

ADR (Architecture Decision Record)

---

# Problem

Contribution Lifecycle의 끝(boundary)을 어디로 정의할 것인가?

현재 Audit에서 확인된 런타임 상태:

```
Compared → Harvested → Archived
```

그러나 Archived 시점에서 Contribution Identity가 축소된다.

```
Compare~Harvest: Identity = (filePath, userId)
Archive: Identity = filePath (userId 손실)
```

Flow View가 Lifecycle 전체를 시각화하려면
이 Identity 축소 문제를 먼저 해결해야 한다.

---

# Decision Criteria

Flow View는 무엇을 우선해야 하는가?

| # | Criteria | Definition |
|---|----------|------------|
| 1 | **Runtime Fidelity** | 실제 런타임 객체를 그대로 표현하는가 |
| 2 | **Identity Preservation** | Lifecycle 전체에서 동일 Entity 추적이 가능한가 |
| 3 | **Lifecycle Completeness** | 시작과 끝이 모두 표현되는가 |
| 4 | **Projection Simplicity** | 기존 구조 변경 없이 투영 가능한가 |

---

# Option A — Runtime Contribution Domain

```
Compared
    ↓
Harvested
```

## Description

Lifecycle을 Compare~Harvest 구간으로 제한한다.
Archive는 Lifecycle 외부의 Persistence Event로 취급한다.

## Identity

```
(filePath, userId) — 전 구간 유지
```

## Evidence

- CompareEngine은 `(filePath, userId)`로 CompareResult 생성
- HarvestEngine은 `(filePath, userId)`로 HarvestCandidate 처리
- Identity 축소 없음

---

# Option B — Full Contribution Lifecycle

```
Compared
    ↓
Harvested
    ↓
Archived
```

## Description

Lifecycle을 Archive까지 확장한다.
Archive도 Lifecycle의 일부로 포함한다.

## Identity

```
Compare~Harvest: (filePath, userId)
Archive: filePath (userId 손실)
```

## Evidence

- HarvestResult.harvestedFiles는 `string[]` (filePath만)
- HarvestResult.harvestedClients는 `string[]` (clientUsername만, 파일과 연결 안 됨)
- History Snapshot에 data로 HarvestResult 저장

---

# Evidence — Identity Preservation Matrix

| Field | filePath | userId | clientUsername |
|-------|----------|--------|----------------|
| `CompareResult` | ✅ | ✅ | ✅ |
| `HarvestCandidate` | ✅ | ✅ | ✅ |
| `HarvestResult.harvestedFiles` | ✅ | ❌ | ❌ |
| `HarvestResult.harvestedClients` | ❌ | ❌ | ✅ |
| `HarvestResult.failedFiles` | ✅ | ✅ | ✅ |
| `History Snapshot` | ✅ | ❌ | ❌ |

---

# Evaluation

| Criteria | Option A | Option B |
|----------|----------|----------|
| Runtime Fidelity | 높음 | 중간 |
| Identity Preservation | 높음 | 낮음 |
| Lifecycle Completeness | 낮음 | 높음 |
| Projection Simplicity | 높음 | 중간 |

## Analysis

### Runtime Fidelity

Option A는 실제 런타임에서 추적 가능한 구간만 표현한다.
Option B는 Archive까지 포함하지만, Archive에서는 Identity가 축소된다.

### Identity Preservation

Option A는 `(filePath, userId)`가 전 구간에서 유지된다.
Option B는 Archive에서 userId가 손실되어 동일 Entity 추적이 불완전하다.

### Lifecycle Completeness

Option A는 Archive가 빠져 Lifecycle이 불완전할 수 있다.
Option B는 Lifecycle 완결성이 보장된다.

### Projection Simplicity

Option A는 기존 구조 변경 없이 투영 가능하다.
Option B는 HarvestResult 구조 변경이 필요할 수 있다.

---

# Tradeoffs

## Option A

### 장점
- Identity Loss 없음
- 기존 코드 변경 불필요
- Projection 단순

### 단점
- Archive가 Flow 밖으로 밀려남
- Lifecycle 완결성 부족

## Option B

### 장점
- Lifecycle 완결성
- Archive까지 시각화

### 단점
- Archived에서 userId 소실
- HarvestResult 구조 변경 필요
- Projection 복잡도 증가

---

# Decision

**Option A를 선택한다.**

Lifecycle은 `Compared → Harvested`로 정의한다.
Archive는 Lifecycle 외부의 Persistence Event로 취급한다.

## Reasoning

1. Runtime Fidelity가 가장 높다
2. Identity Preservation이 보장된다
3. Projection Simplicity가 높다
4. 기존 코드 변경 불필요

Archive는 별도의 "History View"나 "Snapshot View"에서 표현할 수 있다.
Flow View는 Contribution Entity Flow에 집중하는 것이 적절하다.

---

# Consequences

## Flow View

```
[Client]
    src/foo.ts
        ↓
    Compared (filePath, userId)
        ↓
    Harvested (filePath, userId)
```

Flow View는 Compared~Harvested 구간만 시각화한다.

## Projection

Runtime Metadata → Contribution Flow Node 변환:

```
CompareResult → Compared Node
HarvestCandidate → Harvested Node (Architect Selection은 Edge)
```

## Renderer

기존 FlowRenderer.buildFlow() 확장:

```
File Dependency Flow (기존)
Contribution Flow (신규)
```

둘은 독립적으로 동작한다.

## Future Extension

Archive까지 확장이 필요하면:

1. HarvestResult 구조 변경 (harvestedFiles를 객체 배열로)
2. History Snapshot에 (filePath, userId) 보존
3. Option B 전환

이 결정은 v0.3.33 이후로 미룬다.
