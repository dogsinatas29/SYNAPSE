## 🧠 상세 설계 및 로직

### 1. 전역 배열 스프레드(Array Spread) 연산자 일소 (Call Stack 폭발 방지)
- **문제점:** 자바스크립트(V8 엔진)에서 대규모 배열을 함수 인자로 풀거나 합칠 때 `[...array]` 또는 `push(...array)` 구문을 사용하면 최대 호출 스택(약 65K ~ 120K) 리밋에 걸려 확정적인 크래시 발생.
- **조치 내역:** 백엔드(Node.js 파이프라인) 전역을 대상으로 정규식 스캔(`\[\s*\.\.\.`)을 돌려 모든 노드, 엣지, 클러스터 배열 복사 로직을 네이티브 메서드로 교체.
  - `[...array]` -> `array.slice()`
  - `[...arr1, ...arr2]` -> `arr1.concat(arr2)`
  - 타겟 컴포넌트: `BootstrapEngine`, `GraphModel`, `GridSystem`, `CommitManager`, `StateManager`, `CanvasPanel`

### 2. GhostExpander O(N*E) GC Thrashing 및 Hang 버그 해결 (핵심)
- **문제점:** 사용자가 제보한 "부트스트랩만 주구장창 하고 있다"는 Hang 현상의 원인. `GhostExpander.ts`에서 250,000개의 레퍼런스를 순회할 때마다 55,000개의 `existingNodeIds` Set을 Array로 변환하여 문자열 검사(`.some(...)`)를 수행 중이었음. 
- **수학적 팩트:** `250,000 * 55,000 = 13,750,000,000` (약 137억 번)의 배열 원소 할당과 문자열 비교가 발생. 가비지 컬렉터(GC)가 미친 듯이 돌며 프로세스 동결(수십 분 이상 소요).
- **조치 내역 (O(1) 전환):** 
  - 루프 진입 전 `existingNodeIds`의 모든 부모 디렉터리 경로를 미리 잘라서 `existingDirectories` Set 캐시로 구성 (약 10ms 소요).
  - 루프 내부에서는 `existingDirectories.has(targetNodeId)`의 O(1) 해시 테이블 탐색으로 검사 대체.
  - **결과:** 137억 번의 연산이 단 0.01초 만에 완료되도록 초고속화 달성.

### 3. CanvasPanel TypeScript Strict Mode 에러 해결
- **문제점:** `CanvasPanel.ts` 내부 임시 상태 복사 시 `map(n => ...)` 구문에서 파라미터 `n`의 타입이 `any`로 암시적 유추되어 빌드(TS7006) 실패.
- **조치 내역:** `n: any`로 명시하고, 내부의 `push(...chunk.map)` 구문 자체를 해체하여 직관적인 `for...of` 루프로 리팩토링. 타입 에러와 배열 스프레드 잔재를 동시 제거 완료.

### 🛠️ Step 1 Fix: 3개 O(N²)/O(N×C) Probe → O(N) 전환

#### 1. FILE_ACTING_AS_DIR (CanvasPanel.ts)
```typescript
// BEFORE (O(N²) — 73K² = 5.3B comparisons)
nodes.filter(n => n.type !== 'directory' &&
    nodes.some(x => x.id.startsWith(n.id + '/')))

// AFTER (O(N) — Set lookup)
const parentDirs = new Set(nodes.map(n => { const i = n.id.lastIndexOf('/'); return i > 0 ? n.id.substring(0, i) : null; }).filter(Boolean));
nodes.filter(n => n.type !== 'directory' && parentDirs.has(n.id))
```

#### 2. ORPHAN_NODES (DataPipeline.ts)
```typescript
// BEFORE (O(N×C) — clusters.find() linear search)
nodes.filter(node => !node.cluster_id || !clusters.find(c => c.id === node.cluster_id))

// AFTER (O(N) — Set.has())
const clusterIdSet = new Set(clusters.map(c => c.id));
nodes.filter(node => !node.cluster_id || !clusterIdSet.has(node.cluster_id))
```

#### 3. EMPTY_CLUSTER_VERIFY (DataPipeline.ts)
```typescript
// BEFORE (O(C×N) — nodes.some() per cluster)
clusters.filter(c => !nodes.some(n => n.cluster_id === c.id))

// AFTER (O(C+N) — Map lookup)
const nodeCountByCluster = new Map(nodes.map(n => [n.cluster_id || n.data?.cluster_id, 0]));
for (const n of nodes) { const cid = n.cluster_id || n.data?.cluster_id; if (cid) nodeCountByCluster.set(cid, (nodeCountByCluster.get(cid) || 0) + 1); }
clusters.filter(c => (nodeCountByCluster.get(c.id) || 0) === 0)
```

**예정 수정:** `Array.find()` → `Map.get()`으로 O(1) 전환

```

→ this._clusterMap.get(node.cluster_id)
```

## Phase 3 — Heatmap Data Pipeline Stabilization (완료)

### 3-1 Heatmap 렌더러 텅 빈 데이터 셋 입력 버그 해결 (EXTREME_SCALE)

**증상:** 트래픽 히트맵 토글 시 엣지(378,955개) 스캔 연산이 0.010ms만에 허무하게 끝나며 렌더링 결과물이 아무것도 나타나지 않음.

**원인 분석:**
1. **Edge Virtualization의 함정:** 최근 도입된 O(N) 엣지 가상화 로직(`_visibleEdgesCache`)이 리프(Leaf) 클러스터 기준으로만 매핑된 상태에서, `EXTREME_SCALE` 환경에서는 루트(Root)나 레벨 2 클러스터 뷰만 존재하므로, 매핑을 실패하고 `[]`(빈 배열)을 반환.
2. **Webview Cache의 Silent Failure:** `CanvasPanel.ts`에서 인라인 스크립트를 주입하더라도, VS Code 확장을 `vsce package`로 전역 설치 후 구동할 경우 강력한 로컬 캐싱 정책으로 인해 최신 `canvas-engine.js` 폴백(Fallback) 코드가 런타임에 실행되지 않는 버그 발견.
3. **초기화 타이밍 엇갈림:** 빈 캔버스 상태(nodes=0, edges=0)에서 이전 세션의 `showHeatmap=true` 상태가 복원되며 1차 텅 빈 집계를 마친 뒤, `loadProjectState`가 37만 개의 데이터를 부어넣었으나 정작 히트맵 캐시는 갱신되지 않고 영원히 비어있음.

**적용된 조치 (v0.3.33.1_fix5 ~ fix7):**
* `[v0.3.33.1_fix5]` **Bulletproof Edge Aggregation:** 캐시(`_visibleEdgesCache`, `metaEdges`)가 비어있을 시, 원본 `this.edges` 전체를 1회 순회하며 화면에 현재 렌더링된 가시적 클러스터(`_visibleClusterIds`) 최상단까지 멱등하게 거슬러 올라가(`getRep`) 강제로 엣지를 매핑하고 캐싱하는 강력한 폴백(Fallback) 추가.

## 최종 정의

v0.3.33.1_fix2는 단순히 **"Linux Kernel이 열린다"**를 증명하는 버전이 아니다.

최종 목표는:

```
Linux Kernel이 열린다
+ Linux Kernel을 탐색할 수 있다
+ Linux Kernel에서 죽지 않는다
```

즉 종료 기준은 `Bootstrap Success`가 아니라 **`Bootstrap Success + Interaction Stability`**까지 포함한다.

이 시점에서 v0.3.33.1_fix2를 완결하고, 이후 버전(v0.3.34+)은 기능 추가가 아닌 새로운 영역(LOD, 대규모 탐색 UX, 시각화 고도화 등)으로 넘어간다.

이 방향이면 v0.3.33.1_fix2는 **안정화 패치가 아닌 "VSCode-main / Linux Kernel 대응 완료 버전"**으로 정의하는 것이 타당하다.

## 🔧 2026-07-18 Hotfix — 대용량 파일 Header-Only 의존성 스캔 적용

### 배경

- 기존 `FileScanner`는 1MB 초과 파일을 즉시 스킵하여, 대형 소스 파일에서 의존성(`references`)이 통째로 누락되는 문제가 있었음.
- Linux Kernel / 대규모 모노레포 환경에서 이 스킵이 누적되면 그래프의 연결성이 급격히 약화됨.

### 적용 내용

- 파일: `src/core/FileScanner.ts`
- 변경 전:
  - `stats.size > 1024 * 1024`인 경우 `return summary`로 즉시 종료.
- 변경 후:
  - 1MB 초과 파일은 **헤더 128KB만 읽어 UTF-8 파싱** 후 기존 정규식/스캐너 파이프라인을 그대로 수행.
  - 1MB 이하 파일은 기존대로 전체 파일 스캔 유지.

### 구현 포인트

- 상수 추가:
  - `MAX_FULL_SCAN_BYTES = 1MB`
  - `HEADER_SCAN_BYTES = 128KB`
- 신규 메서드 추가:
  - `readFileHeaderUtf8(filePath, byteLimit)`
  - `fs.openSync/readSync/closeSync` 기반으로 고정 바이트 헤더만 로드.
- 대형 파일 처리 시 경고 로그를 `Skipping`에서 `Large file header scan`으로 변경.

### 기대 효과

- 대형 파일에서 완전 스킵이 사라져 의존성 추출 누락률 감소.
- 전체 파일 전량 로드 없이 헤더 중심 스캔으로 메모리/시간 비용 통제.
- 기존 정규식 기반 파서와의 호환성 유지(아키텍처 변경 최소화).

## 🧪 2026-07-18 Hotfix — External 1041 자동 분류기 연결

### 배경

- Linux Kernel에서 `external=1041`과 `cluster_ghosts=1041`이 1:1로 맞아떨어졌고, 이 실체를 판정하는 분류기가 필요했음.
- 단순 로그 출력이 아니라, `GHOST_EXT_STATS -> GHOST_TOP20 -> GHOST_ORIGIN_TOP20 -> GHOST_CLASSIFICATION -> ACTION_DECISION` 순서로 자동 판정하는 계층을 추가함.

### 적용 파일

- `src/core/GhostClassifier.ts`
- `src/core/DataPipeline.ts`

### 구현 내용

1. **GHOST_EXT_STATS**
- unresolved external node를 `header / source / rust / symbol / unknown`으로 집계.
- Linux Kernel 기준으로 1차 분기 규칙이 바로 적용되도록 구성.

2. **GHOST_TOP20**
- target 빈도 상위 20개를 출력.
- include 계열 헤더가 중심인지, 매크로/심볼 아티팩트가 중심인지 즉시 구분 가능.

3. **GHOST_ORIGIN_TOP20**
- target별 referencedByCount와 sampleSources를 수집.
- 단순 external 목록이 아니라, 어느 소스가 외부 참조를 양산하는지 추적 가능.

4. **GHOST_CLASSIFICATION**
- `validExternal / resolvableInternal / parserArtifact` 3종으로 자동 분류.
- `include/linux/*.h`, `asm/*.h`, `uapi/*.h`가 실제 파일로 해석되면 `resolvableInternal`로 승격.
- `EXPORT_SYMBOL*`, `LIST_HEAD`, `container_of`, `__init`, `__iomem`은 `parserArtifact`로 판정.

5. **ACTION_DECISION**
- `resolvableInternal >= 60%`이면 `INCLUDE_RESOLUTION`.
- `parserArtifact >= 40%`이면 `PARSER_FILTER`.
- `validExternal >= 40%`이면 `KEEP_GHOST_CLUSTER`.

### 분석 결과

- 이번 분류기는 external 1041의 정체를 사람이 해석하는 대신, 코드를 통해 자동 판정하는 방향으로 설계됨.
- `projectRoot`와 `existingNodeIds`를 함께 사용해 on-disk 존재 여부와 graph 상 존재 여부를 교차 검증함.
- 결과적으로 `cluster_ghosts`는 보존하되, 그 안의 원인을 `include resolver / parser artifact / genuine external`로 분리할 수 있게 됨.

### 기대 효과

- 다음 버전에서 `external 1041`의 실체를 숫자로 확정할 수 있음.
- Linux Kernel 같은 대규모 C/C++ 프로젝트에서는 community 레이아웃보다 먼저 include 해석 계층을 보강할 근거가 생김.

## 🔧 2026-07-19 Hotfix — WebGL 초기화 버그(TDZ) 및 O(N³) CPU 병목 해결

### 1. WebGLRenderer 초기화 버그 (TDZ Error) 해결
- **증상:** `Cannot access 'maxEdges' before initialization at WebGLRenderer.initBuffers` 에러 발생.
- **원인:** `maxEdges` 변수가 `const`로 선언되기 전에 참조(TDZ)되는 고전적인 호이스팅/스코프 버그. 이로 인해 WebGLRenderer가 생성되지 못하고 Canvas 2D로 강제 폴백됨.
- **조치:** `ui/webgl-renderer.js`에서 `maxEdges` 할당문(`this.maxEdges = maxEdges;`)의 위치를 상수 선언부 하단으로 안전하게 이동. 

### 2. Canvas 2D `drawClusters` 병목 최적화 (O(N³) → O(C log C))
- **증상:** WebGL 폴백 상태에서 68k 그래프(Linux Kernel)를 렌더링할 때 `drawClusters`에만 132ms가 소모되며 극심한 랙 유발.
- **원인:** 
  - 2,898개의 클러스터를 깊이(Depth) 기준으로 정렬(`Array.prototype.sort`)하는 과정에서, 두 클러스터를 비교할 때마다 `getDepth(c)`를 반복 호출함.
  - `getDepth(c)` 내부에서 부모 클러스터를 찾기 위해 매번 `this.clusters.find(p => p.id === curr.parent_id)`를 사용(O(N) 배열 완전 탐색).
  - 추가로 `_isAncestorCollapsed` 함수 내부에서도 동일하게 `this.clusters.find()`를 반복 사용.
- **조치:**
  - `canvas-engine.js`에 이미 존재하던 `this._clusterMap` (Map 구조)을 활용하여 부모 탐색 복잡도를 O(N)에서 O(1)로 단축.
  - `depthCache` Map을 도입하여 한 번 계산된 클러스터 깊이는 다시 탐색하지 않도록 메모이제이션 적용.
- **기대 효과:** 132ms가 걸리던 Cluster 정렬 및 렌더링 준비 과정이 1ms 이하로 단축.

### 3. CPU 100% 점유 및 렌더링 지연(RAF 루프 중복 실행) 버그 해결
- **증상:** `render-frame` 타이머 경고가 수백 번 출력되고 렌더 시간이 비정상적으로 5,000ms 이상 소요되는 현상.
- **원인:** `startLoop()`가 여러 번 호출되면서 `requestAnimationFrame(loop)`가 중복 실행(수십~수백 개의 렌더링 루프가 동시에 동작하여 CPU 자원을 100% 갈아먹음).
- **조치:** `startLoop()` 진입 시 기존 `_rafId`가 존재하면 `cancelAnimationFrame(this._rafId)`를 강제로 호출하여 **오직 단 하나의 렌더링 루프(RAF)만 실행되도록 완벽히 통제**.
- **기대 효과:** Linux Kernel 스케일에서도 불필요한 루프 오버헤드가 사라져 CPU 사용률이 극도로 안정화되고 20~30 FPS 이상의 쾌적한 렌더링 달성.

## 🔧 2026-07-19 Hotfix — `computeClusterBounds` O(N×C) 병목 완벽 제거 (5초 Hang 해소)

### 1. `[FRAME] 5117.50ms` 렌더링 멈춤(Hang) 원인 분석
- **증상:** 리눅스 커널급 프로젝트(노드 68K, 클러스터 2,900개) 렌더링 진입 시, 단일 프레임 처리 시간이 5초를 넘어 브라우저 메인 스레드가 완전히 굳어버리는 치명적 지연 발생.
- **원인:** `canvas-engine.js`의 `updateLOD()` 단계에서 호출되는 `computeClusterBounds` 함수가 내부적으로 무자비한 루프를 돌고 있었음.
  - 2,901개의 클러스터 각각에 대해 `computeClusterBounds` 호출.
  - 이 안에서 다시 노드 68,000개에 대해 `this.nodes.filter(...)` 실행.
  - 추가로 `this.clusters.filter(...)`로 자식 클러스터까지 재귀 탐색.
  - **수학적 연산량:** 노드 68,000개 × 클러스터 2,900회 = 매 렌더 루프당 **약 2억 번 이상(O(N×C))의 순회 연산 폭주**.

### 2. Hash Map 기반 O(1) 인덱싱 아키텍처 도입
- **조치:**
  - `_buildClusterIndices()` 헬퍼 함수를 신설.
  - 렌더링 파이프라인에서 단 한 번만 `this.nodes`와 `this.clusters` 배열을 훑어서 `this._clusterNodesCache`, `this._childClustersCache`라는 `Map`(Hash Table)에 각 클러스터의 자식들을 미리 분류(Indexing).
  - 이후 수천 번 재귀 호출되는 `computeClusterBounds` 내에서는 무거운 배열 검색(`filter()`)을 폐기하고, 캐싱된 `Map`에서 키 값으로 즉시 조회(O(1)).
- **기대 효과:**
  - 2억 번에 달하던 연산 병목이 즉시 해소됨.
  - `COMPUTE_CLUSTER_BOUNDS` 처리 시간이 5초대에서 즉각적인 밀리초(ms) 단위로 단축되어, 초거대 스케일 그래프에서도 실시간 반응성을 복구.

## 🔧 2026-07-19 Hotfix — 렌더링 루프 영구 정지(Hang) 버그 해결

### 1. 빈 화면(Blank Canvas) 증상 원인 분석
- **증상:** 초거대 스케일 병목(`computeClusterBounds`)을 해결하고 파이프라인 처리가 완료되었음에도 불구하고 캔버스에 아무것도 그려지지 않음.
- **원인:** 중복 렌더링 루프를 방지하기 위해 `startLoop()`에 추가했던 방어 로직에 치명적인 순서 오류가 있었음.
  - `this._loopRunning`이 `true`인 상태에서 마우스 오버 등 상호작용으로 인해 `startLoop()`가 재호출되면, 
  - `cancelAnimationFrame(this._rafId)`를 통해 대기 중인 정상 프레임을 먼저 취소(Kill)해버린 직후, 
  - `if (this._loopRunning) return;` 조건문에 걸려 새로운 프레임을 예약하지 못하고 그대로 종료됨.
  - 결과적으로 렌더링 루프가 완전히 죽어버리며 화면이 갱신되지 않는 현상 발생.

### 2. 조치 내역
- **조치:** `startLoop()` 방어 로직의 순서를 교정.
  - `if (this._loopRunning) return;` 문을 최상단으로 올려, 이미 루프가 정상적으로 돌고 있을 경우 기존 루프를 방해하지 않고 안전하게 무시하도록 변경.
  - 이 검문을 통과한 경우(루프가 꺼져 있는 경우)에만, 혹시 남아있을지 모를 찌꺼기(Zombie) `_rafId`를 취소하도록 로직을 재배치.
- **기대 효과:** 마우스 인터랙션으로 인한 루프 사망 버그가 완벽히 차단되며 초고속 렌더링 화면이 정상 출력됨.

## 🔧 2026-07-19 Hotfix — Edge Materialization Cache (O(1) LOD Filtering)

### 1. 가시성 재계산 지연 원인 분석
- **증상:** 초거대 스케일 그래프(378k Edges) 환경에서 클러스터 확장/축소나 External Ghost 등을 토글할 때 발생하는 가시성 재계산 파이프라인(`VISIBLE_EDGE_BUILD`)이 약 400~500ms 동안 브라우저 메인 스레드를 블로킹하여 화면을 버벅이게 만듦.
- **원인:** `updateLOD()` 파이프라인 안에서 378k 개의 전체 엣지를 `filter()`로 순회하며 매번 `nodeMap.get(e.from)` 및 `nodeMap.get(e.to)`를 호출하여 소속 클러스터를 식별하고 있음. 
  - (378,000 * 4회 = 약 150만 번의 Map Lookup 오버헤드 발생)

### 2. 조치 내역
- **Edge Pre-computation (O(1) Caching):** `_performRender()`에서 노드 맵(`nodeMap`)이 최신 상태로 갱신된 직후, 전체 `this.edges` 배열을 순회하여 각 엣지에 `_fromCluster` 및 `_toCluster` 속성을 캐싱(`EDGE_CACHE_CLUSTERS`).
- **Map 조회 100% 제거:** 기존 `VISIBLE_EDGE_BUILD`의 필터 로직과 Aggregate Meta Edges(LOD) 생성 루프에서 `nodeMap` 접근 방식을 완전 폐기하고, 미리 굽힌 `edge._fromCluster`와 `edge._toCluster` 값을 즉시 읽어 O(1) 필터링으로 변경.
- **기대 효과:** 극심한 CPU 병목을 유발하던 150만 번의 참조 조회를 제거하여, 가시성 재계산 딜레이를 절반 이하(예측: 200~250ms 이하)로 즉각 단축하고 체감 버벅임을 완화함.
> **Note:** 본 조치는 임시 구제책(Immediate Relief)이며, 최종 해결책인 Cluster-Edge Index 및 진정한 Viewport Edge Virtualization 도입 전 징검다리 역할을 합니다.

## 🔧 2026-07-20 Hotfix — Render Prep $O(N \times C)$ Removal & Edge Virtualization

### 1. `drawClusters` 내부 순수 JS 배열 순회 지연 원인 분석
- **증상:** `drawClusters` 렌더링에만 무려 **1830ms**가 소요됨. 그러나 `console.time` 계측 결과 캔버스 그리기 함수(`fillRect`, `strokeRect`, `fillText`) 자체는 **3.5ms**에 불과했음.
- **원인:** 클러스터 렌더 루프(2,896번 반복) 내부에서 매번 `_visibleNodesCache.filter()` (크기 67,140)를 수행하여 특정 클러스터에 속한 가시 노드 개수를 세는 PROBE 로그(`CLUSTER_VISIBLE_NODES`)가 발견됨. 
  - (67,140 * 2,896 = **약 1억 9천 4백만 번의 반복 순회 발생**)

### 2. 조치 내역 1: `drawClusters` 병목 파괴
- **조치:** O(N*C)로 동작하던 `CLUSTER_VISIBLE_NODES` 카운터를 제거. 루프 진입 전 `_clusterVisibleNodeCountMap`을 1회 순회로 선행 구축(O(N))하고, 루프 내부에서는 O(1)로 가져오도록 변경.
- **결과:** 1830ms가 걸리던 `drawClusters`가 **4.36ms**로 약 **406배 최적화**됨.

### 3. 조치 내역 2: Cluster-Edge Index (Edge Virtualization) & `aggregateEdges` 병목 파괴
- **증상:** 최적화 이후에도 `VISIBLE_EDGE_BUILD` 타이머가 여전히 **190ms**를 점유함. 확인 결과, `VISIBLE_EDGE_BUILD` 내부의 메타 엣지 조립 구간(`LOD:aggregateEdges`)에서 또 다시 `this.edges` 전체 378,000개를 순회하며 엣지 양끝 노드의 부모 트리를 역추적(`findVisibleRep`)하는 로직(756,000회 호출)이 존재했음.
- **조치:** 
  1. `EDGE_CACHE_CLUSTERS` 시점에 구축한 `this._clusterEdgeMap` (클러스터 ID -> 소속 Edge 배열)을 활용.
  2. 전체 378k Edge 순회를 폐기하고, `_clusterEdgeMap`을 클러스터 단위(최대 2,896개)로 순회하도록 Hoisting 적용.
  3. 부모 탐색 결과를 `repCache` Map에 저장하여 756,000회의 트리 역추적을 단 2,896회로 99.6% 삭감.
- **기대 효과:** 극소수의 클러스터만 렌더링될 경우 순회 비용이 수천 회 수준으로 떨어져, 남은 190ms의 지연마저 완벽히 제거됨.

### 4. 조치 내역 3: Adaptive Rendering Profile (Project Scale Analyzer) & UI 적용
- **증상:** 극단적 스케일(리눅스 커널 등)을 초기 로드할 때 엔진이 무리하게 모든 레이어를 그리려다 뻗을 수 있음. 단순 노드 수 비교로는 병목의 주범인 '거대 Edge 트래픽'을 제대로 판별하기 어려움.
- **조치:** `loadProjectState` 직후 노드/엣지/클러스터 개수에 가중치를 부여해 스케일 점수(`scaleScore`)를 산정하고 자동 프로파일을 적용.
  - **평가 기준:** `nodeCount + (edgeCount * 5) + (clusterCount * 10)` (SYNAPSE 병목의 80% 이상이 Edge 연산임에 착안)
  - **적용 조건:** `scaleScore > 500,000` (예: Linux Kernel은 약 1,900,000점)
  - **액션 (`EXTREME_SCALE`):** `showExternalLayer` 비활성화, `showContextVault` 비활성화, 1Depth 이외의 자식 클러스터 자동 `collapsed` 처리.
- **UX 개선:** 로딩 직후, 사용자가 당황하지 않도록 화면 중앙에 **"자동 프로필이 적용되었습니다"** 모달(팝업) 창을 띄워 현재 강제 적용된 렌더링 옵션 상태(체크박스 형태)를 투명하게 고지함.
- **기대 효과:** 거대 프로젝트 렌더링 시 브라우저 Lock을 원천 방지하고, 사용자에게 최적화된 초기 탐색 환경과 인지적 안정감을 제공함.

### 5. 조치 내역 4: Adaptive Profile 및 Layout 엔진 분리 (Layout Graph ≠ Visible Graph)
- **증상:** 사용자가 제보한 **"레이아웃 그래프가 비저블 그래프와 동일해지는 현상"** 확인. Extreme Scale 프로파일 적용 시 `showExternalLayer = false` 및 Level 2 이하 자식 노드가 모두 강제로 접힘(`cluster.collapsed = true`). 이 직후 실행되는 Frontend 레이아웃 함수(`distributeClustersHierarchically`) 내부에서 `if (cluster.collapsed)` 분기를 타고 클러스터 크기를 `250x60`으로 강제 축소 계산해버리는 치명적 결함 발견.
- **결과:** 레이아웃 엔진이 "보여지는 상태(Visible Graph/Collapsed State)"에 오염되어, 대륙(Roots)들이 축소된 자식 크기를 기준으로 서로 중앙에 밀집(압축) 배치됨. 이후 유저가 "Roots Only" 상태에서 클러스터들을 펼치면, 압축된 좌표계 위에서 렌더링되므로 경계 박스가 대량으로 중첩되고 붕괴되는 현상 발생.
- **조치 내역:** `ui/canvas-engine.js`의 `distributeClustersHierarchically` 함수 내에서 `cluster.collapsed` 여부를 검사하여 크기를 강제로 `250x60`으로 반환하는 분기 전체를 삭제.
- **철학적 달성:** SYNAPSE의 설계 철학인 **"레이아웃 엔진은 항상 전체 그래프(Layout Graph)를 기준으로 풀 사이즈를 계산해야 하며, 프로파일(Profile) 및 렌더링은 가시성(Visible Graph)만을 제한해야 한다"**는 원칙을 완전히 구현함. 이제 접혀 있는 클러스터라도 내부 자식들의 크기만큼 거대한 빈 공간(Space)을 정상적으로 점유하며, 클러스터들이 서로 침범하지 않음.

### 💡 [참고] 자동 프로파일(Adaptive Profile) 적용 기준 요약

- **발동 조건:** `scaleScore > 500,000` 인 경우 (EXTREME_SCALE)
  - `scaleScore = nodeCount + (edgeCount * 5) + (clusterCount * 10)`
- **자동 적용 항목:**

## 🛠️ Technical Details (기술적 세부 사항)

### 1. Rendering Pipeline Optimization
- **[EN]** Removed `_visibleNodesCache.filter()` inside the `drawClusters` render loop. Replaced with O(1) lookup via `_clusterVisibleNodeCountMap`.
- **[KR]** `drawClusters` 루프 내부의 `_visibleNodesCache.filter()` 순회를 제거하고, 사전 구축된 `_clusterVisibleNodeCountMap`을 통한 O(1) 단일 조회로 대체했습니다.

### 2. Edge Virtualization
- **[EN]** Replaced full edge array iteration (378k edges) during `VISIBLE_EDGE_BUILD` with hoisted cluster-level iteration using `_clusterEdgeMap`.
- **[KR]** `VISIBLE_EDGE_BUILD` 단계에서 발생하던 전체 엣지 배열(약 37만 개) 순회를 제거하고, `_clusterEdgeMap`을 활용한 클러스터 단위 순회로 변경했습니다. 부모 역추적 캐싱(`repCache`)을 통해 75만 회의 연산을 2,896회로 99.6% 삭감했습니다.

### 3. Adaptive Scale Profile
- **[EN]** Introduced `scaleScore` calculation upon project load (`nodes + edges*5 + clusters*10`). Projects exceeding 500,000 points automatically trigger the `EXTREME_SCALE` profile, collapsing 2nd-depth clusters and hiding external layers to prevent browser lockup.
- **[KR]** 프로젝트 로드 시 스케일 점수(`scaleScore = 노드 + 엣지*5 + 클러스터*10`)를 산정하여 500,000점 초과 시 `EXTREME_SCALE` 프로파일을 자동 가동합니다. 브라우저 락(Lock)을 방지하기 위해 2-Depth 이하 클러스터를 자동 접음 처리하고 외부 참조 레이어를 끕니다. (적용 시 자동 팝업 알림 제공)

### 4. Layout vs Visibility Rule Enforced
- **[EN]** Removed the `cluster.collapsed` conditional exit inside `distributeClustersHierarchically`. Layouts are now strictly calculated based on reality (full node footprint), ensuring visual rendering does not alter spatial physics.
- **[KR]** `distributeClustersHierarchically` 레이아웃 함수 내의 `if (cluster.collapsed)` 강제 크기 축소 분기를 삭제했습니다. "레이아웃 엔진은 절대 가시성 상태에 의존하면 안 된다"는 SYNAPSE 코어 규칙이 성공적으로 구현되었습니다.
