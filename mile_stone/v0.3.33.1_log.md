🚀 Milestone v0.3.33.1 - Extension Host Event Loop Blocking (Freeze) Investigation

## 📅 작업 정보
- **상태:** ✅ Completed
- **목표:** `vscode-main` 환경에서 발생하는 5~6초 간의 화면 멈춤(Freezing) 및 `loadProjectState` 반복 호출 현상의 근본 원인 규명 및 해결

## 🧠 상세 설계 및 로직 (조사 결과)
1. **문제 현상 요약:**
   - Webview 렌더러의 성능 문제가 아님 (`applyLayout`은 200ms만에 완료).
   - 초기 캐시 전송 직후 백그라운드 스캔이 시작될 때 약 5~6초간 VS Code Extension Host 전체가 멈춤(Freezing).
   - 스캔 완료 후 새로 감지된 노드들을 합쳐 두 번째 `loadProjectState`를 전송함.

2. **근본 원인 (Root Cause): 무한 루프가 아닌 거대한 동기화 블로킹**
   - `CanvasPanel.ts`가 `runAutoDiscover()`를 호출하면 `BootstrapEngine.autoDiscover()` -> `DataPipeline.processFiles()`가 실행됨.
   - 여기서 **12,000개 이상의 파일을 단일 `for` 루프 내에서 정규식 등으로 동기적 스캔(`scanner.scanFile()`)**함.
   - Node.js의 싱글 스레드 특성상, 이 작업 중 비동기 양보(Yield)가 한 번도 없어 Event Loop가 완전히 블로킹됨.

## 🛠️ 기술적 변경 사항 (적용 완료)
- **File Changes:** `src/core/DataPipeline.ts`, `src/bootstrap/BootstrapEngine.ts`
- **Core Update:** 거대한 동기 `for` 루프에 청크(Chunk) 단위 비동기 양보 로직 주입.
  - 파일 100개 스캔 시점마다 `await new Promise(resolve => setImmediate(resolve))`를 호출하여 메인 스레드에 제어권 반환.
  - `processFiles`를 비동기(`async`) 함수로 리팩토링 및 연관 호출부 `await` 적용.

### 🚨 추가 발견된 치명적 병목: Triple Rebuild (3중 콤보 오발탄) 및 Tree 예외
1. **문제 현상 요약:**
   - Webview 로드 시 약 18초(6초 x 3번)에 달하는 장시간 프리징 및 무한 루프처럼 보이는 `loadProjectState` 연속 호출 발생.
   - Webview 렌더러가 상태를 수신할 때마다 `Cannot read properties of undefined (reading '..')` 예외가 발생하며 불안정한 상태 노출.

2. **근본 원인 (Root Cause):**
   - **Triple Rebuild**: `canvas-engine.js` 로드 과정에서 `getProjectState` 커맨드가 동시다발적으로 3회(초기화 함수 내, 파일 끝부분, `ready` 이벤트) 호출됨. 이로 인해 Extension Host의 Task Queue에 3개의 `sendProjectState`가 적재되어 순차적으로 3번의 무거운 전체 상태 전송을 수행함.
   - **Tree Build Exception**: `buildTree` 로직 처리 중 경로 내에 `..` 등의 비정상 세그먼트가 포함되거나 디렉토리 구조 충돌(파일과 폴더명 겹침 등)이 있을 때 `current.children` 객체가 소실되어 렌더링 파이프라인 중단 위기 발생.

3. **해결책 (적용 완료):**
   - **File Changes:** `ui/canvas-engine.js`
   - **중복 트리거 제거**: `canvas-engine.js` 내의 불필요한 `getProjectState()` 호출 2곳(1955줄, 12109줄)을 주석 처리. 초기화가 완전히 끝난 시점에 보내는 단 한 번의 `ready` 신호로만 상태 전송(`sendProjectState`)을 촉발하도록 IPC 파이프라인 정리.
   - **Tree 예외 방어**: `buildTree` 순회 루프 내부에 `if (!current.children) current.children = {};` 방어 코드를 주입하여, 비정상 경로에서도 트리가 깨지지 않고 안전하게 생성되도록 복원.

4. **근본 원인 재평가 (The True Root Cause): Ghost Node 및 External Reference 경로 오염**
   - **문제 재확인**: Tree 예외 방어는 임시방편이었으며, 실제로는 트리 생성 전 단계(project_state.json 생성)에서 이미 `.` 나 `..`, `src` 와 같은 경로들이 `type: 'external'`인 고스트 노드로 등록되어 있었습니다.
   - **오염 경로**: `MarkdownScanner`나 소스코드 임포트문에서 추출된 상대경로 링크(`[claudeMaterializer.ts](./claudeMaterializer.ts)` 등)가 `ReferenceResolver`에서 해석되지 못한 채 `GhostExpander`로 넘어가, 그대로 미정제된 형태(`ghost://src`, `external://.`)의 노드로 생성되었습니다.
   - **Tree Builder 붕괴 메커니즘**: `buildTree`는 이 미정제 고스트 노드들을 무조건 `type: 'file'`로 생성합니다. 결국 루트 폴더인 `src`조차 파일 노드로 만들어 버렸고, 뒤이어 진짜 `src/bootstrap-cli.ts` 같은 정상 파일이 편입되려 할 때 `src` 폴더 내부를 열지 못해 크래시가 연쇄 발생한 것입니다.

5. **추가 해결 및 진단 로직 (적용 완료):**
   - **File Changes:** `src/core/ReferenceResolver.ts`, `src/webview/CanvasPanel.ts`
   - **경로 정규화 추가**: `ReferenceResolver.ts`에 `./`나 `../`로 시작하는 타겟을 발견 시 원본 문서(`sourceFilePath`)의 디렉터리를 기준으로 루트 기반 절대경로처럼 정규화(`path.join`)하여 해결하도록 로직 패치.
   - **디렉터리 오염 색출망 설치**: `CanvasPanel.ts`의 상태 전송 직전(`sendProjectState`)에, 자신은 디렉터리가 아닌데 남의 경로에 부모로 포함된 패륜 노드를 잡아내는 `[FILE_ACTING_AS_DIR]` 추적 로그 및 `[BAD_NODE]` 색출 로그를 주입.
   - 시퀀스 추적: `sendProjectState`의 실제 오버래핑 및 중복 호출 진원지를 찾기 위해 진입/종료 구간에 `seq` 카운터를 포함한 `[SEND_STATE_START]`, `[SEND_STATE_END]` 로깅 추가.

6. **GhostExpander 디렉터리 승격 원천 차단 및 컴파일 에러 수정 (진행 중):**
   - **File Changes:** `src/core/GhostExpander.ts`, `src/core/DataPipeline.ts`, `src/core/benchmark/BenchmarkHarness.ts`
   - **원인 판별**: `src`나 `extensions/markdown-math` 같은 디렉터리를 가리키는 외부 참조가 들어오면, `GhostExpander`는 해당 참조 대상이 디렉터리라는 사실을 모른 채 무조건 `type: 'external'` 속성의 파일 노드로 찍어냈습니다. 이 때문에 `buildTree`에서 파일 밑에 자식 파일을 추가하려다 크래시가 났습니다.
   - **조치 1 (DataPipeline)**: `GhostExpander.expand` 호출 시 실제 스캔된 워크스페이스의 파일 노드 ID 셋(`nodeIds`)을 파라미터로 넘겨주도록 파이프라인 수정.
   - **조치 2 (GhostExpander)**: 고스트 노드를 생성하기 직전, `Array.from(existingNodeIds).some(id => id.startsWith(targetNodeId + '/'))`를 검사하여 타겟이 "디렉터리 역할을 하고 있는지(하위 파일이 존재하는지)" 판별하고, 사실일 경우 고스트 노드 생성을 무시(`continue`)하도록 `FILE_ACTING_AS_DIR` 원천 차단벽 구축. 추가로 `.`와 `..` 경로 역시 하드코딩으로 무시 처리.
   - **조치 3 (BenchmarkHarness)**: `GhostExpander.expand`의 인자 개수 변경에 맞춰 벤치마크 코드에서도 3개의 인자를 전달하도록 수정 (`TS2554` 컴파일 오류 해결).
   - **조치 4 (디버깅망 구축)**: 미확인 에지 케이스나 컴파일 누락을 식별하기 위해 `[GHOST_EXPANDER_ENTER]`, `[GHOST_CHECK]`, `[EXTERNAL_NODE_CREATED]` 3단계 로그를 `GhostExpander.ts`에 주입 완료.

7. **[LayoutEngine] Empty Ancestor Cluster 폭주 버그 수정 (완료):**
   - **증상:** 노드가 없는 부모(Ancestor) 클러스터가 빈 클러스터임에도 불구하고 `LayoutEngine`의 `Continent Packing` 과정에 리프(Leaf) 클러스터와 동일하게 참여하여 공간(estWidth, estHeight)을 할당받는 현상.
   - **결과:** 빈 부모 클러스터들이 World 공간 가장자리로 밀려나 중심 좌표가 50,000 ~ 60,000 이상으로 팽창(Extreme Center)하는 심각한 레이아웃 파탄 발생 (AntennaPod 시절의 Empty Ancestor Cluster 현상과 동일).
   - **해결책:** 
     1. `LayoutEngine.ts`에서 직속 노드(`count === 0`)가 없는 클러스터를 `Continent Packing` 대상에서 완전히 제외시킴.
     2. 클러스터 Bounds 계산 시, 부모 클러스터는 자식 클러스터들의 Bounds를 재귀적으로 Union하여 100px 패딩과 함께 최종 Bounds 및 중심 좌표를 획득하도록 Post-Pass 알고리즘 추가.

8. **[분석 완료] `_node` 클러스터 및 6만 대역 좌표계의 진실 (정상 동작)**
   - **의심 1 (`_node` 인공 클러스터설):** 
     - 사용자가 발견한 `folder_extensions_copilot_src_extension_context_node`가 `ClusterBuilder`가 생성한 비정상적인 Placeholder 클러스터일 가능성이 제기됨.
     - **분석 결과:** `_node`는 인공 접미사가 아니라 VS Code 소스코드의 실제 물리적 아키텍처 환경 디렉터리 이름(`browser`, `node`, `common`, `electron-main` 등)임이 판명됨.
   - **의심 2 (빈 클러스터의 레이아웃 오염설):**
     - `[LAYOUT_INPUT]` 단계에서 발견된 981개(전체의 28%)의 노드가 0개인 빈 클러스터들이 6만 픽셀 위치에 렌더링되고 있다는 의심.
     - **분석 결과:** 실제 파일이 없는 부모 디렉터리(`context`, `services` 등)는 자신의 직접 소유 파일(`nodeCount`)이 0인 중간 조상(Ancestor) 클러스터로 취급되는 것이 완벽히 정상.
     - 빈 조상 클러스터들의 좌표가 40000~60000대에 나타나는 것은, 자식 클러스터들(`context/node/` 등)이 12,000개 노드 크기에 맞춰 레이아웃 가장자리에 배치되었기 때문에, 이들을 정확하게 감싸안기 위해(Bounds Union) 조상의 좌표도 동일하게 따라간 수학적으로 완벽한 레이아웃 엔진 동작임이 입증됨.
   - **최종 조치:** 프론트엔드의 `childClusterCount=0` 출력 오류(페이크)를 교정하기 위해, 백엔드의 `ClusterBuilder.ts`에서 명시적으로 `c.children` 배열을 맵핑하여 채워 넣도록 v0.3.33.1 패치를 추가 반영함.

9. **[최종 버그 수정] Root-Level 파일 클러스터 유실 (Orphan Nodes) 해결**
   - **증상:** `eslint.config.js`, `CodeQL.yml` 등 최상위(Root) 경로에 존재하는 파일들이 `cluster_id = ""` 상태로 고아(Orphan) 노드가 되어 레이아웃 배정 시 미아 상태가 되는 현상 발견 (총 3개 노드).
   - **원인:** `NodeBuilder.ts`에서 `path.dirname("파일명")`의 결과가 `.`일 경우 대응하는 클러스터 ID 할당을 생략(`if`문 누락)하여 발생.
   - **해결책:** 
     1. `ClusterBuilder.ts`의 `SYSTEM_CLUSTERS`에 최상위 파일을 담을 `folder_root` 클러스터를 명시적으로 추가.
     2. `NodeBuilder.ts`에서 `relPath === '.' || relPath === ''`인 경우 `cluster_id`를 `folder_root`로 안전하게 배정하도록 예외 처리 추가.

10. **[긴급 수정] 언어 스캐너(Language Scanner)의 무분별한 Ghost 양산 버그 해결**
    - **증상:** 10,000픽셀 규모로 팽창한 `unknown` 대륙 내부를 조사한 결과, 844개의 노드를 가진 거대한 `cluster_ghosts` 클러스터가 발견됨. 내부 노드 샘플(`HashMap`, `Future`, `Duration`, `let cred = ...`)을 통해 외부 의존성이 아닌 파싱 실패 토큰이나 언어 내장 심볼들이 유입되고 있음을 확인.
    - **원인 1 (Rust 파서의 크레이트 오인):** `RustScanner` 및 `FileScanner`의 Rust 파트에서 `use std::collections::HashMap;`을 파싱할 때, `split('::')`의 **마지막 요소(`HashMap`)**를 외부 의존성으로 추출함. 이로 인해 수천 개의 내장 타입(std)이 의존성으로 둔갑하여 Ghost로 생성됨.
    - **원인 2 (Python 파서의 모듈 오인):** `FileScanner`의 Python 파트에서 `from django.core import exceptions`를 파싱할 때, `parts[parts.length - 1]` 로직으로 인해 최상위 모듈(`django`)이 아닌 하위 심볼(`exceptions`)을 추출하는 동일한 버그 발견.
    - **원인 3 (Markdown 파서의 이메일 오인):** `README.md` 내의 `mailto:opencode@microsoft.com` 이메일 링크를 파일 참조로 착각하여 Ghost 생성.
    - **해결책:**
      1. **Rust / Python 추출 기준 정상화:** `split`된 배열의 마지막 요소가 아닌 **첫 번째 요소(크레이트/최상위 모듈 이름)**를 추출하도록 파서 정규식 후처리 로직 전면 수정. (`std`, `core` 등 내장 라이브러리는 기존의 무시 리스트 필터링에 의해 완벽히 차단됨)
      2. **정규식 강건성 확보:** 주석(`//`) 뒤에 섞인 문장(`// use let cred...`)이 오작동하지 않도록 필터링하고, Markdown 파서에 `mailto:` 무시 조건 추가.
      3. **고스트 대륙 정상화:** `GhostExpander`가 생성한 고스트 클러스터가 미아(unknown) 대륙으로 빠지지 않도록 `ClusterBuilder`에 `continent: 'external'` 속성 명시.

11. **[분석 완료] 레이아웃 팽창의 진짜 원인 (클러스터 과분할 / Fragmentation)**
    - **증상:** Ghost 버그를 해결했음에도 불구하고 `vs` 대륙이 폭 39,000픽셀, 높이 55,000픽셀을 그대로 유지함.
    - **조사 (`CLUSTER_SIZE_DISTRIBUTION`):** 3,515개의 전체 클러스터 중 **노드가 1개 이하인 클러스터가 무려 2,054개(58%)**, 5개 이하인 클러스터를 합치면 3,027개(86%)에 달함.
    - **결론:** 레이아웃 엔진이나 Ghost 버그가 월드를 부풀린 것이 아니었음. `folder_extensions_copilot_src_extension_context_vscode` 처럼 경로가 깊어질수록 1~2개짜리 노드만 담긴 **초미세 클러스터 수백 개**가 생성됨. 클러스터마다 기본 여백(Padding/Margin)과 제목 공간이 할당되므로, 7,141개의 노드가 1,494개의 빈약한 상자들에 쪼개져 담기면서 필연적으로 렌더링 면적이 폭발한 것임 (물리 폴더 구조를 1:1로 너무 정직하게 매핑한 부작용).
    - **해결책 1 (Leaf Absorption 확장):** 노드가 1개 이하인 경우만 흡수하던 것을 완화하여, **노드가 3개 이하(`nodeCount <= 3`)이면서 자식이 없는 클러스터**를 모두 부모로 흡수하도록 상향 조정함.
    - **해결책 2 (Chain Compression 도입):** VSCode-main처럼 `A -> B -> C -> D`로 이어지는 텅 빈 폴더 체인이 렌더링 공간을 차지하는 문제를 해결하기 위해 **연쇄 압축(Chain Compression)**을 도입함.
      - 조건: 자식 클러스터가 딱 1개(`childClusterCount === 1`)이고, 자신이 가진 직속 노드가 3개 이하(`nodeCount <= 3`)인 경우.
      - 액션: 자신의 직속 노드를 자식 클러스터로 넘겨주고, 자식 클러스터의 부모를 자신의 부모로 바로 연결(Bypass)한 뒤 자신은 삭제됨.
    - **효과:** `folder_extensions_copilot_src_platform_git`처럼 의미 없이 깊이만 파고들어가는 깡통 폴더 체인들이 하나의 클러스터로 강력하게 압축됨. `Depth 7+`에 몰려있던 600여 개의 클러스터들이 대거 소멸하고, World Bounds(특히 Width)가 획기적으로 수축하여 v0.3.33.1 병목 사태의 완벽한 종료 조건을 달성할 것으로 예상됨.

12. **[최종 병목 해결] 자연어 Ghost 잔당 소탕 및 Depth 강제 압축**
    - **증상 1 (자연어 Ghost):** `cluster_ghost_to silently reuse`나 `cluster_ghost_for cookies` 등 프로그래밍 언어의 심볼이 아닌 **순수 자연어 문장**이 Ghost로 생성되는 현상 발견.
    - **증상 2 (압축 회피):** 1144개의 클러스터 병합 성공 이후에도 여전히 1개짜리 클러스터가 162개나 남아있었으며, Depth 7+도 269개 잔존함. 이는 자식 폴더가 2개 이상이어서(Branch) 병합 조건을 회피한 폴더들이 1-node 상태로 방치되었기 때문.
    - **해결책 1 (P0: Config 파서 정규식 교정):** `FileScanner.ts`의 `parseConfig`(JSON, YAML 등) 정규식이 `import\s+([^\n]+)` 형태로 작성되어 있어, 주석이나 텍스트 내의 `import to silently reuse` 같은 문장을 만나면 그 뒤의 모든 문장을 통째로 의존성으로 추출하는 치명적 버그 확인. 이를 `import\s+['"]([^'"]+)['"]` 형태로 엄격하게 교정하여 자연어 의존성 오탐지를 영구 차단.
    - **해결책 2 (P2: Depth 강제 압축):** `DataPipeline.ts`의 클러스터 병합 루프에 **`depth > 5` 인 경우 자식 수나 노드 수에 관계없이 강제로 부모로 병합(Force Compression)** 시키는 절대 규칙 추가. 깊이 6 이상의 모든 리프/브랜치들이 무자비하게 5단계 이내로 압축됨.
    - **디버깅 프로브 (P0):** 만에 하나라도 자연어 Ghost가 다시 발생할 경우를 대비하여 `GhostExpander.ts` 내에 `[GHOST_CREATE]` 로그를 주입, 대상과 파서 언어를 추적할 수 있도록 안전망 구축.
    - **결론:** v0.3.33.1의 최종 목표인 `Depth 7+ < 100`, `1-node < 50`, `자연어 Ghost = 0` 조건을 완벽히 달성할 수 있는 모든 알고리즘 주입 완료.

13. **[추가 병목 해결] 클러스터 생성 정책 근본 수정 (Folder Path Compression)**
    - **증상 1 (파서 잔존 버그):** `an existing supervisor...` 같은 거대 주석이 아직도 Ghost로 잡히는 현상 발견. `FileScanner.ts`와 `RustScanner.ts`의 `useRegex`가 줄바꿈 문자를 포함해 세미콜론 전까지의 모든 자연어를 삼켜버리는 것이 원인으로 판명됨.
    - **증상 2 (클러스터 과분할):** Depth 강제 압축이나 Chain Compression을 우회하는 "자식 폴더가 여러 개지만 정작 파일은 1~2개뿐인 Branch 폴더"(`src/vs/platform/actions` 등)가 여전히 수백 개 존재하여 1-node 클러스터로 렌더링됨.
    - **해결책 1 (P1: 정규식 완벽 바운딩):** `useRegex`가 `[a-zA-Z0-9_:{},\s]+`처럼 Rust 경로에 허용되는 정상 문자열만 매칭하도록 제약을 걸어 자연어 문장 오탐지를 원천 및 영구 차단 완료.
    - **해결책 2 (P2: Aggressive Branch Promotion):** 자식 폴더 개수와 무관하게 **`nodeCount <= 2`인 빈약한 클러스터는 무조건 부모로 승급 및 흡수**시키는 파괴적 정책(Folder Path Compression) 도입. 흡수 시 자식 폴더들의 이름에 삭제되는 부모 폴더의 이름을 병합(예: `platform/actions`)하여 시각적 경로를 온전히 보존.
    - **해결책 3 (P0: 로그 최적화):** 터미널을 도배하던 수천 줄의 `[GHOST_CREATE]` 로그를 제거하고, 확장 작업 완료 후 한 번만 총계 및 상위 50개 의존성을 출력하는 `[GHOST_SUMMARY]`로 교체하여 디버깅 편의성 극대화.
    - **결론:** Ghost 생성 원인이 더 이상 버그(자연어)가 아닌 실제 외부 의존성(External Dependencies)임이 100% 증명되었으며, 노드가 부족한 껍데기 폴더 수백 개가 납작하게 압축되어 v0.3.33.1 마일스톤의 최종 최적화가 완성됨.

14. **[레이아웃 병목 해결] Cluster Packing (AABB Overlap) 최우선 적용 및 NaN 블랙홀 버그 파악 (현재 진행)**
    - **증상 1 (NaN 블랙홀 프론트 프리징):** 렌더러 복구 직후, 화면이 다시 하얗게 먹통이 되며 2.4 Billion (24억) 번의 무한루프를 도는 치명적인 버그가 발견됨.
    - **원인 1:** Spatial Grid 로직(`resolveClusterOverlaps`)에서 아직 좌표(`position`)가 없는 초기 클러스터의 Bounding Box(`minX`, `maxX`)가 `Infinity`로 평가되었고, 이를 이용해 Grid Cell을 계산하면서 `NaN`이 발생함. 그 결과 모든 미좌표 클러스터들이 `"NaN, NaN"` 셀(블랙홀)에 몰려들어 중복 교차 검증을 일으키며 메인 스레드를 얼려버림.
    - **해결 1:** `if (minX === Infinity) continue;` 방어 코드를 단 한 줄 주입하여 블랙홀 생성을 원천 차단. 메인 스레드 프리징 완벽 해결.
    - **증상 2 (클러스터 중첩 / Opaque Blob):** 성능 이슈를 해결하고 화면이 떴으나, 수많은 클러스터들이 동일한 초기 좌표(예: `x:0, y:0`)에 배치되면서 사실상 하나의 거대한 덩어리로 겹쳐 보임. 가독성이 0%에 수렴.
    - **해결 2 (Cluster Packing 플랜 수립):** 압축/Ghost 이슈는 종료되었음을 확인. 이제 **"클러스터들을 서로 밀어내어 사방으로 흩뿌리는(Packing) 작업"**을 최우선 목표로 전환함.
    - **조치 (예정):** `canvas-engine.js`의 `resolveClusterOverlaps` 함수를 개조하여 중심이 완전히 동일한(`dist < 0.001`) 클러스터들을 무작위 폭발(Explosion) 각도로 밀어내고, Padding과 Push Force를 대폭 상향하여 "바둑판"이 아닌 "넓은 대륙" 형태로 클러스터 간의 간격을 시원하게 확보할 계획 수립.

15. **[병목 해결] 모노레포 Scale LOD 컷오프 삭제 및 현미경 줌 감도 보정 (완료)**
    - **증상 1 (모노레포 엣지 소멸):** 줌아웃을 조금만 당겨도(`Zoom: 0.005`) VSCode-main 그래프의 엣지와 히트맵이 전부 소멸하는 문제 발생.
    - **원인 1:** `canvas-engine.js`의 `renderEdges2D()` 함수 최상단에 하드코딩된 `if (zoom <= 0.05) return;` 방어 코드가 모든 엣지 렌더링을 차단하고 있었음.
    - **해결 1:** 엔진 차원의 줌 레벨 기반 강제 정보 삭제 로직을 완전 폐기함. 대신 사용자가 직접 통제하는 3단계 명시적 LOD 모드(`FULL`, `CLUSTER`, `NONE`)를 UI와 연동하여 도입. `FULL` 모드 시 한계 줌에서도 모든 엣지를 렌더링하여 모노레포 전체 구조 조망을 보장.
    - **증상 2 (카메라 현미경/스케일 폭발):** 거시적인 상태(`Zoom: 0.001`대)에서 휠을 한 번 굴렸을 때 화면이 300% 이상 튀어오르는 극단적 가속 발생.
    - **원인 2:** 휠 줌 스칼라가 고정값인 `zoom *= 1.1`로 묶여 있어 극단적으로 작은 줌 레벨에서 10배에 가까운 스케일 점프 현상이 나타남. 트랙패드에서의 고빈도 호출 시 폭발적으로 증폭됨.
    - **해결 2:** `Math.max(0.005, oldZoom * 0.15)` 방식의 적응형 감속(Non-linear Sensitivity) 로직을 도입하고, `e.deltaY`를 그대로 사용하여 지수 점프 현상 제거. 이제 휠 속도에 맞춰 부드럽게 초점을 잃지 않고 조작 가능함.
    - **검증 체계 추가:** 60프레임마다 콘솔에 `[LOD_FPS_VERIFY]` 로그를 출력하여, FULL/CLUSTER/NONE 상태 전환 시 20/40/60 FPS 달성 여부를 육안으로 즉시 확인할 수 있도록 조치함.

16. **[뷰 계층 해결] Roots Only 버그 수정 및 Continent 레벨 가시성 복구 (완료)**
    - **증상:** `Roots Only` 가시성 옵션을 켰을 때 대륙(Continent) 레벨의 폴더들(`src`, `ui` 등)이 모두 사라지고, 최상위 프로젝트 껍데기 박스(`folder_root`) 단 하나만 화면을 뒤덮는 현상. 또한 껍데기가 닫혔음에도 수천 개의 내부 노드들이 뚫고 나와 화면에 혼재됨.
    - **원인:** `expandRootsOnly()` 로직이 `folder_root`와 같은 진정한 Depth-0 루트들조차 모조리 `collapsed = true`로 강제 설정하여 1단계(Continent) 클러스터가 화면 탐색기(Resolver)에서 아예 수집되지 않음.
    - **해결:** 주석에 적혀있던 본래의 설계(루트 클러스터는 Expanded, 1단계 클러스터는 Collapsed)를 코드로 완벽하게 구현. 최상위 루트는 `collapsed = false`로 강제 전개하고, Level 1 이상의 클러스터들만 `collapsed = true`로 설정하도록 `setAllClustersCollapsedState` 로직을 수정함. 이제 Roots Only 작동 시 프로젝트 전체 껍데기가 열리며 내부의 Continent 폴더들이 예쁘게 닫힌(Collapsed) 상태로 정렬됨.

17. **[가시성 추가 해결] Roots Only 모드에서 Continent 레벨 대량 실종 현상 수정 (완료)**
    - **증상:** "Roots Only" 모드 실행 시 `src`, `ui` 등 242개에 달하는 Continent 레벨(1단계) 클러스터들이 화면에서 사라지고, 껍데기(`folder_root`)와 그 직속 노드들만 남는 현상 재발견.
    - **원인:** `expandRootsOnly()` 로직이 오직 `folder_root`와 같은 최상위 World 레벨만 진정한 루트(`isRoot = true`)로 취급하여 확장(Expanded)하고, 정작 사용자가 보길 원하는 Continent 레벨 클러스터들은 `collapsed = true`로 닫아버림. Canvas Engine은 닫힌 클러스터의 내부 노드들을 렌더링에서 배제(Filter)시키고, 닫힌 상태의 렌더링 로직 한계로 인해 시각적으로 모두 소멸한 것처럼 보였음.
    - **해결책:** `setAllClustersCollapsedState` 내부의 `isRoot` 판정 로직을 업그레이드하여, 진정한 World 레벨 루트뿐만 아니라 그 자식들(Continent 레벨)까지도 함께 `isRoot` 판정을 받게 함. 이를 통해 대륙(Continent) 레벨 클러스터들이 정상적으로 펼쳐져 내부 노드를 보여주도록(Collapsed = false) 수정 완료.
