
```js
// 수정 전 — O(C) per call
(this.clusters || []).find(c => c.id === clusterId)
```

**엣지 루프에서 2회 호출:**
```
O(E × C) = 69,677 edges × ~200 clusters ≈ 14,000,000회 배열 탐색
→ NodeCacheTime 1238ms의 직접 원인
```

## Phase 0 핫픽스 — getSemanticGroup O(E×C) → O(E) ✅

### 변경 내용

**`ui/canvas-engine.js`**

`getSemanticGroup(node)` 시그니처에 `clusterLayerMap` 선택 인자 추가:
```js
// 수정 후
getSemanticGroup(node, clusterLayerMap) {
    const layer = clusterLayerMap
        ? clusterLayerMap.get(clusterId)   // O(1)
        : clusters.find(...)               // O(C) fallback
}
```

`updateNodeStats()` 엣지 루프에서 이미 구축된 `clusterLayerMap` 전달:
```js
// 수정 전
const tgtGroup = this.getSemanticGroup(tgtNode);        // O(C) × E

// 수정 후
const tgtGroup = this.getSemanticGroup(tgtNode, clusterLayerMap); // O(1) × E
```

### 이론적 예측

```
수정 전: O(E × C) ≈ 70K × 200 = 14M ops → 1238ms
수정 후: O(E)     ≈ 70K        = 70K ops  → ~6ms 수준 (200배 개선)
```

## Phase 2.1 Backend Projector 핫픽스 & IPC Timeout 픽스 ✅

### 병목 및 버그 원인

1. **Backend Projector O(N * E) 병목:** `ProjectionLayer.ts`에서 각 엣지에 대해 부모 파일 노드를 찾기 위해 전체 그래프 노드를 배열로 순회 (`Array.find()`)하여 `O(N * E)` 지연 발생. 대형 프로젝트에서 `project()` 메서드 자체가 `26초` 이상 점유.
2. **Frontend Loading Timeout:** 캔버스 UI 초기화 시점에 백엔드에서 `sendProjectState`를 호출하지만, 내부적으로 `engine.autoDiscover(...)`를 1만 개 이상의 파일을 대상으로 동기화(await) 대기함. 이로 인해 IPC 페이로드가 발송되지 못하고 프론트엔드의 `Force removing loading overlay via timeout (3000ms)`이 먼저 발생. 그 결과 `canvas-engine`이 `projectState`를 수신하지 못한 채 빈 화면을 렌더링.

### 변경 내용

**`src/core/projection/ProjectionLayer.ts`**
- `projectToFileLevel()`에서 노드 조회를 위한 `Map` 캐싱 적용 (`const nodeMap = new Map()`).
- `Array.find()` 기반의 O(N*E) 룩업을 O(1) 해시 검색으로 대체. -> `26,000ms` 소요되던 투영 프로세스가 `1~2ms`로 극적 감소.

**`src/webview/CanvasPanel.ts`**
- `sendProjectState()` 내의 `autoDiscover` 로직을 비동기 블록으로 분리.
- `forceReset`이 아닐 경우 초기 `postMessage`를 즉시 발송하여 프론트엔드가 즉각 반응하도록 보장하고, 백엔드에서 조용히 `autoDiscover` 및 스냅샷 병합을 이어가도록(Non-blocking) 수정.

Density 모드를 활성화하여 테스트한 결과, 파이프라인 전방 차단이 완벽하게 동작함을 확인했습니다.

**테스트 결과 (VSCode-main 프로젝트 규모 추정, 1933 엣지 로드 환경):**
```text
RawEdgeCount: 1933
MaterializedEdgeCount: 0
UpdateNodeStatsInputEdges: 0
ValidationInputEdges: 0 (로깅 스킵됨 = Payload 배열 길이 0)
NodeCacheTime: 1.8ms (nodes=685, edges=0)
GraphBuildTimeMs: 로깅 스킵됨 (로딩 오버레이 렌더링 프레임 생략될 정도로 즉시 반환)
```

**결과 요약:**
`Create Less` 철학 검증 성공. 
정책 기반 필터링(MaterializationPolicy)을 통해 엣지가 $O(0)$으로 소멸하면서 `updateNodeStats`, `validateEdgesBatch`, `Adjacency` 생성 등 뒤따르는 모든 $O(E)$ 파이프라인 연산이 근원적으로 차단됨을 증명했습니다.

## Phase 2.2 — UI 렌더링 파이프라인 및 백엔드 Layout 병목 극복 ✅

### 병목 및 버그 원인

1. **Backend Force Layout O(C²) 병목:** `DataPipeline.scanProject`가 백엔드에서 동작하며 `LayoutEngine.applyLayout`을 호출할 때, 수천 개의 클러스터(C)에 대해 Force-Directed Graph Layout 연산(O(C²))이 150번이나 실행되었습니다. 대형 프로젝트(예: VSCode-main)에서는 수억 번의 연산으로 인해 Extension Host가 약 24.7초간 `Unresponsive` 상태에 빠지고, 반발력(Repulsion)이 폭주하여 노드 좌표가 `±600,000` 바깥으로 튕겨 나갔습니다.
2. **Frontend `JSON.stringify` 병목:** `canvas-engine.js` 내의 `[DEBUG_RENDER_NODES]` 및 `[DEBUG_NODES]`가 수만 개의 노드 배열을 `JSON.stringify`로 직렬화하여 출력하면서, Webview V8 엔진의 이벤트 루프가 멈추고 엄청난 메모리와 GC 부하를 유발했습니다.

### 변경 내용

**`src/core/LayoutEngine.ts`**
- 클러스터 개수(C)가 일정 수치를 초과하면 노드 개수의 제곱에 반비례하여 강제로 반복 횟수(ITERATIONS)를 대폭 줄이는 안전장치 추가.
- `ITERATIONS = Math.max(0, Math.floor(500000 / (C * C)))`
- 이로써 Extension Host 이벤트 루프 블로킹 해제 및 우주 끝까지 노드가 밀려나는 초거대 척력 부작용 차단.

**`ui/canvas-engine.js`**
- `JSON.stringify`를 호출하는 모든 대형 배열 로깅(`DEBUG_RENDER_NODES`, `DEBUG_NODES`, `FLOW_DEBUG` 등) 완전 주석 처리 및 잔여 구문 에러 해결.
- 렌더링 직전 가시 노드들의 최소/최대 좌표를 파악할 수 있도록 O(N) 순회 방식으로 `[PERF] NodeBounds` 로깅 및 `[PERF] Camera` 상태 로깅 추가.

**결과 요약:**
Webview 프리징(stringify 병목), 화면 먹통(초거대 좌표 이탈), Extension Host 프리징(Layout O(C²))의 3대 중대 결함이 모두 식별 및 제거되었습니다.

- 렌더링 파이프라인에서 카메라 줌/팬만 일어날 때는 노드/엣지 반복문을 돌지 않게 되어 **FPS 대폭 향상**. (12K Nodes / 70K Edges 환경에서 Viewport 외부 요소 전부 Culling 처리).

## Phase 3A 핫픽스 — Spatial Query 무효화 및 레이아웃 붕괴 현상 수정 ✅

### 병목 및 버그 원인

1. **`RBush` 대소문자 미일치로 인한 인덱스 구축 실패:** `node_modules/rbush/rbush.js` (UMD) 패키지는 전역 객체로 `RBush` (대문자 R, B)를 내보냅니다. 프론트엔드 엔진에서 `typeof rbush !== 'undefined'`로 소문자 체크를 하여 공간 인덱스 트리가 생성되지 않고(null), fallbackMode로 전환되어 모든 `search` 및 `insert` 동작이 무시되고 있었습니다.

### Phase 3D: 클러스터 드래그 시 시각적 경계 박스(Bounding Box) 미갱신 버그 수정
- **증상:** 노드나 클러스터 헤더를 드래그하여 이동시킬 때, 노드들은 마우스를 따라 이동하지만 클러스터의 시각적 경계선(박스)은 기존 위치에 고정되어 있는 문제 및 중첩 클러스터 동기화 실패.
- **원인:**
  1. 클러스터 경계 영역(bounds)이 렌더링 최적화를 위해 공간 인덱스(RBush) 구축 시점에 한 번만 계산되고, 드래그 도중(`mousemove`)에는 업데이트되지 않았음.
  2. 중첩된 클러스터(클러스터 내부의 클러스터) 구조에서 부모 클러스터와 자식 클러스터를 함께 재계산하는 연계 로직이 누락되어, 부분적으로만 박스가 이동함.
- **조치:**
  - `canvas-engine.js`에 `computeClusterBounds()` 전용 메서드를 분리하여 동적으로 경계 박스를 재계산(O(1) 근접 연산)할 수 있도록 구현.
  - `mousemove` 이벤트 루프 내에서, 드래그되어 영향을 받는 노드들의 소속 클러스터를 식별하고, 해당 클러스터의 **최상위 부모(Top-level Ancestor)**를 역추적하여 위에서부터 아래로 재귀적으로 경계선을 동기화하도록 로직 고도화.
  - 결과적으로 부모 클러스터를 통째로 이동시키거나 내부의 자식 노드만 단일 이동시켜도 모든 계층의 클러스터 박스가 실시간 60FPS로 끊김 없이 갱신되도록 해결.

### LayoutEngine World Packing 구조 (`LayoutEngine.ts:294-323`)

```ts
let worldX = 0, worldY = 0, worldRowMaxHeight = 0;
const MAX_WORLD_WIDTH = 12000;

for (const cont of sortedContinentsArr) {
    if (worldX + cont.estWidth > MAX_WORLD_WIDTH && worldX > 0) {
        worldX = 0;
        worldY += worldRowMaxHeight;  // ← 누적!
        worldRowMaxHeight = 0;
    }
    // continent 배치 (worldX, worldY)
    worldX += cont.estWidth;
    worldRowMaxHeight = Math.max(worldRowMaxHeight, cont.estHeight);
}
```

### Root Cause: `loadProjectState()` 카메라 초기화 이중 경로

`ui/canvas-engine.js`의 `loadProjectState()` 내에 두 개의 서로 다른 카메라 복원 경로가 존재하여 `fitView()`가 특정 조건에서 실행되지 않음.

```js

    if (wsState.camera) camera = wsState.camera;      // ①
    else if (projectState.view) camera = projectState.view; // ②
    this.updateZoomDisplay();
}
```
데이터가 아직 할당되기 전에 카메라를 원점 근처로 고정시킴.

**경로 2 (L6316-6334, 데이터 준비 후):**
```js

    if (projectState.transform) {
        transform = projectState.transform;  // ③

    }
```

## Phase 4-A — VisibleGraph Resolver Spec & Implementation (7/10)

### 배경

Phase 3까지 Hierarchy Tree, Depth 계산, Ancestor 탐색, Root 검출, LOD State가 모두 검증됨. 그러나 "Visible Graph" 개념 자체가 코드베이스에 존재하지 않았고, `_visibleNodesCache`는 단순 Render Cache일 뿐 계층적 LOD를 표현하지 못함.

Phase 11 사전 분석 (Phase 0 Structure Investigation, Phase 1-A, Phase 1-B) 결과:
- `_visibleNodesCache`는 **Visibility Layer가 아니라 Render Cache** → 별도 Visible Graph Resolver 필요
- 좌표는 LOD와 완전히 독립적 → Layout 수정 불필요
- `ClusterHierarchy`는 Phase 2에서 frontend에 구축 완료, backend에는 없음

### Resolver Spec 확정

Phase 4-A에서 논의된 핵심 변경사항:

1. **depth 기반 LOD → Telescope Expansion 방식으로 전환**
   - 잘못된 가정: `LOD0=depth0, LOD1=depth1, ...`
   - 올바른 모델: `LOD = Expansion Policy` — `expandedClusters`가 상태의 중심

2. **visibleClusters Fixed-Point Telescope:**
   ```
   visibleClusters = roots
   repeat:
     for each c in visibleClusters:
       if c.id in expandedClusters:
         visibleClusters += children(c)
   until stable
   ```

3. **findVisibleRepresentative(node):**
   - `path = [node.cluster_id, ...ancestors(node.cluster_id)]`
   - 반환: `path.find(id => visibleClusters.has(id))` — **가장 깊은 visible ancestor**

4. **Aggregate Edge 규칙:**
   - `fromRep ≠ toRep` → `aggregate[fromRep→toRep]++`
   - same-cluster edge는 skip (internal)

5. **LOD0 (Virtual Project):**
   - `expandedClusters.size === 0` → 가상 `__PROJECT__` cluster 1개 반환, edges 없음

6. **Resolver Stateless 원칙:**
   - `resolveVisibleGraph(rawGraph, hierarchy, expandedClusters)` — `currentLODLevel`은 Resolver가 보지 않음

### 미해결 이슈

**LOD1 expandedClusters 불일치:**
- Spec 표: LOD1 = `expandedClusters = {roots}`, visibleClusters = `app, core, docs` (roots only)
- Telescope 알고리즘: `expandedClusters = {roots}` → roots가 expanded → children까지 전부 visible → LOD1이 아니라 LOD2
- 해결 필요: **LOD1은 expandedClusters = `{}` (빈 set), LOD0은 Resolver 밖에서 UI 레이어가 처리**

2. `collapseCluster()` 내부에서 로그가 찍히려면 `if (!this.clusterHierarchy) return;` 방어 코드를 통과해야 함. `initLODState()`에서 이미 정상 로딩되었기에 `this.clusterHierarchy`는 유효함.
3. 그러나 UI 토글 이벤트 핸들러(`canvas-engine.js:8234`) 내에서 상태 반전과 `self.render()` 호출만 이루어지고, 가장 중요한 **`this.isGraphDataDirty = true;`** 플래그 설정이 누락되어 있었음.
4. `isGraphDataDirty` 플래그가 `true`가 되지 않으면 `render()` 함수 내부에서 `updateNodeStats()`가 실행되지 않고 조기 종료됨.
5. `updateNodeStats()`가 실행되지 않으므로, 백엔드로부터 전달받는 `_computeResolverVisibleIds()` (LOD Resolver) 로직이 트리거되지 않아 `event=resolver`가 출력되지 않으며 엣지 필터링(`_visibleGraphClusterIds`)도 갱신되지 않았음.

### 변경 내용

**`ui/canvas-engine.js`**
- `renderClusterVisibilityPanel` 내의 `toggleBtn.addEventListener('click', ...)` 핸들러에 `self.isGraphDataDirty = true;` 구문을 삽입.
- 이를 통해 사용자가 UI에서 클러스터를 접거나 폈을 때, 엔진이 변경된 `expandedClusters` 상태를 감지하여 LOD Resolver를 재실행하고(`updateNodeStats` → `_computeResolverVisibleIds`), 엣지 필터링까지 파이프라인이 매끄럽게 흐르도록 수정.

2. Console 로그에 `[perf_engine] event=collapse ...` 및 `[perf_engine] event=resolver ...`가 정상적으로 찍히는지 확인.

## 4. 최종 진범: State Cache Poisoning (상태 캐시 오염)

마지막 디버깅(BAD_NODE_INSPECTION)을 통해 드디어 **최종 원인**이 밝혀졌습니다.

### 🔍 원인 분석 (How it happened)
1. 과거 버전(v0.3.33 이전)에서 존재했던 버그로 인해, 고스트 노드들이 `sys_cluster_buffer`로 강제 이주당함.
2. 이 잘못된 상태(`cluster_id: 'sys_cluster_buffer'`)가 로컬의 `project_state.json`에 영구적으로 캐시됨.
3. 이후 코드를 고쳐 강제 이주 로직을 없앴으나, `loadProjectState`가 과거의 오염된 캐시를 읽어들임.
4. `StateManager.mergeState` 과정에서 `bufferNodes`(캐시)가 `coreSnap`(실제 파일 스캔 결과)보다 병합 우선순위가 높기 때문에, 캐시된 노드가 De-duplication에서 승리함.
5. 캐시된 노드의 `n.cluster_id`가 이미 `'sys_cluster_buffer'` 였으므로, **새로 스캔된 정상 폴더 경로(`folder_test_mcp_src` 등)가 무시되고 과거의 오염된 클러스터 상태가 영구히 유지**되는 현상이 발생.

## v0.3.33.3 `sys_cluster_buffer` Bounds 팽창 원인 분석 (진행 중) 🚧

### 병목 및 버그 원인

**증상:**
1. `sys_cluster_buffer`의 `computedHeight`가 65199 픽셀로 비정상적으로 팽창.
2. `sys_cluster_buffer`는 398개의 직속 노드(directNodes)를 가지며 자식 클러스터(childClusters)는 0개임.
3. 이로 인해 렌더링 시 최상위 컨티넌트들의 배치가 `Y=65000` 부근으로 밀려나는 현상 발생.

**원인 분석 (사용자-에이전트 합동 추론):**
1. **[기각] 계층 붕괴 가설**: `sys_cluster_buffer`가 모든 클러스터를 자식으로 삼켰을 가능성은 `childClusters: 0` 확인을 통해 완전히 제거됨.
2. **[기각] Workspace Restore 좌표 덮어쓰기 가설**: `DESKTOP_TRACK` 로그를 통해 레이아웃 엔진 이후부터 렌더링 직전까지 65549로 좌표가 고정됨을 확인.
3. **[유력] 속성 불일치(Attribute Mismatch)로 인한 Bounds 찢어짐 가설**:
   - 백엔드 `LayoutEngine.ts`는 노드 소속 판별 시 `n.cluster_id`만 참조함. 만약 비어있을 경우 `__unclustered__`로 할당하여 세계의 최하단에 배치.
   - 반면 프론트엔드 `canvas-engine.js`는 `n.cluster_id || n.data.cluster_id`를 참조함.
   - 따라서, 동일한 노드가 백엔드에서는 `__unclustered__`로 취급되어 하단(Y=65000)에 배치되었으나, 프론트엔드에서는 `sys_cluster_buffer` 소속으로 인식됨.
   - 이로 인해 `sys_cluster_buffer`의 실제 노드들(상단)과 불일치 노드들(하단)이 하나의 클러스터로 집계되면서 Bounds가 100 ~ 65299로 찢어지게 됨.
4. **[진단 로그 추가] BUFFER_EXTREMES**:
   - `canvas-engine.js`의 Bounds 계산 과정 직전에 `sys_cluster_buffer`에 속하는 노드 중 Y 좌표 상위/하위 5개를 출력하는 로그 추가.
   - 이를 통해 65000 픽셀 근처에 있는 노드들의 정체를 파악하고 `cluster_id` 속성 불일치 여부를 최종 확정 예정.

### 🚨 진범 체포 및 최종 결론
**원인: `StateManager.ts`의 무자비한 고스트(Ghost) 노드 강제 이주 정책**

`[NODE_CLUSTER_CHECK]` 로그를 통해 확인된 사실:
- `test/mcp/src/application.ts` 등 `Y=65000` 이상에 위치한 노드들은 원래 **정상적인 클러스터(예: `folder_test...`) 소속**이었음.
- 그러나 파일을 삭제하거나 `.synapseignore`에 추가하는 등의 이유로 디스크 스캔 결과(`coreSnap.nodes`)에서 누락될 경우, `StateManager.ts`의 `mergeState` 함수에서 `!isOnDisk` 조건에 걸리게 됨.
- 기존 로직은 이 노드들을 `ghost` 상태로 변경함과 동시에 **아무런 좌표 초기화 없이 무조건 `sys_cluster_buffer`로 강제 소속 변경**해 버림. (`finalClusterId = 'sys_cluster_buffer'`)
- 결과적으로, 원래 자기 대륙(`test` 등)의 저 멀리 하단(Y=65000, 90000)에 예쁘게 배치되어 있던 좌표를 그대로 간직한 채 소속만 Buffer Cluster로 바뀌게 됨.
- 결국 Buffer Cluster는 Y=100에 있는 노드부터 Y=90000에 있는 노드까지 모조리 품게 되어 **Bounds Height가 65199에서 90000까지 찢어지는 대형 사고**가 발생한 것임.

### 🛠️ 해결책 (v0.3.33.3 Fix)
- **`src/core/canvas-engine/StateManager.ts` 수정**:
  ```typescript
  } else if (!isOnDisk) {
      finalStatus = 'ghost';
      // 강제 이주 금지! 원래 소속(cluster_id)을 유지하여 바운즈 찢어짐 방지
      finalClusterId = n.cluster_id !== undefined ? n.cluster_id : 'cluster_ghosts';
  }
  ```
- 이 수정으로 인해 고스트 노드들은 원래 자신이 속해 있던 클러스터(폴더) 내부에 그대로 남아 렌더링되며, 더 이상 엉뚱한 System Cluster를 수만 픽셀 크기로 팽창시키지 않음.

- **원인:** `src/core/LayoutEngine.ts`에서 노드에 `position` 프로퍼티가 아예 없는 경우(즉 초기 데이터 생성 시 좌표를 부여받지 못한 노드들), 좌표 배치 로직(`n.position.x = cx...`)을 완전히 스킵해버림. 이로 인해 프론트엔드(`canvas-engine.js`)에서 스킵된 노드들을 일괄적으로 `(0,0)`에 몰아넣었고, 모든 노드가 한 점에 겹치게 되며 클러스터 영역(Bounds) 역시 극도로 좁게 왜곡되어 화면에서 완전히 소멸된 것처럼 처리됨.
- **수정:** `LayoutEngine.ts` (Phase 5: Place Nodes inside Clusters) 단계에서 `n.position` 객체가 없으면 `{x:0, y:0}`로 초기화한 뒤 정상적인 그리드 간격 수식을 적용하도록 보완. 이제 노드들이 클러스터 내부 영역에 정상적으로 펼쳐져 렌더링됨.

### 4. 클러스터 드래그 — 단일 경로로 통합

**`ui/canvas-engine.js`** — 클러스터 드래그 경로를 `draggingCluster`로 통합

**Before:** 노드 있으면 `selectedNodes`, 없으면 `draggedEmptyCluster` 두 경로 분리  
**After:** 어떤 클러스터든 `draggingCluster` 단일 경로

**mousemove에서 이동 처리:**
```js
// 자신 + 모든 자식·손자 클러스터 ID 수집
collectIds(this.draggingCluster.id) → subtreeIds

// 클러스터 position 이동
for (const cluster of this.clusters) {
    if (subtreeIds.has(cluster.id)) cluster.position += dx/dy;
}

// 소속 노드 이동
for (const node of this.nodes) {
    if (subtreeIds.has(node.cluster_id)) node.position += dx/dy;
}
```

**효과:** 최상위 루트든 중간 폴더든 리프 클러스터든, 헤더를 잡고 드래그하면 하위 모든 클러스터와 노드가 함께 이동.
