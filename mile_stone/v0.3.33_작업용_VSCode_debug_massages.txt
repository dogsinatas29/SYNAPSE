NodeCacheTime ($1238.6\text{ms}$) vs EdgeCacheTime ($40.0\text{ms}$)여기 자네가 말한 "Cache Build 내부에 무슨 작업이 숨어있음"의 스모킹 건이 있다.노드가 $12,193$개이고 엣지가 $69,677$개다. 상식적으로 연결선($O(N^2)$에 가까운 대량 데이터)을 처리하는 EdgeCacheTime은 단 $40\text{ms}$밖에 안 걸렸다.그런데 고작 $12,193$개짜리 노드 객체를 처리하는 NodeCacheTime이 무려 $1,238.6\text{ms}$를 처먹고 있다. 엣지보다 30배나 느리다!🔍 NodeCacheTime 내부에서 터진 병목 가설노드 $1.2\text{만}$ 개 순회하며 메모리 캐시 만드는 건 최신 JS 엔진에서 $10\text{ms}$도 안 걸려야 정상이다. $1.2$초나 붙잡고 있다는 건 canvas-engine.js:5838 라인 근처에서 노드 하나하나를 캐싱할 때마다 무거운 동적 연산을 인젝션하고 있다는 뜻이다.오브젝트 불변성/깊은 복사 (Deep Clone) 오버헤드:노드 캐시를 빌드할 때 백엔드에서 넘어온 생 데이터(Raw Object)를 안전하게 보호한답시고 JSON.parse(JSON.stringify(node))나 무거운 재귀적 구조 분해 할당을 1.2만 번 반복하고 있을 가능성.네임스페이스 및 구조 복원 엔진의 동적 개입:시냅스가 대형 모노레포를 견디기 위해 실행하는 CONTINENT, CLUSTER 분할 및 매핑 알고리즘이 이 NodeCacheTime 루프 내부에 인라인(Inline)으로 박혀서 노드 한 개 처리할 때마다 전체 맵의 경로를 문자열 파싱(split('/'))하고 비교 연산하고 있을 가능성.DOM/Canvas Context 미리 찌르기 버그:루프 내부에서 Canvas 텍스트의 너비를 미리 계산하겠다고 ctx.measureText()를 $1.2\text{만}$ 번 다이렉트로 호출하며 CPU의 실행 파이프라인을 다 깨부수고 있을 가능성.

## 1. TransferTime 버그

```text
TransferTime: -1783082993606.4ms
```

이건 거의 100% 시간 기준 혼용입니다.

```ts
// Backend
Date.now() // 1783082994000

// Frontend
performance.now() // 393.6
```

그리고

```ts
393.6 - 1783082994000
```

을 하면

```text
-1783082993606.4
```

비슷한 숫자가 나옵니다.

즉

```text
Date.now()
vs
performance.now()
```

혼용 가능성이 매우 높습니다.

이건 성능 병목 증거라기보다

```text
측정 시스템 버그
```

로 보는 게 맞습니다.

먼저 고쳐야 합니다.

v0.3.32

보다

"무엇을 보여줄까?"

가 더 중요한 단계로 넘어가게 될 가능성이 크다.
