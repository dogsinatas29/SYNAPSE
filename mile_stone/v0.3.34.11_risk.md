# v0.3.34.11 Risk Analysis

## SYNAPSE Intent Intelligence Engine Risk Assessment

---

# 목적

v0.3.34.11의 목표는 단순 AST 통합이 아니다.

이 버전의 목표는

```text
Architecture Intelligence Report
```

를 생성하는 것이다.

최종 산출물은:

```text
logic_report.html
```

이며,

아키텍트가 실제 의사결정을 내릴 수 있는

증거 기반(Evidence-backed) 구조 분석 문서를 생성해야 한다.

---

# 핵심 원칙

## Principle A

### Intent Engine이 최종 판단자다

```text
Source Code
↓
Regex Scanner
↓
Intent Candidate
↓
Evidence Providers
(AST / Symbol / Contract / Runtime)
↓
Intent Engine
↓
Architecture Intelligence Report
```

최종 결과는 Intent Engine이 결정한다.

어떤 Evidence Provider도 단독으로 결과를 결정하지 못한다.

---

## Principle B

### Evidence First

모든 결론은 반드시 증거를 가진다.

허용되지 않는 형태:

```text
folder_fs ↔ folder_mm

Strong Bridge
```

허용되는 형태:

```text
folder_fs ↔ folder_mm

Strong Bridge

Evidence

fs/read_write.c
↓
mm/filemap.c

Function Call

fs/buffer.c
↓
mm/page-writeback.c

Ownership Dependency
```

---

## Principle C

### Deterministic Architecture Intelligence

동일한 소스코드에 대해

```text
Windows
Linux
macOS

VS Code
Cursor
VSCodium
Windsurf
```

환경이 달라도

최종 Architecture Conclusion은 동일해야 한다.

달라질 수 있는 것은

```text
Evidence Quantity
Confidence
```

뿐이다.

---

## Principle D

### Architecture First

SYNAPSE는

```text
Code Intelligence Tool
```

이 아니다.

SYNAPSE는

```text
Architecture Intelligence Tool
```

이다.

사용자는 함수 호출 목록이 아니라

```text
어디를 수정해야 하는가
왜 수정해야 하는가
수정하면 무엇이 달라지는가
```

를 원한다.

---

## Principle E

### Linus Test

리포트는

리누스 토르발즈급 메인테이너가 읽어도

의미가 있어야 한다.

즉 다음 질문에 답해야 한다.

```text
왜 이게 문제인가?

그 증거는 무엇인가?

이걸 수정하면 무엇이 좋아지는가?

신뢰할 수 있는 분석인가?
```

# B-01 (Analysis Boundary — NOT a Risk)

## Runtime Hidden Dependency

### 분류

```text
Analysis Boundary
```

Risk가 아니다.

이것은 SYNAPSE의 결함이 아니라

정적 분석 자체의 고유한 한계다.

---

### 설명

다음은 어떤 정적 분석 도구도 완전 분석 불가.

```text
Function Pointer
Ops Table
Callback
Event Dispatch
Runtime Registration
```

예)

```text
file_operations
net_device_ops
io_uring_ops
thinker->func()  ← Doom Engine
```

---

### 근거

```text
clangd        → 불가
rust-analyzer → 불가
IntelliJ      → 불가
Visual Studio → 불가
```

SYNAPSE만의 한계가 아니다.

---

### 처리

미티게이션 대상이 아니다.

반드시 리포트에 명시해야 한다.

예)

```text
Analysis Boundary:
이 엣지는 Function Pointer 기반이므로
정적 분석으로 추적 불가.
정적 분석 가능 영역에서만 결과 제공.
```

---

### 목적

사용자가 보고서를 읽을 때

```text
SYNAPSE가 놓친 것인가?
```

가 아니라

```text
정적 분석 한계 영역임을 인지한 상태에서 읽는다.
```

가 되도록.

# R-16

## Evidence Contradiction Risk

### 설명

복수 Evidence Provider가 서로 다른 답을 됩니다.

예)

```text
Regex  : A → B  Positive
AST    : A → B  Negative
Contract: A → B  Positive
Runtime: A → B  Unknown
```

---

### 영향

Intent Engine이 올바른 신뢰도를 계산하지 못하면

```text
허위 Confidence
```

가 생성된다.

---

### 위험도

Critical

---

### 대응

Evidence Conflict Resolution Engine 필수.

출력 예)

```text
Evidence Conflict Detected

Regex:      Positive
AST:        Negative
Contract:   Positive
Runtime:    Unknown

Decision:   Weak Dependency
Confidence: 41%
Reason:     AST Negative → Contract 우선, Runtime 미확인
```

출력에 직접 노출.

숨기지 않는다.

# 최종 결론

v0.3.34.11의 가장 큰 리스크는

AST도 아니고

HTML도 아니다.

진짜 리스크는

```text
결론은 있는데

증거가 없는 것
```

이다.

그리고 그 다음 리스크는

```text
증거는 있는데

왜 중요한지 설명하지 못하는 것
```

이다.

그리고 세 번째 리스크는

```text
증거는 있는데

서로 충돌하는 것
```

이다.

이것이 v0.3.34.11의 가장 어려운 문제다.

Regex, AST, Contract, Runtime이

서로 다른 이야기를 할 때

Intent Engine이 무엇을 신뢰할 것인가를

결정하는 것.

v0.3.34.11은

그래프를 보여주는 버전이 아니다.

증거를 기반으로

아키텍트가 결정을 내릴 수 있는

Architecture Intelligence Report를 생성하는 버전이다.

## Design Intent Inference (Architectural Archaeology)

### 설명

다음 질문은 v0.3.34.11이 답할 수 없다.

```text
이 구조가 의도된 설계인가?
이 결합이 기술 부채인가?

```

---

### 이유

이 질문에 답하려면

```text
Commit History
Issue Tracker
Design Document
Code Review Discussion
```

가 필요하다.

설계 의도를 추론할 수 없다.

### 목표 버전

```text
v0.4.x 이후
```

Git History + Issue Tracker + Commit Intent 통합 시

비로소 가능한 영역이다.

```text
Trustworthy Structural Intelligence
```
