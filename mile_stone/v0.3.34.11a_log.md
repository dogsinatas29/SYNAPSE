```

                        IntentEdge[]
```

### 핵심 설계 원칙

| 원칙 | 내용 |
|---|---|
| **Finding-first** | Action은 반드시 Finding에서 도출. IntentEdge 단독 → Action 생성 금지 |
| **IntentEdge 역할 한정** | Action 결정 ❌, 신뢰도 보정만 ⭕ |
| **Top N 제한** | Generator가 아닌 Exporter 책임 |
| **Deterministic** | 동일 입력 → 동일 Finding → 동일 Action 100% 보장 |

### FindingGenerator 탐지 규칙

| 탐지 조건 | findingType |
|---|---|
| A→B 이면서 B→A 도 존재 | `circular_dependency` |
| `fanOut >= 5 && fanOut > globalAverageFanOut * 2` | `hub_concentration` |
| 동일 source에서 confidence < 0.4 엣지가 3개 이상 | `diffuse_coupling` |
| 단일 엣지, confidence < 0.35 | `weak_link` (Finding만, Action 생성 금지) |

### ArchitectureActionGenerator 매핑

```
circular_dependency → separate
hub_concentration   → separate
diffuse_coupling    → boundary
weak_link           → Finding만 생성 (Action 없음)
```

### impactScore 계산식 (확정)

```typescript
// Structural Importance = fanOut + fanIn + edgeDensityRatio 합산 후 0~1 정규화
structural = outEdges.length + inEdges.length + (outEdges.length / totalEdges)
impactScore = min(1.0, structural / maxStructural)
```

- `fanOut`: 외부 의존 수
- `fanIn`: 이 노드를 의존하는 외부 수
- `edgeDensityRatio`: 해당 노드 관련 엣지 수 / 전체 엣지 수
- Linux `mm/`, `scheduler/` → fanIn도 크므로 impactScore 높음 = "중요 노드" (분리 후보 아님)

## Phase 3: Architecture Decision Support (최종 확정 계획)

### 목표
단순한 숫자(Metric)나 현상(Finding) 나열을 넘어, 아키텍트가 납득할 수 있는 구체적인 **실행 가능 후보(Action Candidate)**를 도출하는 **의사결정 지원(Decision Support)** 엔진으로 격상.

### 핵심 구현 내용

#### 1. Structural Role Classification (God Object 폐기)
허브 = 악이라는 단순 규칙에서 벗어나 노드의 **구조적 역할(Structural Role)**을 결정론적으로 분류합니다. 
절대값 대신 백분위(Percentile, 예: `P90(fanIn)`) 기반의 임계치를 사용하며, 특히 `fanIn`의 절대적 볼륨(P90 이상)을 보장하여 오탐을 방지합니다.
- **Shared Infrastructure (정상):** 높은 `fanIn`을 갖지만 서브시스템 편향도가 낮음. → Action: **KEEP (명시적 유지 권장)**
- **Orchestrator (정상/주의):** 높은 `fanOut`을 가지며 다수의 서브시스템 제어. → Action: **KEEP (명시적 유지 권장)**
- **Domain Bottleneck (비정상):** 높은 `fanIn`과 높은 서브시스템 편향도(예: 60% 이상) 동반. → Action: **SEPARATE**

#### 2. Temporary Subsystem Provider 추상화
단순 디렉터리를 서브시스템으로 간주하는 위험성을 피하기 위해 `getSubsystem(node)` 추상 계층을 도입합니다.
- 초기에는 `path.split('/')[0]`을 사용하지만, 이는 임시 구현(Temporary)임을 명시하고 향후 Semantic Cluster 등으로 교체 가능하도록 설계합니다.

#### 3. Fact와 View의 분리 (Impact Vector 도입)
Magic Score(단일 점수)를 만들지 않고 Bootstrap 철학(Fact와 Interpretation 분리)에 따라 구조 벡터(Struct/Vector)를 유지합니다.
- **Bundle (Fact):** `impact = { fanIn, fanOut, skew, cycle }` 형태의 원시 벡터만 저장.
- **Priority (View):** 리포트 출력 단계(Exporter)에서만 우선순위를 위한 정렬용 복합 점수를 계산.

#### 4. Finding 메시지 포맷 고정 및 템플릿화된 Potential Effect
- **Finding 구조화:** `observation`, `interpretation`, `consequence` 필드를 명시적으로 분리하여 아키텍트 문서 형태를 고정합니다.
- **Potential Effect 템플릿화:** 단정적 예측(Expected Effect)을 버리고, 증거 기반 추론 범위 내의 잠재적 효과(Potential Effect)를 템플릿화하여 제공합니다.

## Phase 4: Subsystem Architecture Transition (2026-08-01)

### 목표
단순한 파일 수준(Node-centric)의 결합도 분석에서 벗어나, 아키텍트가 실제로 고민하는 **서브시스템 수준(Architecture-centric)**으로 의사결정 지원 계층을 격상. "파일"은 주인공이 아니라 증거(Evidence)로 역할 전환.

### 핵심 구현 내용

#### 1. Architecture -> Evidence 계층 분리
- **Subsystem-level Protagonist:** `fanIn`, `fanOut`, `skew` 계산과 구조적 역할 판정(`Shared Infrastructure`, `Orchestrator`, `Domain Bottleneck`)을 파일 단위에서 **서브시스템 단위**로 묶어 수행합니다. (예: `module.h` -> `module` subsystem)
- **Evidence Pattern:** 단순 파일 나열을 방지하고 "왜 이 서브시스템이 문제인가"를 증명하기 위해 구조적 결합 패턴을 추가했습니다. (예: `kernel/* -> drivers/* 67%`)
- **Top Files:** 각 서브시스템 판정의 원인이 되는 실제 코드를 증명하기 위해 `Evidence Layer`로 핵심 파일(Top Files)을 최대 3개까지만 제한하여 남겼습니다.

#### 2. Action Candidate 정교화 및 제한
- Action 대상이 파일(`gaudi2_regs.h`)에서 서브시스템(`module subsystem`)으로 변경되었습니다.
- **Top 10 강제 제한:** 40,000개가 넘는 비현실적인 Action 도출을 헌법 기준에 맞추어 `Top 10`으로 엄격히 잘라내어 아키텍트의 인지 부하를 없앴습니다.

#### 3. Control vs Dependency 분리 (Roadmap)
- 단순 의존성(fanIn/fanOut) 수가 절대적인 "시스템 제어(Control)"를 의미하지 않음을 인지했습니다. (예: `types.h`는 거대하지만 제어자가 아님)
- 리포트에 **Analysis Scope** 섹션을 명시하여 현재 한계(Dependency Structure만 분석 중이며 Runtime 제어나 Ownership은 포함되지 않음)를 투명하게 공개했습니다.
- 진정한 의미의 `Control Score`, `Coupling Score`, `Impact Score`, `Risk Score` 분리는 다음 마일스톤(v0.3.35)으로 연기했습니다.

### 핵심 구현 내용

#### 1. 질문 교체 (현실 기반의 5문답)

#### 2. Unresolved Symbol 격리 및 노이즈 차단

Finding 내부에 실질적인 결합을 증명하는 중간 브릿지인 **Critical Intent Edges**를 계산하고 출력하도록 엔진을 고도화했습니다.

## Phase 4.2: Architect Onboarding Map (6-Level Architecture) (2026-08-01)

### 목표
단순한 "구조 이상 탐지기"에서 벗어나, 낯선 거대 레포지토리를 처음 열었을 때 아키텍트가 던지는 질문의 순서와 인지 과정(Mental Model)에 맞춘 **"6단계 아키텍처 온보딩 맵(Architect Onboarding Map)"**으로 보고서 생성 계층을 전면 재설계.

### 시스템이 잘못된 위치 (근본 원인)
현재 엔진은 `Phase 0(지도)`와 `Phase 1(이해)`를 건너뛰고 바로 `Phase 4(절단 지점)`와 `Phase 5(분리 후 예측)`로 뛰어넘었음. 
그 결과 "왜 module을 잘라야 하는지", "module이 어디에 붙어 있는지"에 대한 컨텍스트(Subsystem Story)가 증발하여 아키텍트가 납득할 수 없는 리포트가 생성됨.

### 6-Level Architect Onboarding Map
새로운 질문 계층은 압축률 문제가 아니라 **질문의 계층을 유지하면서 증거를 접어두는(Folding) 문제**임. 요약은 하되 언제든 근거(Evidence)로 내려갈 수 있어야 함.

1. **System Map (시스템 구성)**
   - 질문: 이 시스템은 무엇으로 이루어져 있는가? (주요 클러스터 식별)
   - 결과: `[drivers, fs, net, mm, kernel]`
2. **Structural Flows (연결과 흐름)**
   - 질문: 시스템은 어떻게 움직이는가? (주요 Intent Edge 파악)
   - 결과: `kernel → drivers`, `UI → Command Service`
3. **Entry Points (작업별 진입점)**
   - 질문: 나는 어디서부터 봐야 하는가? (단일 진입점이 아닌 Task별 진입점 셋 도출)
   - 결과: `Feature Dev → Command Registry`, `Rendering → WebGLRenderer`
4. **Impact Analysis (변경 영향 범위)**
   - 질문: 여기 수정하면 어디까지 터지는가? (Blast Radius 계산)
   - 결과: `FileService 수정 → [Explorer, Search, SCM]`
5. **Boundary Analysis (절단 지점)**
   - 질문: 어디를 잘라야 하는가? (Subsystem 간 결합도 기반 경계 탐색)
   - 결과: `drivers ↔ kernel (12,443 edges)`
6. **Action Candidates (개입 결과 예측)**
   - 질문: 자르면 뭐가 좋아지는가? (분리 전후 비교 및 추정)
   - 결과: `kernel ↔ drivers (12,443 edges) → 분리 후 kernel-api ↔ drivers (321 edges)`

이 계층형 분석이 적용되면 리눅스 커널이든 VSCode든 동일한 온보딩 틀로 해석 가능.

## Phase 6: Architecture Forensics - The Drift Report (2026-08-03)

### 💡 "Why is this here?" - 증명 단계로의 진입
설계와 로드맵의 확장을 전면 동결하고, v0.3.34.11a의 유일한 성공 조건을 **"아키텍트가 납득할 수 있는 Drift Report 1장 생성"**으로 압축했습니다. 

1. **Drift Score의 객관화:** 
   복합 점수(Betweenness, Entropy 등)를 모두 폐기하고 오로지 `External Traffic Share (외부 커뮤니티와 주고받는 트래픽 비율)`만을 사용하여 직관적인 관측치를 제공합니다.
2. **Community Signature 고정:**
   Louvain 알고리즘의 고질적 한계(실행 시마다 ID 변동)를 방어하기 위해 `Community ID` 대신 커뮤니티 내 `Top 3 Degree 노드`를 추출해 시그니처(`{mm, page_alloc, slab}`)로 활용합니다.
3. **Physical Region Granularity (Stage -1):**
   리전의 단위를 자동 추론하지 않고, 프로젝트별 고정 뎁스 프로파일(Linux=2~3, VSCode=3 등)을 도입하여 과압축이나 과분할을 선제 차단합니다.
4. **Community Stability (Stage 0.2B):**
   동일 입력에 대한 Louvain 3회 반복 및 NMI/ARI 측정을 통해 안정성을 검증하고, 미달 시 `Purity Variance`가 큰 불안정 리전을 즉각 리포팅합니다.

### 🛠️ 첫 번째 Linux Kernel 검증 실행 및 결과
`src/cli/generate_drift_report.ts`를 최초 작성하여 128MB의 리눅스 커널 `intent_edges.json`을 파싱하고 시뮬레이션했습니다.

- **관측 결과 1 (Purity):** `fs/btrfs/extent_io.c`의 Purity가 91%로 관측됨. 즉, btrfs는 다른 곳(mm 등)으로 이탈하지 않고 매우 견고하게 뭉쳐있음이 증명됨.
- **관측 결과 2 (Drift 없음):** `extent_io.c`의 External Traffic Share는 13%에 불과함. 즉 원래 있어야 할 곳에 제대로 위치해 있는 정상 노드임.
- **관측 결과 3 (가중치 왜곡 의심):** Community Signature가 `{types.h, errno.h, string.h}`처럼 전역 헤더로 잠식되고, Top Dependency가 `alpha/bitops.h`로 잡히는 현상 발생.

이는 기계적 스크립트가 성공적으로 동작했음을 알림과 동시에, 현재 `intent_edges.json`의 가중치 산정(Weight/EvidenceCount) 방식에 중대한 노이즈가 끼어 있음을 증명했습니다. 
이를 해결하기 위해, 특정 타겟(btrfs)에 집착하지 않고 **Global Top 20 Community Hubs** 및 **Global Top 20 Drift Sources**를 출력하도록 스크립트를 재편하여 가중치 검증 작업에 착수했습니다.

## Phase 7: Layer Classification & Community Quality Audit (2026-08-03)

### 💡 Garbage In, Garbage Out 차단 (증거 보존 원칙)
이전 단계에서 발생한 "전역 헤더 허브(types.h 등)의 커뮤니티 잠식 현상"을 해결하기 위해 `include/*`, `arch/*` 등 인프라 레이어를 강제 삭제(Drop)하는 방안을 기획했으나, 아키텍처 포렌식 원칙("증거 인멸 금지")에 따라 전면 백지화했습니다. 노이즈 역시 아키텍처의 일부이며, 삭제가 아닌 **계층 분리(Classification)**를 통해 보존해야 합니다.

### 🛠️ Execution Plan (Stage -0.6 ~ -0.65)
Drift Report 진입을 전면 봉인(Halt)하고, Louvain 엔진이 묶어내는 커뮤니티의 건강도를 진단하는 **Community Quality Audit**을 최우선 과제로 삼았습니다.

1. **Stage -0.6: Layer Classification**
   모든 노드를 물리적 특성에 따라 3대 계층으로 정밀 분류합니다.
   - **Business Layer:** 코어 로직 (`fs/*`, `drivers/*`, `net/*`, `mm/*`, `kernel/*` 등)
   - **Infrastructure Layer:** 전역 API 및 추상화 (`include/*`, `lib/*` 등)
   - **Architecture Layer:** 하드웨어 종속 구현 (`arch/*`)

2. **Stage -0.65: Community Quality Audit**
   전체 노드를 대상으로 Louvain 알고리즘을 수행한 뒤, 가장 거대한 Top 5 커뮤니티를 뽑아내어 **계층 감염도(Layer Infection)**와 **서브시스템 순도(Subsystem Purity)**를 덤프합니다.
   - `Layer Distribution`: 커뮤니티가 Business(비즈니스), Infrastructure(인프라), Architecture(플랫폼) 중 어디에 종속되어 있는지 백분율(%)로 측정. (예: Architecture 비중이 60% 이상이면 기능이 아닌 플랫폼으로 묶인 불량 커뮤니티로 판정)
   - `Region Distribution`: Business 노드만을 대상으로 소속 Physical Region 비율 측정.
   - `Top Regions`: 해당 커뮤니티를 지배하는 서브시스템 목록 출력 (`fs/btrfs`, `fs/ext4` 등).
   - `Community Signature`: 인프라 노드 방해를 막기 위해 **Business 노드 중 확장자가 .h가 아닌 Top 3 노드**로만 대표 이름(`{extent_io, inode}`)을 생성하여 신뢰성 확보.

### 🚀 검증 목표
위 단계에서 생성된 `Community Quality Audit` 리포트의 `Region Distribution` 및 `Top Nodes` 데이터를 아키텍트가 직접 확인하여, "Louvain 엔진이 단순한 Regex 매칭 노이즈를 넘어 상식적인 리눅스 서브시스템 단위(예: `fs/btrfs`, `mm/page_cache`)의 결합도를 제대로 묶어내는지"를 증명합니다. 검증이 성공적으로 완료될 경우 비로소 봉인을 풀고 Drift 평가 단계로 진입할 예정입니다.

## Phase 8: The Grand Conclusion (2026-08-03)

### 💡 4-Way Benchmark 최종 결과 분석
4개의 그래프 격리 수준에 따른 벤치마크 수행 결과, 대륙 생성기(Louvain)의 지능 문제가 아니라 **입력 엣지 데이터(도로망)의 질적 문제**임이 완벽하게 증명되었습니다.

- **Graph A (Business Only):** 가장 우수한 결과. 특히 Community #21(`drivers/gpu`)은 Purity 89%, Entropy 0.859로 사실상 완벽한 대륙(Continent)을 형성함. (Louvain 엔진 자체의 정합성 증명)
- **Graph B (Business + Infra):** 품질 약간 악화.
- **Graph C (Business + Arch):** 품질 크게 악화. (`checksum.h` 등 `arch/*` 레이어가 오염의 핵심 원인임이 증명됨)
- **Graph D (Full Graph):** 최악의 군집화.

### 💡 근본 원인: "RegexProvider Edge Semantics 부족"
일부 커뮤니티(Community #4, #6 등)가 `sound/soc`, `drivers/iio`, `drivers/clk` 등 이질적인 서브시스템으로 오염된 근본 원인은, 현재의 `intent_edges.json`이 **"기능적 결합(Function Call)"**과 **"단순 문자열 동시 출현(Shared Include/Macro)"**을 구분하지 못하고 모두 가중치 1(Weight 1)로 묶어버렸기 때문입니다. 

결론적으로, 현재 SYNAPSE의 엣지는 아키텍처의 의미(Semantics)를 온전히 담지 못하고 있으며, 이것이 가짜 커뮤니티를 양산한 진짜 범인입니다.

### 🚀 v0.3.35 로드맵 확정: "Semantic Weight & Edge Quality Audit"
이에 따라 v0.3.34 계열의 무리한 Drift Report 고도화를 전면 중단하고, 다음 버전(v0.3.35)에서 **"도로망 데이터의 의미론적 복원"**에 모든 화력을 집중합니다.

1. **Extractor Payload 확장:** 엣지 생성 시 단순히 `RegexProvider` 출처만 남기는 것이 아니라, 결합의 실제 증거를 포함하도록 추출기 아키텍처 확장.
   - `sharedIncludes: []`
   - `sharedMacros: []`
   - `sharedSymbols: []`
   - `functionCalls: []`
2. **Edge Quality Audit:** 페이로드 확장 후, 우수 커뮤니티(GPU)와 오염 커뮤니티(SOC+CLK)의 엣지 결합 사유를 대조하여 진짜 접착제를 검증.
3. **Semantic Weight 도입:** `Shared Include(1)`, `Shared Macro(2)`, `Shared Symbol(4)`, `Function Call(8)` 등 의미론적 가중치를 부여하여 진정한 **Weighted Architecture Graph** 구축.

이번 마일스톤(v0.3.34.11a)은 **"SYNAPSE의 대륙 생성 아키텍처 자체는 유효함을 입증하고, 향후 최우선으로 타격해야 할 핵심 병목(Extractor)을 정확히 찾아냈다"**는 점에서 역사적인 성과를 거두었습니다.
