# SYNAPSE v0.3.34.13 작업 로그 (Community Quality Metrics Engine)

## Phase 1: 마일스톤 스코프 재정의 및 철학 확립 (2026-08-03)
- **목표:** "실험체보다 실험실을 먼저 만든다"
- 특정 알고리즘을 맹신하는 도구에서 '알고리즘을 검증하는 도구'로 철학 영구 전환.
- `Metrics Layer`와 `Classifier Layer` 분리 및 `Dominance` 3축 분해.

## Phase 2: 실제 데이터 검증(Stage A.5) 및 물리 법칙 발견 (2026-08-04)
- **Degree vs PageRank 동기화:** 정규식(Regex) 기반 엣지의 방향성 부재로 둘이 유사한 Kernel Gravity(Architecture) 편향을 보임.
- **Eigenvector의 진짜 정체:** Business Layer(Driver Gravity) 측정기로서 기능함 발견.
- **Cohesion (응집도) 수식 한계:** 희소 그래프(Sparse Graph)에서 `Internal/Max Possible` 수식이 무의미함(0.00% 수렴)을 증명. "Density는 커뮤니티 품질 지표가 아닐 수 있다"는 반증 성공. Cohesion은 정식 지표에서 보류(Research) 상태로 강등.
- **마일스톤 우선순위 재조정:** Classifier 규칙 설정 전면 보류. 

## Phase 3: Dominance Vector 확립 및 검증 (Stage B.5 진행 중)
- 커뮤니티를 단일 점수로 평가하지 않고 `Size`, `Traffic(Degree)`, `Dependency(PageRank)`, `Ecosystem(Eigenvector)` 4차원 **Community Signature(지문)**로 관측하도록 구조 변경.
- "허브형", "생태계형", "혼합형" 커뮤니티 종(Species) 구분이 목적.

## Phase 4: Graph Integrity 붕괴 발견 및 Stage 우선순위 변경 (Stage B.5.1)
- **발견 사항:** Dominance 연산 결과(Traffic, Ecosystem)가 0.00%로 붕괴하는 현상을 역추적한 결과, 그래프 내부 엣지 매핑이 100% 끊어져 있음(Missing Source/Target)을 증명.
- **원인 분석:** Node ID는 `uuid`나 `절대 경로` 포맷을 따르는 반면, 엣지의 `from/to` 속성은 `fix_cluster.sh`와 같은 "Display Label"을 가리키고 있음 (Export Layer의 Node-Edge Identity 매핑 버그).
- **물리학적 의의:** Purity, Entropy, Retention은 '노드 속성' 기반이라 살아남았으나, Cohesion, Dominance 등 '연결 구조(Topology)' 기반 메트릭은 전부 0으로 수렴함. 이는 우리가 설계한 **메트릭과 물리학이 틀린 것이 아니라, 그래프 추출 장비가 고장난 것**임을 증명한 거대한 성과.
- **다음 마일스톤:** Stage B(Dominance) 연구를 전면 보류하고, 가장 기저 계층인 **Graph Integrity Recovery (Node-Edge 매핑 교정)**를 최우선 순위로 격상함.

## Phase 5: Graph Integrity 재감사 및 가설 정정 (Stage B.5.2, 2026-08-04)
- **핵심 정정:** Phase 4의 "100% 붕괴" 가설은 최신 재감사 결과 기준으로 기각.
- **재감사 결과:** `Valid Edges = 674 / 697`, `Degree Sum = 1348`, `Eigenvector Non-zero > 0` 확인.
- **해석:** 문제의 본질은 그래프 전체 붕괴가 아니라, 일부 endpoint mismatch 및 분석 컨텍스트 차이로 인한 해석 오차였음.
- **결론:** Stage B 연구 재개. 핵심 병목은 Integrity 붕괴가 아니라 **Species 해상도 부족 + 가중치 계층 부재**.

## Phase 7: Stage B.5.4-A/B 구현 - Structural Purity + Hub Gravity (2026-08-04)
- **Structural Purity 도입:**
	- 수식: `SP = internal / (internal + external)`
	- 목적: Path Purity로 설명되지 않는 Linux Infrastructure Mesh를 분리
- **Hub Gravity 도입:**
	- 수식: `HubGravity = GlobalDegree / LocalCommunityDegree`
	- 출력: `avg`, `p90`, `Top Hub Gravity Nodes`
- **Species 규칙 업데이트:**
	- `Infrastructure Mesh` 신규 분류 강화
	- `Subsystem Core` 조건 분리 (`pathPurity` + `structuralPurity`)
	- `Bridge Cluster`는 low structural purity 기반으로 판정 강화

## Phase 25: 의미 체계 재검증 - "버그"가 아니라 "정의 모호함" 문제 발견 (2026-08-04)
- **배경 판단:** Phase 23-24에서 식별한 P0/P1 버그들을 다시 역추적한 결과, 단순 렌더러 오류가 아니라 엔진 자체의 **의미 정의(Semantic Definition)** 불명확이 근본 원인임을 발견. 이는 "버그를 고쳐야 한다"의 문제가 아니라 "정의를 먼저 정해야 한다"로 문제의 성질이 변경됨.

		- Species stability: run 간 Contract/Subsystem 등 일관성 우수
		- AST verification: 9,297 resolved, 188 false positives 정밀도 높음
		- Evidence Vault 구조: Layer 1-4 증거 분리 명확
	- **렌더러(Report Generator):** 출력 계층 버그 존재 (3-4시간 수정 가능) ⚠️
		- undefined 템플릿 변수 미치환
		- Section 간 데이터 참조 불일치
	- **의미 체계(Semantic Definitions):** 아직 정의되지 않음 ❌ ← **이게 가장 큰 문제**
		- Infrastructure Mesh의 정확한 정의가 불명확
		- Species 경계의 판정 기준이 다중화됨
		- Coverage vs Confidence의 혼동

- **의미 모호함 사례 분석:**

	**[사례 1] Infrastructure Mesh 정의 불일치**

		```
		hit: 2/3 (3회 중 2회 나타남)

		```

		```
		0.80 -> count=0
		0.82 -> count=0
		0.84 -> count=0
		0.86 -> count=0
		```
	- Recommendation:
		```
		"No high-priority mesh residue after ghost-aware filtering"
		```
	- Verdict:
		```
		Mesh: ✅ Detected
		```
	- **문제:**
		- Presence Matrix는 "2/3 → Probable" 이라고 말함
		- Threshold Sweep은 "count=0 → 고신뢰 기준에서 탐지 불가" 라고 말함
		- Recommendation은 "무시해도 됨" 이라고 말함
		- Verdict는 "있음" 이라고 말함
	- **진짜 질문:** "Infrastructure Mesh는 정확히 무엇인가?"

		```
	- **현재 코드 상태:** 옵션 A, B, C가 분산되어 있고 하나의 명확한 정의로 통일되지 않음

		- False positive 188개는 절대값
		- Precision/Recall로 환산하면? (false positive rate가 몇 %인가?)
		- 2.4% 샘플이 대표성 있는가? (random? biased toward header files?)
	- **진짜 질문:** "이 2.4% 샘플 결과를 전체에 외삽할 신뢰도는?"
	- **현재 설정:** MEDIUM confidence (60-70%) 으로 보수적이지만, 그 "60-70%"의 근거가 명시적이지 않음

	- **현재 해석:** "거짓 양성 정밀 타격" 으로 보이지만, 실은 "확인 가능한 9,297개 중 정말 거짓은 188개"라는 뜻일 수도 있음
	- **필요한 것:** Precision/Recall 재계산 및 False Positive 유형별 분류

## Phase 26-Addendum: 아키텍처 재진단 - "버그 4개" vs "계층 결손 1개" (2026-08-04 최종)
- **핵심 발견:** Phase 23-24에서 진단한 4개의 독립 버그는 사실 **하나의 아키텍처 결손으로 인한 다양한 증상**이다.
- **재진단의 본질: "Semantic Layer 부재"**

	**Fact vs Interpretation의 분리:**
	```
	Raw Fact: hit=1, runCount=3
	
	해석 방법 1: "Detected" (1회라도 나오면 탐지)
	해석 방법 2: "Probable" (3회 중 1회는 노이즈?)
	해석 방법 3: "Unstable" (신뢰도 낮음)
	해석 방법 4: "Calibrated-Out" (threshold sweep에서 0)
	
	→ 4가지 해석이 동시에 보고서에 나타남
	```

	**문제: "의미 해석"을 하는 계층이 없다**
	
	```
	표준 아키텍처:
	[Fact]  (Raw JSON: hit, count, threshold_sweep, ...)
	  ↓
	[Interpretation]  (Domain Logic: "이것은 CALIBRATED_OUT")
	  ↓
	[Presentation]  (Template: "Calibrated Out이니까 이렇게 표시")
	
	현재 B5:
	[Fact]  (Raw JSON)
	  ↓
	[Presentation]  (Template가 동시에 4가지 해석 시도)
	  ↓
	모순 발생
	```

- **SSOT (Single Source of Truth)의 정의 재검토:**

	**일반적인 오류:**
	```
	"Validation JSON이 SSOT다"
	→ 아니다. Validation JSON은 Raw Facts일 뿐이다.
	```

	**올바른 이해:**
	```
	Raw Facts ≠ SSOT
	SSOT = Facts + Domain Interpretation
	
	즉:
	Validation JSON (Facts only)
	  ↓
	Semantic Contract (Facts + Interpretation)  ← 이것이 SSOT
	  ↓
	Renderer (SSOT만 읽음)
	```

- **구체적 예: Infrastructure Mesh의 4가지 해석**

	**Raw Facts:**
	```json
	{
	  "Infrastructure_Mesh": {
	    "presenceMatrix": {
	      "hit": 1,
	      "runCount": 3,
	      "status": "Probable",
	      "confidence": 0.33
	    },
	    "thresholdSweep": {
	      "0.80": 0,
	      "0.82": 0,
	      "0.84": 0,
	      "0.86": 0
	    }
	  }
	}
	```

	**Renderer의 다중 해석 (현재 구조):**
	```
	Section 2:
	  "Infrastructure Mesh: 1 community"
	  → presenceMatrix.hit 읽음
	
	Section 3:
	  "Probability: 33%"
	  → presenceMatrix.confidence 읽음
	
	Section 5:
	  "No high-priority mesh"
	  → recommendation 필드 읽음
	
	Section 6:
	  "Evidence: 0/3 runs"
	  → thresholdSweep.count 읽음
	
	Section 7:
	  "Calibrated Out"
	  → threshold_sweep all-zero 조건 읽음
	
	AI Prompt:
	  "target=7500"
	  → 독립 계산
	```

	**결과:**
	```
	보고서가 말하는 것: "Mesh는 있다", "Mesh는 없다", "Mesh는 불안정하다"
	동시에 존재.
	```

	**Semantic Contract가 있다면:**
	```typescript
	const contract = {
	  mesh: {
	    state: "CALIBRATED_OUT",  // Domain Interpretation
	    confidence: 0.33,
	    hitRate: "1/3",
	    decision: "EXCLUDE_FROM_SURGERY"
	  }
	};
	
	// 모든 섹션이 동일하게 읽음
	section2.use(contract.mesh.state);      // "CALIBRATED_OUT"
	section5.use(contract.mesh.state);      // "CALIBRATED_OUT"
	section6.use(contract.mesh.state);      // "CALIBRATED_OUT"
	section7.use(contract.mesh.state);      // "CALIBRATED_OUT"
	aiPrompt.use(contract.mesh.state);      // "CALIBRATED_OUT"
	
	// → 불가능한 모순 제거됨
	```

- **ROI 계산의 동일한 구조:**

	**현재 (Fact만 있음):**
	```
	Raw Facts:
	  edges_before = 26478
	  edges_after = 7877 (또는 7500?)
	
	Section 2:
	  projection = (26478 - 7877) / 26478 = 0.702 = 70%
	
	Section 5:
	  projection = 56% (다른 기준 사용)
	
	Section 3:
	  projection = 6000~9000
	
	AI Prompt:
	  target = 7500
	
	결과: 70%, 56%, 7500, 7877, 26478 동시 존재
	```

	**Semantic Contract (Interpretation 있음):**
	```typescript
	const contract = {
	  surgery: {
	    optionA: {
	      externalEdgesBefore: 26478,
	      externalEdgesAfter: 7877,
	      reductionPercent: 0.702,
	      confidence: "MEDIUM"
	    }
	  }
	};
	
	// 모든 섹션이 동일한 값 사용
	section2.reduction = contract.surgery.optionA.reductionPercent;   // 70.2%
	section5.reduction = contract.surgery.optionA.reductionPercent;   // 70.2%
	section3.target = contract.surgery.optionA.externalEdgesAfter;    // 7877
	aiPrompt.target = contract.surgery.optionA.externalEdgesAfter;    // 7877
	
	// → 자동으로 일관
	```

- **Semantic Layer의 진정한 역할: "Domain Interpreter"**

	**많은 사람이 착각하는 것:**
	```
	Semantic Layer = "데이터 정규화 계층"
	→ 데이터를 좀 정리해주는 것 정도로 생각
	```

	**실제:**
	```
	Semantic Layer = "도메인 언어 번역기"
	→ Raw Facts를 비즈니스 도메인 개념으로 변환
	
	예:
	  Raw Fact: "hit=1/3, threshold_sweep=[0,0,0,0]"
	  ↓ Interpretation
	  Domain Concept: "CALIBRATED_OUT"
	  ↓
	  Presentation: "Infrastructure Mesh is not reliably detected at established confidence thresholds"
	```

- **아키텍처 성숙도 전환점:**

	**현재 (v0.3.34.13):**
	```

	  - Graph Engine 정확도 높음
	  - Species Classification 안정적
	  - AST Verification 신뢰할 수 있음
	
	Semantic: ☆☆☆☆☆ (0/10)
	  - "의미 해석 계층"이 구조적으로 비어있음
	  - Renderer가 그 역할을 억지로 하고 있음
