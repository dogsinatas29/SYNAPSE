## v0.3.34.15 추가 작업 (Cluster Bounds 계산 누락 진단 및 수정)

### 날짜
- 2026-08-05 (후속 세션)

### 문제 개요
- LayoutEngine.applyLayout() 실행 후에도 `cluster.bounds`와 `worldBounds`가 전부 0으로 유지됨.
- `[ACTIVE_CLUSTERS]` / `[WORLD_BOUNDS]` 로그에서 width/height = 0 확인.
- 반면 `[BACKEND_LAYOUT] nodeCount=90 minY=0 maxY=640` 및 `node_center=(70,0)` 로그는 노드 배치가 정상적으로 이루어졌음을 보여줌.
- 즉 "노드는 배치됐는데 클러스터 바운드는 계산되지 않는" 상태.

### 진단 과정
1. `applyLayout()` 내부에 `[BOUND_BUILD]` / `[BOUND_NODE]` 로그 추가.
2. 반환 직전에 `[CLUSTER_BOUNDS_MAP]`와 `[ACTIVE_CLUSTER_BOUNDS]` 비교 로그 추가.
3. 로그 분석 결과:
   - 계산 자체는 수행됨 (`clusterBounds` Map에 정상 값 존재).
   - `activeClusters[].bounds`에도 정상적으로 반영됨.
   - DataPipeline 및 Reporter 단계에서도 일관된 non-zero bounds 확인.

### Root Cause
- v0.3.34 minimal fallback LayoutEngine이 cluster bounds 계산 로직을 전혀 포함하지 않음.
- `return { clusterBounds: new Map(), worldBounds: zero, ... }` 상태로 즉시 반환.
- Cluster 객체와 layoutResult 간 bounds 동기화 경로가 부재.

### 수정 내용
- `src/core/LayoutEngine.ts` 수정:
  - 노드 배치 루프 직후 cluster bounds 계산 블록 추가.
  - 각 클러스터에 대해 min/max 계산 → `BoundingBox` 생성.
  - 계산 결과를 `clusterBounds` Map과 `activeClusters[i].bounds` 양쪽에 동시 기록.
  - `worldBounds`도 실제 노드 분포에 기반해 계산.
- 추가된 진단 로그:
  - `[BOUND_BUILD]`, `[BOUND_NODE]`
  - `[CLUSTER_BOUNDS_MAP]`
  - `[ACTIVE_CLUSTER_BOUNDS]`

### 검증 결과
- `[CLUSTER_BOUNDS_MAP]`와 `[ACTIVE_CLUSTER_BOUNDS]`가 동일한 정상 값으로 일치.
- 최종 렌더 단계에서 `cluster_count=2`, `world_width=1260`, `world_height=640` 정상 출력.
- Determinism 검증: **PASS** (Semantic Hash 일치).
- Reporter의 `[LAYOUT] cluster_count` 및 bounds 관련 진단도 이제 정확한 값을 보고함.

### 영향
- Cluster bounds 계산이 LayoutEngine의 필수 단계로 자리 잡음.
- 이후 Renderer / Reporter가 신뢰할 수 있는 bounds 정보를 받을 수 있게 됨.
- v0.3.34.x deterministic consistency 목표에 한 걸음 더 가까워짐.
  - diff report 해석
  - 향후 Semantic Numeric Field 확장 예정(필드명 + annotation 병행)

## 2026-08-05 Cluster Promotion / Metadata Desync 분석 (Linux kernel 샘플)

### 실행 명령
```bash
npx ts-node -e '
import { dataPipeline } from "./src/core/DataPipeline";
import { ProjectMetadata } from "./src/core/ProjectMetadata";
import * as fs from "fs";

const root = "/home/dogsinatas/다운로드/linux-7.2-rc3";
ProjectMetadata.getInstance().initialize(root, "linux-7.2-rc3");

const files = [
  root + "/kernel/sched/core.c",
  root + "/kernel/sched/fair.c"
];

dataPipeline.processFiles(files, root).then(r => {
  fs.writeFileSync("/tmp/graph.json", JSON.stringify(r, null, 2));
  console.log("[GRAPH] 생성 완료:", r.nodes.length, "nodes,", r.clusters.length, "clusters");
});
'
```

### 핵심 로그 증거

1. `[CLUSTER_INVARIANT_FAIL]` 다수 발생
   - `nodeCount= undefined` 상태로 Promotion 후보 평가
   - `folder__home_dogsinatas______linux_7_2_rc3_kernel_sched nodeCount= undefined actual= 2`

2. Render 단계 불일치
   ```
   [RENDER DIAGNOSTIC] CLUSTER DUMP
   CLUSTER id=cluster_ghosts type=system nodes=0 (computed count=88)
   ```
   → `cluster.nodes` 메타데이터는 0, 실제 `node.cluster_id` 기준 집계는 88

3. Summary vs Render 클러스터 수 차이
   - `[SUMMARY_SOURCE] clusterTraffic.size= 10`
   - `[RENDER_SOURCE] clusters.length= 2`

### 분석 결론

**P0 우선순위: Cluster Metadata ↔ Node Cluster Assignment 불일치**

- 현재 구조는 `cluster.nodes` (메타데이터)와 `node.cluster_id` (노드 측 진실)가 동시에 존재.
- Promotion/Collapse 후 `node.cluster_id`만 변경되고 `cluster.nodes` / `cluster.nodeCount`는 갱신되지 않음.
- 이로 인해 Summary, Render, Heatmap, Hub Ranking이 서로 다른 소스를 읽는 현상 발생.

**Promotion Transaction 문제는 2차 원인**

- `[PROMOTION_REMOVED]` 이후 클러스터가 Summary에 재등장하는 증거는 이번 로그에서 확인되지 않음.
- 오히려 "Registry View (10개) vs Visible View (2개)" 차이가 더 명확함.

### v0.3.34 권장 수정 우선순위

1. **P0** — Cluster Single Source of Truth 확립
   - `cluster.nodes` / `nodeCount` 제거 또는 계산 전용으로 변경
   - 필요 시 `groupBy(node.cluster_id)`로 실시간 집계

2. **P1** — Promotion 종료 후 `validateClusterLifecycle()` 삽입
   ```ts
   for (const c of clusters) {
     const actual = nodes.filter(n => n.cluster_id === c.id).length;
     if (actual !== (c.nodes?.length || 0)) {
       console.error(`[CLUSTER_DESYNC] ${c.id}`);
     }
   }
   ```

3. **P2** — Promotion Delete 직후 `has` 검사 추가
   ```ts
   clusters.splice(i, 1);
   const stillExists = clusters.some(cc => cc.id === c.id);
   console.log('[PROMOTION_POST_DELETE_CHECK]', c.id, 'stillExists=', stillExists);
   ```

4. Summary / Render 양쪽에 `clusterMap.size` / `clusters.length` 동시 로깅 강화

### 영향 예상
- `cluster_ghosts nodes=0 (computed=88)` 패턴이 Heatmap, Hub Ranking, Layout 이상의 상당 부분을 설명함.
- 위 P0 해결 시 Promotion Atomicity 문제도 자연스럽게 완화될 가능성 높음.

## v0.3.34.15 후속 작업 (External Layer Compression 1차 적용)

### 날짜
- 2026-08-06

### 문제 개요
- 거대한 C/C++ 프로젝트(예: Linux 커널) 분석 시, 150개가 넘는 외부 종속성(Ghost Nodes) 헤더 파일들이 개별 노드로 캔버스에 렌더링되어 극심한 레이아웃 폭발(Layout Explosion) 및 렌더링 부하 발생.
- `linux` 등 특정 도메인에 90% 이상 쏠리는 현상이 확인되어 단순 도메인 그룹화만으로는 해결 불가 판정.

### 수정 내용
- `src/core/GhostExpander.ts` 수정:
  - 외부 종속성 고스트 노드 생성 시 임시로 모든 노드가 단일 부모 클러스터인 `cluster_ghosts` (External Dependencies)로 편입되도록 로직 강제. (`getGhostClusterId` 고정)
  - `addGhostCluster` 호출 시 해당 클러스터에 `collapsed: true` 속성을 기본 부여하여(Collapse-by-default) 렌더러로 전달.

### 검증 결과
- **Ghost Compression**: 논리적인 압축은 현재 1단계(`cluster_ghosts` 단일화)로 통합 성공.
- **Layout = Reality 규칙 확인**: `LayoutEngine.ts`는 룰에 의거하여 `collapsed: true`를 무시하고 150개 노드의 실질적인 Bounds(`1880 x 1040`)를 그대로 유지함을 확인.
- **발견된 한계**: UI 파이프라인에서 카메라(Bounds)를 실제 화면상의 렌더링 박스 크기가 아닌, 백엔드의 거대한 실물 Bounds 기준으로 잡아버려 "거대한 빈 공터"가 캔버스에 나타나는 현상 진단.

### 다음 마일스톤 (v0.3.34.16 / v0.3.35)
- Layout 엔진은 Reality를 유지하되 프론트엔드의 Camera Fit 로직을 시각적 바운드(Visible Bounds) 기준으로 변경하는 **Visible Bounds Engine (B+ 정책)** 설계 승인 완료.
