- **원인 1 (Collapse 상태 초기화 실패)**: 백엔드 `ClusterBuilder.ts`와 `GraphModel.ts`에 하드코딩된 최상위 `cluster_ghosts` 초기 선언부에 `collapsed: true` 속성이 누락되어 있었음. 이로 인해 프론트엔드가 초기화될 때 `!c.collapsed` 조건에 걸려 `cluster_ghosts`를 무조건 `expandedClusters`에 추가해버림.

- **해결 방안**:
  1. `ClusterBuilder.ts`, `GraphModel.ts`에 `cluster_ghosts` 정의부에 `collapsed: true` 강제 주입.
  2. `canvas-engine.js`의 `computeVisibleBounds` 함수 내에 **Telescope LOD(System B) Hierarchy Check** 로직을 도입. 현재 순회 중인 클러스터의 `parentNode`가 접혀있다면(`!expandedClusters.has(parentNode.id)`), 해당 자식 클러스터는 Bounds 계산에서 완전히 배제(`continue`)하도록 수정.
- (완료) `canvas-engine.js`에 `computeVisibleBounds()` 함수 추가 및 `fitView` 로직 변경.
  - `computeWorldBounds()` 유지 (Layout=Reality 보존).
  - UI 상수에 맞춘 `COLLAPSED_CLUSTER_WIDTH = 250`, `COLLAPSED_CLUSTER_HEIGHT = 80` 도입.
- (완료) `GhostExpander.ts`에서 도메인 하위 클러스터 할당 로직 구현 (v0.3.35).

- (완료) `ui/canvas-engine.js`의 `requestContextData` 내부 Virtual Debug 추출 로직 수정.
  - 기존의 단편적인 `c.collapsed !== true` (System A) 검색 로직을 버리고, 렌더링 측면의 **Telescope LOD (System B)** 규칙(`engine.expandedClusters` 및 부모 상태 검사)을 엄격히 적용하여 백엔드로 전달될 클러스터 범위 필터링 동기화.

- (완료) `VirtualDebugger.ts` 및 `CanvasPanel.ts`를 리팩토링하여 `Architecture Surgery Pipeline` 직접 연결 (v0.3.34.17)

- (완료) `filterSnapshot.ts` 리팩토링 및 "Roots Only / Cluster State Mismatch" 버그 완벽 수정 (v0.3.34.18)
  - **문제**: 캔버스에서 "Roots Only" 버튼 클릭 시 수천 개의 폴더가 닫히지 않고 오직 10개의 폴더만 접히는 `collapsedClusters: 10` 버그 발생. 
  - **원인**: 백엔드의 `filterSnapshot.ts`가 중간 단계의 빈 폴더(Intermediate empty folders)들을 스냅샷에서 필터링하여 완전히 제거해버림. 이로 인해 리프 폴더(Leaf folders)들이 부모를 잃어버렸고, 프론트엔드의 `buildHierarchy` 복구 로직이 부모를 찾다 실패하여 리프 폴더들의 `parent_id`를 `null`로 할당함. 그 결과 2900개가 넘는 리프 폴더들이 "최상위 루트(True Root)"로 인식되어 Roots Only 상태에서 닫히지 않음.
  - **해결**: `filterSnapshot.ts`에서 하위 노드가 존재하는 클러스터의 모든 조상(Ancestor) 폴더들을 역추적하여 보존(Keep)하도록 O(N) 알고리즘 재설계. 이로써 부모-자식 관계가 단절되지 않으며 프론트엔드에서 수천 개의 폴더를 올바른 레벨(Depth)로 인식하여 "Roots Only" 모드가 정상 작동함.

- (완료) `VirtualDebugger` CLI 호출 붕괴 원인 분석 및 `ValidationEngine` 리팩토링 결정 (v0.3.34.19)
  - **문제**: VSIX 환경에서 `VirtualDebugger.ts`가 `child_process.execSync('npx ts-node ...')`를 호출할 때 `TypeError: Cannot read properties of undefined (reading 'fileExists')` 에러가 발생하며 파이프라인이 붕괴됨.
  - **원인**: VSIX 패키징(`vsce package`) 과정에서 `package.json`의 `devDependencies`에 위치한 `typescript`와 `ts-node`가 제거(Pruning)됨. 따라서 런타임에 Extension Host가 `ts-node`를 실행하려 할 때 TypeScript 파서를 찾지 못해 죽어버리는 근본적인 아키텍처 결함 확인.
  - **해결 결정**: `ts-node` CLI 호출 방식과 `temp json` 파일 덤프 방식을 전면 폐기하고, 4단계 리팩토링(실험실의 시냅스 완전 이식)을 진행하기로 확정. `b5_validation_layer.ts`를 인메모리 함수형인 `ValidationEngine`으로 분리하여 직접 `import` 및 호출하는 구조로 전환 예정.

## ⚠️ 진실 공급원(Source of Truth) 전수 검사 및 4대 치명적 결함 수정 (2026-08-07)
- **증상**: 캔버스의 노드 계층 구조(Hierarchy)가 리로드나 부트스트랩을 거칠 때마다 무작위로 평탄화(Flat)되거나 대륙 배치가 흔들리며, ASR 진단 보고서의 대상(Subject)이 널뛰는 현상 지속. "상태 스냅샷, 클러스터 구조, 렌더러가 서로 복합적으로 오염되고 있다"는 사용자 가설 입증.
- **원인 및 해결 (총 4곳의 비결정적 상태 오염원 차단)**:
  1. **`CanvasPanel.ts` (계층 증발)**: `handleSaveState`에서 UI 스냅샷을 디스크로 저장할 때 `parent_id`와 `children` 필드를 누락하여 모든 클러스터가 루트로 승격되는 버그. -> 방어적 복사 및 필드 보존 패치 완료.
  2. **`VirtualDebugger.ts` (원본 훼손)**: ASR 대상 추출을 위해 `targetNodes`를 생성하는 과정에서, 깊은 복사(Deep Copy)를 수행하기 전에 원본 글로벌 `state.nodes` 객체의 `cluster_id`를 직접 조작(Mutate)하여 캔버스의 진실 공급원을 영구 파괴하는 치명적 버그. -> 복제본 생성 후 필터링/수정하도록 패치 완료.
  3. **`CommunityDetector.ts` (무작위 난수 셔플링)**: 실험실(Laboratory) AEL 프레임워크 도입 시, Louvain 알고리즘 내부에 노드 셔플링을 위해 `Math.random()`을 사용하여 부트스트랩마다 커뮤니티(대륙) 형태가 100% 바뀌는 비결정적 문제. -> Pass/Iteration 기반 LCG 시드 난수로 교체하여 100% 결정론 확보.
  4. **`BootstrapEngine.ts` (파일 순서 비결정성)**: `getDiscoverableFiles`에서 `fs.readdirSync()`가 OS 환경에 따라 파일 스캔 순서를 무작위로 반환하여 이후 모든 노드/엣지의 삽입 순서가 꼬이는 나비효과. -> `.sort()`를 명시적으로 호출하여 스캔 순서 고정 완료.
  5. **`BootstrapEngine.ts` (과거 망령 피드백 루프)**: 스캔된 자동 생성 노드가 과거 스냅샷(`project_state.json`)에 남아있던 `cluster_id`나 `community_label`을 병합하여 진실이 과거에 의해 오염되는 버그. -> 수동 노드(Manual Nodes)에만 예외를 허용하고 자동 노드는 병합을 완벽 차단.

## 🕵️ 수 초 뒤 클러스터 가시성 폭발 사건 (The Orient Express CT Scan) - 2026-08-07
- **증상**: 부트스트랩 직후 `Roots Only` 버튼을 클릭하여 화면을 쾌적하게(가시 클러스터 620개) 정리해두어도, 사용자가 아무 조작도 하지 않았는데 약 6~10초 뒤 갑자기 전체 노드와 클러스터(2919개)가 풀 전개되며 화면이 폭발함.
- **CT 스캔(정밀 진단 프로브) 주입 및 판독**:
  - `canvas-engine.js`의 핵심 진입점(`loadProjectState`, `rebuildGraphData`, `_computeResolverVisibleIds`) 상단에 호출 스택을 남기는 프로브 주입.
  - **판독 결과 1 (백엔드의 묻지마 폭격)**: `t=6.3s` 경, 백엔드(`CanvasPanel.ts`)가 비동기 작업을 마친 뒤 프론트엔드로 `sendProjectState(isAuthoritative: true)` IPC 메시지를 전송하여 강제 리로드를 트리거함.
  - **판독 결과 2 (프론트엔드의 비결정론적 초기화)**: `loadProjectState` 내부에서 백엔드가 보내준 `projectState.clusters`를 매핑할 때, `collapsed` 값이 없으면 무조건 `false`(펼침)로 덮어쓰는 치명적 하드코딩 발견 (`collapsed: c.collapsed === true ? true : false`). 
  - 이로 인해 이후에 존재하는 "부모가 없으면 Depth 1로 간주하여 접기(`if (cluster.collapsed === undefined)`)" 로직이 영구적으로 무력화되며, 2919개 클러스터 전체가 강제로 펼쳐짐.
- **원인 해결**:
  - 프론트엔드 캐싱 로직 오류 및 초기화 하드코딩 완전 제거 완료.

## 🚀 O(N) 순회 병목 제거 및 RBush Spatial Index 완전 복구 (2026-08-08)
- **증상 1 (캔버스 프리징 및 CPU 폭주)**: 렌더 루프(`render-frame`) 진입 후 69990개 노드와 385662개 엣지를 그릴 때, 프레임이 500ms~1000ms까지 튀거나 DevTools가 완전히 뻗어버림.
- **원인 1 (클러스터 노드 캐시 붕괴)**: 2919개의 클러스터를 RBush에 인덱싱하기 위해 `buildSpatialIndex`가 호출되었으나, `this._clusterNodesCache`가 텅 빈 상태로 통과되어 모든 클러스터의 내부 노드 수가 0으로 인식됨. 그 결과 2919개 전체 클러스터의 `bounds`가 `null`로 떨어져 RBush 트리에 단 1개의 클러스터도 삽입(Insert)되지 않았음 (O(N) 강제 Fallback 가동).
- **해결 1 (캐시 실시간 갱신 삽입)**: `buildSpatialIndex` 초입에 `if (typeof this._buildClusterIndices === 'function') this._buildClusterIndices();` 호출을 강제로 주입하여 클러스터 바운딩 박스를 계산하기 직전에 노드 매핑 캐시가 항상 100% 최신 상태로 채워지도록 보장.
- **결과 1**: `RBUSH_CLUSTER_COUNT`가 0에서 2918개로 완벽히 복원되며, O(1) 공간 컬링 정상 작동 완료.
- **원인 2 (DevTools 렌더러 Crash)**: 캔버스 렌더 속도(`drawClusters 5ms`) 자체는 완벽하게 빨랐으나, 60fps 렌더 루프 내부에서 RBush 상태나 캐시 길이를 덤프하는 `console.log`(`[RBUSH_CLUSTER_COUNT]`, `[VISIBLE_GRAPH_SOURCE]`, `[NULL_BOUNDS_ACTIVITY]`)가 프레임당 5~6개씩 스팸으로 출력되며 브라우저 메모리를 가득 채우고 DevTools를 멈추게 함.
- **해결 2 (Log Spam 완벽 제거)**: 렌더 루프 내부의 디버깅성 `console.log` 구문과 잘못된 블록 주석 처리(`/*`)로 인해 발생한 Syntax Error(`[ENGINE_MISSING]`)를 완벽히 수정 및 주석 처리 완료. `[NULL_CLUSTER]` 에러만 1회 출력되도록 제한.
- **미해결 1건 특이사항 확인**: 2919개 중 정확히 단 1개의 클러스터(`folder_report`, `📂 report`)만이 `[NULL_CLUSTER]`로 떨어지는 현상 확인. (루프 폭주 등 시스템적 장애는 해결되었으므로 이 1건의 특수 클러스터 문제만 확인하면 렌더링 파트 완전 정상화).

## 🔍 [folder_report] 유령 클러스터(Node 0개) 미스터리 추적 (2026-08-08)
- **증상**: `computeClusterBounds`에서 `folder_report` 클러스터가 지속적으로 `null` 바운즈를 반환하며 `[NULL_CLUSTER]` 에러를 유발. 확인 결과 해당 클러스터의 귀속 노드(`directNodes`)가 **0개**인 상태.
- **원인 분석**:
  1. `DirectoryTreeBuilder.ts`의 `isDoc()` 함수가 `.md` 확장자와 `report` 단어를 필터링하지만, `/home/.../linux-7.2-rc3/report` 경로 내부의 191MB 짜리 `temp_target_state.json` 파일은 필터를 우회하여 트리 구조(DirectoryTree)에 등록됨.
  2. 트리에 등록된 경로를 기반으로 백엔드 `ClusterBuilder.ts`가 `folder_report` 클러스터를 합법적으로 생성함.
  3. 반면 `NodeBuilder.ts`에서 생성된 해당 파일의 노드가 `FileScanner.ts`의 용량 제한(191MB) 혹은 중간 필터링 로직에 의해 캔버스로 전송되지 않아, 결과적으로 "클러스터는 존재하나 노드는 증발한" 비대칭 상태가 렌더러로 주입됨.
- **조치 사항 (정밀 프로브 주입)**:
  - `ClusterBuilder.ts`: `folder_report`가 생성되는 시점을 정확히 포착하는 `[CREATE_CLUSTER]` 프로브 투입.
  - `NodeBuilder.ts`: `report` 폴더 내부의 파일들이 노드로 매핑되는지 감시하는 `[REPORT_FILES]` 프로브 투입.
  - 이를 통해 "클러스터 생성기 문제인지, 파일 스캐너 문제인지, NodeBuilder 문제인지, GhostRule 문제인지" 단번의 로그 판독으로 확정 지을 예정.
