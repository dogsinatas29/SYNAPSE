# 🚀 Milestone v0.3.34.18 - Data Reliability & Architect Workflow (ASR 고도화)

## 📅 작업 정보
- **상태:** 🏗️ Planned
- **관련 마일스톤:** v0.3.34.17
- **목표:** ASR 3.0의 분석 정확도(Ghost/Impact)를 교정하고, "전체 프로젝트 스캔" 뿐만 아니라 "특정 클러스터 정밀 스캔" 환경에서 실무 아키텍트의 '작업 지시서(Actionable Guide)' 역할을 수행한다.

## 🧠 상세 설계 및 로직 (아키텍처 스캔 리포트 고도화 철학)

### 1. 전역 스캔(Global) vs 국소 스캔(Local)
- **Global Scan**: "이 프로젝트는 건강한가?" (전체 프로젝트 통계)
- **Local Scan**: "특정 클러스터(예: `drivers/gpu`)는 전체 안에서 어떤 역할인가?" (클러스터 단위 정밀 분석)
- 아키텍트의 실제 워크플로우(전체 감지 → 수상한 영역 선택 → 집중 분석 → 수술 계획)를 완벽히 지원하기 위해 국소 스캔 리포트 기능을 강화.

### 2. 신뢰성(Reliability)의 양대 축
- **설명 가능성 (Explainability & Traceability)**: 
  - 점수(Entropy 68점)만 뱉는 블랙박스 타파.
  - "왜 68점인가?" → "Boundary Ratio가 3.47이라서" → "3.47은 어디서 왔나?" → "drivers에서 include로 88196개의 엣지가 있어서" 로 이어지는 **Why Chain (Traceability)** 보장.
- **오탐(False Positive) 오염 방지**:
  - 데이터가 틀리면 진단 자체가 붕괴됨.
  - 정적 파서 착시(예: `#ifdef CONFIG_*` 등 런타임 무관 엣지)를 방지하기 위해 **Ghost Breakdown** (Generated Header, Conditional Compile, Platform Specific 등)을 정교화.

## 🛠️ 기술적 변경 사항 (우선순위 및 다음 패치 목표)

### P0 (시스템 생존 - 최우선 해결 과제)
- **Dummy Data Purge (가짜 데이터 제거)**: `ValidationReportBuilder.ts`에 잔존하는 하드코딩 템플릿(Cost Projection, Entropy 0.68, False Positive 12.5%, Impact File 복붙 평가 등) 전면 제거. 계산 불가 시 `N/A`, 실패 시 `UNKNOWN` 반환을 원칙으로 하여 ASR 리포트의 신뢰도 붕괴 방어.
- **Selected Cluster Scope 검증 (Analysis Scope Validation)**: 전역 분석과 선택 분석 시 보고서 생성 단계로 넘어가는 파이프라인 무결성 점검 (현재 Scope 추출 자체는 362->10->7로 정상 작동 확인됨).

### P1 (사용 가능 상태 - 워크플로우 뚫기)
- **Cluster Meta Edge 렌더링 회귀 버그 (UI/Rendering)**: 초거대 모노레포(VSCode, Linux Kernel 등)에서 `EDGE VISIBILITY`를 `CLUSTER (Meta Edges)`로 설정 시 카메라 Zoom에 관계없이 엣지가 증발하는 버그 수정. 아키텍트의 "관심 영역 식별" 단계를 가로막는 요소.

### P2 (데이터 신뢰성 - Data Reliability)
- **Ghost Breakdown**: Ghost 엣지 분류 체계 정교화 (`isGhost: true, ghostType: "Conditional Compile"` 등 메타데이터 부여) 및 정적 파서의 False Positive 필터링. 
- **Evidence Location**: 수술 부위를 정확히 지목하기 위해 `파일+라인+심볼` 3종 세트(`GraphModel.ts:812 createDependencyEdge()`) 맵핑.
- **Explainability / Why Chain**: 점수 산출 공식을 투명하게 렌더링하여 "왜 이런 점수가 나왔는가?"에 대한 원시 데이터 → 중간 계산 → 최종 점수 추적(Traceability) 기능 제공.

### P3 (아키텍트 기능 - Architect Workflow)
- **Trend Analysis**: `synapse_history.json`을 활용하여 과거 대비 지표 변화량(Boundary Ratio, Ghost 증감 등) 추적.
- **Safe Entry Points**: 신규 인력 온보딩을 위해 `EntryScore`를 산출하여 가장 안전한 진입점(Safest 10) 제공.
- **Architectural Entry Flow**: 단순 중요도가 아닌 **실행 흐름(Execution Flow)** 기준 추천 리딩 순서 자동 생성.

### P4 (고급 기능 - Advanced)
*데이터 신뢰성이 완벽히 확보된 이후에만 진행 가능. 현재는 Impact Score 등이 흔들리고 있으므로 후순위로 미룸.*
- **Refactor ROI**: `ImpactScore / Complexity(LOC)` 공식을 통한 가성비 높은 리팩토링 우선순위 제시. (당장 구현 시 잘못된 Impact가 증폭될 위험 있음)
- **Cut Candidates**: **Bridge Edge / Articulation Point** 개념을 도입한 수치화.
- **Change Amplification**: 특정 파일 변경 시 파급되는 수정 범위 산출 (Blast Radius 유사).
- **Performance Layer**: CPU, Memory, Hot Path 등 런타임 성능 지표 스캔.

## ⚠️ 예외 처리 및 주의 사항
- "데이터가 틀린데 설명만 잘하면 그럴듯하게 거짓말하는 시스템이 된다."
- 최우선 순위는 무조건 **데이터의 정확도(False Positive 제거)**이며, 그 다음이 설명 가능성, 마지막이 고급 분석(ROI, Cut Candidate 등)이다.
- 클러스터 선택 분석 시, 전역 그래프와 로컬 서브그래프의 인덱스가 충돌하지 않도록- **Meta Edge LOD 픽스:** 클러스터 병합(Collapse) 시 내부 노드들이 가시성(Visibility)에서 컷아웃되면서 메타 엣지 집계에서 누락되는 현상 해결. (`this._clusterEdgeMap` 전체 순회로 변경하여, 노드가 숨겨져도 리프 클러스터가 활성 상태면 트래픽이 정상적으로 집계됨)
- **Fit View B+ Policy 파기:** Fit View 연산 시 접힌 클러스터가 시각적 위치(`cluster.position`)를 참조하여 원점(0,0)으로 바운딩 박스를 왜곡시키던 B+ Policy 제거. 렌더러와 동일하게 실제 공간(Reality Bounds)을 참조하도록 수정하여 거대 줌 이탈(Jumping) 방지.

## 📝 Post-Work Log (작업 후 기록) - *작업 중 추가된 요소 및 릴리즈 노트 기반의 최종 결과물 기록*지시서(Actionable Guide)' 수준으로 진단력을 강화한다. 과거 기획된 주관적 Diagnosis Reasoner(ADR) 대신 팩트 기반의 아키텍트 워크플로우를 최우선으로 도입한다.

## 🧠 상세 설계 및 로직 (피드백 반영)

### 1. 거장들의 시각 (Linus Torvalds & John Carmack)
* **Linus Torvalds 관점 (신뢰성 & 구조)**: "이 숫자가 어디서 왔는가?", "재현 가능한가?", "왜 점수가 87인가?"를 집요하게 묻는다.
  * *대응책:* Impact Score 산출 공식(Score Formula)을 투명하게 공개하고, `Fan-Out`, `Dependency Depth`, `Propagation Path` 등의 세부 근거(Why Chain)를 통해 점수의 논리적 기틀을 마련한다.
* **John Carmack 관점 (성능 & 병목)**: "가장 비싼 함수는?", "어디가 병목인가?", "왜 느린가?"를 묻는다.
  * *대응책:* ASR은 기본적으로 '구조(Architecture) 스캔'이지만, 추후 Performance Layer(Top Hotspots, Top Allocation Nodes, Top Dependency Hubs) 확장이 고려되어야 한다 (장기 과제).

### 2. 실무 아키텍트의 시각 (온보딩 및 리팩토링)
실무 아키텍트는 "이 분석이 맞나?"를 넘어 **"그래서 월요일에 어디부터 손대야 하는가?"**를 묻는다.
현재 ASR 3.0의 답변 가능성은 다음과 같다:
- **온보딩할 때 어디부터 봐야 하나 (70%)**: Impact Files로 '중심부'는 알 수 있으나 '진입점(Entry Points)' 및 '실행 흐름(Execution Flow)' 설명이 부족.
- **어디가 위험한가 (90%)**: External Edges, Blast Radius를 통해 충분히 위험 구역 식별 가능.
- **어디에서 진입해야 안전한가 (30%)**: 최악(Worst 10)은 보여주지만, 안전지대(Safest 10, Fan-In 1 / Fan-Out 0)는 안 보여줌.
- **어디를 잘라야 하는가 (60%)**: 이상 결합(Cluster 간 External Edges)은 보이나, 구체적인 `Cut Candidates(단절 후보군)` 제시는 부족.
- **어디부터 리팩토링해야 하는가 (50%)**: 위험도(Risk)는 제공하나 변경비용(Complexity)을 나눈 `Refactor ROI(투자 대비 효율)` 지표가 부재.

## 🛠️ 기술적 변경 사항 (우선순위 및 다음 패치 목표)

현업 아키텍트의 실무적 요구사항을 반영하여 ASR 3.0의 다음 목표를 S~B 등급으로 분류하여 추진한다.

### S급 (최우선 과제 - 데이터 신뢰성 확보)
0. **Cluster Meta Edge 렌더링 누락 버그 픽스 (Hotfix)**: ✅ **완료** (WebGL 가속 모드 동작 시 Canvas 2D 호출이 Bypass되던 원인을 파악하여, 백그라운드 2D 오버레이에 명시적으로 렌더링 처리)
1. **Ghost Breakdown (고스트 세부 분류)**: `AGGREGATE` 하드코딩 등 후처리 의존을 제거. `Scanner` 단에서 엣지 생성 시점부터 `isGhost: true, ghostType: "AndroidSDK", source: "android.app.Activity"` 메타데이터를 정식 부여하여 데이터 계층을 근본적으로 정비.
2. **Evidence Location (증거 위치 맵핑)**: "어디가 문제인가?"를 넘어 "어디를 열어야 하는가?"에 답하기 위해, 단순 파일명(`GraphModel.ts`)이 아닌 **파일+라인+심볼 3종 세트**(`GraphModel.ts:812 createDependencyEdge()`)를 제공하여 해상도 극대화.
3. **Trend Analysis (추세선 분석)**: `synapse_history.json`을 기반으로 과거 대비 지표 변화량(예: Boundary Ratio 10%→15%→20% 악화 경고, Ghost 3000→800→120 개선 확인)을 추적하여 프로젝트의 '방향성'을 CTO 및 아키텍트에게 제공.

### A급 (핵심 가치 확보 - 실무 작업 가이드)
4. **Safe Entry Points (안전 진입점)**: 신규 인력이 가장 중요한(위험한) 파일부터 만지다 터지는 참사를 막기 위해 도입. 단순 Fan-In/Out 고정값이 아닌 `EntryScore = BoundaryCrossing + FanIn + FanOut + LOC` 조합 공식을 통해 지나치게 작은 유틸 파일만 뽑히는 문제를 방지.
5. **Refactor ROI (리팩토링 투자 대비 효율)**: 아키텍트의 수술 순서 결정을 위해 `Refactor ROI = ImpactScore / Complexity(LOC)` 공식을 도입. (향후 Complexity는 `LOC + Dependency Count + Cyclomatic Complexity`로 고도화 예정)
6. **Change Amplification (변경 증폭도)**: "이 파일 하나 수정하면 몇 개 파일이 터지나?"에 답하는 지표. `Blast Radius`와 유사하나 파급 경로의 크기에 집중하여 리팩토링 우선순위 결정에 강력한 데이터 제공. (장기 과제에서 A급으로 승격)
7. **Architectural Entry Flow (구조적 진입 흐름)**: 온보딩 전용 기능. 단순 중요도가 아닌 **실행 흐름(Execution Flow)**을 기준으로 "어디서 시작해서 어디로 이동해야 하는가"에 대한 추천 리딩 순서(`extension.ts → DataPipeline.ts → GraphModel.ts`)를 자동 생성.

### B급 (고도화 과제 - 구조 수술 도구)
8. **Cut Candidates (단절 후보군 강화)**: 단순 엣지 카운트가 아닌, 그래프 이론의 **Bridge Edge** 및 **Articulation Point(단절점)** 개념을 도입. "GraphModel.ts를 분리하면 Rendering Layer와 Analysis Layer가 단절되며 External Edge가 43% 감소함" 수준의 구체적 분리 결과까지 예측.

### 향후 과제 (장기 로드맵)
9. **Performance Layer**: CPU, Memory, Hot Path 등 존 카멕 스타일의 성능 지표 스캔 (현재는 구조 스캔에 집중).

## ⚠️ 예외 처리 및 주의 사항
- ASR은 여전히 진단(Diagnosis)보다 사실 관측(Scan)을 우선한다.
- 아키텍트 가이드(작업 지시서) 기능을 강화하더라도, AI 환각이나 무리한 추론은 철저히 배제하고 철저히 결합도 수학에 기반해 추출한다.
- 과거 기획되었던 `Diagnosis Reasoner` (주관적 진단기) 도입은 당분간 완전히 배제한다.
