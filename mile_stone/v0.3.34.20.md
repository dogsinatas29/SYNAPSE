````markdown
```text

    ↓

```

```text

```

```text

```text

enum 참조

# 🐧 Linux Kernel Analysis Limitations

AST는 Linux Kernel 분석 품질을 크게 향상시킬 수 있지만 모든 문제를 해결하지는 못한다.

```text

Field Access
Function Call

```

구분 가능

---

```

현재:

```text

위험 파일
```

```text

## Level 2 - Symbol Awareness

예:

```c
schedule();
```

현재:

```text
schedule 사용

```

```text

```

하지만

```text

```

까지 연결하지는 못한다.

이는 미래의

```text

```

## Level 3 - Build Awareness

Linux Kernel의 가장 어려운 문제:

```c

```

정규식:

```text

→ 의존성 생성
```

실제:

```text
CONFIG_SMP=n
```

↓

```text
의존성 없음
```

---

또는:

```make
obj-$(CONFIG_EXT4_FS) += ext4/
```

```text

 ↓
Makefile
 ↓

 ↓

```

현재 SYNAPSE:

```text
Source Code
 ↓
#include
```

만 해석

# 🔬 Why AST Is Not Enough For Linux Kernel

AST는:

```text
Type Reference
Interface
Struct Usage
Function Call
Macro Usage
```

를 구분할 수 있다.

그러나 Linux Kernel의 실제 의존성은 코드보다 Build System에 의해 결정된다.

예:

```c
#ifdef CONFIG_SMP
#include <linux/smp.h>
#endif
```

AST는:

```text
linux/smp.h
```

의존성을 인식한다.

하지만:

```text
CONFIG_SMP=n
```

이면

실제 빌드에는 존재하지 않는다.

이 정보는 AST만으로는 획득할 수 없다.

따라서 Linux Kernel 분석 정확도의 최종 상한은:

```text
Kconfig
Makefile
Conditional Compilation
```

해석 능력에 의해 결정된다.
````
