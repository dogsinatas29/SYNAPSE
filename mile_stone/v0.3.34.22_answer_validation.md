# v0.3.34.22 Answer Validation Criteria

This document defines the ultimate pass/fail criteria for SYNAPSE as an **Architect Answer Engine**. A technical pass (emitting a `Finding`) is irrelevant if the final `Answer` fails these human-centric validations.

## Core Validation Philosophy
1. **Actionability:** Can a human architect make a decision based on this answer?
2. **Explainability:** Does the answer defend itself with traceable, structural evidence?
3. **Accuracy:** Does the answer align with the actual design intent of the system?

## The "Architect's Approval" Tests

### Q1: Entry Points Test
- **Test:** Give the generated Entry Point list to a new developer.
- **Pass:** The developer can trace the core execution flow of the system starting *only* from those files.
- **Fail:** The developer hits a dead end, or the entry point is a utility file (e.g., `StringUtils.ts`) that has no control authority.

### Q2: Authority Test
- **Test:** Show the Authority list to the original system creator.
- **Pass:** The creator agrees that the top 5 nodes are the actual architectural pillars of the system. The "근거" (Evidence) listed matches their mental model (e.g., "Yes, GraphModel is dominant because it owns the state").
- **Fail:** The list elevates highly-referenced utilities (e.g., `Logger`) above actual domain logic because of naive `fan-in` counting.

### Q3: Criticality Test (Pending Phase 6)
- **Test:** Review the `UTILITY` vs `CORE` classification.
- **Pass:** Changing a `UTILITY` node feels safe; changing a `CORE` node feels terrifying. The classification accurately reflects this psychological reality.
- **Fail:** A core domain model is classified as `SUPPORTING` because it lacks external dependencies.

### Q4: Extension Test (Pending Phase 7)
- **Test:** A developer wants to add a new feature (e.g., a new Rule).
- **Pass:** The system correctly identifies `IRule` and `RuleRegistry` as the places to plug in.
- **Fail:** The system points to concrete classes or irrelevant interfaces.

### Q5: Blast Radius Test (Pending Phase 8)
- **Test:** Propose deleting the #1 "High Blast Radius" node.
- **Pass:** The system correctly explains *why* the deletion is catastrophic, listing exactly which other critical pipelines will collapse.
- **Fail:** The system identifies a node with high fan-out but no actual impact on core pipelines.

### Q6: Boundary Test (Pending Phase 5)
- **Test:** Map the identified boundaries against the folder structure or logical layers.
- **Pass:** The engine successfully separates `UI/View` logic from `Core/Domain` logic and identifies the `Adapter` bridging them.
- **Fail:** The engine hallucinates a boundary inside a tightly coupled cohesive module.

### Q7 & Q8: Flow Test
- **Test:** Compare the emitted pipelines against a human-drawn sequence diagram of the system's main use case.
- **Pass:** The engine's pipelines match the sequence diagram's primary lifelines.
- **Fail:** The engine misses the main orchestration path, or outputs noisy paths that no human would care about.

---

## Conclusion
Until SYNAPSE passes these human-centric validations, it remains a structural analyzer, not an architect assistant. Future development (Phases 5-8) must continuously benchmark against these exact tests.
