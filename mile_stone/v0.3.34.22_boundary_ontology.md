# v0.3.34.22 Boundary Ontology

The Boundary layer (Phase 5) is responsible for dividing the system into logical layers, islands, and structural communities **strictly based on topological evidence**, avoiding naive directory-based grouping.

## The Prime Directive
> Boundary is defined by Structural Gravity (Modularity), not File System Location.

## Core Concepts & Findings

### 1. `BOUNDARY` (Community / Layer)
A high-cohesion subgraph where internal structural gravity exceeds external structural gravity.
- **Evidence Source:** `CommunityEvidence` (derived from Louvain Community Detection algorithm).
- **Target Type:** `GROUP` (A new target type in `Finding` mapping to multiple node IDs that belong to the boundary).

### 2. `BOUNDARY_CROSSER` (Bridge / Adapter)
A node that sits on the fracture plane between two Boundaries, facilitating communication.
- **Structural Profile:** High fan-out to a different boundary, or acts as a singular path between two boundaries.
- **Target Type:** `NODE`.

### 3. `BOUNDARY_ISLAND`
A Boundary community that has extremely low connectivity (e.g., 0 or 1 edge) to the primary system logic. Often represents external tools, deprecated code, or highly decoupled utility packages.
- **Target Type:** `GROUP`.

## Analysis Pipeline

```text
Graph
  ↓
BoundaryAnalyzer (Wraps CommunityDetector, emits CommunityEvidence)
  ↓
ReasoningSnapshot (Now holds Group/Community structures)
  ↓
Boundary Rules (Evaluates structural cohesion and cross-community edges)
  ↓
Boundary Findings (BOUNDARY, BOUNDARY_CROSSER, BOUNDARY_ISLAND)
```

## Explainability
When the Answer Engine processes these findings for Q6 ("시스템 경계는 어디인가?"), it will translate them as:
- "Identified Core Community comprising X nodes (e.g., Engine internals)."
- "Identified UI Community comprising Y nodes."
- "Node Z acts as a Boundary Crosser bridging UI and Core."
