# v0.3.34.22 Phase 7 Validation (Extension Point Layer)

This document defines the strict validation criteria for the Extension Point Layer, ensuring the engine mathematically separates structural extension points from naive interfaces.

## Required Validation Tests (`test/phase7_validation.test.ts`)

### 1. Simple Abstraction Test (Negative Case)
- **Scenario:** `ILogger` has 2 implementations (`ConsoleLogger`, `FileLogger`). It is injected into 50 different classes. There is no central registry; it's just a common dependency.
- **Expected Result:** The engine must NOT classify `ILogger` as an `EXTENSION_POINT`.
- **Fail Condition:** `ILogger` is classified as an `EXTENSION_POINT` just because it has implementations.

### 2. Registry Extension Test (Positive Case)
- **Scenario:** `IRule` has 10 implementations. It is NOT injected individually into 50 classes. Instead, it is registered in `RuleRegistry` and consumed as a collection by `RuleEngine`.
- **Expected Result:** The engine must classify `IRule` as an `EXTENSION_POINT` with high confidence.
- **Fail Condition:** The engine fails to identify the registry pattern or ignores `IRule`.

### 3. Open/Closed Test
- **Scenario:** `IScanner` has 5 implementations. It is injected into `FileScanner` which explicitly takes an array/collection of `IScanner`s.
- **Expected Result:** `IScanner` is an `EXTENSION_POINT`.

### 4. Implementation Count Test
- **Scenario:** `IDatabase` has exactly 1 implementation (`SqlDatabase`). Even if it's injected centrally, it's just a dependency inversion boundary, not an active extension point.
- **Expected Result:** The confidence is extremely low or it is rejected entirely as an `EXTENSION_POINT` until actual polymorphic variation is proven.
