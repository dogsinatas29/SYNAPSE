## 🧠 상세 설계 및 로직
### "Reasoner는 추측하지 않는다. IR Builder가 증명한다."
v0.3.34 실그래프 테스트(0 Findings)가 남긴 가장 큰 교훈은 **역할 경계의 확립**입니다.
Reasoning Engine은 `DEFINES_PAYLOAD`를 받으면 그것을 기정사실로 두고 후속 역할(CORE, STATE_OWNER)을 판독하는 순백의 논리 기계입니다. 
따라서 "이게 진짜 Payload인가, 아니면 단순 Config 옵션 껍데기인가?"를 고민하는 불확실성(Heuristics)의 영역은 전적으로 **Semantic Edge Extraction Layer(IR Builder)**가 감당해야 합니다.

### Candidate → Evidence → Confidence 파이프라인 도입
단순 매핑(`interface` 발견 = `DEFINES_PAYLOAD`)의 한계를 극복하고, 실제 프로젝트의 노이즈(예: `ThemeConfig`, `LoggerOptions` 등 가짜 Payload)를 걸러내기 위해 다단계 증명 파이프라인을 도입합니다.

**핵심 원칙:**
> **Architecture IR Builder는 Semantic Edge를 생성하는 시스템이 아니라, Semantic Evidence를 수집하고 검증하여 Semantic Edge를 증명하는 시스템이다.**

```text
[ Raw AST Graph ] (include)
      ↓
(1) Semantic Candidate Generator
  ├─ `interface GraphSchema` 발견 → Candidate: { type: DEFINES_PAYLOAD, source: GraphSchema, ... }
      ↓
(2) Evidence Collection (Contextual Analysis)
  ├─ [LANGUAGE] `interface_declaration` 증거 획득 (+0.4)
  ├─ [STRUCTURAL] `referenced_by_pipeline` 증거 획득 (+0.3)
  ├─ [STRUCTURAL] `referenced_by_3_models` 증거 획득 (+0.2)
  ├─ [NEGATIVE] `only_used_by_logger` 반증 획득 (-0.3)
  └─ ※ Linux C 커널의 경우: `interface` 대신 [STRUCTURAL] `function_pointer_table` (+0.4) 획득
      ↓
(3) Confidence Evaluator
  ├─ 증거의 합산 스코어 계산 (Positive + Negative) → Final Confidence 계산
  └─ 언어 편향 방지: STRUCTURAL Evidence 존재 여부 교차 검증
      ↓
(4) Final Promotion (Architecture IR)
  ├─ 언어별 Threshold(예: TS=0.8, C=0.6) 및 STRUCTURAL 조건 충족 시 `DEFINES_PAYLOAD` 엣지 주입
  ├─ 주입된 엣지에 상세한 `IPromotionReason[]` 기록
  └─ 탈락(Reject) 시 `RejectedCandidateReport`에 기각 사유(Negative Evidence 위주) 보존
      ↓
[ Enriched Semantic Graph ]
      ↓
[ Reasoning Engine ] (추측 없는 확정적 논리 실행)
```

## 🛠️ 기술적 변경 사항
- **Node/Edge Update:**
  - `ISemanticCandidate` 및 `ISemanticEvidence` 타입 정의 (Negative/Positive 스코어 포함).
  - 언어별 Threshold Profile 도입 (`languageFamily`에 따른 기준값 차등 적용).

## ✅ 최종 Acceptance Criteria (성공 기준)
단순 엣지 생성이 아니라, **"왜 생성되었는지 설명 가능한가?"**와 **"가짜를 완벽히 걸러내는가?"**를 증명해야 한다.

1. **1차 검증 (E2E Mock Graph):** 기존 Phase 9 테스트 완벽 통과.
2. **2차 검증 (Real SYNAPSE Graph):** 실제 `project_state.json` 위에서 파이프라인 정상 가동 확인.
3. **3차 검증 (Adversarial & Real-world Check):**
   - **Positive Ground Truth:** `GraphModel` 또는 `GraphSchema`가 적절한 증거(`referenced_by_pipeline` 등)를 수집하여 `DEFINES_PAYLOAD` 및 최종 `CORE / STATE_OWNER`로 승격되어야 함.
   - **Negative Ground Truth:** `Logger.ts`, `ThemeManager.ts`, `ConfigManager.ts` 등의 가짜 Payload 후보들이 빈약한 구조적 증거와 반증(Negative Evidence)에 의해 `DEFINES_PAYLOAD` 승격에서 탈락하고, 최종 `NOT CORE` 판정을 받아야 함 (`RejectedCandidateReport` 확인).
   - **Provenance Ground Truth:** 판정뿐 아니라 판정의 계보(Lineage)까지 완벽히 출력 가능해야 함 (예: `CORE ← STATE_OWNER ← DEFINES_PAYLOAD ← referenced_by_pipeline`).

## ⚠️ 예외 처리 및 주의 사항
- **허위 Payload 방지:** 필드가 많은 인터페이스라도, 그것을 참조하는 객체가 단순 유틸리티(`Logger`)뿐이라면 Confidence를 올리지 않음으로써 `DEFINES_PAYLOAD` 승격을 차단해야 한다.
- **의존성 방향:** AST의 `include` 방향과 런타임/시맨틱 엣지의 방향이 다를 수 있음(예: 의존성 역전). Extractor는 제어 흐름(Control Flow)과 데이터 흐름(Data Flow)을 구분하여 엣지 방향을 정확히 꽂아야 한다.
