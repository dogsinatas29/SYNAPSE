## 2. Extension Point Discovery Engine 설계 (아키텍처 축 발견)
- **개념 전환**: ExtensionCandidate(구현체 중심) -> ExtensionPointCandidate(확장 축 중심)으로 시스템 철학 변경.
- **IS_EXTENSION_POINT 메타데이터**: Self-loop 엣지로 인한 향후 그래프 연산 노이즈를 방지하기 위해 엣지가 아닌 `ISemanticNodeFact` (Node Fact) 형태로 `IS_EXTENSION_POINT`를 정의하기로 결정.
- **후보군 필터링 (Threshold)**: 단일 구현체만 있는 인터페이스 배제를 위해, `incoming IMPLEMENTS/EXTENDS >= 2` 인 노드만 Candidate로 승격하도록 기준 수립.
- **가중치 (Evidence Tier)**:
  - Tier 1: Extension Density (단순 확장 구현체 수)
  - Tier 1.5: Cross-cluster Density (구현체가 여러 클러스터/대륙에 걸쳐 있는지 여부 - 강력한 아키텍처 축의 증거)
- **목표 검증 기준 (Acceptance Criteria)**:
  - Top 5 확장 축 도출 목표: `IRule`, `LanguageScanner`, `ArchitectureAnalyzer`, `IAnswerAggregator`, `ChatAdapter`

  - `ValidationReportBuilder.ts`: 결과 AnswerBundle에서 추출된 Q4 항목들을 마크다운 리포트 `## 7. Architectural Reasoning` 섹션에 반영하도록 렌더링 로직 추가.

## 5. 구조적 증거 생성 한계 극복 (Java/Kotlin 상속 구문 파서 추가)
- **문제점**: `ExtensionPointCandidateGenerator`에 `INHERITANCE` 엣지가 전달되지 않아 확장 축이 0개로 나오는 문제 발생. Android의 다중 상속/다중 라인 구조를 기존 정규식이 잡지 못함.
- **원인**: 
  - `JavaScanner`와 `KotlinScanner`가 단순 정규식으로 `implements`/`extends`를 찾으려 했으나, `extends` 구문이 섞여 있거나 줄바꿈 처리된 Android 코드(`public class Foo extends Bar implements Callback`) 매칭에 실패함.
  - 이로 인해 상속 구조 엣지가 하나도 생성되지 않아 Graph에 INHERITANCE 증거 부족(0건) 현상 발생.
  - 또한 `GraphAnalyzer`의 Assembly Point 후보 판정 정규식도 엄격하여(단수형 `service` 불허 및 무조건 `^` 강제) 명백한 허브 클래스들이 탈락함.
- **조치**:
  - `JavaScanner.ts`: 다중 라인 및 `extends` 뒤에 오는 `implements` 구문까지 견딜 수 있도록 Regex 전면 교체. (`/class\s+\w+(?:<[^>]+>)?(?:[^{]*?)\bimplements\s+([^{]+)/g`)
  - `KotlinScanner.ts`: `:` 뒤에 나오는 다중 상속/생성자 오버라이드 지원 Regex 개선 및 로깅 추가.
  - `GraphAnalyzer.ts`: 진입점 후보 필터링의 Regex에서 `^` 제거 및 `services?` 허용. 평가 전 단계에서 어떤 수치로 평가받고 통과/탈락하는지 추적하는 `[ASSEMBLY_CANDIDATE]` 진단 로그 삽입.
  - `ExtensionPointCandidateGenerator.ts`: `[EXTENSION_CANDIDATES]` 로그를 통해 상속 기반 증거 확보 여부를 투명하게 출력.
- **결과**:
  - Java/Kotlin 프로젝트의 복잡한 상속 구조에서도 정상적으로 INHERITANCE 엣지 생성이 재개되며, Extension Engine으로 후보들이 공급되기 시작함.

## 6. Scanner 파이프라인 단절 해결 (레거시 폴백 차단)
- **문제점**: JavaScanner 정규식을 대폭 수정했음에도 `[JAVA_SCANNER_ENTER]` 로그가 전혀 찍히지 않고, 파이프라인 상에 `INHERITANCE` 엣지가 전혀 없는 문제. 참조 엣지 전량(5583개)의 Provenance가 `UNDEFINED`로 찍힘.
- **원인 (Case E-2 / F-2 파이프라인 이탈)**: 
  - `DataPipeline`이 `FileScanner` 인스턴스를 생성할 때, VSCode Extension 환경과 별도로 동작하거나 `BootstrapEngine`이 제대로 호출되지 않아 `ScannerRegistry`가 비어 있었음.
  - 레지스트리가 비어있어 `.java` 파서를 찾지 못한 `FileScanner`가 자체 하드코딩된 초창기 레거시 함수(`FileScanner.parseJava`)로 폴백해 버렸음. 이 구형 함수는 단순 `import`만 찾고 상속 구조를 찾지 않음.
- **조치**:
  - `FileScanner.ts`에 명시적인 `constructor()`를 추가하여, 인스턴스 생성 시점에 `ScannerRegistry`를 확인하고 비어있으면 `JsTsScanner`, `JavaScanner`, `KotlinScanner` 등 전체 스캐너 군을 자동으로 즉시 등록하도록 락(lock) 메커니즘 구축.
  - 정확한 폴백 증명 및 런타임 추적을 위해 `[FILE_SCANNER_CONSTRUCTOR]` 및 `[LEGACY_PARSE_JAVA]` 로그를 심어 실행 흐름 모니터링 체계 완비.
- **결과**:
  - 어떤 진입점을 거쳐 분석을 실행하더라도 `FileScanner`를 사용할 경우 반드시 최신 `ScannerRegistry`가 장전되도록 강제되어 레거시 파서 이탈 위험을 영구 차단함.

## 7. ScannerRegistry 클래스 맹글링(Mangling) 중복 검사 버그 수정
- **문제점**: `FileScanner`에 강제 주입한 `ScannerRegistry`가 `JsTsScanner` 단 1개만 등록하고 나머지 파서들을 무시하는 버그 발생. (결과적으로 Java 파싱이 Legacy 파서로 다시 폴백함)
- **원인**: 
  - `ScannerRegistry` 내부의 중복 검사 로직이 `s.constructor.name === scanner.constructor.name` 으로 문자열 비교를 수행하고 있었음.
  - VSCode Extension 프로덕션 빌드(Webpack) 과정에서 클래스 이름이 맹글링(Mangling)되어 모든 스캐너의 `constructor.name`이 `""` 또는 동일한 알파벳 단일 문자로 압축됨.
  - 따라서 첫 번째 스캐너 이후 등록하려는 모든 스캐너가 중복(`"" === ""`)으로 판정되어 전부 누락됨.
- **조치**:
  - `ScannerRegistry.ts`의 중복 검사 로직을 문자열 비교에서 메모리 주소 기반 식별 비교(`s.constructor === scanner.constructor`)로 교체하여 맹글링에 면역되도록 수정.
  - `EdgeBuilder.ts` 리턴 직전 `[EDGE_BUILDER_OUTPUT]` 로깅 추가하여 GraphModel 엣지 유입 최종 검증.
  - 모든 스캐너(10개)가 정상 등록되고, JavaScanner가 174개의 `EXTENDS`와 98개의 `IMPLEMENTS` 상속 엣지를 정상적으로 Graph 파이프라인(EdgeBuilder)에 전달하는 것을 입증함.

## 8. 증거 평가 단계 ID 불일치로 인한 Extension Point 증발 버그 수정
- **문제점**: 후보생성 이후 보고서 출력사이 어딘가에서 데이터 증발 발생. `ExtensionPointCandidateGenerator`가 44개의 후보를 성공적으로 생성했음에도 불구하고, Q4 리포트에는 "No significant extension points found."가 출력됨.
- **원인 (Promotion Engine 기각)**:
  - `ExtensionPointCandidateGenerator`는 `candidate.nodeId`에 파일 경로(`edge.to`, 예: `ghost://Callback`)를 저장함.
  - 하지만 후속 단계인 `ExtensionPointEvidenceEvaluator`는 그래프 엣지를 필터링할 때 `target === candidate.nodeId`를 검사하는데, 여기서 `target`은 원본 클래스 이름(`edge.data.originalTarget`, 예: `Callback`)이었음.
  - `Callback === ghost://Callback` 조건이 항상 `false`가 되어 구현체(Implementor) 엣지를 0개로 판정.
  - 이에 따라 `structuralEvidenceCount`가 0이 되어, `PromotionEngine`의 구조적 증거 컷(최소 1개)을 통과하지 못하고 44개 후보가 전원 기각당함.
- **조치**:
  - `ExtensionPointEvidenceEvaluator.ts`의 필터 로직을 수정하여, 원본 이름 비교(`cand_extension_point_${target}` === `candidate.id`) 및 노드 ID 비교(`e.to === candidate.nodeId`)가 모두 완벽하게 매칭되도록 보완.
- **결과**:
  - 44개의 후보들이 억울한 누명을 벗고 증거(Evidence)를 획득하여 정상적으로 승격(Promotion) 심사를 통과하며, ReasoningSnapshot 및 Q4 리포트까지 무사히 도착하게 됨.

## 9. Q4 렌더러 필드 불일치 수정 (answer.findings → answer.items)
- **문제점**: `[EXTENSION_PROMOTION] {promoted:41}`, `[Q4_INPUT] {extensionPoints:44}` 로그 정상 출력에도 Q4 리포트에 "No significant extension points found." 출력.
- **원인**: `ValidationReportBuilder.ts`가 `answer.findings` 필드를 읽고 있었으나, `IAnswer` 인터페이스 실제 필드명은 `items`. `undefined` → else 분기 → fallback 문자열 출력.
- **조치**: `ValidationReportBuilder.ts` Q4 렌더링 블록을 `answer.items`, `item.targetId`, `item.score`, `item.explanation` 기준으로 수정.
- **결과**: Q4 Extension Points 섹션에 41개 승격 결과물이 정상 렌더링됨.

## 10. Framework Noise Filter 적용 (ExtensionPointCandidateGenerator)
- **문제점**: Q4 출력에 `Fragment`, `AppCompatActivity`, `RecyclerView.Adapter`, `Serializable`, `Parcelable` 등 Android/Java SDK 타입이 Extension Point로 승격되어 노이즈 발생.
- **원인**: 후보 생성 단계에서 외부 프레임워크 타입과 프로젝트 고유 확장 축을 구분하지 않음.
- **조치**:
  - `ExtensionPointCandidateGenerator.ts`에 `isFrameworkType()` 메서드 추가.
  - Package prefix 기반 필터: `android.`, `androidx.`, `java.`, `javax.`, `kotlin.`, `com.google.`
  - 클래스명 기반 필터: `Fragment`, `AppCompatActivity`, `RecyclerView.*`, `Serializable`, `Parcelable`, `Comparator`, `ViewModel` 등.
  - `AGGREGATE_` prefix 노드도 후보에서 제외.
- **결과**: 45개 → 약 10~15개 프로젝트 고유 Extension Point로 정제 예상.

## 12. AGGREGATE_unknown 원인 추적 및 상태 분리 (FSM 관점)
- **문제점**: Q4 Extension Points에 `AGGREGATE_unknown (Confidence: 1.00)` 반복 출력.
- **원인 추적**:
  - `VirtualDebugger.ts`: edge가 현재 `rawStateNodes`에 없는 노드를 가리킬 때 `collapsedNode`가 `undefined` → `cluster_id` 조회 실패 → `'unknown'` fallback → `AGGREGATE_unknown` 생성.
  - `[AGGREGATE_NO_CLUSTER]` 로그 분석 결과: `nodeFound: false` — 해당 노드들이 분류 실패가 아니라 현재 View Scope 밖에 있는 정상 노드들.
  - 실제 샘플: `README.md`, `CHANGELOG.md`, `telemetryReporter.ts` 등.
- **설계 전환 (FSM 관점)**:
  - 기존: `UNKNOWN` = 오류 → 제거.
  - 신규: `UNKNOWN` = 도달한 상태(State) → 분류 및 추적.
  - 상태 분리:
    - `AGGREGATE_out_of_scope`: `rawStateNodes`에 없는 노드 (View Scope 이탈, 정상)
    - `AGGREGATE_unknown`: `rawStateNodes`에 있는데 `cluster_id` 없음 (진짜 분류 버그)
