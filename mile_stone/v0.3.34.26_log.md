## 🛠️ 작업 내용 요약

### 1. State 기반 정적 결함 전파 모델 정의
- `schema.ts`에 `PropagationRule`, `FailureImpact`, `FailurePropagationReport` 인터페이스 추가.
- 아키텍처 스케일(리눅스 커널 7만 노드)에서의 OOM(Out of Memory) 방지를 위한 하드 스탑 상수 명시:
  - `MAX_PROPAGATION_DEPTH = 3`: 3단계(Cascade)까지만 탐색 (무한 순회 원천 차단).
  - `MAX_IMPACT_NODES = 1000`: 한 번의 분석당 총 전파 노드가 1000개를 초과하면 즉시 중단.

### 2. FailurePropagator 엔진 구현
- **경로:** `src/core/FailurePropagator.ts`
- 런타임 에러 예측(Execution Simulation) 배제 원칙 준수. 오직 정적 그래프의 결함 노드에서부터 의존성을 따라 파급 범위를 BFS로 탐색하여 개수만 산출 (상태 변경 없음).
- 전파 시뮬레이션 결과로 `directImpact`, `indirectImpact`, `cascadeImpact`, 그리고 `blastRadius` (HIGH/MEDIUM/LOW/SAFE)만 반환.

### 3. StateAuditPipeline 연동 & 캐시 배제 (Compute → Report → Discard)
- **경로:** `src/core/StateAuditPipeline.ts`
- `TransitionGrammar` 검사가 끝난 노드 상태를 이어받아 `FailurePropagator`로 전파 영향을 계산.
- 계산된 세부 데이터는 `ValidationEngine`을 거쳐 보고서(Report)로 생성된 직후 메모리에서 즉시 소멸됨. (어떠한 형태의 캐시나 Snapshot 저장도 금지)

### 4. Validation Report Section 9 신설
- **경로:** `src/core/validation/ValidationReportBuilder.ts`
- `Failure Propagation Report` 서브섹션 렌더링. 
- FSM Audit에서 습득한 교훈 적용: 수천 개의 타격 노드 목록을 인라인으로 렌더링하지 않음. Direct/Indirect/Cascade 등 깊이별 요약(Summary) 카운트와 상위 증거에 접근할 수 있는 `[View Failure Graph]` 명령 링크만 출력하여 5000줄 이상의 거대 보고서 생성을 방지.

### 5. Benchmark 결과 확인
- **경로:** `scripts/verify_anomaly_collector.ts` 수정 및 검증
- 결과:
  - **Linux Kernel** (70,089 Nodes): +90.91 MB 
- 최대 1000 노드 방어 기믹을 통해, 악의적인 결함을 주입해도 힙 메모리 폭발 없이 안정적으로 제어됨을 입증.

## 💡 의사결정 기록 (Invariant)

- **Execution Simulation 및 상태 변화 금지**: 우리는 "이 노드가 지워졌을 때 누가 영향을 받는가?"만 계산한다. "A가 터지면 B가 어떤 상태(CORRUPTED 등)로 바뀌는가?"를 다루지 않는다. 상태 변화 시뮬레이션은 전적으로 v0.3.34.27 `Topology Mutation`의 책임이다.
- **Compute → Report → Discard**: 0.3.34.27 `Topology Mutation` 시 폭발적인 조합 계산이 예상되므로, 지금부터 모든 전파 시뮬레이션 결과는 보고서 작성 즉시 폐기하여 캐시로 인한 메모리 누수를 원천 방어한다.
