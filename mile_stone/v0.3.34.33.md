# 🚀 Milestone v0.3.34.33 - Analyzer Characterization Framework (계측기 특성화)

## 📅 작업 정보
- **상태:** 🏗️ Planned
- **관련 마일스톤:** v0.3.34.32 (이전 버전 링크)
- **목표:** 가상 디버깅 및 시뮬레이션 기반 아키텍처 추론의 완결판. 프로젝트가 아닌 '분석기 자체'를 분석하는 프레임워크를 확립한다. Extractor 편향을 객관적으로 계측(Characterization)하고, 비용 예산을 통제하여 차기 버전 개조의 정량적 근거를 마련한다.

## 🧠 상세 설계 및 로직

v0.3.34.32의 리눅스 반증 테스트를 통해 "Software Property"와 "Extractor Property"가 분리되었다.
본 버전은 이 교훈을 바탕으로 **'계측기의 검증(Phase 14)'**을 전담한다.

Linux 반증 테스트가 남긴 3대 교훈(Blind Spot, Cost Explosion, Software vs Extractor Property 분리)을 완벽히 흡수하기 위해, 본 버전을 세 가지 트랙으로 분할한다. 측정기 개조(Re-Engineering)의 실제 구현은 차기 버전(0.3.34.34)으로 이관하며, 0.3.34.33은 오직 **"무엇을 못 보는가"**와 **"무엇이 시스템을 죽이는가"**에 대한 특성화(Characterization)에만 집중한다.

### Track 0: Characterization Baseline (계측 기준점 고정)
버전 간(v0.3.34.33 vs .34) 비교를 위해 측정 대상(Project)을 고정하는 벤치마크 스위트.
- **Benchmark Project Set:** 규모별로 고정된 프로젝트 풀을 사용하여 측정의 일관성을 확보한다.
  - `Tiny`: 단일 컴포넌트 수준
  - `Medium`: VSCode Extension 수준 (예: AntennaPod)
  - `Large`: 모노레포 수준 (예: VSCode)
  - `Kernel Class`: OS 커널 수준 (예: Linux)

### Track A: Extractor Characterization (관측 한계 특성화)
"무엇을 못 보는가"에 대한 과학적 규명 트랙.
1. **Blind Spot Topology Map (1급 산출물):** 관측 영역과 맹점의 한계 지도화.
   - **Observability Class (가시성 등급):** 관측 해상도를 5단계로 세분화한다. (`Observable` 직접 관측, `Partially Observable` 부분 관측, `Inferable` 추론 가능, `Blind` 완전 맹점, **`Misleading`** 잘못된 관측). 특히 '보이긴 하지만 실제와는 틀리게 맺히는 착시(Misleading)' 상태를 분리하여 위험도를 측정한다.
   - **Missing Coverage (정량적 맹점 비율):** 정성적 Blind Spot 묘사를 넘어 실제 탐지 실패 비율을 수치화.
     - **Effective Coverage (실질 커버리지):** `Coverage`와 `Metric Confidence`를 결합하여 산출한다. 신뢰도 체계는 오직 개별 지표를 나타내는 `Metric Confidence`와 최종 시스템의 `Framework Confidence` 두 가지만 허용한다. (그 외 Coverage Confidence, Measurement Confidence 등 무한 증식 원천 금지)
   - **Detection Stability Score (탐지 안정성 지수):** 분석기가 결정론적(Deterministic)인지 검증하기 위해, 동일 프로젝트 반복 측정 시의 편차를 산출한다. (예: 5회 측정 결과 61%, 60%, 62%, 59%, 61% → Stable)
   - **Blind Spot vs Misleading Risk (맹점 및 착시 위험도 분리):** '모르는 것(Blind)'과 '틀리게 아는 것(Misleading)'의 피해 규모를 분리한다. `Coverage Gap` 기반의 Blind Risk보다, 가짜 엣지로 그래프 전체를 오염시키는 Misleading Risk에 더 높은 가중치를 부여한다. (예: FP Cost = 12, FN Cost = 88)
   - **Recoverability & Source (복구 가능성 및 출처):** 맹점이 발생했을 때 추론 레이어를 통한 복구 가능 여부를 3단계(`Recoverable`, `Partially Recoverable`, `Unrecoverable`)로 평가하고, **복구 출처(Recovery Source)**를 반드시 명시하여 차기 버전 개조의 단서를 제공한다. (예: `Recoverable via AST`, `Recoverable via Semantic`)
2. **Extractor Agreement Matrix (추출기 동의 행렬):** 추출기 간의 탐지 일치율을 교차 검증한다. 단, '모두 다 같이 틀리는' 집단 착시를 방지하기 위해 `Agreement`(동의율)와 `Ground Truth Match`(정답 일치율)를 분리한다.
   - **Consensus Illusion Index (CII, 집단 착시 지수):** `CII = Agreement - Ground Truth Match` 공식을 통해 추출기들이 집단으로 정답에서 벗어나는 정도를 정량화한다. (예: Agreement 95% - Ground Truth 20% = CII 75% → `CRITICAL`)
3. **Extractor Property Registry (추출기 성향 영구 보관소):** 단순 메타데이터를 넘어, 추출기 자체의 특성(Property)을 영구 버전 관리한다.
   - **Schema:** `Strength`(강점), `Weakness`(약점), `Bias`(편향성), `Metric Confidence`
   - **Property Attribution:** 관측 실패가 프로젝트 특성 때문인지(Project Dependency), 추출기 자체의 한계인지(Extractor Dependency)를 분리하여 귀속시킨다.
   - **Property Stability Index (성향 안정성 지수):** 버전이 지남에 따라 추출기의 편향성(Bias)이나 커버리지가 얼마나 심하게 흔들리는지 장기 추적한다. (예: `v33 Bias 0.42 → v34 Bias 0.81` 이면 측정기 자체가 불안정함을 의미)
   - 예) `RegexProvider` → Strength: Naming Convention, Weakness: Dynamic Dispatch, Bias: Over-detects naming
4. **Calibration Dataset (Auto-Calibration 절대 금지):** 보정 행렬(Matrix) 구성을 위한 원시 로깅 데이터를 저장만 한다. v0.3.34.33 내에서 `Auto Calibration`, `Auto Weight Update`, `Auto Confidence Update` 등 측정기가 스스로를 수정하는 행위는 관찰자 효과(Observer Effect)를 유발하므로 원천 금지한다.
5. **Bias Report:** 최종 구조적 착시 현상 리포트.

### Track A.5: Trustworthiness Layer (결과 신뢰성 계층)
- Track A에서 도출된 다양한 지표(Coverage, Confidence, Agreement, Ground Truth)를 종합하여, **"최종적으로 이 분석 결과를 믿고 행동해도 되는가?"**를 단일 지표로 압축한다.
- **※ Confidence Hell 방지 (신뢰도 체계 단순화):** 수많은 중첩된 Confidence 지표 관리에 따른 복잡도를 통제하기 위해, 모든 신뢰도 체계를 개별 측정값의 `Metric Confidence`와 최종 시스템 레벨의 `Framework Confidence(Trustworthiness)` 2단계로만 엄격히 제한한다.
- **Trustworthiness Score (Framework Confidence):** `LOW`, `MEDIUM`, `HIGH`, `ABSOLUTE`
  - 예) Coverage 80%, Confidence 0.3, Agreement 90%, Ground Truth 20% → Trustworthiness `LOW` (숫자만 높은 모래성)
  - 예) Coverage 65%, Confidence 0.95, Agreement 75%, Ground Truth 70% → Trustworthiness `HIGH` (수치는 낮아도 단단한 진실)

### Track B: Performance Characterization (비용 폭발 특성화)
"무엇이 시스템을 죽이는가"에 대한 공학적 진단 트랙.
1. **Cost Profile (1급 산출물):** 추출기별 알고리즘 복잡도 및 병목 기록.
   - **Survivability Class (생존 한계 등급):** 단순 수치(Cost %)가 아닌, 해당 추출기가 파괴되지 않고 정상 동작할 수 있는 '최대 검증 규모'를 직관적으로 명시한다. (예: `Tiny Ready`, `Medium Ready`, `Large Ready`, `Kernel Ready`)
   - **Execution Cost Class:** 단순 Big-O 복잡도가 아닌, 실제 관측된 성능 붕괴 위험도(Observed Cost)에 따른 공식 등급 체계.
     - `SAFE`: 실제 런타임 점유율(Observed) < 5%
     - `SCALING_RISK`: Observed 5~20%. 증폭률에 따라 대형 모노레포에서 병목 가능성.
     - `KERNEL_RISK`: Observed > 20%. 거대 커널 적용 시 시스템 붕괴 위험.
     - `FORBIDDEN`: 알려진 치명적 안티패턴 (예: Loop 내부 JSON 직렬화/I/O).
   - **Theoretical Cost (이론적 복잡도):** O(N), O(N²) 등 코드 레벨의 알고리즘 비용 추산 (Complexity Profile).
   - **Observed Cost (실측 점유율) 및 Cost Budget:** 이론적 복잡도와 무관하게 실제 런타임을 측정하고 허용 예산과 대조.
     - **Metric Confidence:** 샘플링 오차나 환경 변수를 고려한 개별 측정값의 신뢰도.
     - **Cost per Artifact (단위 비용):** 프로젝트 규모와 무관하게 비교 가능한 절대 단위 지표. (예: `2 ms/file`, `0.5 ms/edge`)
     - 예) `AuthorityBuilder` → Theoretical: `O(N)`, Observed: `32%`, Budget: `15%` → Status: `OVER BUDGET` (Class: `KERNEL_RISK`)
   - **Cost Attribution (비용 원인 분석):** 전체 런타임을 소모하는 기능별 근본 원인의 비중. (예: AST Parsing 31%, Edge Expansion 27%, State Mutation 18%, Logging 14%, Serialization 10%)
   - **Cost Owner & Type (비용 주체 및 유형):** 예산을 소비한 서브시스템(진범)과 자원 유형(CPU, I/O, Memory, Serialization, **State Explosion/Graph Growth**)을 식별한다. (예: `EdgeBuilder` → Owner: `Reasoning Layer`, Type: `State Explosion`)
   - **Amplification Factor (증폭률) & Risk Class:** 입력 데이터 대비 파생/생성 데이터의 폭발 비율 및 위험도 등급화.
     - 등급: `<5x (SAFE)`, `5~20x (WATCH)`, `20~100x (HIGH)`, `>100x (CRITICAL)`
     - 예) Linux 커널 스캔 시 190x 증폭 → `CRITICAL`
   - **State Space Growth Profile (상태 공간 팽창률):** 단순한 증폭률(190x)을 넘어, 파이프라인 단계별로 객체가 팽창하는 계층적 궤적을 추적. (예: Input Nodes 63k → Signal Nodes 91k → Virtual Edges 3.2M → Validation Edges 8.7M → Total 12M+)
   - **Memory & Heap Amplification:** 단순 객체 증폭을 넘어 실제 힙 메모리 폭발 궤적을 추적. (예: Input 40MB → Heap 3.2GB = `80x Memory Amplification`)
   - **Marginal Cost Curve & Inflection Point (한계 비용 곡선 및 변곡점):** 규모(Scale) 증가에 따른 비선형적 런타임 상승 궤적을 추적하여 변곡점(Inflection Point)을 시각화한다. (예: 10k files→5s, 40k→21s, 80k→200s 폭발)
   - **Logging Risk:** I/O 병목 및 직렬화 비용 위험도.
2. **Bottleneck Causality Layer (원인 사슬 계층):** 단순한 비용 통계(32%)를 넘어 병목의 인과 관계 사슬을 추적한다.
   - 예) `Cost 32%` → `JSON Serialization` → `Tight Loop 내재` → `3.2M Iterations`
3. **Cost Explosion Report:** 인과 사슬(Causality Layer)을 기반으로 성능 붕괴의 근본 원인을 해부한 최종 리포트.
4. **Failure Pattern Catalog (Postmortem DB):** 시스템 붕괴를 유발하는 치명적 안티패턴을 단순 나열이 아닌 '살아있는 데이터베이스'로 관리하여 향후 정적 검증 룰로 재사용한다.
   - **Pattern Schema:** `Severity`, `Trigger`, `Mitigation`, `Occurrences`, `Projects Seen`, `Observed Cost`, `Last Seen`, `Status`, `Fixed In`
   - **Lifecycle Status:** 패턴의 생애주기를 추적한다. (`OPEN` 발견, `MITIGATED` 완화됨, `FIXED` 해결됨, `REGRESSION` 재발, `ARCHIVED` 폐기)
   - `PATTERN_001`: Loop 내부 JSON 직렬화 및 I/O
     - Trigger: tight loop logging → Mitigation: Counter 누적 및 단일 Flush
     - Data: Severity: `CRITICAL`, Occurrences: 14, Cost: 31%, Status: `REGRESSION`, Fixed In: `v0.3.34.34`
   - `PATTERN_002`: O(N²) Edge Traversal (공간 인덱싱 누락)
   - `PATTERN_003`: Repeated AST Reparse (Cache Miss Storm)
   - `PATTERN_004`: Amplification Storm (파생 객체 연쇄 폭발)

### Track C: Priority Factors (우선순위 팩터 수집 - Score 계산 금지)
- 규명된 Track A(Bias)와 Track B(Cost)를 바탕으로 개조에 필요한 팩터들을 수집만 한다.
- **가중치 합산 금지:** `Priority = Cost + Coverage + Impact` 같은 가중치 수식은 정치적 편향이 개입되므로 34.33에서는 합산하지 않는다. 
  - **수집 항목:** `CoverageGap`, `ObservedCost`, `UsageFrequency`, `ArchitecturalImpact`, `Recoverability`
  - **최종 Score 산출 이관:** 최종 합산 및 의사결정은 v0.3.34.34의 거버넌스 레이어로 완전히 이관하여 측정기의 순수성을 보존한다.
  - **설명:** 발생 빈도(Frequency)와 파괴력(Impact)을 철저히 분리한다. 드물게 발생하더라도 전체 아키텍처를 심각하게 왜곡하는 요소(High Impact)를 포착한다.
- **※ Boundary 원칙 (거버넌스 영역 0.3.34.34 이관):** 본 마일스톤(0.3.34.33)은 '무엇이 가장 치명적인 문제인가(Priority)'까지만 계측한다. 해당 문제를 고치는 데 드는 비용(Fix Cost)과 최종 투자 대비 효용(ROI) 산출은 '거버넌스 및 기획' 영역이므로, 실제 개조를 담당하는 차기 마일스톤(v0.3.34.34)으로 이관하여 계측기(Meter)로서의 순수성을 보존한다.

### Track D: Report Segregation Policy (보고서 계층화 분리)
단일 Source of Truth(계측 데이터)를 기반으로 소비자(Consumer) 목적에 맞춰 보고서를 다형성(Polymorphism)으로 투영한다.
0. **L0 - Raw Metric Dataset:** 측정기에서 추출된 순수 원시 데이터. 진단 및 오류 추적의 최하단 종착지.
1. **L1 - Characterization Model:** L0 데이터를 기반으로 구조화된 핵심 분석 모델. (Coverage, Cost, Amplification 지표)
   - **Framework-Level Confidence Grade:** L1 모델 전체의 데이터 신뢰도를 A~D 등급으로 평가한다. (`A: Ground Truth`, `B: Manual Audit`, `C: Consensus`, `D: Heuristic`). 전체 모델이 Heuristic(D) 수준이라면 개별 지표의 수치가 높아도 L1 전체 결과는 '실험적(Experimental)'으로 취급된다.
   - **Characterization Drift (계측 변위 추적):** 이전 버전 측정값과의 차이(`Δ Coverage`, `Δ Cost`, `Δ Confidence`)를 추적하여 "실제로 진화했는가"를 자동 증명한다. (예: `v33 Coverage 61% → v34 Coverage 83%`)
2. **L2 - Architect Report:** 설계자를 위한 시스템 내부 구조와 병목 분석 뷰. (예: `Observed Cost 28%`, `State Space Growth 3.2M`)
3. **L3 - Executive Report:** 의사결정권자(경영진/PM)를 위한 ROI 및 리스크 요약 뷰. (예: `Priority: 95`, `Evidence Grade: D` → 즉시 개조가 아닌 '추가 조사' 지시)
4. **L4 - Onboarding Report:** 신규 기여자를 위한 생존 가이드 뷰. (예: `어디부터 읽어야 하는가?`, `절대 건드리면 안 되는 병목 구역`)
- **원칙:** 상위 레이어(L2~L4)는 독자적인 측정을 수행하지 않으며, 오직 L1 Model의 번역본(Projection)으로 기능한다.

## ⚠️ 예외 처리 및 주의 사항
- **Analyzer ≠ Logger:** 분석기와 출력기는 철저히 분리되어야 한다. 싱글 스레드 환경(Node.js)에서 I/O 버퍼를 잠식하는 행위를 원천 금지한다.
  - **금지:** 타이트 루프(Tight Loop) 내부에서의 `console.log(JSON.stringify(...))`
  - **권장:** 내부 `stats` 카운터(`stats.missed++`)만 증가시키고, 최종 완료 후 단 1회 출력.
  - **디버깅 샘플링:** 샘플링 버퍼 사용 시 `MAX_DEBUG_SAMPLES = 100` 등의 하드 상한선(Hard Limit) 필수 적용.
- 0.3.34.32에서 제거된 O(N²) 탐색 및 320만 번의 `console.log` 폭탄 사태가 재발하지 않도록 모든 파싱 레이어는 O(1) 캐싱 전략을 의무 준수한다.

## 🚀 MVP Phasing (구현 우선순위)
설계의 거대화(Scope Creep)를 막고 'Property Attribution(실패 원인 분리)'이라는 본질에 집중하기 위해 4대 핵심 산출물만 P0로 고정한다.
1. **P0 (Must Have - 핵심 계측 4대장):** 
   - Blind Spot Topology Map (Misleading, Recoverability 분리)
   - Extractor Agreement Matrix (CII 포함)
   - Extractor Property Registry
   - Cost Profile & Amplification Profile (객체 폭증 추적)
2. **P1 (Nice to Have - 통합 및 패턴 수집):**
   - Trustworthiness Layer (Framework Confidence)
   - Pattern Registry (이전 Failure Catalog, 데이터 누적 후 패턴 저장)
   - Priority Factors (가중치 계산 없는 단순 팩터 수집)
3. **P2 (Later - 장기 고도화):**
   - Marginal Cost Curve (충분한 샘플(Tiny~Kernel) 데이터 누적 후 궤적 분석)
   - Calibration Dataset
   - Characterization Drift
