```
└── Priority = f(Impact, Confidence, Reach, RepairCost)
```

### 3. Priority Engine 설계 방향 논의 (2026-08-26)

v0.3.34.33에서 **가중치 합산 금지** 원칙이 확립됨:

> "Cost + Coverage + Impact 식의 우선순위 계산은 기획적/정치적 가중치 판단이 개입되므로 금지"

#### Option A: Multi-Criteria Ranking (가중치 없음)

```
각 Risk Indicator를 독립 축으로 유지
→ Pareto Front로 Top-N 선택
→ 사용자에게 "어떤 축을 우선시할지" 선택권 위임
```

**장점:** 정치적 판단 배제, 투명성
**단점:** 사용자 결정 부담

#### Option B: Lexicographic Ordering (단계적 필터)

```
1단계: Blast Radius > threshold → CRITICAL
2단계: Boundary Violation → HIGH
3단계: Cycle Detected → MEDIUM
4단계: 기타 → LOW
```

**장점:** 직관적, 결정론적
**단점:** 임계값 설정 민감

#### Option C: Cost-Based Ordering (복구 비용 기준)

```
Priority = RepairCost × Impact
- Blast Radius 크지만 복구 쉬움 → 낮은 우선순위
- Blast Radius 작지만 복구 어려움 → 높은 우선순위
```

**장점:** 실제 ROI 반영
**단점:** RepairCost 추정의 불확실성

### 4. Governance Engine 설계 동결 (2026-08-26)

#### Core Invariant

> Governance Engine does not prioritize.
> Governance Engine only classifies and reveals dominance relationships.
> Any prioritization is a report-layer concern.

#### Non-Goal

This milestone does not introduce any new architectural signals.
It only changes how existing signals are represented and surfaced.

#### Decision: Option A — Pareto Frontier

**Rejected: Option B — Lexicographic Ordering**
Reason: Hidden priority table. Equivalent to weight table in different clothing.

**Rejected: Option C — Cost-Based Ordering**
Reason: RepairCost is an estimate, not an observation. Belongs to Planning, not Governance.

#### Active Dimensions (Frozen)

```
boundary  = boundaryCrossings
cycle     = cycleParticipation
coupling  = fanOut
authority = blastRadius
```

#### Reserved Dimensions

```
entropy, lifecycle, assembly
```

Reason: No stable per-node observable exists yet.

#### Special Rules

- **INTENDED_HUB**: Frontier 제외 (설계 의도 ≠ 위험)
- **UNKNOWN_HUB**: 일반 참여자, 예외 없음
- **Frontier**: 절대 자르지 않음 (Preservation Invariant)
- **Display Window**: Report Layer 책임

#### Layer Boundaries

```
GOVERNANCE LAYER
  RootCauseAggregator → RiskClassifier → RiskVectorBuilder → ParetoFrontier
  Output: FrontierResult (untruncated)

PRESENTATION LAYER
  FrontierPartitioner → DTO / Report
```

#### Orthogonal Axes

```
RiskType  = WHAT kind of risk (classification)
Frontier  = WHERE in dominance space (dominance)
```

#### Implementation Complete

- [x] PriorityLevel enum 제거
- [x] PriorityEngine 제거
- [x] CompressionEngine 제거
- [x] ParetoFrontier 기반 Frontier 생성
- [x] INTENDED_HUB는 Frontier에서 제외
- [x] Frontier Preservation Invariant 유지
- [x] TypeScript build PASS (reporting 관련)

#### 6.2 발견된 이슈

##### Issue A: frontier[0] — 순위 개념 혼입 (수정 완료)

**문제:**

```ts
const top = partitioned.frontier[0];
topRisk = `Dependency concentration around ${top.sourceGroup.ownerCluster}...`;
```

Pareto Frontier는 정렬 개념이 없는 집합이다. `frontier[0]`은 "가장 위험한 노드"를 의미하지 않는다. 단순히 "Frontier 집합 중 첫 번째 원소"일 뿐이다.

이는 "Governance does not prioritize" 원칙과 충돌한다.

**수정 전:**

```ts
if (partitioned.frontier.length > 0) {
    health = "WARNING";
    const top = partitioned.frontier[0];
    topRisk = `Dependency concentration around ${top.sourceGroup.ownerCluster} increases change impact.`;
    action = `Immediate action recommended on ${partitioned.frontier.length} frontier nodes.`;
    whyItMatters = `${top.sourceGroup.ownerCluster} affects ${top.authority} downstream nodes.`;
    sourceVal = "ParetoFrontier (non-dominated set)";
}
```

**수정 후:**

```ts
if (partitioned.frontier.length > 0) {
    health = "WARNING";
    const frontierNames = partitioned.frontier
        .map(v => v.sourceGroup.ownerCluster)
        .join(', ');
    topRisk = `${partitioned.frontier.length} nodes on the Pareto Frontier: ${frontierNames}.`;
    action = `Immediate action recommended on ${partitioned.frontier.length} frontier nodes.`;
    whyItMatters = `These nodes are mutually non-dominated across all risk dimensions.`;
    sourceVal = "ParetoFrontier (non-dominated set)";
}
```

**결과:**

- `frontier[0]` 참조 0건 확인
- Frontier 전체를 집합으로 표현
- 순위 개념 제거


### 10. v0.3.34.37 작업 계획 — 보고서 엔진 정렬 (2026-08-26)

#### 10.1 배경

v0.3.34.36에서 Governance Engine의 핵심 철학이 확립됨:

```
Governance Engine does not prioritize.
Governance Engine only classifies and reveals dominance relationships.
Any prioritization is a report-layer concern.
```

하지만 보고서 출력 레이어에는 아직 Priority Engine 시대의 언어가 잔존:

- `High Priority Technical Debt`
- `dangerously fragile`
- `massive side-effects`
- `Risk: [FRONTIER]`
- `High Risk` / `Low Risk`

v0.3.34.37의 목표는 **Governance 철학을 보고서 문구 레벨까지 완전히 관통시키는 것**.

#### 10.2 보고서별 역할 재정의

#### 10.3 핵심 설계 결정

##### 1. RefactorCandidate → ArchitecturalFinding 리네임

현재 `RefactorCandidate`는 "리팩토링 후보"라는 의미지만, 실제로는 FRONTIER/WATCH/INTENDED를 모두 담고 있으므로 의미적으로 부정확.

```ts
// Before
interface RefactorCandidate {
    filePath: string;
    reason: string;
    evidence: string;
}

// After
interface ArchitecturalFinding {
    filePath: string;
    observation: string;
    interpretation: string;
    recommendation: string;
}
```

##### 2. candidates → findings 리네임

```ts
// Before
interface ArchitectInsight {
    candidates: RefactorCandidate[];
}

// After
interface ArchitectInsight {
    findings: ArchitecturalFinding[];
}
```

##### 3. Observation/Interpretation/Recommendation 3단 분리

```
Observation     = 관측 사실만 (수치, 분류, 상태)
Interpretation  = 해석 (판단 형용사 최소화)
Recommendation  = 행동 요청 (검토 항목 중심)
```

##### 4. Risk Type → Topology Type

`Risk Type`은 Priority Engine 잔재. `Topology Type`이 구조적 분류에 더 정확.

##### 5. Blast Radius → Authority Connections

Observation에서 `Authority (Blast Radius): 23`는 이미 해석이 포함된 표현. `Authority Connections: 23`이 더 원시적.
