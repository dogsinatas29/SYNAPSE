# Milestone v0.3.34.38 - Report Truthfulness Fix

## Status

Planned

---

# Objective

v0.3.34.37 completed the structural separation of the reporting system.

However, report generation still contains several cases where generated interpretations do not accurately reflect the underlying evidence.

The purpose of v0.3.34.38 is not to improve subsystem detection quality.

The purpose of v0.3.34.38 is to ensure that reports never state information that is not supported by evidence.

---

# Core Principle

> Reports must never say more than the evidence proves.

Observation → Interpretation → Recommendation

must remain logically consistent.

---

# Scope

## Included

* Evidence ↔ Interpretation consistency fixes
* Executive / Architect Frontier count alignment
* Unknown subsystem truthfulness fixes
* Semantic Context propagation auditing

## Excluded

The following are explicitly deferred to v0.3.34.39:

* BoundaryDetector improvements
* Unknown subsystem reduction
* Semantic Context recovery
* Boundary inference enhancements
* Subsystem recognition expansion

---

# Success Criteria

## SC-1

WATCH findings with:

```text
Coupling: 0
```

must never produce:

```text
multiple outbound connections
```

Expected output:

```text
No outbound coupling detected.
```

---

## SC-2

INTENDED findings must derive connectivity statements from actual coupling values.

---

## SC-3

FRONTIER findings must include the actual subsystem identifier when available.

Example:

```text
The node belongs to the 'src/core/analysis' subsystem.
```

instead of:

```text
The node belongs to the subsystem boundary.
```

---

## SC-4

Executive Frontier count must equal Architect Frontier count.

Both reports must be generated from the same classified data source.

---

## SC-5

Unknown subsystem findings must never claim subsystem ownership.

Forbidden:

```text
It belongs to the 'Unknown' subsystem.
```

Allowed:

```text
No subsystem classification was available.
```

---

## SC-6

Legitimate Unbounded Node

### Case C

Propagation Loss

# Phase 1 - Evidence Interpretation Alignment

## File

```text
src/core/reporting/InsightEngine.ts
```

---

## WATCH Template

Current behavior:

```text
Coupling: 0

↓

This node has multiple outbound connections.
```

This is a factual contradiction.

Replace with evidence-driven generation.

---

## INTENDED Template

Current behavior:

```text
This node has high outbound connectivity.
```

without validating actual coupling values.

Interpretation must derive from evidence.

---

## FRONTIER Template

Current behavior:

```text
The node belongs to the subsystem boundary.
```

Replace with actual subsystem identifier when available.

---

# Phase 2 - Frontier Count Alignment

## Problem

Executive report and Architect report currently derive Frontier statistics from different processing paths.

Observed result:

```text
Executive Frontier Count = 1
Architect Frontier Count = 3
```

This is internally inconsistent.

---

## Fix

Ensure:

```text
buildExecutiveInsight()
```

and

```text
buildArchitectInsight()
```

consume the same classified result set.

---

# Phase 3 - Semantic Context Propagation Audit

## Goal

Determine where subsystem information disappears.

This phase does NOT modify BoundaryDetector.

This phase only traces propagation.

---

## Audit Chain

```text
SemanticContext
    ↓
RootCauseAggregator
    ↓
RiskClassifier
    ↓
InsightEngine
```

---

## Audit Output

For each Unknown finding:

```text
[SC_AUDIT]

Node
Semantic Boundary
Aggregator Boundary
Classifier Boundary
Insight Boundary
```

---

## Classification Rules

### Case A

Detection Failure

Boundary never existed.

---

### Case B

Legitimate Unbounded Node

Node genuinely belongs to no subsystem.

---

### Case C

Propagation Loss

Boundary existed but disappeared during processing.
