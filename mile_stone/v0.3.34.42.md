## 🔬 Scientific Validation Rules (과학적 검증 규칙)
본 마일스톤은 기능 개발이 아닌 과학적 증명 모델에 기반합니다.

### 1. Falsification First (반증주의)
- 발견된 패턴(예: METADATA → SCC 유지)은 보편적 진리가 아닌 '가설'로 취급합니다.
- 타 프로젝트 검증 시 FAIL이 발생하면 `Universal Pattern`이 아닌 `[Project]-Specific Pattern`으로 즉각 강등합니다.

### 2. Failure is Evidence (실패는 반증 증거)
- 특정 프로젝트에서 가설이 기각(FAIL)되는 것은 엔진의 실패가 아닙니다. 그 기각 자체가 과학적 결과이며 반증 증거(Evidence)로 수집되어야 합니다. (성공 = 증거, 실패 = 반증 증거)

### 3. Hypothesis Lifecycle (가설 생애주기 상태 머신)
단순한 Claim을 넘어, 가설의 상태 머신(State Machine)을 도입하여 생애주기를 관리합니다.
- `DISCOVERED` → `PRELIMINARY` → `EXPERIMENTAL` → `PROJECT_VALIDATED` → `CROSS_PROJECT_VALIDATED`
- **강등 조건**: 교차 검증 중 하나라도 실패(FAIL) 시 `PROJECT_SPECIFIC` 또는 `REJECTED`로 즉각 강등.
- 단순 결과 보고서가 아닌, 가설이 겪는 검증 여정 자체를 추적합니다.

### 4. Validation Dataset Bias & Diversity
선별된 4개의 타겟은 우연이 아닌 극단적 다양성을 의도한 것입니다. 향후 이러한 차이를 계량화하는 **Dataset Diversity Score** 개념을 도입하며, 다음 5개 축으로 평가합니다:
1. **Ecosystem**: Node vs Android vs Linux OS
2. **Language**: TypeScript vs Java/Kotlin vs C
3. **Domain**: Frontend IDE vs Backend API vs Android Native vs OS Kernel
4. **Architecture**: Event-driven vs DI Container vs MVVM vs Monolithic Kernel
5. **Scale**: 10k nodes vs 100k+ nodes

## 🧠 상세 설계 및 로직
- **[P-1] Determinism Validation**: 횡단 검증 이전에 동일 프로젝트를 3회 반복 분석하여 생성된 결과가 **100% 동일한지** 증명.
  - 검증 대상(`DeterminismSnapshot`): `claimIds`, `impactHashes`, `reportHashes`(architect, executive, onboarding, simulation).
- **[P-0.5] Profile Detector Validation**: 분석 파이프라인 시작 전, 현재 프로젝트를 정확히 100% 판별해 내는 `ProjectContextDetector`를 구축하고 검증.
- **[P0] Semantic Profile Layer**: 언어 및 프레임워크의 정체성을 최소한의 도메인 지식(Minimalism)으로 엔진에 제공.
  - 예: `arch/* => PLATFORM`, `init/main.c => EntryPoint`.
- **[P0.5] Semantic Classification**: `arch/*` 등을 삭제/무시하는 것이 아니라 `PLATFORM` 등으로 의미 분류(Semantic Role)를 수행. 
  - **주의: 원시 점수(Coupling 등)를 절대 조작하지 않으며, 오직 "해석(Interpretation)" 단계에서만 활용.**
- **[P0.7] Baseline Truth Dataset**: 평가의 기준이 될 절대적 객관적 사실 데이터셋을 정의. 
  - 파일과 심볼(`{ expectedEntryFile, expectedEntrySymbol }`)로 정의하며, `confidence: "CANONICAL" | "STRONG" | "HEURISTIC"` 속성을 포함.
- **[P0.8] Report Accuracy Benchmark**: Baseline Truth Dataset 대비 정확도 점수를 계량화하여 측정 (예: `Project Awareness Accuracy: Linux 30% -> 81%`).
- **[P1.5] Symbol Resolver**: 진입점을 파일이 아닌 '심볼'로 추적. 심볼 자체는 하드코딩된 규칙이 아니라 위상학, AST 증거와 결합되는 **Evidence**로 사용됨.
- **[P1] Project-Aware Entry Point Detection**: Profile을 바탕으로 진입점을 다르게 판별하는 `EntryPointStrategy` 분리. (Symbol Resolver 활용)
- **UNKNOWN Fallback**: 엔진이 프로파일을 확신하지 못하면(`UNKNOWN`), 중단(Stop)하는 것이 아니라 Semantic Layer만 비활성화하고, 기존의 범용 그래프 분석(SCC, Impact 등)은 100% 정상 작동하도록 유지함.
- **Future Foundation (Cost, Risk, Decision 보류)**: 현재 단계(v0.3.34.42)의 핵심은 Validation입니다. Cost, Risk 평가 및 P4(Decision Engine) 의사결정 기능은 시기상조이며 절대 금지. 본 마일스톤에서는 기반 구상 정도로 제한합니다.

## 📋 전체 작업 순서 (Execution Priority)
1. **[P-1] Determinism Validation**: 100% 동일한 결과 보장 (오차 허용 안 함)
2. **[P-0.5] Profile Detector Validation**: ProjectContextDetector 100% 정확도 검증
3. **[P0] Semantic Profile Layer**: 도메인별 Profile(Linux, NestJS 등) 기초 구축
4. **[P0.5] Semantic Classification**: Profile 기반 노드의 Semantic Role 분류 (점수 조작 금지)
5. **[P0.7] Baseline Truth Dataset**: 평가 기준치 및 심볼 정의
6. **[P0.8] Report Accuracy Benchmark**: 진단 결과의 정확도 점수 체계 도입
7. **[P1.5] Symbol Resolver**: 심볼 추적 및 Evidence 평가 엔진
8. **[P1] Project-Aware Entry Point**: Profile/Resolver 기반 진입점 탐지 교정
9. **[P2] Cross-Project Validation**: 위 시스템을 통한 4대 프로젝트 실제 교차 검증 (이후 결과 확인)
10. **[P4] Decision Engine**: ❌ 4대 프로젝트 검증이 끝날 때까지 절대 진입 금지

## ⛔ 절대 금지 사항 (Do NOT)
1. **Cost Engine 구현 금지**: 파일 수, 변경 라인 수, 테스트 범위 등 명확한 지표 데이터 없이 섣부른 비용 산출 금지.
2. **Decision Engine 구현 금지**: 자동 리팩토링 계획, Action Recommendation 등은 시기상조. 우리는 아직 '연구원' 단계임.
3. **Universal Pattern 섣부른 선언 금지**: 4대 프로젝트 검증이 모두 끝나고 명확한 FAIL 사례가 수집되기 전까지는 그 어떤 보편 법칙도 선언할 수 없음.

## ⚠️ 예외 처리 및 주의 사항
- 🚨 **[AST Analysis Constraints]**: 초대형 코드베이스(Linux Kernel 등) 분석 시 전역 AST 탐색 절대 금지. 오직 그래프 엔진이 식별한 4대 핵심 타겟(Top Intervention, Largest SCC, Highest Risk Hub, User Selected)에 대해서만 국소적 AST 허용.
- 🚨 **[Propagation Safety Rules]**: 무한 연쇄 참조에 의한 OOM 방지를 위해 기본 제한(DEPTH=3, NODES=500, EDGES=2000) 강제 적용 및 위반 시 Fail-Fast.
