  - 실제 구현 순서는 `Evidence ➡️ Pattern ➡️ Vocabulary ➡️ Question` 의 상향식(Bottom-Up) 구조를 따른다.

## 🛑 핵심 원칙 (Core Principles)

### 원칙 1. 패턴은 삭제하지 않는다 (No Deletion)
- `Authority Reach`, `Blast Radius`, `Control Score` 등이 중복처럼 보여도 임의로 제거하지 않는다. 우선 `Candidate Group`으로 묶어 실체를 규명한다.

### 원칙 2. Pattern Inventory는 '사실'만 적는다 (Objective Only)
- 주관적 판단을 배제하고, 오직 기계적 사실(비용, 저장소, 누수 현황)만 기록한다.

### 원칙 3. Vocabulary는 30개로 제한한다 (Finite Terms)
- 무한정 늘리지 않고, 아키텍트들이 실무에서 즉시 식별 가능한 30여 개의 핵심 용어만 고정한다.

### 원칙 4. 사용자 확장은 오직 Question Layer에서만 허용한다
- **Question (사용자 확장 가능):** 도메인 특화 질문 추가 허용 (`"결제 시스템의 핵심은 어디인가?"`)
- **Vocabulary (고정):** 아키텍처 용어(Domain Core 등)는 엔진 계약으로 보호되며 수정 불가.
- **Pattern (고정):** 패턴의 정의와 산식은 SYNAPSE Core가 통제하며 수정 불가.
- **Evidence (고정):** 실제 추출되는 원시 데이터는 수정 불가.
- ➡️ *이 구조를 통해 Pattern Explosion과 Vocabulary Drift를 방지하고 진단 무결성을 지킨다.*

## 🛠️ 단계별 산출물 우선순위

### 1순위: Pattern Inventory (`v0.3.34.44_pattern_inventory.md`)
- **질문:** SYNAPSE는 무엇을 알고 있는가?
- **목표:** SYNAPSE 코드베이스에 존재하는 실제 Pattern 전수조사. 계산되나 버려지는 지식 누수를 찾는다.
- **필수 컬럼:** `Pattern`, `Layer`, `Language Independent`, `Source`, `Generation Time`, `Storage`, `In Graph?`, `Persisted?`, `Computed but Dropped?`, `Used in Report?`, `Renderer Impact`, `Memory Impact`, `Bootstrap Impact`, `Vocabulary Candidate?`

### 2순위: Pattern Lineage (`v0.3.34.44_pattern_lineage.md`)
- **질문:** 이 패턴은 어디서 오는가?
- **목표:** 패턴 간의 계보도 생성 및 누수(Leakage) 지점 추적.

### 3순위: Pattern Survival Audit (`v0.3.34.44_pattern_survival.md`) - 🌟 NEW Phase 2.5
- **질문:** 이 버려지는 패턴을 정말 영구 보존(Persist)해야 하는가?
- **목표:** JSON 비대화를 막기 위해 패턴별로 `KEEP`, `ALIAS`, `DERIVED`, `DROP CANDIDATE` 판정.

### 4순위: Vocabulary (`v0.3.34.44_vocabulary.md`)
- **질문:** 아키텍트는 어떤 언어로 생각하는가?
- **목표:** Survival Audit을 통과한 순수 패턴들을 재료로 삼아 30개의 핵심 용어 선별.

### 5순위: Contract (`v0.3.34.44_contract.md`)
- **질문:** 용어는 어떤 패턴으로 정의되는가?
- **목표:** `Vocabulary = Pattern 조합` 의 맵핑 공식 확립. 왜 저장해야 하는가에 대한 계약적 증명.

### 6순위: Vocabulary Dependency Audit (`v0.3.34.44_vocabulary_audit.md`) - 🌟 NEW Phase 4.5
- **질문:** 이 용어들은 정말로 독립적인 개념(Archetype)인가?
- **목표:** Contract에서 증명된 용어들이 사실상 동일한 패턴 조합의 포장지(Alias)에 불과한지 교차 검증하고, 진단 언어의 순도를 높인다.

### 7순위: Question Catalog (`v0.3.34.44_question_catalog.md`) - 🌟 44의 최종 산출물
- **질문:** 정제된 어휘(Archetype)들을 조합하면, SYNAPSE는 현재 어떤 질문에 완벽하게 답할 수 있는가?
- **목표:** 막연한 질문 리스트가 아닌, 우리가 검증을 끝낸 `Knowledge`와 `Cache`에 기반해 100% 논리적으로 방어할 수 있는 "현재 대답 가능한 질문들"을 카탈로그화하여 마일스톤을 닫는다.

## 🎯 Phase 8: Question Distinctness Audit (질문 독립성 검사)
마지막으로 "11개의 질문이 서로 독립적인가?"를 실제 데이터를 통해 시뮬레이션(`v0.3.34.44_question_distinctness_audit.md`)한 결과, 충격적이고 중요한 사실이 밝혀졌습니다. 

이 현상은 **Question Collapse(질문의 붕괴)**가 아니라 **Pattern Collapse(패턴의 붕괴)**입니다.
질문은 잘못되지 않았으나, 우리가 보유한 `Pattern Set`이 오직 '구조적 의존성' 하나뿐이기에, `Domain Core`(도메인적으로 중요한 것)를 찾든 `System Dominator`(시스템 통제권자)를 찾든 결국 **"크고 많이 연결된 모듈"**이라는 동일한 답으로 수렴해버린 것입니다.

## 📝 맺음말 (진단 언어 엔진의 한계 실측과 도약)

0.3.34.44 마일스톤의 가장 큰 성과는 "우리는 뭘 모르는지 몰랐다"는 최초의 무지 상태에서 벗어나, **"우리는 왜 이 질문들에 다르게 대답할 수 없는가"**를 설명할 수 있게 된 것입니다.

질문이 붕괴(Collapse)된 것이 아닙니다. **대상을 측정할 좌표축(Dimension)이 부족했던 것**입니다.
현재 SYNAPSE가 쥔 `Structure Pattern`이라는 단일 축으로는 11개의 질문이 결국 **Core와 Blast라는 2차원 평면에만 투영**되어 버립니다. 하지만 이는 실패가 아니라, Coverage Audit(우리가 무엇을 측정하지 못하는가)을 코딩 전에 완벽하게 실측해 낸 쾌거입니다.

SYNAPSE는 이제 **"무엇을 물을 수 있는가"보다 "왜 질문들이 같은 답으로 수렴하는가"를 인지하게 되었고, 그 원인이 측정 좌표축의 결핍이라는 것까지 완전히 증명한 상태**입니다.
이로써 **44 마일스톤은 더 이상 할 일이 없으므로(No further action required) 성공적으로 닫힙니다.**

다음 **45 마일스톤의 진짜 목표는 "Question Distinctness Recovery (좌표축 확장을 통한 질문 독립성 회복)"**입니다.
`Ownership`(누가 소유하는가), `Churn`(어디가 요동치는가), `Runtime`(어디가 뜨거운가) 좌표축을 추가하여, 붕괴되었던 11개의 질문을 다차원 공간에 다시 흩뿌려 진짜 답을 찾아낼 것입니다!
