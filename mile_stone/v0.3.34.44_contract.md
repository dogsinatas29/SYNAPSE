# 🚀 SYNAPSE Diagnostic Contract (Phase 4)

## 📌 개요
이 문서는 Phase 3 (Vocabulary)에서 증명 가능하다고 판정된 10개의 핵심 아키텍처 용어를 바탕으로, 각 용어가 성립하기 위해 **반드시 요구되는(Required)** 필수 패턴 조합식(Contract Formula)을 정의합니다.

이 계약(Contract)이 확립됨으로써, "왜 특정 패턴(`Blast Radius`, `SCC` 등)을 임시 메모리에서 버리지 않고 Persistence Layer에 영구 보존해야 하는가?"에 대한 아키텍처적 당위성이 증명됩니다.

---

## ⚖️ 공식 계약 명세서 (Contract Specifications)

### 1. Domain Core (도메인 코어)
- **정의:** 시스템이 가장 강하게 의존하고 보호받아야 하는 핵심 책임 영역.
- **필수 패턴 (Required):**
  - `Fan-In`: 집중된 의존성 증명
  - `Blast Radius`: 수정 시 파급력 증명
  - `Cohesion`: 단단한 내부 결속력 증명
- **계약식 (Formula):** `High Fan-In` AND `High Blast Radius` AND `High Cohesion`

### 2. Change Amplifier (변경 증폭기)
- **정의:** 작은 변경만으로도 시스템 전체에 연쇄 파급을 미치는 가장 위험한 영역.
- **필수 패턴 (Required):**
  - `Blast Radius`: 거대한 변경 파급력 증명
  - `Fan-Out`: 외부에 의존하여 취약점을 전파하는 매개체 증명
- **계약식 (Formula):** `High Blast Radius` AND `High Fan-Out`

### 3. Boundary Erosion (경계 침식)
- **정의:** 모듈의 경계가 허물어져 응집도는 낮고 외부 침범만 빈번해진 부패 상태.
- **필수 패턴 (Required):**
  - `Boundary Crossings`: 레이어 및 경계 위반 횟수 증명
  - `Cohesion`: 내부 붕괴 상태 증명
- **계약식 (Formula):** `High Boundary Crossings` AND `Low Cohesion`

### 4. Tangled Core (뒤엉킨 코어)
- **정의:** 중심부에 얽힌 강결합 순환 의존성으로 인해 분리나 모듈화가 불가능해진 덩어리.
- **필수 패턴 (Required):**
  - `Fan-In`: 중심부임을 증명
  - `Cycle Participation (SCC)`: 순환 참조 궤도에 갇혀있음을 증명
- **계약식 (Formula):** `High Fan-In` AND `High Cycle Participation`

### 5. System Dominator (시스템 지배자)
- **정의:** 거대한 덩치와 파급력으로 시스템 전체의 흐름을 중앙 통제하는 모듈.
- **필수 패턴 (Required):**
  - `Size`: 비대한 덩치 증명
  - `Fan-In`: 중앙 통제력 증명
  - `Blast Radius`: 통제권의 파급력 증명
- **계약식 (Formula):** `Large Size` AND `High Fan-In` AND `High Blast Radius`

### 6. God Module (신 모듈)
- **정의:** 하나의 모듈이 너무 많은 책임을 지고 외부에 문어발식으로 의존하는 안티패턴.
- **필수 패턴 (Required):**
  - `Size`: 거대함 증명
  - `Fan-Out`: 문어발식 외부 의존 증명
  - `Cohesion`: 산만한 책임(낮은 응집도) 증명
- **계약식 (Formula):** `Large Size` AND `High Fan-Out` AND `Low Cohesion`

### 7. Stable Foundation (안정된 기반)
- **정의:** 외부 의존성이 전혀 없으면서 수많은 다른 모듈들이 안심하고 의존하는 근간.
- **필수 패턴 (Required):**
  - `Fan-In`: 기반으로서의 사용도 증명
  - `Fan-Out`: 외부로 뻗어나가는 불안정성이 없음을 증명
  - `Cycle Participation (SCC)`: 순환 고리에 빠지지 않은 청정 구역임을 증명
- **계약식 (Formula):** `High Fan-In` AND `Zero Fan-Out` AND `Zero Cycle Participation`

### 8. Architectural Debt (아키텍처 부채)
- **정의:** 당장 청산(리팩토링)하지 않으면 시스템이 무너지는 구조적 지뢰밭.
- **필수 패턴 (Required):**
  - `Boundary Crossings`: 구조적 규칙 위반 증명
  - `Cycle Participation`: 심각한 결합 결함 증명
  - `Cohesion`: 내부 복잡도 폭발 증명
- **계약식 (Formula):** `High Boundary Crossings` AND `High Cycle Participation` AND `Low Cohesion`

### 9. Knowledge Gateway (지식 관문)
- **정의:** 정보가 들어오고 나가는 트래픽 허브.
- **필수 패턴 (Required):**
  - `Fan-In`: 유입량 증명
  - `Fan-Out`: 유출량 증명
  - `Boundary Crossings`: 경계를 넘나드는 다리(Bridge) 역할 증명
- **계약식 (Formula):** `High Fan-In` AND `High Fan-Out` AND `High Boundary Crossings`

### 10. Abandoned Island (고립된 섬)
- **정의:** 아무도 의존하지 않으며 파급력도 제로인 데드코드(Dead Code) 의심 영역.
- **필수 패턴 (Required):**
  - `Fan-In`: 호출되지 않음 증명
  - `Blast Radius`: 영향력 제로 증명
- **계약식 (Formula):** `Zero Fan-In` AND `Zero Blast Radius`

## 🎯 패턴 가치 검증 결론 (The Value Verification)

이 10대 계약서를 완성함으로써, Phase 2.5(Survival Audit)에서 KEEP 판정을 받았던 패턴들이 **실제로 얼마나 많이 계약에 차출되는지(Usage Frequency)**가 명확해졌습니다.

| Pattern | 사용된 Contract 수 | 1차 Persistence 우선순위 |
| :--- | :---: | :---: |
| **Fan-In** | 7개 | 🌟 P0 (이미 저장됨) |
| **Blast Radius** | 5개 | 🚨 **P0 (반드시 구출 1순위)** |
| **Cohesion** | 5개 | 🌟 P0 (이미 저장됨) |
| **Fan-Out** | 4개 | 🌟 P0 (이미 저장됨) |
| **Cycle Participation** | 3개 | 🚨 **P0 (반드시 구출 2순위)** |
| **Boundary Crossings** | 3개 | 🚨 **P0 (반드시 구출 3순위)** |
| **Size** | 2개 | 🌟 P0 (이미 저장됨) |

**결론:**
`Blast Radius`, `Cycle Participation`, `Boundary Crossings` 이 세 가지 패턴은 **10대 핵심 용어 중 절반 이상의 계약을 지탱하는 가장 치명적인 인프라**입니다. 이들이 Memory 상에서 버려진다면 SYNAPSE는 절반의 단어도 구사할 수 없습니다.

따라서 차후 진행될 Phase 6 (Persistence Audit)에서 이 3개의 패턴을 `Graph JSON`으로 구출하는 것이 가장 시급한 아키텍처적 과제임이 이 계약서를 통해 최종 승인되었습니다.
