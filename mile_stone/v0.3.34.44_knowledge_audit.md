# 🚀 SYNAPSE Knowledge vs Cache Audit (Phase 6.5)

## 📌 개요
우리는 앞선 Phase 6(Persistence Audit)에서 `Blast Radius`, `SCC`, `Boundary Crossings`를 Evidence(근거) 형태로 `project_state.json`에 저장해야 한다고 결론지었습니다. 

하지만 이 문서는 그 결론을 뒤집는 가장 근본적인 철학적 질문을 던집니다.
**"우리가 영구 보존하려는 그것들은 잃어버리면 영원히 복구할 수 없는 진짜 지식(Knowledge)인가, 아니면 언제든 소스 코드(그래프)만 있으면 다시 똑같이 계산해 낼 수 있는 캐시(Cache)에 불과한가?"**

SYNAPSE의 진정한 목적은 아키텍처를 압축하여 보여주는 것(Visual Architecture Engine)이며, 파일 크기 비대화를 감수하면서까지 Cache를 Knowledge인 것처럼 속여 저장하는 것을 배격합니다.

---

## ⚖️ 지식(Knowledge) 판별 감사 (Audit)

판별 기준은 단 하나입니다: **"그래프 구조(Source Code)만으로 100% 동일하게 재생성할 수 있는가?"**

| 데이터 유형 | 재생성 가능 여부 | 판정 | 이유 |
| :--- | :---: | :---: | :--- |
| **Fan-In / Fan-Out** | YES | 🟡 **Cache** | 그래프 엣지만 세면 언제든 동일하게 복원됨 |
| **SCC (Cycle Members)** | YES | 🟡 **Cache** | Tarjan 알고리즘만 다시 돌리면 완벽히 복원됨 |
| **Blast Radius (Affected Nodes)** | YES | 🟡 **Cache** | 하향식 전파 탐색(Traversal)만 다시 돌리면 완벽히 복원됨 |
| **Boundary Crossings (Violations)** | YES | 🟡 **Cache** | 룰 엔진과 그래프가 있으면 언제든 복원됨 |
| **Layer Assignment (계층 할당)** | NO | 🟢 **Knowledge** | "이 폴더가 Presentation 계층이다"라는 사실은 코드에 명시되어 있지 않은 **인간의 맥락(Context)** 임 |
| **Rule Definition (도메인 룰)** | NO | 🟢 **Knowledge** | "UI는 DB를 볼 수 없다"는 아키텍트가 정의한 **Source of Truth** 임 |
| **Vocabulary Mapping (용어 맵핑)** | NO | 🟢 **Knowledge** | "Blast Radius가 높은 곳이 Change Amplifier다"라는 **진단 언어적 약속** 임 |

---

## 🎯 감사 결론: SYNAPSE의 진짜 Source of Truth

위 판정 결과, 충격적인 사실이 드러납니다.
그토록 중요하게 다뤘던 **`Blast Radius`, `SCC`, `Boundary Crossings`는 아무리 저장 비용이 비싸고 무효화 반경이 넓다 한들 본질적으로는 'Cache(캐시)'**입니다. 날아가도 시간만 주면 다시 복구할 수 있습니다. 

반면, `Rule`, `Layer`, `Vocabulary`는 파일이 날아가면 시스템이 절대 스스로 추론할 수 없는 진짜 **'Knowledge(지식)'**입니다. 

따라서 SYNAPSE의 `project_state.json` (Persistence Layer) 설계 철학은 다음과 같이 재정의되어야 합니다.

1. **Knowledge는 절대적으로 보호한다:** 
   - 도메인 룰, 계층 정의, 수동으로 맵핑한 태그 등은 유실되지 않도록 최우선으로 영구 보존(Persist)한다.
2. **Cache는 성능을 위해 '선택적으로' 저장할 뿐이다:** 
   - `Blast Radius`나 `SCC`를 저장하는 이유는 그것이 '지식'이라서가 아니라, 단지 **'렌더링 속도 방어(Optimization)'**를 위해서다.
3. **최종 목표는 압축(Compression)이다:** 
   - 아키텍트는 "Blast Radius = 52"나 "SCC 궤도 멤버"라는 날것의 데이터를 보고 싶은 것이 아닙니다. 
   - 그들은 **"이 파일을 건드리면 결제 계층 전체가 영향을 받는다"**라는 압축된 형태의 지식을 원합니다. 

이로써 0.3.34.44 마일스톤이 도달해야 했던 진정한 결론이 내려졌습니다.
우리는 "무엇을 계산할 수 있는가(Pattern Foundation)"를 완벽히 정립했으며, 이제 다음 마일스톤(또는 엔진)의 목표는 **이 패턴들을 바탕으로 아키텍처를 시각적으로 압축(Pattern ➡️ Vocabulary ➡️ Compression)하여 사용자에게 직관적으로 보여주는 Visual Architecture Engine**으로 진화하는 것입니다.
