# 🚀 SYNAPSE Pattern Survival Audit (Phase 2.5)

## 📌 개요
"버려지는 정보를 정말로 모두 영구 보존(Persist)해야 하는가?"에 대한 답을 찾는 감사(Audit) 문서입니다.
`project_state.json`의 비대화를 방지하고, UI를 위한 휴리스틱(Heuristics)이나 완벽히 중복되는 Alias(별칭) 패턴들이 엔진 계약(Engine Contract)으로 굳어지는 것을 막기 위해 모든 패턴을 4가지(`KEEP`, `ALIAS`, `DERIVED`, `DROP CANDIDATE`) 생존 등급으로 분류합니다.

---

## ⚖️ Survival Audit Table

| Pattern | Persist? (생존 여부) | Reason (사유) |
| :--- | :--- | :--- |
| **Blast Radius** | ✅ **KEEP** | `Change Amplifier`, `Critical Risk`, `Simulation`의 근간이 되는 핵심 전파 영향도. 계산 비용이 높으므로 리포트 이후 소멸(Drop)시키지 않고 반드시 저장소로 끌어내려야 함. |
| **Authority Reach** | 🚫 **ALIAS** | `Blast Radius`와 100% 동일한 수치이나, 특정 모듈(`RiskVectorBuilder`)에서 이름표만 바꿔 쓴 별칭(Alias). 별도 저장할 필요 없으며, 엔진에서 공식 퇴출(또는 `Blast Radius`로 치환) 권장. |
| **Control Score** | 🔄 **DERIVED** | `Fan-In × Size`로 도출되는 온보딩 리포트용 UI 휴리스틱. 재료가 되는 `Fan-In`과 `Size`가 이미 저장되므로, 이를 굳이 JSON에 저장할 가치가 없음. 이후 Vocabulary 또는 Question 레이어에서 실시간 연산식(Formula)으로 빼는 것이 타당. |
| **Cycle Participation (SCC)** | ✅ **KEEP** | 강한 결합(Tight Coupling) 및 아키텍처 부패를 감지하는 데 필수. 한 번 계산된 SCC 멤버십은 반드시 보존되어야 함. |
| **Boundary Crossings** | ✅ **KEEP** | 모듈 간 침범(Boundary Erosion)을 측정하는 핵심 재료. |
| **Concentration (집중도)** | 🗑️ **DROP CANDIDATE** | 계산은 하고 저장도 되지만, 후속 리포트나 분석에서 실효성 있게 사용된 이력이 없음. 당장 지우지는 않더라도 영구 보존 리스트에서 제외를 검토. |
| **Fan-In / Fan-Out / Size** | ✅ **KEEP** | 파이프라인의 기초 Aggregate 단위. |
| **Cohesion (응집도)** | ✅ **KEEP** | 내부 결속력을 나타내는 핵심 지표. 이미 저장되고 있음. |

## 🎯 감사 결론 및 설계 결정 (Architectural Decisions)

1. **저장소 수술 명단 확정**
   - 🚨 `Blast Radius`, `Cycle Participation (SCC)`, `Boundary Crossings` 세 가지는 당장 Persistence Layer로 내려서 Graph JSON에 보존되도록 파이프라인을 수정해야 합니다. 
   - ❌ `Authority Reach`는 독립적인 패턴 자격을 박탈합니다.
   - ❌ `Control Score`는 패턴이 아닌 단순 연산식(Contract Formula)으로 강등시킵니다.

2. **Vocabulary의 순도 확보**
   - 앞으로 정의할 30개의 `Vocabulary`는 위에서 **KEEP** 판정을 받은 순수 패턴(Pure Patterns)들만을 재료로 조립되어야 합니다.
   - 예: `Dominator` 어휘를 정의할 때, 허상이었던 `Control Score`를 쓰지 않고 명시적으로 `High Fan-In` + `Large Size` 계약식으로 정의합니다.
