# 🚀 SYNAPSE Persistence Audit (Phase 6)

## 📌 개요
단순히 "어떤 값을 저장할 것인가"를 논의하는 구현 문서가 아닙니다. 
우리는 지금까지 원시 패턴(Raw Pattern)이 분석 패턴(Analytical Pattern)을 거쳐 진단 어휘(Vocabulary)로 승격되는 전체 파이프라인을 증명했습니다. 

이 문서는 가장 비싼 연산인 **`Blast Radius`, `SCC`, `Boundary Crossings` 세 가지 Tier 1 분석 패턴을 어떤 형태로(Shape) 저장해야 "숫자(Value)가 아닌 근거(Evidence)"를 영구 보존하여 SYNAPSE Knowledge Model을 진정으로 확립할 수 있는지**를 감사(Audit)합니다.

---

## ⚖️ Audit 1: 생성 비용 (Generation Cost) 분석
"매번 재계산하는 것보다 한 번 연산 후 저장하는 것이 압도적으로 싼가?"를 묻습니다.

| Pattern | 시간 복잡도 | 생성 비용 | 저장 효율성 |
| :--- | :---: | :--- | :--- |
| **Fan-In / Fan-Out** | O(V+E) | 낮음. AST 파싱 시 기본 획득 | 이미 저장 중 |
| **Boundary Crossings** | O(E) | 낮음~중간. 엣지를 필터링하는 룰 엔진 통과 | 높음 |
| **SCC (Cycle Participation)** | O(V+E) | 중간. Tarjan 등 DFS 기반 전역 탐색 필요 | 높음 (그래프가 클수록 이득) |
| **Blast Radius** | O(N * (V+E)) | **매우 높음.** 모든 노드에 대해 N-Depth 전파 시뮬레이션 필요 | **매우 높음 (필수)** |

**결론:** `Blast Radius`와 `SCC`는 렌더링 루프나 질의 타임에 실시간으로 돌리기에는 비용이 너무 큽니다. 이들을 1회 연산 후 `project_state.json`에 캐싱하는 것은 성능 방어를 위한 필수 선택입니다.

---

## ⚡ Audit 2: 변경 민감도 (Invalidation Sensitivity)
"사용자가 파일 한 줄을 수정하면 저장된 값이 얼마나 파괴되는가?"를 묻습니다. 이를 통해 전역 재계산(Full Recalculation)인지 증분 캐시(Incremental Cache)인지 결정합니다.

| Pattern | 민감도 (Sensitivity) | 무효화 반경 (Invalidation Radius) |
| :--- | :--- | :--- |
| **Boundary Crossings** | 🟢 Local (낮음) | 수정된 노드와 그 이웃 간의 엣지 룰만 재검사 |
| **SCC (Cycle)** | 🔴 Global (매우 높음) | 엣지 하나가 추가/삭제되면 거대한 순환 고리가 새로 합쳐지거나 깨질 수 있음 |
| **Blast Radius** | 🟠 Cascading (높음) | 최하단 노드 1개가 수정되면, 그 노드를 의존하는 상위 N-Depth 노드들의 파급력 수치 전체가 도미노처럼 재계산되어야 함 |

**결론:** 
- `Boundary Crossings`는 증분(Incremental) 업데이트가 가능합니다.
- 그러나 `Blast Radius`와 `SCC`는 무효화 반경이 너무 넓어 **배치 처리(Batch Processing) 혹은 전체 백그라운드 재계산(Full Traversal)** 전략이 더 안전합니다.

## 🧬 Audit 3: 저장 형태 (Storage Shape - Evidence First)
"단순한 숫자(Value)를 저장할 것인가, 아니면 그 숫자가 도출된 증거(Evidence)를 저장할 것인가?"

**SYNAPSE의 철학은 `Evidence First`입니다.** UI에서 텍스트로 보여주기만 할 것이라면 숫자로 족하지만, 캔버스 엔진(Canvas Engine)이 시각적으로 이를 렌더링하고, 분석 엔진(Insight Engine)이 다른 패턴과 결합하려면 반드시 추적 가능한 '근거'가 보존되어야 합니다.

### ❌ Bad Shape (Value Only)
```json
{
  "nodeId": "authService",
  "blastRadius": 52,
  "isInCycle": true,
  "boundaryViolations": 3
}
```
*문제점: 52라는 숫자가 어디서 왔는지, 어떤 사이클에 묶여 있는지, 어떤 경계를 깼는지 설명할 수 없습니다.*

### ✅ Good Shape (Evidence First)
```json
{
  "nodeId": "authService",
  "analyticalPatterns": {
    "blastRadius": {
      "score": 52,
      "affectedNodes": ["userController", "loginView", "..."] // 파급이 도달하는 증거
    },
    "scc": {
      "cycleId": "scc-001", // 어느 사이클 궤도에 묶여 있는지 식별
      "members": ["authService", "tokenManager", "dbConnection"] // 동료 증거
    },
    "boundary": {
      "violations": [
        { "edgeId": "edge-09", "rule": "UI cannot depend on DB" } // 경계 위반 증거
      ]
    }
  }
}
```

## 🎯 감사 결론 (Final Conclusion)

**"SYNAPSE Knowledge Model의 공식화"**
1. **Tier 1 패턴들은 단지 '숫자'가 아닙니다.** 이들은 `affectedNodes`, `cycleId`, `violations` 라는 명확한 물증(Evidence)을 가지고 저장되어야 합니다.
2. 이 형태로 저장됨으로써, 단순 텍스트 리포트가 아니라 **캔버스 UI 상에서 "Blast Radius 노드들을 하이라이팅"하거나 "SCC 멤버들을 한 클러스터로 시각화"**하는 것이 가능해집니다.
3. 생성 비용(Cost)을 고려할 때 이 데이터를 파일(JSON)로 저장하는 것은 정당하며, 변경 민감도(Invalidation)를 고려할 때 무효화 로직은 매우 신중하게 설계되어야 합니다.

이로써, `Blast Radius`, `SCC`, `Boundary Crossings`를 영구 저장소에 안착시키는 **구현 설계 단계로 진입할 수 있는 최종 아키텍처 라이센스(License)**가 완벽히 발급되었습니다.
