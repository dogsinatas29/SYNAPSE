# 🚀 SYNAPSE Diagnostic Vocabulary (Phase 3)

## 📌 개요
단순한 용어집(Glossary)이 아니라, Phase 2.5 `Survival Audit`에서 살아남은 순수 패턴(KEEP)들만을 재료로 사용하여 아키텍트들의 **30대 핵심 용어를 과연 몇 개나 수학적으로 증명해낼 수 있는지**를 테스트하는 검증 문서입니다.

이 작업을 통해 "지금 우리에게 진짜 부족한 패턴이 무엇인가?"라는 질문에 대한 답이 자연스럽게 도출됩니다.

---

## 🧬 재료 창고 (Available KEEP Patterns)
오직 아래의 패턴 조합으로만 용어를 증명해야 합니다.
- **Size / Fan-In / Fan-Out / Internal Edges**
- **Cohesion**
- **Blast Radius**
- **Cycle Participation (SCC)**
- **Boundary Crossings**

---

## 🟢 증명 가능한 용어 (Provable Terms)
현재 확보된 패턴만으로 완벽하게 계약(Contract)을 체결할 수 있는 핵심 어휘들입니다.

### 1. Domain Core (도메인 코어)
- **정의:** 시스템이 가장 강하게 의존하고 보호받아야 하는 핵심 영역
- **필요 패턴:** `Fan-In`, `Blast Radius`, `Cohesion`
- **계약식:** `High Fan-In` + `High Blast Radius` + `High Cohesion`
- **증명 여부:** ✅ **Provable**

### 2. Change Amplifier (변경 증폭기)
- **정의:** 작은 변경만으로도 시스템 전체에 파급력을 미치는 위험 모듈
- **필요 패턴:** `Blast Radius`, `Fan-Out`
- **계약식:** `High Blast Radius` + `High Fan-Out`
- **증명 여부:** ✅ **Provable**

### 3. Boundary Erosion (경계 침식)
- **정의:** 모듈의 경계가 무너져 내부 결속은 약해지고 외부 침범이 빈번한 상태
- **필요 패턴:** `Boundary Crossings`, `Cohesion`
- **계약식:** `High Boundary Crossings` + `Low Cohesion`
- **증명 여부:** ✅ **Provable**

### 4. Tangled Core (뒤엉킨 코어)
- **정의:** 중심부에 얽힌 순환 의존성으로 인해 분리가 불가능해진 덩어리
- **필요 패턴:** `Fan-In`, `Cycle Participation`
- **계약식:** `High Fan-In` + `High Cycle Participation`
- **증명 여부:** ✅ **Provable**

### 5. System Dominator (시스템 지배자)
- **정의:** 거대한 덩치와 파급력으로 시스템 전체의 흐름을 통제하는 모듈
- **필요 패턴:** `Size`, `Fan-In`, `Blast Radius`
- **계약식:** `Large Size` + `High Fan-In` + `High Blast Radius`
- **증명 여부:** ✅ **Provable**

### 6. God Module (신 모듈)
- **정의:** 모든 일을 다 하려고 하며, 외부에 과도하게 의존하고 덩치가 비정상적으로 큰 덩어리
- **필요 패턴:** `Size`, `Fan-Out`, `Cohesion`
- **계약식:** `Large Size` + `High Fan-Out` + `Low Cohesion`
- **증명 여부:** ✅ **Provable**

### 7. Stable Foundation (안정된 기반)
- **정의:** 변경될 확률이 적고 많은 모듈이 신뢰하고 의존하는 근간
- **필요 패턴:** `Fan-In`, `Fan-Out`, `Cycle Participation`
- **계약식:** `High Fan-In` + `Zero Fan-Out` + `Zero Cycle Participation`
- **증명 여부:** ✅ **Provable**

### 8. Architectural Debt (아키텍처 부채)
- **정의:** 경계를 무시하고 순환 참조를 일으켜 즉각적인 청산이 필요한 위험군
- **필요 패턴:** `Boundary Crossings`, `Cycle Participation`, `Cohesion`
- **계약식:** `High Boundary Crossings` + `High Cycle Participation` + `Low Cohesion`
- **증명 여부:** ✅ **Provable**

### 9. Knowledge Gateway (지식 관문)
- **정의:** 여러 모듈의 지식이 교차하며 중계기 역할을 하는 허브
- **필요 패턴:** `Fan-In`, `Fan-Out`, `Boundary Crossings`
- **계약식:** `High Fan-In` + `High Fan-Out` + `High Boundary Crossings`
- **증명 여부:** ✅ **Provable**

### 10. Abandoned Island (고립된 섬)
- **정의:** 아무도 의존하지 않고, 파급력도 없어 데드코드(Dead Code)로 의심되는 영역
- **필요 패턴:** `Fan-In`, `Blast Radius`
- **계약식:** `Zero Fan-In` + `Zero Blast Radius`
- **증명 여부:** ✅ **Provable**

## 🔴 증명 불가 용어 (Unprovable Terms: 패턴 부족)
아키텍처 진단에 필수적인 용어이나, 현재 SYNAPSE가 해당하는 Raw/Aggregate 패턴을 획득(Scan)하지 못해 정의할 수 없는 어휘들입니다.

### 11. Extension Point (확장 지점)
- **정의:** 인터페이스나 추상 클래스를 통해 다형성이 뻗어나가는 플러그인 경계
- **필요 패턴:** `Interface Count`, `Abstract Class Inheritance`, `Polymorphic Reach`
- **증명 여부:** ❌ **Unprovable** (SYNAPSE에 현재 상속/인터페이스 집계 패턴이 부재함)

### 12. Knowledge Bottleneck / Ownership Risk (지식 병목)
- **정의:** 특정 개발자 한 명에게만 지식이 독점되어 퇴사 시 버스 팩터(Bus Factor)가 터지는 구역
- **필요 패턴:** `Git Blame Authors`, `Commit Frequency`, `Code Ownership`
- **증명 여부:** ❌ **Unprovable** (Git Metadata 패턴이 부재함)

### 13. Test Blind Spot (테스트 사각지대)
- **정의:** 파급력(Blast Radius)은 매우 높은데 테스트 코드가 덮어주지 못하는 지뢰밭
- **필요 패턴:** `Blast Radius` (보유), `Test Coverage`, `Test File Ratio`
- **증명 여부:** ❌ **Unprovable** (테스트 검증 패턴이 부재함)

### 14. High Churn Component (격동의 컴포넌트)
- **정의:** 코드가 끊임없이 수정되며 안정화되지 못한 기술 부채 생산기지
- **필요 패턴:** `Git Commit Frequency`, `PR Churn Rate`
- **증명 여부:** ❌ **Unprovable**

### 15. Over-engineered Abstraction (과잉 추상화)
- **정의:** 구현체는 하나뿐인데 불필요하게 겹겹이 인터페이스를 두른 빈 껍데기
- **필요 패턴:** `Interface Count`, `Implementation Ratio`
- **증명 여부:** ❌ **Unprovable**

## 🎯 설계 결론 (Design Conclusion)

1. **현재 아키텍처의 한계와 성과**
   - 현재 살아남은 KEEP 패턴만으로도 의존성, 파급력, 구조적 부패를 측정하는 **10대 핵심 어휘(Provable)**를 완벽하게 정의할 수 있었습니다.
   - 단방향/양방향 의존성 구조에 대한 진단력은 이미 훌륭합니다.

2. **부족한 패턴의 발굴 (The Missing Links)**
   - 반면 다형성(Polymorphism), 소유권(Git Ownership), 품질(Test Coverage), 변경 빈도(Churn)와 관련된 용어는 철저하게 0개 증명되었습니다.
   - **이로써 향후 어떤 종류의 Scanner(패턴 수집기)를 추가 개발해야 하는지가 명확하게 증명되었습니다.**

이 문서를 통해 `Phase 4: Contract (계약 체결)`로 넘어갈 10개의 1차 Vocabulary가 성공적으로 확정되었습니다.
