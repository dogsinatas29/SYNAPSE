# SYNAPSE v0.3.34.45 Mission Contract
## Question-Driven Architecture Diagnostic Platform

# 1. Core Philosophy

SYNAPSE는 코드 분석기가 아니다.

SYNAPSE는 사용자가 정의한 질문(Question)에 대해,
아키텍처 용어(Vocabulary)를 사용하여,
패턴(Pattern)을 발견하고,
보고서(Report)로 설명하는 Architecture Diagnostic Platform 이다.

# 4-1. Detector Contract (새로 확립된 규칙)

이번 확장을 통해 확립된 Detector 계층의 엄격한 계약(Contract)입니다.

1. **단일 책임 원칙 (SRP):** Detector는 오직 "이 노드가 해당 패턴일 가능성이 얼마나 되는가(confidence)?" 만을 평가합니다.
2. **Top-N 금지:** 상위 10개, 50개 등 개수를 자르거나 정렬(Ranking), 페이지네이션 하는 것은 100% Report 계층의 책임입니다. Detector 내부에 하드코딩해서는 안 됩니다.
3. **Candidate 집합 반환:** 10만 개가 넘는 전체 노드를 덤프(Dump)하는 것을 막기 위해, Detector는 P50(중앙값) 이상 등 유의미한 점수를 획득한 노드들만을 컷오프하여 `isCandidate: true` 속성과 함께 반환합니다.

```json
{
  "patternId": "system_core",
  "targetId": "src/core/InsightEngine.ts",
  "confidence": 0.91,
  "isCandidate": true,
  "evidence": {
    "fanIn": 83,
    "authorityReach": 0.88
  }
}
```

# 13. Action Plan: Detector Layer Discovery & Pilot Extraction

0.3.34.45 마일스톤의 진짜 첫 목표는 존재하지 않는 JSON 딕셔너리를 만드는 것이 아니라, 리포터(Reporter)와 분석기(Analyzer) 내부에 엉겨 붙어 있는 판정 로직들을 뜯어내어 **독립된 Detector Layer**를 발굴(Discovery)하는 것이다.

단, 한 번에 모든 패턴을 추출하는 위험을 피하기 위해 **가장 순수한 형태의 패턴 하나(Root Entry Point)를 파일럿으로 삼아 "Detector라는 개념 자체가 성립하는가"를 먼저 증명**한다.

## Step 0. Pattern Boundary Audit (추출 가능성 검증)

각 패턴의 현재 로직이 순수한 "검출(Detection)"인지, 아니면 정렬과 Top-N을 포함한 "보고서 휴리스틱(Report Heuristic)"인지 경계를 점검한다. (`Root Entry Point`는 명확한 조건식을 가져 1차 타겟으로 적합함을 확인)

## Step 1. Pilot Extraction: Root Entry Point

가장 단순하고 명확한 `Root Entry Point`만을 떼어내어, `PatternDetector`라는 개념 모델이 실제 코드에 들어맞는지(Fit) 증명한다.

- `src/core/analysis/patterns/PatternDetector.ts`: `interface PatternDetector` 정의 (메서드: `detect(graph: Graph, metrics: Metrics): PatternFinding[]`)
- `EntryPointDetector.ts`: `OnboardingAnalyzer.ts` 내의 판독 로직 이동.
- (참고: `Registry`나 `Factory` 같은 관리 패턴은 파일럿 검증 이후 적합성을 고려하여 도입한다.)

## Step 2. Pilot Validation & Expansion Decision

`EntryPointDetector`가 완벽하게 동작하는지 검증된 이후에만, 비로소 `System Core`, `Change Amplifier`, `Cascade Failure Point`의 추출(Extraction) 및 런타임 딕셔너리(`JSON`) 구축으로 단계를 확장한다.

# 16. Mid-Term Checkpoint & Priority Shift (Question Resolution)

현재까지 `Metric → Detector → Finding` 구조와 파일럿 Detector 4개의 추출은 입증되었다. 하지만 마일스톤 45의 진짜 핵심인 **"Question-Driven Architecture"** 가 아직 작동하지 않는다. 특히 **사용자의 언어(Vocabulary)**와 **엔진의 알고리즘(Pattern)**을 분리하는 방화벽이 누락되어 있어, Open/Protected IP 경계가 무너질 위험이 있다.

따라서 Registry 및 Dictionary 설계나 품질 검증에 앞서, `Question → Vocabulary → Pattern → Detector` 의 완벽한 4단계 파이프라인이 런타임에 단절 없이 해석되는지 먼저 증명해야 한다.

## Step 6-1. Diagnostic Pipeline 파일럿 (Open-Protected Boundary)

## 🚀 Phase 5.5: Structural vs Flow Centrality Test (구조와 흐름 분리 검증)

### 1. Phase 5.5-A 완료 결과 (내적 검증)
- **독립성 입증:** `fanIn`과 `fanOut`은 상관계수 -0.06으로 완전 독립임이 증명됨. 구조적 통제와 흐름 통제는 완전히 다른 현상이다.
- **다중 홉 파급력:** `blastRadius`는 `fanOut`과 강한 상관관계(0.86)를 보이나, 30%의 노드에서 다중 홉(Multi-hop) 연쇄 증폭이라는 고유한 정보를 가짐을 입증.
- **위상(Position)의 중요성:** `GraphModel`은 역할(Model)과 무관하게 위상학적으로 완벽한 구조적 Sink(fanIn 57, fanOut 3)임이 밝혀짐.
- **결론:** 군집(Cluster)이 아닌, 시스템 전체를 지배하는 **거대한 특이점(Outlier)**들이 양 축(Inward, Outward)으로 분리되어 존재한다.

### 2. Phase 5.5-B 최종 실행 계획 (외적 검증)
목표: "소프트웨어 아키텍처에서 fanIn과 fanOut은 서로 독립적인 중심성 축이며, 이 독립성이 프로젝트 규모와 도메인을 넘어 반복되는가?"

가장 과학적인 6단계 관측 순서 (블라인드 테스트 원칙):
1. **Phase 5.5-B-0 (Projection Validation):** 비교 대상(SYNAPSE, VS Code, Linux) 간 Node=File, Edge=Import/Include 단위 통일성 확보.
2. **Phase 5.5-B-2 (Correlation):** `Corr(fanIn, fanOut) ≈ 0` (Pearson 및 Spearman) 독립성이 타 프로젝트에서도 반복되는가 가장 먼저 확인.
3. **Phase 5.5-B-1 (Distribution Shape):** L-shape (Cloud + Long Tail) 형태가 관측되는가.
4. **Phase 5.5-B-3 (Outlier Intensity):** P99/P50 상대 강도 유지 여부 확인.
5. **Phase 5.5-B-4 (Axis Separation):** High In/Low Out 과 Low In/High Out의 직교 분리 재확인.
6. **Phase 5.5-B-5 (Node Observation):** 모든 수치적 보편성이 증명된 후, 비로소 노드 이름을 까보고 아키텍처 역할을 사후 설명(Position → Role).

### 3. 다음 실행 항목
- VS Code 일부(src/vs/base, src/vs/platform 등) 샘플 추출기 작성 (Node=File, Edge=import).
- 추출된 부분 그래프로 Phase 5.5-B-2(Correlation) 확인.

### 4. Phase 5.5-B 추출 프로토콜 보완 (Edge Semantic Equivalence)
- **0순위 규칙 추가 (Edge Semantic Equivalence):** 
  - 추출 방법(AST)보다 중요한 것은 관측 대상의 **의미 일치**이다. 
  - TS의 `import`(모듈 의존성)와 C의 `#include`(전처리 의존성)가 과연 동일한 아키텍처 의존성(Architectural Dependency)을 표현하는가? 이 의미적 동치성이 증명되어야만 Cross-Project 비교가 성립한다.
- **blastRadius 보류 (Phase 5.5-C로 이동):**
  - 현재 목표는 `fanIn`과 `fanOut` 두 축의 독립성 증명에 집중한다. SYNAPSE 외부에서 측정된 적 없는 `blastRadius`는 B 단계에서 완전히 배제한다.

### 6. Phase 5.5-B 추출 프로토콜 확정 (Projection Equivalence)
- **핵심 목표:** 도구(Tool)의 종속을 피하고, 투영 동등성(Projection Equivalence)을 확보한다.
- **프로토콜 명세 (Requirement):**
  1. **AST-level Extraction:** 단순 텍스트 정규식이 아닌 구문 트리 수준에서 명시적 정적 의존성(Explicit Static Dependency)만을 추출한다.
  2. **Internal Resolution:** 추출된 참조 문자열(예: `<linux/sched.h>` 또는 `'vs/base/common/uri'`)을 프로젝트 내부의 물리적 파일 절대 경로로 완벽히 해소(Resolution)해야만 Edge로 인정한다.
  3. **External Pruning:** 해소되지 않는 외부 의존성은 모두 버린다.
- **구현(Implementation) 방침:**
  - 도구 특정 금지: Tree-sitter는 현재의 유력한 후보일 뿐, libclang이나 컴파일러 API 등 무엇을 쓰든 위 요구사항을 만족하고 결과가 같다면 무방하다.
  - 다음 단계: 
    1. TS 추출기 하드코딩 제거 (명령어 인수 기반).
    2. Linux AST 추출 및 Resolution 가능성(POC) 검증 우선 수행.
    3. 동일 밀도의 프로토콜이 양립 가능함이 입증되면 전체 스캔으로 확대.

### 7. Phase B-0.5 프로토콜 스케일 검증 (Protocol Scale Validation)
- **목적:** POC(단일 파일) 성공이 전체 스케일에서의 투영 동등성을 보장하지 않으므로, 대규모 샘플을 통해 해소율(Resolution Rate)을 측정.
- **대상 (Linux):** `kernel/`, `mm/`, `fs/` 서브시스템.
- **평가 기준:** 
  - `Resolved` (내부 맵핑 성공)
  - `External Pruned` (외부 의존성 배제)
  - `Unresolved` (미해소, 에러)
- **Action:** 이 3대 지표를 우선 계측하여 프로토콜의 안정성(Unresolved 비율 극소화)이 확보되었을 때만 상관계수(Phase B-1 ~ B-5) 분석으로 넘어간다.

### 🛠️ Phase B-2 진행 상황: 목표 조정 (Goal Adjustment)
- **명분 변경:** "법칙 증명(Law Validation)" ❌ → "패러다임 교차 반례 탐색(Cross-Paradigm Falsification)" ✅
- **프레임 유지:** "완전 직교", "보편 법칙"과 같은 확정적 어조를 배제하고, "여러 언어/패러다임에서 반복 재현되는 강한 경험적 관찰"이자 "현재까지 반례를 찾지 못해 가설이 지지되고 있는 상태"로 보수적인 학자적 관점을 엄수함.

#### 📌 향후 반례 탐색 우선순위 (Target Priority)
1. **Godot (C++):** 대규모 객체지향 엔진. (현재 가설을 깰 가장 강력한 1순위 후보)
2. **AntennaPod (Java):** 안드로이드 정통 클래스/모듈 기반.
3. **분포 형상 검증 (Distribution Shape):** P99/P50 및 아웃라이어 인텐시티 검증.
4. **Node Observation** (최후 단계)

*주의: 특정 영역(Linux, Rust)에서 관측되는 약한 비선형 구조(dCor ≈ 0.17)에 주목하며 반례를 집중적으로 탐색할 것.*

### 🛠️ Phase B-1 ~ B-3.5: 분포 형상과 꼬리의 중력 검증 계획 (업데이트)

- **연구 목표 수정:** "Gravity Law에 대한 직접적인 증거"라는 확정적 주장을 배제하고, **"Core Separation이 왜 발생하는지 설명할 수 있는 분포적 특성이 존재하는가?"**를 확인하는 것으로 목표를 재설정합니다.
- **분석 도구 최적화:** Bin 설정에 따라 왜곡될 수 있는 히스토그램보다, 롱테일 비교에 훨씬 안정적인 **CCDF(상보누적분포함수) 및 Log-Log CCDF**를 최우선 시각화 지표로 삼습니다.

#### 📌 분석 우선순위 및 세부 항목
1. **Phase B-1: CCDF & Log-Log CCDF**
   - 5개 프로젝트 전체 노드 대상.
   - fanIn과 fanOut이 각각 어떤 형태의 롱테일을 형성하는지 최우선 검증.
2. **Phase B-3: Outlier Intensity (아웃라이어 강도)**
   - P99 / Median, Top1(Max) / Median, Top10 Mean / Median 측정.
   - 꼬리(특이점)가 일반 노드 대비 몇 배의 질량을 흡수하고 있는지 정량화.
3. **Phase B-3.5: Core Stability (특이점 심도에 따른 분리 가속도)**
   - Top 5% → Top 1% → Top 0.5% → Top 0.1% 로 Cutoff를 내리며 Overlap 변화 관측.
   - "극단적 특이점으로 갈수록 역할 분화가 강화되는가?" 검증.
4. **Phase B-3.25: Asymmetry (양 축의 중력장 비대칭성)**
   - Max fanIn / Max fanOut
   - P99 fanIn / P99 fanOut
   - Median fanIn / Median fanOut
   - 두 축 중 어느 쪽 꼬리가 훨씬 무거운지 비교하여 코어 분리의 원인 단서 확보.
5. **Phase B-4: Node Observation (최후 단계)**
   - 실제 최상위 코어 노드들이 어떤 파일(물리적 실체)인지 정성적 확인.

### 🛠️ Phase B-6: Predictive Power Validation (실용적 예측력 검증)

- **최종 연구 목표의 실용화 전환:** 
  "소프트웨어 아키텍처는 반드시 두 종류의 심장을 가진다"는 철학적 가설을 넘어, **"fanIn Top 집합과 fanOut Top 집합은 아키텍처 역할을 예측하는 실용적 탐침(Probe)으로 작동한다"**는 가설로 진화합니다.
- **아키텍처 탐침 가설 (Architectural Probe Hypothesis):**
  - `fanIn Top N` -> 위험 구역 예측 (수렴 코어: 타입, 모델, 설정, 유틸리티)
  - `fanOut Top N` -> 작업 구역 예측 (발산 코어: 진입점, 부트스트랩, 오케스트레이터, 조립기)

#### 📌 예측력 검증 테스트
1. **Test 1:** fanIn Top 20 리스트만으로 해당 파일들이 시스템의 "위험 구역(Danger Zone)"임을 예측할 수 있는가?
2. **Test 2:** fanOut Top 20 리스트만으로 해당 파일들이 기능 추가 및 변경이 잦은 "작업 구역(Work Zone)"임을 예측할 수 있는가?
3. **Test 3 (Blind Test):** 프로젝트명을 가린 상태에서 파일명만 보고 Sink(수렴)인지 Source(발산)인지 분류할 수 있는가?

이 검증이 성공한다면, SYNAPSE는 단순히 그래프를 그리는 도구를 넘어 **"처음 보는 거대 코드베이스에서도 1초 만에 뼈대와 뇌를 찾아내는 내비게이션"**이라는 거대한 상업적/실용적 가치를 확보하게 됩니다.
