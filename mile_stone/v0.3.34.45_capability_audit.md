# 🔍 v0.3.34.45 Pattern Capability Audit

**작성일:** 2026-09-17
**목표:** 45 마일스톤 계약(Contract)에 명시된 11개의 Pattern이 현재 코드베이스 상에서 실제로 검출(Detect) 가능한 상태인지, 그리고 이를 뒷받침할 Evidence가 확보되어 있는지 검증합니다.

## 📊 Capability Audit 결과 (3-Tier Status Matrix)

현재 코드베이스(`src/core/`)를 전수 조사한 결과, 11개 패턴 중 **독립된 `PatternDetector` 클래스 형태로 완벽하게 분리된 것은 단 하나도 없습니다.** 대신, 로직들이 리포터(Reporter)와 분석기(Analyzer) 내부에 엉겨 붙어 있습니다. 

이를 바탕으로 11개 패턴을 3단계로 분류(Status Matrix)했습니다.

| Pattern | Status | 특징 (증거 및 구현 상태) |
| :--- | :---: | :--- |
| **Root Entry Point** | `Implemented` | 코드 존재, `OnboardingAnalyzer`에서 계산 중, 실제 보고서 사용 |
| **System Core** | `Implemented` | 코드 존재, `InsightEngine`에서 계산 중, 실제 보고서 사용 |
| **Change Amplifier** | `Implemented` | 메트릭 존재(`blastRadius`), 실제 보고서 사용 |
| **Cascade Failure Point** | `Implemented` | 메트릭 존재(`simulation`), 실제 룰 엔진에서 처리 중 |
| **Boundary Fortress** | `Extract Required` | 명시적 Detector는 없으나 `boundaryCrossings`로 재구성 가능 |
| **Boundary Candidate** | `Extract Required` | 후보 판정 로직이 파편화되어 존재, 추출 시 즉시 사용 가능 |
| **Weak Boundary** | `Extract Required` | 기존 결합도 계산 결과(`fanOut` + 외부 연결)로 재구성 가능 |
| **Safe Refactoring Zone** | `Extract Required` | `OnboardingReport` 내 하드코딩(`fanIn == 0`), 추출 필요 |
| **Learning Hub** | `Research` | 이름만 존재, 코드 없음, 증거 없음 |
| **Peripheral Component** | `Research` | 이름만 존재, 코드 없음, 증거 없음 |
| **Architectural Chokepoint** | `Research` | 이름만 존재, 코드 없음, 증거 없음 |

## 🎯 Audit 분석 결론 및 45의 진짜 목표

### 1. Detector Layer의 부재 (The Missing Link)
처음 우리가 상상한 이상적인 구조는 `Question → Vocabulary → Pattern → Detector` 였습니다.
그러나 Audit이 보여준 현실은 **`Question → Vocabulary → Pattern → ??? → Report`** 입니다.
중간에 `Detector Layer`가 통째로 증발해 있고, 리포터가 직접 데이터를 가공하고 있습니다.

### 2. 다음 단계 (Action Plan)
패턴을 삭제(Cut-off)하지 않고, 카탈로그에 `Research` 상태로 남겨둡니다. 45 마일스톤의 진짜 목표는 "JSON 딕셔너리 만들기"에서 **"Detector Layer Discovery & Extraction"**으로 상향 조정됩니다.

1. **Pattern Status Matrix 확정 (완료):** 현재 자산을 `Implemented`, `Extract Required`, `Research`로 정확히 분류.
2. **Detector Extraction:** `Implemented`와 `Extract Required`에 해당하는 판정 로직들을 리포터에서 뜯어내어 독립된 `PatternDetector` 클래스로 조립 및 분리.
3. **Registry 구축:** 분리된 Detector들을 런타임에 엮어주는 `PatternRegistry` 구현.
4. **Dictionary 공식화:** 런타임 실체(Registry)가 확보된 후, 비로소 `questions.json`, `vocabulary.json`, `patterns.json` 작성.
