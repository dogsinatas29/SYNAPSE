## 📅 작업 정보 - **상태:** 🏗️ In-Progress
- **관련 마일스톤:** v0.3.34.45
- **목표:** `fanIn`과 `fanOut` 지표가 과거의 현상을 설명하는 데 그치지 않고, 미래의 유지보수 위험도와 작업 구역을 **사전 예측**할 수 있는지 실증한다. "SYNAPSE가 미지의 코드베이스에서 코드를 읽기 전에 어디가 뼈대이고 제어부이며, 건드리면 크게 터지는지를 예측할 수 있는가?"를 증명하는 것이 최종 목적이다.

## 🧠 상세 설계 및 로직 (검증 우선순위)

가장 핵심적인 검증은 **D-1 → D-2 → E** 3단계입니다. 이 세 가지가 통과하면 SYNAPSE는 단순 관찰 결과를 넘어 실제 "탐침(Probe)"으로 승격됩니다.

### 1순위: Validation D-1 (PostgreSQL 블라인드 테스트)
- **목적:** 완전히 낯선 도메인(DBMS), 언어(C), 보수적 문화의 코드베이스에서 예측력 검증.
- **사전 분류 체계 정의 (사후 해석 차단):**
  - **Structural Core (수렴):** Type Hub, Domain Model, Utility, Configuration
  - **Control Core (발산):** Entry Point, Dispatcher, Orchestrator, Registry
  - **Infrastructure:** Adapter, Driver, External Integration
- **채점 기준 (목표값 사전 고정):**
  - **Exact Match:** 역할 정확히 일치
  - **Partial Match:** 상위 분류(Structural vs Control) 일치
  - **Mismatch:** 완전 오답
  - **강한 성공:** Exact ≥ 60% AND Exact+Partial ≥ 90%
  - **성공:** Exact+Partial ≥ 80%
  - **실패:** Exact+Partial < 70%
- **절차:** PostgreSQL 파싱 (`/home/dogsinatas/다운로드/postgres/synapse_data/project_state.json`) → 지표 추출 → **코드 열기 전 사전 예측 기록** → 실제 코드 열고 대조.

### 2순위: Validation D-2 (Kubernetes 또는 React 블라인드 테스트)
- **목적:** D-1이 C 언어나 모놀리식 생태계만의 특성이 아니라는 것을 증명하기 위해, 완전히 이질적인 언어(Go/JS)와 아키텍처(클라우드 분산 / 프론트엔드)에서 D-1과 동일한 검증 수행.

### 3순위: Validation E (Change Impact / Co-Change Network)
- **목적:** 정적 아키텍처(SYNAPSE)가 진화 아키텍처(Git Evolution)의 미래 변경 영향도를 추정할 수 있는지 입증.
- **방법:** `git log --name-only`를 분석하여 파일 수정 시 동반 수정 파일 평균 개수(Blast Radius) 측정. `uri.ts -> [event.ts, lifecycle.ts...]` 형태의 Co-Change Network 기록.
- **성공 기준:** fanIn 코어 집단이 무작위 집단보다 압도적으로 거대한 동반 수정 파급력을 가짐.

### 4순위: Validation G (Search Compression)
- **목적:** 특정 버그(예: Playback 버그) 과제 부여 시 랜덤 탐색 vs Top 20 탐색 간의 "최초 진입 파일 수, 탐색 단계 수, 도달 시간"을 측정하여, 내비게이션으로서의 객관적 효율성 증명.

### 5순위: Validation A/B (Blind Git Behavior Validation)
- Git 이력을 후행 지표로 활용하되, 사후 해석 방어를 위해 위험도/작업 집중도를 먼저 예측 기록한 뒤 실제 로그 대조.

### 6순위: Validation C (기존 프로젝트 역할 분류 유의성)
- 기존 분석 프로젝트에서 발견된 정성적 역할 예측 적중률이 Random Baseline 대비 통계적 우위를 가짐을 입증.

### 7순위: Validation F (Onboarding Compression)
- 랜덤 100회 샘플링 평균 시스템 이해도 vs Top 20 기반 이해도 비교 (측정 변인 통제가 어려워 최후순위).

## 💡 최종 선언 목표 (D-1, D-2, E 통과 시)
> "fanIn은 구조적 중심성(Structural Centrality)을 탐지하고, fanOut은 제어 중심성(Control Centrality)을 탐지하는 탐침이다. 두 지표는 다양한 코드베이스에서 반복적으로 서로 다른 종류의 핵심 노드를 노출시키며, 변경 영향도와 탐색 우선순위를 결정하는 경험적 휴리스틱으로 활용될 수 있다."
