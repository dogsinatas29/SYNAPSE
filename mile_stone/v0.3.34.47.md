## 🚫 연구 무결성 규칙 (Research Integrity Rules)

이 프로젝트가 "디젤게이트(시험실 조작)"에 빠지지 않기 위해 다음 규칙을 엄격히 준수한다.

### Rule 1. 프로젝트 식별 메타데이터 전면 금지
TopologyClassifier 및 후속 분류 엔진은 프로젝트, 언어, 빌드 시스템, 패키지 관리자, 프레임워크, 벤더를 식별할 수 있는 모든 메타데이터를 절대 사용할 수 없다.
- **금지 예시:** `linux/*`, `postgres*`, `react`, `Cargo.toml`, `go.mod`, `pom.xml`, `package.json`, `Kconfig`, `Kbuild`, `CMakeLists.txt`, `requirements.txt` 등.
- 이러한 정보는 관측 데이터가 아니라 도메인 힌트(Domain Hint)로 간주하여 완전히 배제한다.

### Rule 2. 분류 입력 제한 및 타입 강제 (Type Enforcement)
TopologyClassifier가 사용할 수 있는 최하위 입력은 **Observation Dataset**에 존재하는 위상 수학적 물리량으로만 제한한다.
- **허용:** `fanIn`, `fanOut`, `clusterSize`, `astValidatedEdges` (측정 신뢰도 보조 지표)
- **금지:** `filePath`, `fileName`, `directoryName`, `projectName`, `language`, `extension`
- **기술적 강제 (Enforcement):** 미래의 개발자가 우회하지 못하도록 TopologyClassifier는 Node 객체 전체를 받지 않으며, 오직 `TopologyClassifierInputDTO`만 인자로 받도록 타입 시스템으로 강제한다.

### Rule 3. 블라인드 재현성 원칙
새로운 규칙은 반드시 `node_001`, `node_002` 처럼 **이름이 완전히 제거된 데이터셋**에서도 동일한 결과를 재현해야 한다. 파일명 제거 시 예측 성능이 급락하는 규칙은 Topology Rule로 인정하지 않는다.

### Rule 4. 프로젝트 독립성 검증
어떤 규칙도 "특정 프로젝트(예: Linux)에서만 동작"하면 채택할 수 없다. 최소 3개 이상의 이기종 프로젝트군에서 교차 재현성 검증을 통과해야 한다.

### Rule 5. 명명(Naming)과 분류(Classification) 분리
코어 엔진 내부 로직은 `Class_A`, `Class_B` 형태의 군집(Cluster) 타입만 알아야 한다.
- "Control Singularity"와 같은 의미론적 이름(Semantic Name)은 엔진 내부에 하드코딩되지 않으며, UI/Report 계층에서 붙이는 별칭(Alias)으로만 취급한다.

### Rule 6. Observation Dataset 불변성 (Dataset Immutability)
Observation Dataset은 측정 엔진이 직접 산출한 순수 물리량만 저장할 수 있다. 해석, 점수, 역할, 확률, 분류 결과, 파생 통계(Percentile)도 절대 포함될 수 없다.
- AST 정보는 "이 노드가 Service 객체다"라는 식의 분류 목적(Type B)으로 사용될 수 없으며, 오직 "이 노드의 Edge가 정적 분석으로 97% 확인되었다"는 **측정 신뢰도(Measurement Confidence, Type A)** 지표로만 활용된다.

### Rule 7. LLM 비의존성 검증 (LLM Independence)
어떤 분류 규칙도 "LLM이 그렇게 말했다"는 이유만으로 채택될 수 없다.
- 채택의 유일한 근거는 반드시 Observation Dataset과 Validation Dataset에서 계산 가능한 객관적인 통계값이어야 한다.

### Rule 8. 파생 지표의 투명성 (Feature Provenance)
TopologyClassifier에 입력되는 모든 파생 지표(Feature)는 반드시 Observation Dataset의 순수 물리량으로부터 **직접 계산 가능(Directly Computable)**해야 한다.

### Rule 9. 측정 출처 추적 (Measurement Provenance)
Observation Dataset에 들어갈 수 있는 값은 반드시 SYNAPSE 측정 엔진(또는 결정론적 알고리즘)이 직접 산출한 원시 측정값이어야 한다. Observation 생성 시 `measurementFingerprint`를 포함하여 출처를 증명해야 한다.

### Rule 10. 측정기 진화 격리 (Metric Evolution Lock)
서로 다른 `graphVersion` 및 `measurementFingerprint`(Scanner Config, Cutoff Rules 등 해시값)에서 추출된 관측 데이터는 **동일한 통계 실험(군집화/검증)에 혼합하여 사용할 수 없다.** ValidationEngine 진입 시 fingerprint가 불일치하면 즉시 검증을 중단(`throw Error`)한다.

### Rule 11. 파이프라인 증명 (Pipeline Provenance)
어떤 과정을 거쳐 생성된 데이터인지 메타데이터 수준에서 엄격히 분리해야 한다. "SYNAPSE가 측정한 값"과 "LLM이 해석한 값"이 데이터셋 레벨에서 섞이는 것을 차단한다.

### Rule 12. 검증 독립성 (Validation Independence)
ValidationEngine은 어떠한 판정(`APPROVED`/`REJECTED`)도 내리지 않는 순수 "측정기"여야 한다. ValidationEngine은 군집 실험 결과를 입력받아 재현성과 분포 유사성 수치만 계산하며, 채택 결정은 Alias Registry가 담당한다.

### Rule 13. 해석 전 반증 의무화 (Anti-Hallucination Guardrail)
관측된 현상(예: J=1.0)에 대해 아키텍처적 의미(예: 마이크로 패키지 구조)를 부여하기 전에, 반드시 해당 현상을 기각할 수 있는 기초 통계 감사(Density Audit)를 선행해야 한다.
- **Zero-Degree Audit:** `fanIn == 0` 또는 `fanOut == 0` 비율 측정
- **Tie Density Audit:** 특정 점수에 몰린 노드의 밀집도 측정
- **Graph Coverage Audit:** 전체 노드 대비 엣지 밀도 측정
- **조치:** 위 감사를 통과하지 못한 이상 데이터(예: Zero-Degree 98%) 발견 시, 즉각 해석을 중단(`Interpretation Blocked`)하고 `Graph Quality Warning` 상태로 전환한다. 이후 부트스트랩 불완전성(가설 A), Resolver 결함(가설 B), 관측 모델 한계(가설 C) 등 원인 조사 단계로 진입해야 하며, 원인 규명 전까지는 절대 구조적 특성으로 단정짓지 않는다.



### Rule 14. Data Quality Gate (품질 미달 데이터 해석 영구 금지)
측정된 데이터를 Validation Engine이나 Percentile 통계에 입력하기 전, 반드시 다음 4가지 품질 감사(Quality Audit) 지표를 통과해야 한다. 빈칸(측정되지 않은 품질 지표)이 존재하는 데이터셋에 대해 어떠한 아키텍처적 해석이나 의미 부여도 엄격히 금지된다.
1. **Resolver Accuracy (Parse Capture Rate)**
2. **Path Normalization Rate**
3. **Node Lookup Hit Rate**
4. **Final Edge Capture Rate**

## 🧠 상세 설계 및 로직 (연구 프로토콜)

**가설과 실험, 검증을 완벽히 분리한 6단계 데이터 파이프라인 설계.**

### Step 1. Dataset 1: Raw Observation Dataset (순수 관측)
SYNAPSE가 측정한 순수 원시 물리량(fanIn, fanOut, clusterSize). AST는 측정의 '신뢰도' 보조 지표로만 격하되어 사용된다.
- **포맷 예시:**
  ```json
  {
    "datasetId": "dataset_obs_001",
    "generator": "GraphBuilder",
    "pipeline": "SYNAPSE_GRAPH_PIPELINE",
    "measurementFingerprint": "sha256(resolver_set+cutoff_rules+...)",
    "records": [
      {
        "nodeId": "node_0001",
        "projectId": "proj_linux",
        "metrics": {
          "fanIn": 1147,
          "fanOut": 67,
          "astValidatedEdges": 1100, // 측정 신뢰도용 AST 활용 (Rule 6)
          "regexOnlyEdges": 114
        }
      }
    ]
  }
  ```

### Step 1.5. Dataset 1.5: Feature Engineering Dataset (파생 특성)
Observation 값을 수학적으로 계산한 특성(Percentile, Ratio).

### Step 2. Dataset 2: Identity Vault (아이덴티티 저장소)
원본 `graph_linux.json`과의 맵핑 정보를 숨기는 비밀키 저장소.

### Step 3. Hypothesis & Experiment Dataset (가설 및 실험 데이터셋)
가설(규칙), 실험(실행 방법), 결과(발견된 군집)를 철저히 분리한다.

#### Dataset 3A: Hypothesis (가설)
수학적 규칙(Rule) 그 자체.
- **포맷 예시:**
  ```json
  {
    "hypothesisId": "H001",
    "type": "RULE",
    "condition": "fanInPercentile >= 95 && fanRatio >= 5"
  }
  ```

#### Dataset 3B: Experiment Definition (실험 정의)
가설을 어떤 프로젝트 데이터셋에 어떻게 적용할 것인지 정의한 실행서.
- **포맷 예시:**
  ```json
  {
    "experimentId": "EXP001",
    "targetHypothesisId": "H001",
    "targetDatasetIds": ["proj_linux_feat", "proj_vscode_feat", "proj_godot_feat"]
  }
  ```

#### Dataset 3C: Discovery Result (실험 결과)
실험기(Experiment Runner)가 가설을 데이터셋에 적용하여 실제로 찾아낸 노드들의 묶음(군집).
- **포맷 예시:**
  ```json
  {
    "experimentId": "EXP001",
    "projectId": "proj_linux",
    "discoveredNodes": ["node_001", "node_052", "..."],
    "featureCentroid": { "fanRatio": 5.4, "fanInPercentile": 96.2 }
  }
  ```

### Step 4. Validation & Robustness Dataset (검증 데이터셋)
Dataset 3C에서 찾아낸 군집이 프로젝트 간 얼마나 일치하고 강건한지 측정. (판정 없음)

#### Dataset 4A: Validation Metrics (순수 검증)
ValidationEngine이 군집들의 교차 프로젝트 통계를 계산. (count 방지를 위해 matchedNodeRatio 사용)

#### Dataset 4B: Robustness Metrics (스트레스 테스트)
RobustnessEngine이 Hypothesis(Dataset 3A)의 임계값을 미세 조정하여(Sweep), 4A의 지표가 급격히 붕괴하는지(Overfitting) 관찰한 결과.

### Step 5. Dataset 5: Alias Registry (명명 및 승인)
최종적으로 강건함이 입증된 가설에만 채택 결정(Approved)과 아키텍처 의미론적 별칭(Control Singularity 등)을 부여한다.

## 🏗️ SYNAPSE Language Resolver 5-Stage Audit (우선 과제)

Kubernetes 사건을 기점으로 마일스톤의 본질이 변경되었습니다.
Percentile Validation은 일단 동결하고, **Resolver ➔ Normalize ➔ Lookup ➔ Edge ➔ Survival 전체 체인을 계측하는 품질 측정기**를 먼저 만드는 것을 최우선 목표로 확정합니다.

### 🔍 5-Stage Resolver Audit 설계

모든 언어의 추출 파이프라인 품질을 측정하기 위해, 단순한 "문자열 발견"을 넘어 최종 그래프 생존 여부까지 추적하는 5단계 감사 프레임워크를 도입합니다.

#### Stage 1. Parse Rate (문자열 발견)
- **목표:** 정규식이나 파서가 코드 상의 실제 `import / use / include` 문자열을 누락 없이 찾아내는가?

#### Stage 2. Normalize Rate (경로 변환)
- **목표:** 추출된 문자열이 SYNAPSE 가상 경로로 정상 치환되는가?

#### Stage 3. Lookup Rate (노드 매칭)
- **목표:** 정규화된 가상 경로가 인덱스 상의 실제 Node ID와 매칭되는가?

#### Stage 4. Edge Generation Rate (Edge 생성)
- **목표:** Lookup에 성공한 노드 쌍(Source ➔ Target)이 Edge 객체로 정상 생성되는가?

#### Stage 5. Graph Survival Rate (최종 그래프 생존)
- **목표:** 생성된 Edge가 Boundary Filter 등 사후 필터링 단계에서 삭제되지 않고 최종 그래프에 살아남았는가?

---

### ⚠️ 핵심 지표 정의 (Capture Rate vs Survival Rate)
필터링(Stage 5)에서 삭제된 엣지 때문에 Resolver(Stage 1~4)가 억울하게 평가절하되지 않도록 지표를 분리합니다.

- **Total Imports:** 전체 Import 구문 수
- **Excluded Imports:** 표준/외부 라이브러리로 판별되어 의도적으로 제외된 수
- **Resolvable Imports:** SYNAPSE가 반드시 찾아내야 하는 내부 참조 수

> 💡 **Resolver Capture Rate** = `Stage 4 (생성된 Edge) / Resolvable Imports`
> 💡 **Graph Survival Rate** = `Stage 5 (최종 생존 Edge) / Stage 4 (생성된 Edge)`

---

### 🚦 품질 평가 기준 (Quality Gate)
언어별 특성(Alias, Build Tags 등)을 고려하여 현실적인 평가 기준을 도입합니다.

- **≥ 95%:** 🟢 Excellent (신뢰 가능)
- **90% ~ 95%:** 🟡 Warning (주의 요망)
- **< 90%:** 🔴 Investigation Required (해석 중단 및 즉시 조사)

### 🔍 4차 검증 계획 (Semantic Trace 삽입 및 단일 실패 지점 확정)
- **계획 변경 배경**: 이전 감사(Audit) 결과가 Semantic Collapse 가설을 강하게 지지하나, 확정을 위해서는 단일 참조(Reference)가 파이프라인 어느 지점에서 소실되는지 전 구간 추적이 필요함.
- **수정된 목표**: '의미(Semantic) 소실 여부 수집'에서 **'Go 패키지 분석 중 특정 지점(단일 실패 지점, Failure Point) 확정'**으로 격상.
- **주요 추적 대상**: K8s의 핵심 패키지 5종 (`schema`, `serializer`, `runtime`, `labels`, `metav1`).
- **추적 지점 (Instrumentation)**:

  2. **Broadcast Fail (`[TRACE-3]`)**: Broadcast 판정식 내부에서 타겟 디렉터리(`packageMap`) 매칭 실패 사유 확인.
  3. **Resolver Output (`[TRACE-3-OUT]`)**: 최종적으로 `unresolved` 강등 여부 및 도출된 `ResolutionKind` 확인.
