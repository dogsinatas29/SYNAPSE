### 📌 [D-3.3 Track B] Package Boundary Discovery (최우선 과제)
- **D-3.3A-0 Structural Shannon Entropy & Monopoly Index (HHI):**
  - 단순 압축률이나 자기참조적 랭킹 생존율을 폐기하고, 패키지의 엣지 점유율 분포를 관측함.
  - 깊이를 줄일 때 발생하는 현상이 "정보 손실"이 아니라 단일 거대 패키지가 시스템을 집어삼키는 **"모듈 블랙홀(Hub Explosion)"** 임을 확인.
  - 하지만 Shannon Entropy만으로는 건강한 핵심 코어(Legitimate Core, 예: K8s `api/core`)와 블랙홀(VSCode `src/vs`)을 구분하지 못함.
  - 시장 독점도를 측정하는 **HHI(Herfindahl-Hirschman Index)**와 **Gini Coefficient** 개념 도입 필요성을 확보.
- **D-3.3A-1 Architectural Resolution Layer (아키텍처 해상도 계층):**
  - **새로운 문제 정의:** 우리가 찾고 있던 것은 "진짜 패키지가 무엇인가(New Truth)"가 아니었음. 진짜 진실(Reality)은 이미 파일 단위(Node=File)의 그래프로 존재함. 우리가 만들고 있는 것은 "현재 질문에 맞춰 어떤 구조를 얼마만큼의 해상도(Resolution)로 보여줄 것인가"를 결정하는 시각적/분석적 관찰 창(View)임.
  - **Selective Expansion (선택적 팽창/분해):** 전역 롤업 대신, 각 서브트리의 내부 건강도를 개별 측정하여 해상도를 스스로 조절함.
  - **[가장 거대한 가설] Common Layer vs Question-Aware:** 
    - 가설 A (공통 계층): Q4든 Q5든 같은 Resolution(예: Depth 4)을 통과해야 한다.
    - 가설 B (질문 인지형): Q4는 Q4 전용 렌즈(예: Depth 3), Q5는 Q5 전용 렌즈(예: Depth 5)가 필요하다.
    - 만약 가설 B가 맞다면, 이는 단순한 "패키지 중간 표현(Package IR)"을 넘어, 질문에 종속적인 **"Question-Specific Projection"**을 설계해야 함을 의미함.
  - **D-3.3A-1 실행 우선순위 (5단계 실험):**
    1. **VSCode 대상 Q4 Resolution Sweep:** Depth 2, 3, 4, 5, Raw 전체에 대해 Q4를 돌려, `platform`, `base` 등 기반 계층으로 안정 수렴하는 최적 해상도를 탐색.
    2. **VSCode 대상 Q5 Resolution Sweep:** 동일한 조건에서 Q5를 돌려, `generated`, `legacy`, `testdata` 등 비활성 영역으로 수렴하는 최적 해상도를 탐색.
    3. **최적 Resolution 비교:** Q4와 Q5가 찾아낸 최적 해상도가 일치하는지(가설 A), 다른지(가설 B) 비교.
    4. **아키텍처 결정:** 공통 Resolution Layer 유지 여부 vs Question-Aware Engine 채택 여부 확정.
    5. **Adaptive 알고리즘 설계:** 위 결정에 따라, 헌법(Reality 수정 금지, 의미 역전 금지)을 준수하는 적응형/해상도 조절 알고리즘 설계 돌입.
- **아키텍처적 결론:** "최적의 패키지 경계는 언어나 전역 규칙이 아니라, '현재 질문이 무엇인가'에 따라 유동적으로 해상도를 조절하되 진실을 왜곡하지 않는 Question-Aware Resolution Engine의 산물이다."

## 🎯 [추가 계획] v0.3.34.48 Post-Milestone Pipeline Verification
새로운 기능(v0.3.34.49) 설계나 AST 도입 논의를 전면 보류하고, **현재 파이프라인이 실제로 어느 수준까지 정확하게 작동하는지 끝까지 검증**하는 단계입니다. 
"계획 → 구현 → 결과 → 다음 계획"이 아니라, **"구현 → 측정 → 검증 → 증거 → 다음 계획"**이라는 SYNAPSE의 핵심 원칙을 실천합니다.

### 1. 전체 파이프라인 데이터 무결성 검증 (Current Pipeline Integrity)
가장 우선적으로 **"앞 단계의 데이터가 다음 단계에서 왜곡 없이 전달되는가"**를 증명해야 합니다.
- `Source` → `Scanner / Resolver` (Edge Accuracy)
- `Resolver` → `Graph` (Topology Integrity)
- `Graph` → `Metrics` (fanIn/fanOut 등 수치 계산 정확성)
- `Metrics` → `Ranking` (결정론적이고 논리적인 순위 산출)
- `Ranking` → `Pattern Detection` (의도된 패턴 발견)
- `Pattern` → `Insight` (도메인 통찰 도출)
- `Insight` → `Report` (결과물 생성)
- **역추적 검증:** 최종 보고서(Report)에서 발견된 결과가 원본 Graph/Metric까지 역추적(Evidence-preserving) 가능한가?

### 2. 결과 안정성 및 민감도 검증 (Stability & Monotonicity)
- **Ranking Stability:** 파일 순서 변경, 디렉토리 탐색 순서 변경, JSON Key 순서 변경 등 **비의미적 입력 변화**에 대해 결과가 100% 동일하게(Deterministic) 유지되는가?
- **Ranking Sensitivity:** 특정 노드의 의존성을 인위적으로 조작했을 때, **의미적 입력 변화**에 따라 Metric과 Ranking이 단조적(Monotonicity)으로 반응하는가?

### 3. 점진적 확장 실험 매트릭스 (Generalization Matrix)
현재 프로젝트 검증이 완료된 이후에만 다음 단계로 넘어갑니다. 한 번에 여러 변수를 섞지 않고 실패 원인을 분리(Isolate)합니다.
| 실험 단계 | 프로젝트 | 언어 | 검증 목적 |
| :--- | :--- | :--- | :--- |
| **Phase 1 (진행 중)** | **현재 (Antigravity)** | **현재 (TS)** | **전체 Pipeline 무결성 및 역추적 검증** |
| Phase 2 | 현재 (Antigravity) | 다른 언어 (Python 등) | Resolver 일반화 (동일 구조, 타 언어) |
| Phase 3 | 다른 프로젝트 | 현재 (TS) | 프로젝트 독립성 (동일 언어, 타 구조) |
| Phase 4 | 다른 프로젝트 | 다른 언어 | 일반화 최종 검증 |

### 4. 의사결정 분기 (AST Necessity Evaluation)
AST는 사전에 결정된 해결책이 아닙니다. 파이프라인 검증 결과에 따라 데이터가 스스로 필요성을 입증하거나 폐기합니다.
- **분기 A (현재 Resolver로 충분):** Pipeline Integrity, Semantic Accuracy, Ranking, Report Evidence가 모두 `PASS` 한다면, **"현재 검증 범위에서는 AST 도입을 요구하는 증거가 발견되지 않음"**으로 결론 냅니다.
- **분기 B (특정 단계에서 한계 발견):** 언어 특성(매크로, 템플릿, 오버로딩 등)으로 인해 `Resolver Ambiguity → Wrong Edge → Wrong Authority` 왜곡이 반복 관찰될 경우에만, 이 문제가 정규식 보강으로 해결 가능한지 아니면 AST가 필수적인지를 **별도의 실험**으로 분리하여 평가합니다.

### 📌 [v0.3.34.48 Post-Verification] Phase 3 — Ranking Semantic Correctness

#### 1. Ranking Semantic Correctness — FAIL / Semantic Gap Identified
Real-project validation demonstrated that the current degree-based ranking is data-correct but does not semantically distinguish the documented Hub concept from passive high-in-degree registry/type nodes. `InsightEngine.ts` (fanIn=1, fanOut=10) and `types.ts` (fanIn=9, fanOut=0) provide a concrete counterexample.

> **결론:** 데이터 파이프라인(Edge→Metric→Ranking)은 정확하게 작동했으나, 질문에 대한 Metric 자체가 방향성(Directionality)을 완전히 압축해 버리는 오류를 범했습니다. 그 결과 서로 완전히 다른 구조적 역할(Controller vs Passive Registry)이 단일 축(Degree) 상에서 구별 불가능한 상태가 되었습니다.

No replacement metric or ranking algorithm has been selected. Further investigation is required at the `Question → Vocabulary → Pattern → Detector → Metric` contract level.

#### 2. Phase 3-B 진행 계획
* **목표:** 현재 SYNAPSE가 정의한 Vocabulary/Question/Pattern 계약 수준에서, "현재 Metric(Degree)으로 분별이 가능한가?"를 판단하는 정보 손실(Information Loss) 감사를 수행합니다.
* **조치:** 어떠한 새로운 알고리즘도 지금 설계하지 않으며, 오직 `Question → Vocabulary → Pattern → Detector → Metric` 역전 현상이 어디서 정보 손실을 야기했는지만 감사 표(Audit Table)로 작성합니다.
