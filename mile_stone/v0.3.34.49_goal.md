# Milestone v0.3.34.49 - Diagnostic Contract Restoration

## Background

v0.3.34.48의 감사(Audit)를 통해 SYNAPSE의 핵심 문제가 Resolver 정확도, Regex 한계, AST 부재가 아니라는 사실이 확인되었다.

검증 결과, 다음 계층은 정상적으로 동작함이 증명되었다.

```text
Source
  ↓
Resolver
  ↓
Graph
  ↓
Metric
```

Source 코드의 import 구문은 Graph Edge로 보존되었으며, Graph는 Metric으로 정상 변환되고, Metric은 Report까지 역추적 가능한 수준의 Evidence Preservation을 유지하고 있었다.

반면, 원래 설계 목표였던 다음 계층은 실제 실행 경로에서 존재하지 않거나 우회(Bypass)되고 있음이 확인되었다.

```text
Question
  ↓
Vocabulary
  ↓
Pattern
  ↓
Detector
  ↓
PatternFinding
  ↓
Report
```

실제 코드베이스에서는 다수의 Report Builder와 Insight Engine이 Pattern Detector를 통하지 않고 Metric을 직접 소비하고 있었으며, 일부 Detector는 Wiring되지 않은 고아(Orphaned) 상태였다.

따라서 v0.3.34.49의 목표는 새로운 분석 기능 추가가 아니라, 진단 체계의 계약(Contract)을 복원하는 것이다.

---

# Goal

## Primary Goal

**Restore the Diagnostic Contract**

Report는 오직 PatternFinding만 소비해야 하며, Metric을 직접 소비해서는 안 된다.

```text
Reports MUST consume PatternFinding[] only.
```

---

## Architectural Principle

SYNAPSE는 Metric Reporting Tool이 아니다.

SYNAPSE는 Architect Question을 Pattern으로 변환하고, Pattern을 Finding으로 변환하여, Finding을 Architect Language로 표현하는 Diagnostic Platform이다.

따라서 Report 계층은 원시 데이터(Metric)를 직접 해석해서는 안 된다.

반드시 다음 흐름을 따라야 한다.

```text
Question
  ↓
Vocabulary
  ↓
Pattern
  ↓
Detector
  ↓
PatternFinding
  ↓
Report
```

---

# Non-Goals

이번 마일스톤에서는 다음 작업을 수행하지 않는다.

## Analysis Capability Expansion

* AST 도입
* Tree-sitter 도입
* Resolver 교체
* Scanner 재작성
* 언어 지원 확장

## Pattern Expansion

* 신규 Pattern 추가
* 신규 Dictionary 추가
* 신규 Question 추가

## Metric Research

* PageRank 연구
* Centrality 연구
* Weight Formula 연구
* Ranking Formula 개선

이 항목들은 Diagnostic Contract 복원 이후 검토한다.

---

# Success Criteria

## SC-1. Report Direct Metric Access Removal

Report 계층은 다음 데이터를 직접 참조할 수 없다.

```text
fanIn
fanOut
degree
topImpactFiles
boundaryCrossings
blastRadius
authorityReach
clusterTraffic
```

Report는 PatternFinding만 소비해야 한다.

---

## SC-2. PatternFinding as Single Diagnostic Language

Report 입력은 다음 단일 타입으로 통합된다.

```text
PatternFinding[]
```

Report는 Finding을 표현할 수는 있지만 생성해서는 안 된다.

---

## SC-3. No Pattern, No Report Claim

Pattern으로 정의되지 않은 개념은 Report에 등장할 수 없다.

예시:

```text
Hub Ranking
Core Ranking
Impact Ranking
```

위 개념은 Pattern 계약이 존재하지 않는다면 Report에서 제거되어야 한다.

---

## SC-4. Evidence Traceability

모든 Report Claim은 다음 체인을 따라 역추적 가능해야 한다.

```text
Report Claim
  ↓
PatternFinding
  ↓
Detector
  ↓
Evidence
  ↓
Graph
  ↓
Source
```

Evidence Chain이 존재하지 않는 Claim은 허용되지 않는다.

---

## SC-5. Detector Wiring Verification

현재 존재하는 Detector의 실제 연결 상태를 검증한다.

대상:

```text
Root Entry Point
System Core
Change Amplifier
Cascade Failure Point
```

각 Detector에 대해:

* 실제 호출 여부
* 실제 입력 존재 여부
* 실제 Finding 생성 여부

를 검증하고 문서화한다.

# Pattern Classification Baseline

v0.3.34.48 감사 결과를 기준으로 다음 분류를 유지한다.

## A - Evidence Sufficient

현재 Evidence만으로 증명 가능

```text
Safe Refactoring Zone
```

## B - Evidence Derivable

현재 Graph 정보만으로 계산 가능

```text
Boundary Candidate
Weak Boundary
Change Amplifier
```

## C - Source Signal Gap

정의는 있으나 Source Signal 부족

```text
System Core
Boundary Fortress
```

## D - Definition Gap

정의 자체가 불충분

```text
Learning Hub
Peripheral Component
Architectural Chokepoint
```

## E - Dynamic Gap

정적 분석만으로 증명 불가

```text
Root Entry Point
Cascade Failure Point
```

v0.3.34.49 종료 시점에 SYNAPSE는 다음 구조를 가져야 한다.

```text
Source
  ↓
Resolver
  ↓
Graph
  ↓
Evidence
  ↓
Detector
  ↓
PatternFinding
  ↓
Report
```

Report가 Metric을 직접 해석하는 경로는 제거되거나 명시적으로 금지된다.

# Final Statement

v0.3.34.48은 문제를 발견한 마일스톤이었다.

v0.3.34.49는 발견된 문제를 기준으로 Diagnostic Contract를 복원하는 마일스톤이다.

이번 버전의 성공 기준은 더 많은 분석을 하는 것이 아니라,

**Architect Dictionary → Pattern → Detector → Report**

라는 원래 설계가 실제 실행 경로에 존재하도록 만드는 것이다.
