### [조사 완료] Ghost 96 근본 원인 재확정 (read-only, 코드 미수정)

**요약 (FACT):** 신규 Ghost 증가의 직접 원인은 문서 영역(`mile_stone/`, `release_note/`, `scratch/`)이 분석 입력에서 제외되지 않아 Markdown cross-reference가 Graph edge로 생성되고, 이 edge가 절대경로 `external://` ID를 사용하는 반면 동일 파일의 Node는 상대경로 ID로 등록되어 **ID scheme mismatch**가 발생한 결과로 확인됨. 현재 Bootstrap/Scanner는 해당 문서 영역을 분석 입력에서 제외하지 않는다.

**1) NOT_FOUND source 36개 전수 조사 (FACT)**
```
Unique NOT_FOUND source     : 36
filesystem 존재             : 36 / 36 (100%)
filesystem 없음             : 0
```
모든 소스 파일이 실제로 존재함 → "파일이 없어서 Ghost"가 아니라 "파일은 있는데 ID가 안 맞아서 Ghost".

**2) ID scheme mismatch 재현 검증 (FACT)**
```
Node registry ID : mile_stone/v0.2.18.2.md            (상대경로) → 등록됨
Edge from/to ID  : external:///home/.../mile_stone/v0.2.18.2.md (절대경로 + external:// prefix) → nodeIndex에 없음 → GHOST
```
`AnomalyCollector.classifyReference()`는 문자열 비교만 하므로 동일 파일이라도 ID 정규화가 안 되면 무조건 GHOST 판정.
→ **A/B 유형 분류(53/20) 재검토 필요**: 다수가 실제로는 "node 없음"이 아니라 "다른 ID로 이미 존재"할 가능성.

**3) Bootstrap exclusion 경계 조사 (FACT) — 왜 문서 영역이 통과하는가**
```

release_note/  → 미등록 → 스캔됨

### [아키텍처 설계 방향 확정] ArchitecturalChokepointDetector (2026-09-26)

**사용자 피드백 기반 갭 상태 최종 정리:**
```
Definition Gap     : CLOSED (Betweenness Centrality 확정)

```

**핵심 교훈 정리:**
```
1. "Betweenness 자체는 버릴 필요가 없으나, 필터링 없는 생(Raw) Betweenness는 그대로 쓰기 어렵다."
2. Linux 실험의 진정한 교훈 (성공적 검증):

   "현재 그래프 모델(import/include)에서는 전역 교차점이 존재하지 않는 분리된 구조(Case A)"임을 
   정확하게 수치로 증명해 낸 것이다.
```

**ArchitecturalChokepointDetector 설계 방향 (P0~P3):**

1. **파이프라인의 2단계 분리 (P0)**
   - Stage 1: Raw Betweenness (순수 그래프 이론적 중앙성 계산)
   - Stage 2: Architectural Context Filter (도메인/컨텍스트 기반 정제)

2. **Category Weighting 적용 (P1, P2)**
   - `Final Score = Raw Betweenness × CategoryWeight`
   - 강한 범용성: `TEST`, `FIXTURE`, `MOCK`, `GENERATED` (Weight 0.0)
   - 약한 범용성: `UTILITY` (Weight 0.5 - 프로젝트마다 기준이 다를 수 있음)
   - 유효 대상: `RUNTIME` (Weight 1.0)

3. **CategoryClassifier Provider 분리 (P3)**
   - 분류 로직을 Detector 내부에 하드코딩하지 않고, 독립된 Provider(`CategoryClassifier`)로 분리.
   - 향후 경로 기반, 파일명 기반, AST 기반, 혹은 사용자 정의(synapse.config.json) 규칙으로 확장 가능하도록 인터페이스화.

이제 모든 검증과 설계 원칙이 확정되었으므로, 위 구조를 바탕으로 `ArchitecturalChokepointDetector` 실제 구현에 착수합니다.
```

## 4. Final Discrepancy Reconciliation: Exact Brandes Performance

**Discrepancy Log:**
> Previous Exact Brandes (Linux): ~44.3 min
> Current Integrated Exact Brandes (Linux): 188.88s ≈ 3.15 min

**Analysis & Reconciliation:**
- **Same Scale:** Both tests used the identical Linux `project_state.json` (approx. 99,808 nodes, 151,551 valid dependency edges).
- **Same Algorithm:** Both compute 100% Exact Brandes without any sampling or graph partitioning.
- **Root Cause of ~14x Speedup:** The discrepancy stems directly from the **Memory layout & V8 JIT Optimization** introduced in the current `BetweennessProvider.ts`.
  - The previous 44-minute prototype likely utilized `Map<string, string[]>` adjacency lists and manipulated string `id` arrays inside the nested BFS loops. This creates an enormous Garbage Collection bottleneck and slows down traversal with continuous hash map lookups.
  - The integrated version maps all Node IDs to contiguous integers (`0...N-1`) *upfront*. The entire BFS traversal runs exclusively on pre-allocated `Int32Array` (`dist`) and `Float64Array` (`sigma`, `delta`, `bc`), completely sidestepping the JS heap and object allocation.
- **Conclusion:** 동일 graph와 Exact Brandes를 대상으로 현재 구현은 typed-array 기반의 정수 인덱싱을 사용하며, 이전 string/Map 중심 prototype보다 약 14배 빠르게 실행되었습니다. 불일치가 완전히 해명되었습니다.
