# 📝 v0.3.34.50_log.md - Contract Inventory & Gap Discovery

### [초기 선언] v0.3.34.49 기준선(Baseline) 동결
v0.3.34.49의 성과(`ArchitecturalChokepointDetector` 파이프라인 관통 및 성능 불일치 규명 완료)를 기점으로 기존 탐지 알고리즘 및 그래프 지표 도출 로직을 **완전 동결(FREEZE)**한다.

v0.3.34.50에서는 새로운 기능을 추가하지 않으며, 다음 항목에 대한 전수 조사를 진행한다.

### 1. Inventory Strategy
다음의 5단계 파이프라인이 누락 없이 이어져 있는 Pattern을 "CLOSED(관통됨)"로 정의하며, 그 외의 상태는 모두 "Gap"으로 기록한다.
1. `PatternRegistry` (정의 및 등록)
2. `Vocabulary` (도메인 용어 매칭)
3. `Detector` (Finding 및 Evidence 생성, 런타임 Trace 발생)
4. `Report` (Finding 소비 및 Evidence의 마크다운 렌더링)
5. `Contract Audit` (Static & Runtime 검증 통과)

### 8. SAFE_REFACTORING_ZONE Report 경로 추적 결과

278개의 Finding이 ReportConsume 단계에서 0개로 기록된 이유입니다.

**1. PatternId 참조 여부**
* `FindingReportAdapter.ts`의 `buildOnboardingSection()` 내에 명시적으로 존재함.
* `findings.filter(f => f.patternId === PatternId.SAFE_REFACTORING_ZONE)`

**2. targetScope 필터 여부**
* **존재하지 않음.** `targetScope === 'CLUSTER'`와 같은 조건 검사 없이, `patternId`만 일치하면 그대로 순회하며 `traceReportConsume()`을 호출함.

**3. Finding 자체가 Adapter까지 도달했는가? (진짜 이유)**
* 코드 구조상 **도달하지 못했습니다.**
* `SafeRefactoringZoneDetector`는 `OnboardingAnalyzer.ts` 내부에서 강하게 묶여 있으며, `InsightEngine.buildOnboardingInsight()`가 실행될 때 **무조건(Unconditionally)** 실행되어 278개의 Finding을 만듦.
* `ReportBundleGenerator.ts`는 명령(Command)과 상관없이 모든 Insight(Executive, Onboarding, Simulation, Architect)를 기본적으로 사전 빌드함. (여기서 278개가 생성됨)
* 하지만 정작 생성된 리포트 섹션을 렌더링하는 `FindingReportAdapter.buildOnboardingSection()` 호출은 `message.command === 'fetchOnboardingReport'` **일 때만** 실행됨.
* 이전에 덤프한 `diagnostic_trace.json`은 `fetchSimulationReport` 번들 실행을 캡처한 것이므로, **Adapter 진입 자체가 단절**되어 Consume 0이 기록된 것임. 필터에 의해 Drop 된 것이 아님.

각 Report Command에 따라 11개 Pattern이 어떻게 동작하는지 계측한 매트릭스입니다. (O: Consumed, F: Found, R: Ran but 0 findings, -: Did not run)

```text
PATTERN                       EXEC    ARCH    SIM     ONBD    
------------------------------------------------------------

CASCADE_FAILURE_POINT         R       R       R       R       
SAFE_REFACTORING_ZONE         F       F       F       O       
ARCHITECTURAL_CHOKEPOINT      F       F       O       F       
ROOT_ENTRY_POINT              R       R       R       R       
LEARNING_HUB                  R       R       R       R       
PERIPHERAL_COMPONENT          -       -       -       -       
BOUNDARY_FORTRESS             -       -       -       -       
BOUNDARY_CANDIDATE            R       R       R       R       
WEAK_BOUNDARY                 -       -       -       -       
```

**새로운 관측 팩트:**
1. **Unconditional Execution 구조**: 엔진은 Report Command의 종류와 무관하게 모든 활성 Detector를 항상 구동시킵니다(F, R). 이후 `FindingReportAdapter` 단계에서 특정 Command(SIM, ONBD 등)에 해당하는 결과만 선택적으로 리포트에 소비(O)합니다.
2. **Category C의 생존 증명**: `SYSTEM_CORE`, `CHANGE_AMPLIFIER`, `CASCADE_FAILURE_POINT` 등은 실행이 단절된(죽은) 코드가 아니었습니다. 정상적으로 실행(R)되었으나, 단지 현재의 스냅샷 데이터에서 필터 조건을 만족하는 노드가 없어 0개의 Finding을 반환했을 뿐입니다. 
3. **완전 단절 그룹 확인**: `PERIPHERAL_COMPONENT`, `BOUNDARY_FORTRESS`, `WEAK_BOUNDARY`는 어떠한 Command에서도 구동되지 않았습니다.

### 10. .50 최종 결론 및 시사점

초기 가설이었던 '대부분의 패턴이 죽어있을 수 있다'는 사실상 기각되었습니다. 

**확실히 입증된 팩트:**
1. **모든 Detector는 파이프라인에 정상적으로 연결되어 있으며, Runtime에서 실행됨이 확인되었다.** (완전히 끊어진 Detector는 단 하나도 발견되지 않음)
2. 일부 Detector(`SafeRefactoringZoneDetector`, `ArchitecturalChokepointDetector`)는 실제 스냅샷 환경에서 대량의 Finding을 정상적으로 생성한다.
3. 나머지 6개의 Detector(`SystemCoreDetector` 등)는 실행은 되었으나 현재 조사 대상 스냅샷 데이터 기준으로는 조건을 만족하지 못해 Finding을 0개 반환했다.

**아직 입증되지 않은 한계 (v0.3.34.51을 위한 과제):**
* 'Dead Pattern은 없다'고 단정할 수는 없습니다.
* `BoundaryPatternDetector` 등 1:N 구조의 Detector 내부에서, 개별 Pattern(`BOUNDARY_FORTRESS`, `WEAK_BOUNDARY` 등)을 생성하는 구체적인 분기 경로가 **실제로 도달 가능한지(Reachable) 여부**는 현재의 Trace만으로는 입증되지 않았기 때문입니다.

결론적으로 .50 마일스톤은 '죽은 코드 찾기'가 아닌, **Pattern Registry → Detector → Finding → Report → Trace**로 이어지는 전체 계약 지형도를 성공적으로 복원하고 가시화한 단계로 마무리됩니다.


**결론:**
`BoundaryGraphBuilder`는 10개의 `BOUNDARY_NODE`를 정상적으로 생성했으나, 파이프라인 후반부인 `evidenceBundle.findings`에는 **단 1건도 전달되지 않고 소실**되었습니다. 

이로써 .50에서 관측된 'Boundary 계열 패턴들의 Runtime 실행은 확인되었으나 Finding은 0개였던 현상'은, **Detector 조건 미달이나 도달 불가능(Unreachable) 상태가 아닌, 입력 데이터의 증발(Case D: Builder -> Bundle 전달 누락)** 때문임이 100% 확정되었습니다.


### 13. [Postscript] 런타임 입력 검증 (Case D 강한 의심)

(논리적 점프를 메우기 위한 최종 확인)

`BoundaryPatternDetector.detect()` 내부에 로깅을 삽입하고 런타임에 직접 입력을 관측했습니다.

```text
[BOUNDARY_DETECTOR_INPUT] Total findings received: 0
[BOUNDARY_DETECTOR_INPUT] Total findings received: 0
[BOUNDARY_DETECTOR_INPUT] Total findings received: 0
```

**최종 증명:**
단순히 외부 파일(simulation_evidence.json)만 비어 있는 것이 아니라, 실제 런타임 메모리 상에서도 `BoundaryPatternDetector`에 전달되는 배열의 길이가 정확히 0이었습니다. 
이로써 Builder에서 생성된 10개의 데이터가 파이프라인 과정에서 완전히 유실되는 **Case D(입력 데이터 전달 누락)**가 단 하나의 빈틈 없이 증명되었습니다.


### 14. [Postscript] OnboardingPatternDetector Reachability 추가 확인

`OnboardingPatternDetector` (LEARNING_HUB, PERIPHERAL_COMPONENT) 역시 동일한 파이프라인 누수 문제의 영향을 받는지 확인하기 위해 Reachability 조건을 추출했습니다.

**분기 구조 특징:**
- Boundary 패턴들과 달리 두 패턴은 상호 배타적이지 않은 **독립 분기(Parallel Branches)** 구조를 가집니다.
- 유일한 생성 조건은 **`simContext.evidenceBundle.findings` 배열이 비어있지 않고 실제 파일 대상이 존재할 것** 뿐이었습니다.

**결론:**
이 두 패턴 역시 분기 자체는 100% 열려있으나(Reachable), 앞서 증명된 **Case D(입력 데이터 전달 누락)**로 인해 `findings` 배열이 0개로 전달되면서 생성 루프에 단 한 번도 진입하지 못한 동일한 파이프라인 누수 희생양임이 확인되었습니다.
