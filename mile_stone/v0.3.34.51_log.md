

# v0.3.34.51 Pattern Reachability Audit Log

### 1. 마일스톤 시작
v0.3.34.50을 통해 모든 Detector가 정상적으로 파이프라인에 연결되어 Runtime에서 실행된다는 사실이 증명되었습니다. 
하지만 일부 Detector(예: BoundaryPatternDetector, OnboardingPatternDetector 등) 내부의 개별 Pattern 분기 경로가 실제로 도달 가능한지(Reachable)는 확인되지 않았습니다.

이에 따라 v0.3.34.51에서는 **Pattern Reachability Audit**을 수행합니다. 

**분석 질문:**
`Detector 내부의 Pattern 생성 분기가 실제로 도달 가능한가?`

이 로그는 각 Detector 내부의 생성 조건을 식별하고, 해당 조건을 만족시킬 수 있는 Fixture가 현재 데이터셋에 존재하는지 조사하는 과정을 기록합니다.

### 2. BoundaryPatternDetector Reachability Inventory

정적 분석을 통해 Boundary 계열 패턴들의 생성 조건(Condition)과 분기 맵(Branch Map)을 추출했습니다.

#### Step 1 & 2. Condition & Branch Map

`BoundaryPatternDetector` 자체는 메트릭을 직접 계산하지 않고, 선행 단계인 `BoundaryGraphBuilder`에서 계산된 `strength` 속성(텍스트)을 읽어 분기합니다.

**Branch Map (BoundaryPatternDetector.ts):**
```typescript
if (strength === 'Strong') {
    patternId = PatternId.BOUNDARY_FORTRESS;
} else if (strength === 'Moderate') {
    patternId = PatternId.BOUNDARY_CANDIDATE;
} else if (strength === 'Weak') {
    patternId = PatternId.WEAK_BOUNDARY;
}
```
-> *상호 배타적(Mutually Exclusive) 분기 구조입니다. Strong이 최우선으로 평가되며, 충족 시 하위 단계는 무시됩니다.*

**Upstream Condition (BoundaryGraphBuilder.ts):**
세 패턴 모두 공통적으로 **기본 승격 조건(PROMOTED)**을 만족해야 합니다.
- 기본 조건: `size >= 5` && `internalEdges >= 3` && ( `cohesion >= 0.45` OR (`cohesion >= 0.2` && `targetConcentration >= 0.5`) OR `isMassive` )

이를 바탕으로 한 개별 패턴의 도달 조건은 다음과 같습니다.

---

**PATTERN: BOUNDARY_FORTRESS**
*   **Condition:** 
    *   Base: `PROMOTED`
    *   Strength: `isMassive` (size >= 100 && internalEdges >= 1000) OR `strengthVal >= 0.75` OR `inboundEdges >= 100`
*   **Required Metrics:**
    *   size, internalEdges, crossSubfolderEdges, structuralExternalUniqueDeps, inboundEdges, targetConcentration
*   **Fixture Exists:** UNKNOWN

**PATTERN: BOUNDARY_CANDIDATE**
*   **Condition:** 
    *   Base: `PROMOTED`
    *   Strength: `BOUNDARY_FORTRESS` 조건 미달 AND (`strengthVal >= 0.45` OR `inboundEdges >= 30`)
*   **Required Metrics:** (동일)
*   **Fixture Exists:** UNKNOWN

**PATTERN: WEAK_BOUNDARY**
*   **Condition:** 
    *   Base: `PROMOTED`
    *   Strength: 상위 두 조건 미달. (예: `cohesion`이 0.2~0.44 사이이면서 `targetConcentration >= 0.5` 인 경우 승격되지만, `inboundEdges < 30` 이면 여기에 도달)
*   **Required Metrics:** (동일)
*   **Fixture Exists:** UNKNOWN

### 6. OnboardingPatternDetector Reachability Inventory

Boundary 계열과 마찬가지로, `OnboardingPatternDetector`의 패턴 생성 조건을 정적으로 추출했습니다.

#### Step 1 & 2. Condition & Branch Map 추출

이 Detector는 `simContext.evidenceBundle.findings` 배열을 순회하여, 대상 ID(sourceId, targetId, nodeId)가 '실제 파일'인 항목들의 빈도수를 집계해 `topFiles` 목록을 만듭니다.

**Branch Map 구조 (OnboardingPatternDetector.ts):**
상호 배타적 분기가 아닌 **독립(Parallel) 분기** 구조입니다.
```typescript
if (topFiles.length > 0) { ... emit PERIPHERAL_COMPONENT (최대 3개) ... }
if (topFiles.length > 0) { ... emit LEARNING_HUB (1개) ... }
```

**PATTERN: PERIPHERAL_COMPONENT (Safe Areas)**
*   **Condition:** 
    *   `topFiles` 배열이 1개 이상 존재.
    *   해당 파일들의 빈도수(externalEdges)를 오름차순으로 정렬하여 하위 3개를 무조건 선정.
*   **Required Metrics:** `simContext.evidenceBundle.findings` 의 길이 > 0 및 대상이 실제 파일일 것.
*   **Fixture Exists:** UNKNOWN (하지만 코드 상 입력 배열만 들어오면 무조건 생성되는 구조)

**PATTERN: LEARNING_HUB (Read Later)**
*   **Condition:** 
    *   `topFiles` 배열이 1개 이상 존재.
    *   `trueEntryPoint` 및 최상위 파이프라인 4개 파일에 속하지 않는 첫 번째 실제 파일을 선정.
*   **Required Metrics:** 동일
*   **Fixture Exists:** UNKNOWN (입력 배열 길이와 충분한 파일 다양성만 있으면 무조건 생성)

#### Step 3. 입력 전달 누락에 의한 강제 0개 (Case D)

`OnboardingPatternDetector`의 두 패턴은 모두 **`simContext.evidenceBundle.findings`에 의존**합니다.
앞서 Boundary 조사에서 증명되었듯이, 현재 `simulation_evidence.json` 파일은 findings 배열이 비어있는 상태입니다 (length = 0).

따라서 `topFiles` 배열 역시 항상 길이가 0이 되며, 이로 인해 두 패턴 모두 **도달 가능성(Reachability) 자체는 100% 열려있지만, 입력 데이터가 없어 영원히 0개를 반환**하는 동일한 파이프라인 누수(Case D)의 피해자임이 확인되었습니다.

### 8. Root Cause Audit: 파이프라인 객체 흐름(Object Flow) 추적

사용자님의 지시에 따라, 추론을 배제하고 Builder의 출력값이 Detector 입력으로 전달되는 객체 흐름을 런타임 단계별로 추적했습니다.

**[추적 결과: 배관(Pipeline)은 완벽하게 연결되어 있음]**

1.  **Priority 1 (Builder 반환값 수신자):**
    *   `BoundaryAnalyzer.ts`에서 `this.builder.build()`를 호출하여 10개의 클러스터 반환값을 수신합니다.
    *   수신 즉시 `SemanticFinding(BOUNDARY_NODE)` 형태로 래핑됩니다.
2.  **Priority 2 (EvidenceBundle 적재 지점):**
    *   `ArchitectureAnalysisEngine.run()`이 이 10개의 Finding을 `context.findings`에 집어넣습니다.
    *   이를 `VirtualDebugger.ts`가 받아 `simulationContext` 객체로 만들고, `synapse_report/surgery/simulation_evidence.json`에 물리적 파일로 직렬화(Serialize)하여 덤프합니다. (직접 스크립트를 작성하여 테스트한 결과 정상적으로 319개의 finding이 파일에 기록됨을 확인했습니다.)
3.  **Priority 3 & 4 (InsightEngine 입력 객체와 동일성):**
    *   `ReportBundleGenerator.ts`가 리포트를 생성할 때, 앞서 덤프된 `simulation_evidence.json`을 읽어와서 객체로 역직렬화(Deserialize)합니다.
    *   이 역직렬화된 객체(Bundle B)가 `InsightEngine`으로 전달되고, 그 내부에서 Detector들이 호출됩니다.
    *   즉, Builder가 생성한 원본 객체(Bundle A)와 Detector가 받은 객체(Bundle B)는 **메모리 참조값이 서로 다릅니다.**

**[최종 분석 결론]**
코드 상의 논리적 단절이나 의도적인 필터링 로직은 **없었습니다.**
모든 데이터 전달은 정확한 경로를 따르고 있으며, 단 하나 유일한 중간 매개체는 **`simulation_evidence.json` 파일(I/O)**입니다.
하지만 이것이 파일이 비워졌음을 의미하는지, 다른 경로의 파일을 읽었는지, 직렬화 과정에서 유실되었는지는 아직 관측되지 않았습니다.

현재 확인된 것은 "코드 상의 경로 존재(Call Trace)" 뿐이며, 실제 데이터가 어디서 증발하는지에 대한 "데이터 추적(Data Trace)"은 확보되지 않았습니다. 파일 덮어쓰기나 Race Condition은 아직 가설일 뿐이며, 다음 단계로 정확한 Data Trace 덤프를 수행해야 합니다.
