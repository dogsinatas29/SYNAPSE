# 🚀 Milestone v0.3.34.56 - Validation of propagationDepth Necessity

## 📅 작업 정보
- **상태:** 🏗️ Planned
- **관련 마일스톤:** v0.3.34.55 (Contract Void 발견)
- **목표:** `CascadeFailureDetector`에서 기대하는 `propagationDepth` 필드가 아키텍처 상 필수적인지(의미론적 필요성) 검증하고, 이를 통해 Dead Field 여부를 판정한다.

## 🧠 상세 설계 및 로직

지금 단계에서 `.56`으로 넘어가서 "원래 설계자의 의도"를 추적하는 것은 증거 대비 탐색 범위가 너무 넓어 보입니다.

현재까지 확보된 FACT만 정리하면:

1. `CascadeFailureDetector`는 v0.3.34.45부터 `propagationDepth`를 소비했다.
2. `FailurePropagator`는 v0.3.34.26부터 존재했지만 `maxDepth`를 반환한 적이 없다.
3. 코드베이스 어디에도 `CASCADE` Evidence 생성기가 존재한 적이 없다.
4. `.45`, `.49` 문서에는 `propagationDepth`가 등장한다.
5. 따라서 "Consumer는 존재하지만 Producer는 역사상 존재한 적이 없다."

여기까지는 강한 FACT입니다.

그런데 그 다음 문장의 "후보 1, 2, 3 중 원래 설계자가 무엇을 의도했는가"는 현재 모두 동일한 수준의 가설입니다.
오히려 지금은 "설계 의도 추적"보다 먼저 해야 할 검증이 하나 있습니다.

### 먼저 확인해야 할 것: `propagationDepth`가 실제로 필요한가?

현재 Detector 점수식:
```ts
failureScore =
  (affectedNodeCount * 10) +
  (propagationDepth * 50) +
  (cascadeImpact * 100);
```

여기서 조사해야 할 것은 `affectedNodeCount`와 `cascadeImpact` 만으로도 Detector가 정상 동작하는가? 또는 `propagationDepth`가 없으면 Detector가 의미를 잃는가? 입니다.

왜냐하면 현재 발견된 상황은 단순 구현 누락이 아니라 "Consumer가 존재하고 Producer는 역사상 없음" 이기 때문입니다. 이 경우 가능한 해석은 둘입니다.

**해석 A: `propagationDepth` Producer 구현이 누락됨**
```text
설계 완성본:
  maxDepth 생성 -> propagationDepth -> Detector
```

**해석 B: `propagationDepth` 자체가 설계 잔재(dead field)**
```text
초기 설계에 넣음 -> 구현 안 됨 -> 아무도 사용 안 함 -> Detector에만 남음
```

현재 증거만으로는 A와 B를 구분할 수 없습니다. 따라서 `.56`의 목표를 "원래 설계자의 의도 찾기"로 잡기보다는 **"propagationDepth 필드의 필요성 검증"**으로 잡는 것이 더 결정론적입니다.

추천 조사 순서는 다음 4단계를 거칩니다.

### Step 1. 전파 경로 추적 (Detector → Pattern → Report)
- `CascadeFailureDetector`가 생성한 `CASCADE_FAILURE_POINT` 패턴이 최종 보고서(ArchitectReport, Insight 등)에 어떻게 반영되는지 추적합니다.

### Step 2. `propagationDepth=0` 상태에서의 Pattern 생성 검증
- `propagationDepth`가 항상 0으로 주어질 때(`|| 0` Fallback), 후보군 컷오프(Median P50)가 정상적으로 동작하여 유의미한 Pattern을 생성하는지 확인합니다.

### Step 3. 메트릭 동작성 검증 (`affectedNodeCount`, `cascadeImpact`)
- 점수식 `(affectedNodeCount * 10) + (cascadeImpact * 100)` 만으로도 시스템의 결함 전파 위험도를 변별하고 Pattern을 생성(발화)할 수 있는지 평가합니다. (완료: `propagationDepth=0`이어도 발화 정상 동작 확인)

### Step 3b. 랭킹 민감도 분석 (Ranking Sensitivity Analysis)
- 단순 발화 여부(동작)가 아닌 랭킹 품질(품질)을 검증합니다.
- `propagationDepth`가 있는 가상의 데이터와, `propagationDepth=0`으로 고정된 데이터를 비교하여:
  - Top N 후보 순위 변화
  - P50 기준선 변화
  - 생성된 Finding 수 변화
- 이 변화가 미미하다면 Dead Field 확정, 순위가 크게 요동친다면 설계상 중요한 필수 필드로 판정합니다.

### Step 4. 최종 판정 (Dead Field 기각 유력 / Essential 미확정)
- 랭킹 민감도 분석(Step 3b) 결과, 가상의 Mock 데이터 환경에서는 `propagationDepth` 제거 시 랭킹 순위가 요동치고 P50 컷오프가 변화함을 확인했습니다. 
- **FACT**: `propagationDepth`는 점수식에 실질적 영향을 주며, `propagationDepth=0`이어도 Detector는 동작합니다.
- **LIKELY**: `propagationDepth`는 의미 있는 위험도 신호일 가능성이 높으며, 아무 의미 없는 설계 잔재(Dead Field) 가설은 크게 약화되었습니다.
- **아직 미확정 (Essential Metric)**: 만약 실제 프로젝트 환경에서 `cascadeImpact`(광범위성)와 `propagationDepth`(깊이)가 매우 강한 양의 상관관계를 가진다면(즉 깊어지면 무조건 많이 퍼진다면), 사실상 둘 중 하나만 있어도 랭킹 품질은 변하지 않을 수 있습니다.
- **다음 마일스톤 액션 (v0.3.34.57)**: Producer 복구를 섣불리 결정하지 않고, 실제 벤치마크 데이터셋(VS Code, Linux 등)에서 `FailurePropagationReport`의 분포를 수집하여 **Real Dataset Sensitivity Validation**을 먼저 수행합니다.
