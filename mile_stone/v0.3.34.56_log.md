# Milestone v0.3.34.56 Log - CascadeFailureDetector & propagationDepth 분석 기록

## 1. 전파 경로 추적 (Step 1)
- **발견 사항**: `InsightEngine.ts` 내 `buildSimulationInsight`에서 `CascadeFailureDetector`가 정상 실행됨.
- **보고서 도달**: 수집된 `patternFindings` 배열이 `ReportBundleGenerator.ts`로 전달되고, `FindingReportAdapter.buildSimulationSection`을 통해 최종적으로 `SIMULATION_DEBUG.md` 리포트의 `### Cascade Failure Points` 섹션에 정상적으로 렌더링됨을 확인함.
- **결론**: 패턴 생성 후 폐기되지 않으며, 전파 경로는 정상적으로 동작하고 있음.

## 2. Mock 데이터 기반 발화 및 랭킹 민감도 검증 (Step 2, 3, 3b)
- **`propagationDepth=0` 발화 검증**: 점수식 `(affectedNodeCount * 10) + (cascadeImpact * 100)` 만으로도 P50(Median) 이상의 후보군을 추출하여 정상적으로 Pattern 발화가 일어남을 검증.
- **랭킹 민감도 분석 (Ranking Sensitivity Analysis)**:
  - 10개의 가상 노드를 대상으로 테스트 수행.
  - `propagationDepth`가 존재할 때 (P50 컷오프: 850점): "깊지만 좁은(Deep-but-narrow)" 패턴을 가진 노드들이 랭킹 상위권 진입.
  - `propagationDepth = 0`일 때 (P50 컷오프: 700점): 랭킹 순위가 크게 요동치고, 피해 규모는 작지만 깊게 전파되는 핵심 노드들이 후보군에서 아예 탈락.
- **결론**: `propagationDepth`는 단순한 '설계 잔재'가 아니라, 토폴로지 위험도 평가에서 구조적 차이(깊이 편차)를 변별하는 매우 중요한 가중치임. (Dead Field 가설 기각)

## 3. 실제 데이터 관측 가능성 증명 (Real-world Extractability)
- **목적**: Mock 데이터에서의 순위 변화가 실제 환경(Real Dataset)에서도 유의미한지 증명하기 위해, 캔버스 환경에서 `FailurePropagationReport` 추출이 가능한지 사전 검증.
- **진행 과정**:
  - 확장 프로그램 자체의 `project_state.json`을 사용하여 `FailurePropagator`로 BFS 전파 시뮬레이션 추출 시도.
  - 초기 시도에서 추출 결과가 0건으로 나옴 (JSON 스냅샷의 엣지는 `from/to` 포맷인데, Propagator는 `source/target` 포맷을 기대하는 문제 발생).
  - 포맷 매핑 후 재실행 결과, **정상적으로 21개의 연쇄 붕괴(Cascade > 0) 케이스 추출 성공**.
- **관측 사례**:
  - `src/extension.ts`: Direct(37), Indirect(28), Cascade(25)
  - `scripts/test_generate.ts`: Direct(2), Indirect(9), Cascade(19) - "좁지만 극단적으로 깊은 전파" 사례 직접 관측됨.
- **결론**: 실제 프로젝트에서 `FailurePropagationReport`를 추출하고 `sourceNodeId` 단위로 분포를 확보할 수 있음이 완벽히 증명됨.

## 4. v0.3.34.56 종료 결론
1. **FACT**: `propagationDepth`는 점수식에 실질적 영향을 주며, `0`이어도 발화 가능함.
2. **LIKELY**: 의미 있는 신호일 가능성이 높으며, 아무 의미 없는 설계 잔재(Dead Field) 가설은 크게 약화됨.
3. **미확정 (Essential Metric 여부)**: 실제 데이터 환경에서 `cascadeImpact`와 `propagationDepth` 간의 상관관계(Collinearity)가 어느 정도인지 아직 알 수 없으므로, 필수 필드 여부는 미확정.
4. **넥스트 마일스톤 (.57)**: 섣부르게 Producer 복구 설계를 시작하지 않고, 벤치마크 데이터를 통해 **Real Dataset Sensitivity Validation**을 먼저 수행하여 필드의 필수성 유무를 최종 판별하기로 결정함.

## 5. 추가 분석: Real Dataset 기반 랭킹 민감도 및 Depth Metric 가치 검증
- **목표**: 실제 데이터에서 `cascadeImpact`가 동일할 때, 깊이(Depth) 정보가 순위에 실질적인 변별력을 제공하는지 확인.
- **실험 방법**: `extract_real_propagation.ts` 스크립트를 수정하여 BFS 도중 도달한 `maxDepth`를 계산하고, 실제 캔버스 스냅샷(641 노드)의 시뮬레이션 결과에 반영함.
- **관측 사례 (Collision Case)**:
  - **Collision 1 (`cascadeImpact = 10`)**: 
    - `BoundaryAnalyzer.ts` (maxDepth=6, affected=17)
    - `ScenarioRunner.ts` (maxDepth=4, affected=23)
  - **Collision 2 (`cascadeImpact = 5` - 랭킹 역전 사례)**:
    - `RendererCore.ts` (maxDepth=5, affected=13) -> 점수 880 (Depth 포함)
    - `CanvasEngine.ts` (maxDepth=3, affected=22) -> 점수 870 (Depth 포함)
- **분석 결과**: `cascadeImpact`가 동일하더라도 `maxDepth`가 다름을 확인했으며, Depth 정보를 점수식에 포함하면 피해 규모(affected)가 작더라도 깊이 침투한 결함의 순위가 역전됨.
- **아키텍처적 결론 도출**:
  1. **FACT**: 실제 데이터에서 `cascadeImpact` 동률 사례가 다수 존재하며, BFS maxDepth를 점수식에 넣으면 실제 랭킹 역전이 발생함.
  2. **LIKELY**: `propagationDepth`는 Dead Field가 아닐 가능성이 매우 높으며, 설계자가 의도한 "깊이 계열 메트릭"은 랭킹 변별력에 필수적인 독립적 위험 신호임이 입증됨.
  3. **UNCONFIRMED**: 하지만 실험에 사용된 `maxDepth`가 원래 설계자가 의도했던 `propagationDepth`와 완전히 동일한 개념(정의)인지는 아직 증명되지 않았음 (평균 깊이인지 95 percentile인지 불명확).
- **넥스트 스텝 조율**: 당장 코드를 수정(Producer 복구)하는 대신, 다음 단계(.58)에서 과거 문서 및 히스토리 조사를 통해 `propagationDepth`의 정확한 정의와 기원을 추적하는 것이 선행되어야 함.
