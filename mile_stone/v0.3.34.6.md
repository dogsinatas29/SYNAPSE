## 🧠 상세 설계 및 로직

### 1. 설계 철학: 측정(Measure) 우선, 판단(Judge)은 보류
- 강결합(Strong Coupling)이 무조건 나쁜 결합(Bad Coupling)은 아니다. (예: `uri.ts`, `event.ts` 등 코어 허브와의 결합은 필수적임).
- 따라서 v0.3.34.6에서는 **"이 엣지를 끊어라"라는 개입(Intervention)은 절대 하지 않는다.**
- 오직 **"무엇이, 어떤 형태의 엣지로, 얼마나 강하게 연결되어 있는가?"**를 정량화하는 데 집중한다.

### 2. 핵심 개념: `ClusterBridge` 모델 도입
클러스터 A와 B 사이를 연결하는 모든 엣지(Bridge Edges)를 그룹화하여 수치화된 메트릭을 제공한다.

```ts
interface ClusterBridge {
    sourceCluster: string;
    targetCluster: string;

    totalEdges: number;

    // Provenance Stats
    typeOnlyEdges: number;
    runtimeEdges: number; // UNKNOWN_RUNTIME
    functionCallEdges: number;
    constructorEdges: number;
    inheritanceEdges: number;
    frameworkRegistrationEdges: number;

    // 최종 결합도 점수
    couplingScore: number;
}
```

### 3. Coupling Score (결합도 가중치) 모델
`EdgeProvenance`에 기반하여 결합의 강도를 산정한다. 구체적인 가중치는 다음과 같다:

| Edge Provenance | 가중치 | 이유 |
|---|---:|---|
| `TYPE_ONLY` | 1 | 런타임 영향력 제로, 가장 느슨한 결합 |
| `UNKNOWN_RUNTIME` | 2 | 동적 참조 혹은 분석 실패 엣지 (중간 위험도) |
| `DECORATOR` | 3 | DI 등을 통한 간접 결합 |
| `FRAMEWORK_REGISTRATION` | 4 | VSCode 런타임 확장을 위한 등록성 결합 |
| `FUNCTION_CALL` | 5 | 명시적인 런타임 심볼 호출 |
| `CONSTRUCTOR_CALL` | 7 | 인스턴스 직접 생성 (높은 의존도) |
| `INHERITANCE` | 10 | 상속 (가장 강한 결합, 변경 시 파급력 최대) |

- **Coupling Score 산식:** `Σ(edgeWeight)`
- 이를 통해 `chat ↔ editor`의 Score와 `chat ↔ notebook`의 Score를 정량적으로 비교할 수 있게 된다.

## 🛠️ 기술적 변경 사항

### 1. UI 파이프라인 연동 (Visible Cluster Pair Analysis)
- **별도의 새로운 UI 패널을 만들지 않는다.**
- 기존의 **Cluster Visibility Panel**을 "분석 입력 장치"로 활용한다.
- **사용자 행동:** 캔버스에서 분석하고 싶은 클러스터 2~3개(예: `chat`, `editor`)만 Visibility 토글(✓)을 켠다.
- **이벤트 트리거:** 뷰포트 내 Visible 클러스터가 변경될 때마다 백그라운드에서 `ClusterBridge` 분석을 자동 실행한다.
- **결과 출력:** 브릿지 엣지 개수, Provenance 분포, `Coupling Score`를 로그 패널(또는 캔버스 오버레이)에 덤프한다.

### 2. `GraphAnalyzer` 또는 `AiOrchestrator` 확장
- 가시성 상태를 넘겨받아 `GraphViewBuilder`를 거친 후 엣지를 추출하는 로직 구현.
- `ClusterBridgeAnalyzer` 유틸리티 클래스를 신설하여 위 수식에 따른 스코어링을 처리.

---

## ⚠️ 예외 처리 및 주의 사항
- **스코어 폭주 방지:** 단일 파일에서 100번의 Function Call이 일어났을 때 스코어가 500이 되는 것을 막기 위해, Edge Weight 산정 시 단순 총합(Sum)을 쓸지, 유니크 참조(Unique Reference) 기반으로 보정할지 실험을 통해 튜닝해야 함.
- **UI 지연 방지:** Visibility 토글 시 캔버스 렌더링을 차단하지 않도록 `ClusterBridge` 연산은 Web Worker나 비동기 태스크로 처리할 것.
- **다중 클러스터 선택:** N개의 클러스터가 선택되었을 경우 N(N-1)/2 개의 `ClusterBridge` 조합을 모두 계산하여 매트릭스로 도출할 수 있는 확장성을 고려할 것.
