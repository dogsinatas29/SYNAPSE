## 0. Fundamental Assumption (근본 전제)
- **Graph Fidelity (`Given Graph G`)**: 이 문서의 오라클은 "Resolver가 소스코드를 100% 완벽하게 파싱하여 현실과 동일한 구조의 그래프 G를 생성했다"는 전제하에 성립합니다. C/C++ 정규식 파싱 오류 등 Resolver 한계로 생성된 가짜 엣지나 누락(Graph Error)은 메트릭의 책임이 아닙니다.
- **Cluster Partition Fidelity (`Given Cluster C`)**: DC3와 RetainedPairs는 기본 단위가 `Cluster Pair`이므로, **"클러스터링 알고리즘이 도메인 경계를 완벽히 나누었다"**는 전제에 완벽히 종속됩니다. 만약 `Linux arch`처럼 거대한 단일 폴더를 하나의 클러스터로 묶어버리면 DC3는 과소평가되며, 반대로 과도하게 잘게 쪼개면 과대평가됩니다. 즉, 이 메트릭들의 정확성은 `Graph Fidelity + Cluster Fidelity` 두 가지 전제 위에 성립합니다.

## 1. Measurement Unit & The Identity of X (측정 단위와 대상)
메트릭이 무엇을 세는가(What to count)를 결정하기 전, **무엇을 기준으로 셀 것인가(Unit)**와 **평가 대상(X)이 무엇인가**를 확정합니다.

- **평가 대상 ($X$)**: 원본 그래프 $G$의 **개별 File (Node)**. 
  - 단, $X$는 **반드시 $G_{scc}$에서 크기가 1인 단일 노드(Singleton SCC)로 존재**해야 합니다. $X$가 거대 SCC에 묶여 있다면, 거시적 도메인 브릿지가 아니므로 본 탐지기의 평가 대상에서 완전히 제외(Skip)됩니다. 이 규칙을 통해 $G_{scc} \setminus \{X\}$ 연산이 수학적으로 완벽하게 성립합니다.
- **측정 단위 (Unit)**: X가 매개하는 의존성의 단위는 **Cluster Pair**를 기본 단위로 수행합니다. (단, $C_s \neq C_t$)
  - **SCC-Cluster Attribution Rule**: $G_{scc}$ 상의 경로는 실제 파일 경로가 아닌 단일 클러스터 라벨이 부여된 SCC 노드들의 경로입니다. 본 탐지기에서는 **"각 SCC는 오직 단 하나의 Cluster에만 귀속된다"**고 전제합니다. 만약 하나의 SCC가 여러 Cluster에 걸쳐 형성되었다면(다중 도메인 얽힘), 해당 SCC 전체는 거시적 브릿지 분석에서 제외(Out of scope)됩니다. (KISS 원칙 적용)

## 2. DC3 Semantic Definition (본질적 의미)
DC3(Dependency Concentration)가 세고자 하는 것은 단순한 트래픽(볼륨)이 아닙니다. 100개의 파일이 `parser`에서 `reporting`으로 흐르는 것은 1개의 도메인 커플링일 뿐입니다.
- **명칭과 실제 의미의 괴리 보완**: `DC3`는 내부 호환성을 위한 Legacy Name이며, 이 메트릭의 실제 의미론적 정체는 **Distinct Cross-Cluster Bridge Breadth(고유 교차 클러스터 브릿지 폭)**입니다. 즉, "얼마나 다양한 도메인 간의 브릿지 역할을 하는가?"를 측정합니다.

**수학적 정의:**
모든 메트릭 연산은 원본 그래프 $G$가 아닌, 순환 구조를 단일 노드로 압축한 **SCC Condensation DAG ($G_{scc}$)** 위에서 수행됩니다. (이때 평가 대상 $X$는 독립된 단일 SCC이므로 $G_{scc}$ 상의 한 노드로 존재합니다.)

먼저 $X$를 관통하는 고유 클러스터 쌍의 집합 $P_X$를 정의합니다:
$$ P_X = \{ (C_s, C_t) \mid C_s \neq C_t \land C_s \neq C_X \land C_t \neq C_X \land \exists \text{ path } C_s \dots X \dots C_t \text{ in } G_{scc} \} $$

$$ \text{DC3}(X) = | P_X | $$

- **Pair 정의**: $C_s \rightarrow C_t$ (서로 다른 두 외부 클러스터 간의 단방향 흐름).
- **Cycle 처리 (SCC Collapse)**: 순환 구조 내부의 노드는 "이질적 도메인 간의 매개(Architecture Bridge)"라는 본질에 어긋나므로, 모든 연산 전에 $G_{scc}$로 압축합니다.
- **Limitation (Intra-SCC 탐지 제외)**: 이 규칙에 따라, 거대한 SCC 내부에서 벌어지는 병목(Intra-SCC Bottleneck)은 본 탐지기(Detector)의 범위를 벗어납니다. 본 메트릭은 철저히 **"거시적 도메인(SCC/Cluster) 간의 횡단 병목"**만을 타겟으로 합니다.
- **Dedup 규칙 (중복 제거)**: 하나의 클러스터 쌍($C_A \rightarrow C_B$) 사이를 지나는 Raw Node Pair가 수백 개라도, DC3는 이를 **1개(Distinct Cluster Pair)**로 취급한다.

## 3. AP Semantic Definition (우회로의 본질)
AP는 4가지 완전히 다른 메트릭으로 해석될 수 있으며, SYNAPSE가 찾는 병목(Chokepoint)을 정의하기 위해 단 하나를 선택해야 합니다.

- `AP_exists` (우회로 존재 여부): 단 하나의 우회로라도 있으면 1, 없으면 0. (너무 단순함)
- `AP_ratio` (유지율): 원래 존재하던 쌍 중 유지되는 쌍의 비율.
- `AP_capacity` (대체 가능한 총 Flow): 우회 경로가 몇 개나 존재하는가? (우회 풍부성)
- **`RetainedPairs` (채택)**: $X$를 관통하던 고유 클러스터 쌍 $P_X$ 중에서, $X$를 제거하더라도 $G_{scc}$ 내 다른 우회 경로가 존재하여 도달 가능성이 "유지(Retained)"되는 쌍의 **개수(Count)**.
- **수학적 정의**: 
$$ \text{RetainedPairs}(X) = | \{ (C_s, C_t) \in P_X \mid \exists \text{ path } C_s \dots C_t \text{ in } G_{scc} \setminus \{X\} \} | $$
- **명칭 변경 이유**: `AP_count = 10`일 때, 사용자가 "10개의 우회 경로가 있다"고 오해하는 것을 방지하기 위해, **유지되는 쌍의 수(Retained Pair Count)**로 명확히 명명합니다.
- **유지 조건 (Retention)**: 우회 여부는 반드시 **$G_{scc} \setminus \{X\}$** 위에서 판별되어야 합니다. 즉, 우회 경로 자체가 다시 X를 지나가는 것은 허용되지 않습니다.

## 4. Oracle Construction Rules (G1~G7 정답 유도 과정)
위에서 확립한 Semantic Definition을 바탕으로 G1~G7의 정답(Oracle)을 유도합니다.

1. **G1 (단일 직선)**: `C_A \rightarrow X \rightarrow C_B`. 클러스터 쌍 1개. 우회로 없음. $\rightarrow$ `DC3=1, RetainedPairs=0`
2. **G2 (단일 우회로)**: `C_A \rightarrow C_Y \rightarrow C_B` 존재. 유지됨. $\rightarrow$ `DC3=1, RetainedPairs=1`
3. **G2b/G2c (원격 우회로)**: X를 거치지 않는 다단계/원격 우회로가 `C_s \rightarrow C_t` 흐름을 이어줌. 유지됨. $\rightarrow$ `DC3=1, RetainedPairs=1`
4. **G3 (거대 순환 구조)**: `A \leftrightarrow B \leftrightarrow C \dots` 등 거대한 SCC. 이 거대 SCC 내부의 노드 $X$는, 거시적 도메인 간의 브릿지가 아니라 모듈 내부 복잡도일 뿐이므로 평가 대상에서 원천 제외됨. $\rightarrow$ `본 Detector 관찰 대상 아님 (Skip)`
5. **G4 (거대 허브)**: 서로 다른 수많은 클러스터 쌍이 X를 관통하며, 각각 독립적 우회로가 존재. $\rightarrow$ `DC3=N, RetainedPairs=N`
6. **G5 (Strict Cut)**: G4처럼 다수의 클러스터 쌍이 X를 관통하지만, 우회로 전혀 없음. $\rightarrow$ `DC3=N, RetainedPairs=0`
7. **G6 (볼륨 팽창 - Scale Control)**: `C_A \rightarrow X \rightarrow C_B` 이나, $C_A$ 내부 노드가 10,000개임. 트래픽 볼륨에 상관없이 고유 쌍은 1개이므로 $\rightarrow$ `DC3=1, RetainedPairs=0`
8. **G7 (도메인 분산 - Scale Control)**: $X$ 하나가 서로 독립된 4개 클러스터의 흐름을 각각 1개 노드씩만 연결함. $\rightarrow$ `DC3=4`

## 5. Architectural Chokepoint Semantic Definition (P3 사전 정의)
Detector 설계(`.62`)로 넘어가기 전, 측정하고자 하는 **"Chokepoint(병목)"의 본질적 의미**를 선언합니다.

> **"Architectural Chokepoint란, 매우 넓은 클러스터 매개 폭(High DC3)을 지니면서, 그 매개 역할이 사라질 경우 시스템의 구조적 도달성이 대거 소실되는(High CriticalPairs) 절대적 길목이다."**

- **DC3 (Bridge Breadth):** 노드가 얼마나 다양한 모듈 간의 '브릿지' 역할을 수행하는가 (다양성).
- **CriticalPairs (Reachability Loss):** $X$를 제거했을 때, 해당 방향의 Cluster-to-Cluster reachability가 소실되는(X-removal-critical) 고유 클러스터 쌍의 수 (장애 유발이 아닌, 구조적 도달성 상실).
- **SR (Tie Breaker):** Structural Breadth. 단절이 유발하는 실제 Blast Radius가 아니라, 동점자 처리를 위한 2차적 구조적 폭(Breadth) 지표.

이 세 가지의 조합만이 단순한 Hub(트래픽 집중)와 진정한 Chokepoint(구조적 흐름 상실)를 구분해 낼 수 있습니다.
