## A1. `SYSTEM_CORE` 구현 분석 및 계약 검증 (Phase A-2)

### 1. 대상 소스 코드
- `src/core/analysis/patterns/detectors/SystemCoreDetector.ts`

### 2. 실제 구현 분석 (Reverse-Engineering)
`SYSTEM_CORE`의 구조적 판정이 코드 레벨에서 실제로 어떻게 동작하는지 분석했다.

1. **대상 제한 (Target Scope)**:
   - 전체 노드를 대상으로 탐색하지 않는다. 
   - `evidenceType === 'BOUNDARY_NODE'`를 만족하는 시맨틱 경계 노드 집합만 후보로 제한한다.

2. **평가 지표 (Metrics & Weights)**:
   - `fanIn` (가중치: 10)
   - `authorityReach` (가중치: 100)
   - `blastRadius` (계산식: `fanOut * size`, 가중치: 2)
   - **Control Score (통제력) = `(fanIn * 10) + (blastRadius * 2) + (authorityReach * 100)`**

3. **판정 임계치 (Threshold)**:
   - 절대적인 수치 기준이 아니라 **상대 평가**를 사용한다.
   - 산출된 `Control Score`들의 **후보군 중앙값 이상**에 해당하는 노드를 모두 `SYSTEM_CORE`로 분류한다.

4. **증거 산출 (Evidence Generation)**:
   - `Core traits (FanIn: X, BlastRadius: Y) -> Control Score: Z` 형태의 시맨틱 증거(SEMANTIC_METRICS)를 생성한다.

### 3. 의미론적 제약 (Semantic Constraints) 도출
이 구현 구조에 따라 LLM의 상상력은 다음과 같이 제한된다.
- **제약 1**: 전체 노드 대상이 아니라 경계 노드(Boundary Node) 내에서의 순위이므로, *"전체 시스템에서 가장 중요한 코어다"*라고 선언할 수 없다. 
- **제약 2**: Median Cutoff 방식을 사용하므로, 1~2개의 절대적 코어가 아니라 상당히 넓은 범위의 노드들이 `SYSTEM_CORE`로 묶여서 나올 수 있다.
- **제약 3**: `fanIn`과 `authorityReach`가 절대적인 영향을 미치므로, 이를 `의존성 집중도`와 `권위 도달력`이라는 관측어로 번역해야 한다.

### 4. 작업 내용 결론
위의 분석을 바탕으로, 3대 금지 원칙(Intent, Value, Action)을 준수하는 **A1 Vertical Contract**를 도출하여 `v0.3.34.63_report_dictionary.md`에 등재 완료함.

### 5. 추가 검증: BOUNDARY_NODE의 기원 및 authorityReach 유령 지표
사용자의 지침에 따라 `BOUNDARY_NODE`의 판정 과정과 각 지표의 실제 데이터 원천을 `BoundaryGraphBuilder.ts`와 `SystemCoreDetector.ts`를 교차 검증하며 추적했습니다. 그 결과 매우 중대한 사실이 추가로 밝혀졌습니다.

1. **`BOUNDARY_NODE`의 기원 (Scope 정의)**:
   - 전체 개별 파일(Node)이 아니라, `BoundaryGraphBuilder`가 식별하고 병합(Promotion)한 **디렉터리 기반의 모듈 단위**입니다.
   - 즉, `SYSTEM_CORE`는 특정 파일 하나가 아니라 "시스템 내의 모듈/컴포넌트 단위" 중 하나를 가리킵니다.

2. **`authorityReach`는 유령 지표 (Phantom Metric)**:
   - `SystemCoreDetector`에서는 `f.metadata?.authorityReach || 0.0` 코드로 참조하고 있으며 가중치도 100이나 부여되어 있습니다.
   - 하지만 이를 생성하는 `BoundaryAnalyzer.ts` 및 `BoundaryGraphBuilder.ts`를 확인한 결과, **어디에서도 `authorityReach` 값을 생성하거나 주입하지 않습니다.**
   - 결론적으로 현재 모든 `SYSTEM_CORE` 판정에서 `authorityReach`는 항상 `0.0`이며, 실제 `Control Score`는 오로지 `(fanIn * 10) + (blastRadius * 2)`로만 결정되고 있었습니다.

3. **`blastRadius`의 실제 데이터 의미**:
   - `size`는 바이트 크기가 아니라 **모듈 내 포함된 파일의 개수(`memberIds.length`)**입니다.
   - 따라서 `blastRadius = fanOut * size`는 **"이 모듈이 의존하는 외부 모듈 수 × 이 모듈 내부의 파일 수"**를 의미합니다.

이러한 깊은 기원 추적을 통해 A1 계약의 내용이 완전히 바뀌어야 함을 확인했습니다.

## A4. 구조적 결합 이상 (Erosion / Coupling) 분석 및 검증

### 1. 대상 소스 코드 탐색 결과
사용자님의 경고대로 A4에 해당하는 패턴들의 실제 구현을 코드베이스 전체에서 추적했습니다.

- `Boundary Leakage`: **존재하지 않음 (Not Implemented)**
- 관련 로직 발견 위치: `src/core/analysis/reasoning/SmellDetector.ts`의 `ui-core-coupling` 및 `layer-inversion`

### 2. 발견된 로직 (SmellDetector) 분석
현재 '결합 이상'을 판정하는 코드는 다음과 같은 방식으로 동작합니다.

1. **ui-core-coupling**
   - 대상: 노드가 3개 이상인 강결합 컴포넌트(SCC, 순환 참조 그룹)
   - 로직: SCC 내부에 파일 경로상 `ui`, `view`, `widget` 문자열을 포함한 노드와 `core`, `domain`, `services` 문자열을 포함한 노드가 섞여 있으면 "UI-Core Coupling in Massive SCC"라는 냄새(Smell)로 판정합니다.
2. **layer-inversion**
   - 대상: 전체 Graph Edge
   - 로직: 출발지 파일 경로에 `core`가 있고 도착지 파일 경로에 `ui`가 있으면 "Layer Inversion"으로 판정합니다.

### 3. 의미론적 제약 및 문제점
이 로직은 A4 질문("어디서 구조적 결합 이상이 관측되는가?")을 방어할 수 없습니다.

- **이름 기반 휴리스틱의 한계**: 실제 아키텍처의 의존성 규칙이나 경계를 수학적으로 측정하는 것이 아니라, 단순히 파일 경로에 특정 문자열(`core`, `ui`)이 들어가는지만 봅니다. 프로젝트가 이 네이밍 규칙을 따르지 않으면 전혀 동작하지 않습니다.
- **Value Judgment 내포**: "이상(Anomaly)"이나 "냄새(Smell)"라는 가치 판단을 미리 정해진 문자열 휴리스틱에 의존하여 내리고 있습니다.
- **구조적 누수(Leakage)나 침식(Erosion) 미구현**: 실제 `BoundaryGraphBuilder`가 A3에서 잘 만들어놓은 `BOUNDARY_NODE` 간의 불법적인 참조나 우회 의존성을 측정하는 로직은 하나도 없습니다.

### 4. 결론
A4 역시 A2와 마찬가지로 **CONTRACT MISMATCH (또는 PENDING)** 상태입니다. 현재 구현된 휴리스틱 기반의 Smell 로직은 A3의 훌륭한 Boundary 구조를 전혀 활용하지 못하고 있습니다. 
따라서 A4의 지원 패턴(Supporting Pattern)은 현재 **없음(NULL)**으로 명시하고, A3에서 발견한 Boundary를 활용하여 진정한 의미의 의존성 누수(Boundary Leakage)를 계산하는 새로운 Detector 설계가 필요합니다.

   - `externalDensity` = `externalEdges / size`
   - `complexityScore` = `size * (internalDensity)^2 * externalDensity`
   - `blastRadius` = `externalDensity * size` (= 수학적으로 `externalEdges`와 동일함)
3. **데이터 원천**: 이전 단계에서 생성된 `simContext.evidenceBundle` (정적 그래프 기반 `BOUNDARY_NODE` 결과물).
4. **"Blast Radius" 의미 일치 여부**: **불일치 (Phantom Naming)**. 코드가 부르는 `blastRadius`는 실제 런타임 전파나 Downstream Reachability가 아니라 단순히 모듈의 `externalEdges` 개수일 뿐입니다.
5. **Threshold (분류 타입)**: `complexityScore >= medianScore` (A1과 동일한 **Median-relative** 분류).
6. **Evidence 문자열 평가**: `Change Amplifier (Complexity: X, BlastRadius: Y)`. 가짜 이름인 `BlastRadius`가 Evidence로 그대로 노출되어 환각을 유발할 위험이 큽니다.
7. **Claim Boundary 제한**: "영향이 크다(Propagation)"는 런타임 전파 주장을 절대 할 수 없으며, 단지 "해당 모듈은 내부 밀도와 외부 결합도가 복합적으로 높아, 구조적으로 복잡한(Complexity) 모듈로 분류된다"까지만 허용해야 합니다.

### 3. 결론
E2는 실제 계산식과 부여된 의미(Blast Radius, Propagation) 간에 큰 괴리가 있습니다. 하지만 Metric 자체(`complexityScore`)는 "변경 시 고려해야 할 구조적 복잡도"로서 충분히 유의미하므로, **Vocabulary를 수정하는 조건으로 VERIFIED (조건부)** 처리하고 Contract를 갱신합니다.

## E3. `SAFE_REFACTORING_ZONE` 구현 분석 및 계약 검증

### 1. 대상 소스 코드 탐색 결과
- `src/core/analysis/patterns/detectors/SafeRefactoringZoneDetector.ts`

### 2. 역추적 7단계 결과

1. **실제 대상 단위 (Scope)**: 전체 노드 중 테스트/스크립트 등(Noise)을 제외한 **개별 소스 파일 단위(File Node)**.
2. **실제 Metric**: `inDegree === 0` (다른 파일이 해당 파일을 의존하지 않음).
3. **데이터 원천**: 전체 원시 그래프(`context.snapshot.edges`). 모듈 묶음(Boundary)을 무시한 전역 스캔.
4. **"Safe Zone" 의미 일치 여부**: **심각한 불일치 (Value Judgment/Over-interpretation)**. "나를 호출하는 곳이 없다(Zero Fan-In)"는 것은 진입점(Entry Point)이거나 단순 말단(Leaf)이라는 뜻이지, 결코 "수정해도 안전하다(Safe)"는 뜻이 아닙니다. 진입점 로직을 잘못 건드리면 앱 전체가 무너집니다. 컴파일 의존성이 없다는 사실을 "안전"이라는 가치로 비약했습니다.
5. **Threshold (분류 타입)**: `Absolute` (`inDegree === 0` 인 모든 노드).
6. **Evidence 문자열 평가**: `Zero Fan-In (no consumers depend on this file)`. 증거 자체는 자신이 측정한 것을 매우 정직하게 노출하고 있습니다.
7. **Claim Boundary 제한**: "이 영역을 리팩토링해도 안전하다"는 지시(Action Judgment)를 전면 금지합니다. 단지 "다른 파일에 의해 참조되지 않는 고립된(또는 최상위) 노드"라는 구조적 사실(Structural Isolation)까지만 허용합니다.

### 3. 결론
E3는 E2보다 더 명백하게 "구조적 상태(Zero Fan-in)"를 "행동적 가치(Safe)"로 과도하게 포장(Translation Leak)한 사례입니다. 증거(Evidence) 자체는 명확하고 훌륭한 정적 지표이므로, **Vocabulary를 "Zero Fan-In, Structural Isolation"으로 강제 수정하는 조건으로 VERIFIED (조건부)** 처리합니다.

## O2. `ROOT_ENTRY_POINT` 구현 분석 및 계약 검증

### 1. 대상 소스 코드 탐색 결과
- `src/core/analysis/patterns/detectors/EntryPointDetector.ts`

### 2. 역추적 7단계 결과

1. **실제 대상 단위 (Scope)**: `systemAssemblyPoints` (Validation 결과물) 또는 `evidenceBundle.findings` 내 파일들.
2. **실제 Metric**: 파일명 문자열 매칭 점수(`priorityScore = +10000` for main, index, bootstrap) - (depth * 10) - (fanIn * 5) + fanOut.
3. **데이터 원천**: 파일 경로 문자열 및 기본 노드 속성.
4. **"Entry Point" 의미 일치 여부**: **부분적 일치 (Naming Heuristic)**. 실제 정적 그래프의 최상단 Root나 런타임 시작점을 보장하는 수학적 구조 탐색이 아닙니다. `main`, `index` 등의 **이름 관습(Naming Convention)**에 99% 의존합니다.
5. **Threshold (분류 타입)**: 점수 내림차순 정렬 후 Top-1 추출.
6. **Evidence 문자열 평가**: `Matched entry point naming convention (Score: X)`. 매우 정직하게 "Naming convention"이라고 명시하여 환각을 덜 유발합니다.
7. **Claim Boundary 제한**: "이 파일이 아키텍처의 실제 구조적/런타임 시작점이다"라고 단정할 수 없습니다. "이름(Naming Convention)과 디렉터리 깊이 관습으로 볼 때 진입점일 가능성이 가장 높은 파일"까지만 허용됩니다.

### 3. 결론
O2는 구조적 분석이 아니라 파일명 휴리스틱에 의존하므로, 계약 상 `Entry Point (Structural)`라는 주장을 폐기하고 **`Entry Point (Naming Convention)`으로 축소하는 조건 하에 VERIFIED (조건부)** 처리합니다.

## O4. `LEARNING_HUB` (Reading Order) 구현 분석 및 계약 검증

### 1. 대상 소스 코드 탐색 결과
- `src/core/analysis/patterns/detectors/OnboardingPatternDetector.ts`

### 2. 역추적 결과

1. **실제 대상 단위**: 이전 시뮬레이션/분석에서 탐지된 `evidenceBundle.findings` 내의 파일들.
2. **실제 Metric**: Findings에서의 단순 등장 빈도 수(`counts.get(src) + 1`).
3. **동작 방식**: 
   - 파일명 휴리스틱(model, service 등)을 사용해 `pipeline` 후보군을 먼저 뽑고 제외함.
   - EntryPoint 파일도 제외함.
   - 남은 파일 중 가장 **등장 빈도가 높은 단 1개의 파일**을 추출.
4. **"Reading Order(읽기 순서)" 의미 일치 여부**: **완전 불일치 (CONTRACT MISMATCH)**. 코드 자체 주석에도 `// --- 2. LEARNING_HUB (Read Later) ---` 라고 명시되어 있습니다. "무엇을 먼저 읽어야 하나(O4)"라는 순서를 전혀 생성하지 않으며, 오히려 "파이프라인을 다 읽고 나중에 읽어야 할 복잡한 파일 1개"를 던져줄 뿐입니다.
5. **Evidence 문자열 평가**: `High relative impact score`. 빈도를 셌으면서 impact score라는 거짓 Evidence 라벨(Phantom Metric)을 사용합니다.

### 3. 결론
`LEARNING_HUB`는 A2(Dependency Mediation)에서도 실패했고, O4(Reading Order)에서도 실패했습니다. 학습 순서를 제공하는 어떠한 수학적 경로/정렬 로직도 존재하지 않으므로 **O4는 PENDING / CONTRACT MISMATCH** 처리하며, `LEARNING_HUB` 패턴은 현재 어떠한 질문에도 답변할 수 없는 폐기 대상(Orphaned Pattern)으로 확정됩니다.

## D1. Virtual Debug (Trace/Propagation) 구현 분석 및 계약 검증

### 1. 대상 소스 코드 탐색 결과
- `src/core/reasoning/analyzers/PropagationAnalyzer.ts`
- `src/core/FailurePropagator.ts`

### 2. 역추적 7단계 결과

1. **시작점이 실제 Event인가?**: **아닙니다.** 특정 실행 이벤트가 아니라, 정적 검사에서 결함(Health !== HEALTHY)으로 마킹된 노드들 전체가 무작위(순회 순서) 시발점이 됩니다.
2. **Trace가 실제 실행되는가 (시뮬레이션인가)?**: **아닙니다.** 런타임 이벤트 전파를 시뮬레이션하지 않습니다. `FailurePropagator`는 정적 그래프 Edge를 타고 최대 `MAX_PROPAGATION_DEPTH`까지 단순 BFS(너비 우선 탐색)를 수행하는 정적 도달 가능성(Static Reachability) 계산기일 뿐입니다. `PropagationAnalyzer`는 심지어 `crossBoundaryDependencies` 배열을 단순 문자열로 이어붙여 최대 2-Depth의 가짜 Path를 만듭니다.
3. **Trace의 Edge가 실제 그래프 Edge인가?**: `FailurePropagator`는 실제 Edge를 사용하지만, `PropagationAnalyzer`는 Dependency Boundary 배열 요소 간 결합을 인위적으로 이어붙입니다.
4. **방문 순서가 보존되는가?**: 아니오. 단순 BFS 방문 노드 집합(Set/Array)으로 평탄화되어, 1->2->3 의 순차적 인과 관계 경로(Chain)가 유지되지 않습니다.
5. **종료 조건**: 런타임 종료 조건(Target Reached 등)이 없으며, 인위적인 하드코딩 리밋(`MAX_IMPACT_NODES`, `MAX_PROPAGATION_DEPTH`)으로 탐색을 중단시킵니다.
6. **Evidence가 실제 Trace를 보존하는가?**: 보존하지 않습니다. Evidence는 `HIGH_PROPAGATION` 같은 단순 라벨링으로 끝나며, 원본 Path 원시 데이터를 훼손합니다.
7. **Trace에서 다른 의미를 훔쳐오는가?**: "어디까지 영향이 간다"는 정적 Reachability를 "치명적이다", "장애가 전파된다(Failure Propagation)"는 동적/가치 판단적 단어로 과장 포장(Translation Leak)하고 있습니다.

### 3. 결론
D1 구현체는 런타임 추적이나 시뮬레이션(Trace)이 아니며 단순한 정적 의존성 그래프 탐색(Static Reachability / Dependency Chain)입니다. `Virtual Debug`와 `Simulation`이라는 단어 자체가 심각한 환각(Phantom Naming)을 유발하므로, **계약을 "Static Reachability(정적 도달 가능성)"로 전면 강등/수정하는 조건 하에 CONDITIONALLY VERIFIED (RECLASSIFIED)** 처리합니다. 또한, E2 및 E3의 어휘/질문 텍스트 수정 지시도 Dictionary에 모두 반영하였습니다.
