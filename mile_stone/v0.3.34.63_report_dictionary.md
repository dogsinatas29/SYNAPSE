## ⚖️ SYNAPSE SUPREME LAW (3대 금지 원칙)

SYNAPSE는 아키텍처의 판사가 아니라, **증거 기반 관측기(Evidence-backed Observer)**이다. 
판단(Decision)은 인간(Architect/Tech Lead)의 몫이다. 따라서 다음 3가지는 시스템 차원에서 영구 금지된다.

> **⛔ 1. Historical Intent 금지 (역사적 의도/심리 추론)**
> - *"개발자가 유지보수를 쉽게 하려고 이렇게 짰다."* (X)
> - *"왜 이렇게 만들었는가?"* (X)
> - **Rule**: SYNAPSE는 관측 가능한 구조만 설명하며, 과거 설계자의 의도나 심리를 추론하지 않는다.

> **⛔ 2. Value Judgment 금지 (가치 판단/품질 평가)**
> - *"이 결합도는 나쁘다(Bad) / 이 구조는 훌륭하다(Good)."* (X)
> - *"이 설계는 잘못되었다(Wrong)."* (X)
> - **Rule**: 높은 결합도는 상황에 따라 최적화일 수도, 부채일 수도 있다. SYNAPSE는 특정 패턴이 존재한다는 사실(Classify)까지만 보고하며, 그것이 좋은지 나쁜지 평가하지 않는다. 평가어(Important, Bad, Rotting)는 관측어(Centrality, Mediation, Concentration)로 대체된다.

> **⛔ 3. Action Judgment 금지 (행동 지시)** *※ Architect Report 한정*
> - *"여기가 집중되어 있으니 먼저 수정해야 한다(Must fix first)."* (X)
> - **Rule**: Architect Report는 오직 '무엇이 존재하는가(사실)'만 보고한다. '무엇을 해야 하는가(행동)'는 Execution Report의 영역이다.

> **⛔ 4. Fake Evidence Label & Phantom Metric 금지**
> - 실제 Detector에서 계산하지 않는 지표(Phantom Metric)나 가짜 이름을 Evidence 문자열에 포함해서는 안 된다.
> - **Rule**: 패턴의 이름(Pattern Name)은 의미를 보장하지 않는다. 오직 실제 구현된 Metric과 Evidence Source만이 의미를 보장한다. (Pattern Name ≠ Semantic Meaning)

## 검증 상태(Status) 정의

본 문서에서 패턴의 검증 상태는 다음 5가지 중 하나로 분류됩니다.

1. **VERIFIED**: 원래 설계된 질문(Question)과 대상 패턴(Detector)의 실제 동작(Metric/Classification)이 완전히 일치함.
2. **CONDITIONALLY VERIFIED (RECLASSIFIED)**: 패턴의 증거 수집 방식 자체는 유효하나, 기존 질문이나 어휘가 과도한 추론(Phantom Naming)을 포함하여 질문과 허용 어휘를 실제 동작에 맞춰 재정의(Reclassified)한 상태.
3. **CONTRACT MISMATCH**: 패턴의 실제 동작이 질문의 의미를 전혀 충족하지 못하며, 계약을 수정하더라도 해당 질문에 답할 수 없음.
4. **PENDING**: 아직 검증이 진행되지 않았거나, 기존 패턴 중 적합한 것이 없어 신규 설계가 필요한 상태.
5. **ORPHANED**: 어떤 질문에도 대응하지 못하고 계약 불일치가 확정되어 시스템에서 영구 폐기(제거)되어야 할 패턴.

## 1. Architect — Understand

목적: 현재 시스템의 구조적 사실을 관측한다.

| ID | Question                 | Required Vocabulary                                                         | Supporting Pattern                        | Status            |
| -- | ------------------------ | --------------------------------------------------------------------------- | ----------------------------------------- | ----------------- |
| A1 | 어디서 구조적 중심성이 관측되는가?      | Structural Centrality                                                       | `SYSTEM_CORE`                             | VERIFIED          |
| A2 | 무엇이 구조적으로 연결을 매개하는가?     | Dependency Mediation                                                        | 신규 Detector / 재설계 필요                      | CONTRACT MISMATCH |
| A3 | 어디서 구조적 경계가 관측되는가?       | Boundary Structure, Cohesion, Internal Connectivity, External Dependency    | `BOUNDARY_FORTRESS`, `BOUNDARY_CANDIDATE` | VERIFIED          |
| A4 | 어디서 구조적 결합 이상이 관측되는가?    | Coupling Pattern, Boundary Leakage                                          | 신규 Detector 필요                            | PENDING           |
| A5 | 어디서 의존성 집중/병목 패턴이 관측되는가? | Dependency Concentration, Propagation Concentration, Betweenness Centrality | `ARCHITECTURAL_CHOKEPOINT`                | VERIFIED          |

### Architect Boundary

허용:

* 현재 구조
* 관측된 중심성
* 관측된 경계
* 관측된 결합 및 경로 매개 구조
* 실제 계산된 Metric과 Classification

금지:

* 역사적 의도 추론
* 설계 품질 평가
* 변경 우선순위 지시
* 실제로 계산하지 않은 Metric의 주장
* 정적 구조를 런타임 전파 사실로 해석

## 3. Onboarding — Learn

목적: 시스템을 이해하기 위한 관점과 학습 순서를 제공한다.

| ID | Question                | Required Vocabulary       | Supporting Pattern    | Status                  |
| -- | ----------------------- | ------------------------- | --------------------- | ----------------------- |
| O1 | 이 시스템을 어떤 관점으로 이해해야 하나? | Perspective, Mental Model | 신규 모델 필요              | DESIGN PENDING          |
| O2 | 어디서 시작해야 하나?            | Entry Point (Naming Convention) | `ROOT_ENTRY_POINT`    | CONDITIONALLY VERIFIED |
| O3 | 어떤 순서로 따라가야 하나?         | Learning Path, Route      | 신규 모델 필요              | DESIGN PENDING          |
| O4 | 무엇을 먼저 읽어야 하나?          | Reading Order             | 신규 모델 필요 (`LEARNING_HUB` 기각) | PENDING / ORPHANED |

### Onboarding Boundary

Onboarding은 구조의 품질을 평가하는 보고서가 아니다.

목표는 관측된 구조를 학습자가 어떤 순서와 관점으로 탐색할 수 있는지를 표현하는 것이다.

특히 `LEARNING_HUB`는 Architect A2의 Dependency Mediation을 현재 지원하지 않는다.

따라서 A2에서 계약 불일치가 발견되었다는 사실만으로 O4의 적합성까지 자동으로 판단해서는 안 된다.

O4는 별도의 계약으로 검증한다.

## 4. Virtual Debug — Trace

목적: 특정 문제 또는 이벤트가 구조를 따라 어떤 경로로 전파되는지를 추적한다.

| D1 | 정적 의존성 구조상 어디까지 도달 가능한가? | Static Reachability, Reachable Node Set | `FailurePropagator` (BFS) | CONDITIONALLY VERIFIED |

### Virtual Debug Boundary

D1은 특정 이벤트의 경로를 추적한다.

다음 의미를 D1의 경로 증거로부터 자동 추론하지 않는다.

* Core
* Boundary
* Ownership
* Risk
* Priority
* Design Quality

정적 구조상의 경로와 실제 시뮬레이션/Trace 결과는 구분한다.

### A5와 D1의 Semantic Ownership 구분
* **A5 (`ARCHITECTURAL_CHOKEPOINT`)**: 경로 전체에서의 매개 위치를 다룬다. "어떤 노드가 정적 최단경로를 가장 많이 매개(Betweenness Centrality)하는가?"
* **D1 (Static Reachability)**: 특정 시작점에서의 도달 집합을 다룬다. "특정 노드에서 출발할 때 정적 의존성을 따라 어디까지 도달(Reachable Node Set) 가능한가?"

두 영역 모두 "전파(Propagation)"라는 단어를 쓰면 의미가 섞이게 되므로, A5는 **매개(Mediation/Concentration)**, D1은 **도달 가능성(Reachability)** 으로 어휘를 엄격히 분리한다.

## 🚀 .63 Roadmap (The Decision Support Evolution)

### Phase A-1: Question Exhaustive Audit (완료)
- 4대 보고서의 책임 경계(`Understand`, `Act`, `Learn`, `Trace`)를 획정하고, 목적과 가치 중립성에 어긋나는 질문들을 배제하여 최종 질문 목록을 고정했다.

### Phase A-2: Semantic Contract Dictionary (최우선 과제)
- 단순한 '금지어 사전'을 넘어, LLM이 관측된 증거를 뛰어넘어 임의의 주장(가치 판단 등)을 하는 것을 막기 위해 다음 수직 계약을 고정한다.
- `Question → Required Vocabulary (관측어) → Allowed Evidence → Supporting Pattern → Supporting Metric → Claim (Inference Boundary)`
- **우선순위**: A1 계약부터 하나씩 설계하며 SYNAPSE의 실제 코드/Metric과 1:1로 대응하는지 검증한다.

### Phase B: Pattern Inventory Audit
- 확정된 질문별로 기존 11개 패턴 중 재사용 가능한 패턴, 조합형 복합 패턴, 누락된 패턴을 분류한다.

### Phase C: Missing Pattern Design
- `Erosion(A4)`, `Extraction Point(E4)`, `Extension Point(E5)`, `Priority Model(E1)` 등 의사결정 지원을 위한 수학적 모델을 신규 설계한다.

### Phase D: Chokepoint 재방문
- Missing Pattern 설계가 완료된 후, `ARCHITECTURAL_CHOKEPOINT(A5)` 패턴을 다시 방문하여 임계치(Threshold)와 Pattern Contract를 최종 확정한다.

## 📝 A3 Semantic Contract Verification — VERIFIED

```text
A3. 어디서 구조적 경계가 관측되는가?
        │
        ▼
[Required Vocabulary]
Boundary Structure
Cohesion
Internal Connectivity
External Dependency
Boundary Classification
(※ 'Boundary Separation'은 위 Metric들의 조합 결과에 대한 상위 설명어로만 제한적 사용 가능)
        │
        ▼
[Scope]
전체 파일(Node)을 디렉터리 계층(Hierarchical Queue)으로 탐색하여 분리/승격된 모듈(Directory) 집단
        │
        ▼
[Allowed Evidence]
size (모듈 내 파일 개수)
internalEdges (내부 연결선 수)
inboundEdges (외부에서 모듈로 들어오는 연결선 수)
cohesion (내부 연결 / (내부 연결 + 외부 고유 클러스터 의존성))
targetConcentration (외부 의존성 집중도)
isMassive (물리적 거대함 여부)
        │
        ▼
[Supporting Pattern]
BOUNDARY_FORTRESS
BOUNDARY_CANDIDATE
(※ 동일한 Boundary 후보군에서 서로 다른 절대 임계치(OR 조건) 규칙으로 분류되는 패턴)
        │
        ▼
[Classification Rule]
* 프로모션 기본 조건: size >= 5 AND internalEdges >= 3 AND (cohesion >= 0.45 OR (cohesion >= 0.2 AND targetConcentration >= 0.5) OR isMassive)
* BOUNDARY_FORTRESS: cohesion >= 0.75 OR inboundEdges >= 100 OR isMassive
* BOUNDARY_CANDIDATE: cohesion >= 0.45 OR inboundEdges >= 30
        │
        ▼
[Claim Boundary (허용된 주장)]
"해당 디렉터리 기반 모듈에서 정의된 cohesion 및 외부 의존성 관련 지표가 Boundary 분류 임계치를 충족한다."
(이후 문맥에 따라 "이 모듈은 현재 분석 기준에서 구조적 경계 패턴으로 분류됩니다" 수준까지만 허용)
        │
        ├── ✕ "이 모듈은 아키텍처적으로 완벽하다" (Value Judgment 금지)
        ├── ✕ "이 모듈을 다른 모듈과 분리해야 한다" (Action Judgment 금지)
        └── ✕ "이 모듈은 마이크로서비스로 분리하기 위해 설계되었다" (Historical Intent 금지)
```
