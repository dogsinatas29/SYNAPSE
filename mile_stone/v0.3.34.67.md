### 🔍 권장 감사 순서 (Distribution Reconstruction Audit)

1. **[Phase 0] A2 Input Evidence Inventory**
   - 새 데이터를 만드는 것이 아니라, `a2_phase1_raw.json` 및 `snapshot.edges`/`nodes`에 이미 존재하는 정보(`sourceNode`, `targetNode`, `sourceBoundary`, `targetBoundary`)를 확인합니다.
2. **[Phase 1] Distribution Reconstruction**
   - Raw Evidence에서 `Contact Participation` (참여 노드 수)와 `Contact Concentration` (특정 노드에 기여도가 얼마나 집중되는지)를 재계산할 수 있는지 확인합니다.
3. **[Phase 2] Derived View Sufficiency Audit**
   - Contact Breadth, Contact Participation, Contact Concentration을 의미론적으로 분리하여 관측합니다.
   - 단, Concentration 관측을 Gateway나 Chokepoint로 의미론적 비약(Semantic Jump)하는 것은 철저히 금지합니다.
4. **[Phase 3] Information Loss Boundary**
   - Module-level `bothPairCount`에서는 사라졌지만, Raw Evidence에서는 완전히 재구성 가능한지 (Derived View), 일부 정보가 유실되는지, 아예 존재하지 않는지 경계를 파악합니다.
5. **[Phase 4] Core Model Decision**
   - 재구성 테스트 결과(CASE A, B, C)에 따라 Core Data Model 변경 여부를 결정합니다.

## 🛠️ 기술적 변경 사항
- **File Changes:** `scratch/` 영역에서 **A2 Distribution Reconstruction Audit** 스크립트 작성 및 실행.
  - 입력: `a2_phase1_raw.json`, `a2_phase2_normalized.json`
  - 검사 항목: Module별 distinctBoundaryPairCount, Participating Contact Node 수, Node별 Boundary Pair contribution 등.
  - 출력 형태: `{ moduleId, bothPairCount, participatingNodeCount, nodeContributionDistribution, reconstructionStatus }`

## ⚠️ 예외 처리 및 주의 사항
- **의미론적 점프 금지:** Contact Concentration(집중) 관측을 Architectural Intent(Gateway, Chokepoint)로 비약하지 마십시오.
- **분리 원칙:** `Derived View ≠ Core Evidence`. 계산 가능하다고 무조건 Core에 넣지 않고, Module 결과에 없다고 무조건 Core가 부족하다고 판단하지 않습니다.
- **미리 가정 금지:** CASE A(완전 재구성), CASE B(일부 유실), CASE C(완전 유실) 중 어느 것도 미리 가정하지 않고 순수하게 데이터의 재구성 가능성만 봅니다.
