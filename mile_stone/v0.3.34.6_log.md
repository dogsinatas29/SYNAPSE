### [10] 일부 클러스터 렌더링 시 Virtual Debug 진입 실패 버그 완벽 수정
- **파일:** `src/core/VirtualDebugger.ts`, `src/webview/CanvasPanel.ts`
- **내용:**
  - **증상:** "전체를 Expand해서 simulation debug하면 결과가 나오지만, 일부 클러스터만 띄워두고 작업하면 Simulation debug에 아예 진입을 안함 (신호가 안들어옴)"
  - **원인 1 (Hierarchical Matching 누락):** `VirtualDebugger`가 분석 대상 노드를 필터링할 때, 노드의 `cluster_id`와 UI에서 전달받은 `visibleClusterIds`를 **정확한 문자열 일치(Exact Match)**로만 비교. 즉 사용자가 부모 클러스터(예: `folder_src`)를 열었을 때 그 안의 자식 노드(`folder_src/webview` 등)는 일치하지 않아 **분석 대상 노드가 0개가 되는 현상**이 발생함.
  - **원인 2 (Report URL 오기입):** 분석 대상 노드가 0개라서 `System is stable` 결과가 나오더라도 `LOGIC_REPORT.md`가 열려야 하지만, 백엔드가 `report/LOGIC_REPORT.md`에 파일을 썼음에도 불구하고 `CanvasPanel.ts`가 `WORKSPACE_ROOT/LOGIC_REPORT.md`를 열려고 시도하다가 조용히 예외(Exception)를 뱉고 실패함. 사용자는 아무런 피드백도 받지 못해 멈춘 것으로 인식함.
  - **해결 방안:** 
    1. `VirtualDebugger.ts`에서 부모 클러스터만 켜져 있어도 자식 경로의 노드들이 전부 포함되도록 `lastIndexOf('/')`를 이용한 역추적 계층 매칭(Hierarchical Matching) 로직 추가 적용 완료.
    2. `CanvasPanel.ts`에서 `reportUri` 경로를 `report/LOGIC_REPORT.md`로 정상 수정.

### [11] 하위 호환성 버그 (Legacy Cluster IDs) 완벽 수정
- **파일:** `src/core/VirtualDebugger.ts`, `src/core/analysis/ClusterBridgeAnalyzer.ts`, `ui/canvas-engine.js`, `src/webview/CanvasPanel.ts`
- **내용:**
  - **증상:** 여전히 "Parent/child 관계가 끊어져서 같은 레벨로 평탄화되어 표시됨" 및 "Simulation debug 진입 불가".
  - **원인:** 과거 버전에서 생성된 `project_state.json`의 클러스터 ID(`cli/src` 등)는 새로운 `folder_` 접두사 포맷(`folder_cli_src`)을 따르지 않으며 `parent_id` 정보조차 존재하지 않음. 이 레거시 데이터가 최신 그래프(coreSnap)를 덮어쓰면서(Overwrite) 계층이 깨지고, `VirtualDebugger`의 `lastIndexOf('/')` 슬래시 기반 역추적 로직이 `folder_` 포맷을 인식하지 못해 매칭에 실패함. 게다가 중간 폴더(Intermediate Folders) 자체가 레거시 상태에서는 누락되어 있어 루트 레벨로 강제 이동됨.
  - **해결 방안:**
    1. **`canvas-engine.js` (UI 계층 복구 & 중간 폴더 자동 생성):** `c.parent_id`가 없을 경우 `c.id` 문자열을 분석하여 슬래시(`/`) 기반 레거시 포맷과 언더스코어(`_`) 기반 신규 포맷 모두에서 올바른 부모 ID를 추론하도록 개선. 만약 추론된 부모 폴더가 기존 `idMap`에 존재하지 않을 경우(과거 레거시에서 누락된 중간 폴더), 이를 온더플라이(On-the-fly)로 생성하여 `this.clusters`에 동적 주입함으로써 완벽한 트리 구조를 재건(`createMissingAncestors` 로직 추가).
    2. **`VirtualDebugger.ts` & `ClusterBridgeAnalyzer.ts`:** 문자열 파싱에만 의존하던 기존 방식에서 탈피하여, `state.clusters`로부터 명시적인 `parent_id` 매핑 맵(`parentMap`)을 구성. 이를 최우선으로 사용하여 상위 클러스터를 정확히 역추적하고, `parent_id`가 없는 경우에만 `/` 및 `_` 기반 문자열 분리를 수행하도록 2중 안전 장치(Fallback) 마련 완료.
    3. **`CanvasPanel.ts`:** `ClusterBridgeAnalyzer.analyzeVisibleClusters` 호출 시 `allClusters` 배열을 넘겨주어 분석기가 정확한 `parent_id` 트리를 구성할 수 있도록 수정.

### [12] Virtual Debug 진입 시 Silent Timeout 통신 버그 픽스
- **파일:** `ui/canvas-engine.js`, `src/webview/CanvasPanel.ts`
- **내용:**
  - **증상:** 사용자가 `Simulation Debug` 버튼을 누르면 로그나 에러 메시지 전혀 없이 묵묵부답으로 멈추는(아무 일도 일어나지 않는) 현상.
  - **원인:** 백엔드(`CanvasPanel.ts`)가 분석 전 최신 상태를 얻기 위해 웹뷰로 `requestContextData` IPC 메시지를 발송하나, 정작 `canvas-engine.js`의 `handleMessage` 스위치 문에 해당 메시지를 수신하는 케이스가 누락되어 있어 웹뷰가 응답하지 않음. 백엔드는 5000ms 동안 대기하다가 Timeout으로 간주하고 비어있는 상태(Empty State)를 반환하여 분석이 아무 노드 없이 조용히 종료됨.
  - **해결 방안:** `canvas-engine.js`에 `requestContextData` 핸들러를 추가하여 백엔드 요청 시 현재 화면의 `nodes, edges, clusters` 스냅샷을 즉시 반환하도록 수정 완료.

  - **증상:** 웹뷰 콘솔에 `RAF_LOOP: [숫자]` 형식의 로그가 초당 60회씩 끝없이 도배되며, 중요한 이벤트 신호(버튼 클릭 등)가 파묻혀 보이지 않고 리눅스 커널 등 대형 프로젝트 로드시 심각한 렉(프레임 저하)을 유발함.

  - **해결 방안:** 성능 병목 및 로그 식별 방해의 주범인 해당 콘솔 카운트 출력 코드를 완전히 삭제 조치함. 더불어 Simulation Debug 버튼 동작 여부를 시각적으로 확인할 수 있도록 명시적인 UI 로깅(`console.log`)을 추가함.

  3. **Coupling Strength:** 특정 클러스터 간(예: block ↔ drivers)의 실질적인 결합 강도를 도출하여 "어디가 진짜로 강결합인가"에 대한 지표 확보 성공.
- **아직 가치가 증명되지 않은 / 개발이 필요한 가치:**
  1. **Coupling Density:** Density 값(절단 지점 개수)의 실무적 유의미성은 향후 다양한 프로젝트(VSCode Main 등)에서의 추가 테스트를 통해 검증이 필요함.
  2. **Investigation Order:** 현재는 단순 정렬 기준(가장 큰 SCC, 가장 강한 Bridge 등)에 불과하며, 실질적인 "조사 순서 계산 엔진"은 아님.
  3. **Intervention Simulator (v0.3.34.7):** 현재 리포트에 표기된 "Top Intervention Targets"는 특정 엣지 절단 시 파급력(Impact)을 보여주며 매우 유용함을 입증함. 단, 이는 어디까지나 측정(Measure)의 연장선이며, 본격적인 "이렇게 하면 이런 일이 생긴다" 식의 완전한 시뮬레이션(Flight Simulator) 예측 엔진 고도화가 34.7의 핵심 미션임.
- **우선순위 최종 결론:** SYNAPSE의 가장 큰 사업적 차별화는 AST(이미 좋은 툴이 많음)가 아니라, **"이 모듈을 자르면 어떻게 되는가"를 보여주는 능력**임. 따라서 `34.6 (Coupling Measurement) → 34.7 (Intervention Simulator) → 34.8 (AST Microscope)` 순서가 가장 이상적임. 34.7이 완성될 때 비로소 SYNAPSE는 "구조를 보여주는 툴"에서 **"아키텍처 의사결정 지원 툴"**로 격상될 것임.
