## 🧠 배경 및 문제 정의 (Context)
3개 프로젝트 교차 테스트 결과, SYNAPSE 엔진 자체는 이미 프로젝트별로 유의미하고 상이한 풍부한 구조적 증거(Structural Evidence)를 생산하고 있음이 입증되었습니다 (`.70` 마일스톤 성과). 

그러나 현재의 **Report Layer**는 그 데이터가 **어떤 질문(Question)에 답하기 위해, 어떤 용어(Vocabulary)를 빌려, 어떤 패턴(Pattern)을 검증하여 나온 것인지**에 대한 추론의 계보(Lineage)를 모두 생략한 채 결과만 출력하고 있습니다.

가장 중요한 근본적 오류는 **보고서의 목적을 "LLM에게 밀어넣을 데이터 덤프"로 오해했다는 점**입니다. 
SYNAPSE 보고서의 최종 소비자는 LLM이 아니라 **사람(Human)**입니다. 사람은 질문과 패턴의 맥락 없이 나열된 수만 개의 엣지와 랭킹(Report A/B)을 보면 "그래서?"라는 인지 부하를 겪게 됩니다.

## 🛠️ 핵심 설계 및 로직 (The 71 Contract)

### 1. SYNAPSE 보고서의 본질: "판단용 인터페이스"
보고서는 데이터를 복사해 두는 곳이 아닙니다. 질문 중심의 목차(Index)이자, 사람이 판단을 내리기 위한 인터페이스입니다. 상세한 증거 데이터는 본문에서 제거하고 외부 HTML(또는 별도 뷰어)로 격리(Externalize)합니다.

### 2. Analysis Contract 템플릿 (보고서 최소 단위)
앞으로 보고서의 각 섹션은 단순한 데이터 목록이 아니라, 다음의 Analysis Contract 템플릿을 따릅니다.

```markdown
## [Question ID] — [Question Title]

Question:
<question text>

Vocabulary:
<required vocabulary>

Pattern:
<pattern>

Finding:
<Verified finding summary, or "No verified finding emitted.">

[View Evidence](evidence_viewer.html?q=A1)
```

### 3. 단계별 마이그레이션 계획 (Step 1~7)

- **Step 1:** `Question Dictionary` 확정 (A1, A3, A5, E2, O2 등)
- **Step 2:** 각 질문에 `Question Contract` 연결 (Vocabulary, Allowed Evidence, Supporting Pattern, Claim Type 매핑)
- **Step 2-A:** `Contract` ↔ 기존 런타임 구현 간 2차 교차 검증 (DOCUMENTED / IMPLEMENTED / RUNTIME VERIFIED 엣지 케이스 점검)
- **Step 3:** 런타임 렌더러에서 Report에 해당 Contract 렌더링 (A3 등의 MISMATCH를 실질적으로 해결)
- **Step 4:** 기존 마크다운 본문에서 거대한 데이터 덤프(Report A/B, Cross-Boundary Reference) 제거
- **Step 5:** 기존 HTML 생성 경로(`ValidationReportBuilder.buildHtml` 등) 복구 및 분리
- **Step 6:** 마크다운 본문의 `[View Evidence]` 링크와 HTML 뷰어 연결
- **Step 7:** 3개 프로젝트(VSCode, AntennaPod, Godot)의 실제 출력 산출물을 통해 파이프라인 검증

### 4. 질문 종류에 따른 유연한 Contract 매핑 (Semantic Law)
모든 질문이 반드시 Pattern-level Claim을 가져야 하는 것은 아닙니다.
- **Observation Question (예: 경계는 어디에 있는가?)** -> Pattern: `Structural Boundary Observation` (Claim 불필요)
- **Validation Question (예: 어떤 경계가 요새화되었는가?)** -> Pattern: `BOUNDARY_FORTRESS` (Claim 필요)

## ⚠️ 예외 처리 및 주의 사항 (Constraints)
- **[Rule 0 - No Assumption]** : 이 렌더링 계약을 채우기 위해 LLM에게 새로운 해설문이나 추론("따라서 core부터 분석하는 것이 좋습니다")을 작성하게 하지 않습니다. 
- **빈칸은 빈칸으로 둔다**: 상태가 `NOT VERIFIED`라면, 억지로 Finding을 지어내지 않고 상태 자체를 결과로 렌더링합니다. (마크다운에만 명시하고 HTML 증거는 생성하지 않음)
- **UI 소유권의 엄격한 분리 (UI Ownership)**: 정보의 중복(Copy)을 막고, 3계층 모델에 따라 렌더링 책임을 나눕니다.

| Layer | 컴포넌트 | 소유 정보 (Responsibility) | 출력 형태 |
|---|---|---|---|
| **Layer 1** | **Markdown Report** | `Question`, `Vocabulary`, `Finding Summary` | 사람이 읽는 질문과 최종 발견된 갯수 (요약본) |
| **Layer 2** | **HTML Viewer** | `Pattern` | 검증된 패턴 이름과 해당 패턴에 속한 Target 노드 목록 |
| **Layer 3** | **HTML Viewer** | `Evidence` | 각 Target의 구체적인 Raw Metadata (수치, Metric) |

*(※ Markdown에는 Pattern 리스트나 Evidence가 절대 침범하지 않으며, HTML에는 Question/Vocabulary나 NOT VERIFIED 빈칸 섹션이 존재하지 않습니다. Markdown에서 결론이 있는 경우에만 HTML로 링크합니다.)*

- **증거의 외부화(Externalization)**: 증거를 마크다운 본문에 구구절절 설명하지 않습니다. 상세 데이터는 반드시 외부 뷰어로 넘기고(Drill-down), 마크다운은 추론의 흐름(Lineage)만 유지합니다.
- **Legacy HTML 활용의 한계**: 과거 `ValidationReportBuilder.buildHtml` 코드를 재사용하되, **CSS/Table UI/Layout 등 렌더링 자산(Infrastructure)만 재활용하고 기존의 Semantic Content Model(과거 ASR의 Warning/Risk 등)은 철저히 폐기/재설계합니다.**

## ✅ 성공 기준 (Success Criteria)
- 보고서가 단순히 "예뻐지는 것"이 아니라, `Question → Vocabulary → Pattern → Finding → Evidence`의 연결이 실제 런타임 산출물에서 끊어지지 않아야 합니다.
- Pattern 상태가 `NOT VERIFIED`일 때, Evidence 링크가 존재하더라도 마크다운 보고서 본문이나 HTML 증거 뷰어가 이를 "검증된 것처럼" 포장하거나 표현하지 않아야 합니다.

## 📝 Post-Work Log (작업 후 기록)
- **Step 3 (A3 Pilot) 검증 완료**: A3(Structural Boundaries) 질문에 대한 Contract 렌더링 파이프라인 검증 성공.
  - **발견된 결함 및 수정 (Dual Defect)**:
    - **결함 A (Producer)**: `InsightEngine`이 A3에 필요한 `BoundaryPatternDetector`를 실행하지 않고 있던 구조적 결함을 수정.
    - **결함 B (Consumer)**: `FindingReportAdapter`가 A3의 계약 대신 `CROSS_BOUNDARY_REFERENCE`를 하드코딩으로 소비하던 문제를 수정.
  - **의의**: A3 렌더러 리팩토링뿐만 아니라 `Question → Contract → Detector → InsightEngine → Adapter → Markdown`의 전체 계보를 온전히 복구함. 또한 `Observation`과 `Pattern Verification`의 상태 분리를 실제 출력물로 증명함.
- **Step 4~7 (전체 확장 및 레거시 제거) 검증 완료**: A1, A5, E2, O2 전체 렌더링 계보 복구 및 UI 소유권 완전 격리.
  - **레거시 잔재 제거**: `ReportBundleGenerator.ts` 내부의 구형 하드코딩 렌더러(Architectural Findings 덤프, Onboarding N/A 표시, SCC Validation Claims 등)를 전면 삭제.
  - **E2 시뮬레이션 경로 복구**: `SIMULATION_DEBUG` 렌더링 시 남아있던 `findings.length > 0` 가드 때문에 E2(Change Amplifier) 섹션이 누락되던 결함 수정.
  - **NOT VERIFIED 감사(Audit) 가시성 확보**: HTML Evidence 뷰어에서 인스턴스가 0건일 때(NOT VERIFIED) "빈칸"으로 버려두지 않고, `Expected Patterns`와 `Pattern Instances Found: 0`을 명시적으로 출력하여 "검사하지 않음"과 "검사했으나 발견되지 않음"을 완벽하게 구분.
  - **의의**: "NOT VERIFIED도 중요한 관측 결과다"라는 SYNAPSE 철학을 런타임 결과물(Real Graph Dataset)로 증명하고, 마크다운 뷰어와 HTML 증거 뷰어의 역할을 완전 분리(PROVEN)함.
