# v0.3.34.73 — P1 Resolver Audit: Read-Only Investigation Report

## 작업 1 — 실제 코드 경로 추적

| 컴포넌트 | 기능 및 실행 경로 |
| :--- | :--- |
| **`ReferenceResolver.ts`** | `GhostPolicy`에서 정제된 `ReferenceWithSource[]`를 입력으로 받음.<br>- **원본 경로**: `ref.target`<br>- **정규화**: 상대 경로(`.`, `..`)를 sourceFilePath 기준으로 정규화하고, VSCode 모듈(`vs/` -> `src/vs/`) 하드코딩 처리, 확장자 복원(`.ts`, `.js` 등) 수행.<br>- **대상 노드 검색 키**: 정규화된 `targetNodeId`.<br>- **검색 결과**: `SymbolIndex` 또는 `existingNodeIds`에서 조회. 실패 시 `resolutionKind = 'unresolved'` 할당. |
| **`GhostExpander.ts`** | `ResolvedReference[]`를 입력받아 Ghost 노드를 생성.<br>- **Ghost 판정 조건**: `ref.resolutionKind === 'unresolved'` 이고, 해당 경로가 디렉터리로 쓰이거나 이미 존재하는 노드가 아닐 경우 Ghost 노드로 확정 (`isGhost = true`). |
| **`GhostClassifier.ts`** | 생성된 Ghost 노드들을 분석하여 분류.<br>- `makeExternalSemantic()`를 호출해 대상 문자열을 정규식 기반으로 분류 (`ExternalEcosystem`, `ExternalOriginType`).<br>- 내부 파일 존재 여부를 직접 파일 시스템에서 검사하지 않으며, 단순히 문자열 기반으로 `validExternal`, `resolvableInternal`, `parserArtifact`로 휴리스틱하게 판정함. |
| **`EdgeBuilder.ts`** | `ExpandedReference[]`를 입력받아 최종 엣지 생성.<br>- **최종 엣지**: `from: ref.sourceId`, `to: ref.targetId`<br>- 대상이 Ghost 노드(`unresolved`)인 경우에도 동일하게 엣지를 생성하여 그래프에 주입함. |
| **`DataPipeline.ts`** | 위 클래스들을 순차적으로 호출하며, OOM(Out of Memory) 방지를 위해 각 단계가 끝나면 배열을 명시적으로 비움(`length = 0`). |

## 작업 2 — 기존 데이터 조사 (스키마 한계 확인)

현재 저장소에 남아 있는 덤프 파일들(`diagnostic_trace.json`, `allFindings.json`, `04_RAW_DATA.json`)의 스키마와 내용을 분석한 결과는 다음과 같습니다.

- **`diagnostic_trace.json`**: `DetectorComplete`, `DetectorStart`, `EvidenceCreated`, `FindingCreated` 등 패턴 탐지기(Detector) 레벨의 로직만 기록되며, **리졸버의 참조 해석 과정(Resolver Trace)은 일절 포함되지 않습니다.**
- **`04_RAW_DATA.json`**: 최종적으로 완성된 그래프의 Node(Ghost 포함)와 Edge 목록만 가지고 있습니다.
- **역추적 불가 판정**: `DataPipeline.ts` 458번 라인에서 메모리 최적화를 위해 `resolvedReferences.length = 0`으로 데이터를 삭제하고 있으므로, 기존 덤프만으로는 `원본 참조 → 해석된 경로 → 최종 Ghost`로 이어지는 생애주기를 **역추적할 수 없습니다.** (대상 파일 존재 여부를 매핑 실패와 연결 지을 수단이 기존 데이터엔 없음)

## 작업 3 & 4 — Ghost 분류 및 산출물 (P1 진행 결과 요약)

1. **실제 호출 경로와 Ghost 판정 조건**: 위 작업 1에 명시된 대로, `ReferenceResolver`의 `symbolIndex` 및 `existingNodeIds` 검색 실패가 곧바로 `unresolved`로 직결되고, 이는 `GhostExpander`에서 아무런 파일시스템 체크 없이 무조건 Ghost 노드로 승격됩니다.
2. **기존 덤프의 스키마 및 역추적 가능성**: 역추적 **불가능**. 기존 덤프에는 원본 소스의 `rawTarget`과 정규화 실패 사유를 매핑할 필드가 없습니다.
3. **분류표 작성을 위한 제약**: 현재 데이터만으로는 `INTERNAL_TARGET_EXISTS`(경로 정규화 실패)와 `INTERNAL_TARGET_MISSING`(실제 누락)을 완벽하게 구분할 수 없습니다.

### ⚠️ 다음 단계 (P2) 진입을 위한 필수 선제 조건
사용자님의 지시대로 코드 수정 없이 Read-Only로 분석한 결과, **"기존 데이터만으로는 내부 파일 존재 여부와 매핑 실패 사유를 역추적할 수 없다"**는 팩트가 도출되었습니다. 

따라서 P2(내부 참조 매핑 정확도 검증)에서 정답률을 측정하기 위해서는, `DataPipeline.ts`에서 삭제되는 `ResolvedReference` 데이터를 가벼운 JSON 파일(예: `05_RESOLVER_TRACE.json`)로 덤프하는 **[관측용 로그 덤프 코드 추가]**가 불가피합니다.
