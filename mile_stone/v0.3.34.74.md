# 🚀 Milestone v0.3.34.74 - Architecture Metric Verification & Engine Core Fixes
## 📅 작업 정보
- **상태:** 🏗️ Planned 
- **관련 마일스톤:** v0.3.34.73
- **목표:** v0.3.34.73에서 고정된 지표 추출 로직을 바탕으로, 각 Evidence(증거)와 관측값이 아키텍처적 주장(Claim)으로 연결될 수 있는지의 '타당성(Validity)'을 독립적으로 검증하고, 파이프라인의 알려진 필터링 버그를 수정한다.

## 🧠 검증 과제 (Validation Targets) 및 작업 범위

### 1. A3 격리성 분류 (Isolation Validity)
- **목적:** Fan-In이 높은 경계(Boundary)와 실제 컴포넌트의 격리성(Isolation)을 구분.
- **검증 내용:** 현재 `Fan-In` 수치나 단방향 의존성 등 특정 지표가 "해당 컴포넌트가 시스템에서 안전하게 격리되어 재사용 가능하다"는 주장을 온전히 뒷받침할 수 있는가?

### 2. 패턴 간 교차 검증 (Cross-Pattern Verification)
- **목적:** 서로 다른 패턴(A1, A2, A3, A5 등)이 동일한 노드(모듈)를 어떻게 설명하고 있는지 충돌 여부 확인.
- **검증 내용:** 예를 들어, A1(Core)로 판정된 노드가 A5(God Object)나 A3(Isolated)와 중복 판정되었을 때, 이 패턴들이 서로 모순되는 주장을 하고 있지 않은지 교차 점검.

### 3. E2 지표 의미 (Complexity Score)
- **목적:** `complexityScore`가 진정한 '변경 증폭(Change Amplifier)'이라는 주장에 대한 근거 확인.
- **검증 내용:** 복잡도가 높다고 해서 반드시 변경이 증폭되는가? 변경 증폭을 증명하려면 결합도(Coupling)나 커밋 이력 등 추가적인 컨텍스트나 다른 지표가 필요한지 검토.

### 4. O2 그래프 방향 (Entry Point Validity)
- **목적:** `inDegree=0`의 의미가 실제 소프트웨어의 의존 관계 및 실행 진입점(Entry Point)과 일치하는지 검증.
- **검증 내용:** 아무도 호출하지 않는 모듈(`inDegree=0`)이 반드시 시스템의 진입점인가? 단지 데드 코드이거나, IoC(Inversion of Control) 컨테이너에 의해 동적으로 로드되는 모듈은 아닌지 구분할 기준 마련.

### 5. Evidence 표현 (Consistency of Presentation)
- **목적:** 관측값(Observation), 선정 조건(Condition), 패턴 주장(Claim) 간의 연결 일관성 유지.
- **검증 내용:** 보고서상에서 "어떤 원시 데이터를 바탕으로(관측값) -> 어떤 룰을 거쳐(선정 조건) -> 어떤 결론에 도달했는지(패턴 주장)"가 논리적 비약 없이 일관되게 표현되는지 렌더링 검토.

### 6. [FIX] P3 Root Cause: Data Pipeline Parsing Bug (Chromium 4,172 Ghost Nodes)
- **목적:** `session_*` 파일 및 기타 예약어 기반 휴리스틱 필터링으로 인한 정상 소스 파일 누락 문제 수정.
- **구현 계획:**
  - `src/core/NodeBuilder.ts` 내의 `fileName.startsWith('session_')` 필터 제거 혹은 확장자 방어(예: `.json`에만 적용) 추가.
  - `src/bootstrap/BootstrapEngine.ts` 내의 `logic_report` 및 `synapse` 필터링이 일반 소스코드에 영향을 주지 않도록 정밀화 (`synapse.config.json`의 Blacklist 의존성 강화).

# 🚀 Milestone v0.3.34.74 - ReferenceResolver Fallback Implementation (UNIQUE_EXACT_MATCH C++ Includes)

## 📅 작업 정보 
- **상태:** ✅ Completed
- **관련 마일스톤:** v0.3.34.73
- **목표:** 기존에 External로 잘못 분류되어 Ghost 노드로 쌓이던 프로젝트 내부의 미해석 C++ include 참조(`UNIQUE_EXACT_MATCH` 및 `PathResolutionFailure`)들을, C++ 컴파일러와 유사하게 Project Root 기반 탐색을 통해 복구한다. 이를 통해 Ghost 수를 대폭 감소시킨다.

## 🧠 상세 설계 및 로직 
- `ReferenceResolver.ts`에 기존 상대 경로 및 Symbol Index 탐색 실패 시 `projectRoot`를 기반으로 물리적 파일 존재 여부(fs.existsSync)를 확인하는 fallback 로직 구현.
- `existingNodeIds`에 등록되지 않았더라도 물리적으로 존재하는 타겟 헤더는 Ghost(External)가 아닌 `direct`로 분류하여 스캐너의 누락(Scannable하지만 AST 파이프라인에서 생성되지 않은 파일 등)을 올바르게 드러내도록 설계.
- 기존의 Godot `Ghost Root Clumping` 방지를 위한 C/C++ 내부 참조 부모 경로 첨부 기능을 훼손하지 않도록 분기 로직 삽입 위치를 세밀하게 조정.
- 파일 탐색 과정에서 `fs.existsSync` I/O 오버헤드를 최소화하기 위해 `isCppHeader`인 경우 및 `projectRoot`가 존재하는 경우로 한정지어 성능 병목 방지.

## 🛠️ 기술적 변경 사항 
- **Node Update:** 물리적으로 존재하는 `unresolved` 참조 노드들이 External Ghost에서 `direct` 내부 참조 타겟으로 승격.
- **Edge Update:** 
  - `PathResolutionFailure`로 분류되던 include dependency Edge들이 프로젝트 내부 타겟 노드를 가리키도록 올바르게 연결됨.
- **File Changes:** 
  - `src/core/ReferenceResolver.ts`: Fallback 단계 (`// [v0.3.34.74] Fallback: C++ Project Root Base Search`) 및 `existingNodeIds`에 없어도 물리 파일이 존재하면 direct를 유지하는 검증 조건 보강.
  - `src/core/ReferenceResolver.ts`: `{`와 `}` 블록 구문 스코프 수정 및 TSError(brace mismatch) 구문 교정 완료.

## ⚠️ 예외 처리 및 주의 사항 
- **ReadOnly File System 제약 (EROFS)**: Godot 스냅샷 환경 내 I/O 저장이 실패하더라도, Bootstrap 런타임 내 메모리 Graph 상에서는 External Ghost 수치가 정상 감소하며 `Unverified References` 또는 내부 연결로 보존되어야 함.
- **성능 병목**: `existsSync`의 무분별한 호출을 방지하기 위해 `isCppHeader`(`endsWith('.h', '.hpp', '.inc', '.inl' 등)`) 조건을 먼저 만족할 때만 호출하도록 제한.

## 📝 Post-Work Log (작업 후 기록) 
- `ReferenceResolver.ts` 내부의 블록 및 `return` 구문 괄호 매칭 에러(TS1005, TS2366) 픽스 및 `npx tsc --noEmit` 통과 확인.
- C++ 프로젝트 (`Body.inl`, `core_bind.compat.inc` 등) 대상의 Reference Resolver Fallback 적용 완료.
- 실측 검증 시, `cluster_ghost_unverified` 내부의 1,416개 Ghost 중 277건(`UNIQUE_EXACT_MATCH`) 및 `PathResolutionFailure` 항목이 복구되는 것을 목표로 하였으며, 엔진 내부 변경 완료.

- **실행 전제:** 본 계획서는 순수 설계 명세이며, 사용자의 별도 명시적 실행 승인 전까지 코드 수정 및 실행은 전면 동결된다.

### 2. 세부 검증 시나리오 및 통과 기준

#### 시나리오 A: 정상 경합 경로 (Normal Concurrency Race)
- **실행 조건:** 동일한 출력 경로를 대상으로 2개의 프로세스를 `SYNC_PUBLISH_BARRIER` 환경변수 하에 동시 기동. 양측의 `ready` 마커 확인 후 `release` 마커를 발행하여 동일 시점에 `os.link` 호출.
- **통과 기준 (Assertions):**
  1. 두 프로세스의 `outputWriteErrorsCount` 정렬 결과가 정확히 `[0, 1]`일 것 (1 승자, 1 패자).
  2. 승자 프로세스는 종료 코드 `0` 또는 감사 검증에 따른 상태를 유지하고 출력 파일을 정상 영구화할 것.
  3. 패자 프로세스는 커널 `FileExistsError(EEXIST)`에 의해 즉시 `FAIL` 처리되고 `output_write_errors`에 충돌 에러가 100% 동기화될 것.
  4. 게시된 `out.json`이 유효한 JSON 구조를 유지하고 0바이트 손상/절단이 없을 것.
  5. 패자 프로세스의 임시 파일이 디스크에 잔존하지 않고 청소될 것 (`lingering_tmps == 0`).

#### 시나리오 B: 타임아웃 Fail-Closed 경로 (Timeout Fail-Closed Path)
- **실행 조건:** `SYNC_PUBLISH_BARRIER` 환경변수가 설정되었으나, 테스트 러너가 의도적으로 `release` 마커를 생성하지 않고 타임아웃(5초)을 유도.
- **통과 기준 (Assertions):**
  1. 프로세스가 5초 경과 후 암묵적으로 게시(`os.link`)를 진행하지 않고 **게시를 즉시 중단(Abort)**할 것.
  2. 타임아웃 발생 시 `output_write_errors`에 `Barrier timeout expired without release signal` 에러를 명시 기록하고 종합 상태 `overallTreeIntegrityStatus = "FAIL"`을 반환할 것.
  3. 목적지 경로에 어떠한 파일도 생성되지 않아야 하며, 생성 중이던 임시 파일은 100% 삭제 정리될 것 (`lingering_tmps == 0`).

#### 시나리오 C: 사후 정리 실패 경로 (Post-Publish Cleanup Failure Path)
- **실행 조건:** `os.link()` 성공 후 `os.remove(tmp_path)`에서 예외가 모의 주입되는 경우.
- **통과 기준 (Assertions):**
  1. 게시 자체의 성공(목적지 파일 존재 및 무결성)과 사후 정리의 실패(임시 파일 잔존 경고)가 오류 메시지에서 명확히 분리 표기될 것.
  2. 종합 판정은 보수적 안전성 원칙에 따라 `FAIL`로 경고 처리될 것.

## 🔬 [설계] SYNAPSE 외부 스크립트 통합 분류 프레임워크 (External Script Integration Framework)

### 1. 목적 및 기본 경계
- **목적:** 외부 스크립트를 엔진에 무분별하게 통합하는 대신, 7대 분류 체계(`V/D/E/R/A/O/U`)와 11대 검토 기록 양식을 통해 통합 적합성과 책임 경계를 사전에 평가한다.
- **경계 분리:** 본 프레임워크는 순수 문서·설계 검토이며, 코드 수정, 스크립트 실행, 대상 소스 트리 접근을 일체 수반하지 않는다. EXP-C `STRICT FREEZE`와 완전히 독립된 트랙으로 운영된다.

### 2. 7대 외부 스크립트 분류 체계
- **`V (Validation)`:** 기존 결과의 정확성·정합성 검증 (우선 통합 후보)
- **`D (Diagnostic)`:** Ghost, resolver, 필터링 등 원인 추적 (엔진 결과와 대조 후 판단)
- **`E (Evidence)`:** 원본 데이터, 계산식, 판정 근거 연결 (공통 증거 계약 후보)
- **`R (Regression)`:** 변경 전후 결과 비교 및 불변 조건 확인 (반복성 확인 후 판단)
- **`A (Analysis)`:** 프로젝트별 탐색, 일회성 가설 검증 (독립 유지 우선)
- **`O (Orchestration)`:** 복수 스크립트 실행 순서 및 결과 취합 (의존성 검토 후 판단)
- **`U (Unknown)`:** 목적·입출력·책임 불명확 (통합 보류, 임의 통합 금지)

### 3. 스크립트별 11대 검토 기록 규격
1. `식별 정보`: 파일 경로, 버전/커밋
2. `목적`: 검증 가설 및 해결 문제
3. `입력 계약`: 읽어들이는 스냅샷/설정 명시
4. `출력 계약`: 산출 JSON 스키마/상태값 명시
5. `책임 분류`: V/D/E/R/A/O/U 배정
6. `중복 관계`: 엔진/타 스크립트와의 중복 여부
7. `부작용 위험`: 파일 변경/프로세스 실행 여부 (비파괴성)
8. `실패 처리`: 에러/타임아웃의 안전한 Fail-Closed 처리
9. `검증 상태`: 보고됨 / 문서 검토 / 독립 검증
10. `권고 방향`: 유지 / 정리 / 통합 후보 / 보류
11. `미확인 사항`: 판단 출처 및 잔여 질문

## 📋 [계획] P1 증거 등록부 - §114 공식 원장 상호 연계 및 사전 스키마 정합성 규격 (Pre-Schema Alignment Specification Plan)

### 1. 목적 및 기본 경계
- **목적:** P1 증거 등록부(11대 필드 규격)와 §114 공식 결함 및 미해결 원장(10대 필드 규격) 간의 개념적 참조 관계를 정립하고, 필드 혼동(`verification_status` vs `evidence_level`, `verification_scope` vs `verification_method`)을 방지하는 정합성 구조를 정의한다.
- **엄격한 경계 통제:** 본 계획은 순수 문서상 사전 스키마 검토이며, 실제 파일 열람, 해시 계산, 파일시스템 순회, 스크립트 실행, 프로덕션 코드 수정을 일체 수반하지 않는다. EXP-C `STRICT FREEZE` 및 P6 `NOT APPROVED` 상태를 영구적으로 준수한다.

### 2. P1 vs §114 스키마 분리 및 참조 원칙
- **독립 필드 분리:**
  - `P1.verification_status` (거버넌스 검증 상태)와 `§114.evidence_level` (증거 강도 등급)은 결코 동일시되지 않으며 독립 필드로 유지된다.
  - `P1.verification_scope` (확인 적용 경계)와 `§114.verification_method` (확인 도구/기법)는 개별 물리량으로 분리 유지된다.
  - `P1.governance_impact`와 `§114.technical_status`는 직접 매핑을 배제하고 독립 기록 및 상호 참조 관계로 유지된다.
- **존재 상태의 이중화:**
  - `reported_presence_status`: 제공된 기록에서 보고된 존재 상태 (`REPORTED_PRESENT`)
  - `independent_presence_status`: 실제 파일의 독립 확인 여부 (`UNVERIFIED` 유지)
- **해시 3분할 및 결측 규칙:**
  - `hash_value`: 64자리 hex 또는 `null` (결측 상태 표기)
  - `hash_applicability`: `APPLICABLE`, `NOT_APPLICABLE` (비적용 근거 확인 시에만 사용), `UNDETERMINED`
  - `hash_verification_status`: 독립 실측 전까지 `UNVERIFIED` 보존
- **원장 보고값 보존:**
  - `§114.evidence_level`의 `CONFIRMED_CONTRACT_DEFECT` 등은 원장 보고값(`REPORTED_LEDGER_VALUE`)으로 보존하되, 의미적 혼재 해소를 위해 `PROPOSED_ENUM (PENDING_REDEFINITION)` 상태로 관리한다.

### 3. 단계별 추진 로드맵
1. **P1 사전 스키마 정합 초안 동결:** `PRE_SCHEMA_SPECIFICATION_FINAL_ALIGNMENT_DRAFT` 상태 유지 (문서상 구조적 정합성 통과, 공식 등재 보류).
2. **P2 Gate 1 및 기준선 공백 분석 준비:** 역사적 증거 소실 경위 및 과거 실행 격리 한계 명세화.
3. **P3 Gate 2 Safety Contract v2.5 대조 준비:** 5대 안전 계약 미충족 항목 정밀 문서 대조.
4. **P4 R07 A/B/C 검증 규격서 작성 준비:** 배리어 타임아웃 5초 Fail-Closed 검증 조건 정의.
5. **P5 실행 경계 및 승인 체크리스트 검토:** 파이프라인 안전성 요건 명문화.

### 4. 최종 상태 및 4대 판정 우선순위 규격 (계층 및 경계 분리)
- **단락(Short-circuit) 실행과 NOT_EXECUTED 규칙:**
  - `NOT_EXECUTED`는 단지 선행 단계 실패나 기한 초과 등으로 인해 후속 검사가 수행되지 않았음을 나타내는 실행 상태 마커일 뿐이며, 그 자체만으로 `FINAL_FAIL`을 의미하지 않는다.
  - 유효한 증거 하에서 선행 검사의 명시적 FAIL(S1 래퍼 비정상/DEADLINE, S2 스트림 위반 등)이 확정 입증되어 후속이 `NOT_EXECUTED`가 된 경우 $\rightarrow$ **`FINAL_FAIL` (종결 파일 작성)**.
  - 선행 검사의 명시적 위반 입증 없이 증거 불완전/파싱 오류/측정 불능으로 인해 후속이 `NOT_EXECUTED`로 미완료된 경우 $\rightarrow$ **`NOT_ESTABLISHED` (종결 파일 생성하지 않음)**.
  - `NOT_EXECUTED`가 존재하면 모든 검사가 PASS가 아니므로 `FINAL_PASS`는 원천 차단된다.
- **4대 판정 우선순위:**
  1. **우선순위 1 (증거 무효/불완전):** 3대 증거 파일 부재, I/O 에러, 파싱 실패, `run_id` 불일치, Supervisor 기록 구조 손상, 선행 명시적 FAIL 증거 없이 `NOT_EXECUTED`로 미완료 $\rightarrow$ **외부 거버넌스 판정 `NOT_ESTABLISHED` (종결 파일 생성하지 않음)**.
  2. **우선순위 2 (유효 증거 하의 명시적 FAIL):** 증거 유효성이 확립된 상태에서 V1 실측 불일치, S4 다이제스트 모순/기준선 불일치, V3 트리 무결성 != PASS 또는 12대 카운터 != 0, 유효한 Supervisor 기록의 선행 FAIL 확인 및 이에 따른 후속 `NOT_EXECUTED` $\rightarrow$ **외부 거버넌스 판정 `FINAL_FAIL` (종결 파일 `final_state: "FINAL_FAIL"` 작성)**.
  3. **우선순위 3 (전 항목 PASS):** 증거가 유효하고 모든 필수 검사가 예외 없이 PASS $\rightarrow$ **외부 거버넌스 판정 `FINAL_PASS` (종결 파일 `final_state: "FINAL_PASS"` 작성)**.
  4. **우선순위 4 (Fallback Safety):** 결정론적 조건 1~3에 포섭되지 않는 모든 미확정 예외 상태 $\rightarrow$ **외부 거버넌스 판정 `NOT_ESTABLISHED` (종결 파일 생성하지 않음)**.
- **3대 핵심 경계 조건:**
  - **경계 A (증거 유효성과 결과 분리):** `has_valid_evidence = True`는 기록의 신뢰성 및 귀속성 자격만을 뜻하며, 검사 합격을 의미하지 않음.
  - **경계 B (Supervisor FAIL 증거 자격):** 증거 유효성 선행 확립, `run_id` 현재 실행 완벽 귀속, 규격상 명시적 FAIL 정의 3대 조건이 동시 충족될 때에만 `FINAL_FAIL`의 유효 증거로 인정.
  - **경계 C (V1 측정 불가 vs 불일치 분리):** 매니페스트 부재/읽기 실패는 측정 불능으로 `NOT_ESTABLISHED`, 실측 완료 후 기준선 불일치는 명시적 위반으로 `FINAL_FAIL`.
- **Verifier 종결 파일 작성 조건과 상태값 표현 계층 분리:**
  - **상황 A (우선순위 2/3):** 확정 판정에 따라 종결 파일을 배타적 작성하며, 내부 `final_state` 값은 `"FINAL_PASS"` 또는 `"FINAL_FAIL"` 2개 값으로만 엄격 제한.
  - **상황 B (우선순위 1/4):** 증거 불완전, 부재, 손상, 예외 시 종결 파일을 생성하지 않음 (`sys.exit(1)`).
  - **표현 계층 원칙:** `NOT_ESTABLISHED`는 파일 내부 필드값이 아니며, 유효한 종결 파일이 성립하지 못했을 때 외부 거버넌스가 내리는 최종 판정이다.

#### 오류 타입
- `SynapseError(code, message)`: `name`, `code`(readonly), `message`. 표준 `Error` 상속.
- `CombinedTestFailure(label, primaryError, prototypeError)`: 표준 `Error` 상속. `primaryError`와 `prototypeError`는 전달받은 순서 그대로 원본 값 변환 없이 보존(`undefined` 포함).
- 두 클래스는 저장소에 없다(심볼 검색 0건). 신규 정의 대상이다.
- 닫힌 코드 목록은 위 호출 순서 표의 코드 + `MATRIX_FAILURE`.

#### `resolveGuarded(body, protoCheck): void`
- 본문과 proto 검사를 **둘 다** 실행. 실패 여부는 Boolean 플래그(`bodyFailed`, `protoFailed`)로 판정 (`throw undefined` 누락 방지).
- 둘 다 실패: `CombinedTestFailure('GUARDED', bodyError, protoError)` throw (순서: primary가 1번째, prototype이 2번째).
- 하나만 실패: 원본 값 그대로 throw.
- S1~S7: ok/ok, throw A/ok, ok/throw B, A/B 복합, `throw undefined` 3종(본문·proto·양쪽).
- 판정 분리: **R2-a** 함수 정확성(S1~S7 결과), **R2-b** 호출 연결(케이스·스위트 판정부 모두 `resolveGuarded` 호출, 직접 `try/catch` 우회 경로 0개). 둘 다 PASS여야 P0-2 종결.

#### 제한값 전달 및 보관 계약 (P1-1, P1-3)
- **`ValidatedLimits` 불변성 및 타입 계약 (P1-3):**
  - 프로토타입이 `null` 또는 `Object.prototype`인 순수 평면 데이터 객체여야 하며 심벌 키나 getter/setter 접근자 속성을 일절 불허한다.
  - 정확히 5개 필드(`maxJsonBytes`, `maxParseDepth`, `maxStringLength`, `maxNodes`, `maxEdges`)만 존재해야 하며 미지의 추가 키는 거부한다.
  - 5개 필드 모두 유한한 안전 정수(`typeof v === 'number' && Number.isSafeInteger(v) && v > 0`)여야 하며, `NaN`, `Infinity`, `-Infinity`, 소수, 음수, 0은 즉시 `INVALID_LIMITS_CONFIG`로 거부한다.
  - 입력 `rawLimits`와의 참조 공유를 완전히 차단하기 위해 5개 숫자 필드를 새 평면 객체로 복사한 후 `Object.freeze()`하여 반환한다 (불필요한 Deep Clone 지양).
  - **Proxy 신뢰 경계 통일 (P0-C):** `rawLimits` 역시 `Proxy` 객체에 대해서는 신뢰 가정(Trust Assumption)이 적용된다. 일반 객체에 대한 프로토타입/디스크립터 검사(getter/setter 차단)는 수행하지만, `Proxy`의 내부 트랩(`getPrototypeOf`, `getOwnPropertyDescriptor`, `ownKeys` 등) 실행 방지까지 엔진이 보장하는 것은 아니다.
- **Factory 내부 보관:** 반환된 `ValidatedLimits`는 Factory 내부 스코프에 격리 보관되며, 이후 3단계(크기 검사), 4단계(파서: `maxParseDepth`, `maxStringLength`), 5단계(구조 검증: `maxNodes`, `maxEdges`)에 안전하게 전달된다.
- **D2 계약:** 생략 시 기본값 객체 적용, 5개 필드 전부 지정 시 커스텀 적용, 일부 필드 누락 객체 전달 시 `INVALID_LIMITS_CONFIG`로 즉시 거부(암묵적 병합 금지).

#### 파서·직렬화 및 단일 출처 계약 상세 (P0-3, P0-4, P1-2, P1-4, R7)
- **목적 분리 원칙 (Scope Isolation):**
  - 본 P3-1 계약(RFC 8785, UTF-8 바이트 검증, canonicalization)은 기존 SYNAPSE 분석 데이터의 SSOT인 `project_state.json`을 입력으로 받아 무결성을 검증하고, 동일한 정규화 결과에서만 후속 데이터를 파생하는 독립적 수집 경계에만 한정된다.
  - 빌드 시스템 심볼 분리(Track A / 어댑터 분리)의 본질은 심볼/참조 격리 및 그래프 분석 오염 차단이며, UTF-8/JCS 계약에 종속되거나 결합되지 않는다.
- **Factory 인자 독립성 및 `rawParams` 보안/오류 평가 7단계 순서 (P1-4):**
  - `rawLimits`는 Factory의 제2 매개변수(`rawLimits: unknown = DEFAULT_INGESTION_LIMITS`)이며 `rawParams`의 내부 속성이 아니다.
  - `rawLimits` 검증(1단계)은 `rawParams`의 속성에 접근하지 않고 독립 수행된다. 제1 매개변수와 제2 매개변수가 동시 위반인 경우 정의된 호출 순서에 따라 1단계 `INVALID_LIMITS_CONFIG`가 우선 발생한다.
  - **2단계 `rawParams` 7단계 순차 평가 (오류 우선순위 및 임의 getter 실행 차단):**
    1. 프로토타입 검사: `typeof rawParams !== 'object' || rawParams === null || Array.isArray(rawParams)`인 경우 즉시 거부. 유효 객체인 경우 `const proto = Object.getPrototypeOf(rawParams)`로 1회만 조회·보관하여 불필요한 중복 트랩 조회를 방지하며, `proto !== null && proto !== Object.prototype`인 경우 → `INVALID_FACTORY_PARAMS`
    2. 심벌 키 검사: `Object.getOwnPropertySymbols(rawParams).length > 0` → `INVALID_FACTORY_PARAMS`
    3. 허용된 own key 집합 검사: `Object.getOwnPropertyNames(rawParams)`의 길이가 2이고 `'snapshotId'`와 `'jsonText'` 두 키를 정확히 포함하는 집합인지 확인 (프로퍼티 삽입 순서는 무관하며 `{ snapshotId, jsonText }`와 `{ jsonText, snapshotId }` 모두 허용; 키 누락 또는 추가 키 존재 시) → `INVALID_FACTORY_PARAMS`
    4. 프로퍼티 디스크립터 검사: `Object.getOwnPropertyDescriptor(rawParams, key)`를 각 키별로 **1회 조회하여 변수에 보관**한다. 디스크립터 조회 결과가 없거나(`undefined`), 두 필드 중 하나라도 `get` 또는 `set` 접근자가 존재하는 경우 → `INVALID_FACTORY_PARAMS`
    5. 자체 데이터 속성(own data property) 존재 검사: 보관된 디스크립터에 `value` 속성이 존재하지 않는 경우(`'value' in desc === false`) → `INVALID_FACTORY_PARAMS`
    6. `snapshotId` 값 검사 (O2 확정 규격): 보관된 디스크립터의 값에 대해 다음 위반 시 즉시 `INVALID_SNAPSHOT_ID`를 발생시킨다.
       - 타입 검사: `typeof descSnapshotId.value !== 'string'`
       - 길이 검사: `descSnapshotId.value.length < 1 || descSnapshotId.value.length > 128` (빈 문자열 `""` 거부)
       - 문자 집합: `!/^[a-zA-Z0-9_-]+$/.test(descSnapshotId.value)` (경로 탐색 문자 `/`, `\`, `.` 및 공백·제어 문자 차단)
       - Windows 예약 장치 이름: `/^(CON|PRN|AUX|NUL|COM[1-9]|LPT[1-9])$/i.test(descSnapshotId.value)` (대소문자 구분 없이 거부)
       - **보안 범위 및 확장 계약 명시 (O2-1, O2-2):**
         - O2-1: 현재 `.`을 원천 금지하므로 `CON.txt`, `NUL.json` 등 확장자가 포함된 형태도 사전 차단된다. 단, 예약 장치명 검사는 독립적 보안 계약이므로 향후 문자 집합 변경 시에도 확장자 부착 예약 장치명은 독립적으로 거부 대상으로 처리해야 한다.
         - O2-2: 명시적 정규식 `/^(CON|PRN|AUX|NUL|COM[1-9]|LPT[1-9])$/i`로 차단되는 Windows 예약 장치명(`CON`, `PRN`, `AUX`, `NUL`, `COM1`~`COM9`, `LPT1`~`LPT9`)과, 허용 문자 집합(`^[a-zA-Z0-9_-]+$`)에 의해 차단되는 비ASCII 첨자 장치명(`COM¹`~`COM³`, `LPT¹`~`LPT³` 등)을 엄격히 구분한다. `COM0`은 예약 장치명이 아니며 ASCII 숫자 `0`을 포함하므로 현행 규칙상 차단 대상이 아님을 명확히 한다(잘못된 차단 설명 배제). 향후 식별자 문자 집합 확장 시 예약 장치명 목록과의 독립 검증을 재검토 대상으로 기록한다.
         - 본 검사는 `snapshotId`를 안전한 단일 경로 구성요소로 취급하기 위한 입력 제약이며, 실제 파일 시스템 경로 결합 및 접근의 안전성은 파일 핸들러 구현 검증(P0/P1)에서 독립적으로 증명되어야 한다.
       - *참고:* UUID v4 및 `test_snap_01`, `baseline-snapshot-1` 등 테스트 식별자는 완전 허용된다.
    7. `jsonText` 값 검사: 보관된 디스크립터의 `typeof descJsonText.value !== 'string'`인 경우 → `INVALID_FACTORY_PARAMS`
       - **배치 의도 명시:** 1~6단계를 통해 객체의 구조(프로토타입, 심벌 키, 2개 own key 화이트리스트, 디스크립터 유효성)와 가벼운 `snapshotId` 식별자를 먼저 완결 검증한 후, 잠재적으로 수십 MB에 달하는 거대한 `jsonText` 본문의 타입 검사로 안전하게 진입하기 위한 의도된 순서 배치이다.
    - **안전성 및 Proxy 신뢰 경계 통일 (P0-C):** `rawParams`와 `rawLimits` 모두 `Proxy` 객체는 신뢰 가정(Trust Assumption) 대상이며, 엔진은 Proxy 내부 트랩 실행 방지까지 보장하지 않는다. 일반 객체에 대한 디스크립터 검사(getter/setter 실행 차단)와 Proxy 트랩 방지는 서로 독립된 보안 속성이다.
- **입력 크기 및 파서 경계 (P1-2):**
  - **BOM 거부 범위 한정:** 입력 `jsonText`의 **첫 번째 코드 단위(인덱스 0)가 `\uFEFF`인 경우에 한해서만** 파일 선두 BOM으로 간주하여 `JSON_SYNTAX_ERROR`로 거부한다. JSON 문자열 값 내부(예: `"hello\uFEFFworld"`)에 포함된 `\uFEFF`는 일반 유효 Unicode 문자로 허용하며, 그 외 문법 위치의 `\uFEFF`는 일반 파서 구문 오류로 처리한다.
  - **입력 크기 및 서로게이트 오류 우선순위:** (1) `jsonText.length > limits.maxJsonBytes` 빠른 검사 초과 시 `JSON_INPUT_TOO_LARGE`가 서로게이트 검사보다 우선 발생한다. (2) 빠른 검사를 통과한 경우에 한해 UTF-16 문자열의 고립 서로게이트를 선제 검사하여 발견 즉시 `INVALID_SURROGATE`로 거부한다. (3) 1회 인코딩된 `sourceBytes.byteLength > limits.maxJsonBytes` 최종 바이트 초과 시 `JSON_INPUT_TOO_LARGE`가 발생한다.
  - **서로게이트 및 구문 오류 코드 매핑 확정:**
    - UTF-8 변환 전 원문 UTF-16 문자열에 고립 서로게이트 존재: `INVALID_SURROGATE`
    - JSON 문자열 토큰 디코딩 후(예: `"\uD800"` 이스케이프) 고립 서로게이트 발견: `INVALID_SURROGATE`
    - 이스케이프되지 않은 원시 C0 제어문자(`U+0000~U+001F`): `JSON_SYNTAX_ERROR`
    - 6단계 RFC 8785 직렬화 단계에서 비정상 Unicode 발견 (방어적): `JCS_UNSUPPORTED_VALUE`
  - **`maxStringLength` 선제 검사(Pre-allocation Check) 및 점진적 디코딩 계약:**
    - **측정 단위 및 서로게이트 쌍 청크 경계 처리 규칙:**
      - 측정 단위는 escape sequence를 해석한 **디코딩된 JavaScript UTF-16 코드 단위(Code Unit)**이다 (예: `"\u0061"`은 길이 1).
      - 유효한 서로게이트 쌍(Surrogate Pair: High Surrogate `U+D800~U+DBFF` + Low Surrogate `U+DC00~U+DFFF`)은 UTF-16 코드 단위 **2개(`length = 2`)**로 정확히 계산한다. Unicode 코드 포인트(Code Point, 1개) 기준으로 측정하는 것을 엄격히 금지하여 UTF-16 인덱싱 및 JCS 규범과의 일관성을 유지한다.
      - 이스케이프 표기 형태(예: `"\uD83D\uDE00"`) 또한 디코딩 결과 기준으로 2개의 UTF-16 코드 단위로 계산한다.
      - **청크 경계 분리 처리:** 디코딩 청크(`MAX_DECODING_CHUNK_LENGTH = 1024`) 경계에서 서로게이트 쌍이 분리되더라도(예: 청크 1 끝의 High Surrogate와 청크 2 시작의 Low Surrogate), 누적 길이는 각각 코드 단위 1개씩 총 2개로 온전히 누적한다.
      - **경계를 넘는 연속적 유효성 검사:** 고립 서로게이트 검출 및 Unicode 유효성 검사는 청크 경계에 의해 단절되지 않고 상태를 유지하여 청크 경계를 넘어 연속적으로 수행한다 (청크 끝의 미완성 High Surrogate가 다음 청크의 유효한 Low Surrogate와 올바르게 결합하는지 검증하며, 유효한 Low Surrogate가 이어지지 않거나 문자열이 종료되면 즉시 `INVALID_SURROGATE` 발생).
    - **전체 토큰 선할당 금지 및 선제 검사 통과 조각 기반 조립 원칙:**
      - **선제 검사 통과 조각 기반 조립 원칙:** 최종 문자열 조립은 반드시 선제 길이 검사(`currentLength + nextChunk.length <= maxStringLength`)를 사전에 통과한 개별 조각들만을 순차적으로 내부 버퍼에 추가하여 수행해야 한다.
      - **전체 토큰 선할당 및 사후 검사 우회 엄격 금지:** 파서는 문자열 토큰 전체를 별도의 메모리에 단일 완성 문자열로 먼저 디코딩·생성한 뒤 길이를 사후 검사하거나 형식적으로 청크 검사만 흉내 내는 우회 구현을 계약 위반으로 규정하며 엄격히 금지한다.
      - `nextChunk` 자체가 이미 전체 토큰을 포함하는 거대 문자열이어서는 안 된다.
      - 이스케이프 시퀀스(예: `\uXXXX`, `\"`, `\\` 등)와 일반 문자 구간은 점진적(incremental)으로 해석되어야 한다.
      - **디코딩 조각 단위 및 최대 청크 상한:** 기본적으로 코드 단위 단위(Code Unit by Code Unit)로 점진 누적하며, 일반 문자열 연속 구간에 대해 청크 단위를 둘 경우 구현의 임의 거대 메모리 할당을 방지하기 위해 최대 디코딩 청크 상한(`MAX_DECODING_CHUNK_LENGTH = 1024` UTF-16 Code Units)을 초과하는 조각 생성을 금지한다 (`nextChunk.length <= MAX_DECODING_CHUNK_LENGTH`).
      - **선제 검사 불변식:** 버퍼에 다음 조각을 추가하기 직전에 항상 다음 불변식을 검사한다:
        $$currentLength + nextChunk.length \le maxStringLength$$
      - **초과 조각 버퍼 추가 차단:** 초과가 예상되는(`currentLength + nextChunk.length > maxStringLength`) 조각은 **결코 버퍼에 추가하지 않고**, 즉시 디코딩을 중단하며 `STRING_LENGTH_EXCEEDED`를 발생시킨다.
    - **적용 범위 및 방어적 재검증:**
      - 객체 키(Object Key)와 문자열 값(String Value) 모두에 동일하게 위 점진적 선제 검사 규칙을 적용한다.
      - 최종 조립 완료 후의 전체 길이 검사는 파서 구현 오류를 방어하기 위한 2차 안전장치(방어적 재검증)로 유지한다.
  - **특수 키 보존 및 프로토타입 오염 방지 통합 검증 계약 (P0-B, P1-2):**
    - **핵심 목표:** `__proto__`, `constructor`, `prototype` 등 특수 키가 포함된 JSON 입력이 파싱, JCS 정규화, canonical 바이트 재파싱, 8단계 구조 동등성 검증 전 과정을 통과할 때, 데이터 손실이나 형태 왜곡 없이 100% 보존됨과 동시에 전역 `Object.prototype`이 오염되지 않음을 검증한다. (주의: 본 테스트는 특수 키가 일반 데이터 키로 보존되는지와 JCS 키 정렬 순서를 확인하는 것이며, 모든 객체 오염 방지 자체를 포괄 증명하는 것으로 과장하지 않는다.)
    - **필수 검증 테스트 벡터 (P0-B):**
      ```json
      {
        "__proto__": {"polluted": true},
        "constructor": {"prototype": {"polluted": true}},
        "prototype": "ordinary-data"
      }
      ```
      - JCS canonical 최종 기대 문자열 (UTF-16 코드 단위 정렬: `"__proto__"` < `"constructor"` < `"prototype"`):
        ```json
        {"__proto__":{"polluted":true},"constructor":{"prototype":{"polluted":true}},"prototype":"ordinary-data"}
        ```
    - **단계별 불변식 및 검증 기준:**
      1. **파서 컨테이너 생성 및 대입:** 파서는 `Object.create(null)` 기반의 프로토타입 없는 순수 딕셔너리를 사용하거나, `Object.defineProperty(obj, key, { value, writable: true, enumerable: true, configurable: true })`를 사용하여 모든 키를 예외 없이 **자체 열거 가능 데이터 속성(own enumerable data property)**으로만 생성한다. 단순 프로퍼티 대입(`result[key] = value`)은 프로토타입 오염 위험으로 영구 금지된다.
      2. **전역 오염 무결성 검증:** 파싱 및 재파싱 직후 `({}).polluted === undefined` 및 `Object.prototype.polluted === undefined`를 검증하여 프로토타입 체인 오염이 0건임을 보장한다.
      3. **JCS 직렬화기 순회:** `Object.keys()` 단일 기준으로 순회하며, 자체 열거 가능 문자열 키인 `"__proto__"`, `"constructor"`, `"prototype"`이 UTF-16 코드 단위 정렬 규칙(`"__proto__"` < `"constructor"` < `"prototype"`, 첫 문자 `_` U+005F < `c` U+0063 < `p` U+0070)에 따라 누락 없이 온전히 직렬화된다.
      4. **8단계 구조 동등성(Structural Equivalence) 비교기 알고리즘:**
         - 비교 대상: `Object.keys(a)`와 `Object.keys(b)`.
         - 키 집합 비교: 정렬된 키 배열 `keysA`와 `keysB`에 대해 `keysA.length === keysB.length && keysA.every((k, i) => k === keysB[i])` (Set 1:1 일치).
         - 값 재귀 비교: 각 키의 매핑 값(중첩 객체 및 원시값)에 대해 타입 및 값을 재귀적으로 1:1 비교.
         - **프로토타입 비교 영구 배제:** `Object.getPrototypeOf()` 결과(예: `null` vs `Object.prototype`)는 파서의 안전한 내부 구현 표현일 뿐 JSON 데이터 모델의 일부가 아니므로 구조 동등성 평가에서 **일절 비교하지 않는다**.
         - 불일치 시 즉시 `REPARSE_MISMATCH` 발생.
  - 최상위 컨테이너(`{}` or `[]`) = 깊이 1. 컨테이너 진입 시점에 검사 (`maxParseDepth=1` 6대 경계 사례 준수, 7단계 재파싱에도 동일 깊이 정책 강제 적용).
- **JCS Unicode 방어 사전조건 (P0-3):**
  - 6단계 RFC 8785 직렬화기는 유효한 Unicode 문자열만 입력받는다는 방어적 불변조건을 강제한다.
  - 4단계 파서를 우회하거나 잔존한 고립 서로게이트나 유효하지 않은 Unicode가 직렬화 단계에서 발견될 경우 즉시 `JCS_UNSUPPORTED_VALUE`로 거부한다.
- **단일 출처 `SafeSnapshotCanonicalLedger` 및 결정론적 파생 규격 (P0-4, R7, O4):**
  - **`sourceHash`**: Factory에 전달된 `jsonText`를 UTF-8로 인코딩한 바이트 배열(`sourceBytes`)의 SHA-256이다 (`SHA256(sourceBytes)`). 파일 시스템의 원본 파일 바이트 해시를 의미하지 않는다. UTF-8 인코딩은 고립 서로게이트 검사를 통과한 뒤 1회 수행하며, 생성된 `sourceBytes`는 크기 검증과 `sourceHash` 계산에 재사용하여 불필요한 반복 인코딩을 방지한다.
  - **`canonicalHash`**: RFC 8785 정규화 바이트의 SHA-256 (`SHA256(canonicalBytes)`).
  - `snapshotId`, `sourceHash`, `canonicalHash`, `canonicalByteLength`, `canonicalBytes` (`#private` 원장), 파생된 `nodeBytes`, `edgeBytes`를 캡슐화한다.
  - **내부 저장소 타입 불변식 및 방어적 복사 인터페이스 규격:**
    - **내부 저장소 순수 TypedArray 고정:** 원장 내부의 `#private` 바이트 저장 필드(`canonicalBytes`, `nodeBytes`, `edgeBytes`)는 정확히 순수 `Uint8Array` 인스턴스여야 하며, Node.js `Buffer`뿐만 아니라 `Uint8Array`의 임의 하위 클래스(Subclass) 및 내부 슬롯이 없는 가짜 객체(`Object.create(Uint8Array.prototype)`) 유입도 일절 허용하지 않는다 (`ArrayBuffer.isView(internalBytes) && Object.getPrototypeOf(internalBytes) === Uint8Array.prototype && !Buffer.isBuffer(internalBytes)`).
      - `ArrayBuffer.isView`: 실제 TypedArray/DataView 내부 슬롯 존재 확인
      - `Object.getPrototypeOf(...) === Uint8Array.prototype`: Uint8Array 하위 클래스, DataView, 타 TypedArray 계열 배제
      - `!Buffer.isBuffer`: Node.js Buffer 명시적 배제
    - **대응 필드별 기준 구현 및 메모리 독립성:** 외부 노출 메서드는 각 대상 필드에 1:1 대응하여 독립된 새 메모리 공간을 할당·반환한다.
      - `getCanonicalBytes(): Uint8Array` → `new Uint8Array(this.#canonicalBytes)`
      - `getNodeBytes(): Uint8Array` → `new Uint8Array(this.#nodeBytes)`
      - `getEdgeBytes(): Uint8Array` → `new Uint8Array(this.#edgeBytes)`
      (Node.js `Buffer.prototype.slice()`가 원본 메모리를 공유하는 뷰를 반환할 수 있는 위험을 원천 배제).
    - **독립 검증 조건 분리:**
      1. **저장소 타입 불변식:** 원장 내부 필드가 정확히 순수 `Uint8Array` 인스턴스이며 `Buffer` 및 하위 클래스가 아님을 검증.
      2. **메모리 독립성:** 호출자가 반환된 `Uint8Array`의 요소를 임의로 수정(`bytes[0] ^= 0xFF`)하더라도, 원장 내부 저장 바이트는 절대 변하지 않음을 검증.
  - **검증 전용 증거 취득 및 외부 노출 인터페이스 명세:**
    - 검증 러너는 `#private` 필드를 외부에서 직접 읽는 비정상 접근을 시도하지 않으며, 표준 공개 메서드 `ledger.getCanonicalBytes()`를 호출하여 방어적 복사본 바이트를 취득한 뒤 RFC 원문 118바이트와 1:1 바이트 비교를 수행한다.
  - **R7 노드·엣지 바이트의 결정론적 파생 규격:**
    - `nodeBytes`와 `edgeBytes`는 7단계 canonical 재파싱 결과의 `nodes` 및 `edges` 배열 객체로부터만 파생된다.
    - 직렬화 형식은 각 요소의 RFC 8785 JCS Canonical JSON 직렬화 결과에 대한 UTF-8 인코딩 바이트열이며, 원본 배열의 1:1 인덱스 순서(0 ~ N-1) 및 속성 참조 관계의 결정론적 동일성을 보존한다.
- **RFC 8785 적합성 증거 체계 및 O4 공식 기준 벡터 명세 (P0-1 vs O4 분리):**
  - **검증 범주 체계:**
    - **범주 A (O4):** RFC 8785 공식 원문 Section 3의 단일 종단 간(End-to-End) 정규화 사례와 속성 정렬 사례를 1:1 대조하는 공식 준수 증거.
    - **범주 B (P0-1 규범):** UTF-16 코드 단위 키 정렬, `-0`→`0`, 지수 표기 규범, 비유한 수(`NaN`, `Infinity`) 거부, 부록 B(Appendix B) 숫자 직렬화 등 RFC 규범 동작 검증.
    - **범주 C (SYNAPSE 경계):** `1e400`, `1e-400` 언더플로 거부, 자원 제한, 중복 키 거부 등 엔진 자체 경계 검증.
    - 범주 B/C의 통과가 범주 A의 통과를 증명하지 않으며, 반대도 성립하지 않음 (P0-1과 O4 독립 판정).
  - **O4 공식 기준 벡터 명세 (RFC 8785 Section 3 1:1 고정):**
    - **원칙 및 범위 (O4-1 원문 출처 및 불변성):**
      - 공식 원문: [RFC 8785 — JSON Canonicalization Scheme (JCS)](https://www.rfc-editor.org/rfc/rfc8785.html) (RFC Editor).
      - 원문의 Section 3 단일 종단 간(End-to-End) 정규화 과정을 3단계 정규화 산출물 및 최종 UTF-8 Hex 바이트열 산출로 명확히 구분하여 1:1 대조 기준으로 고정한다:
        - §3.2.2.2–3.2.2.3: 원본 JSON 입력 및 ECMAScript 직렬화 중간 문자열
        - §3.2.3: JCS 속성 정렬 적용 canonical JSON 최종 문자열 및 보조 속성 정렬 벡터
        - §3.2.4: 최종 UTF-8 Hex 기대 바이트열 (정확히 118바이트)
      - 본 공식 벡터의 입력과 기대 출력은 문자 단위로 RFC 원문과 완전 일치해야 하며, 어떠한 임의 변형도 금지된다.
      - 부록 B(Appendix B)의 숫자 경계값 예제는 §3 공식 벡터와 혼합하지 않는다.

    - **O4-1 RFC 8785 Section 3 공식 원문 1:1 정적 대조표:**
      | 단계 | RFC 8785 원문 조항 | 원문 내용 (문자 단위 1:1 대조) | 명세 상태 |
      |---|---|---|---|
      | 1. 원본 JSON 입력 | §3.2.2 | `{"numbers": [333333333.33333329, 1E30, 4.50, 2e-3, 0.000000000000000000000000001], "string": "\u20ac$\u000F\u000aA'\u0042\u0022\u005c\\\"\/", "literals": [null, true, false]}` (개행/공백 포함) | 원문과 1:1 일치 |
      | 2. ECMAScript 중간값 | §3.2.2 | `{"numbers":[333333333.3333333,1e+30,4.5,0.002,1e-27],"string":"€$\u000f\nA'B\"\\\\\"/","literals":[null,true,false]}` | 원문과 1:1 일치 |
      | 3. JCS canonical 최종값 | §3.2.3 | `{"literals":[null,true,false],"numbers":[333333333.3333333,1e+30,4.5,0.002,1e-27],"string":"€$\u000f\nA'B\"\\\\\"/"}` | 원문과 1:1 일치 |
      | 4. UTF-8 Hex 바이트열 | §3.2.4 | 118바이트 Hex 배열 (행별 20B * 5행 + 18B = 정확히 118바이트 산출 입증) | 원문과 1:1 일치 |
      | 5. 속성 정렬 보조 벡터 | §3.2.3 | 입력 7개 키, 정렬 키 순서(`\r` < `1` < `\u0080` < `\u00f6` < `\u20ac` < `\ud83d\ude00` < `\ufb33`), 최종 canonical 문자열 전체 | 원문과 1:1 일치 |

    - **118바이트 Hex 산출 구조 입증 (Section 3.2.4):**
      - 1행: `7b 22 6c 69 74 65 72 61 6c 73 22 3a 5b 6e 75 6c 6c 2c 74 72` (20바이트: `{"literals":[null,tr`)
      - 2행: `75 65 2c 66 61 6c 73 65 5d 2c 22 6e 75 6d 62 65 72 73 22 3a` (20바이트: `ue,false],"numbers":`)
      - 3행: `5b 33 33 33 33 33 33 33 33 33 2e 33 33 33 33 33 33 33 2c 31` (20바이트: `[333333333.3333333,1`)
      - 4행: `65 2b 33 30 2c 34 2e 35 2c 30 2e 30 30 32 2c 31 65 2d 32 37` (20바이트: `e+30,4.5,0.002,1e-27`)
      - 5행: `5d 2c 22 73 74 72 69 6e 67 22 3a 22 e2 82 ac 24 5c 75 30 30` (20바이트: `],"string":"€$\u00`)
      - 6행: `30 66 5c 6e 41 27 42 5c 22 5c 5c 5c 5c 5c 22 2f 22 7d` (18바이트: `0f\nA'B\"\\\\\"/"}`)
      - **합계:** 20 * 5 + 18 = 정확히 **118바이트**. (단순 선언이 아닌 행별 바이트 매핑으로 검증됨).

    - **1. 원본 JSON 입력 (§3.2.2):**
      ```json
      {
        "numbers": [333333333.33333329, 1E30, 4.50,
                    2e-3, 0.000000000000000000000000001],
        "string": "\u20ac$\u000F\u000aA'\u0042\u0022\u005c\\\"\/",
        "literals": [null, true, false]
      }
      ```
    - **2. ECMAScript 직렬화 중간 기대 문자열 (§3.2.2):**
      ```json
      {"numbers":[333333333.3333333,1e+30,4.5,0.002,1e-27],"string":"€$\u000f\nA'B\"\\\\\"/","literals":[null,true,false]}
      ```
    - **3. JCS canonical JSON 최종 기대 문자열 (§3.2.3):**
      ```json
      {"literals":[null,true,false],"numbers":[333333333.3333333,1e+30,4.5,0.002,1e-27],"string":"€$\u000f\nA'B\"\\\\\"/"}
      ```
    - **4. RFC 명시 UTF-8 Hex 기대 바이트열 (§3.2.4, 정확히 118바이트):**
      ```text
      7b 22 6c 69 74 65 72 61 6c 73 22 3a 5b 6e 75 6c 6c 2c 74 72
      75 65 2c 66 61 6c 73 65 5d 2c 22 6e 75 6d 62 65 72 73 22 3a
      5b 33 33 33 33 33 33 33 33 33 2e 33 33 33 33 33 33 33 2c 31
      65 2b 33 30 2c 34 2e 35 2c 30 2e 30 30 32 2c 31 65 2d 32 37
      5d 2c 22 73 74 72 69 6e 67 22 3a 22 e2 82 ac 24 5c 75 30 30
      30 66 5c 6e 41 27 42 5c 22 5c 5c 5c 5c 5c 22 2f 22 7d
      ```
    - **5. 속성 정렬 검증용 보조 벡터 (§3.2.3, O4-3 확장):**
      - 입력 JSON:
        ```json
        {
          "\u20ac": "Euro Sign",
          "\r": "Carriage Return",
          "\ufb33": "Hebrew Letter Dalet With Dagesh",
          "1": "One",
          "\ud83d\ude00": "Emoji: Grinning Face",
          "\u0080": "Control",
          "\u00f6": "Latin Small Letter O With Diaeresis"
        }
        ```
      - UTF-16 코드 단위 정렬 후 기대 속성 키 순서:
        `"\r"` (U+000D) < `"1"` (U+0031) < `"\u0080"` (U+0080) < `"\u00f6"` (U+00F6) < `"\u20ac"` (U+20AC) < `"\ud83d\ude00"` (U+D83D U+DE00) < `"\ufb33"` (U+FB33)
      - 정렬된 기대 값 순서:
        `"Carriage Return"`, `"One"`, `"Control"`, `"Latin Small Letter O With Diaeresis"`, `"Euro Sign"`, `"Emoji: Grinning Face"`, `"Hebrew Letter Dalet With Dagesh"`
      - 최종 JCS canonical 기대 문자열 (전체 대조):
        `{"\r":"Carriage Return","1":"One","\u0080":"Control","\u00f6":"Latin Small Letter O With Diaeresis","\u20ac":"Euro Sign","\ud83d\ude00":"Emoji: Grinning Face","\ufb33":"Hebrew Letter Dalet With Dagesh"}`
  - **바이트 단위 일치 및 판정 계약 (O4-2 검증 증거 계통 고정):**
    - 검증 증거 계통은 반드시 다음 파이프라인 직통 경로로만 수행되어야 한다:
      `RFC Input` → `P3-1 Factory` → `JCS Serializer` → `ledger.getCanonicalBytes()` → `Byte-for-byte comparison` → `PASS / FAIL`
    - 외부 제3의 JSON 직렬화기(`JSON.stringify` 등)를 우회 경유하여 바이트를 만들어 대조하는 행위는 엄격히 금지된다 (`#private` 직접 접근을 배제하고 오직 공개 인터페이스 `ledger.getCanonicalBytes()`를 통해 취득한 바이트로 1:1 대조 필수).
    - 실제 파이프라인 정규화 결과 바이트와 원문 Hex 바이트열 간에 **바이트 단위 1:1 완전 일치**를 검증하며, 불일치 시 `UNVERIFIED`가 아닌 **검증 실행 후 즉시 `FAIL`** 판정으로 기록한다.
    - **명세 고정과 런타임 적합성의 엄격한 구분:** 본 O4 공식 벡터를 문서에 고정하는 것은 **검증 기준의 사전 확정(SPECIFIED)**이며, SYNAPSE 구현의 RFC 8785 적합성을 증명하는 것이 아니다.
    - **거버넌스 상태 불변:** `P0-1 RFC 8785 규범 적합성`은 실제 런타임 검증 증거가 확보될 때까지 반드시 **`UNVERIFIED`**로 엄격히 유지한다.

#### 1. 다중 객체 공존 실측 메트릭 및 중복 집계 방지 정의 (O1-1)
단일 파이프라인 호출 내에서 `jsonText`, `sourceBytes`, 원본 파싱 객체 트리, `canonicalBytes`, canonical 재파싱 객체 트리, `nodeBytes`, `edgeBytes`가 동시에 생성·보관되므로, 다음 지표를 필수 전수 수집하되 중복 집계를 엄격히 구분한다:
- `peakHeapUsed`, `peakHeapTotal`: V8 힙 객체 점유량
- `peakRss`: OS 레벨의 프로세스 상주 메모리(Resident Set Size)
- `peakExternal`, `peakArrayBuffers`: Node.js Buffer 및 TypedArray C++ 백업 메모리
- `peakBufferBytes`: 원장(#private) 및 파생 TypedArray 명시적 할당 버퍼 크기
- `gcPauseTotal`, `elapsedMs`: GC 정지 시간 및 전체 처리 소요 시간
- **중복 집계(Overlap) 방지 주의사항:** `peakBufferBytes`는 Node.js의 `external`, `arrayBuffers` 및 `rss`와 물리적 메모리 영역이 중복된다. 세 지표를 단순 산술 합산하여 총 메모리라고 주장하는 것을 금지하며, V8 힙, C++ ArrayBuffer, OS RSS를 각각 독립적인 계층 메트릭으로 기록·평가한다.

#### 3. 스택 깊이 50% 공식의 성격 분리 및 판정 기준 (P0-E, O1-2, O1-4)
- **실패 경계 측정 ($D_{\text{fail}}$):** 특정 런타임 실행 환경(OS, V8 버전, Node.js 버전)에서 스택 오버플로(`RangeError: Maximum call stack size exceeded`)가 발생하는 최소 실패 경계 깊이를 실측한 환경 종속적 결과값이다.
- **50% 공식의 성격:** $\text{maxParseDepth} \le 0.5 \times D_{\text{fail}}$ 공식은 안전 마진 설정을 위한 **"정책 후보(Policy Candidate)"**일 뿐이며, 수학적으로 증명된 절대적 안전 상한이 아니다. 실제 파서의 재귀 호출 프레임 수가 입력 깊이에 완벽히 정비례하지 않을 수 있으므로 다음 판정 절차를 거쳐야만 상한으로 승격된다:
  1. 실제 파서의 재귀 프레임 구조와 객체·배열 교차 중첩 시나리오에서 $\text{maxParseDepth}$ 깊이의 완전 정상 성공 확인.
  2. $\text{maxParseDepth} + 1$ 깊이에서 `RangeError` 크래시 없이 즉시 `PARSE_DEPTH_EXCEEDED` 거부 발생 확인.
  3. 7단계 canonical 바이트 재파싱 단계에서도 동일한 경계 동작 일치 확인.
  4. 런타임 환경 종속성을 고려하여, 최종 상한 수치는 거버넌스 정책 승인(`CLOSED_BY_POLICY`)을 거쳐 확정.

#### 4. 3대 복합 부하(Combinatorial Load) 측정 시나리오 (O1-3)
단일 필드 개별 측정 외에 실제 시스템 메모리 피크를 유발하는 다음 3대 복합 부하 조합을 필수로 실측하여 힙 고갈 여부를 검증한다:
1. **조합 1:** 최대 JSON 크기(`maxJsonBytes`) + 최대 노드 수(`maxNodes`)
2. **조합 2:** 최대 JSON 크기(`maxJsonBytes`) + 최대 엣지 수(`maxEdges`)
3. **조합 3:** 최대 노드 수(`maxNodes`) + 최대 엣지 수(`maxEdges`) + 최대 문자열 길이(`maxStringLength`)

- **포괄성 한계 및 운영 기준선 명시 (P0-D):**
  - 위 3대 복합 부하 시나리오는 대표적 과부하에 대한 운영상 허용 범위를 측정하기 위한 최소 기준선이며, 모든 메모리 위험을 100% 포괄하는 절대 상한 증명으로 간주되지 않는다.
  - 특히 다음의 잔여 메모리 압박 패턴은 복합 부하 시나리오에서도 완전히 해소되지 않을 수 있으므로, 향후 O1 실측 보고서에서 독립적으로 한계를 명시해야 한다:
    - 매우 많은 짧은 문자열 (V8 내부 해시 테이블 및 문자열 인스턴스 오버헤드 급증)
    - 적은 수의 매우 긴 문자열 (단일 버퍼 및 UTF-8 재인코딩 메모리 급증)
    - 노드와 엣지의 동시 최대치 집중
    - 6단계 `canonicalBytes` 생성 후 7단계 canonical 재파싱 객체 트리의 일시적 동시 공존
    - 9단계 `nodeBytes`, `edgeBytes` 독립 생성에 따른 추가 복사 및 메모리 보유

#### 5. O1 4단계 종결 절차 프로토콜 (Resolution Protocol)
1. **1단계: 실측 권한 요청 및 승인 (Measurement Authorization Request):**
   - Code Freeze / Execution Freeze 상태에서 실측을 위한 전용 벤치마크 프로파일러 실행 권한을 독립 요청한다.
2. **2단계: 런타임 실측 및 증거 수집 (Measurement Execution & Evidence Capture):**
   - SYNAPSE 파이프라인 실제 출력물(Linux Kernel, VSCode, AntennaPod 등)을 표본으로 V8 메모리(`peakHeapUsed`, `peakRss`, `peakExternal` 등) 및 실행 시간을 실측하고 로그를 고정 기록한다.
3. **3단계: 기본값 및 상한 제안 (Limits & Default Proposal):**
   - 실측 증거에 기반하여 안전 기본값(`DEFAULT_INGESTION_LIMITS`)과 커스텀 허용 상한(`MAX_INGESTION_LIMITS`)의 `[min, max]` 범위를 산출하여 제안서를 작성한다 (D3 분리 원칙).
4. **4단계: 거버넌스 정책 승인 및 계약 종결 (Policy Approval & Contract Closure):**
   - 아키텍트/사용자의 정식 검토 및 승인을 거쳐 수치를 확정하고, 거버넌스 상태를 `CLOSED_BY_POLICY`로 전환한다.
   - **정책 승인 전까지 구현 승인(`Implementation Authorization`) 및 코드 확정은 영구 금지된다.**

### ⚠️ 예외 처리 및 주의 사항
- Code Freeze·Execution Freeze가 `ACTIVE`다. 이 문서는 해제를 요청하지 않는다.
- `canonicalStringify`는 `undefined`·`NaN`을 `null`로 바꾸고 순환 검출이 없다. 계약용으로 쓰지 않으며 수정하지 않는다(기존 해시 결과 변동 위험).
- 환각 방지: `SynapseError`, `CombinedTestFailure`, `resolveGuarded`, 팩토리, 파서는 **신규 제안**이며 기존 API가 아니다.
- Proxy는 `params`·`limits` 모두 신뢰 가정이며 검출을 보장하지 않는다.
- 객체 자체의 물리적 불변성은 주장하지 않는다. `#private` 방어적 복사만 계약한다.
- `maxJsonBytes` 빠른 경로는 `.length`가 UTF-8 바이트 수가 아님을 전제로 두 번째 검사를 반드시 수행한다.
- 성능: 대형 입력에서 UTF-8 인코딩·정규화 바이트 재파싱이 메모리를 두 배로 쓸 수 있다(O1 실측 대상).
- 열린 항목: O1(실측 및 상한 정책 승인). O2(`snapshotId` 규칙) 및 O4(RFC 공식 예제)는 기준 확정 완료(`SPECIFIED`).
- 한 가지 정책 명시: D6은 언더플로만 거부하며, `2^53+1` 같은 일반 반올림은 허용한다(IEEE 754 double 해석).

### 6.1 문제 정의 및 원인 (Root Cause)
- Kubernetes 재부트스트랩(`13,109` 노드) 후 `cluster_ghost_unverified` (`⚠️ Unverified References`)에 남은 `468`개 노드를 전수 해부한 결과, 프로젝트 프로파일이 아닌 **범용 언어 문법 해석기(`ReferenceResolver`, `GhostExpander`, `ShellScanner`)의 구조적 결함**으로 인해 정상 외부 모듈과 셸 플래그가 `Unverified`로 잘못 유입됨을 확인:

## 10. ⚠️ Godot 실측 검증 한계 및 차기 마일스톤 과제 (Known Limitations & Next Milestone Backlog)

1. **최상위 `tests/` 상대 경로 미인식 결함**:

2. **서드파티·외부 라이브러리 분석 범위(Scope Boundary) 선언 부재**:
