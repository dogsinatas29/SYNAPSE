
### 2.3. [P0-3] `filePath` 입력 정책 2단계 처리 순서 및 미래 구현 계약

입력 검증과 정규화 결과 검증의 단계를 엄격히 분리하고, 예외 처리 동작을 규정합니다:

```
[입력 노드 (rawNode)] 
       │
       ▼
[Stage 1: 입력 무결성 검증 (Input Validation)]
       ├─ id 유효성 (비문자열, 빈 문자열, 공백 거부)
       ├─ filePath 상태 판정 (undefined, null, string, non-string)
       └─ 일치성 판정 (filePath !== undefined 인 경우 id === filePath 필수)
       │
       ▼ (통과 시)
[Stage 2: 정규화 및 결과 검증 (Normalization & Result Validation)]
       ├─ filePath 유효 문자열: filePath' = M_path(filePath), id' = M_path(id) 검증
       └─ filePath === undefined: Fallback 적용 filePath' = M_path(id) 검증
```

#### 1) Stage 1: 입력 검증 규약 (Fail-Closed Input Validation)
- **$n.id$ 검증**:
  - `typeof n.id !== 'string'` $\to$ 즉시 치명적 예외 발생 (`throw Error("INVALID_ID_TYPE")`)
  - `n.id.trim() === ""` $\to$ 즉시 치명적 예외 발생 (`throw Error("EMPTY_ID")`)
- **$n.filePath$ 검증**:
  - `n.filePath === null` $\to$ 즉시 치명적 예외 발생 (`throw Error("NULL_FILE_PATH_REJECTED")`)
  - `typeof n.filePath !== 'string' && n.filePath !== undefined` $\to$ 즉시 치명적 예외 발생 (`throw Error("INVALID_FILE_PATH_TYPE")`)
  - `typeof n.filePath === 'string' && n.id !== n.filePath` $\to$ 즉시 치명적 예외 발생 (`throw Error("ID_FILE_PATH_MISMATCH")`)

#### 2) Stage 2: 정규화 및 결과 검증 (Independent Oracle Comparison)
- **정상 경로 ($n.filePath$ 유효 문자열)**:
  - 독자 정규화 기대값: $E_{path} = \text{auditNormalize}(n.filePath)$
  - 산출 노드 $n'$의 $n'.id \equiv E_{path} \land n'.filePath \equiv E_{path}$ 전수 대조.
- **Fallback 경로 ($n.filePath \equiv \text{undefined}$)**:
  - 독자 정규화 기대값: $E_{path} = \text{auditNormalize}(n.id)$
  - 산출 노드 $n'$의 $n'.id \equiv E_{path} \land n'.filePath \equiv E_{path}$ 전수 대조.

#### 3) 프로덕션 필수 계약 명시 (Production Contract Requirement)
- **`null` 거부 정책의 성격**: 
  - 과거 코드의 느슨한 falsy 처리(`!filePath`) 관행을 영구 배제하고, `null`은 오염된 비정상 데이터로 취급하여 **프로덕션 `NodeBuilder.ts` 구현 시 반드시 명시적 예외를 던지도록 설계해야 하는 필수 요구 계약**으로 확정합니다.

### 2.4. [P1-1] 반사실적 Role 분류기(Counterfactual Classifier) 체계 완결

Role 전이의 원인이 테스트 세그먼트 규칙 때문인지, 파일명 패턴 때문인지 수학적으로 분리 증명하기 위해 **동일한 기본 판정선(Priority 1~5, 7~10 동일 유지)**을 공유하는 4대 반사실적 분류기를 정의합니다.

#### 1) 4대 반사실적 분류기 정의
모든 분류기는 Priority 1~5(Grammar, Config, Tooling Asset, Document, Asset)를 최우선 평가하며, Priority 6(Test)의 적용 여부만 제어합니다:

1. **기본 분류기 ($R_{\text{base}}$)**:
   - Priority 1~5 평가 $\to$ **Priority 6 (Test 규칙 전체) 건너뜀** $\to$ Priority 7~10 평가.
   - *목적: 테스트 규칙이 일체 존재하지 않았을 때 노드가 부여받았을 원초적 Role 판정.*
2. **순수 세그먼트 분류기 ($R_{\text{seg\_only}}$)**:
   - Priority 1~5 평가 $\to$ Priority 6에서 **오직 세그먼트 규칙만 적용(파일명 패턴 비활성화)** $\to$ Priority 7~10 평가.
3. **순수 파일명 패턴 분류기 ($R_{\text{file\_only}}$)**:
   - Priority 1~5 평가 $\to$ Priority 6에서 **오직 파일명 패턴만 적용(세그먼트 규칙 비활성화)** $\to$ Priority 7~10 평가.
4. **완전 복합 분류기 ($R_{\text{full}}$)**:
   - Priority 1~5 평가 $\to$ Priority 6에서 **세그먼트와 파일명 패턴 모두 적용** $\to$ Priority 7~10 평가.
   - *Phase B 표준 타깃 분류기.*

#### 2) 엄격한 인과관계 판정식 (Formal Causality Formulas)
전이 대상 노드 $n$의 원본 Role $R_{\text{orig}}$과 실제 산출 Role $R_{\text{actual}}$에 대해:

$$\begin{aligned}
\text{Pure Segment Causality} &\iff R_{\text{base}} \neq \text{TEST} \land R_{\text{file\_only}} \neq \text{TEST} \land R_{\text{seg\_only}} \equiv \text{TEST} \land R_{\text{full}} \equiv \text{TEST} \land R_{\text{actual}} \equiv \text{TEST} \\
\text{Pure File-Pattern Causality} &\iff R_{\text{base}} \neq \text{TEST} \land R_{\text{seg\_only}} \neq \text{TEST} \land R_{\text{file\_only}} \equiv \text{TEST} \land R_{\text{full}} \equiv \text{TEST} \land R_{\text{actual}} \equiv \text{TEST} \\
\text{Dual Causality} &\iff R_{\text{base}} \neq \text{TEST} \land R_{\text{seg\_only}} \equiv \text{TEST} \land R_{\text{file\_only}} \equiv \text{TEST} \land R_{\text{full}} \equiv \text{TEST} \land R_{\text{actual}} \equiv \text{TEST} \\
\text{Higher Priority Immunity} &\iff R_{\text{base}} \in \{\text{GRAMMAR}, \text{CONFIG}, \text{TOOLING\_ASSET}, \text{DOCUMENT}, \text{ASSET}\} \\
&\quad\implies R_{\text{seg\_only}} = R_{\text{file\_only}} = R_{\text{full}} = R_{\text{actual}} = R_{\text{base}}
\end{aligned}$$
