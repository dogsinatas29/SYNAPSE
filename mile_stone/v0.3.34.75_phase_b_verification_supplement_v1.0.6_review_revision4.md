## 2. P0: 핵심 수학적 매핑 및 알고리즘 명세 (Mathematical & Algorithmic Specifications)

### 2.1. 전체 노드 사상 함수 $M^*$ 및 Edge Endpoint 보존 불변식

#### 1) 부분 매핑 $M_{\text{id}}$에서 전체 매핑 $M^*$로의 확장
변환 대상 노드 집합 $V_{\text{target}} \subseteq V_{\text{NodeBuilder}} \subseteq V$에 대해, $M_{\text{id}}: V_{\text{target}} \to V'_{\text{target}}$는 일대일 전단사 함수입니다. 그러나 엣지 $e \in E$의 양 끝점($e.\text{from}, e.\text{to}$)은 $V_{\text{target}}$ 외부에 존재하는 노드(Ghost 노드, External 노드, 비-대상 NodeBuilder 노드)를 가리킬 수 있습니다.

따라서 전체 노드 집합 $V$에 대해 작용하는 **전체 사상 함수(Total Mapping Function) $M^*$**를 다음과 같이 정의합니다:

$$M^*(x) \triangleq \begin{cases} 
M_{\text{id}}(x), & \text{if } x \in V_{\text{target}} \\ 
x, & \text{if } x \notin V_{\text{target}} 
\end{cases}$$

#### 2) Edge 집합 전단사 및 완전 보존 불변식
변환된 엣지 집합 $E'$는 원본 엣지 집합 $E$에 대해 다음 불변식을 100% 만족해야 합니다:

1. **엣지 기수 불변 (Cardinality Invariant)**:
   $$|E'| \equiv |E|$$
2. **엣지 ID 보존 (ID Bijectivity)**:
   $$\forall e \in E, \quad e'.\text{id} \equiv e.\text{id} \quad (\text{단사성: } \forall e_1 \neq e_2 \implies e'_1.\text{id} \neq e'_2.\text{id})$$
3. **Endpoint 사상 일치성 (Endpoint Conformance under $M^*$)**:
   $$\forall e \in E, \quad e'.\text{from} \equiv M^*(e.\text{from}) \land e'.\text{to} \equiv M^*(e.\text{to})$$
4. **Endpoint 존재성 (Endpoint Existence)**:
   $$\forall e' \in E', \quad e'.\text{from} \in V' \land e'.\text{to} \in V'$$
5. **비-Endpoint 속성 불변 (Non-Endpoint Attribute Preservation)**:
   - 엣지의 `from`, `to`를 제외한 모든 메타데이터(`type`, `weight`, `data` 등)는 원본 객체와 Deep-Equal 일치.
   - **엄격한 부재 검사 규약**: `originatingId === undefined`와 같이 `undefined`와 빈 문자열(`""`)을 엄격히 구분하며, 단순 falsy 검사(`!originatingId`)를 배제.
6. **유령 엣지 생성 부재 (No Spurious Edges)**:
   $$E' \equiv \{ \text{transformEdge}(e) \mid e \in E \}$$

#### 3) 역매핑 $M_{\text{id}}^{-1}$ 독립 검증 5단계 절차
검증기는 수학적 정의에 그치지 않고, 다음 5단계 절차를 실행하여 역매핑의 유효성을 실증합니다:
- **Step 1**: 모든 $u \in V_{\text{target}}$에 대해 순서쌍 $(u, M_{\text{id}}(u))$를 수집.
- **Step 2**: 변환 ID를 키로, 원본 ID를 값으로 하는 역매핑 테이블 $M_{\text{rev}}$ 생성.
- **Step 3**: 역매핑 테이블의 크기가 대상 노드 수와 일치함을 검증 ($|M_{\text{rev}}| \equiv |V_{\text{target}}|$, 키 충돌 0건 확인).
- **Step 4**: 모든 $u \in V_{\text{target}}$에 대해 $M_{\text{rev}}(M_{\text{id}}(u)) \equiv u$ 전수 대조.
- **Step 5**: 불일치 또는 누락이 단 1건이라도 발생 시 즉시 치명적 예외 발생 (`throw Error("BIJECTIVE_INVERSE_MAPPING_FAILED")`).

### 2.2. 경로 정규화 8단계 결정적 알고리즘 (`auditNormalize`)

단순 20개 사례 나열을 넘어, 모든 입력 경로를 단 하나의 결정적 결과로 변환하는 알고리즘을 규정합니다.

```
Algorithm: auditNormalize(rawPath: string): string
Input: 임의의 경로 문자열 rawPath
Output: POSIX 표준화된 정규 경로

1. [Input & Empty Check]
   if rawPath is undefined or null or rawPath === "" then return rawPath;

2. [Virtual URI Bypass Check]
   if rawPath startsWith "ghost://" or "external://" or "builtin://" then
       return rawPath; // 가상 URI는 내부 세그먼트 변형 없이 원본 100% 보존

3. [Separator Normalization]
   let p = rawPath with all '\\' replaced by '/';

4. [Prefix Extraction & UNC Detection]
   let prefix = "";
   if p matches /^\/\/[^\/\s]+\/[^\/\s]+/ and not p.startsWith("///") then
       prefix = "//";      // 유효 UNC (서버명과 공유명 존재)
       p = p.substring(2);
   else if p.startsWith("/") then
       prefix = "/";       // POSIX 절대 경로
       p = p.replace(/^\/+/, "");
   else
       prefix = "";        // 상대 경로 또는 Windows 드라이브

5. [Windows Drive Preservation]
   if p matches /^[a-zA-Z]:/ then
       // 드라이브 문자 및 콜론 대소문자 보존, 드라이브 직후 슬래시 정규화
       p = p.substring(0, 2) + p.substring(2).replace(/^\/+/, "/");

6. [Consecutive Separator Collapse]
   p = p with all occurrences of /\/+/ replaced by "/";

7. [Segment Filtering & Parent Directory Preservation]
   let parts = p.split('/');
   let resolvedParts = [];
   for each part in parts do:
       if part === "" or part === "." then
           continue; // 빈 세그먼트 및 현재 디렉터리(.) 축약 제거
       else
           resolvedParts.push(part); // ".."를 포함한 모든 유의미 세그먼트 순서 보존
   end for
   p = resolvedParts.join('/');

8. [Final Assembly & Trailing Handling]
   if prefix === "/" and p === "" then return "/";
   if prefix === "//" and p === "" then return "/"; // 공유명 소실 시 절대 경로 강등
   return prefix + p;
```

- **20대 매트릭스 수렴 보장**: 위 8단계 알고리즘은 rev3 §2.2에 명시된 20대 Canonical Test Cases(POSIX 절대, UNC, Windows 드라이브, 점 축약, `..` 보존 등)에 대해 100% 동일한 기대값을 출력함을 수학적으로 보장합니다.

### 2.3. Oracle 입력 범위 및 저장소 기준 상대 경로 변환 규약

#### 1) 입력 경로 계약 (Input Path Contract)
- 워크스페이스 루트 경로를 $W_{\text{root}}$ (예: `/home/project`)라 할 때, Oracle의 Role 분류기는 **저장소 기준 상대 경로($p_{\text{rel}}$)**를 입력으로 요구합니다.
- 임의의 입력 경로 $p$에 대해 $p_{\text{rel}}$ 도출 절차:
  1. $p$가 가상 URI(`ghost://`, `external://`)인 경우 $\to$ Role 분류 대상에서 제외하고 해당 스키마 Role(`GHOST`, `EXTERNAL`)로 직행.
  2. $p$가 $W_{\text{root}} + '/'$로 시작하는 절대 경로인 경우 $\to$ $p_{\text{rel}} = p.\text{substring}(W_{\text{root}}.\text{length} + 1)$.
  3. $p$가 이미 상대 경로인 경우 $\to$ $p_{\text{rel}} = p$.
  4. $p$가 $W_{\text{root}}$ 외부에 위치한 절대 경로인 경우 $\to$ 비정상 진입으로 간주하여 `EXTERNAL`로 분류하거나 거부.

#### 2) `basename` 완전 일치 및 경로 세그먼트 평가
- Priority 2 CONFIG 등에서 "파일명 완전 일치"는 경로의 마지막 세그먼트인 **`path.posix.basename(p_rel)`**과의 대조로 명시합니다.
  $$\text{isConfigExactMatch} \iff \text{basename}(p_{\text{rel}}) \in \{ \text{"config.json"}, \text{"package.json"}, \text{"tsconfig.json"}, \dots \}$$

### 2.4. `TOOLING_SCRIPT` 정밀 분류 및 루트 판정

- **문제 A(절대 경로 판정 불일치) 해소**:
  $p_{\text{rel}}$을 기준으로 평가하므로, 루트 파일 여부는 **`!p_rel.includes('/')`**로 명확히 판정됩니다.
- **문제 B(하위 디렉터리 오분류) 해소**:
  `src/domain/tools/model.py`와 같은 소스 코드가 도구 스크립트로 왜곡되지 않도록 디렉터리 범위를 **저장소 최상위 도구 디렉터리**로 제한합니다.

#### 정밀 `TOOLING_SCRIPT` 매칭 규칙
```typescript
function isToolingScript(p_rel: string): boolean {
    const isRoot = !p_rel.includes('/');
    const baseLower = path.posix.basename(p_rel).toLowerCase();

    // 1. 루트 전용 빌드 매니페스트 및 설정 파일
    if (isRoot) {
        if (['sconstruct', 'setup.py', 'makefile', 'gruntfile.js', 'gulpfile.js'].includes(baseLower)) {
            return true;
        }
        if (/\.(sh|bash|zsh|bat|cmd|ps1)$/i.test(baseLower)) {
            return true;
        }
    }

    // 2. 저장소 최상위 디렉터리가 도구화 경로인 경우
    // 예: scripts/..., build/..., tools/..., ci/...
    if (/^(scripts|build|tools|ci)(\/|$)/i.test(p_rel)) {
        return true;
    }

    // 3. src/ 또는 lib/ 하위에 존재하는 파일은 내부 폴더명이 tools여도 일반 소스로 보존
    return false;
}
```

### 2.5. Role 입력 모집단 및 RUNTIME / UNCLASSIFIED 경계 규약

NodeBuilder가 다루는 노드 모집단과 Fallback 경계를 정의합니다:

1. **전체 노드 모집단 ($V_{\text{all}}$)**: SSoT 스냅샷의 모든 노드.
2. **NodeBuilder 대상 노드 ($V_{\text{NodeBuilder}}$)**: 파일 시스템 스캐너가 수집한 물리 파일 노드.
3. **Role 분류 대상 파일**:

4. **`UNCLASSIFIED` 보존 경계**:

## 3. P1: 반사실적 인과관계 및 Gate 1 기준선 증거 (Causality & Baseline Evidences)

### 3.1. 3대 개념 분리 및 적합성 검증 ($R_{\text{actual}} \equiv R_{\text{full}}$)

반사실적 분석에서 인과 분류, 구현 적합성, 실행 경로 증거의 3대 개념을 엄격히 분리합니다:

1. **반사실적 인과 분류 (Causal Classification)**:
   - 독립 Oracle의 4대 분류기($R_{\text{base}}, R_{\text{seg\_only}}, R_{\text{file\_only}}, R_{\text{full}}$)를 비교하여 규칙의 수학적 기여도를 순수 세그먼트, 순수 파일 패턴, 복합 기여로 범주화.
2. **구현 적합성 검증 (Implementation Conformance)**:
   - 전이 대상 노드에 대해 실제 산출 Role $R_{\text{actual}}$이 완전 Oracle의 판정과 일치하는지 단언:
     $$\forall n \in V_{\text{transition}}, \quad R_{\text{actual}}(n) \equiv R_{\text{full}}(n)$$
     - Gate A: $R_{\text{sim}} \equiv R_{\text{full}}$
     - Gate B: $R_{\text{prod}} \equiv R_{\text{full}}$
3. **실행 경로 증거 (Execution Trace)**:
   - 런타임 분기 로그를 통해 실제 코드가 어떤 분기 조건을 통과했는지 확인하는 별도 증거 (Gate B 사후 단계).

#### 잔여 실패 범주 (`UNEXPLAINED_TRANSITION`) 및 모집단
- **전이 모집단 정의**:
  $$V_{\text{transition}} \triangleq \{ n \in V_{\text{NodeBuilder}} \mid R_{\text{orig}}(n) \neq \text{TEST} \land R_{\text{actual}}(n) \equiv \text{TEST} \}$$
- **실패 판정**: $V_{\text{transition}}$ 내의 모든 노드는 반드시 Pure Segment, Pure File, Dual Causality 중 하나에 속해야 하며, $R_{\text{full}} \neq \text{TEST}$이거나 세 범주 어디에도 속하지 않는 노드가 발견되면 즉시 치명적 예외 발생 (`throw Error("UNEXPLAINED_TRANSITION_DETECTED")`).

## 4. Gate C1 / C2 완전 자립형 실행 규약 (Self-Contained Gate Specifications)

Gate C1과 C2를 본 문서 단독으로 완전히 이해하고 집행할 수 있도록 입출력, 환경, 권한, 실패 조치를 명문화합니다:

### 4.1. Gate C1 (Pre-Mutation Non-Destructive Pipeline Verification)
- **목적**: 실제 SSoT 데이터를 변경하기 전, 격리된 비파괴 환경에서 전체 파이프라인의 생존성 및 예상 SSoT Diff, 3종 리포트 무결성을 사전 검증.
- **실행 환경**: 원본 저장소와 완전히 분리된 임시 격리 디렉터리 (예: `/tmp/synapse_isolated_c1/`). 원본 SSoT 파일에 대한 쓰기 권한 원천 차단.
- **입력 데이터**: 원본 `project_state.json`의 격리 복사본, 프로덕션 수정본 `NodeBuilder.ts`.
- **수행 작업**:
  1. 전체 `DataPipeline` 가동 및 그래프 생성.
  2. 산출된 후보 상태와 원본 간의 Diff를 계산하여 Allow-list ID와 100% 일치하는지 검산.
  3. 3종 리포트(Onboarding, Architect, Simulation Debug)를 생성하여 의도치 않은 의미적 드리프트가 0건인지 검증.
- **필요 권한**: **`별도 Execution Authorization`** (이 권한은 실제 SSoT 변경 권한을 포함하지 않음).
- **실패 시 조치**: 파이프라인 오류 발생 또는 예상치 못한 Diff 발견 시 즉시 작업을 중단하고 임시 디렉터리를 폐기하며, 코드 동결 상태로 회귀.

### 4.2. Gate C2 (Post-Mutation SSoT Verification)
- **목적**: 마스터의 명시적 승인을 받아 실제 프로덕션 SSoT(`synapse_data/project_state.json`)를 갱신한 후, 최종 상태의 정합성과 리포트 결과를 사후 검증.
- **실행 환경**: 공식 프로젝트 워크스페이스.
- **입력 데이터**: 공식 워크스페이스 SSoT.
- **수행 작업**:
  1. 승인된 변환을 공식 SSoT에 반영.
  2. 실제 갱신된 `project_state.json`의 Diff가 Gate C1에서 사전 검증된 예상 Diff와 바이트 단위로 일치하는지 검증.
  3. 공식 3종 리포트를 재생성하여 Gate C1 리포트와 SHA-256 일치 확인.
  4. 감사 로그 및 최종 Git 커밋 생성.
- **필요 권한**: **`별도 SSoT Mutate Authorization AND Execution Authorization`**.
- **권한 한정 범위**: Gate C2 승인은 해당 회차의 승인된 변경 범위(Allow-list ID)에만 엄격히 국한되며, 향후 모든 변경에 대한 포괄적 권한으로 확장되지 않음.
- **실패 시 조치**: 불일치 발생 시 즉시 Git 체크아웃(`git restore project_state.json`)으로 원본 복구 후 비상 정지.
