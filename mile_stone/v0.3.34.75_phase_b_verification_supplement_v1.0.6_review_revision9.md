## 2. P0: Gate C2 Crash-Durable Transaction & Safe Atomic-Replace Protocol (§2.4 전면 보강)

### 2.1. 파일시스템 및 운영체제 전제 조건 (Filesystem Prerequisites)
- 본 트랜잭션 규약은 **동일 파일시스템 내에서 POSIX `rename(2)`의 원자성과 디렉터리 엔트리 `fsync`가 보장되는 로컬 파일시스템(Linux ext4, xfs 등)**을 전제로 합니다. 원자적 rename 시맨틱을 보장하지 않는 원격 네트워크 파일시스템(NFS, CIFS 등)은 지원 대상에서 제외합니다.

### 2.2. 영속 트랜잭션 저널 규약 (`project_state.json.journal`)
메모리 휘발성 데이터에 의존하지 않고, 크래시 발생 후 재시작 시에도 복구 상태를 판별할 수 있도록 디스크에 영속 저널을 기록합니다:

```typescript
interface TransactionJournal {
    txId: string;               // 트랜잭션 고유 UUID
    timestamp: string;          // ISO 8601 타임스탬프
    sourcePath: string;         // 'synapse_data/project_state.json'
    backupPath: string;         // 'synapse_data/project_state.json.bak_c2'
    tempPath: string;           // 'synapse_data/project_state.json.tmp_c2'
    hOrig: string;              // 원본 파일의 SHA-256 Checksum
    hCandidate: string;         // 승인된 변환 후보의 SHA-256 Checksum
    state: 'PREPARING' | 'BACKED_UP' | 'MUTATED' | 'COMMITTED' | 'ROLLED_BACK';
    pid: number;                // 실행 프로세스 ID
    hostname: string;           // 실행 호스트명
    sourceDev: number;          // 원본 파일 st_dev (Inode 디바이스)
    sourceIno: number;          // 원본 파일 st_ino (Inode 번호)
}
```

### 2.3. 락 소유권 및 Stale Lock 판정 규약 (`project_state.json.lock`)
1. **락 생성**: `synapse_data/project_state.json.lock`에 `{ pid, hostname, timestamp, txId }`를 `O_CREAT | O_EXCL`로 기록하고 `fsync(lock_fd)` 및 디렉터리 `fsync` 수행.
2. **Stale Lock 판정**: 이미 락 파일이 존재할 경우:
   - 락 파일 내부의 `hostname`이 현재 머신과 일치하는지 확인.
   - 일치하는 경우, OS 시그널 검사 `process.kill(pid, 0)` 실행:
     - 시그널 전송 성공 (프로세스 생존): **동시 실행 충돌로 판정, 즉시 비상 정지 (`throw Error("CONCURRENT_MUTATION_LOCKED")`)**.
     - `ESRCH` 오류 반환 (프로세스 사망 확인): 비정상 종료된 **Stale Lock**으로 판정하고, 후술할 저널 기반 크래시 복구 머신으로 진입.
     - 다른 호스트이거나 권한 오류(`EPERM`): 외부 소유 락이므로 즉시 중단.

### 2.4. Crash-Durable 실행 및 원자적 교체 6단계 절차

```
[1. Lock 획득 (O_EXCL)] ──> [2. lstat 검사 & Inode 기록] ──> [3. Journal 기록 (PREPARING) & fsync]
                                                                                │
┌───────────────────────────────────────────────────────────────────────────────┘
▼
[4. Backup 생성 (O_EXCL) & fsync(bak) & fsync(dir)] ──> [5. Journal 갱신 (BACKED_UP) & fsync]
                                                                                │
┌───────────────────────────────────────────────────────────────────────────────┘
▼
[6. Temp 생성 (O_EXCL) & fsync(tmp)] ──> [7. Inode 재검증] ──> [8. rename(tmp -> target) & fsync(dir)]
                                                                                │
┌───────────────────────────────────────────────────────────────────────────────┘
▼
[9. Journal 갱신 (MUTATED) & fsync] ──> [10. 사후 검증] ──(성공 시)──> [11. COMMITTED & 정리]
                                                      └──(실패 시)──> [12. 원자적 롤백 절차]
```

1. **Step 1: 사전 검사 및 Inode 캡처**:
   - `fs.lstatSync("synapse_data/project_state.json")` 실행: 반드시 일반 파일이어야 하며 심볼릭 링크 거부 (`stat.isFile() && !stat.isSymbolicLink()`).
   - Inode 번호 캡처: `sourceDev = stat.dev`, `sourceIno = stat.ino`.
   - 잔여 임시 파일(`*.bak_c2`, `*.tmp_c2`, `*.restore_tmp`) 존재 시 즉시 중단.
2. **Step 2: 초기 저널 영속화 (`PREPARING`)**:
   - 저널 생성 (`O_CREAT | O_EXCL`) $\to$ `fsync` $\to$ 디렉터리 `fsync`.
3. **Step 3: 내구성 백업 생성 및 저널 갱신 (`BACKED_UP`)**:
   - `project_state.json.bak_c2`를 `O_CREAT | O_EXCL`로 생성하고 스트림 복사.
   - `fs.fsyncSync(fd_bak)` $\to$ `fs.closeSync(fd_bak)` $\to$ 디렉터리 `fsync(dir_fd)`.
   - $H_{\text{bak}} = \text{sha256}(project\_state.json.bak_c2)$ 계산 및 $H_{\text{orig}} \equiv H_{\text{bak}}$ 단언.
   - 저널 상태를 `BACKED_UP`으로 원자적 갱신 $\to$ `fsync(journal_fd)`.
4. **Step 4: 임시 파일 기록 및 Inode 일치 검증**:
   - `project_state.json.tmp_c2`에 승인된 변환 결과 기록 (`O_CREAT | O_EXCL`) $\to$ `fsync(fd_tmp)`.
   - **TOCTOU 방지 Inode 재검증**:
     `currStat = fs.lstatSync("synapse_data/project_state.json")`.
     단언: `currStat.dev === sourceDev && currStat.ino === sourceIno` (외부 프로세스에 의해 원본 파일이 교체되지 않았음을 물리적으로 보증).
5. **Step 5: 원자적 교체 및 저널 갱신 (`MUTATED`)**:
   - `fs.renameSync("synapse_data/project_state.json.tmp_c2", "synapse_data/project_state.json")`.
   - `synapse_data/` 디렉터리에 대해 `fs.fsyncSync(dir_fd)` 실행 (디렉터리 엔트리 내구성 보장).
   - 저널 상태를 `MUTATED`로 갱신 $\to$ `fsync(journal_fd)`.
6. **Step 6: 사후 검증 및 최종 커밋 (`COMMITTED`)**:
   - SSoT Diff 및 3종 리포트 전수 검증 통과 시:
     저널 상태를 `COMMITTED`로 갱신 $\to$ `fsync` $\to$ 백업 파일, 저널 파일, 락 파일 안전 삭제.

### 2.5. Crash 복구 상태 판정 머신 (Crash Recovery State Machine)
프로세스 크래시 후 시스템이 재시작되거나 Stale Lock이 감지되었을 때 영속 저널을 판독하여 다음 상태 전이를 강제합니다:

| 저널 기록 상태 | 실제 파일 상태 및 해시 대조 | 자동 복구 동작 | 최종 전이 상태 |
|---|---|---|:---:|
| **`PREPARING`** | 백업 생성 미완료 상태 | 임시/저널/락 파일 삭제 후 원본 유지 | **CLEAN_ABORT** |
| **`BACKED_UP`** | $H_{\text{target}} \equiv H_{\text{orig}}$ (원본 불변), 백업 해시 $H_{\text{bak}} \equiv H_{\text{orig}}$ 유효 | 미적용 크래시이므로 임시/백업/저널/락 안전 삭제 | **CLEAN_ABORT** |
| **`MUTATED`** | $H_{\text{target}} \equiv H_{\text{candidate}}$, 백업 해시 $H_{\text{bak}} \equiv H_{\text{orig}}$ 유효 | 교체 완료 후 사후 검증 중 크래시. Gate C1 리포트와 재검증 후 통과 시 `COMMITTED` 전이, 불일치 시 롤백 | **VERIFY_OR_ROLLBACK** |
| **`ROLLED_BACK`** | $H_{\text{target}} \equiv H_{\text{orig}}$ 복구 확인 | 저널/락 파일 안전 삭제 | **CLEAN_ABORT** |
| **비정상 상태** | • 원본 파일 누락 또는 비-일반 파일 감지<br>• 백업 파일 누락 또는 백업 해시 파손($H_{\text{bak}} \not\equiv H_{\text{orig}}$)<br>• 저널 파일 문법 파손 또는 미등록 상태 | **자동 복구 전면 금지**. 락 및 저널을 유지한 채 시스템 영구 비상 정지 | **`EMERGENCY_MANUAL_LOCK`** |

## 3. P0: 경로 정규화, UNC 대소문자 정책 및 순차 파이프라인 (§3 보강)

### 3.1. UNC 대소문자 정책 및 $W_{\text{canon}}$ 상대화 알고리즘 (`getRelativePathIfInside`)

#### 1) UNC 대소문자 정책
- **서버명(Server) 및 공유명(Share)**: Windows 및 POSIX 네트워킹 표준에 따라 **대소문자 무관(Case-Insensitive) 비교**를 강제 (`server.toLowerCase()`, `share.toLowerCase()`).
- **공유명 하위 서브패스(Subpath)**: SYNAPSE의 렉시컬 정규화 계약에 따라 **대소문자 구분(Case-Sensitive) 바이트 비교**를 수행.

#### 2) `getRelativePathIfInside` 완전 알고리즘
```typescript
export function getRelativePathIfInside(p: string, W_canon: string): string | null {
    if (p === W_canon) return null; // 워크스페이스 루트 자체는 파일이 아님

    // 1. POSIX 루트 특수 분기: W_canon === '/'
    if (W_canon === '/') {
        if (p.startsWith('/') && !p.startsWith('//')) {
            return p.substring(1); // 선행 슬래시만 제거 ('/home/a.ts' -> 'home/a.ts')
        }
        return null;
    }

    // 2. Windows 드라이브 루트 특수 분기: W_canon === 'C:/'
    if (/^[a-zA-Z]:\/$/.test(W_canon)) {
        const drive = W_canon.substring(0, 2).toUpperCase();
        if (/^[a-zA-Z]:\//.test(p) && p.substring(0, 2).toUpperCase() === drive) {
            return p.substring(3); // 'C:/' 접두사 제거 ('C:/project/a.ts' -> 'project/a.ts')
        }
        return null;
    }

    // 3. 일반 Windows 드라이브 하위 경로: W_canon === 'C:/workspace'
    if (/^[a-zA-Z]:\//.test(W_canon)) {
        const drive = W_canon.substring(0, 2).toUpperCase();
        if (!/^[a-zA-Z]:\//.test(p) || p.substring(0, 2).toUpperCase() !== drive) {
            return null; // 다른 드라이브 또는 비-드라이브 경로
        }
        const pSub = drive + p.substring(2);
        const wSub = drive + W_canon.substring(2) + '/';
        if (pSub.startsWith(wSub)) {
            return pSub.substring(wSub.length);
        }
        return null;
    }

    // 4. UNC 경로: W_canon === '//server/share'
    if (W_canon.startsWith('//')) {
        const uncPattern = /^\/\/([^/]+)\/([^/]+)(\/.*)?$/;
        const matchW = W_canon.match(uncPattern);
        const matchP = p.match(uncPattern);
        if (!matchW || !matchP) return null;

        // 서버명과 공유명은 대소문자 무관 비교
        if (matchW[1].toLowerCase() !== matchP[1].toLowerCase() ||
            matchW[2].toLowerCase() !== matchP[2].toLowerCase()) {
            return null;
        }

        const subW = (matchW[3] || '').replace(/^\/+/, '');
        const subP = (matchP[3] || '').replace(/^\/+/, '');
        if (subW === '') {
            return subP; // W_canon이 //server/share 자체인 경우
        }
        const prefix = subW.endsWith('/') ? subW : subW + '/';
        if (subP.startsWith(prefix)) {
            return subP.substring(prefix.length);
        }
        return null;
    }

    // 5. 일반 POSIX 경로: W_canon === '/home/project'
    const prefix = W_canon.endsWith('/') ? W_canon : W_canon + '/';
    if (p.startsWith(prefix)) {
        return p.substring(prefix.length);
    }
    return null;
}
```

### 3.2. Oracle 경로 파이프라인 4단계 순차 호출 계약
임의의 경로 $p$에 대해 다음 4단계 파이프라인을 엄격한 순서로 강제하며, 중간 단계 실패 시 즉시 파이프라인을 중단합니다:

```
[입력 rawPath] ──> [Step 1. auditNormalize(rawPath)] ──> [Step 2. isAbsolutePath & 상대화]
                                                                        │
┌───────────────────────────────────────────────────────────────────────┘
▼
[Step 3. validateNoWorkspaceEscape(p_rel)] ──> [Step 4. determineNodeRole(p_rel)]
```

1. **Step 1 (정규화)**: $p_{\text{norm}} = \text{auditNormalize}(rawPath)$.
2. **Step 2 (경계 검증 및 상대화)**:
   - 가상 URI인 경우: Role 스키마로 직행.
   - 절대 경로인 경우(`isAbsolutePath(p_norm)`):
     $p_{\text{rel}} = \text{getRelativePathIfInside}(p_{\text{norm}}, W_{\text{canon}})$.
     만약 $p_{\text{rel}} === \text{null}$이면 **즉시 거부 (`throw Error("EXTERNAL_ABSOLUTE_PATH_REJECTED: " + rawPath)`)**.
   - 상대 경로인 경우: $p_{\text{rel}} = p_{\text{norm}}$.
3. **Step 3 (워크스페이스 탈출 검증)**:
   `validateNoWorkspaceEscape(p_rel)` 실행. 깊이가 0 미만으로 떨어지면 **즉시 거부 (`throw Error("WORKSPACE_ESCAPE_DETECTED")`)**.
4. **Step 4 (역할 판정)**:
   검증된 $p_{\text{rel}}$을 10단계 Oracle 규칙표에 전달하여 최종 Role 도출.

## 4. P1: Oracle 4대 분류기 및 Role 전이 인과관계 판정 알고리즘 (§4 보강)

### 4.1. $V_{\text{NodeBuilder}}$ 물리 노드 모집단 경계 명문화
- **모집단 정의**: $V_{\text{NodeBuilder}}$는 SYNAPSE 파일 스캐너가 워크스페이스 파일시스템을 순회하여 발견한 **실제 물리 파일 노드(Physical File Nodes)의 집합**으로 엄격히 한정합니다.
- **배제 대상**: `ghost://`, `external://`, `builtin://` 등 가상 스키마 노드 및 집계 노드(`AGGREGATE_*`)는 $V_{\text{NodeBuilder}}$에 포함되지 않으며, Role 강제 승격 대상에서 원천 배제됩니다.

### 4.2. 전이 인과관계 판정 알고리즘 (`classifyRoleTransition`)
전이 모집단 $V_{\text{transition}} \triangleq \{ n \in V_{\text{NodeBuilder}} \mid R_{\text{orig}}(n) \neq \text{TEST} \land R_{\text{actual}}(n) \equiv \text{TEST} \}$에 대해 다음 공식 알고리즘을 강제합니다:

```typescript
export function classifyRoleTransition(
    r_orig: string,
    r_base: string,
    r_seg: string,
    r_file: string,
    r_full: string,
    r_actual: string
): 'PURE_SEGMENT_CAUSALITY' | 'PURE_FILE_CAUSALITY' | 'DUAL_CAUSALITY' | 'CONFORMANCE_MISMATCH' | 'NOT_A_TRANSITION_TARGET' | 'UNEXPLAINED_TRANSITION' {
    // 1. 구현 적합성 선행 검증 (Implementation Conformance Check)
    if (r_actual !== r_full) {
        return 'CONFORMANCE_MISMATCH';
    }

    // 2. 최종 TEST 승격 불변식 검증 (Target Must Be TEST)
    if (r_full !== 'TEST') {
        return 'NOT_A_TRANSITION_TARGET';
    }

    // 3. Phase A 원본 불변식 검증 (Baseline Role Invariant)
    // 원본 Role이 이미 TEST였거나, 테스트 규칙이 없는 r_base에서 TEST인 노드는 신규 승격 대상이 아님
    if (r_orig === 'TEST' || r_base === 'TEST') {
        return 'NOT_A_TRANSITION_TARGET';
    }

    // 4. 반사실적 인과관계 3대 상호 배타적 분기
    const segIsTest = (r_seg === 'TEST');
    const fileIsTest = (r_file === 'TEST');

    if (segIsTest && fileIsTest) {
        return 'DUAL_CAUSALITY';
    }
    if (segIsTest && !fileIsTest) {
        return 'PURE_SEGMENT_CAUSALITY';
    }
    if (!segIsTest && fileIsTest) {
        return 'PURE_FILE_CAUSALITY';
    }

    // 5. 상기 3대 범주에 속하지 않는 전이는 미설명 왜곡으로 간주
    return 'UNEXPLAINED_TRANSITION';
}
```

- **실패 판정**: $V_{\text{transition}}$ 내의 노드 중 `classifyRoleTransition` 결과가 `CONFORMANCE_MISMATCH` 또는 `UNEXPLAINED_TRANSITION`을 반환하는 노드가 1건이라도 존재하면 **즉시 검증을 영구 중단 (`throw Error("UNEXPLAINED_ROLE_TRANSITION_DETECTED")`)**합니다.

## 5. P1: 전체 사상 $M^*$ 정의역 완전성 및 `deepEqualJSON` 비교 계약 (§5 보강)

### 5.1. $M_{\text{id}}$ 정의역($V_{\text{target}}$) 완전성 및 전역 단사성 검증 절차
변환 테이블 $M_{\text{id}}$가 Allow-list 집합 $V_{\text{target}}$과 완벽히 일치함을 보증하는 6단계 검증 절차:

1. **정의역 양방향 완전 일치 (Domain Exact Match)**:
   - $M_{\text{id}}$의 모든 키가 $V_{\text{target}}$에 포함됨: $\forall k \in \text{keys}(M_{\text{id}}), k \in V_{\text{target}}$.
   - $V_{\text{target}}$의 모든 노드가 $M_{\text{id}}$에 존재함: $\forall u \in V_{\text{target}}, M_{\text{id}}.\text{has}(u)$.
   - 단언: $M_{\text{id}}.\text{size} \equiv V_{\text{target}}.\text{size}$.
2. **매핑 값 유효성**: $\forall v \in \text{values}(M_{\text{id}})$, `typeof v === 'string' && v.trim() !== ''`.
3. **매핑 내부 단사성 (Injectivity on Target)**:
   `new Set(M_id.values()).size === V_target.size` (대상 노드 간 충돌 0건).
4. **전역 배타성 (Global Disjointness)**:
   $$\forall v \in \text{values}(M_{\text{id}}), \quad v \notin (V \setminus V_{\text{target}})$$
   (변환된 새 ID가 비대상 노드의 기존 ID와 단 1건도 교집합을 갖지 않음).
5. **비대상 항등 사상**: $\forall x \in V \setminus V_{\text{target}}, M^*(x) \equiv x$.
6. **전체 기수 보존 검산**: $|M^*(V)| \equiv |V|$.

### 5.2. `deepEqualJSON` 재귀 비교 알고리즘 및 Edge 메타데이터 불변 계약

JavaScript의 `===` 배열 참조 비교 결함을 원천 해결한 정규 재귀 비교 함수:

```typescript
export function deepEqualJSON(a: any, b: any): boolean {
    if (a === b) return true;
    if (a === null || b === null || typeof a !== 'object' || typeof b !== 'object') {
        return false;
    }

    // 1. 배열 타입 및 원소별 순서 보존 비교
    const aIsArray = Array.isArray(a);
    const bIsArray = Array.isArray(b);
    if (aIsArray !== bIsArray) return false;

    if (aIsArray) {
        if (a.length !== b.length) return false;
        for (let i = 0; i < a.length; i++) {
            if (!deepEqualJSON(a[i], b[i])) return false;
        }
        return true;
    }

    // 2. 객체 Own Property 키 정렬 및 값 재귀 비교
    const keysA = Object.keys(a).filter(k => Object.prototype.hasOwnProperty.call(a, k)).sort();
    const keysB = Object.keys(b).filter(k => Object.prototype.hasOwnProperty.call(b, k)).sort();

    if (keysA.length !== keysB.length) return false;
    for (let i = 0; i < keysA.length; i++) {
        if (keysA[i] !== keysB[i]) return false;
        if (!deepEqualJSON(a[keysA[i]], b[keysB[i]])) return false;
    }

    return true;
}
```

- **Edge 메타데이터 불변성 강제**:
  모든 엣지 $e \in E$에 대해, 변경 허용 필드인 `from`, `to`를 제외한 잔여 객체 `restE = { id: e.id, type: e.type, data: e.data, provenance: e.provenance, weight: e.weight }`가 변환 전후 `deepEqualJSON(restE_orig, restE_trans) === true`임을 전수 검증합니다.
