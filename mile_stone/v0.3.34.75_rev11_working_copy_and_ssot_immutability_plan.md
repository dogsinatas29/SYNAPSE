## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 근본 원인 및 완전한 제거
과거 rev1~10 보완 문서는 **"공식 SSoT(`project_state.json`)를 디스크 상에서 인플레이스로 수정하고 크래시 시 이를 복구해야 한다"**는 잘못된 전제에서 출발했습니다.  
이로 인해 파일 시스템의 원자성 한계를 메우기 위해 2단계 저널, 복구 락, Stale Lock 세대 판독, 14개 분기 복구 매트릭스라는 극단적인 복잡성에 빠졌습니다.

### 1.2 "최고의 복구는 복구할 필요 자체를 만들지 않는 것"
사용자의 명확한 KISS 원칙에 따라, 문제를 아키텍처 수준에서 원천 차단합니다:
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **SSoT 영구 불변**: 수집기(Bootstrap)가 생성한 `project_state.json`은 읽기 전용 불변 원본으로 박제합니다.
2. **Working Copy 격리 분석**: 분석·검증 파이프라인은 원본의 일회용 복사본(Working Copy)에서 실행되며, 실패 시 해당 복사본을 즉시 폐기하고 원본에서 다시 복사합니다. 롤백 저널과 상태 복구 매트릭스는 완전히 불필요합니다.
3. **데이터 소유권 분리**: 캔버스 프레젠테이션과 사용자 편집 데이터는 SSoT 원본에서 완전히 분리된 전용 오버레이 파일(`layout.json`, `user_graph.json`)로 영속화합니다.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① project_state.json           │ ② Disposable Working Copy             │
│    [Immutable SSoT]            │    [In-Memory / Temporary]            │
│    - 수집기(Bootstrap) 전용     │    - 원본 복사본에서 분석·검증 수행   │
│    - 노드, 엣지, 클러스터      │    - 실패 시 즉시 폐기 (롤백 불필요)  │
│    - 분석 중 읽기 전용 (RO)    │    - 분석 산출물은 리포트로 저장      │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가 노드/엣지            │
│    - 뷰포트(zoom, offset)      │    - 사용자 편집 라벨/메타데이터      │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. SSoT 생명주기 및 불변성 계약 (SSoT Lifecycle Contract)

SSoT 불변성은 영구적 속성이면서 Bootstrap 세대별로 명확히 관리됩니다.

| 생명주기 단계 | 허용되는 동작 | SSoT (`project_state.json`) 처리 정책 |
|:---|:---|:---|
| **Phase 1: 최초 생성 (Bootstrap)** | 프로젝트 초기 스캔 | `BootstrapEngine`이 신규 SSoT 생성 후 디스크 `fsync` 기록. |
| **Phase 2: 기준선 고정 (Baseline Frozen)** | 분석 및 일반 운영 | **영구 불변 고정 (Read-Only)**. 파일 해시 매니페스트 등록. |
| **Phase 3: 분석 및 검증 (Analysis)** | 토폴로지 분석, 리포트 생성 | **원본 수정 절대 금지**. 메모리 또는 임시 Working Copy에서만 수행. |
| **Phase 4: UI 인터랙션 (Canvas UI)** | 드래그, 줌, 클러스터 접힘 | SSoT 쓰기 완전 차단. 오직 `layout.json`에만 저장. |
| **Phase 5: 사용자 그래프 편집** | 노드/엣지 추가, 삭제, 수정 | SSoT 쓰기 완전 차단. 오직 `user_graph.json`에만 저장. |
| **Phase 6: 명시적 재수집 (Re-Harvesting)**| 사용자의 명시적 전체 재스캔 요청 | **기존 SSoT 덮어쓰기 금지**. 기존본을 `project_state.v{N}.json`으로 보존 후 새 세대 SSoT 생성. |

> ⚠️ **재생성 금지 규약**:
> - 기존 SSoT의 손상이나 분석 실패를 복구하기 위한 자동 재생성은 엄격히 금지합니다.
> - 분석 복사본이 손상되면 복사본만 폐기하고 원본에서 다시 복사합니다.

## 5. `layout.json` 원자적 저장 및 동시성 제어 계약 (Layout Contract)

`layout.json`은 크래시 복구 매트릭스를 필요로 하지 않는 경량 파일(수십 KB)이지만, 사용자 레이아웃 보존을 위해 파일 시스템 수준의 원자성을 엄격히 준수합니다.

### 5.1 원자적 저장 프로토콜 (Atomic Save Sequence)
1. **임시 파일 생성:** 대상 디렉터리(`synapse_data/`) 내에 임시 파일 `layout.json.tmp.{pid}.{timestamp}` 생성.
2. **페이로드 직렬화 및 기록:** JSON 직렬화 후 임시 파일에 기록.
3. **임시 파일 `fsync`:** `fsyncSync(tmpFd)`로 데이터 및 파일 메타데이터 내구성 확보 후 닫기.
4. **부모 디렉터리 `fsync` (1차):** 임시 파일 엔트리 내구성 확보.
5. **원자적 교체 (`rename`):** POSIX 원자적 연산인 `fs.renameSync(tmpPath, layoutPath)` 호출로 교체.
6. **부모 디렉터리 `fsync` (2차):** 교체된 디렉터리 엔트리 내구성 확보.
- **예외 처리:** 도중 실패 시 임시 파일은 즉시 unlink하며, 기존 `layout.json`은 1바이트의 손상 없이 보존됩니다.

### 5.2 Extension Host 직렬화 및 Revision 동기화
- **단일 Writer 보장:** 저장은 오직 VS Code Extension Host 메인 스레드의 직렬 큐(Serial Queue)를 통해 처리됩니다.
- **단조 증가 Revision:** `layout.json`에는 정수형 `revision`이 포함되며, 저장 시마다 1씩 증가합니다.
- **Stale Write 차단:** 웹뷰가 전달한 revision이 디스크의 최신 revision보다 낮으면 저장을 거부하고 최신 상태를 웹뷰로 다시 전송합니다 (Snap-back 완벽 차단).

### 5.3 오버레이 병합 및 유효성 검증 규칙 (Validation Rules)
로드 시 Extension Host는 다음 규칙에 따라 안전하게 병합합니다:
1. **정상 항목:** 유효한 좌표 `[x, y]`는 SSoT의 초기 좌표를 덮어씁니다.
2. **잘못된 항목 격리:** `NaN`, `Infinity`, 범위를 벗어난 비정상 좌표는 무시하고 SSoT의 초기 좌표를 유지합니다.
3. **고아 ID (Orphan NodeId):** SSoT에 존재하지 않는 NodeId는 병합하지 않고 `layout.orphans`로 격리 보존(사후 복구용).
4. **파일 전체 파손 시 (JSON Syntax Error):** SSoT의 초기 좌표로 안전하게 캔버스를 띄우며, 사용자에게 `layout.json` 파손 알림을 띄우고 원본 SSoT는 절대 변조하지 않습니다.

### 5.4 레이아웃 초기화의 정의
- **레이아웃 초기화:** `layout.json`을 물리 삭제하는 대신, `revision`을 증가시키며 `positions: {}` (빈 오버레이)를 기록하여 SSoT의 초기 스냅샷 좌표로 복귀합니다 (오래된 웹뷰 요청에 의한 역전 방지).
- **자동 배치 재계산:** 백엔드 레이아웃 엔진(ELK/Dagre)을 재실행하는 기능은 별도의 독립 명령어로 제공합니다.

## 6. SSoT 기준선 무결성 검증 (Sanity Guard)

- **역할 한정:** 전체 SSoT SHA-256 검사는 쓰기 방지 장치가 아니라, **비정상 변경 감지(Assertion Guard)**로 한정합니다.
- **검증 프로토콜:**
  1. 분석 파이프라인 구동 시 원본 SSoT SHA-256 기록.
  2. 일회용 Working Copy 생성 후 SHA-256 일치 확인.
  3. Working Copy에서 분석 실행.
  4. 분석 완료 후 원본 SSoT SHA-256 재검증 $\rightarrow$ **0 Byte Diff 불변성(PASS) 강제 단언**.
- **영구 고정 기준선 매니페스트:**
  - **Godot Production SSoT:** `ddd7aa2982b591f881c95692bbb26f9adde521366742a36a40b49a3b5e56174b` (32,107,872 bytes)
  - **VS Code Production SSoT:** `2524c6da38c7d9951a60678eb90766e9ba217cb100667038ff7836bbe627052b` (61,600,613 bytes)
  - **VS Code Regex Subset:** `a8443c3e8b1e8517283c090c9e7a2c953bd35247b82029a91f2314ffb53bde1a` (31,232,831 bytes)
