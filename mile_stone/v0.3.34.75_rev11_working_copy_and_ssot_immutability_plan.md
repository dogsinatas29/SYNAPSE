## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 완전한 일소
과거의 복잡성은 "과거 SSoT를 이력으로 보관하고 롤백·교체하겠다"는 미련에서 출발했습니다.  
SYNAPSE는 소스 코드 형상 관리 도구가 아니며, **"현재 프로젝트 소스 트리의 아키텍처를 시각화하고 진단하는 분석 엔진"**입니다.  
프로젝트 코드가 바뀌어 재수집(Re-Bootstrap)이 발생하면, 이전 SSoT의 세대 번호를 따질 필요 없이 **새로운 단일 `project_state.json`이 유일한 기준 원본**이 됩니다.

### 1.2 단순화된 3대 불변식
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **Bootstrap 소유 교체 가능 SSoT (`project_state.json`)**: 수집기(Bootstrap)만 작성하며, UI와 분석기는 절대 직접 수정하지 않는 읽기 전용 기준 원본 (Bootstrap-owned replaceable SSoT).
2. **분석별 독립 Working Copy**: 분석 파이프라인(전체 클러스터 분석, 선택 그룹 분석 등)은 디스크 원본에서 직접 파싱된 독립 메모리 객체에서 실행되며, 종료 시 즉시 폐기.
3. **2대 오버레이 분리**: 사용자의 시각적 조작은 `layout.json`(좌표/뷰포트)에, 사용자 그래프 편집은 `user_graph.json`(노드/엣지 추가·수정·삭제)에만 영속화.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① project_state.json           │ ② Disposable Working Copy             │
│    [SSoT: Bootstrap-Owned]     │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - 노드, 엣지, 클러스터      │    - 분석 A/B 간 객체 공유 0건        │
│    - UI/분석기 직접 수정 금지  │    - 분석 종료 시 즉시 GC 폐기        │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가/수정/삭제 노드       │
│    - 뷰포트(zoom, offset)      │    - 사용자 확정/수정/삭제 엣지       │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 통합 단일 Writer 락 및 Stale Lock 원자적 인계 계약 (P0-1 완결)

### 3.1 단일 로컬 Extension Host 범위 한정
- 본 계약의 대상 범위는 **"단일 로컬 머신의 동일 워크스페이스"**로 명시적으로 한정합니다.

### 3.2 원자적 최초 획득 및 직렬화된 Stale 회수 (Two-Phase Lock Takeover)
확인과 삭제 사이의 TOCTOU 경쟁 및 타 세션 락 오삭제를 차단하기 위해 **"회수 전용 배타 락(`takeover.lock`)"**을 통한 직렬화를 확립합니다:

```
[최초 Writer 시도: openSync('.active_writer.lock', 'wx')]
     │
  (성공) ──> [Primary Writer 획득 완료]
     │
  (EEXIST) ──> [Stale 회수 시도: openSync('.takeover.lock', 'wx')]
                     │
                  (실패: EEXIST) ──> [다른 Host가 이미 회수 중: 즉시 Read-Only 진입]
                     │
                  (성공: 배타적 회수 권한 단독 획득)
                     │
                     ├─ 1. 기존 락 파일 읽기 (oldSessionId, oldPid 확인)
                     ├─ 2. process.kill(oldPid, 0) === ESRCH 확인 (프로세스 완전 사망 단언)
                     │     (살아있다면 즉시 takeover.lock 삭제 후 Read-Only 복귀)
                     ├─ 3. 새 락 데이터 작성 후 fs.renameSync('.takeover.lock', '.active_writer.lock')
                     │     (단독 회수자이므로 원자적 덮어쓰기 완료)
                     ▼
              [Primary Writer 안전 승격]
```

1. **단독 회수권 획득:** `fs.openSync('.takeover.lock', 'wx')` 성공 Host만 회수에 진입하며, 실패한 Host는 즉시 읽기 전용으로 차단되어 회수자 간의 경쟁이 불가능합니다.
2. **PID 부재 필수 검증:** `process.kill(oldPid, 0)`이 `ESRCH` (완전 사망)인 경우에만 인계를 진행합니다. 살아있는 프로세스의 락은 절대 임의 회수하지 않습니다.
3. **`takeover.lock` 자체 크래시 방어:** 회수 도중 Host가 비정상 종료된 경우, 락 내부의 PID가 `ESRCH`인 경우에만 다음 회수자가 unlink 후 재시도할 수 있습니다.
4. **락 파일 빈 파일(Zero-byte) 크래시 방어:** 락 생성 직후 크래시로 파일 내용이 빈 경우, 파일 생성 시각(`ctime`)이 10초를 초과하고 워크스페이스 내 다른 활성 Host가 없을 때만 안전하게 unlink합니다.

## 4. Re-Bootstrap 원자적 교체 및 플랫폼별 보장 범위 (P0-2, P1-3 완결)

### 4.1 Re-Bootstrap 원자적 교체 (Atomic Replace Phase)
1. **임시 파일 생성:** 대상과 동일한 파일시스템(`synapse_data/project_state.json.tmp`)에 완전한 수집 결과를 기록.
2. **내구성 및 유효성 검증:** 파일 FD `fsync` 후 JSON 파싱 및 필수 토폴로지 유효성 검사 수행.
3. **원자적 교체:** 검증 통과 시 `fs.renameSync('project_state.json.tmp', 'project_state.json')`으로 단 1회의 원자적 rename 수행. 실패 시 기존 SSoT 100% 보존.
4. **플랫폼별 보장 범위:**
   - **POSIX (Linux / macOS):** 파일 FD fsync + 부모 디렉터리 fsync를 모두 수행하여 완전한 크래시 내구성 보장.
   - **Windows (`win32`):** OS `MoveFileEx` 기반의 원자적 파일 교체(Atomic Visibility)만 보장하며, 디렉터리 엔트리 내구성은 지원 가능한 파일 수준 내구성으로 한정함을 명시.

### 4.2 분석 파이프라인의 읽기 일관성 (Read Phase)
- 분석기는 분석 시작 시 `fs.readFileSync('synapse_data/project_state.json')`를 통해 **파일 전체를 메모리로 한 번에 읽어 독립 객체(Working Copy)로 완전히 파싱한 후 분석을 시작**합니다.
- POSIX 환경에서는 이미 열린 파일 디스크립터/inode가 유지되므로 분석 도중 Re-Bootstrap이 발생해도 영향이 없으며, 인메모리 객체는 디스크 교체와 완전히 독립적입니다.

### 4.3 Re-Bootstrap 이후 기존 오버레이의 로드·병합 유효성 검증 (P0-2 완결)
SSoT가 Re-Bootstrap으로 교체된 후, 기존 오버레이 파일이 로드될 때의 데이터 처리 정책을 확정합니다:
1. **오버레이 로드 시 참조 무결성 필터링 (Graceful Filtering on Load):**
   - Canvas 로더는 `user_graph.json`과 `layout.json`을 읽어 현재 교체된 SSoT와 대조합니다.
   - SSoT에서 사라진 노드/엣지에 대한 `modifiedNodes`, `modifiedEdges` 항목은 **캔버스 렌더링 시 자동으로 표시에서 제외(Ignore & Filter)**합니다.
   - 고아 Custom Edge(끝점이 사라진 엣지) 역시 렌더링에서 자동 제외합니다.
2. **비파괴 데이터 보존 원칙 (No Auto-Deletion on Load):**
   - 로드 시 유효하지 않은 항목이 발견되더라도, **사용자 오버레이 파일 디스크 원본에서 해당 데이터를 자동으로 영구 삭제하지 않습니다.**
   - 오버레이 파일의 자동 정규화는 오직 사용자가 캔버스에서 명시적으로 새로운 편집을 수행하여 "저장"할 때만 수행됩니다. 이를 통해 일시적인 브랜치 전환이나 롤백 시 사용자의 기존 편집 데이터가 유실되는 사고를 원천 방지합니다.

## 5. `user_graph.json` 완전 스키마 및 Tombstone 정규화 계약 (P0-3, P1-1, P1-2 완결)

### 5.1 스키마 정의 및 엄격한 식별자 규칙 (P1-2 완결)
```typescript
export interface NodeMetadataPatch {
    label?: string;
    description?: string;
    customProperties?: Record<string, string | number | boolean>; // 원시 타입만 허용
}

export interface EdgeMetadataPatch {
    label?: string;
    weight?: number;
    status?: 'proposed' | 'confirmed';
}

export interface CustomNode {
    id: string; // 엄격한 RFC 4122 UUID v4: ^user::[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
    label: string;
    data?: any;
}

export interface CustomEdge {
    id: string; // 엄격한 RFC 4122 UUID v4
    from: string;
    to: string;
    type?: string;
    label?: string;
}

export interface UserGraphData {
    revision: number;                                  // 웹뷰-Host 간 OCC 동시성 제어 정수 (아래 §5.2)
    customNodes: Record<string, CustomNode>;           // key === CustomNode.id
    modifiedNodes: Record<string, NodeMetadataPatch>;  // SSoT 노드 메타데이터 패치
    deletedNodeIds: string[];                          // 노드 Tombstone (SSoT 및 Custom Node 통합)
    
    customEdges: CustomEdge[];                         // Custom Edge 목록 (from !== to)
    modifiedEdges: Record<string, EdgeMetadataPatch>;  // SSoT 엣지 메타데이터 패치 (id/from/to 수정 금지)
    deletedEdgeIds: string[];                          // 엣지 Tombstone
}
```

### 5.2 Revision 및 OCC의 역할 정의 (P1-1 완결)
- **Primary Host 내부의 직렬 큐가 물리적 동시 저장을 차단하지만, `revision`은 웹뷰(클라이언트)와 Host 간의 비동기 상태 역전(Stale Overwrite)을 방지하는 필수 안전장치**입니다.
- 웹뷰가 저장 요청 시 자신이 마지막으로 수신한 `expectedRevision`을 전달하며, Host 메모리의 `currentRevision`과 일치할 때만 저장을 허용하고 `revision + 1`을 기록합니다. 불일치 시 저장을 거부하고 최신 상태를 반환하여 Snap-back을 차단합니다.

### 5.3 Tombstone 정규화 및 Custom Node/Edge 충돌 규칙 (P0-3 완결)
1. **Custom Node의 삭제 모델:**
   - 삭제된 Custom Node는 `customNodes` 딕셔너리에서 제거함과 동시에 **`deletedNodeIds` Tombstone에 등록**하여 활성 노드로 취급되지 않도록 합니다.
2. **Custom Edge의 삭제 모델:**
   - `deletedEdgeIds`에 등록된 Custom Edge는 `customEdges` 배열에 남아있더라도 활성 엣지로 취급되지 않으며, 저장 정규화 단계에서 `customEdges` 배열에서 자동 제거됩니다.
3. **양방향 Tombstone 우선순위:**
   - 동일 Node ID가 `deletedNodeIds`와 `modifiedNodes`에 공존 시: `modifiedNodes[id]` 자동 제거.
   - 동일 Edge ID가 `deletedEdgeIds`와 `modifiedEdges`에 공존 시: `modifiedEdges[id]` 자동 제거.
4. **Custom Edge 끝점 유효성 및 Self-loop 거부:**
   - `customEdges`의 `from`과 `to`는 반드시 SSoT 노드이거나 활성 Custom Node여야 하며, **`deletedNodeIds`에 포함된 노드를 참조하거나 Self-loop(`from === to`)인 경우 저장을 즉시 거부**합니다.
5. **Tombstone 중복 정규화:** `deletedNodeIds` 및 `deletedEdgeIds` 내의 중복 ID는 저장 시 Set을 통해 고유 배열로 자동 정규화합니다.
