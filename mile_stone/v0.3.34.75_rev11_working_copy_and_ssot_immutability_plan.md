## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 완전한 일소
과거의 복잡성은 "과거 SSoT를 이력으로 보관하고 롤백·교체하겠다"는 미련에서 출발했습니다.  
SYNAPSE는 소스 코드 형상 관리 도구가 아니며, **"현재 프로젝트 소스 트리의 아키텍처를 시각화하고 진단하는 분석 엔진"**입니다.  
프로젝트 코드가 바뀌어 재수집(Re-Bootstrap)이 발생하면, 이전 SSoT의 세대 번호를 따질 필요 없이 **새로운 단일 `project_state.json`이 유일한 기준 원본**이 됩니다.

### 1.2 단순화된 3대 불변식
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **Bootstrap 소유 교체 가능 SSoT (`project_state.json`)**: 수집기(Bootstrap)만 작성하며, UI와 분석기는 절대 직접 수정하지 않는 읽기 전용 기준 원본 (Bootstrap-owned replaceable SSoT).
2. **분석별 독립 Working Copy**: 분석 파이프라인(전체 클러스터 분석, 선택 그룹 분석 등)은 디스크 원본에서 직접 파싱된 독립 메모리 객체에서 실행되며, 종료 시 즉시 폐기.
3. **2대 오버레이 분리**: 사용자의 시각적 조작은 `layout.json`(좌표/뷰포트)에, 사용자 그래프 편집은 `user_graph.json`(노드/엣지 추가·수정·삭제)에만 영속화.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① project_state.json           │ ② Disposable Working Copy             │
│    [SSoT: Bootstrap-Owned]     │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - 노드, 엣지, 클러스터      │    - 분석 A/B 간 객체 공유 0건        │
│    - UI/분석기 직접 수정 금지  │    - 분석 종료 시 즉시 GC 폐기        │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가/수정/삭제 노드       │
│    - 뷰포트(zoom, offset)      │    - 사용자 확정/수정/삭제 엣지       │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 통합 단일 Writer 락: 디렉터리 배타 락 및 완전한 Read-Only 격리 규약 (P0-1 완결)

### 3.1 단일 로컬 파일시스템 범위 한정
- 본 계약의 대상 범위는 **"단일 로컬 머신의 표준 로컬 파일시스템(ext4, xfs, APFS, NTFS 등)에 마운트된 동일 워크스페이스"**로 명시적으로 한정합니다.
- 네트워크 파일시스템(NFS, SMB 등)이나 특수 분산 마운트는 SYNAPSE의 비목표이며, `mkdir`의 원자적 배타성을 일반화하지 않습니다.

### 3.2 원자적 배타 획득 및 무조건적 Read-Only Fallback (Zero-Split-Brain Policy)
살아있는 Primary Host가 존재하는 상태에서 다른 창이 락을 강제 삭제하여 발생하는 Split-Brain(다중 Writer 공존)을 아키텍처 수준에서 원천 차단하기 위해, **"소유권 증명 불가 시 쓰기 전면 불허"** 원칙을 확립합니다:

1. **원자적 배타 디렉터리 생성 (O_EXCL Equivalent):**
   - Extension Host 활성화 시 `fs.mkdirSync('synapse_data/.writer_lock_dir')` 호출로 배타적 디렉터리 생성을 시도합니다.
   - 지원되는 로컬 파일시스템에서 `mkdir`은 이미 디렉터리가 존재할 경우 `EEXIST`를 반환하는 완벽한 원자적 배타 연산입니다.
2. **최초 락 생성 직후 실패 처리 (Fail-Safe on Init):**
   - `mkdirSync`가 성공한 직후, 내부에 `{ hostSessionId: UUID, pid: process.pid, createdAt: Date.now() }`를 담은 `owner.token`을 기록합니다.
   - **토큰 기록 중 I/O 에러 또는 크래시 발생 시:** Host는 절대로 Writer 권한을 활성화하지 않고 즉시 비활성화/실패 상태로 전환합니다. 토큰이 없는 미완성 디렉터리는 자동 삭제하지 않고 방치하여 다른 Host가 오인 획득하지 못하도록 보호합니다.
   - 정상적으로 토큰 기록까지 완료된 경우에만 **Primary Writer** 권한을 정식 부여받습니다.
3. **충돌 시 완전한 Read-Only Fallback (`EEXIST`):**
   - 이미 `.writer_lock_dir`이 존재하면, **어떠한 자동 회수, 프로세스 생존 검사, 파일 삭제, 백그라운드 덮어쓰기도 일체 시도하지 않습니다.**
   - 해당 Host는 즉시 **읽기 전용 모드(Read-Only Session)**로 진입하며, 모든 저장 IPC 요청을 진입점에서 즉시 거부(`REJECTED_SECONDARY_HOST_READ_ONLY`)합니다.
   - `EEXIST` 이외의 파일시스템 에러(권한 부족, I/O 에러 등) 발생 시 조용히 넘기지 않고 치명적 락 획득 실패 에러로 로깅합니다.
4. **UI 강제 삭제 금지 및 Split-Brain 차단 (No UI Force-Delete):**
   - **Secondary Host의 UI 웹뷰에 락을 임의로 삭제하는 버튼이나 명령어를 일체 제공하지 않습니다.** (UI 버튼 클릭 시 실행 중인 Primary Host의 소유권과 충돌하여 발생하는 Split-Brain 원천 차단).
   - UI에는 오직 객관적 사실 알림만 표시합니다:
     > **"[안내] 다른 Extension Host의 잠금이 존재하거나 이전 세션의 잠금이 남아 있습니다. 현재 세션은 읽기 전용 모드로 동작합니다."**
5. **정상 종료 시 해제:**
   - Host 정상 비활성화(`deactivate`) 시, 디렉터리 내부의 `owner.token`을 읽어 `hostSessionId`가 자신의 세션 ID와 엄격 일치할 때만 `fs.rmSync('synapse_data/.writer_lock_dir', { recursive: true })`로 안전하게 락을 해제합니다.
6. **비정상 종료 후 외부 수동 복구 (External Manual Recovery):**
   - 이전 Host가 비정상 크래시되어 락 디렉터리가 영구 방치된 경우의 복구는 **"모든 관련 VS Code 프로세스를 완전히 종료한 후, 사용자가 외부 터미널/파일 탐색기에서 `synapse_data/.writer_lock_dir`을 명시적으로 직접 삭제하고 재시작"**하는 수동 절차로만 규정합니다.
   - **효과:** 계약을 준수하는 Extension Host 간에는 자동 락 회수 및 Secondary Host의 강제 삭제 경로가 존재하지 않으므로, 정상적인 락 프로토콜 범위에서 다중 Writer 공존을 방지합니다. 외부에서 실행 중인 락을 임의 삭제하거나 파일시스템의 배타성 보장이 깨지는 경우까지 수학적으로 배제하는 것은 아닙니다.

## 4. Re-Bootstrap 원자적 교체 및 오버레이 유효성 계약 (P0-2, P1-3 완결)

### 4.1 Re-Bootstrap 원자적 교체 및 플랫폼별 보장 범위 (P1-3 완결)
1. **임시 파일 생성:** 대상과 동일한 파일시스템(`synapse_data/project_state.json.tmp`)에 완전한 수집 결과를 기록.
2. **내구성 및 유효성 검증:** 파일 FD `fsync` 후 JSON 파싱 및 필수 토폴로지 유효성 검사 수행.
3. **원자적 교체:** 검증 통과 시 `fs.renameSync('project_state.json.tmp', 'project_state.json')`으로 원자적 rename 수행. 실패 시 기존 SSoT 100% 보존.
4. **플랫폼별 보장 및 비보장 범위의 엄격한 분리:**
   - **POSIX (Linux / macOS):** 동일 파일시스템 내에서 `renameSync`는 원자적 가시성 교체를 보장하며, 지원되는 파일시스템 및 정상 마운트 환경에서 파일 FD fsync 및 부모 디렉터리 fsync를 통해 디렉터리 엔트리 내구성을 확보합니다. 단, 파일시스템 구현 한계나 하드웨어 쓰기 캐시 미지원 환경까지 무조건적인 크래시 내구성을 일반화하지는 않습니다.
   - **Windows (`win32`):** OS `MoveFileEx` 기반의 동일 파일시스템 내 원자적 파일 교체(Atomic Visibility)만 보장하며, POSIX의 디렉터리 fsync나 inode 유지 동작은 보장되지 않으므로 디렉터리 엔트리 내구성은 지원 가능한 파일 수준 내구성으로 한정함을 명시합니다.
5. **분석 읽기 일관성:** 분석기는 파일 전체를 읽고 완전히 파싱한 후에만 Working Copy를 생성하여 분석을 시작하므로, 파싱 완료 후의 디스크 파일 교체와 완전히 독립적입니다.

### 4.2 오버레이의 로드 필터링 및 컬렉션 단위 저장 정규화 경계 (P0-2 완결)
1. **로드 시 비파괴적 필터링 (Graceful Filtering on Load):**
   - 캔버스 로드 시 현재 SSoT(`project_state.json`) 및 활성 Custom Node와 대조하여 다음 항목을 **화면 표시에서만 자동 제외(Ignore & Filter)**합니다:
     - SSoT에서 사라진 노드에 대한 `modifiedNodes` 및 사라진 엣지에 대한 `modifiedEdges`.
     - **Custom Node Layout 좌표 필터링:** `layout.json`의 좌표 중, 현재 활성 상태인 SSoT 노드 및 활성 `customNodes`에 속하지 않거나, Tombstone(`deletedNodeIds`)에 포함된 노드의 좌표는 렌더링에서 완전히 제외합니다.
     - 사라진 클러스터 접힘 상태 및 양 끝점 중 하나라도 결손된 고아 Custom Edge 화면 표시 제외.
   - **디스크 원본 보존:** 로드 시점에는 디스크 상의 `user_graph.json`이나 `layout.json`을 절대 자동 삭제하거나 수정하지 않습니다 (일시적 브랜치 전환 시 사용자 편집 데이터 영구 보존).
2. **컬렉션 단위 저장 정규화 경계 (Collection-Level Normalization Scope):**
   - 사용자가 캔버스에서 편집 후 저장을 수행할 때, **"사용자가 실제로 변경을 가한 대상 컬렉션"에 한해서만 정규화를 적용**합니다:
     - `layout.json` 저장 시: 활성 노드(SSoT 노드 + 활성 Custom 노드)의 좌표 컬렉션만 정규화하여 저장.
     - `user_graph.json` 노드 수정 시: `modifiedNodes` 컬렉션 중 현재 유효한 SSoT 노드 패치만 정규화하여 저장.
     - 수정한 적 없는 다른 컬렉션의 오래된 블록은 임의로 파괴하지 않고 디스크 원본 상태를 보존합니다.

## 5. `user_graph.json` 완전 스키마 및 Tombstone 정규화 계약 (P0-3, P1-1 완결)

### 5.1 스키마 정의 및 엄격한 타입·식별자 검증 (P0-3 완결)
```typescript
export interface NodeMetadataPatch {
    label?: string;
    description?: string;
    customProperties?: Record<string, string | number | boolean>; // 원시 타입만 허용 (NaN/Infinity 불허)
}

export interface EdgeMetadataPatch {
    label?: string;
    weight?: number;                                              // 유한한 숫자 (Number.isFinite 필수)
    status?: 'proposed' | 'confirmed';
}

export interface CustomNode {
    id: string; // 반드시 ^user::[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
    label: string;
    customProperties?: Record<string, string | number | boolean>; // data?: any 전면 배제 및 원시 타입 강제
}

export interface CustomEdge {
    id: string; // 반드시 ^user::[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
    from: string;
    to: string;
    type?: string;
    label?: string;
}

export interface UserGraphData {
    revision: number;                                  // 웹뷰-Host 간 OCC 동시성 제어 정수
    customNodes: Record<string, CustomNode>;           // key === CustomNode.id
    modifiedNodes: Record<string, NodeMetadataPatch>;  // SSoT 노드 메타데이터 패치
    deletedNodeIds: string[];                          // 노드 Tombstone (SSoT 및 Custom Node 통합)
    
    customEdges: CustomEdge[];                         // Custom Edge 목록 (from !== to)
    modifiedEdges: Record<string, EdgeMetadataPatch>;  // SSoT 엣지 메타데이터 패치 (id/from/to 수정 금지)
    deletedEdgeIds: string[];                          // 엣지 Tombstone (SSoT 및 Custom Edge 통합)
}
```

### 5.2 Layout 및 UserGraph Revision 스키마 및 OCC 생명주기 (P1-1 완결)
`layout.json` 역시 단독 저장 파일이므로 독립적인 `revision` 스키마를 보유하며, 두 오버레이 파일은 각각 독립적인 OCC 생명주기를 가집니다:

```typescript
export interface LayoutData {
    revision: number;                                  // Layout 전용 OCC revision
    positions: Record<string, { x: number; y: number }>;
    view: { zoom: number; offset: { x: number; y: number } };
    clusters: Record<string, { collapsed: boolean }>;
}
```

1. **Host 시작 시 로드:** Host 활성화 시 `layout.json`과 `user_graph.json` 디스크 파일에 기록된 `revision`을 각각 읽어 메모리의 `currentLayoutRevision`, `currentUserGraphRevision` 초기값으로 로드합니다 (파일 부재 시 0).
2. **저장 및 원자적 갱신 순서:**
   - 웹뷰가 저장 요청 시 전달한 `expectedRevision`이 메모리의 `currentRevision`과 일치할 때만 저장을 승인합니다.
   - 디스크 임시 파일에 `newRevision = currentRevision + 1`을 기록하고 rename을 수행합니다.
   - **디스크 rename이 최종 성공한 직후에만** Host 메모리의 `currentRevision`을 `newRevision`으로 증가시킵니다. 디스크 저장 실패 시 메모리 `currentRevision`은 절대 증가하지 않고 유지됩니다.
3. **웹뷰 응답 유실 및 재동기화 (Resynchronization Policy):**
   - Host의 디스크 저장은 성공했으나 웹뷰로의 IPC 응답이 유실되어 웹뷰가 다음 요청에서 구 `expectedRevision`을 전달한 경우, Host는 OCC 불일치를 감지하고 저장을 거부합니다.
   - 이때 Host는 디스크에 기록된 최신 오버레이 상태와 최신 `currentRevision`을 웹뷰로 재전송(Force Resync)하여 웹뷰 상태를 안전하게 복원합니다.

### 5.3 Custom Node 삭제 시 연쇄 Edge Tombstone 및 ID 검증 분리 (P0-3 완결)
1. **ID 유형별 검증 기준의 엄격한 분리:**
   - **Custom Node/Edge ID:** 엄격한 RFC 4122 UUID v4 정규식(`^user::[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`)을 검사하며, `customNodes`의 Key와 객체 내부의 `id`가 엄격 일치해야 합니다.
   - **SSoT Node/Edge ID:** 실제 활성 `project_state.json`에 존재하는 ID 집합과 대조합니다.
   - **Node Tombstone (`deletedNodeIds`):** 항목이 SSoT Node ID이거나 유효한 Custom Node ID 형식이어야 합니다.
   - **Edge Tombstone (`deletedEdgeIds`):** 항목이 SSoT Edge ID이거나 유효한 Custom Edge ID 형식이어야 합니다.
   - SSoT ID와 동일한 ID의 Custom Node/Edge 생성은 저장을 즉시 거부합니다.
2. **Custom Node 삭제와 연결 Custom Edge의 원자적 연쇄 처리 (Cascading Tombstone):**
   - 사용자가 Custom Node를 삭제할 경우, **해당 노드를 끝점(`from` 또는 `to`)으로 참조하는 모든 Custom Edge도 동일한 저장 트랜잭션 내에서 `customEdges`에서 제거되고 `deletedEdgeIds` Tombstone에 자동 등록**됩니다.
   - 저장 실패 시 메모리 상태는 직전 유효 상태로 롤백되어 메모리-디스크 간 불일치를 차단합니다.
3. **런타임 원시 타입 및 유한 숫자 검증:**
   - `customProperties`의 모든 값은 `string`, `boolean`, 또는 유한한 `number`(`typeof v === 'number' && Number.isFinite(v)`)여야 하며 `NaN`, `Infinity`는 저장을 거부합니다.
   - `modifiedEdges`의 `weight` 역시 `Number.isFinite(weight) && weight >= 0` 검사를 강제합니다.
4. **양방향 Tombstone 우선순위:**
   - 동일 Node ID가 `deletedNodeIds`와 `modifiedNodes`에 공존 시: `modifiedNodes[id]` 자동 제거.
   - 동일 Edge ID가 `deletedEdgeIds`와 `modifiedEdges`에 공존 시: `modifiedEdges[id]` 자동 제거.
5. **Custom Edge 끝점 유효성 및 Self-loop 거부:**
   - `customEdges`의 `from`과 `to`는 반드시 SSoT 노드이거나 활성 Custom Node여야 하며, `deletedNodeIds`에 포함된 노드를 참조하거나 Self-loop(`from === to`)인 경우 저장을 즉시 거부합니다.
