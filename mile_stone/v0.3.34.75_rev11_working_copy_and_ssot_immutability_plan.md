## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 완전한 일소
과거의 복잡성은 "과거 SSoT를 이력으로 보관하고 롤백·교체하겠다"는 미련에서 출발했습니다.  
SYNAPSE는 소스 코드 형상 관리 도구가 아니며, **"현재 프로젝트 소스 트리의 아키텍처를 시각화하고 진단하는 분석 엔진"**입니다.  
프로젝트 코드가 바뀌어 재수집(Re-Bootstrap)이 발생하면, 이전 SSoT의 세대 번호를 따질 필요 없이 **새로운 단일 `project_state.json`이 유일한 기준 원본**이 됩니다.

### 1.2 단순화된 3대 불변식
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **단일 SSoT (`project_state.json`)**: 수집기(Bootstrap)만 작성하며, UI는 절대 쓰지 않는 읽기 전용 불변 원본.
2. **분석별 독립 Working Copy**: 분석 파이프라인(전체 클러스터 분석, 선택 그룹 분석 등)은 디스크 원본에서 직접 파싱된 독립 메모리 객체에서 실행되며, 종료 시 즉시 폐기.
3. **2대 오버레이 분리**: 사용자의 시각적 조작은 `layout.json`(좌표/뷰포트)에, 사용자 그래프 편집은 `user_graph.json`(노드/엣지 추가·수정·삭제)에만 영속화.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① project_state.json           │ ② Disposable Working Copy             │
│    [Immutable SSoT]            │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - 노드, 엣지, 클러스터      │    - 분석 A/B 간 객체 공유 0건        │
│    - 분석 중 읽기 전용 (RO)    │    - 분석 종료 시 즉시 GC 폐기        │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가/수정/삭제 노드       │
│    - 뷰포트(zoom, offset)      │    - 사용자 확정/수정/삭제 엣지       │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 통합 단일 Writer 락 (Bootstrap 및 오버레이 직렬화)

동일 워크스페이스에 대한 다중 창 쓰기 및 Bootstrap과 오버레이 저장 간의 파일 충돌을 원천 차단하기 위해 **통합 단일 Writer 락**을 확립합니다:

1. **단일 로컬 Extension Host 범위 한정:** 대상 워크스페이스는 단일 머신의 로컬 파일시스템으로 한정합니다.
2. **원자적 Writer 락 획득 (`synapse_data/.active_writer.lock`):**
   - Host는 활성화 시 `fs.openSync('.active_writer.lock', 'wx')`로 독점 락 생성을 시도합니다.
   - 성공 시 Primary Writer 권한을 획득하며, 실패 시 즉시 **읽기 전용 모드(Read-Only)**로 전환하여 모든 저장 IPC 요청을 진입점에서 차단합니다.
3. **Bootstrap과 오버레이 저장의 직렬화:**
   - **Bootstrap(재수집)과 오버레이 저장(`layout.json`, `user_graph.json`)은 Primary Host 내부의 동일한 직렬 큐(Serial Queue)를 통해 순차 실행**됩니다.
   - 따라서 Bootstrap이 원본을 교체하는 동안 오버레이 저장이 동시에 끼어드는 경합이 발생하지 않습니다.
4. **Stale Lock 회수 규약:**
   - 기존 락의 소유자 PID가 `process.kill(pid, 0) === ESRCH` (프로세스 완전 사망)일 때만 Stale로 확정하여 안전하게 해제 후 재획득합니다. (살아있는 프로세스의 락은 절대 임의 회수하지 않음).

## 4. Re-Bootstrap 원자적 교체 및 분석 읽기 일관성 계약

Re-Bootstrap 시 파일 교체와 분석 파이프라인의 읽기 일관성을 완벽히 보장합니다:

1. **분석 파이프라인의 독립 읽기 (Read Phase):**
   - 분석기는 분석 시작 시 `fs.readFileSync('synapse_data/project_state.json')`를 통해 **파일 전체를 메모리로 한 번에 읽어 독립 객체(Working Copy)로 완전히 파싱한 후 분석을 시작**합니다.
   - 분석 도중 디스크 파일이 교체되더라도, 이미 파싱된 인메모리 Working Copy는 디스크 변경에 전혀 영향을 받지 않습니다.
   - 출처 추적이 필요할 경우 파싱 당시의 SHA-256 해시를 리포트 메타데이터에 기록합니다.
2. **Re-Bootstrap의 원자적 교체 (Replace Phase):**
   - Bootstrap은 결과를 임시 파일 `project_state.json.tmp`에 기록하고 `fsync`를 수행합니다.
   - JSON 파싱 및 필수 구조 유효성 검증을 완료한 후, `fs.renameSync('project_state.json.tmp', 'project_state.json')`으로 **단 1회의 원자적 rename**을 수행합니다.
   - POSIX 환경에서는 부모 디렉터리 `fsync`를 수행하여 내구성을 보장합니다.

## 5. `user_graph.json` 최소 참조 무결성 및 저장 계약

세대 번호(`generationId`)를 완전히 제거하고, 순수하게 현재 활성 SSoT와의 참조 무결성만 검증합니다:

```typescript
export interface UserGraphData {
    revision: number;                                  // OCC 동시성 제어용 단조 증가 정수
    customNodes: Record<string, CustomNode>;           // key === CustomNode.id (^user::[0-9a-f-]{36}$)
    modifiedNodes: Record<string, NodeMetadataPatch>;  // SSoT 노드 메타데이터 패치
    deletedNodeIds: string[];                          // 노드 Tombstone (SSoT 및 Custom Node 통합)
    
    customEdges: CustomEdge[];                         // Custom Edge 목록 (from !== to)
    modifiedEdges: Record<string, EdgeMetadataPatch>;  // SSoT 엣지 메타데이터 패치 (id/from/to 수정 금지)
    deletedEdgeIds: string[];                          // 엣지 Tombstone
}
```

### 5.1 저장 시 4대 참조 무결성 검증 (Validation on Save)
1. **수정 대상 유효성 검증:** `modifiedNodes`와 `modifiedEdges`의 모든 키는 현재 `project_state.json`에 실제로 존재하는 ID여야 합니다.
2. **Custom Edge 양 끝점 무결성 (Dangling Edge 차단):**
   - `customEdges`의 `from`과 `to`는 반드시 유효 노드여야 하며, **Tombstone(`deletedNodeIds`)에 포함된 노드를 참조하는 엣지는 저장을 거부**합니다:
     $$\text{endpoint} \in (\text{SSoT.nodes} \cup \text{customNodes}) \land \text{endpoint} \notin \text{deletedNodeIds}$$
   - Self-loop(`from === to`)은 허용되지 않습니다.
3. **Tombstone 충돌 정규화:** 동일 ID가 수정과 Tombstone에 공존 시 Tombstone만 남기고 수정본은 자동 삭제 정규화합니다.
4. **원자적 저장:** 임시 파일 작성 $\rightarrow$ `fsync` $\rightarrow$ `renameSync` $\rightarrow$ 디렉터리 `fsync` 시퀀스 준수.
