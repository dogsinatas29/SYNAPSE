## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 근본 원인 및 완전한 제거
과거 rev1~10 보완 문서는 **"공식 SSoT(`project_state.json`)를 디스크 상에서 인플레이스로 수정하고 크래시 시 이를 복구해야 한다"**는 잘못된 전제에서 출발했습니다.  
이로 인해 파일 시스템의 원자성 한계를 메우기 위해 2단계 저널, 복구 락, Stale Lock 세대 판독, 14개 분기 복구 매트릭스라는 극단적인 복잡성에 빠졌습니다.

### 1.2 "최고의 복구는 복구할 필요 자체를 만들지 않는 것"
사용자의 명확한 KISS 원칙에 따라, 문제를 아키텍처 수준에서 원천 차단합니다:
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **SSoT 영구 불변**: 수집기(Bootstrap)가 생성한 세대별 SSoT는 읽기 전용 불변 원본으로 박제합니다.
2. **Working Copy 격리 분석**: 분석·검증 파이프라인은 원본에서 독립적으로 파싱된 일회용 인메모리 객체(Working Copy)에서 실행되며, 실패 시 해당 복사본을 즉시 폐기하고 원본에서 다시 로드합니다. 롤백 저널과 복구 매트릭스는 완전히 불필요합니다.
3. **데이터 소유권 분리**: 캔버스 프레젠테이션과 사용자 편집 데이터는 SSoT 원본에서 완전히 분리된 전용 오버레이 파일(`layout.json`, `user_graph.json`)로 영속화합니다.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① generations/project_state.vN │ ② Disposable Working Copy             │
│    [Immutable SSoT]            │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - 노드, 엣지, 클러스터      │    - 실패 시 즉시 폐기 (롤백 불필요)  │
│    - 분석 중 읽기 전용 (RO)    │    - 분석 산출물은 리포트로 저장      │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가/수정/삭제 노드       │
│    - 뷰포트(zoom, offset)      │    - 사용자 확정/수정/삭제 엣지       │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 원자적 단일 Writer 락 및 직렬화된 Stale Lock 인계 계약 (P0-1 완결)

### 3.1 단일 로컬 Extension Host 범위 한정
- 본 계약의 대상 범위는 **"단일 로컬 머신의 동일 워크스페이스"**로 명시적으로 한정합니다.

### 3.2 직렬화된 Stale Lock 회수 프로토콜 (Two-Phase Lock Takeover)
두 Host가 동시에 Stale 판단 후 락을 맞교체하는 TOCTOU 경쟁을 방지하기 위해, **"회수 전용 배타 락(`takeover.lock`)"**을 통한 직렬화를 도입합니다:

```
[최초 Writer 시도: openSync('.active_writer.lock', 'wx')]
     │
  (성공) ──> [Primary Writer 획득 완료]
     │
  (EEXIST) ──> [Stale 회수 시도: openSync('.takeover.lock', 'wx')]
                     │
                  (실패) ──> [다른 Host가 회수 중: 즉시 Read-Only Fallback]
                     │
                  (성공: 배타적 회수 권한 단독 획득)
                     │
                     ├─ 1. 기존 락 파일 읽기 (기존 Session ID, PID 확인)
                     ├─ 2. process.kill(pid, 0) === ESRCH 확인 (완전 부재 단언)
                     ├─ 3. 신규 락 데이터 작성 후 fs.renameSync('.takeover.lock', '.active_writer.lock')
                     │     (단독 회수자이므로 경쟁 덮어쓰기 물리적 0건)
                     ▼
              [Primary Writer 안전 승격]
```

1. **단독 회수 권한 획득:** Stale 의심 시 임의로 락을 덮어쓰지 않고, 반드시 `fs.openSync('synapse_data/.takeover.lock', 'wx')`를 먼저 성공한 단 1개의 Host만 회수 절차에 진입합니다.
2. **동시 회수자 차단:** `takeover.lock` 생성에 실패한 다른 모든 Host는 즉시 **읽기 전용 모드(Read-Only Session)**로 진입하며 모든 저장 IPC 요청을 진입점에서 차단합니다.
3. **원자적 인계:** 단독 회수 권한을 쥔 Host가 `ESRCH` 검증 후 `fs.renameSync('.takeover.lock', '.active_writer.lock')`을 수행하므로, 제3의 Host가 중간에 끼어들어 락을 덮어쓰는 경쟁이 원천 차단됩니다.

## 4. `user_graph.json` 완전 스키마 및 엄격한 참조 무결성 검증 계약 (P0-4 완결)

### 4.1 스키마 정의 및 수정 필드 안전 제한
```typescript
export interface NodeMetadataPatch {
    label?: string;
    description?: string;
    customProperties?: Record<string, string | number | boolean>; // 원시 타입만 허용
}

export interface EdgeMetadataPatch {
    label?: string;
    weight?: number;
    status?: 'proposed' | 'confirmed';
}

export interface UserGraphData {
    revision: number;
    customNodes: Record<string, CustomNode>;           // ID: user::{uuid}
    modifiedNodes: Record<string, NodeMetadataPatch>;  // SSoT 노드 메타데이터 패치
    deletedNodeIds: string[];                          // 노드 Tombstone
    
    customEdges: CustomEdge[];                         // ID: user::{uuid}
    modifiedEdges: Record<string, EdgeMetadataPatch>;  // SSoT 엣지 메타데이터 패치 (id/from/to 수정 금지)
    deletedEdgeIds: string[];                          // 엣지 Tombstone
}
```

### 4.2 엄격한 참조 무결성 저장 검증 (Validation on Save)
저장 실행 전 Extension Host는 다음 5대 무결성 검증을 필수로 수행하며, 위반 시 저장을 즉시 거부합니다:
1. **`modifiedNodes` 대상 검증:** `modifiedNodes`의 모든 키는 현재 활성 SSoT에 실제로 존재하는 유효한 노드 ID여야 합니다.
2. **`modifiedEdges` 대상 검증:** `modifiedEdges`의 모든 키는 현재 활성 SSoT에 실제로 존재하는 유효한 엣지 ID여야 합니다. (Custom Edge는 `customEdges` 배열에서 직접 관리).
3. **Custom Edge 양 끝점 무결성 검증 (Dangling Edge 차단):**
   - `customEdges`의 `from`과 `to`는 반드시 다음 조건을 만족해야 합니다:
     $$\text{node} \in (\text{SSoT.nodes} \cup \text{customNodes}) \land \text{node} \notin \text{deletedNodeIds}$$
   - 즉, SSoT에 존재하더라도 **Tombstone(`deletedNodeIds`)에 포함된 노드를 참조하는 Custom Edge는 저장을 거부**합니다.
4. **Tombstone 충돌 정규화:** 동일한 ID가 `deletedNodeIds`와 `modifiedNodes`에 동시에 존재하면, `modifiedNodes[id]`를 자동 삭제하고 Tombstone만 영속화합니다.
5. **Revision 무결성:** `Number.isSafeInteger(revision) && revision >= 0` 검사. `MAX_SAFE_INTEGER` 도달 시 저장 거부.
6. **원자적 저장:** 임시 파일 작성 $\rightarrow$ `fsync` $\rightarrow$ 부모 디렉터리 `fsync` (POSIX) $\rightarrow$ `renameSync` $\rightarrow$ 2차 디렉터리 `fsync`.

## 5. 원자적 스냅샷 포인터 기반 Rollback 일관성 보장 (P0-2 완결)

순차 파일 복사로 인한 불일치를 배제하기 위해, **"완성된 스냅샷 디렉터리 + 활성 스냅샷 단일 포인터(`active_snapshot.json`)"** 모델을 공식 채택합니다:

```
synapse_data/
├── snapshots/
│   ├── snap_20261115_1000/           # 스냅샷 A (완성된 불변 디렉터리)
│   │   ├── active_generation.json    # 해당 시점의 활성 SSoT 세대 번호/해시
│   │   ├── user_graph.json           # 해당 시점의 사용자 그래프 데이터
│   │   └── layout.json               # 해당 시점의 레이아웃 좌표/뷰포트
│   └── snap_20261115_1100/           # 스냅샷 B (완성된 불변 디렉터리)
└── active_snapshot.json              # 활성 스냅샷 단일 포인터 (원자적 교체)
```

### 5.1 원자적 롤백 절차
1. **독자의 불변 읽기:** 모든 캔버스 로더는 항상 `active_snapshot.json`이 가리키는 스냅샷 디렉터리에서 세 세트를 읽습니다.
2. **단일 포인터 원자적 교체:**
   - 대상 스냅샷 디렉터리 내 3개 파일의 무결성 검증 완료 후,
   - 임시 포인터 파일 `active_snapshot.json.tmp`를 작성 및 `fsync`하고,
   - `fs.renameSync('active_snapshot.json.tmp', 'active_snapshot.json')` **단 1회의 원자적 rename**으로 활성 스냅샷을 교체합니다.
3. **효과:** SSoT 세대 파일은 일체 덮어쓰지 않으며, 3개 파일을 순차 복사하는 과정이 없으므로 독자는 항상 100% 일관된 스냅샷만 읽게 됩니다.

## 6. 소유 세션 검증 기반 Bootstrap Lock 생명주기 및 분석 경계 (P0-3 완결)

1. **Bootstrap Lock의 배타적 획득:**
   - Bootstrap 실행 시 `fs.openSync('synapse_data/.bootstrap.lock', 'wx')` 성공 시 `{ pid, hostSessionId, startTime }` 기록.
2. **소유 Session ID 검증 기반 해제 (오삭제 방지):**
   - `finally` 블록에서 무조건 `unlink`하지 않고, **현재 락 파일의 `hostSessionId`가 자신의 세션 ID와 일치할 때만 `unlinkSync`를 수행**합니다.
   - 자신이 실행 도중 Stale 처리되어 다른 세션이 락을 인계받았다면, 다른 세션의 락 파일을 절대 삭제하지 않고 안전하게 종료합니다.
3. **분석 시작 경계 및 세대 고정 (Session Pinning):**
   - 분석 시작 시 `.bootstrap.lock`이 존재하면 분석기는 대기하거나 즉시 중단 메시지를 반환합니다.
   - 분석기는 시작 시점에 `active_generation.json`을 검증한 뒤 해당 **불변 세대 파일(`generations/project_state.v{N}.json`) 경로를 분석 세션에 영구 고정(Pinning)**합니다.
   - 분석 실행 도중에 Bootstrap이 완료되어 새 세대(`v{N+1}`)가 활성화되더라도, 이미 실행 중인 분석 세션은 자신이 고정한 불변 `v{N}` 파일만 끝까지 읽으므로 경쟁 조건이 발생하지 않습니다.
