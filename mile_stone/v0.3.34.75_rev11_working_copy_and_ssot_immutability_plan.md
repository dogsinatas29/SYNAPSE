## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 근본 원인 및 완전한 제거
과거 rev1~10 보완 문서는 **"공식 SSoT(`project_state.json`)를 디스크 상에서 인플레이스로 수정하고 크래시 시 이를 복구해야 한다"**는 잘못된 전제에서 출발했습니다.  
이로 인해 파일 시스템의 원자성 한계를 메우기 위해 2단계 저널, 복구 락, Stale Lock 세대 판독, 14개 분기 복구 매트릭스라는 극단적인 복잡성에 빠졌습니다.

### 1.2 "최고의 복구는 복구할 필요 자체를 만들지 않는 것"
사용자의 명확한 KISS 원칙에 따라, 문제를 아키텍처 수준에서 원천 차단합니다:
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **SSoT 영구 불변**: 수집기(Bootstrap)가 생성한 세대별 SSoT는 읽기 전용 불변 원본으로 박제합니다.
2. **Working Copy 격리 분석**: 분석·검증 파이프라인은 원본에서 독립적으로 파싱된 일회용 인메모리 객체(Working Copy)에서 실행되며, 실패 시 해당 복사본을 즉시 폐기하고 원본에서 다시 로드합니다. 롤백 저널과 복구 매트릭스는 완전히 불필요합니다.
3. **데이터 소유권 분리**: 캔버스 프레젠테이션과 사용자 편집 데이터는 SSoT 원본에서 완전히 분리된 전용 오버레이 파일(`layout.json`, `user_graph.json`)로 영속화합니다.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① generations/project_state.vN │ ② Disposable Working Copy             │
│    [Immutable SSoT]            │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - 노드, 엣지, 클러스터      │    - 실패 시 즉시 폐기 (롤백 불필요)  │
│    - 분석 중 읽기 전용 (RO)    │    - 분석 산출물은 리포트로 저장      │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가/수정/삭제 노드       │
│    - 뷰포트(zoom, offset)      │    - 사용자 확정/수정/삭제 엣지       │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 원자적 단일 Writer 획득 및 다중 Host 경쟁 차단 계약 (P0-1 완결)

TOCTOU 경쟁 조건을 원천 차단하기 위해, 단순 파일 비교가 아닌 OS 커널 수준의 **원자적 배타적 파일 생성(`O_CREAT | O_EXCL`)** 기반 독점 Writer 획득 계약을 확립합니다:

### 3.1 원자적 Writer 락 획득 프로토콜
1. **독점 락 파일 생성:**
   - Extension Host는 워크스페이스 활성화 시 `fs.openSync('synapse_data/.active_writer.lock', 'wx')` (`O_CREAT | O_EXCL`) 호출로 락 획득을 시도합니다.
   - 락 파일 내부에는 `{ hostSessionId: UUID, pid: process.pid, createdAt: Date.now() }`를 기록합니다.
2. **독점 락 획득 성공 시 (Primary Writer):**
   - 해당 Host는 정식 Writer 소유권을 부여받고 모든 사용자 저장(`layout.json`, `user_graph.json`)을 직렬 큐를 통해 배타적으로 처리합니다.
3. **독점 락 획득 실패 시 (`EEXIST` - Read-Only Fallback):**
   - 이미 다른 Extension Host가 워크스페이스를 선점하고 있으므로, 해당 Host는 **읽기 전용 모드(Read-Only Session)**로 진입합니다.
   - UI 웹뷰에 "다중 창 실행 감지: 읽기 전용 모드로 실행 중입니다" 알림을 표시하며, **모든 저장 IPC 요청을 진입점에서 즉시 거부(`REJECTED_READ_ONLY_SECONDARY_HOST`)**합니다.
4. **비정상 종료 및 Stale Lock 회수:**
   - 락 파일이 존재할 경우, 기록된 `pid`의 생존 여부를 `process.kill(pid, 0)`으로 확인합니다.
   - 프로세스가 부재(`ESRCH`)하거나 하트비트 타임아웃(30초)을 초과한 경우에만 안전하게 락을 해제하고 소유권을 재획득합니다.

## 4. `user_graph.json` 완전 스키마 및 저장·수정·충돌 처리 계약 (P0-2, P0-4 완결)

### 4.1 스키마 및 허용 필드 제한
```typescript
export interface UserGraphData {
    revision: number;
    customNodes: Record<string, CustomNode>;           // ID: user::{uuid} (SSoT 충돌 차단)
    modifiedNodes: Record<string, NodeMetadataPatch>;  // 허용 필드: label, description, metadata
    deletedNodeIds: string[];                          // 노드 Tombstone
    
    customEdges: CustomEdge[];                         // 허용: id(user::), from, to, type, label
    modifiedEdges: Record<string, EdgeMetadataPatch>;  // 허용 필드: label, weight, status ('confirmed')
    deletedEdgeIds: string[];                          // 엣지 Tombstone
}
```
> ⚠️ **수정 필드 안전 제한:**
> - `modifiedEdges`에서는 `id`, `from`, `to` 등 구조적 토폴로지 핵심 식별자의 수정을 엄격히 금지하며, 오직 메타데이터(`label`, `weight`, `status`)만 허용합니다. 토폴로지 연결 변경은 삭제 후 신규 생성을 강제합니다.

### 4.2 충돌 및 우선순위 규칙 (Precedence Rules)
1. **Tombstone 절대 우선:** 특정 ID가 `deletedNodeIds` 또는 `deletedEdgeIds`에 포함되어 있으면, `modifiedNodes`나 `modifiedEdges`에 수정본이 존재하더라도 **Tombstone을 절대 우선 적용**하여 화면에서 완전히 숨깁니다.
2. **고아 엣지 자동 숨김:** 사용자 커스텀 엣지(`customEdges`)의 `from` 또는 `to` 대상 노드가 SSoT 또는 `deletedNodeIds`에 의해 삭제된 경우, 해당 엣지는 유효하지 않은 것으로 판정하여 캔버스 렌더링에서 자동으로 숨깁니다.

### 4.3 저장 무결성 및 OCC 동시성
- **단일 Writer:** §3에서 락을 획득한 Primary Host 직렬 큐만 단독 저장.
- **OCC 검증:** `expectedRevision === currentRevision` 일치 시에만 `revision + 1`로 저장 허용.
- **원자적 저장:** 임시 파일 `user_graph.json.tmp` 작성 $\rightarrow$ `fsync` $\rightarrow$ 부모 디렉터리 `fsync` (POSIX) $\rightarrow$ `renameSync` $\rightarrow$ 2차 디렉터리 `fsync` 시퀀스를 layout.json과 동일하게 엄격 준수.

## 5. 원자적 스냅샷 포인터 기반 Rollback 일관성 보장 (P0-2, P0-5 완결)

순차 파일 복사로 인한 중간 상태 노출 결함을 원천 제거하기 위해, **"완성된 스냅샷 디렉터리 + 활성 스냅샷 단일 포인터(`active_snapshot.json`)"** 모델을 공식 채택합니다:

```
synapse_data/
├── snapshots/
│   ├── snap_20261115_1000/           # 스냅샷 A 디렉터리 (완성된 세트)
│   │   ├── active_generation.json    # 해당 시점의 활성 SSoT 세대 번호/해시
│   │   ├── user_graph.json           # 해당 시점의 사용자 그래프 데이터
│   │   └── layout.json               # 해당 시점의 레이아웃 좌표/뷰포트
│   └── snap_20261115_1100/           # 스냅샷 B 디렉터리 (완성된 세트)
└── active_snapshot.json              # 활성 스냅샷 단일 포인터 (원자적 교체)
```

### 5.1 원자적 롤백 절차 (Atomic Rollback Protocol)
1. **독자가 읽는 기준:** 모든 캔버스 로더와 소비자는 항상 `active_snapshot.json`이 가리키는 스냅샷 디렉터리에서 세 세트를 읽습니다.
2. **롤백 실행 시:**
   - 대상 스냅샷 디렉터리가 디스크에 완전히 온전하게 존재하는지 검증합니다.
   - 신규 포인터 임시 파일 `active_snapshot.json.tmp`에 대상 스냅샷 경로를 기록하고 `fsync`를 수행합니다.
   - `fs.renameSync('active_snapshot.json.tmp', 'active_snapshot.json')` **단 1회의 원자적 파일 교체**로 활성 스냅샷을 전환합니다.
3. **효과:** 3개 파일을 순차적으로 덮어쓰는 과정이 완전히 사라지므로, 어떤 독자도 중간 상태를 읽을 수 없으며 100% 원자적 롤백이 수학적으로 보장됩니다.

## 6. 원자적 Bootstrap Lock 및 분석기 동시성 계약 (P0-3 완결)

1. **Bootstrap Lock의 원자적 독점 획득:**
   - Bootstrap 실행 시 `fs.openSync('synapse_data/.bootstrap.lock', 'wx')` (`O_CREAT | O_EXCL`)로 원자적 배타 락을 획득합니다.
   - 락 파일 내부에는 `{ pid: process.pid, startTime: Date.now() }`를 기록합니다.
   - 이미 락이 존재할 경우 다른 Bootstrap 실행은 즉시 거부됩니다.
2. **분석기 측 Lock 확인 및 세대 고정:**
   - 분석 파이프라인 시작 시 `.bootstrap.lock`의 존재 여부를 확인합니다.
   - 만약 Bootstrap이 진행 중이면 분석기는 대기하거나 "재수집 진행 중: 완료 후 재시도" 메시지를 반환하고 즉시 중단합니다.
   - 분석 시작 시 결정된 활성 SSoT 세대 파일 경로(`generations/project_state.v{N}.json`)를 분석 세션 객체에 영구 고정(Pinning)합니다. 분석 도중 신규 세대가 생성되더라도, 실행 중인 분석기는 세션에 고정된 불변 세대 파일만 끝까지 읽으므로 일관성이 유지됩니다.
