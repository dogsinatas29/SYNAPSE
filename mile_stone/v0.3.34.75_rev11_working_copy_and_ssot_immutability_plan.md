## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 근본 원인 및 완전한 제거
과거 rev1~10 보완 문서는 **"공식 SSoT(`project_state.json`)를 디스크 상에서 인플레이스로 수정하고 크래시 시 이를 복구해야 한다"**는 잘못된 전제에서 출발했습니다.  
이로 인해 파일 시스템의 원자성 한계를 메우기 위해 2단계 저널, 복구 락, Stale Lock 세대 판독, 14개 분기 복구 매트릭스라는 극단적인 복잡성에 빠졌습니다.

### 1.2 "최고의 복구는 복구할 필요 자체를 만들지 않는 것"
사용자의 명확한 KISS 원칙에 따라, 문제를 아키텍처 수준에서 원천 차단합니다:
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **SSoT 영구 불변**: 수집기(Bootstrap)가 생성한 세대별 SSoT는 읽기 전용 불변 원본으로 박제합니다.
2. **Working Copy 격리 분석**: 분석·검증 파이프라인은 원본에서 독립적으로 파싱된 일회용 인메모리 객체(Working Copy)에서 실행되며, 실패 시 해당 복사본을 즉시 폐기하고 원본에서 다시 로드합니다. 롤백 저널과 복구 매트릭스는 완전히 불필요합니다.
3. **데이터 소유권 분리**: 캔버스 프레젠테이션과 사용자 편집 데이터는 SSoT 원본에서 완전히 분리된 전용 오버레이 파일(`layout.json`, `user_graph.json`)로 영속화합니다.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① generations/project_state.vN │ ② Disposable Working Copy             │
│    [Immutable SSoT]            │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - 노드, 엣지, 클러스터      │    - 실패 시 즉시 폐기 (롤백 불필요)  │

├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가/수정/삭제 노드       │
│    - 뷰포트(zoom, offset)      │    - 사용자 확정/수정/삭제 엣지       │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 원자적 단일 Writer 락 및 Stale Lock 직렬화 인계 완결 (P0-1 완결)

### 3.1 단일 로컬 Extension Host 범위 한정
- 본 계약의 대상 범위는 **"단일 로컬 머신의 동일 워크스페이스"**로 명시적으로 한정합니다. (공유 네트워크 파일시스템은 비목표).

### 3.2 `takeover.lock`의 완전한 생명주기 및 Stale 회수 규칙
회수 전용 락(`takeover.lock`) 자체가 Stale 되어 워크스페이스가 영구 Read-Only에 빠지는 문제를 원천 차단하기 위해, 회수 락에도 메타데이터와 자동 만료 규칙을 엄격히 정의합니다:

1. **`takeover.lock` 스키마 및 원자적 생성:**
   - 회수 시도 시 `fs.openSync('synapse_data/.takeover.lock', 'wx')` 성공 Host만 진입.
   - 락 내부 기록: `{ hostSessionId: UUID, pid: process.pid, createdAt: Date.now() }`.
2. **`takeover.lock` 자체의 Stale 판정 (Self-Healing Recovery):**
   - 만약 `.takeover.lock`이 이미 존재하여 획득 실패 시, 락 파일을 읽어 생존을 검증합니다:
     ① 기록된 `pid`가 `process.kill(pid, 0)` 검사 결과 `ESRCH` (완전 부재)인 경우.  
     ② 또는 생성 시각(`createdAt`)으로부터 **10초(Takeover TTL)**를 초과한 경우 (회수 작업은 단순 rename이므로 10초 초과는 비정상 크래시로 확정).
   - 위 Stale 조건 충족 시, `fs.unlinkSync('.takeover.lock')`을 안전하게 수행하고 다시 `openSync('wx')`로 락 획득을 1회 재시도합니다.
3. **정상 완료 후 정리:**
   - `.takeover.lock`을 `.active_writer.lock`으로 `fs.renameSync`하는 즉시 `takeover.lock`은 파일시스템에서 원자적으로 사라지며 신규 Primary Writer 락으로 승격 완료됩니다.

## 4. `user_graph.json` 완전 스키마 및 엄격한 참조 무결성 검증 계약 (P0-3 완결)

### 4.1 스키마 정의 및 수정 필드 안전 제한
```typescript
export interface NodeMetadataPatch {
    label?: string;
    description?: string;
    customProperties?: Record<string, string | number | boolean>; // 원시 타입만 허용
}

export interface EdgeMetadataPatch {
    label?: string;
    weight?: number;
    status?: 'proposed' | 'confirmed';
}

export interface UserGraphData {
    revision: number;
    generationId: number;                              // 검증 기준 SSoT 세대 번호 (P1-1 완결)
    customNodes: Record<string, CustomNode>;           // ID 규칙: user::{uuid}
    modifiedNodes: Record<string, NodeMetadataPatch>;  // SSoT 노드 메타데이터 패치
    deletedNodeIds: string[];                          // 노드 Tombstone (SSoT 및 Custom Node 통합)
    
    customEdges: CustomEdge[];                         // ID: user::{uuid}
    modifiedEdges: Record<string, EdgeMetadataPatch>;  // SSoT 엣지 메타데이터 패치 (id/from/to 수정 금지)
    deletedEdgeIds: string[];                          // 엣지 Tombstone
}
```

### 4.2 엄격한 저장 검증 및 정규화 규칙 (Validation on Save)
1. **ID 네임스페이스 및 고유성 검증:**
   - 모든 `customNodes`의 Key 및 `customEdges`의 ID는 정규식 `^user::[a-f0-9\-]{36}$`을 강제합니다.
   - `customEdges` 배열 내에서 ID 중복이 발견되면 저장을 즉시 거부합니다.
2. **수정 대상 유효성 검증:**
   - `modifiedNodes`의 모든 키는 현재 활성 SSoT의 실제 노드 ID여야 합니다.
   - `modifiedEdges`의 모든 키는 현재 활성 SSoT의 실제 엣지 ID여야 합니다. (Custom Edge 수정은 `customEdges` 배열 내에서 인라인 관리).
3. **Custom Node 삭제 모델 및 끝점 무결성 검증 (Dangling Edge 차단):**
   - **Custom Node 삭제 규칙:** 사용자가 추가한 커스텀 노드를 삭제할 경우, `customNodes` 딕셔너리에서 제거함과 동시에 **`deletedNodeIds` Tombstone에도 등록**하여 오버레이 순서와 무관하게 삭제 상태를 영속화합니다.
   - **Custom Edge 끝점 검증:** `customEdges`의 `from`과 `to`는 반드시 다음 조건을 만족해야 하며, 위반 시 저장을 즉시 거부합니다:
     $$\text{endpoint} \in (\text{SSoT.nodes} \cup \text{customNodes}) \land \text{endpoint} \notin \text{deletedNodeIds}$$
     *(즉, SSoT 노드이든 Custom 노드이든 `deletedNodeIds`에 등록된 노드를 참조하는 Custom Edge는 영속화를 거부)*.
4. **Edge Tombstone 충돌 정규화:**
   - 동일한 Edge ID가 `deletedEdgeIds`와 `modifiedEdges`에 동시에 존재하는 경우, `modifiedEdges[id]`를 자동 삭제하고 **Tombstone(`deletedEdgeIds`)만 영속화**합니다.
5. **SSoT 세대 일관성 검증 (P1-1 완결):**
   - UserGraph 저장 시 파일의 `generationId`와 현재 시스템의 `activeGeneration`이 일치하는지 확인합니다. 세대 불일치 시 저장을 거부하고 최신 세대 기준으로 재동기화합니다.

## 5. 원자적 스냅샷 포인터 기반 Rollback 일관성 보장

순차 파일 복사로 인한 불일치를 배제하기 위해, **"완성된 스냅샷 디렉터리 + 활성 스냅샷 단일 포인터(`active_snapshot.json`)"** 모델을 공식 채택합니다:

```
synapse_data/
├── snapshots/
│   ├── snap_20261115_1000/           # 스냅샷 A (완성된 불변 디렉터리)
│   │   ├── active_generation.json    # 해당 시점의 활성 SSoT 세대 번호/해시
│   │   ├── user_graph.json           # 해당 시점의 사용자 그래프 데이터
│   │   └── layout.json               # 해당 시점의 레이아웃 좌표/뷰포트
│   └── snap_20261115_1100/           # 스냅샷 B (완성된 불변 디렉터리)
└── active_snapshot.json              # 활성 스냅샷 단일 포인터 (원자적 교체)
```

1. **독자의 불변 읽기:** 모든 캔버스 로더는 항상 `active_snapshot.json`이 가리키는 스냅샷 디렉터리에서 세 세트를 읽습니다.
2. **단일 포인터 원자적 교체:**
   - 대상 스냅샷 디렉터리 내 3개 파일의 무결성 검증 완료 후,
   - 임시 포인터 파일 `active_snapshot.json.tmp`를 작성 및 `fsync`하고,
   - `fs.renameSync('active_snapshot.json.tmp', 'active_snapshot.json')` 단 1회의 원자적 rename으로 활성 스냅샷을 교체합니다.
3. **플랫폼 보장 범위:** Linux 및 macOS(POSIX)에서는 부모 디렉터리 `fsync`를 수행하여 완벽한 크래시 내구성을 보장하며, Windows에서는 OS `MoveFileEx` 기반의 원자적 가시성 교체를 보장합니다.

## 6. 소유 토큰 파일 분리 기반 Bootstrap Lock 해제 원자성 완결 (P0-2 완결)

소유권 확인과 `unlinkSync` 사이의 TOCTOU 오삭제 경쟁을 원천 차단하기 위해, **"디렉터리 기반 배타 락 또는 소유 토큰 파일 분리"**를 도입합니다:

```
[Bootstrap 시작 시]
  ├─ 1. fs.mkdirSync('synapse_data/.bootstrap_lock_dir')  // OS 커널 원자적 배타 획득
  └─ 2. fs.writeFileSync('synapse_data/.bootstrap_lock_dir/owner.token', sessionToken)

[Bootstrap 종료/해제 시: finally 블록]
  ├─ 1. owner.token을 읽어 자신의 sessionToken과 일치하는지 확인
  ├─ 2. 일치 시: owner.token 삭제 후 rmdirSync('synapse_data/.bootstrap_lock_dir')
  └─ 3. 불일치 시 (타 세션이 이미 회수함): 절대 rmdir하지 않고 안전 종료
```

- **효과:** `mkdir`은 POSIX 및 Windows 커널 수준에서 완벽한 원자적 배타 연산입니다. 이미 디렉터리가 존재하면 커널이 `EEXIST`로 차단합니다.
- 해제 시에도 자신의 `owner.token`이 확인될 때만 안전하게 해제되므로, 지연 스케줄링된 구 세션이 신규 세션의 락 디렉터리를 오삭제하는 경쟁이 물리적으로 불가능합니다.
- **분석 세션 고정 (Session Pinning):** 분석기는 시작 시점에 `active_generation.json`을 검증한 뒤 해당 불변 세대 파일(`generations/v{N}.json`) 경로를 세션에 영구 고정하여, 도중에 Bootstrap이 새 세대를 활성화해도 시작 세대만 끝까지 읽습니다.
