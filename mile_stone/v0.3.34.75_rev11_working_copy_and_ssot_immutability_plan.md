## 1. 개요 및 설계 철학 (KISS & Lean Architecture)

### 1.1 단순화된 핵심 데이터 모델
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**

1. **Bootstrap 소유 교체 가능 SSoT (`project_state.json`)**: 수집기(Bootstrap)만 작성하며, UI와 분석기는 절대 직접 수정하지 않는 읽기 전용 기준 원본.
2. **분석별 독립 Working Copy**: 분석 파이프라인은 디스크 원본에서 직접 파싱된 독립 메모리 객체에서 실행되며 종료 시 즉시 GC 폐기.
3. **2대 오버레이 분리**:
   - `layout.json`: 사용자의 시각적 캔버스 조작(노드 드래그 좌표, 뷰포트 줌/오프셋, 클러스터 수동 접힘)만 영속화.
   - `user_graph.json`: 사용자 그래프 편집(커스텀 노드/엣지, 메타데이터 패치, SSoT 숨김용 Tombstone)만 영속화.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① project_state.json           │ ② Disposable Working Copy             │
│    [SSoT: Bootstrap-Owned]     │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - UI/분석기 직접 수정 금지  │    - 분석 종료 시 즉시 GC 폐기        │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 노드 좌표(positions)      │    - 커스텀 노드/엣지 (삭제 시 delete) │
│    - 뷰포트(zoom, offset)      │    - 노드/엣지 메타데이터 패치        │
│    - 클러스터 접힘(clusters)   │    - SSoT 숨김 목록(hiddenNode/EdgeIds)│
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 핵심 아키텍처 규약 (Lean Protocol)

### 3.1 디스크 락 폐지 및 단일 직렬 I/O 큐 (`SynapseFileQueue`)
- **디렉터리 락(`.writer_lock_dir`) 전면 폐지:** 비정상 크래시 시 사용자가 터미널에서 수동 삭제해야 하는 UX 결함을 제거합니다.
- **단일 직렬 I/O 큐 (`SynapseFileQueue`):** Host 프로세스 내부의 모든 파일 쓰기(SSoT 교체, `layout.json`, `user_graph.json`)는 단일 FIFO Promise Chain 큐로 직렬화합니다.
- **OCC Revision 기반 Snap-back 방지:**
  - 웹뷰는 저장 요청 시 자신이 알고 있는 기준 Revision(`expectedRevision`)을 전달합니다.
  - Host 메모리의 최신 Revision과 불일치할 경우(`expectedRevision < currentRevision`), 오래된 쓰기는 즉시 거부(`REJECTED_STALE_REVISION`)하고 최신 디스크 상태를 웹뷰로 강제 푸시합니다.
  - 이를 통해 드래그 중 구 버전 응답 도착으로 캔버스 위치가 튀는 Snap-back 버그를 완벽히 차단합니다.

### 3.2 안전한 원자적 파일 교체 및 Windows 재시도 규약
- **동일 디렉터리 배타적 임시 파일 생성:**
  - 대상 파일과 동일 디렉터리 내에 임시 파일 생성 (`fs.openSync(tmpPath, 'wx')`).
  - 데이터 기록 $\rightarrow$ 파일 `fsyncSync(tmpFd)` $\rightarrow$ `fs.closeSync(tmpFd)`.
- **원자적 파일 교체 (`renameSync`):**
  - `fs.renameSync(tmpPath, targetPath)`로 원자적 교체.
- **Windows(NTFS) 잠금 지연 재시도 (Exponential Backoff):**
  - Windows 환경에서 백신 프로그램, 검색 인덱서, File Watcher 등으로 인해 대상 파일 덮어쓰기 시 일시적 `EPERM` 또는 `EBUSY` 에러가 발생할 수 있습니다.
  - 이에 대비하여 **50ms $\rightarrow$ 100ms $\rightarrow$ 200ms 간격으로 최대 3회 재시도**를 수행하며, 연속 실패 시에만 에러를 반환하고 임시 파일을 정리합니다.
- **임시 파일 정리:** `renameSync` 이전 단계 실패 시 임시 파일 즉시 언링크(`fs.unlinkSync`). 대상 파일은 온전히 보존됩니다.

### 3.3 Custom 엔티티 수명주기 및 Tombstone 단순화
- **RFC 4122 UUID v4 충돌 배제:** UUID v4는 122비트 난수 엔트로피를 가지므로 현실적으로 식별자 충돌 가능성은 무시할 수 있는 수준입니다.
- **Custom 엔티티 삭제 단순화:** 사용자가 커스텀 노드/엣지를 삭제하면 `customNodes` 및 `customEdges` 컬렉션에서 즉시 삭제(`delete`)합니다. 영구 Tombstone을 유지할 필요가 없습니다.
- **Tombstone 용도 한정 (`hiddenNodeIds`, `hiddenEdgeIds`):**
  - Tombstone은 **오직 소스 코드 형상에 기반한 SSoT 노드·엣지를 캔버스에서 숨기는 용도로만 사용**합니다.
  - 사용자가 SSoT 엔티티를 숨기면 `hiddenNodeIds` / `hiddenEdgeIds`에 등록되고, 복원 시 해당 목록에서 제거됩니다.
- **단순한 멱등 Reset:**
  - Reset은 `user_graph.json`과 `layout.json` 파일을 삭제하거나 빈 객체로 초기화하는 멱등한 작업입니다.
  - 복잡한 큐 배리어나 상태 추적 없이 단일 큐 직렬 작업으로 완료됩니다.

### 3.4 경량 SSoT 검증 기준선 (메모리 절감)
- 60MB 대규모 SSoT(14,748 노드, 107,220 엣지) 전체 JSON 파싱본(약 198MiB)을 인메모리에 영구 상주시키지 않습니다.
- 검증에 필요한 것은 오직 ID 실존 여부와 해시뿐이므로, Host는 **`ssotNodeIds: Set<string>`**, **`ssotEdgeIds: Set<string>`**, 그리고 **`ssotSha256: string`**만 경량 캐시로 보관합니다. (힙 메모리 점유율을 수 MiB 수준으로 대폭 절감하는 추정 효과).

### 3.5 마이그레이션 없음 및 좌표 폴백 규칙
- **기존 파일 무수정 원칙:** 기존 `project_state.json`에 기록되어 있는 `position`이나 `canvas_state`는 삭제하거나 변조하지 않고 보존합니다.
- **초기값 및 폴백:**
  - `layout.json`이 존재하면 해당 파일의 좌표를 최우선 적용합니다.
  - `layout.json`이 없거나 손상된 경우, 경고 로그를 남기고 `project_state.json` 내부의 기존 좌표(과거 좌표)를 초기값으로 폴백 읽기만 수행합니다. (SSoT에 쓰기는 절대 수행하지 않음).

### 5.3 Phase 1 필수 합격 기준 (Acceptance Criteria)
1. **SSoT 무결성 및 SHA-256 불변 증명:**
   - 캔버스에서 노드를 이동하고 저장을 수행한 직후, `project_state.json` 파일의 SHA-256 해시가 작업 전과 바이트 단위로 100% 동일함을 실측 로그로 증명.
2. **레이아웃 영속성 및 위치 복원:**
   - 노드 이동 후 저장 $\rightarrow$ VS Code 창 리로드(재시작) 후 노드 위치 및 뷰포트 상태가 `layout.json`에서 정확히 복원됨을 검증.
3. **SSoT 기존 좌표 보존 및 읽기 전용 폴백:**
   - `project_state.json` 내부의 기존 `position` 및 `canvas_state` 필드는 수정되지 않으며, `layout.json`이 존재하지 않을 때에만 초기값으로 폴백 읽기됨을 확인.
4. **손상 폴백 안전성:**
   - `layout.json` 파일이 비정상 종료 등으로 깨지거나 손상된 경우, 에러로 크래시되지 않고 경고 로그 기록 후 SSoT의 초기 좌표로 안전하게 폴백함을 검증.
5. **원자적 교체 및 Windows 재시도 동작 검증:**
   - 동일 디렉터리 임시 파일(`O_CREAT | O_EXCL`) $\rightarrow$ `fsyncSync` $\rightarrow$ `renameSync` 경로로 저장되며, `EPERM`/`EBUSY` 발생 시 50/100/200ms 지연 재시도가 작동함을 단위 테스트로 입증.
6. **Snap-back 재현 방지 테스트:**
   - 사용자가 노드를 연속 드래그하는 도중에 오래된 Revision을 가진 비동기 저장 요청이 도달하는 시나리오를 시뮬레이션하여, 구 버전 요청이 안전하게 거부되고 최신 위치가 되돌아가지(Snap-back) 않음을 검증.
7. **`handleSaveState` 경로 SSoT 직접 쓰기 0건 검증:**
   - `handleSaveState` 실행 경로에서 `project_state.json`을 대상으로 `writeFile`을 호출하는 코드가 완전히 제거되었음을 `grep` 및 정적 검사로 확인.
