## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 완전한 일소
과거의 복잡성은 "과거 SSoT를 이력으로 보관하고 롤백·교체하겠다"는 미련에서 출발했습니다.  
SYNAPSE는 소스 코드 형상 관리 도구가 아니며, **"현재 프로젝트 소스 트리의 아키텍처를 시각화하고 진단하는 분석 엔진"**입니다.  
프로젝트 코드가 바뀌어 재수집(Re-Bootstrap)이 발생하면, 이전 SSoT의 세대 번호를 따질 필요 없이 **새로운 단일 `project_state.json`이 유일한 기준 원본**이 됩니다.

### 1.2 단순화된 3대 불변식
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **Bootstrap 소유 교체 가능 SSoT (`project_state.json`)**: 수집기(Bootstrap)만 작성하며, UI와 분석기는 절대 직접 수정하지 않는 읽기 전용 기준 원본 (Bootstrap-owned replaceable SSoT).
2. **분석별 독립 Working Copy**: 분석 파이프라인(전체 클러스터 분석, 선택 그룹 분석 등)은 디스크 원본에서 직접 파싱된 독립 메모리 객체에서 실행되며, 종료 시 즉시 폐기.
3. **2대 오버레이 분리**: 사용자의 시각적 조작은 `layout.json`(좌표/뷰포트)에, 사용자 그래프 편집은 `user_graph.json`(노드/엣지 추가·수정·삭제)에만 영속화.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① project_state.json           │ ② Disposable Working Copy             │
│    [SSoT: Bootstrap-Owned]     │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - 노드, 엣지, 클러스터      │    - 분석 A/B 간 객체 공유 0건        │
│    - UI/분석기 직접 수정 금지  │    - 분석 종료 시 즉시 GC 폐기        │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가/수정/삭제 노드       │
│    - 뷰포트(zoom, offset)      │    - 사용자 확정/수정/삭제 엣지       │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 통합 단일 Writer 락: 디렉터리 배타 락 및 완전한 Read-Only 격리 규약 (P0-1 완결 - ACCEPTED)

### 3.1 단일 로컬 파일시스템 범위 한정 및 락 경로 정규화 (P0-2, P1-7 완결)
- 본 계약의 대상 범위는 **"단일 로컬 머신의 표준 로컬 파일시스템(ext4, xfs, APFS, NTFS 등)에 마운트된 동일 워크스페이스"**로 명시적으로 한정합니다.
- **심볼릭 링크 해소 및 Canonical Path 기반 락 경로 결정 (Canonical Path via realpathSync — P0-2, P1-7 완결):**
  동일한 물리적 워크스페이스 디렉터리가 심볼릭 링크(예: `/work/project`와 `/home/user/project-link`)를 통해 서로 다른 경로로 열릴 경우, 단순 `path.resolve()`만으로는 락 경로가 분기되어 복수 Writer가 공존하는 Split-Brain이 발생할 수 있습니다. 이를 방지하기 위해:
  1. Host 활성화 시 워크스페이스 루트의 실제 물리 파일시스템 경로를 `fs.realpathSync.native()`(또는 `fs.realpathSync()`)를 통해 심볼릭 링크가 완전히 해소된 **Canonical Path(`canonicalWorkspaceRoot`)**로 단일화합니다.
  2. 락 경로는 반드시 이 정규화된 Canonical Path를 기준으로 생성합니다:
     $$\text{lockDirPath} = \text{path.join}(\text{canonicalWorkspaceRoot}, \text{'synapse\_data'}, \text{'.writer\_lock\_dir'})$$
  3. **보장 범위의 현실적 한정 (P1-7 완결):** 본 보장 범위는 `realpathSync`로 정규화되는 심볼릭 링크 및 표준 경로 별칭에 한정됩니다. 동일 디렉터리를 서로 다른 bind mount 경로로 마운트하여 진입하는 등 파일시스템 수준에서 상이한 Canonical Path로 노출되는 특수 구성 환경은 미지원 범위로 명시하며, "모든 경로 별칭 차단"과 같은 비현실적 과장 표현은 배제합니다.
- 네트워크 파일시스템(NFS, SMB 등)이나 특수 분산 마운트는 SYNAPSE의 비목표이며, `mkdir`의 원자적 배타성을 일반화하지 않습니다.

### 3.2 원자적 배타 획득 및 무조건적 Read-Only Fallback (Zero-Split-Brain Policy)
살아있는 Primary Host가 존재하는 상태에서 다른 창이 락을 강제 삭제하여 발생하는 Split-Brain(다중 Writer 공존)을 아키텍처 수준에서 원천 차단하기 위해, **"소유권 증명 불가 시 쓰기 전면 불허"** 원칙을 확립합니다:

1. **원자적 배타 디렉터리 생성 (Atomic Exclusive Directory Creation):**
   - Extension Host 활성화 시 `fs.mkdirSync(lockDirPath)` 호출로 배타적 디렉터리 생성을 시도합니다.
   - 지원되는 로컬 파일시스템에서 `mkdir`은 이미 디렉터리가 존재할 경우 `EEXIST`를 반환하는 완벽한 원자적 배타 연산입니다.
2. **최초 락 생성 직후 실패 처리 (Fail-Safe on Init):**
   - `mkdirSync`가 성공한 직후, 내부에 `{ hostSessionId: UUID, pid: process.pid, createdAt: Date.now() }`를 담은 `owner.token`을 기록합니다.
   - **토큰 기록 중 I/O 에러 또는 크래시 발생 시:** Host는 절대로 Writer 권한을 활성화하지 않고 즉시 비활성화/실패 상태로 전환합니다. 토큰이 없는 미완성 디렉터리는 자동 삭제하지 않고 방치하여 다른 Host가 오인 획득하지 못하도록 보호합니다.
   - 정상적으로 토큰 기록까지 완료된 경우에만 **Primary Writer** 권한을 정식 부여받습니다.
3. **충돌 시 완전한 Read-Only Fallback (`EEXIST`):**
   - 이미 `.writer_lock_dir`이 존재하면, **어떠한 자동 회수, 프로세스 생존 검사, 파일 삭제, 백그라운드 덮어쓰기도 일체 시도하지 않습니다.**
   - 해당 Host는 즉시 **읽기 전용 모드(Read-Only Session)**로 진입하며, 모든 저장 IPC 요청을 진입점에서 즉시 거부(`REJECTED_SECONDARY_HOST_READ_ONLY`)합니다.
   - `EEXIST` 이외의 파일시스템 에러(권한 부족, I/O 에러 등) 발생 시 조용히 넘기지 않고 치명적 락 획득 실패 에러로 로깅합니다.
4. **UI 강제 삭제 금지 및 Split-Brain 차단 (No UI Force-Delete):**
   - **Secondary Host의 UI 웹뷰에 락을 임의로 삭제하는 버튼이나 명령어를 일체 제공하지 않습니다.** (UI 버튼 클릭 시 실행 중인 Primary Host의 소유권과 충돌하여 발생하는 Split-Brain 원천 차단).
   - UI에는 오직 객관적 사실 알림만 표시합니다:
     > **"[안내] 다른 Extension Host의 잠금이 존재하거나 이전 세션의 잠금이 남아 있습니다. 현재 세션은 읽기 전용 모드로 동작합니다."**
5. **정상 종료 시 해제:**
   - Host 정상 비활성화(`deactivate`) 시, 디렉터리 내부의 `owner.token`을 읽어 `hostSessionId`가 자신의 세션 ID와 엄격 일치할 때만 `fs.rmSync(lockDirPath, { recursive: true })`로 안전하게 락을 해제합니다. 외부 프로세스가 실행 중 락을 삭제하거나 재생성하지 않는 정상 락 프로토콜 범위에서 안전하게 동작합니다.
6. **비정상 종료 후 외부 수동 복구 (External Manual Recovery):**
   - 이전 Host가 비정상 크래시되어 락 디렉터리가 영구 방치된 경우의 복구는 **"모든 관련 VS Code 프로세스를 완전히 종료한 후, 사용자가 외부 터미널/파일 탐색기에서 `synapse_data/.writer_lock_dir`을 명시적으로 직접 삭제하고 재시작"**하는 수동 절차로만 규정합니다.
   - **효과:** 계약을 준수하는 Extension Host 간에는 자동 락 회수 및 Secondary Host의 강제 삭제 경로가 존재하지 않으므로, 정상적인 락 프로토콜 범위에서 다중 Writer 공존을 방지합니다. 외부에서 실행 중인 락을 임의 삭제하거나 파일시스템의 배타성 보장이 깨지는 경우까지 수학적으로 배제하는 것은 아닙니다.

### 3.3 Host 내부 직렬 작업 큐 체계 및 교차 커밋 정합성 (Host-Internal Serial Queues — P0-1 완결)
단일 Writer Lock은 복수 Extension Host 간의 배타성을 보장할 뿐, 단일 Extension Host 내부에서 비동기 이벤트 루프로 도착하는 동시 IPC 요청을 직렬화하지 못합니다. 이를 해결하기 위해 Host 내부에 다음 2개의 독립 직렬 큐(FIFO Promise Chain)를 확립하며, SSoT 교체와 오버레이 저장 간의 관계는 **비파괴적 필터링 기반 허용 정책(Option A)**으로 확정합니다:

1. **`SSoTTaskQueue` (SSoT 읽기 및 교체 전용 직렬 큐):**
   - **대상 작업:** ① SSoT 디스크 파일 읽기 및 JSON 파싱 (Working Copy 생성), ② Re-Bootstrap의 임시 파일 $\rightarrow$ SSoT 원자적 교체 (`renameSync`).
   - **상호 배타 보장:** SSoT 읽기·파싱 작업이 진행 중일 때 Re-Bootstrap 교체 작업이 끼어들지 못하며, 반대로 교체 작업 중에는 SSoT 읽기가 대기합니다.
   - **분석 계산의 분리 (Decoupled Analysis):** SSoT 파싱이 완료되어 독립 인메모리 Working Copy 객체가 반환된 즉시 큐 슬롯은 해제됩니다. 무거운 분석 알고리즘 계산은 `SSoTTaskQueue` 밖에서 독립 실행되므로, 분석이 오래 걸려도 Re-Bootstrap 작업이 영구 블로킹되지 않으며 분석 도중 SSoT가 교체되어도 독립 복사본은 영향받지 않습니다.
2. **`OverlaySaveQueue` (오버레이 저장 전용 직렬 큐):**
   - **대상 작업:** `layout.json` 및 `user_graph.json`의 저장 요청 직렬화.
   - **독립 OCC 상태 관리:** 큐는 단일 FIFO 큐로 요청을 직렬화하되, 내부 Revision 검증 및 Latch 상태는 **`LayoutData` (`currentLayoutRevision`, `layoutResyncLatch`)**와 **`UserGraphData` (`currentUserGraphRevision`, `userGraphResyncLatch`)**로 완전히 독립 분리하여 처리합니다.
   - **동시 IPC 직렬화:** 웹뷰에서 마우스 드래그나 메타데이터 편집으로 인해 연속적으로 발행되는 비동기 저장 IPC 메시지를 도착 순서대로 엄격히 직렬화하여 처리합니다.
3. **교차 큐 정합성, 검증용 SSoT 스냅샷 소유권 및 Stale Validation 허용 경계 (Option A 채택 — P0-1, P0-2, P1-1, P1-3, P1-5 완결):**
   - **검증용 기준 스냅샷 (`activeValidationSSoT`) 소유권 및 불변 식별자 (P1-5 완결):** Host는 인메모리에 단일 불변 참조 `activeValidationSSoT`를 소유하며, 각 스냅샷은 파싱 시점의 SSoT 파일 내용 전체에 대한 **SHA-256 암호학적 해시값인 불변 식별자 `ssotSnapshotId: string`**을 필수로 보유합니다. (파싱 타임스탬프 `parsedAt: number`는 진단 및 로깅용 메타데이터로만 분리 관리하여 동일 시각 해상도 내 충돌 가능성을 원천 배제합니다).
     - **Re-Bootstrap 원자적 교체 순서 (P1-3 완결):** `SSoTTaskQueue` 내에서 ① 임시 SSoT 객체를 먼저 파싱 및 토폴로지 검증 $\rightarrow$ ② 디스크 `fsyncSync` $\rightarrow$ ③ `fs.renameSync(tmpPath, ssotPath)` 실행 $\rightarrow$ ④ **rename 성공 직후 동일 동기 실행 구간에서 `activeValidationSSoT` 참조를 검증 완료된 새 SSoT 객체 및 신규 SHA-256 `ssotSnapshotId`로 원자적 교체** $\rightarrow$ ⑤ 부모 디렉터리 `fsyncSync` 순서로 완결합니다. 교체 실패 상태는 발생하지 않습니다.
     - **분석용 복사본과의 완전 분리:** 무거운 분석 알고리즘이 사용하는 Working Copy와 달리, `activeValidationSSoT`는 오직 오버레이 저장 진입 시점의 신규 변경분 델타(Delta) 검증 기준선으로만 사용됩니다.
   - **저장 검증 기준 고정 및 Stale Validation Window 허용 (P0-2 완결):**
     - `OverlaySaveQueue`에서 저장 작업이 시작되면, 해당 시점의 `activeValidationSSoT`와 그 `ssotSnapshotId`를 캡처하여 해당 저장 트랜잭션의 검증 기준으로 고정합니다.
     - **유한한 Stale 검증 구간의 허용 (Bounded Stale Validation Window):** 오버레이 저장 작업이 캡처된 SSoT `A`를 기준으로 검증 및 커밋을 진행하는 도중에 Re-Bootstrap이 완료되어 현재 SSoT가 `B`로 교체될 수 있습니다.
     - **Option A 안전성 보장:** 신규 변경분이 직전 SSoT `A`를 기준으로 승인되었더라도, 새 SSoT `B`에 해당 참조가 없다면 §4.2.1의 **"비파괴적 필터링(로드 시 화면 표시만 자동 제외, 디스크 원본 영구 보존)"**에 의해 렌더링에서 안전하게 격리되므로 데이터 왜곡이 발생하지 않습니다. 따라서 두 큐 간에 분산 락이나 롤백 없이도 완벽한 데이터 안전성을 보장합니다.
   - **효과:** 두 큐 사이에 불필요한 분산 트랜잭션 락이나 복잡한 2단계 커밋(2PC) 오버엔지니어링을 배제하고, 일반 저장 및 Re-Bootstrap 과정에서 비활성 참조를 임의 삭제하지 않고 디스크 데이터로 안전하게 보존합니다.

## 4. Re-Bootstrap 원자적 교체 및 오버레이 유효성 계약 (P0-2, P1-3 완결)

### 4.1 Re-Bootstrap 원자적 교체, 임시 파일 규약 및 차등 내구성 계층 (P1-3, P1-4, P0-4 완결)

1. **임시 파일 배타 생성 및 절대 경로 정규화 (Exclusive Temp File Creation):**
   - 모든 저장 대상 경로(`project_state.json`, `layout.json`, `user_graph.json`)는 워크스페이스 루트 기준 절대 경로(`path.resolve(workspaceRoot, 'synapse_data', targetName)`)로 정규화합니다.
   - 대상 파일과 반드시 **동일 디렉터리(동일 마운트/파일시스템)** 내에 생성하여 장치 간 이동 에러(`EXDEV`)를 원천 방지하며, 프로세스 PID, 타임스탬프, 암호학적 난수(Nonce)를 결합하여 이름 충돌 확률을 극소화합니다:
     $$\text{tmpPath} = \text{path.join}(\text{path.dirname}(\text{targetPath}), \text{`.\${path.basename(targetPath)}.\${process.pid}.\${Date.now()}.\${crypto.randomBytes(4).toString('hex')}.tmp`})$$
   - **배타적 생성 플래그 (`wx`) 및 충돌 재시도:** 임시 파일은 `fs.openSync(tmpPath, 'wx')`(`O_CREAT | O_EXCL | O_WRONLY`)로 생성하여, 기존 임시 파일이 존재할 경우 덮어쓰지 않고 에러를 반환합니다. 충돌 발생 시 즉시 새 난수로 1회 재시도하며, 연속 실패 시 `REJECTED_TMP_COLLISION` 에러로 안전하게 중단합니다.
2. **실패 상태의 엄격한 3단계 분리 및 사후 처리 정책 (P0-3, P0-4 완결):**
   - **`PRE_RENAME_FAILURE` (이름 변경 이전 실패):** 임시 파일 생성, 데이터 기록, 파일 fsync, 유효성 검증 단계에서 실패한 경우.
     `try { fs.unlinkSync(tmpPath); } catch (err) { logger.warn('PRE_RENAME_TMP_CLEANUP_FAILED', err); }`를 실행하여 정리를 시도하고 실패 시 별도 경고 로그를 기록합니다. 기존 대상 파일은 온전히 보존됩니다.
   - **`RENAME_SUCCESS` (원자적 교체 성공):** `fs.renameSync(tmpPath, targetPath)` 성공. 임시 파일 삭제는 절대 시도하지 않습니다 (이미 목적지 파일로 이동됨).
   - **`POST_RENAME_DURABILITY_UNCONFIRMED` (디렉터리 동기화 실패):** Level 1 파일 교체(rename) 성공 후 부모 디렉터리 `fsync`가 실패한 경우.
     - **명시적 응답 분리 및 웹뷰 처리 (P0-3, P1-3 완결):** 웹뷰에 반환하는 응답은 가시성 교체와 내구성 확인을 구분하여 반환합니다:
       - **오버레이 저장 (`user_graph.json`):** `{ committed: true, durability: 'unconfirmed', revision: newRevision }` 형태로 반환. 웹뷰는 이를 정상 커밋으로 간주하여 로컬 기대 Revision을 `newRevision`으로 확정 갱신하며 재시도나 Latch를 유발하지 않습니다. (디렉터리 fsync까지 성공한 경우 `durability: 'confirmed'`).
       - **Re-Bootstrap (`project_state.json` — P1-3 완결):** rename 성공 직후 이미 메모리 `activeValidationSSoT`가 신규 객체로 교체 완료된 상태이므로, 부모 디렉터리 fsync 실패 시에도 `{ committed: true, durability: 'unconfirmed', ssotSnapshotId: newSnapshotId }`로 반환합니다. `activeValidationSSoT`는 교체된 상태를 그대로 확정 유지하며, 웹뷰는 재시도하지 않고 새 SSoT 상태를 기준으로 화면을 갱신합니다.
     - **Revision 및 SSoT 처리:** 파일 가시성 교체(`renameSync`)는 이미 디스크 파일시스템 레벨에서 성공하여 신규 데이터로 교체되었으므로, 메모리 상태(Revision 또는 `activeValidationSSoT`)는 롤백하지 않고 정상 갱신 상태를 유지합니다.
     - **중복 재시도 방지 및 복구 기준:** 디렉터리 fsync 실패를 이유로 동일 저장을 재시도할 경우 불필요한 Revision 불일치나 충돌이 발생하므로 재시도하지 않습니다. 프로세스 재시작 시에는 **디스크 파일에서 실제 읽어들인 Revision/SSoT를 기준으로 메모리 상태를 초기화**하며, 이전 메모리 상태를 디스크에 강제 재적용하지 않습니다.
3. **차등 내구성 계층 확립 (Durability Hierarchy: Option B 공식 채택):**
   - **Level 1 (미션 크리티컬 & 사용자 그래프 데이터 — SSoT 및 `user_graph.json`):**
     - 대상: `project_state.json` (구조 SSoT) 및 `user_graph.json` (사용자 생성 Custom Node/Edge, 메타데이터 패치, 영구 Tombstone).
     - 절차: 배타적 임시 파일 생성 $\rightarrow$ 데이터 기록 $\rightarrow$ 파일 `fsyncSync(tmpFd)` $\rightarrow$ 무결성 검증 $\rightarrow$ `renameSync` $\rightarrow$ 플랫폼별 디렉터리 동기화 절차 (POSIX: `fsyncSync(dirFd)` / Windows: 디렉터리 핸들 동기화 불가 시 가시성 확정 및 내구성 결과 분리).
     - **플랫폼별 디렉터리 동기화 결과 분리 및 상태값 명시 (P0-3 완결):**
       - **POSIX 표준 환경:** 파일 교체(`renameSync`) 후 부모 디렉터리 `fsyncSync(dirFd)`를 실행합니다. 디렉터리 fsync 성공 시 내구성 확정 `{ committed: true, durability: 'confirmed', revision }`, 실패 시 `{ committed: true, durability: 'unconfirmed', revision }`을 반환합니다.
       - **Windows (NTFS) 환경:** Windows 커널/런타임 특성상 디렉터리 FD에 대한 POSIX 식 `fsync`가 지원되지 않으므로 디렉터리 엔트리 플러시는 강제할 수 없습니다. 따라서 rename 성공 시 **커밋 가시성은 확정되었으나 파일시스템 레벨 디렉터리 플러시는 미확인**된 상태임을 명시적으로 반영하여 `{ committed: true, durability: 'unconfirmed', revision }`을 반환합니다. (단, rename 자체가 실패한 경우 미커밋 상태로 안전하게 중단됩니다).
     - 보장 한계의 사실적 기술: OS 파일시스템 마운트 옵션(writeback cache) 및 물리 스토리지 하드웨어의 전원 차단 보호 수준에 종속되며, 이를 초과하는 비현실적 "100% 절대 보장"은 주장하지 않습니다.
   - **Level 2 (프레젠테이션 세이프 & 고빈도 UI 레이아웃 — `layout.json`):**
     - 대상: `layout.json` (캔버스 노드 드래그 좌표, 뷰포트 줌/오프셋, 클러스터 수동 접힘).
     - 절차: 배타적 임시 파일 생성 $\rightarrow$ 데이터 기록 $\rightarrow$ 파일 `fsyncSync(tmpFd)` $\rightarrow$ `renameSync`. (부모 디렉터리 `fsync`는 60fps 캔버스 인터랙션의 I/O 병목 방지를 위해 의도적으로 생략).
     - 응답 및 손실 범위의 사실적 기술 (P1-1, P1-6 완결): 저장 성공 응답은 `{ committed: true, durability: 'presentation_safe', revision: newLayoutRevision }`으로 명확히 구분 반환합니다. 비정상 전원 차단 시 손실될 수 있는 데이터는 최근 캔버스 뷰포트 상태 및 디렉터리 엔트리가 디스크에 플래시되지 않은 최신 Layout 파일 교체분 전체가 될 수 있으며, SSoT 구조 데이터와 UserGraph는 Level 1으로 별도 보호됩니다.
4. **Windows 지원 범위 및 내구성 상태값 규약 (P0-3 완결):**
   - 동일 파일시스템 내 `fs.renameSync` 호출을 통해 교체 작업의 성공·실패를 엄격히 구분합니다.
   - Windows 환경에서 디렉터리 fsync는 수행할 수 없으므로, Level 1 성공 응답의 durability는 결정론적으로 `'unconfirmed'`로 설정되며, POSIX와 동등한 디렉터리 디스크 플래시 내구성을 주장하지 않습니다.
   - rename 실패 시 기존 파일 보존 여부를 디스크에서 직접 확인한 범위만 보고하며, 실패 시에는 메모리 상태를 롤백하지 않고 기존 상태를 유지합니다.
5. **SSoT 읽기·교체 직렬화 보장 (§3.3 `SSoTTaskQueue` 연계):**
   - 분석기의 SSoT 파일 전체 읽기 및 JSON 파싱(Working Copy 생성)은 §3.3의 `SSoTTaskQueue` 내부에서 단독 실행됩니다.
   - Re-Bootstrap의 원자적 파일 교체 또한 동일 큐에서 직렬 실행되므로, SSoT를 읽고 파싱하는 도중에 파일이 교체되는 TOCTOU 충돌이 원천 배제됩니다.
   - 파싱 완료 후 Working Copy는 독립 인메모리 객체가 되므로, 이후의 분석 연산은 큐 밖에서 Re-Bootstrap과 독립적으로 안전하게 실행됩니다.

### 4.2 오버레이 로드 필터링 및 컬렉션 단위 전수 저장·병합·보존 경계 (P0-1, P0-2 완결)

1. **로드 시 비파괴적 필터링 (Graceful Filtering on Load):**
   - 캔버스 로드 시 현재 SSoT(`project_state.json`) 및 활성 `customNodes`와 대조하여 다음 항목을 **화면 표시에서만 자동 제외(Ignore & Filter)**합니다:
     - SSoT에서 사라진 노드에 대한 `modifiedNodes` 및 사라진 엣지에 대한 `modifiedEdges`.
     - **Custom Node Layout 좌표 필터링:** `layout.json`의 좌표 중, 현재 활성 상태인 SSoT 노드 및 활성 `customNodes`에 속하지 않거나, Tombstone(`deletedNodeIds`)에 포함된 노드의 좌표는 렌더링에서 완전히 제외합니다.
     - 사라진 클러스터 접힘 상태 및 양 끝점 중 하나라도 결손된 고아 Custom Edge 화면 표시 제외.
   - **과거 Custom ID와 신규 SSoT ID 충돌 시 런타임 투영 격리 정책 (SSoT-Precedence Runtime Projection — P0-3 완결):**
     - 과거 `customNodes`에 기록된 ID가 Re-Bootstrap 이후 신규 SSoT 노드 ID와 충돌하거나, 과거 `customEdges`의 ID가 신규 SSoT 엣지 ID와 충돌할 경우:
       - **디스크 원본 보존:** 디스크 상의 `customNodes` 및 `customEdges`는 절대 자동 삭제·수정하지 않고 온전히 보존(Preserve)합니다.
       - **SSoT 구조적 기준 우선:** 동일 ID 충돌 시 렌더링 엔진과 그래프 모델은 **SSoT 엔티티(`project_state.json`)를 구조적 기준으로 절대 우선**하여 캔버스에 투영합니다.
       - **충돌 Custom 엔티티 렌더링 격리:** 충돌이 발생한 Custom Node 및 Custom Edge는 캔버스 렌더링 대상에서 완전히 격리(Ignore & Isolate)하며, Custom Edge 끝점 해석 시에도 SSoT 노드를 기준으로 연결합니다.
       - **진단 상태 노출 및 수동 정리:** 시스템은 이 충돌 사실을 사용자에게 진단 경고(`WARNING: Custom entity ID collided with active SSoT entity; custom entity isolated`)로 상태 표시줄/로그에 노출하며, 사용자가 명시적 정리 액션을 실행하기 전까지 임의 변조하지 않습니다.
   - **디스크 원본 보존:** 로드 시점에는 디스크 상의 `user_graph.json`이나 `layout.json`을 절대 자동 삭제하거나 수정하지 않습니다 (일시적 브랜치 전환 시 사용자 편집 데이터 영구 보존).
2. **컬렉션별 세부 저장 연산 및 항목·필드 단위 병합 규약 (In-Place Merge Semantics):**
   일반 저장(Normal Save) 시 웹뷰에서 전달된 부분 변경 사항을 디스크 기존 컬렉션과 병합할 때, 전체를 덮어쓰거나 미포함 항목을 임의 삭제하는 것을 엄격히 금지하며 아래 규칙을 따릅니다:

   | 컬렉션 명 | 병합 단위 및 일반 저장 연산 (Merge Granularity) | 디스크 미수정 항목 처리 (Untouched Entries) |
   |:---|:---|:---|
   | **`positions`** | **항목 단위 UPSERT:** 사용자가 드래그/이동한 노드의 `{ x, y }` 전체 교체 | **PRESERVE:** 비활성 노드 좌표를 포함한 기존 좌표 디스크 보존 |
   | **`clusters`** | **항목 단위 UPSERT:** 사용자가 토글한 클러스터의 `{ collapsed }` 전체 교체 | **PRESERVE:** 현재 SSoT에 없는 클러스터라도 디스크 보존 (재수집 시 복원) |
   | **`modifiedNodes`** | **필드 단위 MERGE:** 사용자 편집 필드만 병합, `null` 지정 필드는 삭제 | **PRESERVE:** 수정되지 않은 다른 노드 메타데이터 패치 디스크 보존 |
   | **`modifiedEdges`** | **필드 단위 MERGE:** 사용자 편집 필드만 병합, `null` 지정 필드는 삭제 | **PRESERVE:** 수정되지 않은 다른 엣지 메타데이터 패치 디스크 보존 |
   | **`customNodes`** | **항목 단위 UPSERT / REMOVE:** 추가·수정된 노드 갱신 / 삭제된 노드는 제거 | **PRESERVE:** 삭제 대상이 아닌 기존 Custom Node 디스크 보존 |
   | **`customEdges`** | **항목 단위 UPSERT / REMOVE:** 추가·수정된 엣지 갱신 / 삭제된 엣지는 제거 | **PRESERVE:** 삭제 대상이 아닌 기존 Custom Edge 디스크 보존 |
   | **`deletedNodeIds`** | **APPEND (Set 중복 제거):** 새로 삭제된 SSoT 및 Custom 노드 ID 등록 | **PRESERVE:** 기존 Tombstone 영구 보존 (Custom UUID 제거 불가) |
   | **`deletedEdgeIds`** | **APPEND (Set 중복 제거):** 새로 삭제된 SSoT 및 Custom 엣지 ID 등록 | **PRESERVE:** 기존 Tombstone 영구 보존 (Custom UUID 제거 불가) |

3. **필드 단위 세부 병합, 삭제 센티넬 및 빈 패치 프루닝 규칙 (P0-2, P1-3 완결):**
   - **IPC 입력 DTO와 디스크 스키마 분리:** JSON 직렬화 시 `undefined`가 누락되는 문제를 해결하기 위해, 웹뷰 IPC 요청 DTO에서는 **`null`을 명시적 삭제 센티넬(Deletion Sentinel)**로 정의합니다:
     - DTO 필드 생략 (`undefined`): 기존 디스크 값을 온전히 보존(Preserve).
     - DTO 필드에 유효 값 전달: 해당 필드 값 갱신(Update).
     - DTO 필드에 `null` 전달: 디스크 패치 객체에서 해당 필드를 완전히 제거 (`delete patch[field]`). (`label: null`, `description: null`, `weight: null`, `status: null` 모두 지원).
   - **`customProperties` 개별 속성 키 삭제:**
     - `customProperties[key]`에 원시 값 전달 시: 해당 속성 추가/갱신.
     - `customProperties[key]`에 `null` 전달 시: `delete customProperties[key]`로 해당 속성 키만 제거.
   - **디스크 저장 무결성:** 디스크에 저장되는 `NodeMetadataPatch` / `EdgeMetadataPatch` 객체는 `null` 필드를 영구히 포함하지 않으며, 순수 원시 타입 필드만 보존됩니다.
   - **빈 패치 자동 프루닝 조건 (Empty Patch Pruning):**
     - **노드 패치 프루닝:** `patch.label === undefined && patch.description === undefined && (!patch.customProperties || Object.keys(patch.customProperties).length === 0)` 만족 시, `delete modifiedNodes[nodeId]` 실행.
     - **엣지 패치 프루닝:** `patch.label === undefined && patch.weight === undefined && patch.status === undefined` 만족 시, `delete modifiedEdges[edgeId]` 실행.
4. **Tombstone 생명주기 및 Re-Bootstrap 이후 처리 (P0-1, P0-2, P0-4, P1-3 완결):**
   - **SSoT 노드/엣지 복원 (Restore SSoT Entity):** SSoT 노드·엣지는 소스 코드 형상에 기반하므로, 사용자가 복원 액션을 실행할 경우 `deletedNodeIds` / `deletedEdgeIds`에서 해당 ID를 제거(REMOVE)하는 것이 허용됩니다.
   - **기존 디스크 Tombstone의 역사적 보존 vs 신규 삭제 입력 검증 분리 (P0-2 완결):**
     - **기존 디스크 Tombstone:** Re-Bootstrap으로 인해 소스 코드에서 사라진 과거 SSoT 노드/엣지 ID나 과거 커스텀 ID라도, 디스크에 이미 기록된 Tombstone은 역사적 삭제 상태로 영구 보존(Preserve)되며 일반 저장 시 검증 실패 사유가 되지 않습니다.
     - **신규 삭제 입력 검증:** IPC 요청으로 새로 들어온 Tombstone 추가 항목은, 삭제 요청 처리 시점의 `activeValidationSSoT` 또는 활성 Custom Graph에 실제로 존재하는 유효한 ID인지 검증을 통과해야만 등록됩니다.
   - **Custom 노드/엣지 UUID의 영구 사망 및 리셋 시 영구 보존 규약 (Option A 채택 — P0-1, P0-2, P0-4, P1-2 완결):**
     - 커스텀 노드·엣지의 UUID는 일회용 고유 식별자입니다.
     - **`user::` 전용 네임스페이스 예약 및 기존 SSoT 호환성 사전 검증 (P1-2, P1-4 완결):**
       - `user::` 접두사는 **오직 사용자 생성 Custom 엔티티(Custom Node, Custom Edge)만을 위한 전용 예약 네임스페이스**로 확정합니다. 소스 코드 파서 및 Bootstrap 엔진은 어떠한 경우에도 `user::` 접두사로 시작하는 SSoT 노드·엣지 ID를 생성할 수 없습니다 (스키마 수준 강제).
       - **기존 데이터 호환성 검증 및 마이그레이션 방어 (P1-4 완결):** Bootstrap 엔진의 토폴로지 검증 및 Re-Bootstrap 파싱 단계에서 `project_state.json`에 `user::` 접두사를 가진 SSoT ID가 1건이라도 발견될 경우, 이는 유효하지 않은 SSoT로 판정하여 Re-Bootstrap 저장을 즉시 거부(`REJECTED_RESERVED_NAMESPACE_VIOLATION`)합니다. 기존 데이터베이스/프로젝트가 해당 접두사를 사용하지 않는다는 점을 수집기 검증 단계에서 사전 입증하며, 출처가 불명확한 기존 ID를 임의로 Custom으로 오인 분류하지 않습니다.
     - 커스텀 노드·엣지가 삭제되어 `deletedNodeIds` / `deletedEdgeIds`에 등록되면, 해당 UUID는 **어떠한 복원 액션에서도 Tombstone 배열에서 제거되지 않고 영구 보존**됩니다.
     - 사용자가 UI에서 "삭제된 커스텀 노드 복원"을 수행할 경우, 기존 UUID를 부활시키는 것이 아니라 **내용을 복제한 완전히 새로운 RFC 4122 UUID v4를 발급하여 신규 생성**합니다.
     - 따라서 `deletedNodeIds`에 등록된 Custom UUID는 영구 보존되므로, 동일 UUID로의 신규 생성 시도는 항상 `deletedNodeIds.includes(newId)`에 의해 결정론적으로 거부(`REJECTED_REUSED_UUID`)됩니다.
     - **리셋 시 활성 Custom UUID의 Tombstone 전환 및 영구 보존 순서 (P0-2 완결):**
       기존 Tombstone만 보존하고 활성 Custom Node/Edge를 단순히 컬렉션에서 지우기만 하면, 리셋 이후 동일 UUID가 재사용될 수 있는 결함이 발생합니다. 따라서 `handleResetProjectState` 실행 시 반드시 다음 6단계 순서로 후보 객체를 생성하여 영구 보존을 완결합니다:
       1. **활성 Custom Node Tombstone 등록:** 리셋 시점에 활성 상태인 모든 `customNodes`의 ID를 `deletedNodeIds`에 추가합니다.
       2. **활성 Custom Edge Tombstone 등록:** 리셋 시점에 활성 상태인 모든 `customEdges`의 ID를 `deletedEdgeIds`에 추가합니다.
       3. **기존 Custom UUID Tombstone 보존:** `id.startsWith('user::')`를 만족하는 과거 Custom UUID Tombstone은 전수 유지합니다.
       4. **SSoT Tombstone 초기화:** 소스 코드 형상 복귀 원칙에 따라 SSoT 노드·엣지의 ID만 Tombstone에서 제거합니다.
       5. **Custom 및 패치 컬렉션 초기화:** `customNodes = {}`, `modifiedNodes = {}`, `customEdges = []`, `modifiedEdges = {}`로 초기화합니다.
       6. **후보 객체 검증 및 원자적 커밋:** 후보 객체의 전체 무결성 검증 통과 시 Level 1 원자적 커밋을 수행합니다.
     - **Reset 큐 배리어(Queue Barrier) 및 완전한 상태 기반 멱등성 규약 (P1-1, P1-2 완결):**
       - **원자적 복합 Reset을 위한 큐 배리어 (Atomic Reset Queue Barrier — P1-1 완결):**
         `handleResetProjectState`는 두 개의 독립 파일 커밋 사이에 일반 저장 요청이 끼어들어 정합성이 파괴되는 것을 원천 차단하기 위해 **명시적 큐 배리어(`resetInProgressBarrier: boolean`)**를 확립합니다:
         1. Reset 시작 시 Host 내부에서 `resetInProgressBarrier = true`를 선언하고, 단일 직렬 실행 컨텍스트 내에서 `RESET_USER_GRAPH` 커밋과 `RESET_LAYOUT` 커밋을 **사이에 다른 일반 요청을 일체 끼워넣지 않고 연속 실행**합니다.
         2. 배리어가 활성화되어 있는 동안 웹뷰 등에서 유입되는 모든 일반 저장 IPC 요청(`UPDATE_NODE`, `UPDATE_POSITION` 등)은 `OverlaySaveQueue` 진입점에서 즉시 대기(Enqueue)되거나 배리어 완료 시까지 블로킹됩니다.
         3. 두 파일 커밋이 모두 완료되거나, 중간 실패 발생 시 배리어를 즉시 해제(`resetInProgressBarrier = false`)하고 대기 중인 큐 항목을 순차 처리합니다.
       - **완전한 상태 기반 멱등성 검사 (Complete State-Based Idempotence — P1-2 완결):**
         프로세스 비정상 종료 후 재시작 시 성공 상태가 메모리에 없더라도, **각 파일의 현재 디스크 상태를 기반으로 멱등성을 완전하게 판정**합니다:
         - `user_graph.json`: `customNodes`, `modifiedNodes`, `customEdges`, `modifiedEdges`가 모두 비어있고, `deletedNodeIds` 및 `deletedEdgeIds`에 비-`user::` (SSoT) ID가 전혀 없는 경우 $\rightarrow$ **"이미 Reset 상태"**로 판정.
         - `layout.json` (뷰포트 포함 완전 검증 — P1-2 완결): `positions`가 비어있고, `clusters`가 비어있으며, **동시에 `view.zoom === 1.0` 및 `view.offset.x === 0` 및 `view.offset.y === 0`을 엄격히 만족**하는 경우 $\rightarrow$ **"이미 Reset 상태"**로 판정.
         - 재시작 후 사용자가 Reset을 다시 요청하거나 재시도할 때, **이미 Reset 상태인 파일은 다시 디스크에 쓰지 않고 Revision 증가도 유발하지 않으며(No-op 성공)**, 오직 Reset 상태가 아닌 파일만 단독 커밋하여 Revision을 정확히 `+ 1` 단조 증가시킵니다. 이를 통해 어떠한 크래시나 재시작 상황에서도 Revision의 불필요한 증가 없이 완벽한 멱등성을 보장합니다.
5. **일반 저장과 명시적 정리 액션의 엄격한 분리:**
   - **일반 저장 (Normal Save):** 사용자의 일상적인 편집 작업 저장. 위 2~4항의 규칙만 적용되며, SSoT에 존재하지 않는 비활성 참조는 절대 자동 삭제되지 않습니다.
   - **명시적 정리 액션 (Explicit Clean-up Action):** 사용자가 UI에서 **"비활성 오버레이 정리(Clean-up Obsolete Overlays)"**를 명시적으로 클릭하고 확인한 경우에 한해, 현재 활성 SSoT 및 `customNodes`에 매핑되지 않는 비활성 `positions`, `clusters`, `modifiedNodes`, `modifiedEdges`를 일괄 영구 제거합니다.
6. **Layout 런타임 값 유효성 검증 (Runtime Validation on Save):**
   - `positions[*].x`, `positions[*].y`: 유한한 숫자(`Number.isFinite(v) === true`) 검사 필수. `NaN`, `Infinity`, 문자열 좌표는 즉시 거부.
   - `view.zoom`: 유한한 숫자이며 허용 범위(`0.001 <= zoom <= 10.0`) 검증.
   - `view.offset.x`, `view.offset.y`: 유한한 숫자(`Number.isFinite`) 검증.
   - `clusters[*].collapsed`: 엄격한 `boolean`(`typeof v === 'boolean'`) 검증. SSoT에 없는 클러스터 ID도 위 타입 규칙을 만족하면 디스크에 안전하게 보존.

### 5.2 Layout / UserGraph 독립 Revision OCC 및 Resync Latch 상태 머신 (P1-1, P1-2, P1-4 완결)

1. **독립 Revision 상태 및 오버플로 차단 (Independent Revision & Overflow Guard):**
   - 두 오버레이는 서로 다른 파일이므로 OCC Revision 상태를 완전히 분리하여 관리합니다:
     - `LayoutData`: `currentLayoutRevision` ($0 \le \text{rev} \le \text{Number.MAX\_SAFE\_INTEGER}$)
     - `UserGraphData`: `currentUserGraphRevision` ($0 \le \text{rev} \le \text{Number.MAX\_SAFE\_INTEGER}$)
   - **오버플로 안전 가드:** 저장 연산 진입 시 대상 파일의 Revision에 대해 반드시 다음을 검사하며, 위반 시 저장을 즉시 거부(`REJECTED_REVISION_OVERFLOW`)합니다:
     $$\text{currentLayoutRevision} < \text{Number.MAX\_SAFE\_INTEGER} \quad \text{혹은} \quad \text{currentUserGraphRevision} < \text{Number.MAX\_SAFE\_INTEGER}$$
2. **Host 내부 `OverlaySaveQueue`를 통한 9단계 엄격 직렬 저장 절차 (Strict 9-Step Execution Sequence — P0-1, P0-2, P0-3, P0-5 완결):**
   웹뷰에서 전달되는 저장 IPC 요청은 대상 파일 식별자(`target: 'layout' | 'user_graph'`), 클라이언트의 기준 Revision(`expectedRevision: number`), 그리고 구체적인 변경 행위 DTO(`requestDelta: OverlayActionDTO`)를 포함하며, `OverlaySaveQueue`에서 순차적으로 1개씩 다음 9단계를 엄격히 준수하여 직렬 처리됩니다:
   - **Step 1 — Latch 상태 확인:** 해당 대상의 Latch(`layoutResyncLatch` 또는 `userGraphResyncLatch`)가 활성화된 경우 즉시 저장을 거부(`REJECTED_RESYNC_IN_PROGRESS`). (타겟이 다른 저장은 블로킹되지 않음).
   - **Step 2 — 디스크 최신 Revision 대조 (외부 비동기 쓰기 감지):** 디스크 파일 헤더의 Revision을 읽어 Host 인메모리 Revision(`currentLayoutRevision` 또는 `currentUserGraphRevision`)과 불일치할 경우, 외부 쓰기 발생으로 판정하고 해당 파일의 Resync Latch를 즉시 활성화한 후 최신 디스크 데이터를 웹뷰로 강제 푸시 및 거부.
   - **Step 3 — OCC `expectedRevision` 검증:** `expectedRevision`이 Host 인메모리 최신 Revision과 불일치할 경우(`expectedRevision !== currentRevision`), 저장을 즉시 거부하고 해당 파일의 Resync Latch를 활성화한 후 최신 상태 푸시.
   - **Step 4 — 검증용 기준 SSoT 스냅샷 고정 (`activeValidationSSoT` Capture):** `activeValidationSSoT` 참조를 로컬 변수로 캡처하여 검증 중 Re-Bootstrap이 동시 실행되더라도 이번 저장 트랜잭션의 검증 기준선이 흔들리지 않도록 고정.
   - **Step 5 — Tier 1 기존 디스크 데이터 구조적 무결성 검증:** 디스크에서 로드된 기존 데이터에 대해 스키마 형식, 원시 타입, 문자열 길이, 키 프로토타입 오염, UUID v4 형식, Custom Edge 끝점의 Self-loop 금지 등 구조적 무결성만 검증 (§5.3.2 Tier 1). (현재 SSoT와 대조하지 않음).
   - **Step 6 — Tier 2 신규 IPC `requestDelta` 검증 및 타겟 매칭:** 이번 IPC 요청으로 전달된 명시적 행위 DTO(`requestDelta`)가 `target`과 올바르게 일치하는지 검증하고(`target === 'layout'`이면 `LayoutActionDTO`, `target === 'user_graph'`이면 `UserGraphActionDTO`), Step 4에서 캡처한 `activeValidationSSoT` 및 후보 노드 집합(`candidateNodeSet`)을 기준으로 유효성을 검증 (§5.3.2 Tier 2).
   - **Step 7 — 후보 객체 생성, 최종 상태 불변식 검증 및 Revision 단조 증가 (P1-3, P1-6 완결):**
     - 유효성이 입증된 델타를 기존 디스크 데이터에 병합하여 단일 불변 후보 객체(`candidateData`) 생성.
     - **공통 필수 단계 — 최종 후보 객체 스키마 및 불변식 전수 검증 (Final Candidate Validation — P1-3, P1-6 완결):**
       Tier 1(기존) 및 Tier 2(입력) 검증과 별개로, 디스크 커밋 직전에 최종 완성된 `candidateData` 전체에 대해 다음 공통 불변식을 반드시 전수 재검증하며, 1건이라도 위반 시 후보 객체를 즉시 폐기하고 저장을 거부(`REJECTED_FINAL_CANDIDATE_INVALID`)합니다:
       - **최종 `customProperties` 키 개수 엄격 제한 (P1-3 완결):** 모든 `customNodes` 및 `modifiedNodes` 엔트리에 대해, 기존 속성과 패치가 최종 병합된 객체의 키 개수가 **50개 이하(`Object.keys(obj.customProperties).length <= 50`)**인지 전수 검증.
       - **원시 타입 및 유한성 전수 재검증:** 모든 속성 값이 원시 타입(`string | number | boolean`)이며 숫자는 `Number.isFinite`를 만족하는지 검증.
       - **키-ID 일치 및 중복 배제:** `customNodes`의 모든 엔트리에 대해 `key === node.id` 일치 여부 및 `customEdges` 배열 내 ID 중복 부재 재검증.
       - **Tombstone 상호 배타성 전수 검증:** `deletedNodeIds`와 (`customNodes` $\cup$ `modifiedNodes`), 그리고 `deletedEdgeIds`와 (`customEdges` $\cup$ `modifiedEdges`) 간에 교집합이 정확히 0개인지 최종 확인.
     - 검증 통과 시에만 대상 파일의 새 Revision을 결정론적으로 단조 증가: $\text{newRevision} = \text{currentRevision} + 1$.
   - **Step 8 — 디스크 원자적 영속화 커밋 (Atomic Persistence Commit):**
     - `layout.json` (Level 2): 배타적 임시 파일(`O_CREAT | O_EXCL`) 생성 $\rightarrow$ 데이터 기록 $\rightarrow$ `fsyncSync` $\rightarrow$ `renameSync`.
     - `user_graph.json` (Level 1): 배타적 임시 파일 생성 $\rightarrow$ 데이터 기록 $\rightarrow$ `fsyncSync` $\rightarrow$ `renameSync` $\rightarrow$ 부모 디렉터리 `fsyncSync`.
   - **Step 9 — Host 인메모리 Revision 확정 갱신 및 웹뷰 응답 반환:**
     - 디스크 교체 성공 직후 Host 메모리의 `currentLayoutRevision` 또는 `currentUserGraphRevision`을 `newRevision`으로 확정 갱신.
     - 웹뷰로 저장 성공 응답 반환:
       - `layout.json`: `{ committed: true, durability: 'presentation_safe', revision: newRevision }`
       - `user_graph.json`: `{ committed: true, durability: 'confirmed' | 'unconfirmed', revision: newRevision }`
     - 다음 큐 항목 실행. 저장이 실패한 경우 메모리 Revision은 갱신되지 않으며 임시 파일만 안전하게 정리됩니다.
3. **Resync Latch 결정론적 상태 머신 및 외부 변경 감지 한계 (P1-2, P1-4 완결):**
   - **외부 변경 감지 경로 및 한계 (P1-4 완결):** Host 내부의 Re-Bootstrap 완료 이벤트 핸들러 및 파일 저장 이벤트가 주 알림 신호로 동작하며, 저장 요청 진입 시 디스크 Revision 대조를 통해 요청 이전에 발생한 변경을 포착합니다. 단, 파일 이벤트는 OS 환경에 따라 누락될 수 있고 Revision 대조와 파일 교체 사이의 외부 쓰기를 물리적으로 막는 것은 아니므로, SYNAPSE 협력 프로세스 외부의 비인가 임의 파일 수정까지 완전 차단함을 주장하지 않습니다.
   - **Latch 활성화 및 강제 푸시:** Revision 불일치 감지 시 해당 대상의 Latch(`layoutResyncLatch` 또는 `userGraphResyncLatch`)를 `true`로 설정하고, 디스크의 최신 데이터와 최신 Revision을 웹뷰로 강제 푸시합니다.
   - **Latch 활성 중 신규 요청 차단:** Latch가 활성화된 동안 해당 대상을 향한 모든 신규 저장 요청은 큐 진입 즉시 거부(`REJECTED_RESYNC_IN_PROGRESS`)됩니다.
   - **최신 상태 재전송:** Latch 활성 대기 중 외부 재수집 등으로 인해 디스크 데이터나 Host Revision이 변경될 경우, Host는 변경된 최신 상태를 웹뷰로 즉시 재푸시합니다.
   - **엄격 일치 해제 조건 (Deterministic Release Condition):** 웹뷰가 상태를 반영한 후 반환하는 `{ type: 'RESYNC_ACK', target: 'layout' | 'user_graph', resyncRevision: number }` 메시지에 대해:
     - `target === 'layout'`: $\text{ack.resyncRevision} === \text{host.currentLayoutRevision}$ 일치 시에만 `layoutResyncLatch = false` 해제.
     - `target === 'user_graph'`: $\text{ack.resyncRevision} === \text{host.currentUserGraphRevision}$ 일치 시에만 `userGraphResyncLatch = false` 해제.
     - 과거 구 버전 ACK(`ack.resyncRevision < currentRevision`)는 무시되며 Latch가 유지됩니다.
   - **Fail-Closed 원칙:** 디스크 읽기 실패 또는 웹뷰 재초기화 중에는 Latch가 영구 유지되어 불완전한 상태에서의 추가 저장을 원천 차단합니다.

### 5.3 ID 무결성, 객체 키 보안 및 2계층 런타임 검증 (Two-Tier Validation — P0-1, P0-2, P0-3, P0-4, P0-5, P1-5, P1-6 완결)

1. **엄격한 스키마 Allowlist 및 프로토타입 오염 차단 (P1-5 완결):**
   - **Allowlist 검증:** JSON 파싱 직후 스키마에 정의되지 않은 알 수 없는 필드(Unknown properties)가 포함된 객체는 즉시 저장을 거부(`REJECTED_UNKNOWN_PROPERTY`)합니다.
   - **프로토타입 오염 차단:** 모든 객체형 컬렉션(`positions`, `clusters`, `modifiedNodes`, `modifiedEdges`, `customNodes`, `customProperties`)은 `Object.prototype.hasOwnProperty.call(obj, key)`로 own property를 검증하며, **`__proto__`, `constructor`, `prototype` 키가 포함된 모든 요청은 즉시 저장을 거부**(`REJECTED_PROTOTYPE_POLLUTION`)합니다.
   - 모든 컬렉션 키는 유효한 문자열(1 ~ 512자)이어야 합니다.
2. **명시적 행위 DTO 규약, 타겟 매칭 및 2계층 검증 모델 확립 (Explicit Delta Action DTOs & Two-Tier Validation — P0-1, P0-5, P1-2 완결):**
   웹뷰는 전체 오버레이 컬렉션을 통째로 보내지 않으며, 구체적 변경 작업 단위를 나타내는 명시적 행위 DTO(`requestDelta`)를 Host로 전송합니다.
   
   - **`target`과 `requestDelta`의 허용 조합 및 유효성 매칭 (P0-1 완결):**
     - `target === 'layout'`: 오직 `LayoutActionDTO`(`UPDATE_POSITION`, `UPDATE_CLUSTER`, `UPDATE_VIEWPORT`, `RESET_LAYOUT`)만 허용되며, 다른 유형 전달 시 즉시 `REJECTED_INVALID_TARGET_ACTION` 에러로 거부.
     - `target === 'user_graph'`: 오직 `UserGraphActionDTO`(`UPDATE_NODE`, `DELETE_NODES`, `UPDATE_EDGE`, `DELETE_EDGES`, `ADD_CUSTOM_NODE`, `UPDATE_CUSTOM_NODE`, `ADD_CUSTOM_EDGE`, `UPDATE_CUSTOM_EDGE`, `RESET_USER_GRAPH`)만 허용되며, 다른 유형 전달 시 즉시 거부.
   
   - **Tier 1 — 기존 디스크 데이터 구조적 무결성 검증 (Structural Integrity & Set Normalization):**
     - 디스크에서 파싱된 기존 데이터(`existingDiskData`)에 대해 원시 타입, 문자열 길이, 키 프로토타입 오염, RFC 4122 UUID v4 형식(`^user::...`), Custom Edge 끝점의 Self-loop(`from === to`) 금지 등 **구조적 무결성만 검증**합니다.
     - **SSoT 대조 배제:** Re-Bootstrap으로 인해 소스 코드에서 사라진 과거 SSoT 노드/엣지 패치(`modifiedNodes`, `modifiedEdges`), 과거 Custom Edge 끝점, 과거 Tombstone은 **현재 SSoT와 대조하지 않고 구조적 유효성만 만족하면 온전히 디스크에 보존**합니다. 기존 `customNodes`에 대해서도 현재 SSoT와의 충돌 여부를 재검사하지 않음으로써 Re-Bootstrap으로 인한 기존 오버레이 저장 거부 문제를 원천 방지합니다.
     - **Tombstone 중복 정규화 정책 (In-Memory Set Normalization — P1-2 완결):**
       - 기존 디스크의 `deletedNodeIds` 및 `deletedEdgeIds`에 과거 중복 ID가 존재하더라도, 이를 파일 손상으로 간주하여 저장을 거부하지 않고 온건하게 수용(Tolerant)합니다.
       - **변환 및 직렬화 규칙:** 디스크 파싱 직후 즉시 `new Set(deletedNodeIds)` 및 `new Set(deletedEdgeIds)`로 변환하여 내부 $O(1)$ 중복 제거 및 고속 검색 자료구조로 사용합니다.
       - 신규 저장 시 디스크에 직렬화할 때에는 `Array.from(set)`으로 정규화하여 중복이 제거된 깨끗한 배열로 디스크에 영속화합니다.
   
   - **Tier 2 — 신규 IPC `requestDelta` 검증 및 후보 노드 집합 (`candidateNodeSet`):**
     - 이번 IPC 요청으로 전달된 신규 변경분(`requestDelta`)에 대해서만 Step 4에서 캡처한 `activeValidationSSoT` 및 후보 노드 집합을 기준으로 엄격히 검증합니다:
     - **후보 노드 집합 산출 (`candidateNodeSet`):**
       $$\text{candidateNodeSet} = \Big(\text{existingCustomNodes} \cup \text{newCustomNodes} \setminus \text{deletedNodes}\Big) \cup \text{activeValidationSSoT.nodeIds}$$
     - **델타별 정밀 검증 및 필드별 변경·삭제·보존 규칙 (P0-1, P1-3 완결):**
       - **`UPDATE_POSITION` (Layout):**
         - `position.nodeId` (문자열 1 ~ 512자) 및 `Number.isFinite(position.x)`, `Number.isFinite(position.y)` 검증.
         - 병합: `positions[nodeId] = { x: position.x, y: position.y }` (기존 다른 노드 좌표 보존).
       - **`UPDATE_CLUSTER` (Layout):**
         - `cluster.clusterId` (문자열 1 ~ 512자) 및 `typeof cluster.collapsed === 'boolean'` 검증.
         - 병합: `clusters[clusterId] = { collapsed: cluster.collapsed }` (기존 다른 클러스터 보존).
       - **`UPDATE_VIEWPORT` (Layout):**
         - 유한한 숫자 `0.001 <= view.zoom <= 10.0` 및 `Number.isFinite(view.offset.x)`, `Number.isFinite(view.offset.y)` 검증.
         - 병합: `view` 객체 전체 갱신.
       - **`RESET_LAYOUT` (Layout):**
         - `positions = {}`, `clusters = {}`, `view = { zoom: 1.0, offset: { x: 0, y: 0 } }`로 초기화 커밋.
       - **`ADD_CUSTOM_NODE` (UserGraph):**
         - `node.id`는 반드시 RFC 4122 UUID v4 규격을 준수해야 함 (`^user::...`).
         - `node.label`: 필수 문자열 (1 ~ 256자, 빈 문자열 거부).
         - `node.customProperties`: 선택 객체이며 최대 50개 키 제한, 각 값은 원시 타입(`string | number | boolean`), 숫자 값은 반드시 `Number.isFinite` 검증.
         - **SSoT 충돌 검증 (Tier 2 한정):** `node.id`가 `activeValidationSSoT.nodeIds`에 포함되어 있지 않아야 함 (`!activeValidationSSoT.nodeIds.has(node.id)`).
         - **UUID 영구 재사용 차단:** `!deletedNodeIds.has(node.id)` 및 `!existingCustomNodes.has(node.id)` 검증.
         - 병합: `customNodes[node.id] = { id: node.id, label: node.label, customProperties: node.customProperties }`.
       - **`UPDATE_CUSTOM_NODE` (UserGraph — P0-1, P1-3 완결):**
         - `nodeId`가 `existingCustomNodes`에 존재해야 하며, `deletedNodeIds`에 없어야 함.
         - `patch.label`: 제공 시 문자열 1 ~ 256자 검증 (빈 문자열 거부).
         - `patch.customProperties`: 제공 시 키별 원시 타입 및 숫자 유한성(`Number.isFinite`) 검증, 전체 키 개수 50개 이하 제한.
         - 필드 병합: `patch.label` 제공 시 갱신, `patch.customProperties` 내 각 키는 값 전달 시 갱신, `null` 전달 시 `delete customProperties[key]`로 키 삭제. 생략된 필드는 온전히 디스크 보존.
       - **`ADD_CUSTOM_EDGE` (UserGraph):**
         - `edge.id`는 반드시 RFC 4122 UUID v4 규격을 준수해야 함 (`^user::...`).
         - `edge.from !== edge.to` (Self-loop 금지, 각 1 ~ 512자).
         - `edge.type`: 제공 시 문자열 1 ~ 64자 (빈 문자열 거부).
         - `edge.label`: 제공 시 문자열 0 ~ 256자.
         - **끝점 실존 검증:** `candidateNodeSet.has(edge.from) && candidateNodeSet.has(edge.to)` 만족 필수.
         - `edge.from` 및 `edge.to`가 `deletedNodeIds`에 포함되지 않아야 함.
         - `!deletedEdgeIds.has(edge.id)` 및 기존 `customEdges`에 동일 ID가 없어야 함.
         - 병합: `customEdges.push(edge)`.
       - **`UPDATE_CUSTOM_EDGE` (UserGraph — P0-1, P1-3 완결):**
         - `edgeId`를 가진 엣지가 `existingCustomEdges`에 존재해야 하며, `deletedEdgeIds`에 없어야 함.
         - `patch.type`: 문자열 전달 시 1 ~ 64자 검증(빈 문자열 거부) 및 갱신, `null` 전달 시 필드 삭제 (`delete`).
         - `patch.label`: 문자열 전달 시 0 ~ 256자 검증 및 갱신, `null` 전달 시 필드 삭제 (`delete`).
         - 생략된 필드는 온전히 디스크 보존.
       - **`UPDATE_NODE` (UserGraph — P1-3 완결):**
         - `nodeId`가 `activeValidationSSoT.nodeIds`에 존재해야 하며, `deletedNodeIds`에 없어야 함.
         - `patch.label`: 제공 시 문자열 1 ~ 256자 검증 (null은 삭제).
         - `patch.description`: 제공 시 문자열 0 ~ 2048자 검증 (null은 삭제).
         - `patch.customProperties`: 제공 시 최대 50개 키 제한, 숫자 값 `Number.isFinite` 검증 (null은 해당 키 삭제).
         - 병합: §4.2.3 필드 단위 MERGE 적용 (`null`은 필드 삭제, 빈 패치 시 프루닝).
       - **`UPDATE_EDGE` (UserGraph — P1-3 완결):**
         - `edgeId`가 `activeValidationSSoT.edgeIds`에 존재해야 하며, `deletedEdgeIds`에 없어야 함.
         - `patch.label`: 제공 시 문자열 0 ~ 256자 검증 (null은 삭제).
         - `patch.weight`: 제공 시 반드시 유한한 숫자(`Number.isFinite(patch.weight) === true`) 및 `patch.weight >= 0` 검증 (null은 삭제).
         - `patch.status`: 제공 시 `'proposed' | 'confirmed'` 허용 (null은 삭제).
         - 병합: §4.2.3 필드 단위 MERGE 적용 (`null`은 필드 삭제, 빈 패치 시 프루닝).
       - **`DELETE_NODES` (UserGraph — P0-1 완결):**
         - 삭제 대상 ID는 현재 `activeValidationSSoT` 또는 활성 Custom Graph에 실제로 존재하는 유효한 ID여야 함.
         - 병합: §5.3.5 연쇄 삭제 트랜잭션 수행 (노드 제거 $\rightarrow$ `deletedNodeIds` 등록 $\rightarrow$ `delete modifiedNodes[nodeId]` 메타데이터 패치 동시 제거 $\rightarrow$ 연결 Custom Edge 제거 및 `deletedEdgeIds` 등록 $\rightarrow$ 연결 엣지의 `modifiedEdges` 패치 동시 제거).
       - **`DELETE_EDGES` (UserGraph — P0-1 완결):**
         - 삭제 대상 ID는 현재 `activeValidationSSoT` 또는 활성 Custom Edge에 존재하는 유효한 ID여야 함.
         - 병합: `customEdges`에서 제거, `deletedEdgeIds`에 등록, **동시에 `delete modifiedEdges[edgeId]` 실행하여 메타데이터 패치 영구 정리**.
       - **`RESET_USER_GRAPH` (UserGraph — P0-2, P1-1 완결):**
         - §4.2.4 6단계 순서에 따라 활성 Custom Node/Edge를 Tombstone으로 전환 후 초기화 커밋.
3. **`customNodes` 키-ID 일치 및 신규 SSoT 충돌 금지:**
   - `customNodes`의 모든 엔트리에 대해 `key === node.id` 엄격 일치를 강제합니다.
   - `node.id`는 반드시 RFC 4122 UUID v4 정규식(`^user::[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`)을 만족해야 합니다.
   - 신규 추가 요청에 대해 `node.id`가 `activeValidationSSoT` 노드 ID 집합에 존재할 경우 저장을 즉시 거부(`REJECTED_SSOT_ID_COLLISION`)합니다.
4. **`customEdges` ID 검증 및 신규 SSoT 충돌 금지:**
   - `CustomEdge.id`는 반드시 RFC 4122 UUID v4 정규식을 만족해야 합니다.
   - `customEdges` 배열 내에서 `id`는 유일해야 하며(중복 ID 거부), 신규 추가 시 `activeValidationSSoT` 엣지 ID 집합에 존재하는 ID일 경우 저장을 즉시 거부합니다.
5. **Tombstone 상호 배타성 및 연쇄 삭제 트랜잭션 경계 (P0-1 완결):**
   - **상호 배타성 (Mutual Exclusivity Invariant):**
     - 어떤 ID가 `deletedNodeIds`에 존재하면, 동일 ID는 `customNodes` 또는 `modifiedNodes`에 절대로 공존할 수 없습니다.
     - 어떤 ID가 `deletedEdgeIds`에 존재하면, 동일 ID는 `customEdges` 또는 `modifiedEdges`에 절대로 공존할 수 없습니다.
   - **연쇄 삭제 트랜잭션 단계 (Cascade Deletion Steps — P0-1 완결):**
     어떤 노드 또는 엣지를 삭제하여 Tombstone에 등록할 때, 메타데이터 패치가 남아 상호 배타성을 위반하는 결함을 방지하기 위해 다음 순서를 엄격히 수행합니다:
     - ① **Node 삭제 시:** 단일 `UserGraphData` 후보 객체 메모리 복제 생성 $\rightarrow$ `delete candidate.customNodes[nodeId]` 및 **`delete candidate.modifiedNodes[nodeId]`(SSoT 노드 패치 영구 정리)** 실행 $\rightarrow$ `candidate.deletedNodeIds`에 등록.
     - ② **연결 엣지 연쇄 정리:** 해당 노드를 끝점으로 참조하는 모든 Custom Edge를 `candidate.customEdges`에서 제거하고 `candidate.deletedEdgeIds`에 등록함과 동시에, **해당 노드와 연결되어 있던 모든 엣지의 메타데이터 패치 `delete candidate.modifiedEdges[edgeId]` 실행 및 `candidate.deletedEdgeIds` 등록**.
     - ③ **Edge 삭제 시:** `candidate.customEdges`에서 제거, `candidate.deletedEdgeIds`에 등록, **동시에 `delete candidate.modifiedEdges[edgeId]` 실행하여 패치 영구 정리**.
     - ④ **정리 후 불변식 전수 검증:** 위 정리가 모두 완료된 후보 객체에 대해 상호 배타성 및 스키마 유효성을 최종 검증.
     - ⑤ 후보 객체 전수 검증 통과 시 Level 1 원자적 교체(배타적 임시 파일 $\rightarrow$ `fsyncSync` $\rightarrow$ `renameSync` $\rightarrow$ 플랫폼별 디렉터리 동기화) 일괄 커밋.
     - ⑥ 실패 시 후보 객체는 즉시 폐기되고 기존 메모리/디스크 상태가 보존됩니다.

## 7. 결론 및 최종 감사 판정 요청
본 문서는 Revision 14 정적 감사에서 지적된 7대 잔여 결함 및 계약 공백:
1. **P1-1 (복합 Reset의 큐 배리어 보장):** Reset 시작 시 `resetInProgressBarrier`를 선언하여 `RESET_USER_GRAPH`와 `RESET_LAYOUT` 커밋 사이에 일반 저장 요청이 끼어드는 것을 원천 차단.
2. **P1-2 (Layout Reset의 뷰포트 포함 완전한 멱등성 판정):** `positions`, `clusters` 공백 검증과 더불어 `view.zoom === 1.0`, `view.offset.x === 0`, `view.offset.y === 0`을 엄격히 포함하여 이전 뷰포트 잔존 및 No-op 오판 방지.
3. **P1-3 (병합 후 최종 `customProperties` 최대 50개 전수 검증):** DTO 요청 단위 검증에 그치지 않고, 최종 병합된 객체의 키 개수가 50개 이하인지 Step 7에서 엄격히 전수 검증.
4. **P1-4 (`user::` SSoT 네임스페이스 기존 데이터 호환성 검증):** Re-Bootstrap 및 Bootstrap 검증 단계에서 SSoT ID에 `user::` 접두사가 포함된 경우 저장을 즉시 거부(`REJECTED_RESERVED_NAMESPACE_VIOLATION`)하여 출처 혼동 사전 방지.
5. **P1-5 (`ssotSnapshotId` SHA-256 불변 해시 지정):** 타임스탬프 대신 파일 내용에 대한 SHA-256 암호학적 해시를 필수 고유 식별자로 지정하고 타임스탬프는 진단용으로 분리.
6. **P1-6 (커밋 직전 최종 후보 객체 스키마·상호 배타성 공통 전수 검증):** Tier 1/Tier 2 검증과 별개로 Step 7에서 완성된 `candidateData` 전체에 대해 키 개수, 원시 타입, 키-ID 일치, Tombstone 상호 배타성을 최종 재검증.
7. **P1-7 (Canonical Path 보장 범위의 현실적 한정):** `realpathSync`가 보장하는 심볼릭 링크 및 표준 경로 별칭으로 범위를 한정하고 bind mount 등 특수 구성에 대한 과장 표현 제거.

위 사항을 모두 완결했습니다. 본 rev11 최종 개정 계획서(Revision 15)의 마스터 정적 감사 최종 승인을 요청합니다.
