## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 근본 원인 및 완전한 제거
과거 rev1~10 보완 문서는 **"공식 SSoT(`project_state.json`)를 디스크 상에서 인플레이스로 수정하고 크래시 시 이를 복구해야 한다"**는 잘못된 전제에서 출발했습니다.  
이로 인해 파일 시스템의 원자성 한계를 메우기 위해 2단계 저널, 복구 락, Stale Lock 세대 판독, 14개 분기 복구 매트릭스라는 극단적인 복잡성에 빠졌습니다.

### 1.2 "최고의 복구는 복구할 필요 자체를 만들지 않는 것"
사용자의 명확한 KISS 원칙에 따라, 문제를 아키텍처 수준에서 원천 차단합니다:
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **SSoT 영구 불변**: 수집기(Bootstrap)가 생성한 세대별 SSoT는 읽기 전용 불변 원본으로 박제합니다.
2. **Working Copy 격리 분석**: 분석·검증 파이프라인은 원본에서 독립적으로 파싱된 일회용 인메모리 객체(Working Copy)에서 실행되며, 실패 시 해당 복사본을 즉시 폐기하고 원본에서 다시 로드합니다. 롤백 저널과 복구 매트릭스는 완전히 불필요합니다.
3. **데이터 소유권 분리**: 캔버스 프레젠테이션과 사용자 편집 데이터는 SSoT 원본에서 완전히 분리된 전용 오버레이 파일(`layout.json`, `user_graph.json`)로 영속화합니다.


## 3. 단일 Writer 락의 결정론적 소유권 및 Stale 회수 완결 (P0-1 완결)

### 3.1 단일 로컬 Extension Host 범위 한정
- 본 계약의 대상 범위는 **"단일 로컬 머신의 동일 워크스페이스"**로 명시적으로 한정합니다.

### 3.2 Stale 판정의 절대 조건 및 단일 인계권 보장
TTL만으로 살아있는 프로세스의 락을 회수하거나, 재개된 구 소유자가 신규 소유자의 락을 덮어쓰는 TOCTOU를 원천 차단합니다:

1. **Stale 판정의 절대 조건 (PID 부재 필수):**
   - **오직 `process.kill(pid, 0)`이 `ESRCH` (프로세스 완전 사망)를 반환할 때만 Stale로 판정합니다.**
   - 프로세스가 살아 있다면(`ESRCH` 아님) 아무리 시간이 경과해도 절대 Stale로 판정하지 않으며, 무조건 읽기 전용 모드로 진입합니다 (오판 회수 원천 차단).
2. **`takeover.lock` 획득 및 소유 토큰 인계:**
   - 회수 시도 시 `fs.openSync('.takeover.lock', 'wx')` 성공 Host만 배타적 회수권을 획득합니다.
   - 내부 기록: `{ takeoverToken: UUID, pid: process.pid, targetSessionId: oldSessionId }`.
   - **`takeover.lock` 자체의 Stale 회수:** `takeover.lock`의 소유 PID 역시 `process.kill(pid, 0) === ESRCH`인 경우에만 unlink 후 재시도를 허용합니다 (시간 기반 임의 삭제 배제).
3. **인계 직전 소유권 재검증 및 구 소유자 차단:**
   - 회수 Host는 `.takeover.lock`의 토큰이 자신의 `takeoverToken`과 일치함을 확인하고, 교체 대상 `.active_writer.lock`의 세션 ID가 자신이 확인했던 `targetSessionId`와 여전히 일치할 때만 `renameSync`를 수행합니다.
   - 구 소유자 Host가 뒤늦게 재개되더라도, 자신의 메모리 `hostSessionId`가 디스크 락의 `hostSessionId`와 불일치하므로 모든 저장 시도 시 즉시 강제 종료/읽기 전용으로 격리됩니다.

## 4. `user_graph.json` 완전 스키마 및 엄격한 참조 무결성 검증 계약 (P0-3, P1-1 완결)

### 4.1 스키마 정의 및 수정 필드 안전 제한
```typescript
export interface NodeMetadataPatch {
    label?: string;
    description?: string;
    customProperties?: Record<string, string | number | boolean>; // 원시 타입만 허용
}

export interface EdgeMetadataPatch {
    label?: string;
    weight?: number;
    status?: 'proposed' | 'confirmed';
}

export interface CustomNode {
    id: string; // 반드시 ^user::[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$
    label: string;
    data?: any;
}

export interface CustomEdge {
    id: string; // 반드시 ^user::[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$
    from: string;
    to: string;
    type?: string;
    label?: string;
}

export interface UserGraphData {
    revision: number;
    generationId: number;                              // 검증 기준 SSoT 세대 번호
    customNodes: Record<string, CustomNode>;           // key === CustomNode.id
    modifiedNodes: Record<string, NodeMetadataPatch>;  // SSoT 노드 메타데이터 패치
    deletedNodeIds: string[];                          // 노드 Tombstone (SSoT 및 Custom Node 통합)
    
    customEdges: CustomEdge[];                         // 배열 내 ID 고유성 필수
    modifiedEdges: Record<string, EdgeMetadataPatch>;  // SSoT 엣지 메타데이터 패치 (id/from/to 수정 금지)
    deletedEdgeIds: string[];                          // 엣지 Tombstone
}
```

### 4.2 엄격한 저장 검증 및 충돌 정규화 규칙 (Validation on Save)
1. **엄격한 RFC 4122 UUID v4 정규식 및 Key 일치 검증:**
   - 모든 Custom Node/Edge ID는 `^user::[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`을 만족해야 합니다.
   - `customNodes`의 Key는 내부 객체의 `CustomNode.id`와 반드시 엄격 일치(`key === node.id`)해야 합니다.
   - **SSoT ID 충돌 방지:** Custom ID가 활성 SSoT의 Node/Edge ID와 1건이라도 일치하면 저장을 즉시 거부합니다.
2. **Node 및 Edge Tombstone 충돌 양방향 정규화:**
   - 동일 Node ID가 `deletedNodeIds`와 `modifiedNodes`에 공존 시: `modifiedNodes[id]`를 자동 삭제하고 **Tombstone만 영속화**.
   - 동일 Edge ID가 `deletedEdgeIds`와 `modifiedEdges`에 공존 시: `modifiedEdges[id]`를 자동 삭제하고 **Tombstone만 영속화**.
   - `deletedEdgeIds`에 등록된 Custom Edge가 `customEdges` 배열에 남아 있는 경우: `customEdges` 배열에서 해당 엣지를 자동 정규화 제거.
3. **Custom Edge의 전체 구조 및 끝점 무결성 검증 (Dangling Edge 차단):**
   - 각 Custom Edge는 `id`, `from`, `to`가 모두 빈 문자열이 아니어야 하며, **Self-loop(`from === to`)는 허용되지 않습니다 (`from !== to` 필수)**.
   - `from`과 `to`는 반드시 다음 조건을 만족해야 하며 위반 시 저장을 즉시 거부합니다:
     $$\text{endpoint} \in (\text{SSoT.nodes} \cup \text{customNodes}) \land \text{endpoint} \notin \text{deletedNodeIds}$$
4. **저장 시점 SSoT 세대 원자적 일치 검증 (P1-1 완결):**
   - UserGraph 저장 시, 대상 파일의 `generationId`가 **`active_snapshot.json`이 가리키는 활성 스냅샷 내부의 `active_generation.json`의 `activeGeneration`과 완벽히 일치하는지 저장 직전 커밋 시점에 최종 단언**합니다.
   - 저장 도중 Bootstrap에 의해 활성 세대가 교체된 경우, 저장을 즉시 거부하고 최신 세대 기준으로 재동기화합니다.

```
synapse_data/
├── snapshots/
│   ├── snap_20261115_1000/           # 스냅샷 A (완성된 불변 디렉터리)
│   │   ├── active_generation.json    # 해당 시점의 활성 SSoT 세대 번호/해시
│   │   ├── user_graph.json           # 해당 시점의 사용자 그래프 데이터
│   │   └── layout.json               # 해당 시점의 레이아웃 좌표/뷰포트
│   └── snap_20261115_1100/           # 스냅샷 B (완성된 불변 디렉터리)
└── active_snapshot.json              # 활성 스냅샷 단일 포인터 (원자적 교체)
```

1. **독자의 불변 읽기:** 모든 캔버스 로더는 항상 `active_snapshot.json`이 가리키는 스냅샷 디렉터리에서 세 세트를 읽습니다.
2. **단일 포인터 원자적 교체:**
   - 대상 스냅샷 디렉터리 내 3개 파일의 무결성 검증 완료 후,
   - 임시 포인터 파일 `active_snapshot.json.tmp`를 작성 및 `fsync`하고,
   - `fs.renameSync('active_snapshot.json.tmp', 'active_snapshot.json')` 단 1회의 원자적 rename으로 활성 스냅샷을 교체합니다.
3. **플랫폼 보장 범위:** Linux 및 macOS(POSIX)에서는 부모 디렉터리 `fsync`를 수행하여 완벽한 크래시 내구성을 보장하며, Windows에서는 OS `MoveFileEx` 기반의 원자적 가시성 교체를 보장합니다.

## 6. Bootstrap 디렉터리 락 생명주기 및 Stale 회수 완결 (P0-2 완결)

1. **원자적 디렉터리 배타 획득 및 초기화 크래시 방어:**
   - Bootstrap 실행 시 `fs.mkdirSync('synapse_data/.bootstrap_lock_dir')` (`EEXIST` 차단)로 배타 획득.
   - 즉시 내부에 `{ hostSessionId, pid: process.pid, createdAt: Date.now() }`를 담은 `owner.token`을 기록.
   - **디렉터리 생성 후 토큰 기록 전 크래시 복구:** 디렉터리는 존재하지만 `owner.token`이 부재한 경우, 디렉터리 `ctime`이 30초를 초과하고 해당 시점에 실행 중인 Bootstrap 프로세스가 없을 때만 안전하게 rmdir 후 재시도 허용.
2. **원자적 해제 및 오삭제 방지 (Token-Verified Release):**
   - `finally` 블록에서 `owner.token`을 읽어 자신의 `hostSessionId`와 일치하는지 확인.
   - **해제 순서:**
     ① `owner.token` 내부 상태를 `released: true`로 atomic rewrite.  
     ② `fs.unlinkSync('synapse_data/.bootstrap_lock_dir/owner.token')`.  
     ③ `fs.rmdirSync('synapse_data/.bootstrap_lock_dir')`.
   - 만약 자신의 토큰이 아니거나 이미 회수된 상태라면 절대 `rmdir`하지 않고 안전하게 무동작(No-op) 종료하여 타 세션의 락 오삭제를 원천 차단합니다.
3. **분석 세션 고정 (Session Pinning):**
   - 분석기는 시작 시점에 `active_generation.json`을 검증한 뒤 해당 불변 세대 파일(`generations/v{N}.json`) 경로를 세션에 영구 고정하여, 도중에 Bootstrap이 새 세대를 활성화해도 시작 세대만 끝까지 읽습니다.
