## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 근본 원인 및 완전한 제거
과거 rev1~10 보완 문서는 **"공식 SSoT(`project_state.json`)를 디스크 상에서 인플레이스로 수정하고 크래시 시 이를 복구해야 한다"**는 잘못된 전제에서 출발했습니다.  
이로 인해 파일 시스템의 원자성 한계를 메우기 위해 2단계 저널, 복구 락, Stale Lock 세대 판독, 14개 분기 복구 매트릭스라는 극단적인 복잡성에 빠졌습니다.

### 1.2 "최고의 복구는 복구할 필요 자체를 만들지 않는 것"
사용자의 명확한 KISS 원칙에 따라, 문제를 아키텍처 수준에서 원천 차단합니다:
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **SSoT 영구 불변**: 수집기(Bootstrap)가 생성한 `project_state.json`은 읽기 전용 불변 원본으로 박제합니다.
2. **Working Copy 격리 분석**: 분석·검증 파이프라인은 원본의 일회용 복사본(Working Copy)에서 실행되며, 실패 시 해당 복사본을 즉시 폐기하고 원본에서 다시 복사합니다. 롤백 저널과 상태 복구 매트릭스는 완전히 불필요합니다.
3. **데이터 소유권 분리**: 캔버스 프레젠테이션과 사용자 편집 데이터는 SSoT 원본에서 완전히 분리된 전용 오버레이 파일(`layout.json`, `user_graph.json`)로 영속화합니다.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① project_state.json           │ ② Disposable Working Copy             │
│    [Immutable SSoT]            │    [In-Memory Deep Clone]             │
│    - 수집기(Bootstrap) 전용     │    - 원본 복사본에서 분석·검증 수행   │
│    - 노드, 엣지, 클러스터      │    - 실패 시 즉시 폐기 (롤백 불필요)  │
│    - 분석 중 읽기 전용 (RO)    │    - 분석 산출물은 리포트로 저장      │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가 노드/엣지            │
│    - 뷰포트(zoom, offset)      │    - 사용자 편집 라벨/메타데이터      │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. SSoT 세대 관리 및 불변성 계약 (P0-4 해소)

### 3.1 세대별 불변 파일 및 활성 세대 포인터
SSoT의 영구 불변성과 명시적 재수집을 양립시키기 위해 **"세대별 불변 파일 + 활성 세대 메타데이터"** 구조를 채택합니다.

```
synapse_data/
├── project_state.v1.json          # 1세대 불변 SSoT (영구 보존, Read-Only)
├── project_state.v2.json          # 2세대 불변 SSoT (재수집 완료본, Read-Only)
├── active_generation.json         # 활성 세대 식별자: { "activeGeneration": 2, "sha256": "..." }
└── project_state.json             # 활성 세대 심볼릭 링크(Linux/macOS) 또는 활성 사본
```

### 3.2 안전한 세대 전환 프로토콜
1. **재수집 실행 중:** 기존 `project_state.v1.json`과 `active_generation.json`은 1바이트도 수정하지 않고 읽기 전용으로 서비스 유지.
2. **신규 세대 작성:** 임시 파일 `project_state.v2.json.tmp`에 수집 결과를 기록하고 `fsync` 후 `project_state.v2.json`으로 원자적 rename.
3. **유효성 검증 게이트:** `project_state.v2.json`의 JSON 파싱, 최소 노드 수, 엣지 무결성을 검증. 검증 실패 시 신규 파일 폐기 및 활성 세대(v1) 유지.
4. **활성 세대 전환:** 검증 통과 시 `active_generation.json`을 원자적으로 갱신(`activeGeneration: 2`).

## 4. `layout.json` 원자적 저장 및 동시성 제어 계약 (P0-2, P0-3, P1 해소)

### 4.1 원자적 저장 및 실패 보장 범위의 엄격한 분리 (P0-3)
원자적 가시성(Atomic Visibility)과 크래시 내구성(Crash Durability)을 명확히 분리 정의합니다:

```
[1. tmp 파일 생성] ──> [2. 데이터 기록] ──> [3. tmp fsync] ──> [4. 디렉터리 fsync (POSIX)]
                                                                       │
                                              ┌────────────────────────┘
                                              ▼
                                     [5. fs.renameSync] ──(성공)──> [6. 디렉터리 fsync (2차)]
                                              │                                  │
                                           (실패)                              (실패)
                                              ▼                                  ▼
                                    [기존 layout.json 보존,               [교체는 완료됨,
                                     tmp 파일 unlink]                     내구성 미확인 경고]
```

- **rename 이전 실패 (1~4단계):** 기존 `layout.json`은 100% 손상 없이 보존되며, 임시 파일은 unlink 처리.
- **rename 성공 (5단계):** 새 파일로의 원자적 가시성 교체가 완료된 것으로 간주.
- **rename 이후 실패 (6단계):** 새 파일로 교체는 완료되었으나 디렉터리 내구성을 확인할 수 없는 상태로 로깅. 기존 파일이 보존되었다고 허위 주장하지 않음.
- **크로스 플랫폼 지원:** POSIX 디렉터리 `fsync`는 플랫폼 지원 여부(`process.platform !== 'win32'`)를 감지하여 Windows에서는 파일 FD `fsync` 위주로 안전하게 폴백.

### 4.2 Revision 동시성 검증: `expectedRevision === currentRevision` (P0-2)
단순 대소 비교(`<`)의 맹점을 제거하고 완전한 낙관적 동시성 제어(OCC)를 수립합니다:
- **검증 규칙:** 웹뷰가 저장 요청 시 보낸 `expectedRevision`과 Host 메모리의 `currentRevision`이 **정확히 일치(`===`)할 때만** 저장을 허용하고 `revision + 1`을 기록합니다.
  $$\text{Allow Save} \iff \text{expectedRevision} === \text{currentRevision}$$
- **불일치 시:** 즉시 저장을 거부하고 디스크의 최신 상태와 `currentRevision`을 웹뷰로 반환하여 강제 동기화(Snap-back 원천 차단).
- **자료형:** 안전한 부호 없는 53비트 정수(`Number.isSafeInteger`)를 사용하며, 일반적인 웹뷰 세션 수명 내에서 오버플로우는 물리적으로 불가능합니다.

### 4.3 파싱 후 유효성 검증 및 손상 처리 (P1-1 ~ P1-5)
1. **유한 숫자 검사:** JSON 파싱 후 좌표 값은 `Number.isFinite(x) && Number.isFinite(y)`로 검증하며, 유효 범위를 초과하는 좌표는 배제하고 SSoT의 기본 좌표를 사용.
2. **손상 파일 보존:** `layout.json` 파싱 실패 시, 손상된 파일을 `layout.json.corrupt.{timestamp}`로 백업 격리한 후 기본 좌표로 안전 복귀.
3. **고아 ID 정리 정책:** SSoT에 없는 고아 ID는 최대 500개까지 `orphans` 필드에 보존하며, 초과 시 LRU 정책으로 정리.

## 5. `user_graph.json` 최소 영속성 계약 (P0-5 해소)

사용자 그래프 편집 데이터(`USER_DATA`)를 안전하게 보존하기 위한 영속화 규약입니다.

1. **단일 소유자:** Extension Host 메인 스레드의 직렬 큐(Serial Queue)가 단독 Writer로 동작.
2. **데이터 스키마:**
   ```typescript
   interface UserGraphData {
       revision: number;
       customNodes: Record<string, CustomNode>;   // 사용자 생성 노드
       modifiedData: Record<string, PartialNode>; // 수정한 라벨/메타데이터
       deletedNodeIds: string[];                  // 삭제된 노드 ID 목록
       confirmedEdges: Edge[];                    // 사용자가 확정한 엣지 목록
   }
   ```
3. **ID 충돌 방지:** 사용자가 생성하는 노드 ID는 반드시 `user::` 네임스페이스 접두사(`user::{uuid}`)를 강제하여 SSoT 노드 ID와의 충돌을 원천 차단.
4. **원자적 저장:** §4.1과 동일한 임시 파일 작성 후 원자적 `rename` 방식을 적용.
5. **재수집 세대 전환 시 동작:** 재수집으로 새 SSoT가 생성되어도 `user_graph.json`의 `user::` 노드와 메타데이터는 유지되며, 삭제된 SSoT 노드를 가리키는 고아 참조만 정리 리포트로 사용자에게 통지.

## 6. Working Copy 격리 방식 및 원본 독립성 확정 (P0-6 해소)

### 6.1 인메모리 완전 독립 복제 (In-Memory Deep Clone) 공식 채택
대규모 SSoT(VS Code 61.6MB)에 대한 불필요한 디스크 I/O 복사 비용을 없애기 위해 **"인메모리 완전 독립 복제"**를 공식 채택합니다.

1. **독립성 보장:**
   - SSoT 원본 객체는 `Object.freeze()`로 런타임 변조를 차단.
   - 분석 파이프라인에는 `structuredClone(ssotData)` (또는 성능 최적화된 토폴로지 복제 함수)를 통해 생성된 **완전 독립된 객체(Working Copy)**만 주입.
2. **원본 직접 참조 0건 강제:** 분석 엔진 내부에서 원본 캐시나 싱글톤 상태를 직접 참조하는 것을 정적 린터 및 단언문으로 차단.
3. **폐기 시점:** 분석 및 리포트 파일 저장이 완료되는 즉시 Working Copy 객체에 대한 참조를 해제(`workingCopy = null`)하여 V8 GC에 의해 즉시 수거.
4. **해시 검증 프로토콜:**
   - 분석 시작 전: 디스크 SSoT 파일의 SHA-256 계산 및 기록.
   - 분석 완료 후: 디스크 SSoT 파일의 SHA-256 재계산 $\rightarrow$ **0 Byte Diff 불변성(PASS) 강제 단언**.
   - 이를 통해 분석 도중 원본 파일에 대한 어떠한 쓰기도 발생하지 않았음을 결정론적으로 증명.
