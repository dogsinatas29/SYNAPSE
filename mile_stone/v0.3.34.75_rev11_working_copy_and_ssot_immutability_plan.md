## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 근본 원인 및 완전한 제거
과거 rev1~10 보완 문서는 **"공식 SSoT(`project_state.json`)를 디스크 상에서 인플레이스로 수정하고 크래시 시 이를 복구해야 한다"**는 잘못된 전제에서 출발했습니다.  
이로 인해 파일 시스템의 원자성 한계를 메우기 위해 2단계 저널, 복구 락, Stale Lock 세대 판독, 14개 분기 복구 매트릭스라는 극단적인 복잡성에 빠졌습니다.

### 1.2 "최고의 복구는 복구할 필요 자체를 만들지 않는 것"
사용자의 명확한 KISS 원칙에 따라, 문제를 아키텍처 수준에서 원천 차단합니다:
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **SSoT 영구 불변**: 수집기(Bootstrap)가 생성한 세대별 SSoT는 읽기 전용 불변 원본으로 박제합니다.
2. **Working Copy 격리 분석**: 분석·검증 파이프라인은 원본에서 독립적으로 파싱된 일회용 인메모리 객체(Working Copy)에서 실행되며, 실패 시 해당 복사본을 즉시 폐기하고 원본에서 다시 로드합니다. 롤백 저널과 복구 매트릭스는 완전히 불필요합니다.
3. **데이터 소유권 분리**: 캔버스 프레젠테이션과 사용자 편집 데이터는 SSoT 원본에서 완전히 분리된 전용 오버레이 파일(`layout.json`, `user_graph.json`)로 영속화합니다.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① generations/project_state.vN │ ② Disposable Working Copy             │
│    [Immutable SSoT]            │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - 노드, 엣지, 클러스터      │    - 실패 시 즉시 폐기 (롤백 불필요)  │

├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가/수정/삭제 노드       │
│    - 뷰포트(zoom, offset)      │    - 사용자 확정/수정/삭제 엣지       │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 원자적 단일 Writer 락 및 Stale Lock 인계 계약 (P0-1 완결)

### 3.1 단일 로컬 Extension Host 범위 한정
- 본 계약의 대상 범위는 **"단일 로컬 머신의 동일 워크스페이스"**로 명시적으로 한정합니다. (다중 머신 분산 공유 파일시스템은 SYNAPSE의 비목표).

### 3.2 원자적 획득 및 Stale Lock 원자적 인계 프로토콜
1. **원자적 최초 획득:**
   - Host는 워크스페이스 활성화 시 `fs.openSync('synapse_data/.active_writer.lock', 'wx')` (`O_CREAT | O_EXCL`)로 독점 락 생성을 시도합니다.
   - 성공 시 `{ hostSessionId: UUID, pid: process.pid, createdAt: Date.now(), heartbeat: Date.now() }`를 기록합니다.
2. **독점 락 실패 시 (`EEXIST`) 안전한 인계 절차 (회수 경쟁 차단):**
   - 락 파일 내부의 `hostSessionId`, `pid`, `heartbeat`를 읽습니다.
   - **생존 검증:** `process.kill(pid, 0)`이 `ESRCH` (프로세스 완전 부재)를 반환할 때만 Stale 상태로 판정합니다. (단순 타임아웃만으로는 오판 방지를 위해 회수하지 않음).
   - **원자적 인계 (Atomic Takeover):**
     ① 기존 락 파일을 무조건 삭제하는 방식(`unlink`)은 새 락과의 충돌을 유발하므로 **금지**합니다.  
     ② 새로운 락 내용(`newHostSessionId`, `newPid`)을 담은 임시 파일 `.active_writer.lock.tmp.{newSessionId}`를 작성합니다.  
     ③ `fs.renameSync`로 기존 락 파일을 덮어쓰는 방식을 사용하되, 덮어쓰기 직전 기존 파일의 `hostSessionId`가 앞서 확인한 죽은 PID의 세션 ID와 일치하는지 재확인합니다.
3. **Secondary Host 처리:**
   - 살아 있는 활성 Host가 확인되면 즉시 **읽기 전용 모드(Read-Only Session)**로 진입하며, UI에 읽기 전용 경고를 띄우고 모든 저장 IPC 요청을 진입점에서 즉시 거부(`REJECTED_READ_ONLY_SECONDARY_HOST`)합니다.

## 4. `user_graph.json` 스키마 검증 및 저장 무결성 계약 (P0-4 완결)

### 4.1 엄격한 스키마 정의 및 수정 필드 안전 제한
```typescript
export interface NodeMetadataPatch {
    label?: string;
    description?: string;
    customProperties?: Record<string, string | number | boolean>; // 원시 타입만 허용
}

export interface EdgeMetadataPatch {
    label?: string;
    weight?: number;
    status?: 'proposed' | 'confirmed';
}

export interface UserGraphData {
    revision: number;
    customNodes: Record<string, CustomNode>;           // ID 규칙: user::{uuid}
    modifiedNodes: Record<string, NodeMetadataPatch>;  // 구조적 ID 수정 불가
    deletedNodeIds: string[];                          // 노드 Tombstone
    
    customEdges: CustomEdge[];                         // 허용: id(user::), from, to, type, label
    modifiedEdges: Record<string, EdgeMetadataPatch>;  // id, from, to 수정 엄격 금지
    deletedEdgeIds: string[];                          // 엣지 Tombstone
}
```

### 4.2 스키마 검증 및 충돌 정규화 규칙 (Normalization Rules)
1. **ID 네임스페이스 및 충돌 검증:**
   - 모든 `customNodes`와 `customEdges`의 ID는 정규식 `^user::[a-f0-9\-]{36}$`을 강제합니다. SSoT 노드 ID와 동일한 ID의 신규 생성은 저장 시 즉시 거부됩니다.
2. **참조 무결성 검증 (Dangling Edge 차단):**
   - `customEdges`의 `from`과 `to`는 반드시 SSoT의 유효 노드 ID이거나 `customNodes`에 등록된 ID여야 합니다. 부재 시 저장 거부.
3. **Tombstone 우선순위 및 정규화:**
   - 동일한 ID가 `deletedNodeIds`와 `modifiedNodes`에 동시에 존재하는 경우, 저장 정규화 단계에서 `modifiedNodes[id]`를 자동 제거하고 **Tombstone만 영속화**합니다.
4. **Revision 검증 및 상한:**
   - `revision`은 `Number.isSafeInteger(revision) && revision >= 0`을 만족해야 합니다.
   - `currentRevision >= Number.MAX_SAFE_INTEGER` 도달 시 저장을 거부하고 사용자에게 세션 갱신을 요구합니다.
5. **원자적 저장:** 임시 파일 작성 $\rightarrow$ `fsync` $\rightarrow$ 디렉터리 `fsync` (POSIX) $\rightarrow$ `renameSync` $\rightarrow$ 2차 디렉터리 `fsync` 시퀀스를 동일 적용.

## 5. 원자적 스냅샷 포인터 기반 Rollback 일관성 보장 (P0-2 완결)

기존의 순차 파일 덮어쓰기를 전면 폐기하고, **"완성된 스냅샷 디렉터리 + 활성 스냅샷 단일 포인터(`active_snapshot.json`)"** 모델을 적용합니다:

│   ├── snap_20261115_1000/           # 스냅샷 A 디렉터리 (완성된 세트)
│   │   ├── active_generation.json    # 해당 시점의 활성 SSoT 세대 번호/해시

└── active_snapshot.json              # 활성 스냅샷 단일 포인터 (원자적 교체)

### 5.1 원자적 롤백 절차 및 불변성 보장
1. **SSoT 원본 보존:** 롤백은 SSoT 세대 파일 자체를 덮어쓰지 않으며, 스냅샷 디렉터리 내부의 `active_generation.json`을 통해 과거 SSoT 세대를 참조합니다.
2. **단일 포인터 원자적 교체:**
   - 대상 스냅샷 디렉터리 내 3개 파일의 무결성 검증 완료 후,
   - 임시 포인터 파일 `active_snapshot.json.tmp`를 작성 및 `fsync`하고,
   - `fs.renameSync('active_snapshot.json.tmp', 'active_snapshot.json')` **단 1회의 원자적 rename**으로 활성 스냅샷을 교체합니다.
3. **효과:** 순차 파일 덮어쓰기 중단으로 인한 중간 불일치 상태가 물리적으로 0건이며, 독자는 항상 완성된 한 세트만 읽게 됩니다.

## 6. 원자적 Bootstrap Lock 생명주기 및 분석 시작 경계 확정 (P0-3 완결)

1. **Bootstrap Lock의 완전한 생명주기:**
   - **획득:** `fs.openSync('synapse_data/.bootstrap.lock', 'wx')` 성공 시 락 파일에 `{ pid, startTime, hostSessionId }` 기록.
   - **유지:** 수집 작업 도중 하트비트 타임스탬프 갱신.
   - **해제:** 정상 완료, 에러 발생, 예외 중단 시 `finally` 블록에서 `fs.unlinkSync`로 반드시 해제.
   - **Stale 회수:** PID 부재(`ESRCH`) 확인 시에만 락 해제 및 재시도 허용.
2. **분석 시작 경계 및 세대 고정 (Session Pinning):**
   - 분석 시작 시 `.bootstrap.lock`이 존재하면 분석기는 대기하거나 즉시 중단 메시지를 반환합니다.
   - 분석기는 시작 시점에 `active_generation.json`을 읽고 검증한 뒤, 해당 **불변 세대 파일(`generations/project_state.v{N}.json`) 경로를 분석 세션에 고정(Pinning)**합니다.
   - 분석 실행 도중에 Bootstrap이 완료되어 새 세대(`v{N+1}`)가 활성화되더라도, 이미 실행 중인 분석 세션은 자신이 고정한 불변 `v{N}` 파일만 끝까지 읽으므로 경쟁 조건이 발생하지 않습니다.
