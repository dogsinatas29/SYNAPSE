## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 완전한 일소
과거의 복잡성은 "과거 SSoT를 이력으로 보관하고 롤백·교체하겠다"는 미련에서 출발했습니다.  
SYNAPSE는 소스 코드 형상 관리 도구가 아니며, **"현재 프로젝트 소스 트리의 아키텍처를 시각화하고 진단하는 분석 엔진"**입니다.  
프로젝트 코드가 바뀌어 재수집(Re-Bootstrap)이 발생하면, 이전 SSoT의 세대 번호를 따질 필요 없이 **새로운 단일 `project_state.json`이 유일한 기준 원본**이 됩니다.

### 1.2 단순화된 3대 불변식
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **Bootstrap 소유 교체 가능 SSoT (`project_state.json`)**: 수집기(Bootstrap)만 작성하며, UI와 분석기는 절대 직접 수정하지 않는 읽기 전용 기준 원본 (Bootstrap-owned replaceable SSoT).
2. **분석별 독립 Working Copy**: 분석 파이프라인(전체 클러스터 분석, 선택 그룹 분석 등)은 디스크 원본에서 직접 파싱된 독립 메모리 객체에서 실행되며, 종료 시 즉시 폐기.
3. **2대 오버레이 분리**: 사용자의 시각적 조작은 `layout.json`(좌표/뷰포트)에, 사용자 그래프 편집은 `user_graph.json`(노드/엣지 추가·수정·삭제)에만 영속화.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① project_state.json           │ ② Disposable Working Copy             │
│    [SSoT: Bootstrap-Owned]     │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - 노드, 엣지, 클러스터      │    - 분석 A/B 간 객체 공유 0건        │
│    - UI/분석기 직접 수정 금지  │    - 분석 종료 시 즉시 GC 폐기        │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가/수정/삭제 노드       │
│    - 뷰포트(zoom, offset)      │    - 사용자 확정/수정/삭제 엣지       │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 통합 단일 Writer 락: 원자적 디렉터리 락 기반 단일화 계약 (P0-1 완결)

두 단계 락(`takeover.lock`)의 회수 경쟁 취약점을 완전히 제거하고, OS 커널 수준의 단일 원자적 연산인 **"디렉터리 락(`mkdirSync`)"** 기반으로 단일화합니다:

### 3.1 단일 로컬 Extension Host 범위 한정
- 본 계약의 대상 범위는 **"단일 로컬 머신의 동일 워크스페이스"**로 명시적으로 한정합니다.

### 3.2 디렉터리 락 기반 원자적 Writer 획득 및 Stale 회수 (Directory Lock Protocol)
POSIX 및 Windows 커널에서 디렉터리 생성(`mkdir`)은 완벽한 원자적 배타 연산(`EEXIST` 보장)이며 파일 unlink 간의 경쟁이 발생하지 않습니다:

```
[Writer 획득 시도: fs.mkdirSync('synapse_data/.writer_lock_dir')]
     │
  (성공) ──> [내부에 owner.token 기록: { hostSessionId, pid: process.pid, createdAt: Date.now() }]
     │       └──> [Primary Writer 획득 완료]
     │
  (EEXIST: 이미 락 디렉터리 존재)
     │
     ▼
[Stale 회수 검증 단계]
  ├─ 1. owner.token 읽기: { hostSessionId: oldSessionId, pid: oldPid }
  ├─ 2. process.kill(oldPid, 0) === ESRCH 검증 (프로세스 완전 사망 단언)
  │     (만약 ESRCH가 아니라면: 살아있는 프로세스이므로 즉시 Read-Only 모드로 차단 및 종료)
  │
  ├─ 3. 원자적 인계 (Atomic Rename Eviction):
  │     Host는 임시 퇴출 디렉터리 경로 'synapse_data/.writer_lock_dir.evict.{mySessionId}'를 준비한 후,
  │     fs.renameSync('.writer_lock_dir', '.writer_lock_dir.evict.{mySessionId}') 수행!
  │     (OS 수준에서 rename은 단 1개의 Host만 성공하며, 실패한 다른 Host는 즉시 탈락)
  │
  ├─ 4. 퇴출된 구 디렉터리 정리: fs.rmSync('.writer_lock_dir.evict.{mySessionId}', { recursive: true })
  └─ 5. fs.mkdirSync('.writer_lock_dir')로 새 락 디렉터리 생성 및 새 owner.token 기록!
```

- **회수 경쟁 완전 차단:** 두 Host가 동시에 Stale로 판정하더라도, `fs.renameSync`로 구 락 디렉터리를 자신의 고유 세션 경로로 빼앗아오는(Eviction) 연산은 **오직 1개의 Host만 성공**합니다. 경쟁에서 밀린 다른 Host는 `renameSync` 실패(`ENOENT`) 즉시 탈락하여 읽기 전용으로 안전하게 격리됩니다.
- **Zero-byte 및 토큰 부재 크래시 방어:** 디렉터리는 존재하나 `owner.token`이 부재한 경우, 디렉터리 `ctime`이 10초를 초과하고 워크스페이스 내 생존 프로세스가 없을 때만 위 `renameSync` 퇴출 절차를 통해 안전하게 회수합니다.

## 4. Re-Bootstrap 원자적 교체 및 오버레이 유효성 계약 (P0-2, P1-3 완결)

### 4.1 Re-Bootstrap 원자적 교체 및 플랫폼별 보장 범위
1. **임시 파일 생성:** 대상과 동일한 파일시스템(`synapse_data/project_state.json.tmp`)에 완전한 수집 결과를 기록.
2. **내구성 및 유효성 검증:** 파일 FD `fsync` 후 JSON 파싱 및 필수 토폴로지 유효성 검사 수행.
3. **원자적 교체:** 검증 통과 시 `fs.renameSync('project_state.json.tmp', 'project_state.json')`으로 단 1회의 원자적 rename 수행. 실패 시 기존 SSoT 100% 보존.
4. **플랫폼별 보장 범위 (P1-3):**
   - **POSIX (Linux / macOS):** 동일 파일시스템 내에서 `renameSync`는 원자적 가시성 교체를 보장하며, 파일 FD fsync 및 부모 디렉터리 fsync를 통해 디렉터리 엔트리 내구성을 보장합니다.
   - **Windows (`win32`):** OS `MoveFileEx` 기반의 동일 파일시스템 내 원자적 파일 교체(Atomic Visibility)만 보장하며, 디렉터리 엔트리 내구성은 지원 가능한 파일 수준 내구성으로 한정함을 명시.
5. **분석 읽기 일관성:** 분석기는 파일 전체를 메모리로 한 번에 읽어 독립 객체(Working Copy)로 완전히 파싱한 후 분석을 시작하므로, 디스크 파일 교체와 완전히 독립적입니다.

### 4.2 오버레이의 로드 필터링 및 저장 시 정규화 범위 (P0-2 완결)
1. **로드 시 비파괴적 필터링 (Graceful Filtering on Load):**
   - 캔버스 로드 시 현재 SSoT(`project_state.json`)와 대조하여 다음 항목을 **화면 표시에서만 자동 제외(Ignore & Filter)**합니다:
     - SSoT에서 사라진 노드에 대한 `modifiedNodes` 및 사라진 엣지에 대한 `modifiedEdges`.
     - SSoT에서 사라진 노드 ID에 대한 `layout.json`의 위치 좌표 및 사라진 클러스터 접힘 상태.
     - 양 끝점 중 하나라도 사라진 고아 Custom Edge.
   - **디스크 원본 보존:** 이 과정에서 디스크 상의 `user_graph.json`이나 `layout.json`을 자동 삭제하지 않습니다.
2. **저장 시 정규화 범위 (Normalization Scope on Save):**
   - 사용자가 캔버스에서 편집 후 저장을 수행할 때, **"사용자가 활성 상태로 유지한 데이터"만 정규화하여 저장**합니다.
   - 유효하지 않은 무효 참조 데이터는 저장 페이로드에서 제외되나, 사용자가 직접 수정한 적 없는 오래된 블록을 임의로 파괴하지 않도록 변경 대상 컬렉션 단위로 정규화합니다.

## 5. `user_graph.json` 완전 스키마 및 Tombstone 정규화 계약 (P0-3, P1-1, P1-2 완결)

### 5.1 스키마 정의 및 엄격한 식별자 규칙 (P1-2, P0-3 완결)
```typescript
export interface NodeMetadataPatch {
    label?: string;
    description?: string;
    customProperties?: Record<string, string | number | boolean>; // 원시 타입만 허용
}

export interface EdgeMetadataPatch {
    label?: string;
    weight?: number;
    status?: 'proposed' | 'confirmed';
}

export interface CustomNode {
    id: string; // RFC 4122 UUID v4: ^user::[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
    label: string;
    customProperties?: Record<string, string | number | boolean>; // 일관된 원시 타입 제한 (data?: any 배제)
}

export interface CustomEdge {
    id: string; // RFC 4122 UUID v4: ^user::[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
    from: string;
    to: string;
    type?: string;
    label?: string;
}

export interface UserGraphData {
    revision: number;                                  // 웹뷰-Host 간 OCC 동시성 제어 정수
    customNodes: Record<string, CustomNode>;           // key === CustomNode.id
    modifiedNodes: Record<string, NodeMetadataPatch>;  // SSoT 노드 메타데이터 패치
    deletedNodeIds: string[];                          // 노드 Tombstone (SSoT 및 Custom Node 통합)
    
    customEdges: CustomEdge[];                         // Custom Edge 목록 (from !== to)
    modifiedEdges: Record<string, EdgeMetadataPatch>;  // SSoT 엣지 메타데이터 패치 (id/from/to 수정 금지)
    deletedEdgeIds: string[];                          // 엣지 Tombstone
}
```

### 5.2 Revision 영속화 및 OCC 생명주기 (P1-1 완결)
1. **로드 시 초기화:** Host 시작 시 `layout.json`과 `user_graph.json` 디스크 파일에 기록된 `revision`을 읽어 각각의 인메모리 `currentRevision`으로 설정 (파일 부재 시 0).
2. **원자적 갱신:** 디스크 저장 임시 파일 작성 시 `newRevision = currentRevision + 1`을 기록하며, rename 성공 시에만 메모리의 `currentRevision`을 갱신. 디스크 저장 실패 시 메모리 `currentRevision`은 증가하지 않음.
3. **웹뷰 통신:** 저장 성공 후 웹뷰로 반환되는 IPC 응답에 새 revision을 동기화 전달.

### 5.3 Custom Node 삭제 시 연결 Edge 처리 및 Tombstone 정규화 (P0-3 완결)
1. **Custom Node 삭제와 연결 Edge 원자적 처리 (Cascading Tombstone):**
   - 사용자가 Custom Node를 삭제할 경우, **해당 노드를 끝점(`from` 또는 `to`)으로 참조하는 모든 Custom Edge도 동일한 저장 트랜잭션 내에서 `customEdges`에서 제거되고 `deletedEdgeIds` Tombstone에 등록**됩니다.
2. **Custom Edge/Node ID 형식 검증:**
   - 모든 Custom Node/Edge ID 및 Tombstone ID는 RFC 4122 UUID v4 정규식을 엄격히 만족해야 합니다.
3. **양방향 Tombstone 우선순위:**
   - 동일 Node ID가 `deletedNodeIds`와 `modifiedNodes`에 공존 시: `modifiedNodes[id]` 자동 제거.
   - 동일 Edge ID가 `deletedEdgeIds`와 `modifiedEdges`에 공존 시: `modifiedEdges[id]` 자동 제거.
4. **Custom Edge 끝점 유효성 및 Self-loop 거부:**
   - `customEdges`의 `from`과 `to`는 반드시 SSoT 노드이거나 활성 Custom Node여야 하며, `deletedNodeIds`에 포함된 노드를 참조하거나 Self-loop(`from === to`)인 경우 저장을 즉시 거부합니다.
