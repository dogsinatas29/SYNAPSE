## 1. 개요 및 설계 철학 (Core Philosophy: KISS & Zero-Regeneration)

### 1.1 오버엔지니어링의 완전한 일소
과거의 복잡성은 "과거 SSoT를 이력으로 보관하고 롤백·교체하겠다"는 미련에서 출발했습니다.  
SYNAPSE는 소스 코드 형상 관리 도구가 아니며, **"현재 프로젝트 소스 트리의 아키텍처를 시각화하고 진단하는 분석 엔진"**입니다.  
프로젝트 코드가 바뀌어 재수집(Re-Bootstrap)이 발생하면, 이전 SSoT의 세대 번호를 따질 필요 없이 **새로운 단일 `project_state.json`이 유일한 기준 원본**이 됩니다.

### 1.2 단순화된 3대 불변식
> **"재생성 불가능한 데이터는 원본 보존, 복사본 작업, 재구성은 불필요 (KISS)"**
1. **Bootstrap 소유 교체 가능 SSoT (`project_state.json`)**: 수집기(Bootstrap)만 작성하며, UI와 분석기는 절대 직접 수정하지 않는 읽기 전용 기준 원본 (Bootstrap-owned replaceable SSoT).
2. **분석별 독립 Working Copy**: 분석 파이프라인(전체 클러스터 분석, 선택 그룹 분석 등)은 디스크 원본에서 직접 파싱된 독립 메모리 객체에서 실행되며, 종료 시 즉시 폐기.
3. **2대 오버레이 분리**: 사용자의 시각적 조작은 `layout.json`(좌표/뷰포트)에, 사용자 그래프 편집은 `user_graph.json`(노드/엣지 추가·수정·삭제)에만 영속화.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        SYNAPSE Data Architecture                       │
├────────────────────────────────┬───────────────────────────────────────┤
│ ① project_state.json           │ ② Disposable Working Copy             │
│    [SSoT: Bootstrap-Owned]     │    [Isolated In-Memory Parse]         │
│    - 수집기(Bootstrap) 전용     │    - 원본에서 독립 파싱하여 분석 수행 │
│    - 노드, 엣지, 클러스터      │    - 분석 A/B 간 객체 공유 0건        │
│    - UI/분석기 직접 수정 금지  │    - 분석 종료 시 즉시 GC 폐기        │
├────────────────────────────────┼───────────────────────────────────────┤
│ ③ layout.json                  │ ④ user_graph.json                     │
│    [User Layout Overlay]       │    [User Graph Overlay]               │
│    - 사용자 드래그 좌표(position)│    - 사용자 추가/수정/삭제 노드       │
│    - 뷰포트(zoom, offset)      │    - 사용자 확정/수정/삭제 엣지       │
│    - 클러스터 접힘(collapsed)  │    - 캔버스 프레젠테이션 시 병합      │
└────────────────────────────────┴───────────────────────────────────────┘
```

## 3. 통합 단일 Writer 락: 디렉터리 배타 락 및 완전한 Read-Only 격리 규약 (P0-1 완결 - ACCEPTED)

### 3.1 단일 로컬 파일시스템 범위 한정 및 락 경로 정규화
- 본 계약의 대상 범위는 **"단일 로컬 머신의 표준 로컬 파일시스템(ext4, xfs, APFS, NTFS 등)에 마운트된 동일 워크스페이스"**로 명시적으로 한정합니다.
- **락 경로 절대 정규화:** 작업 디렉터리(CWD) 차이에 따른 식별 분기를 방지하기 위해, 락 경로는 반드시 VS Code 워크스페이스 루트를 기준으로 정규화합니다:
  $$\text{lockDirPath} = \text{path.resolve}(\text{workspaceRoot}, \text{'synapse\_data'}, \text{'.writer\_lock\_dir'})$$
- 네트워크 파일시스템(NFS, SMB 등)이나 특수 분산 마운트는 SYNAPSE의 비목표이며, `mkdir`의 원자적 배타성을 일반화하지 않습니다.

### 3.2 원자적 배타 획득 및 무조건적 Read-Only Fallback (Zero-Split-Brain Policy)
살아있는 Primary Host가 존재하는 상태에서 다른 창이 락을 강제 삭제하여 발생하는 Split-Brain(다중 Writer 공존)을 아키텍처 수준에서 원천 차단하기 위해, **"소유권 증명 불가 시 쓰기 전면 불허"** 원칙을 확립합니다:

1. **원자적 배타 디렉터리 생성 (Atomic Exclusive Directory Creation):**
   - Extension Host 활성화 시 `fs.mkdirSync(lockDirPath)` 호출로 배타적 디렉터리 생성을 시도합니다.
   - 지원되는 로컬 파일시스템에서 `mkdir`은 이미 디렉터리가 존재할 경우 `EEXIST`를 반환하는 완벽한 원자적 배타 연산입니다.
2. **최초 락 생성 직후 실패 처리 (Fail-Safe on Init):**
   - `mkdirSync`가 성공한 직후, 내부에 `{ hostSessionId: UUID, pid: process.pid, createdAt: Date.now() }`를 담은 `owner.token`을 기록합니다.
   - **토큰 기록 중 I/O 에러 또는 크래시 발생 시:** Host는 절대로 Writer 권한을 활성화하지 않고 즉시 비활성화/실패 상태로 전환합니다. 토큰이 없는 미완성 디렉터리는 자동 삭제하지 않고 방치하여 다른 Host가 오인 획득하지 못하도록 보호합니다.
   - 정상적으로 토큰 기록까지 완료된 경우에만 **Primary Writer** 권한을 정식 부여받습니다.
3. **충돌 시 완전한 Read-Only Fallback (`EEXIST`):**
   - 이미 `.writer_lock_dir`이 존재하면, **어떠한 자동 회수, 프로세스 생존 검사, 파일 삭제, 백그라운드 덮어쓰기도 일체 시도하지 않습니다.**
   - 해당 Host는 즉시 **읽기 전용 모드(Read-Only Session)**로 진입하며, 모든 저장 IPC 요청을 진입점에서 즉시 거부(`REJECTED_SECONDARY_HOST_READ_ONLY`)합니다.
   - `EEXIST` 이외의 파일시스템 에러(권한 부족, I/O 에러 등) 발생 시 조용히 넘기지 않고 치명적 락 획득 실패 에러로 로깅합니다.
4. **UI 강제 삭제 금지 및 Split-Brain 차단 (No UI Force-Delete):**
   - **Secondary Host의 UI 웹뷰에 락을 임의로 삭제하는 버튼이나 명령어를 일체 제공하지 않습니다.** (UI 버튼 클릭 시 실행 중인 Primary Host의 소유권과 충돌하여 발생하는 Split-Brain 원천 차단).
   - UI에는 오직 객관적 사실 알림만 표시합니다:
     > **"[안내] 다른 Extension Host의 잠금이 존재하거나 이전 세션의 잠금이 남아 있습니다. 현재 세션은 읽기 전용 모드로 동작합니다."**
5. **정상 종료 시 해제:**
   - Host 정상 비활성화(`deactivate`) 시, 디렉터리 내부의 `owner.token`을 읽어 `hostSessionId`가 자신의 세션 ID와 엄격 일치할 때만 `fs.rmSync(lockDirPath, { recursive: true })`로 안전하게 락을 해제합니다. 외부 프로세스가 실행 중 락을 삭제하거나 재생성하지 않는 정상 락 프로토콜 범위에서 안전하게 동작합니다.
6. **비정상 종료 후 외부 수동 복구 (External Manual Recovery):**
   - 이전 Host가 비정상 크래시되어 락 디렉터리가 영구 방치된 경우의 복구는 **"모든 관련 VS Code 프로세스를 완전히 종료한 후, 사용자가 외부 터미널/파일 탐색기에서 `synapse_data/.writer_lock_dir`을 명시적으로 직접 삭제하고 재시작"**하는 수동 절차로만 규정합니다.
   - **효과:** 계약을 준수하는 Extension Host 간에는 자동 락 회수 및 Secondary Host의 강제 삭제 경로가 존재하지 않으므로, 정상적인 락 프로토콜 범위에서 다중 Writer 공존을 방지합니다. 외부에서 실행 중인 락을 임의 삭제하거나 파일시스템의 배타성 보장이 깨지는 경우까지 수학적으로 배제하는 것은 아닙니다.

### 3.3 Host 내부 직렬 작업 큐 체계 (Host-Internal Serial Queues)
단일 Writer Lock은 복수 Extension Host 간의 배타성을 보장할 뿐, 단일 Extension Host 내부에서 비동기 이벤트 루프로 도착하는 동시 IPC 요청을 직렬화하지 못합니다. 이를 해결하기 위해 Host 내부에 다음 2개의 독립 직렬 큐(FIFO Promise Chain)를 강제합니다:

1. **`SSoTTaskQueue` (SSoT 읽기 및 교체 전용 직렬 큐):**
   - **대상 작업:** ① SSoT 디스크 파일 읽기 및 JSON 파싱 (Working Copy 생성), ② Re-Bootstrap의 임시 파일 $\rightarrow$ SSoT 원자적 교체 (`renameSync`).
   - **상호 배타 보장:** SSoT 읽기·파싱 작업이 진행 중일 때 Re-Bootstrap 교체 작업이 끼어들지 못하며, 반대로 교체 작업 중에는 SSoT 읽기가 대기합니다.
   - **분석 계산의 분리 (Decoupled Analysis):** SSoT 파싱이 완료되어 독립 인메모리 Working Copy 객체가 반환된 즉시 큐 슬롯은 해제됩니다. 무거운 분석 알고리즘 계산은 `SSoTTaskQueue` 밖에서 독립 실행되므로, 분석이 오래 걸려도 Re-Bootstrap 작업이 영구 블로킹되지 않습니다.
2. **`OverlaySaveQueue` (오버레이 저장 전용 직렬 큐):**
   - **대상 작업:** `layout.json` 및 `user_graph.json`의 OCC Revision 검증, 후보 객체 검증, 디스크 기록 및 원자적 교체.
   - **동시 IPC 직렬화:** 웹뷰에서 마우스 드래그나 메타데이터 편집으로 인해 연속적으로 발행되는 비동기 저장 IPC 메시지를 도착 순서대로 엄격히 직렬화하여 처리합니다.

## 4. Re-Bootstrap 원자적 교체 및 오버레이 유효성 계약 (P0-2, P1-3 완결)

### 4.1 Re-Bootstrap 원자적 교체, 임시 파일 규약 및 내구성 계층 (P1-3 완결)

1. **임시 파일 생성 및 격리 규약 (Temp File Isolation Policy):**
   - 대상 파일과 반드시 **동일 디렉터리(동일 마운트/파일시스템)** 내에 생성하여 장치 간 이동 에러(`EXDEV`)를 방지합니다:
     $$\text{tmpPath} = \text{path.join}(\text{path.dirname}(\text{targetPath}), \text{`.\${path.basename(targetPath)}.\${process.pid}.\${Date.now()}.tmp`})$$
   - **실패 시 청소 보장 (Deterministic Cleanup on Error):** 임시 파일 생성, 기록, 동기화, 유효성 검증 중 에러 발생 시, 즉시 `try { fs.unlinkSync(tmpPath); } catch {}`를 실행하여 디스크에 잔여 임시 파일이 방치되지 않도록 보장합니다.
2. **SSoT Level 1 미션 크리티컬 내구성 절차 (POSIX 5-Step Sequence):**
   - ① 동일 파일시스템 내 임시 파일 생성 (`synapse_data/.project_state.json.<pid>.<time>.tmp`).
   - ② 데이터 전체 기록 후 파일 디스크립터 `fsyncSync(tmpFd)`.
   - ③ 임시 파일 닫기 및 JSON 파싱·필수 토폴로지 무결성 사전 검증.
   - ④ `fs.renameSync(tmpPath, 'synapse_data/project_state.json')` 실행 (가시성 원자적 교체).
   - ⑤ 부모 디렉터리 FD `fsyncSync(dirFd)` 실행 (디렉터리 엔트리 영속 내구성 확보).
   - **실패 상태의 엄격한 분리:** 4단계(rename) 성공 후 5단계(디렉터리 fsync)가 실패한 경우, rename 자체는 이미 성공했으므로 "기존 파일이 보존되었다"고 허위 보고하지 않으며, **"파일 가시성 교체 완료, 디렉터리 엔트리 내구성 미확인"** 상태로 명확히 분리 로깅합니다.
3. **오버레이 Level 2 프레젠테이션 세이프 내구성 계층 (Overlay Durability Level):**
   - 대상: `layout.json`, `user_graph.json`
   - UI 캔버스 조작(드래그, 줌, 패치 편집)은 빈번하게 발생하는 경량 작업이므로, 매 저장마다 부모 디렉터리 `fsync`를 강제할 경우 I/O 지연으로 인한 캔버스 버벅임이 발생합니다.
   - 따라서 오버레이는 **동일 파일시스템 임시 파일 기록 $\rightarrow$ 임시 파일 `fsyncSync` $\rightarrow$ `renameSync` 3단계 원자적 교체**만 수행하며, 부모 디렉터리 `fsync`는 의도적으로 생략(OS writeback에 위임)합니다.
   - 전원 차단 등 비정상 종료 시 최악의 영향은 최근 UI 드래그 좌표의 유실로 엄격히 한정되며, SSoT 구조 데이터는 완전하게 보호됩니다.
4. **Windows 보장 범위의 현실적 한정:**
   - 동일 파일시스템 내 `fs.renameSync` 호출을 통해 교체 작업의 성공·실패를 엄격히 구분합니다.
   - 교체 실패 시 기존 SSoT가 보존된 것이 확인된 경우에만 보존을 주장하며, 성공 반환을 디스크 플래시 내구성 보장과 동일시하지 않습니다.
   - 원자적 가시성은 지원 환경에서 별도 검증된 범위로 한정하며, POSIX의 부모 디렉터리 fsync나 열린 inode 유지와 동등한 보장을 주장하지 않습니다.
5. **SSoT 읽기·교체 직렬화 보장 (§3.3 `SSoTTaskQueue` 연계):**
   - 분석기의 SSoT 파일 전체 읽기 및 JSON 파싱(Working Copy 생성)은 §3.3의 `SSoTTaskQueue` 내부에서 단독 실행됩니다.
   - Re-Bootstrap의 원자적 파일 교체 또한 동일 큐에서 직렬 실행되므로, SSoT를 읽고 파싱하는 도중에 파일이 교체되는 TOCTOU 충돌이 원천 배제됩니다.
   - 파싱 완료 후 Working Copy는 독립 인메모리 객체가 되므로, 이후의 분석 연산은 큐 밖에서 Re-Bootstrap과 독립적으로 안전하게 실행됩니다.

### 4.2 오버레이 로드 필터링 및 컬렉션 단위 전수 저장·병합·보존 경계 (P0-2 완결)

1. **로드 시 비파괴적 필터링 (Graceful Filtering on Load):**
   - 캔버스 로드 시 현재 SSoT(`project_state.json`) 및 활성 `customNodes`와 대조하여 다음 항목을 **화면 표시에서만 자동 제외(Ignore & Filter)**합니다:
     - SSoT에서 사라진 노드에 대한 `modifiedNodes` 및 사라진 엣지에 대한 `modifiedEdges`.
     - **Custom Node Layout 좌표 필터링:** `layout.json`의 좌표 중, 현재 활성 상태인 SSoT 노드 및 활성 `customNodes`에 속하지 않거나, Tombstone(`deletedNodeIds`)에 포함된 노드의 좌표는 렌더링에서 완전히 제외합니다.
     - 사라진 클러스터 접힘 상태 및 양 끝점 중 하나라도 결손된 고아 Custom Edge 화면 표시 제외.
   - **디스크 원본 보존:** 로드 시점에는 디스크 상의 `user_graph.json`이나 `layout.json`을 절대 자동 삭제하거나 수정하지 않습니다 (일시적 브랜치 전환 시 사용자 편집 데이터 영구 보존).
2. **전체 컬렉션의 세부 저장 연산 의미 (Collection-Level Operations: UPSERT / REMOVE / PRESERVE):**
   일반 저장(Normal Save) 시 웹뷰에서 전달된 부분 변경 사항을 디스크 기존 컬렉션과 병합할 때, 컬렉션 전체를 덮어쓰거나 미포함 항목을 임의 삭제하는 것을 엄격히 금지하며 아래 규칙을 따릅니다:

   | 컬렉션 명 | 일반 저장 시 연산 의미 (Normal Save Semantics) | 디스크 미포함 항목 처리 (Untouched Entries) |
   |:---|:---|:---|
   | **`positions`** | **UPSERT:** 사용자가 드래그/이동한 노드 좌표만 갱신 | **PRESERVE:** 비활성 노드 좌표를 포함한 기존 좌표 디스크 보존 |
   | **`clusters`** | **UPSERT:** 사용자가 토글한 클러스터 접힘(`collapsed`) 상태 갱신 | **PRESERVE:** 현재 SSoT에 없는 클러스터라도 디스크 보존 (재수집 시 복원) |
   | **`modifiedNodes`** | **UPSERT:** 사용자가 수정한 노드 패치 갱신 / 패치 필드가 비면 제거 | **PRESERVE:** 수정되지 않은 다른 노드 메타데이터 패치 디스크 보존 |
   | **`modifiedEdges`** | **UPSERT:** 사용자가 수정한 엣지 패치 갱신 / 패치 필드가 비면 제거 | **PRESERVE:** 수정되지 않은 다른 엣지 메타데이터 패치 디스크 보존 |
   | **`customNodes`** | **UPSERT / REMOVE:** 추가·수정된 노드 갱신 / 삭제된 노드는 제거 | **PRESERVE:** 삭제 대상이 아닌 기존 Custom Node 디스크 보존 |
   | **`customEdges`** | **UPSERT / REMOVE:** 추가·수정된 엣지 갱신 / 삭제된 엣지는 제거 | **PRESERVE:** 삭제 대상이 아닌 기존 Custom Edge 디스크 보존 |
   | **`deletedNodeIds`** | **APPEND / REMOVE:** 새로 삭제된 ID 추가(Set 중복 제거) / 복원된 ID 제거 | **PRESERVE:** 기존 Tombstone 목록 디스크 보존 |
   | **`deletedEdgeIds`** | **APPEND / REMOVE:** 새로 삭제된 ID 추가(Set 중복 제거) / 복원된 ID 제거 | **PRESERVE:** 기존 Tombstone 목록 디스크 보존 |

3. **일반 저장과 명시적 정리 액션의 엄격한 분리:**
   - **일반 저장 (Normal Save):** 사용자의 일상적인 편집 작업 저장. 위 표의 `UPSERT / PRESERVE` 규칙만 적용되며, SSoT에 존재하지 않는 비활성 참조는 절대 자동 삭제되지 않습니다.
   - **명시적 정리 액션 (Explicit Clean-up Action):** 사용자가 UI에서 **"비활성 오버레이 정리(Clean-up Obsolete Overlays)"**를 명시적으로 클릭하고 확인한 경우에 한해, 현재 활성 SSoT 및 `customNodes`에 매핑되지 않는 비활성 `positions`, `clusters`, `modifiedNodes`, `modifiedEdges`를 일괄 영구 제거합니다.
4. **Layout 런타임 값 유효성 검증 (Runtime Validation on Save):**
   - `positions[*].x`, `positions[*].y`: 유한한 숫자(`Number.isFinite(v) === true`) 검사 필수. `NaN`, `Infinity`, 문자열 좌표는 즉시 거부.
   - `view.zoom`: 유한한 숫자이며 허용 범위(`0.001 <= zoom <= 10.0`) 검증.
   - `view.offset.x`, `view.offset.y`: 유한한 숫자(`Number.isFinite`) 검증.
   - `clusters[*].collapsed`: 엄격한 `boolean`(`typeof v === 'boolean'`) 검증. SSoT에 없는 클러스터 ID도 위 타입 규칙을 만족하면 디스크에 안전하게 보존.

## 5. `user_graph.json` 완전 스키마 및 Tombstone 정규화 계약 (P0-3, P1-1 완결)

### 5.1 스키마 정의 및 엄격한 런타임 타입 검증 (P0-3 완결)
```typescript
export interface NodeMetadataPatch {
    label?: string;                                               // 문자열 (1 ~ 256자)
    description?: string;                                         // 문자열 (0 ~ 2048자)
    customProperties?: Record<string, string | number | boolean>; // 원시 타입만 허용 (최대 50개 키)
}

export interface EdgeMetadataPatch {
    label?: string;                                               // 문자열 (0 ~ 256자)
    weight?: number;                                              // 유한한 숫자 (Number.isFinite 필수, >= 0)
    status?: 'proposed' | 'confirmed';
}

export interface CustomNode {
    id: string;                                                   // RFC 4122 UUID v4
    label: string;                                                // 필수 문자열 (1 ~ 256자)
    customProperties?: Record<string, string | number | boolean>; // data?: any 전면 배제 (최대 50개 키)
}

export interface CustomEdge {
    id: string;                                                   // RFC 4122 UUID v4 (중복 불가)
    from: string;                                                 // 활성 노드 ID (1 ~ 512자)
    to: string;                                                   // 활성 노드 ID (1 ~ 512자, from !== to)
    type?: string;                                                // 문자열 (0 ~ 64자)
    label?: string;                                               // 문자열 (0 ~ 256자)
}

export interface LayoutData {
    revision: number;                                             // Layout 전용 OCC revision (정수, >= 0)
    positions: Record<string, { x: number; y: number }>;
    view: { zoom: number; offset: { x: number; y: number } };
    clusters: Record<string, { collapsed: boolean }>;
}

export interface UserGraphData {
    revision: number;                                             // UserGraph 전용 OCC revision (정수, >= 0)
    customNodes: Record<string, CustomNode>;                      // key === CustomNode.id
    modifiedNodes: Record<string, NodeMetadataPatch>;             // SSoT 노드 메타데이터 패치
    deletedNodeIds: string[];                                     // 노드 Tombstone (중복 없는 ID 배열)
    
    customEdges: CustomEdge[];                                    // Custom Edge 목록 (from !== to, unique id)
    modifiedEdges: Record<string, EdgeMetadataPatch>;             // SSoT 엣지 메타데이터 패치 (id/from/to 수정 금지)
    deletedEdgeIds: string[];                                     // 엣지 Tombstone (중복 없는 ID 배열)
}
```

### 5.2 Revision OCC 생명주기, 오버플로 차단 및 직렬 재동기화 (P1-1 완결)

1. **Revision 정수 범위 및 오버플로 차단 (Overflow Guard):**
   - `revision`은 반드시 다음 조건을 만족해야 합니다:
     $$\text{revision} \in \mathbb{Z}, \quad 0 \le \text{revision} \le \text{Number.MAX\_SAFE\_INTEGER}$$
   - **오버플로 안전 가드:** 저장 연산 직전 반드시 다음 조건을 검사하며, 위반 시 저장을 즉시 거부(`REJECTED_REVISION_OVERFLOW`)합니다:
     $$\text{currentRevision} < \text{Number.MAX\_SAFE\_INTEGER}$$
   - `NaN`, `Infinity`, 음수, 소수점 수치는 런타임 파싱 단계에서 즉시 거부됩니다.
2. **Host 내부 직렬 큐를 통한 원자적 저장 (`OverlaySaveQueue`):**
   - 웹뷰에서 전달되는 동시 저장 IPC 요청은 §3.3의 `OverlaySaveQueue`에서 순차적으로 1개씩 직렬 처리됩니다.
   - ① **큐 진입 후 최신 Revision 재확인:** `expectedRevision === currentRevision` 확인. 불일치 시 저장을 거부하고 즉시 Resync Latch 발동.
   - ② **후보 객체 전수 검증:** 스키마, 타입, 문자열 길이, 참조 무결성 전수 검증.
   - ③ **동일 파일시스템 임시 파일 커밋:** `synapse_data/` 내 임시 파일에 `newRevision = currentRevision + 1` 기록 $\rightarrow$ `fsyncSync` $\rightarrow$ `renameSync`.
   - ④ **디스크 교체 완료 직후 메모리 갱신:** 디스크 교체 성공 후에만 메모리의 `currentRevision`을 `newRevision`으로 갱신 (실패 시 기존 revision 유지 및 임시 파일 삭제).
   - ⑤ 웹뷰로 저장 성공 응답 및 신규 revision 반환 후 다음 큐 항목 실행.
3. **Resync Latch 해제 조건의 결정론적 확정:**
   - 충돌 또는 통신 유실 감지 시 Host는 **Resync Latch**를 활성화하고, 디스크의 최신 오버레이 데이터와 최신 `currentRevision`을 웹뷰로 강제 푸시합니다.
   - **해제 조건:** 웹뷰가 푸시를 수신하여 로컬 상태를 갱신한 후 반환하는 `{ type: 'RESYNC_ACK', resyncRevision: number }` 메시지의 `resyncRevision`이 **Host의 현재 `currentRevision`과 엄격히 일치할 때만 Resync Latch를 해제**합니다:
     $$\text{Release Condition: } \text{ack.resyncRevision} === \text{host.currentRevision}$$
   - 과거 요청에 대한 지연된 ACK(`ack.resyncRevision < host.currentRevision`)는 무시되며 Latch가 유지됩니다.
   - 디스크 읽기 실패 또는 웹뷰 재초기화 중에는 Latch가 영구 유지(Fail-Closed)되어 불완전한 상태에서의 추가 저장을 원천 차단합니다.

### 5.3 Custom Graph 무결성, 참조 무결성 및 Tombstone 전수 검증 (P0-3 완결)

1. **문자열 길이 제한 및 `customProperties` 보안 한계:**
   - `label`: 노드 및 패치 1 ~ 256자, 엣지 0 ~ 256자.
   - `description`: 0 ~ 2048자.
   - `type`: 0 ~ 64자.
   - `from`, `to`: 1 ~ 512자.
   - **`customProperties` 엄격 제한:**
     - 키 개수: 최대 50개 (`Object.keys(v).length <= 50`).
     - 키 길이: 1 ~ 64자.
     - 값 타입: `string` (0 ~ 1024자), `boolean`, `number` (`Number.isFinite(v) === true`).
     - **프로토타입 오염 차단:** `__proto__`, `constructor`, `prototype` 키 포함 시 즉시 저장을 거부.
2. **Custom Edge 참조 무결성 강제 (Referential Integrity):**
   - **끝점 유효성:** Custom Edge의 `from`과 `to`는 반드시 **현재 활성 SSoT 노드이거나 활성 `customNodes`에 존재하는 노드**여야 합니다.
   - **Tombstone 끝점 거부:** `from` 또는 `to` 중 하나라도 `deletedNodeIds`에 포함되어 있으면 저장을 즉시 거부합니다.
   - **자가 루프 금지:** `from === to`인 Self-loop 엣지는 저장을 즉시 거부합니다.
   - **ID 중복 금지:** `customEdges` 배열 내에서 `id`는 유일해야 하며 중복 ID 존재 시 저장을 거부합니다.
3. **Tombstone 중복 배제 및 상호 배타성:**
   - **배열 중복 제거:** `deletedNodeIds` 및 `deletedEdgeIds`는 저장 시 `Set`을 통해 중복 항목을 제거하여 정규화합니다.
   - **상호 배타성 (Mutual Exclusivity):**
     - 어떤 ID가 `deletedNodeIds`에 존재하면, 동일 ID는 `customNodes` 또는 `modifiedNodes`에 공존할 수 없습니다.
     - 어떤 ID가 `deletedEdgeIds`에 존재하면, 동일 ID는 `customEdges` 또는 `modifiedEdges`에 공존할 수 없습니다.
4. **UUID 단회 사용 규약 (Prohibition of UUID Resurrection):**
   - 한 번 삭제되어 `deletedNodeIds` 또는 `deletedEdgeIds`에 등록된 Custom ID로 신규 Custom Node나 Custom Edge를 생성하는 것은 영구히 금지됩니다 (`REJECTED_REUSED_UUID`).
   - 사용자가 동일한 이름의 커스텀 노드를 다시 생성하더라도, 클라이언트는 반드시 완전히 새로운 RFC 4122 UUID v4를 발급해야 하며 이전 ID를 재활용할 수 없습니다.
5. **Custom Node 삭제와 연결 Custom Edge의 원자적 연쇄 삭제 트랜잭션 경계:**
   - ① **후보 객체 생성:** Node 삭제 요청 시, 메모리에서 단일 `UserGraphData` 후보 객체를 복제 생성.
   - ② **연쇄 삭제 수행:** 후보 객체의 `customNodes`에서 해당 노드를 제거하고 `deletedNodeIds`에 등록함과 동시에, 해당 노드를 `from` 또는 `to`로 참조하는 모든 Custom Edge를 `customEdges`에서 제거하고 `deletedEdgeIds`에 등록.
   - ③ **후보 객체 전수 검증:** 위 1~4항의 모든 무결성 규칙을 후보 객체에 대해 검증.
   - ④ **단일 임시 파일 커밋:** 검증 통과 시 동일 파일시스템 내 임시 파일 기록 $\rightarrow$ `fsyncSync` $\rightarrow$ `renameSync`로 일괄 커밋.
   - ⑤ **실패 시 격리:** 디스크 교체 실패 시 후보 객체는 폐기되며 기존 메모리 객체와 디스크 상태가 온전히 유지됨.
